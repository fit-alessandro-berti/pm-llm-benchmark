### 1. Several SQL queries are methodologically weak
The biggest issue is that the SQL is often **not robust enough for event-log analysis**.

- It repeatedly uses:
  ```sql
  MAX(CASE WHEN activity = 'X' THEN timestamp END)
  ```
  This is a major simplification. In process/event data, a claim can have multiple events of the same type. Using `MAX` may select the **last** occurrence, which can produce misleading intervals and fail to reflect the intended temporal-profile semantics.

- The queries generally do **not pair events properly in sequence**. For eventual relationships, you need to ensure you are measuring the relevant occurrence of the second event after the first event. The answer mostly does not do that.

### 2. Query logic is sometimes poorly aligned with the anomaly being checked
Examples:

- **AC query**:
  ```sql
  EXTRACT(EPOCH FROM (c_ts - a_ts)) < 7200 + 3600
  ```
  This flags anything under 3 hours, even though the profile average is 2 hours with 1 hour stdev. That is not really isolating suspicious cases; it may simply capture a large share of nominal cases.

- The same query uses:
  ```sql
  distinct_activities < 4
  ```
  This is a weak proxy for “missing intermediate steps.” It does **not** verify whether **E** or **P** occurred **between A and C**. A claim could have 4+ activities and still be anomalous, or fewer than 4 for a legitimate reason.

- **EN query** joins all E events to all later N events for the same claim, which can create duplicate/mispaired intervals if there are multiple E or N events.

### 3. One important assumption is unsupported and potentially invalid
In the adjuster correlation query:
```sql
LEFT JOIN adjusters a ON a.adjuster_id = CAST(p.resource AS INTEGER)
```
This assumes `claim_events.resource` contains an `adjuster_id` encoded as text. The schema does **not** say that. `resource` is only described as a `VARCHAR` representing the resource performing the activity. This makes the query speculative and potentially unusable.
