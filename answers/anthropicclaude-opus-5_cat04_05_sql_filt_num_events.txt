## Solution

The cleanest way in DuckDB is to use the `QUALIFY` clause with a windowed count — no subquery or join needed:

```sql
SELECT *
FROM event_log
QUALIFY COUNT(*) OVER (PARTITION BY case_id) <= 6
ORDER BY case_id, timestamp;
```

**How it works**

1. `COUNT(*) OVER (PARTITION BY case_id)` attaches the total number of events of a case to every row of that case (it does *not* collapse rows, unlike `GROUP BY`).
2. `QUALIFY` filters on that window value — it's evaluated *after* window functions, whereas `WHERE` is evaluated before them (so `WHERE COUNT(*) OVER (...) <= 6` would be illegal).
3. Every original column and every event of the surviving cases is returned untouched.

## Equivalent formulations

**A. Aggregate + `HAVING`, then semi-join back**

```sql
SELECT e.*
FROM event_log AS e
WHERE e.case_id IN (
    SELECT case_id
    FROM event_log
    GROUP BY case_id
    HAVING COUNT(*) <= 6
)
ORDER BY e.case_id, e.timestamp;
```

**B. CTE + explicit join** (handy if you also want the length as an output column)

```sql
WITH case_length AS (
    SELECT case_id, COUNT(*) AS num_events
    FROM event_log
    GROUP BY case_id
)
SELECT e.*, c.num_events
FROM event_log AS e
JOIN case_length AS c USING (case_id)
WHERE c.num_events <= 6
ORDER BY e.case_id, e.timestamp;
```

**C. `EXISTS` / anti-pattern-free version** (excludes long cases rather than including short ones)

```sql
SELECT e.*
FROM event_log AS e
WHERE NOT EXISTS (
    SELECT 1
    FROM event_log AS x
    WHERE x.case_id = e.case_id
    GROUP BY x.case_id
    HAVING COUNT(*) > 6
);
```

## Notes & gotchas

- **"More than six"  keep  6.** Use `<= 6` (not `< 6`); cases of exactly six events are retained.
- **Count events, not activities.** `COUNT(*)` counts rows/events. If you meant "cases with more than six *distinct* activities", swap in `COUNT(DISTINCT activity)`.
- **`NULL` case_ids** are grouped together as one "case" by `GROUP BY`/`PARTITION BY`. If that's undesirable, add `WHERE case_id IS NOT NULL` first.
- **Ordering** isn't required by the task, but `ORDER BY case_id, timestamp` keeps the log in a readable, trace-oriented form. Add a tie-breaker (e.g. a row-id or `activity`) if timestamps can be identical.
- **Performance:** the `QUALIFY` version scans the table once and sorts/hashes by `case_id`; the `IN`/join versions scan twice. For large logs the `QUALIFY` form is usually the fastest and is the most idiomatic DuckDB.
- **Persisting the result** (e.g. for further process-mining steps):

```sql
CREATE OR REPLACE TABLE event_log_filtered AS
SELECT *
FROM event_log
QUALIFY COUNT(*) OVER (PARTITION BY case_id) <= 6;
```
