# Log Skeleton for Order Fulfillment Process

## Assumptions about the underlying process

Based on the scenario, I assume the event log reflects the following behavior:

- **Normal control-flow order:** `RO  CA  RI  PI  [QC]  PO  GSL  D  IC  RP`
- **RO, CA, RI, PO, GSL, D, IC, RP** always occur **exactly once** per case.
- **PI** (Pick Items) may occur **once or twice** (split/batch picking).
- **QC** (Quality Check) is **optional** (skipped for trusted suppliers), occurring **0 or 1** times.
- No activities are mutually exclusive (every case follows the same overall backbone), so `never_together` is empty.

Because QC is optional, it can only appear as the *antecedent* activity in `always_before`/`always_after` constraints — nothing can be unconditionally guaranteed relative to an optional activity.

## Python Construction

```python
import itertools

activities = ['RO','CA','RI','PI','QC','PO','GSL','D','IC','RP']

# ---------------------------------------------------------
# 1. Activity Occurrences
# ---------------------------------------------------------
activ_freq = {
    'RO':  {1},
    'CA':  {1},
    'RI':  {1},
    'PI':  {1, 2},   # may pick in batches
    'QC':  {0, 1},   # optional check
    'PO':  {1},
    'GSL': {1},
    'D':   {1},
    'IC':  {1},
    'RP':  {1},
}

# ---------------------------------------------------------
# 2. Equivalence (activities that always occur the same
#    number of times -> here: all "exactly-once" activities)
# ---------------------------------------------------------
always_one = ['RO','CA','RI','PO','GSL','D','IC','RP']
equivalence = set(itertools.permutations(always_one, 2))

# ---------------------------------------------------------
# 3. Always Before / Always After
#    (based on fixed backbone order; QC handled specially
#    since it is optional)
# ---------------------------------------------------------
mandatory_seq = ['RO','CA','RI','PI','PO','GSL','D','IC','RP']

always_before = set()
always_after  = set()

for i, later in enumerate(mandatory_seq):
    for earlier in mandatory_seq[:i]:
        always_before.add((later, earlier))
        always_after.add((earlier, later))

# QC only as antecedent (it's optional -> cannot be guaranteed by others)
for earlier in ['RO','CA','RI','PI']:
    always_before.add(('QC', earlier))
for later in ['PO','GSL','D','IC','RP']:
    always_after.add(('QC', later))

# ---------------------------------------------------------
# 4. Never Together
#    (no exclusive alternative paths in this scenario)
# ---------------------------------------------------------
never_together = set()

# ---------------------------------------------------------
# 5. Directly-Follows
#    (only relations that hold in EVERY case)
# ---------------------------------------------------------
directly_follows = {
    ('RO', 'CA'),
    ('CA', 'RI'),
    ('RI', 'PI'),
    ('QC', 'PO'),   # whenever QC occurs, PO immediately follows
    ('PO', 'GSL'),
    ('GSL', 'D'),
    ('D', 'IC'),
    ('IC', 'RP'),
}
# Note: PI -> (QC or PO) is not deterministic (QC optional),
# so PI has no fixed directly-follows successor.

# ---------------------------------------------------------
# Final Log Skeleton
# ---------------------------------------------------------
log_skeleton = {
    'equivalence':        equivalence,
    'always_before':      always_before,
    'always_after':       always_after,
    'never_together':     never_together,
    'activ_freq':         activ_freq,
    'directly_follows':   directly_follows,
}
```

## Summary of key relations

| Constraint | Example | Meaning |
|---|---|---|
| `equivalence` | `(RO, D)` | Every order has exactly one dispatch |
| `always_before` | `(D, GSL)` | Dispatch always preceded by label generation |
| `always_after` | `(RO, D)` | Every received order is eventually dispatched |
| `directly_follows` | `(GSL, D)` | Label generation immediately precedes dispatch |
| `activ_freq` | `QC: {0,1}` | Quality check is optional |
| `never_together` | `{}` | No mutually exclusive activities in this process |

This dictionary (`log_skeleton`) fully captures the declarative behavior implied by the order fulfillment scenario, including optional quality checks, possible multiple picking events, and the strict backbone ordering of the remaining activities.
