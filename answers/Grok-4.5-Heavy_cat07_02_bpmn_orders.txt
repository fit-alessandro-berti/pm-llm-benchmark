**This is a BPMN 2.0 collaboration diagram** (with swimlanes) that models an end-to-end order fulfillment / order-to-invoice process. It shows how four organizational units interact via message flows, decisions, concurrency, data, compensation, and exception handling.

### Participants (Swimlanes)
- **Sales** (top)
- **Production**
- **Procurement**
- **Warehouse** (bottom)

### Sales Lane
- Triggered by a **timer start event** (“Monday morning”).
- A start event leads into a grouped region labeled **“Check customer’s order”**:
  - Task: *Check order for completeness*
  - Task: *Check if customer is already in the database*
  - **Exclusive (XOR) gateway**:
    - Path “Customer not in the database” → Task *Add customer to the database* (with a data association to the **database** data store)
    - Path “Customer in the database”
  - Paths converge at a second exclusive gateway.
- After the group: Task *Send order details* (this emits the message flow “Order details”).
- Intermediate **catching message event** “Product sent”.
- Task *Draft invoice*.
- End event.

### Production Lane
- **Message start event** “Order details arrive”.
- **Parallel (AND) split gateway**.
  - One branch: Task *Plan production*.
  - The other branch effectively waits on an intermediate **catching message event** “Material not faulty”.
- **Parallel (AND) join gateway** (synchronizes planning + material confirmation).
- Task *Manufacture product*.
- Intermediate **throwing message event** “Product complete”.

The parallel gateways implement concurrent planning while waiting for material confirmation from Procurement; manufacturing only proceeds once both are complete.

### Procurement Lane
- **Message start event** “Order details arrive”.
- Expanded **Sub-Process** “Material Compensation Subprocess”:
  - Start → Task *Order materials* (marked as compensatable) → End.
  - Compensation handler (dotted association): Task *Return material* (undoes the material order if compensation is triggered later).
- After the subprocess: Task *Check materials*.
  - Success path signals that materials are OK (feeds the “Material not faulty” message to Production).
  - Exception path (lightning-bolt / error intermediate event) leads to “Order cancelation” and an end event.
- There is also an intermediate event (timer/clock symbol) associated with the check, consistent with timeout or escalation handling.

### Warehouse Lane
- **Message start event** “Product complete”.
- Task *Send product*.
- Intermediate **throwing message event** “Product sent” (which notifies Sales).

### Key Message Flows (dashed lines between lanes)
- “Order details” — from Sales (*Send order details*) to both Production and Procurement message starts.
- Materials OK / “Material not faulty” — from Procurement (*Check materials* success) to Production’s catching event.
- “Product complete” — from Production to Warehouse.
- “Product sent” — from Warehouse back to Sales’ catching event.

### Notable BPMN Constructs Used
- **Timer start event** (periodic trigger).
- **Message start / intermediate catch & throw events** (inter-process communication).
- **Exclusive gateways** (customer exists? decision).
- **Parallel gateways** (concurrent planning + material confirmation).
- **Data store** + data association (customer database).
- **Compensation** (Order materials can later be undone by Return material).
- **Error / exception handling** and order-cancellation path in Procurement.
- Grouping / expanded subprocess for the customer-check and material-ordering logic.
- End events of various kinds (normal, cancellation-related).

### Overall Process Narrative
**Happy path**  
Every Monday morning Sales validates the order and ensures the customer is in the database (adding them if necessary). Order details are sent to Production and Procurement. Procurement orders materials (with the ability to compensate/return them later) and checks them. On success it signals Production. Production plans production in parallel with waiting for the material confirmation, then manufactures the product. Once the product is complete, Warehouse ships it and notifies Sales, which drafts the invoice.

**Exception / compensation path**  
If materials fail the check, Procurement can cancel the order. The compensation handler allows previously ordered materials to be returned. The parallel join in Production ensures manufacturing does not start without confirmed good materials.

This is a classic educational BPMN example that demonstrates multi-participant collaboration, message-based coordination, concurrency, data handling, and compensation/exception patterns in a single coherent order-processing scenario.
