## Explanation of Transformation Logic

**Case Identification:**
I grouped events by the **document/window/task** the user was actively working on, since each represents a distinct unit of work (a "case") rather than grouping strictly by timestamp or application. This produced five cases:
- **CASE-001**: Work on *Quarterly_Report.docx* (opened early, resumed later, then finished)
- **CASE-002**: Work on *Document1.docx* (interrupted midway by other tasks, then resumed)
- **CASE-003**: Handling one email thread ("Annual Meeting") in Chrome
- **CASE-004**: Reviewing *Report_Draft.pdf* in Adobe Acrobat
- **CASE-005**: Updating *Budget_2024.xlsx* in Excel

Even though the user interleaved tasks (e.g., left Document1 to handle email, then Excel, then returned to Document1), each case's events were reassembled using the **document identity** as the case key — this reflects how process mining typically defines a "case" as a specific business object/task instance, not merely a continuous time block.

**Activity Naming:**
Raw low-level actions were mapped to standardized, semantically meaningful activities:
- `FOCUS`  **Open Document** / **Reopen Document** (context-dependent)
- `TYPING`  **Edit Content** (in Word/Excel) or **Compose Reply** (in Email)
- `SAVE`  **Save Document**
- `CLOSE`  **Close Document**
- `SWITCH`  **Navigate to Application** / **Resume Editing** (used to signal transition between cases, attributed to the *destination* case since it initiates a new work episode)
- `CLICK`  Contextualized into **Open Email**, **Reply to Email**, **Send Email** based on the `Action=` attribute
- `SCROLL`  **Review Content** / **Review Email Content**
- `HIGHLIGHT`  **Highlight Key Text**

**Handling Interruptions (SWITCH events):**
Rather than treating `SWITCH` as a generic navigation log, I assigned each SWITCH event to the **case being entered** (the destination window/document), since it marks the start of a new work episode in that case. This avoids duplicate "open" events and cleanly shows how the user's attention moved between the five parallel tasks.

**Resulting Narrative:**
The event log tells a coherent story: the user began drafting a new document (Document1), was interrupted by an email needing a reply, then reviewed a PDF report, updated a budget spreadsheet, returned to finish Document1 (adding a budget reference), and finally resumed and completed the original Quarterly Report — illustrating realistic multitasking behavior fit for analyzing task-switching patterns, cycle times per document, and rework/interruption frequency.
