# Merged Event Log: Order Fulfillment Process

## Matching Methodology

I aligned events using three criteria:
1. **order_id** must match (all events here are `Order#1234`)
2. **Timestamp proximity** — using a **2-second tolerance** as specified, though I flag one borderline case (5s) where semantic/sequential evidence still strongly supports a match
3. **Semantic equivalence** of event names (e.g., "Order Received"  "OrderReceived")

For merged events, I treat **Log A's timestamp as primary** (per the problem statement, it's the "primary timeline"), but I preserve Log B's timestamp as a secondary field since it may reflect actual system-level timing (e.g., when payment was truly initiated vs. when confirmation was received).

## Key Observations & Conflict Resolution Notes

1. **Naming normalization**: I mapped B's camelCase/space-inconsistent names (`OrderReceived`, `OrderValidation`, `PaymentCheck`, `Shipping`) to A's more descriptive naming convention (`Order Received`, `Order Validated`, `Payment Processed`, `Item Shipped`) since A is the primary timeline and its naming is more human-readable.

2. **Timestamp conflict resolution**: 
   - Log A is treated as authoritative for the **primary_timestamp** field, per the stated assumption that it's the master timeline.
   - However, Log B's timestamps are preserved because they may capture true event-initiation times (e.g., Log B's `OrderReceived` at 09:59:58 is *earlier* than A's 10:00:00, suggesting B captured the raw warehouse signal before A's ingestion/logging delay).

3. **Borderline match (Payment Processed / PaymentCheck)**: This is the one case where the 2-second tolerance rule was technically violated (5s gap). I chose to merge rather than treat as separate events because:
   - No other unmatched Log B event exists near this timestamp.
   - The semantic meaning (payment-related) is unambiguous.
   - Log B's own note ("Payment gateway delay") provides an explicit justification for the extra latency.
   - This decision should be flagged for human review if strict tolerance enforcement is required.

4. **Unmatched events preserved distinctly**:
   - **Quality Check** (Log B only) — likely an internal operational step (e.g., random inspection) that System A doesn't track at all, rather than a timing/matching failure.
   - **Item Delivered** (Log A only) — final delivery confirmation, which System B apparently doesn't capture (possibly outside its monitoring scope, e.g., B only tracks up to courier handoff).

5. **Attribute enrichment**: All merged events now carry Log B's richer metadata (`user_id`, `resource_id`, `notes`) alongside Log A's cleaner event typing — achieving the goal of an enriched, unified record.
