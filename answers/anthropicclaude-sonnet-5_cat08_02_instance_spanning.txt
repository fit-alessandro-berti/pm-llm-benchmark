# Process Mining Strategy for Instance-Spanning Constraint Management in Order Fulfillment

## Section 1: Identifying Instance-Spanning Constraints and Their Impact

### 1.1 Data Preparation Requirements

Standard process mining tools assume case independence, so before analysis I would need to **enrich the event log** with resource-state and cross-case timing data:

- **Resource occupancy log**: Derive a secondary log tracking each resource instance (e.g., "Cold-Pack Station C1"–"C5") with START/END timestamps of occupation, computed from the case-level log. This converts the resource into a first-class "object" (aligning with Object-Centric Process Mining / OCPM principles) rather than an attribute.
- **Batch identifier propagation**: Where batch IDs aren't explicit, reconstruct them by clustering "Shipping Label Generation" events by Destination Region + time proximity, validating against any existing Batch ID field.
- **Concurrent-case snapshots**: Create a time-sliced table showing, for every timestamp, which cases are concurrently in "Packing" or "QC" with Hazardous=TRUE, enabling regulatory-limit analysis.

### 1.2 Constraint-Specific Identification & Metrics

**A. Shared Cold-Packing Stations**
- *Technique*: Resource-based mining — extract all Packing events with `Requires Cold Packing=TRUE`, map to specific Cold-Pack station IDs, and construct a **resource utilization timeline** (Gantt-style). Compute queue length over time (# orders with cold-packing requirement waiting vs. 5 stations occupied).
- *Metrics*:
  - **Cold-Pack Queue Time** = (Packing START timestamp)  (timestamp order became ready for packing, i.e., Item Picking COMPLETE)
  - **Station Utilization Rate** = busy-time / total-time per station
  - **Contention Index** = (# orders requiring cold-packing arriving within a rolling window) / (5 stations), flagging peak-hour saturation

**B. Shipping Batches**
- *Technique*: Group completed orders (QC COMPLETE) by Destination Region; identify the batch's "trigger event" (Shipping Label Gen COMPLETE for the batch) and compute per-order wait.
- *Metrics*:
  - **Batch Wait Time** = (Shipping Label Gen timestamp)  (QC COMPLETE timestamp) for each order
  - **Batch Formation Time** = time between first order ready and last order ready within a batch
  - **Batch Size Distribution** and **Batch Fill Efficiency** (actual batch size / target optimal batch size)

**C. Priority (Express) Handling**
- *Technique*: Detect **preemption events** — instances where a Standard order's activity START-COMPLETE is unusually long or shows a gap, correlated with an Express order's activity at the same resource occurring within that window. This requires resource-timeline overlay analysis, not just sequence mining.
- *Metrics*:
  - **Preemption Delay** = additional waiting time incurred by Standard orders when resource reassigned to Express orders (compare actual duration vs. historical median duration for that activity/resource combination)
  - **Express Advantage Ratio** = median cycle time (Standard) / median cycle time (Express) per activity
  - **Interruption Frequency** = count of Standard-order activity interruptions per resource per day

**D. Hazardous Material Regulatory Limit**
- *Technique*: Reconstruct concurrent-case snapshots (1.1) to compute, at each moment, the count of Hazardous=TRUE orders in Packing/QC. Identify moments where count = 10 (binding constraint) and subsequent queuing.
- *Metrics*:
  - **Regulatory Saturation Time** = total duration where concurrent hazardous count = 10 (blocking new hazardous orders from entering)
  - **Hazmat Queue Delay** = wait time for hazardous orders blocked by the cap
  - **Throughput Loss** = (theoretical throughput without cap)  (actual throughput), estimated via simulation baseline

### 1.3 Differentiating Within-Instance vs. Between-Instance Waiting

This is the crux of instance-spanning analysis. I would decompose total cycle time per activity as:

```
Total Duration = Active Processing Time + Within-Instance Wait + Between-Instance Wait
```

- **Active Processing Time**: STARTCOMPLETE for the activity itself, assuming immediate resource availability.
- **Within-Instance Wait**: Delay attributable to the order's own attributes (e.g., missing information, rework, waiting on upstream step completion within the *same* case) — identified by comparing an order's activity duration against the **resource-free baseline duration** (median duration when resource was idle immediately prior).
- **Between-Instance Wait**: The residual — calculated as `Actual Time-to-Start  Time Order Became Eligible`, cross-referenced with the resource occupancy log to confirm the resource was occupied by a *different* case, or the order was held pending batch completion, or blocked by the hazmat cap.

Practically, I'd build a **"cause tag"** for every wait period:
- `WAIT_RESOURCE_BUSY_OTHER_CASE` (cold-pack contention)
- `WAIT_BATCH_FORMATION`
- `WAIT_PREEMPTED_BY_EXPRESS`
- `WAIT_REGULATORY_CAP`
- `WAIT_WITHIN_CASE` (residual/unexplained, own-case bottleneck)

This tagging, done programmatically by joining the case log with the resource-occupancy log and batch reconstruction, allows Pareto analysis of **which constraint contributes most to total delay** — essential for prioritizing intervention.

## Section 2: Analyzing Constraint Interactions

Instance-spanning constraints rarely act in isolation; their **interaction effects** often dominate over individual effects.

**Interaction 1: Express Priority × Cold-Packing Scarcity**
An Express order requiring cold-packing competes for an already-scarce resource (5 stations). If Express orders preempt Standard orders *at* cold-pack stations, this compounds contention — a Standard cold-pack order isn't just waiting for "a station" but is specifically vulnerable to being bumped repeatedly. Process mining approach: filter the resource-occupancy timeline to Cold-Pack stations only, and measure preemption frequency specifically within this resource pool vs. standard packing stations. I'd expect (and should verify via data) a **disproportionately higher preemption rate** at cold-pack stations due to the double constraint (scarcity + priority rule).

**Interaction 2: Batching × Hazardous Material Cap**
If a shipping batch for "South" region contains several hazardous orders, and those orders get queued at QC due to the 10-concurrent cap, the **entire batch's departure is delayed**, not just the hazardous orders — because batching requires *all* orders in the batch to reach Shipping Label Gen. This creates a **cascading delay** where a regulatory constraint on a subset of orders penalizes non-hazardous orders in the same batch. Detection: cross-reference batch composition (via Destination Region + Batch ID) with Hazardous flag; compute correlation between "% hazardous orders in batch" and "batch wait time."

**Interaction 3: Express Preemption × Regulatory Cap**
If an Express hazardous order preempts a Standard hazardous order at QC, but the facility is already at the 10-concurrent hazmat limit, the preemption doesn't just delay the Standard order's *processing* — it may cause the Standard order to be push out of the "active" hazmat slot entirely, forcing it to re-queue behind other hazmat orders, effectively suffering a double penalty.

**Why This Matters for Optimization:**
Optimizing each constraint independently can create **whack-a-mole effects** — e.g., increasing cold-pack capacity might reduce cold-pack queueing but increase the number of concurrent hazardous orders in Packing/QC, pushing against the regulatory cap more often and creating a *new* bottleneck downstream. Effective strategy design requires **joint simulation** (Section 4) rather than isolated fixes, and metrics should include **cross-constraint correlation coefficients** (e.g., correlation between cold-pack queue length and hazmat-cap saturation events) to detect these coupling effects empirically before intervening.

## Section 3: Constraint-Aware Optimization Strategies

### Strategy 1: Predictive Dynamic Slot Reservation for Cold-Packing (Addresses: Cold-Packing Scarcity + Express Priority Interaction)

**Changes Proposed:**
- Move from pure FCFS/preemption at cold-pack stations to a **hybrid reservation system**: use historical arrival-rate data (mined from Item Picking COMPLETE events with `Requires Cold Packing=TRUE`) to forecast near-term demand (e.g., next 30-min window) using simple time-series forecasting (moving average or ARIMA on hourly cold-pack demand).
- Reserve 1 of the 5 stations exclusively for Express cold-pack orders during forecasted high-demand windows, and dynamically release it to Standard orders when Express demand forecast is low — avoiding blind preemption of in-progress Standard orders.
- Cap preemption to **only allow interruption if remaining processing time on the Standard order's activity is below a threshold** (mined from historical activity-duration distributions), preventing costly "restart" preemptions.

**Data Leverage**: Historical duration distributions per activity/resource, arrival rate seasonality (peak-season patterns visible in 3-month log), preemption cost analysis (Section 1's Preemption Delay metric).

**Expected Outcome**: Reduced variance in Standard order cold-pack wait times, reduced total preemption events, while maintaining Express SLA — directly targets the compounding effect identified in Interaction 1.

### Strategy 2: Hybrid Time/Size-Triggered Dynamic Batching with Hazmat-Aware Composition (Addresses: Batching Delay + Batching/Hazmat Interaction)

**Changes Proposed:**
- Replace static "wait until batch full" logic with a **dual-trigger rule**: release batch when EITHER target size is reached OR a maximum wait time (mined as the 80th percentile of historical acceptable Batch Wait Time before SLA breach) elapses — whichever comes first.
- For batches containing hazardous orders, apply a **"fast-track hazmat sub-batching"** rule: cap the number of hazardous orders routed into a single batch cycle to reduce the probability that the batch's completion is gated by the 10-concurrent QC constraint. Route excess hazardous orders to the next batch cycle proactively rather than reactively queuing.

**Data Leverage**: Mine optimal batch size vs. wait-time tradeoff curves per region (from historical Batch Size Distribution and Batch Wait Time metrics); mine correlation between %hazmat-in-batch and batch delay (Interaction 2) to set the hazmat sub-batch cap empirically.

**Expected Outcome**: Reduces average Batch Wait Time by eliminating indefinite waits for slow-forming batches, and decouples hazmat-driven delays from unrelated orders in the same region/batch.

### Strategy 3: Regulatory-Aware Sequencing with "Hazmat Slot" Scheduling (Addresses: Regulatory Cap + all interactions involving Hazmat)

**Changes Proposed:**
- Implement a **virtual token/slot system**: exactly 10 tokens exist for hazardous orders across Packing+QC combined. An order cannot START Packing or QC without acquiring a token; the token releases when the order completes QC (not Packing), since the constraint spans both activities.
- Prioritize token allocation using a **weighted rule**: Express hazardous orders get priority for tokens, but a fairness cap prevents Standard hazardous orders from being starved (e.g., max 3 consecutive token grants to Express before granting to oldest-waiting Standard).
- Feed real-time token-availability forecasts (based on average Packing+QC duration for hazardous orders, mined from log) into the batching logic (Strategy 2) so batch composition decisions account for anticipated hazmat token availability — directly closing the loop on Interaction 2 and 3.

**Data Leverage**: Mine average combined Packing+QC duration for hazardous orders to estimate token turnover rate; use Regulatory Saturation Time metric to identify peak periods requiring proactive load-leveling (e.g., staggering hazardous order release from Item Picking).

**Expected Outcome**: Maintains 100% regulatory compliance (hard constraint never violated) while minimizing Hazmat Queue Delay and preventing cascading batch delays, by making the previously invisible constraint explicit and schedulable.

### Strategy 4 (Bonus — Process Redesign): Decouple QC from Batch-Gating

**Changes Proposed**: Since Shipping Label Generation is currently the batching gate, but QC is also constrained by the hazmat cap, consider redesigning so that orders can complete QC and be held in a **"ready-to-ship" buffer state** independent of the resource that generates labels — allowing QC resources to free up (and release hazmat tokens) as soon as QC completes, rather than being conflated with batch/label timing. This is a minor structural change (adding an explicit buffer state in the log/process) that decouples resource release from downstream batching logic.

## Section 4: Simulation and Validation

**Approach**: Build a **Discrete-Event Simulation (DES)** model calibrated directly from the process-mined event log (not from assumed distributions), using tools like CPN Tools, AnyLogic, or a custom SimPy model, integrated with process mining outputs (e.g., via PM4Py for log-based parameter extraction).

**Model Calibration from Log**:
- Activity duration distributions: fit empirical distributions (not just averages) per activity, per order type, per resource, from the log — capturing variability, not just means.
- Arrival process: model order arrivals as a non-homogeneous Poisson process with rate function fitted to historical hourly/seasonal arrival patterns (critical for peak-season testing).
- Resource pools: explicitly model 5 Cold-Pack stations, N standard stations, QC staff pool — as finite, shared resources with FIFO/priority queues matching real dispatch logic.
- **Batching logic**: implement as a stateful process (accumulator per region) replicating current OR proposed dual-trigger logic.
- **Hazmat token pool**: implement as a semaphore with capacity 10, exactly mirroring the regulatory constraint, shared across Packing and QC.
- **Preemption logic**: model resource seizure/release with interrupt handling for Express orders, calibrated to observed Preemption Delay distributions.

**Validation Before Testing Strategies**:
- Run the "as-is" simulation model and compare output KPIs (throughput, average cycle time, queue lengths at cold-pack, batch wait times, hazmat saturation frequency) against the **actual historical log metrics** computed in Section 1. Require statistical closeness (e.g., KS-test on cycle time distributions) before trusting the model for what-if analysis.

**Testing Proposed Strategies**:
- Run each strategy (Sections 3.1–3.4) as a separate simulation scenario, ideally with multiple replications to capture stochastic variability, and under both **normal and peak-season load** (calibrated arrival rates).
- Focus outputs specifically on:
  - Whether the hazmat cap is *ever* violated (must be zero — hard constraint check)
  - Distribution shift in Cold-Pack Queue Time and Preemption Delay (Strategy 1)
  - Distribution shift in Batch Wait Time and %orders exceeding SLA (Strategy 2)
  - Token utilization/wait time under Strategy 3 vs baseline
  - Sensitivity analysis: vary Express order % and hazmat order % to test robustness of strategies under different peak-season mixes

**Trade-off Analysis**: Explicitly report Pareto trade-offs (e.g., Strategy 1 may improve Standard cold-pack wait but slightly increase average Express wait) so decision-makers can weigh SLA priorities.

## Section 5: Monitoring Post-Implementation

### 5.1 Real-Time Process Mining Dashboards

**Dashboard 1 — Resource Contention Monitor (Cold-Packing)**
- Live queue length and utilization % per Cold-Pack station
- Rolling 7-day trend of Cold-Pack Queue Time (median, p90)
- Preemption event counter (Standard orders interrupted per day) with drill-down to affected case IDs

**Dashboard 2 — Batching Efficiency Monitor**
- Real-time batch-in-progress view per region: current size, elapsed wait, trigger status (size vs. time trigger imminent)
- Batch Wait Time trend, segmented by %hazmat composition, to verify Interaction 2 mitigation
- Batch Fill Efficiency over time

**Dashboard 3 — Regulatory Compliance Monitor**
- Live count of concurrent hazardous orders in Packing+QC (the "token" gauge) — hard alert if approaching 10
- Historical Regulatory Saturation Time trend (should decrease or stay flat while throughput increases — proving efficiency gain without compliance risk)
- Hazmat Queue Delay trend

**Dashboard 4 — Overall Flow / Conformance Dashboard**
- End-to-end cycle time distribution (Standard vs Express), with control charts (e.g., CUSUM) to detect drift
- Conformance checking against the new target process model (including new batching/token rules) to detect deviations — e.g., using token-replay conformance to verify the process is actually operating under the new rules, not silently reverting to old behavior
- Automated cause-tagging (from Section 1.3) recomputed weekly to track shift in the Pareto breakdown of `WAIT_*` categories — the key proof point that between-instance wait specifically has decreased

### 5.2 Specific Constraint-Effectiveness KPIs

| Constraint | Pre-Implementation Baseline | Target Post-Implementation KPI |
|---|---|---|
| Cold-Packing | Median queue time, preemption count/day | 20-30% queue time;  preemption events for Standard orders |
| Batching | Median/p90 batch wait time |  p90 wait time;  batch fill efficiency |

### 5.3 Feedback Loop

Establish a **quarterly re-mining cycle**: re-run the full Section 1 analysis on fresh log data post-implementation to detect concept drift (e.g., changing order mix, new seasonal patterns) and recalibrate simulation model parameters and token/threshold rules accordingly — treating this not as a one-time fix but an ongoing constraint-aware process management practice.
