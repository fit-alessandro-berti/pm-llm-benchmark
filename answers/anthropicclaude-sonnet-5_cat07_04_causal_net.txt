# Business Process Model Visualization

This is a **workflow/process model diagram** (resembling a Workflow net or Petri net-based notation) depicting a request-handling process, along with a legend explaining the routing constructs used.

## Main Process Flow

The process begins and ends with these key activities:
- **a (register request)** – starting point
- **z (end)** – terminal point

**Middle activities** (parallel/alternative paths for examining requests):
- **b** – examine thoroughly
- **c** – examine casually
- **d** – check ticket
- **e** – decide (convergence point)
- **f** – reinitiate request (loop-back activity)

**Final branch** (after the decision):
- **g** – pay compensation
- **h** – reject request

## Flow Logic

1. From **a**, the process splits (using an OR-split, based on the connector dots) into paths leading to **b**, **c**, and **d** — representing different examination methods.
2. These paths converge at **e (decide)**.
3. From **e**, the flow can also loop back to **f (reinitiate request)**, which cycles back to re-examine the request (creating a loop).
4. After **e**, the process splits into either **g (pay compensation)** or **h (reject request)**.
5. Both **g** and **h** converge at **z (end)**.

## Legend (Bottom Right Box)

The inset explains the **routing/gateway symbols** used at connection points (shown as black dots) on the arcs:

| Split Type | Meaning |
|---|---|
| **XOR-split** | Exactly one outgoing branch is taken |
| **AND-split** | All outgoing branches are taken (parallel) |
| **OR-split** | One or more outgoing branches are taken |

| Join Type | Meaning |
|---|---|
| **XOR-join** | Triggered when any one incoming branch completes |
| **AND-join** | Triggered only when all incoming branches complete |
| **OR-join** | Triggered based on a combination of incoming branches |

## Purpose

This diagram likely illustrates a **complaint-handling or claims process**, showing how a request is registered, examined via multiple possible methods, decided upon, and resolved either through compensation or rejection — with a provision to reinitiate the process if needed. The visualization demonstrates the use of formal control-flow patterns (XOR/AND/OR splits and joins) common in **business process modeling** and **workflow management systems**.
