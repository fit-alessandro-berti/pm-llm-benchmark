# Process Mining Strategy for Instance-Spanning Constraint Optimization in Order Fulfillment

## 1. Identifying Instance-Spanning Constraints and Their Impact

Standard process mining (discovery, conformance, performance analysis) is built around **single-case perspectives**. To detect instance-spanning constraints (ISCs), the event log must be **enriched and re-modeled** so that cross-case relationships become explicit, queryable attributes.

### 1.1 Log Enrichment Steps

Before analysis, derive additional attributes for every event:

| Derived Attribute | How Computed | Purpose |
|---|---|---|
| `arrival_time` at step | timestamp of previous activity's COMPLETE | Baseline for waiting time |
| `waiting_time` | `start_time`  `arrival_time` | Isolates queueing/delay vs. processing |
| `resource_busy_with` | Cross-case lookup: which other Case ID occupied the same resource during the waiting interval | Direct evidence of resource contention |
| `batch_id` / `batch_peers` | Join on Destination Region + time window before Shipping Label Gen | Identify co-dependent cases |
| `concurrent_hazmat_count(t)` | Running count of cases with Hazardous=TRUE currently in Packing/QC state at time t | Regulatory cap tracking |
| `interruption_flag` | Detected gap/re-start pattern within a single activity instance (START…pause…resume…COMPLETE) correlated with another case's START on the same resource | Evidence of preemption |

This transforms the log from a "per-case" table into a **multi-instance event stream** that can be queried for cross-case dependencies — essential because classical tools (Petri nets, BPMN discovery) assume case independence.

### 1.2 Constraint-Specific Analysis

**a) Shared Cold-Packing Stations**
- Build a **resource timeline** (Gantt-style reconstruction) for each of the 5 Cold-Packing stations from START/COMPLETE pairs.
- Compute **utilization %** (busy time / available time) per station per hour/day — identify saturation windows (peak season).
- Compute **queue length over time**: count of cold-pack-required orders whose previous activity is COMPLETE but Packing START hasn't occurred, at each timestamp.
- Metric: **Cold-Pack Waiting Time (CPWT)** = Packing START  Item Picking COMPLETE, filtered to `Requires Cold Packing = TRUE`. Report mean, P90, P95 (tail matters more for SLA breach).

**b) Shipping Batches**
- Group completed orders (QC COMPLETE) by Destination Region and time window ending at the shared Shipping Label Gen timestamp/Batch ID.
- Metric: **Batch Wait Time (BWT)** = Shipping Label Gen timestamp  own QC COMPLETE timestamp, per order.
- Metric: **Batch Formation Time** = Shipping Label Gen timestamp  earliest QC COMPLETE among batch peers (this quantifies how much the *fastest* order in a batch was penalized waiting for *stragglers*).
- Metric: **Batch Size Distribution** and **Straggler Contribution** (identify which order type/attribute most often is the last-to-arrive, dragging the batch).

**c) Priority/Express Handling**
- Detect interruption by finding activity instances where duration (COMPLETE  START) significantly exceeds the historical baseline duration for that activity/resource **and** an Express-order START event occurs on the same resource within that window.
- Metric: **Preemption-Induced Delay (PID)** = actual duration  expected (median/percentile) duration for standard orders whose processing overlapped an express arrival.
- Metric: **Express Advantage** = median end-to-end time for Express vs Standard orders at the same step (validates SLA differentiation is actually occurring).
- Use **statistical control-group comparison**: standard orders processed *without* concurrent express arrival vs. *with* — the delta isolates the priority-interruption effect from ordinary variability.

**d) Hazardous Material Regulatory Cap**
- Reconstruct `concurrent_hazmat_count(t)` as a time series across Packing+QC combined (since the rule spans both activities).
- Metric: **Cap-Saturation Time** = total time where count = 10 (facility at hard limit).
- Metric: **Hazmat Queueing Delay** = difference between when a hazmat order *could* start (resource free) vs when it *actually* started (blocked by the global cap) — this is purely a between-instance delay since the local resource may be idle while the regulatory gate is closed.
- Metric: **Throughput Loss** = comparison of hazmat order completion rate during saturated periods vs. non-saturated periods.

### 1.3 Within-Instance vs. Between-Instance Waiting Decomposition

This is the crux of ISC analysis. For every waiting gap (`arrival_time`  `start_time`), classify it using a **decision procedure**:

1. **Resource idle at arrival?** If yes  no contention; delay is due to *scheduling/batch/administrative* lag (between-instance, non-resource) or system latency (within-instance overhead).
2. **Resource busy at arrival, with another Case ID?**  **Between-instance: resource contention.** Attribute the wait to that other case (and tag whether that case was Express, causing preemption, or simply queued ahead by FIFO).
3. **Resource idle, but case is a hazmat order and global count = 10?**  **Between-instance: regulatory cap block.**
4. **Case is complete but waiting on `batch_peers` not yet finished?**  **Between-instance: batching dependency.**
5. **None of the above, and duration itself is long relative to peers?**  **Within-instance: genuine processing time variability** (e.g., a slow picker, a complex order) — this is a *service time* issue, not a *queueing* issue, and should be excluded from ISC-focused optimization (it needs separate root-cause, e.g., training/skill).

This decomposition should be visualized as a **stacked waterfall of total lead time** per case: Processing Time + Resource-Contention Wait + Batch Wait + Regulatory-Cap Wait + Other. This makes the relative contribution of each ISC immediately visible to stakeholders and prioritizes optimization effort.

## 2. Analyzing Constraint Interactions

Instance-spanning constraints rarely act independently; they **compound**, and optimizing one in isolation can create emergent bottlenecks elsewhere. Key interactions to analyze (via joint filtering/correlation in the enriched log):

**Interaction 1: Express + Cold-Packing  Amplified Queue Variance**
When an express order requiring cold-packing arrives and all 5 stations are busy, it may preempt a standard order mid-processing. This:
- Extends the standard order's occupancy of the station (context-switch overhead), *increasing* effective station busy-time and worsening queue length for the *next* orders (express or standard).
- If the preempted standard order is *also* hazmat-flagged, its extended Packing duration inflates `concurrent_hazmat_count(t)`, pushing the facility toward the regulatory cap sooner than a simple hazmat-arrival-rate model would predict.
- **Finding this requires joint filtering**: filter events where `interruption_flag=TRUE AND Requires_Cold_Packing=TRUE`, then check downstream `concurrent_hazmat_count` at that time.

**Interaction 2: Batching + Hazmat Cap  Batch Delay Cascades**
If several orders bound for the same region are hazmat-flagged, and the cap throttles how many can be in Packing/QC simultaneously, these orders finish QC in a staggered, capacity-gated sequence rather than in parallel. Because batching requires *all* peers to reach QC COMPLETE, the batch's dispatch time becomes gated by the *slowest* hazmat order in the group — meaning **non-hazmat peers in the same batch inherit a delay they had no part in causing.**
- Detect via: correlate `Batch Wait Time` with `% hazmat orders in batch` — expect a positive correlation if this interaction is material.

**Interaction 3: Priority vs. Regulatory Cap  Policy Conflict**
Express hazmat orders are *supposed* to be expedited, but the hard 10-concurrent cap applies uniformly. If the cap is already saturated with standard hazmat orders, an express hazmat order queues *despite* its priority flag — the regulatory constraint silently overrides the business priority rule. This is a **policy inconsistency** that needs an explicit resolution mechanism (see Strategy 3 below), not just discovery.

**Why This Matters for Optimization:**
- Fixing Cold-Packing contention alone (e.g., adding a 6th station) may simply shift the bottleneck to the hazmat cap or batch synchronization, yielding a disappointing net improvement — a classic **local optimization / global sub-optimization trap** in constrained systems (Theory of Constraints logic applies directly here).
- Any optimization must be evaluated on **system-level KPIs** (end-to-end cycle time, on-time shipment %) not just the local metric of the constraint being addressed, and ideally tested via simulation (Section 4) before rollout, since interactions are often non-linear and not visible from single-constraint analysis alone.

## 3. Constraint-Aware Optimization Strategies

### Strategy 1: Predictive Reserved-Capacity Policy for Cold-Packing Stations

- **Addresses:** Cold-Packing contention; Priority-Handling interaction with cold-packing.
- **Changes:** Instead of a pure FIFO/free-for-all pool of 5 stations, dynamically reserve 1–2 stations exclusively for Express+Cold-Pack orders during predicted peak windows, with the reservation ratio adjusted by time-of-day/day-of-week using patterns mined from historical arrival rates. Implement **preemption-only-if-beneficial** logic: only interrupt a standard order if its *remaining* expected processing time (estimated from historical duration distributions by resource/order type) exceeds a threshold — otherwise let it finish, avoiding costly context-switch overhead.
- **Data leverage:** Fit an arrival-rate model (e.g., non-homogeneous Poisson) per hour from log timestamps; use queueing theory (M/M/c with priority classes) calibrated on historical utilization to size the reserved pool; use empirical remaining-time distributions to set the preemption threshold.
- **Expected outcome:** Reduced P90/P95 wait time for express cold-pack orders; reduced number of costly preemptions (fewer, more justified interruptions); controlled increase (not explosion) in standard-order wait time — measured via before/after CPWT and PID metrics.

### Strategy 2: Hybrid Dynamic Batch-Triggering with Predictive Membership

- **Addresses:** Batching delays; interaction with hazmat-driven straggler orders.
- **Changes:** Replace static "wait until all regional orders arrive" batching with a **hybrid trigger**: dispatch when batch reaches a target size OR a maximum wait threshold is hit (mined from historical BWT distributions to balance route-cost savings against delay cost). Additionally, use a **predictive completion model** (simple regression/classification on order attributes — hazmat flag, cold-pack flag, current queue depths) to forecast which orders will likely be late; exclude forecasted-late orders from the current batch proactively (route to the next batch) rather than letting them silently delay the whole batch.
- **Data leverage:** Historical BWT and Batch Formation Time distributions per region; correlation analysis between hazmat/cold-pack flags and lateness (established in Section 2); discrete-event simulation to tune size/time thresholds (Section 4).
- **Expected outcome:** Reduced tail (P90/P95) batch wait time, especially for non-hazmat orders currently penalized by hazmat stragglers; modest increase in shipping frequency (slightly smaller average batch) traded for major reduction in delay variance — quantify trade-off via route-cost-per-order vs. delay-cost-per-order.

### Strategy 3: Token-Based Admission Control for Hazmat Concurrency, with Reserved Express Lane

- **Addresses:** Regulatory hazmat cap; conflict between priority policy and hard compliance limit.
- **Changes:** Implement an explicit **semaphore/token system**: 10 tokens total govern entry into Packing/QC for hazmat orders. Reserve 2 tokens exclusively for Express hazmat orders (ratio tuned from historical express/standard hazmat mix) so express orders are never fully blocked by standard hazmat congestion, while guaranteeing the hard cap of 10 is never violated. Apply an **aging-aware priority queue** (priority + wait-time bonus) for the standard hazmat pool to prevent starvation.
- **Data leverage:** Mine historical proportion and arrival pattern of express vs. standard hazmat orders; use processing-time distributions to test different token-split ratios in simulation; validate compliance is maintained under all tested loads.
- **Expected outcome:** Elimination of "hidden" express delays caused by the cap (addressing the Section 2 policy conflict), maintained 100% regulatory compliance, improved P95 wait time for hazmat orders overall due to better queue discipline (vs. simple FIFO).

### Strategy 4 (Capacity/Redesign Option): Cross-Trained Flexible Cold-Packing Surge Capacity

- **Addresses:** Cold-Packing contention at its root (capacity, not just scheduling).
- **Changes:** Cross-train a subset of standard-packing staff to operate cold-packing equipment; during forecasted peak windows (identified via seasonal arrival-rate mining), temporarily convert 1–2 standard stations to cold-pack-capable, informed by a demand forecast model built on 3 months of historical seasonal/peak data.
- **Data leverage:** Time-series forecasting of cold-pack order volume (from log) to trigger surge staffing; cost-benefit analysis of cross-training investment vs. wait-time reduction achieved in simulation.
- **Expected outcome:** Structural reduction in cold-pack queue length during peak season, reducing reliance on preemption (Strategy 1) altogether during the worst periods.

## 4. Simulation and Validation

Given the interactions identified in Section 2, changes should **not** be deployed directly to production; a **calibrated discrete-event simulation (DES)** informed by the process-mined model is essential.

### 4.1 Model Construction
- Use a DES/CPN tool (e.g., CPN Tools, AnyLogic, Simul8, or ProM's simulation plugins) to build a model where:
  - **Cases arrive** per empirically fitted inter-arrival distributions (segmented by Order Type, Cold-Pack flag, Hazmat flag, Region) — extracted directly from the log.
  - **Activities** have durations sampled from fitted empirical distributions (not just averages — capture variance/tails, since queueing behavior is highly sensitive to variance).
  - **Resources** are modeled as explicit finite pools (5 Cold-Pack stations, N standard stations, QC staff) with configurable queue disciplines (FIFO, priority, preemptive-resume).
  - **A global semaphore/counter object** enforces the hazmat concurrency cap across Packing+QC jointly (not per-activity), exactly mirroring the regulatory rule.
  - **A batching module** that accumulates completed orders by region and releases them per the (current or proposed) trigger logic.

### 4.2 Calibration/Validation
- Run the baseline (as-is policy) simulation and compare its output KPIs (waiting time distributions, queue lengths, batch sizes, throughput) against the **real historical log** using statistical tests (Kolmogorov–Smirnov for distributions, MAPE for point KPIs). Only proceed to what-if testing once the baseline model reproduces historical behavior within acceptable tolerance — this validates that the model faithfully captures the ISCs, not just average-case behavior.

### 4.3 What-If Experimentation
- Inject each proposed strategy (reserved cold-pack capacity, hybrid batch trigger, token-based hazmat admission) as alternate policy modules.
- Run **Monte Carlo replications** at multiple load levels (normal, peak-season) to capture stochastic variability, not single-run point estimates.
- Use **Design of Experiments (DOE)** to sweep key parameters (e.g., number of reserved stations: 1 vs 2; batch max-wait threshold: 20 vs 30 vs 45 min; token split: 1/9 vs 2/8 vs 3/7) and identify near-optimal configurations via response-surface analysis.
- **Critical validation check:** confirm the simulated hazmat concurrent count *never* exceeds 10 under any tested configuration — a hard constraint check, not just a KPI to minimize.

### 4.4 Focus Areas for Model Fidelity
- **Resource contention:** explicit finite-capacity queues, not infinite-server approximations.
- **Batching delays:** correct "wait for all members" logic, not simple fixed delays.
- **Priority interruption:** proper preemptive-resume semantics with realistic context-switch cost (not free interruption).
- **Regulatory limits:** a hard blocking constraint (semaphore), verified never violated, distinguished from a soft SLA target.

## 5. Monitoring Post-Implementation

Post-rollout, process mining shifts from retrospective analysis to **continuous, near-real-time monitoring**, ideally via a live dashboard (Celonis, Disco, or custom BI on streaming event data).

### 5.1 Core Dashboard Metrics

| Constraint | Live Metrics | Alert Threshold Example |
|---|---|---|
| Cold-Packing | Station utilization %, current queue length, CPWT (rolling P90), preemption count/day | Queue length > X for > 15 min |
| Batching | Rolling batch size, batch formation time, BWT distribution, % dispatched within target window | BWT P90 exceeding target |
| Priority | Express end-to-end time vs SLA, PID (delay imposed on standard orders), interruption frequency | Express SLA breach rate > threshold |
| Hazmat Cap | Real-time `concurrent_hazmat_count(t)` chart with hard line at 10, time-at-cap %, hazmat queue wait | Any recorded value = 10 sustained > Y minutes |
| Overall | End-to-end cycle time percentiles, throughput/day, on-time delivery % | SLA adherence dropping below target |

### 5.2 Specific ISC-Effectiveness Tracking
- **Before/after comparison** using the same waterfall decomposition from Section 1.3 (Processing vs. Resource-Contention Wait vs. Batch Wait vs. Regulatory-Cap Wait) — the goal is a visibly reduced share of *between-instance* wait components, not just overall cycle time (which could mask trade-offs, e.g., faster express at cost of slower standard).
- **Compliance audit log**: automated check confirming `concurrent_hazmat_count(t)` never exceeded 10 post-implementation — zero-tolerance metric, reported separately from performance KPIs.
- **Statistical Process Control (SPC) charts** on key wait-time metrics to detect drift/regression over time (e.g., control limits on daily average CPWT) — flags if the new policy's benefits erode as volume grows.
- **Interaction re-validation**: periodically re-run the correlation checks from Section 2 (e.g., Batch Wait vs. % hazmat in batch) to confirm the interactions have been genuinely mitigated, not just relocated.

### 5.3 Continuous Improvement Loop
- Schedule **periodic re-mining** (e.g., monthly, and mandatorily before each peak season) to detect concept drift in arrival patterns, order-mix, or new bottlenecks emerging from the optimized configuration — feeding back into re-calibration of reserved capacities, batch thresholds, and token splits (Section 3), and re-validation via simulation (Section 4) before any parameter change is pushed live.
- This establishes a **closed-loop, data-driven governance cycle**: Discover  Enrich  Analyze ISCs  Simulate  Deploy  Monitor  Re-discover, ensuring the fulfillment center's constraint-handling policies remain effective as conditions evolve.
