# Business Process Overview

This process describes an **Order Fulfillment / Request Handling Workflow** that manages both standard and custom customer requests, incorporating validation, approval, and confirmation steps. Below is a detailed breakdown.

---

## 1. Process Initiation

**Start Event  Task A: "Receive Customer Request"**

- The process begins when a customer submits a request.
- Task A represents the intake step where the request is logged and prepared for classification.

---

## 2. First Decision Point: Request Type (XOR Gateway)

**Gateway (XOR): "Check Request Type"**

This is an **exclusive gateway**, meaning only **one path** is taken based on the request type:

- **Standard Path**  Task B1
- **Custom Path**  Task B2

The purpose of this split is to apply different validation logic depending on whether the request follows a routine, pre-defined process (standard) or requires special handling (custom).

---

## 3A. Standard Path

**Task B1: "Perform Standard Validation"**
- Validates the request against standard business rules (e.g., product availability, pricing rules).

**Gateway (AND): "Run Parallel Checks"**
- This is a **parallel split**, meaning both branches execute **simultaneously** and **independently**:
  - **Task C1: "Credit Check"** – Verifies customer creditworthiness.
  - **Task C2: "Inventory Check"** – Confirms stock availability.

**Join (AND merge): "All Parallel Checks Completed"**
- The process **waits** until both checks finish before proceeding (synchronization point).

**Task D: "Calculate Delivery Date"**
- Once both checks pass, the system calculates an estimated delivery date based on inventory and logistics data.

---

## 3B. Custom Path

**Task B2: "Perform Custom Feasibility Analysis"**
- Since custom requests are non-standard, this task evaluates whether the customization is technically and operationally feasible.

**Gateway (XOR): "Is Customization Feasible?"**
- **If Yes**  Task E1: "Prepare Custom Quotation" (proceed with pricing custom request)
- **If No**  Task E2: "Send Rejection Notice"  **End Event**
  - This is a **terminating path**: if customization isn't feasible, the process ends immediately without further approval steps.

---

## 4. Convergence Point

**"After Standard or Custom Path Tasks Completed"**

- This represents an **implicit merge** (not a formal gateway, but a convergence in the pseudo-BPMN) where:
  - The Standard path (after Task D) and
  - The Custom path (after Task E1)
  
  ...both flow into the **next decision point** regarding approval.

- Note: The rejection path (Task E2) does **not** merge here — it exits the process entirely.

---

## 5. Second Decision Point: Approval Check (XOR Gateway)

**Gateway (XOR): "Is Approval Needed?"**

This determines whether managerial oversight is required before finalizing the order. This could depend on factors like:
- Order value exceeding a threshold
- Custom requests always requiring approval
- Discounts or special terms requested

- **If Yes**  Task F: "Obtain Manager Approval"
- **If No**  Skip directly to Task G: "Generate Final Invoice"

---

## 6. Approval Sub-Process

**Task F: "Obtain Manager Approval"**
- A manager reviews the order details (pricing, feasibility, credit risk, etc.)

**Gateway (XOR): "Is Approval Granted?"**

- **If Yes**  Task G: "Generate Final Invoice" (approval successful, proceed to billing)
- **If No**  Task H: "Re-evaluate Conditions" (approval rejected, requires rework)

---

## 7. Rework Loop (Critical Feedback Mechanism)

**Task H: "Re-evaluate Conditions"**

This task triggers a **loop back**, meaning the process does **not** move forward linearly but returns to an earlier step for correction:

- **If original request was Custom**  Loop back to **Task E1: "Prepare Custom Quotation"**
  - The quotation is revised (e.g., adjusted pricing, scope, or terms) and resubmitted for approval.
  
- **If original request was Standard**  Loop back to **Task D: "Calculate Delivery Date"**
  - This suggests that for standard orders, rework might involve recalculating delivery terms (possibly implying that approval issues in standard orders relate to logistics/delivery commitments rather than pricing).

This creates an **iterative cycle**: 
```
Task F (Approval)  Rejected  Task H (Rework)  Back to E1/D  Re-attempt Approval (Task F)  ...
```
This loop continues until approval is granted (Task G) or, presumably, until a maximum retry limit or escalation occurs (though this isn't explicitly modeled here — a potential gap in the process design).

---

## 8. Final Convergence and Closure

**Task G: "Generate Final Invoice"**

- This step is reached either:
  - Directly (if no approval was needed), or
  - After successful approval (Task F  Yes)

- This is the **second merge point** in the process — both approval and non-approval paths converge here.

**Task I: "Send Confirmation to Customer"**
- After invoicing, the customer is notified of the final order confirmation.

**End Event**
- The process terminates successfully.

---

## Summary: Key Structural Elements

| Element | Type | Purpose |
|---|---|---|
| Check Request Type | XOR Split | Route based on Standard vs Custom |
| Run Parallel Checks | AND Split/Join | Simultaneous credit & inventory checks (Standard only) |
| Is Customization Feasible? | XOR Split | Determines if custom order proceeds or is rejected |
| Is Approval Needed? | XOR Split | Determines if managerial sign-off required |
| Is Approval Granted? | XOR Split | Determines success or rework |
| Task H (Rework) | Loop-back | Sends process back to revise quotation/delivery terms |

---

## Key Differences: Standard vs. Custom Requests

| Aspect | Standard Request | Custom Request |
|---|---|---|
| Validation | Standard Validation (B1) | Feasibility Analysis (B2) |
| Parallel Checks | Yes (Credit + Inventory) | No |
| Rejection Possibility | No explicit rejection path | Yes — can end early via Task E2 |
| Rework Target (if approval fails) | Task D (Delivery Date) | Task E1 (Quotation) |
| Key Output Before Approval | Delivery Date | Custom Quotation |

---

## Conditions Triggering Approval or Rework

1. **Approval is triggered** when:
   - The gateway "Is Approval Needed?" evaluates to **Yes** — likely driven by business rules (e.g., high order value, custom pricing, discount thresholds, or policy requiring all custom orders to be approved).

2. **Rework is triggered** when:
   - Manager reviews the request (Task F) and **rejects** it (Gateway: "Is Approval Granted?" = No).
   - This sends the process back to revise either the quotation (custom) or delivery calculation (standard), after which the approval cycle restarts.

---

## Potential Process Gaps (Observations)

- **No maximum loop limit** is defined for the rework cycle (Task H), which could lead to infinite loops if approval is repeatedly denied.
- **No merge back into parallel checks** for standard orders after rework — it's unclear if credit/inventory checks are re-validated after recalculating delivery dates.
- **Escalation path** is absent — e.g., what happens if a manager repeatedly rejects a custom quotation? A secondary review or cancellation option might be a beneficial addition.

---

This process effectively models a **dual-track order management system** with built-in quality control (parallel checks), risk management (approval gateway), and a feedback loop for continuous refinement of custom or standard offers before finalization.
