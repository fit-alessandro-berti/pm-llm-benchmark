###  Assumptions & Data Mapping Notes

1. **Case Identification**: `order_id` is used consistently as the `Case ID` across all tables.
2. **Activity Aggregation**: 
   - When an order had multiple line items, the `Items Picked` activity was aggregated into a single event per order using the **earliest** picking timestamp. Detailed items and pickers are stored in the `Other Attributes` column.
   - Split shipments, invoices, and payments (e.g., Order 1002) are represented as sequential events with `(Partial)` suffixes to preserve the true chronological flow and allow process mining algorithms to detect parallel or fragmented paths.
3. **Resource Mapping**: Actor names were resolved using the provided `Resources` table. If a specific person wasn't tied to a payment, `"Finance System"` was used as a logical placeholder.
4. **Missing Downstream Data (Order 1004)**: Orders 1004 contains `Order Created` and `Items Picked` events, but no corresponding records exist in the Delivery, Invoice, or Payments tables. Only the available events are included. It is assumed the order is either still in fulfillment, paused, or the downstream data was excluded from the sample dataset.
5. **Chronology**: All events are strictly ordered by timestamp within each case to reflect realistic process execution. For direct import into process mining tools (e.g., Celonis, Disco, PM4Py), you may optionally sort the entire table globally by `Timestamp`.
