## 1. Analyzing Resource Behavior and Assignment Patterns

### 1.1 Prepare an analysis-ready event log

Before mining the process, TechSolve should normalize and enrich the log. Important steps include:

- Separate the **actor performing an assignment** from the **agent receiving the assignment**. In the example, the resource is “Dispatcher,” while the assigned agent is embedded in Notes. Create structured fields such as:
  - `Assigned From`
  - `Assigned To`
  - `Resolver Group`
  - `Assignment Reason`
- Standardize skill names. For example, `DB-SQL` and `Database-SQL` may represent the same skill and could otherwise create false mismatch findings.
- Preserve ticket attributes as they existed at each decision point. A ticket initially classified as `App-CRM` may later be diagnosed as `Database-SQL`; this diagnostic evolution should not automatically be treated as an initial routing error.
- Maintain effective-dated agent profiles:
  - Tier
  - Skills and proficiency levels
  - Certifications
  - Shift/calendar
  - Team
  - Location/time zone
- Pair `START` and `COMPLETE` events to calculate actual touch time. The time between two completion events should not automatically be treated as active work.
- Add SLA targets, business-hours calendars, pause states, customer-wait periods, reopen events, and final resolution status.
- Treat reopened tickets consistently—either as continuations of the original case or as linked subprocesses.

The core data model should contain one case per ticket and one ordered event sequence per case, with assignment, work, transfer, escalation, resolution, and reopening events.

---

### 1.2 Agent- and tier-level performance metrics

Metrics should be calculated by agent, team, tier, skill, priority, category, shift, and time period. Raw comparisons between agents should be adjusted for ticket complexity and case mix.

| Area | Recommended measures |
|---|---|
| Workload | Tickets assigned, active WIP, concurrent tickets, arrivals per shift, productive hours, queue size |
| Utilization | Active work time ÷ rostered available time; utilization by skill and tier |
| Processing time | Median and percentile touch time by agent, tier, category, priority, and required skill |
| Waiting time | Created-to-first-assignment, assignment-to-work-start, escalation-to-next-work-start |
| Resolution | End-to-end resolution time, business-hours resolution time, age of open tickets |
| Assignment quality | First-assignment resolution rate, skill-match rate, transfers per ticket, “bounce-back” rate |
| L1 effectiveness | First-contact resolution, escalation rate, time spent before escalation, repeat contact rate |
| Quality | Reopen rate, customer recurrence, post-resolution reassignment, failed resolution rate |
| SLA | Response and resolution compliance, remaining SLA time at assignment, breach rate |
| Fairness | Workload coefficient of variation or Gini index across comparable agents |
| Specialization | Percentage of work matching documented skills, scarce-skill utilization, low-complexity work handled by specialists |

For L1, first-contact resolution should be clearly defined. A practical definition is:

> Percentage of eligible tickets resolved by L1 without transfer to a higher tier and without reopening within a defined period, such as seven days.

Phone tickets may support a literal first-call measure; email and portal cases should use first-contact or first-tier resolution.

Agent comparisons should control for priority, category, complexity, arrival time, and required skill. Otherwise, an L3 specialist handling difficult P1/P2 cases could incorrectly appear less productive than an L1 agent handling routine requests.

### 1.3 Discover the actual resource process

#### Process and variant discovery

A process model should be discovered from the event log, showing paths such as:

- Created  Assign L1  Work L1  Resolve
- Created  Assign L1  Escalate L2  Work L2  Resolve
- Created  Assign L1  Escalate L2  Reassign L2  Resolve
- Created  Direct L2/L3  Resolve
- Resolve  Reopen  Reassign

Variant analysis will quantify:

- Percentage of cases following each path
- Median duration of each variant
- SLA compliance by variant
- Number of assignments and tiers involved
- Categories and skills associated with high-transfer variants

This reveals how the service desk actually operates rather than relying on documented procedures.

#### Handover and social network analysis

Build resource networks where an edge represents a ticket passing from one agent or group to another. Useful measures include:

- Handover frequency
- Average delay after each handover
- Reciprocal transfers or “ping-pong”
- Centrality of agents who receive many escalations
- Communities of agents who regularly collaborate
- Dispatcher-to-agent routing patterns
- Cross-tier and within-tier transfer networks

A highly central specialist may be:

- A valuable expert and informal knowledge hub
- A routing default for uncertain cases
- A bottleneck with excessive dependency
- A sign that other agents lack training

These interpretations should be distinguished using workload, queue delay, and case-complexity data.

#### Role discovery

Create an activity-resource matrix and cluster agents based on the work they actually perform—for example:

- Routine desktop support
- CRM application support
- Database troubleshooting
- Firewall/network support
- Identity and access management

Compare discovered roles with:

- Formal L1/L2/L3 assignments
- Documented skills
- Resolver groups
- Job descriptions

This may reveal de facto specialists, agents working above or below their official tier, or formal skill profiles that no longer reflect actual capability.

#### Conformance checking

Encode intended rules as process or declarative constraints, such as:

- All tickets receive L1 triage unless approved for direct specialist routing.
- Assignments requiring a specialist skill go only to qualified agents.
- P2 tickets must begin work within the response target.
- Escalations must contain a diagnosis and required skill.
- Round-robin assignments should be balanced among available agents in the eligible pool.

Conformance checking can then identify deviations and quantify their frequency, delay, and SLA impact. A deviation is not necessarily harmful; some may represent effective workarounds that should be incorporated into the redesigned process.

---

### 1.4 Analyze skill utilization

Create a skill-to-demand matrix containing:

- Ticket volume by required skill
- Estimated work hours by required skill
- Number of qualified agents by shift
- Agent proficiency level
- Queue and SLA performance by skill pool
- Percentage of assignments with exact, partial, or no skill match

Classify each assignment as:

1. **Qualified match:** agent has the required skill at the necessary level.
2. **Partial match:** related skill exists but proficiency may be insufficient.
3. **Under-skilled assignment:** required skill is absent or below threshold.
4. **Potential overqualification:** a scarce specialist handles work routinely resolved by L1 or a generalist.

For each specialist, calculate:

- Percentage of productive time spent on matching specialist work
- Percentage spent on routine or low-complexity work
- Time spent correcting earlier assignments
- Scarce-skill queue waiting while the specialist performs routine work

“Below skill level” should not be inferred solely from tier. It should be based on empirical complexity and historical success—for example, a ticket type for which qualified L1 agents resolve 90% of cases with low reopen rates.

The snippet illustrates why normalization is important: Agent B12 lists `DB-SQL`, while the later required skill is `Database-SQL`. That could be a terminology issue rather than a true mismatch.

## 2. Identifying Resource-Related Bottlenecks and Issues

### 2.1 Skill-specific capacity bottlenecks

For each skill and time period, estimate:

\[
\text{Skill Load} =
\frac{\text{Demanded service hours for skill}}
{\text{Available qualified-agent hours}}
\]

Analyze this by hour, shift, weekday, and priority. Evidence of a skill bottleneck would include:

- High utilization among qualified agents
- Long assignment-to-start queues for that skill
- Increasing aged WIP
- High SLA breach rates when the skill is required
- Frequent routing to partially qualified agents
- Reassignments concentrated around the same small group of specialists

Queueing effects should be considered: targeting 100% specialist utilization is usually counterproductive because demand is variable and urgent work requires spare capacity.

---

### 2.2 Delay caused by reassignments and escalations

For each transfer, decompose delay into:

- **Dispatch delay:** reassignment event to new assignment
- **Queue delay:** new assignment to next work start
- **Duplicate effort:** work performed by an owner who did not resolve the case
- **Handover delay:** prior work end to next work start
- **Context-recovery time:** additional effort needed by the new agent to review prior work

For ticket \(i\):

\[
\text{Transfer Delay}_i =
\sum(\text{Next Work Start} - \text{Previous Work End})
\]

This descriptive amount should be supplemented with a matched comparison:

- Compare transferred tickets with similar priority, category, complexity, and arrival time that were resolved without transfer.
- Estimate the incremental resolution time, touch time, and SLA breach probability associated with one, two, and three or more transfers.

This avoids attributing all delay to transfers when inherently complex cases are also more likely to be transferred.

---

### 2.3 Incorrect initial assignment

Possible indicators include:

- Reassignment before meaningful work begins
- “Wrong group,” “wrong skill,” or equivalent transfer reason
- Required skill absent from the first assigned agent’s profile
- Rapid transfer to a different skill pool
- Repeated routing from the same dispatcher to the wrong group
- Cases where the ultimate resolver skill was predictable from information available at creation

Separate avoidable routing errors from legitimate diagnostic refinement. For example, a CRM symptom that is later found to be a database issue may represent reasonable diagnosis rather than poor initial routing.

Metrics include:

- First-assignment accuracy
- Percentage of tickets reassigned within 15 or 30 minutes
- Percentage of initial assignments with a skill mismatch
- Average SLA time consumed before reaching the correct group
- Accuracy by channel, dispatcher, category, and ticket form

---

### 2.4 Overloaded and underutilized agents or teams

Use both counts and effort. Ticket counts alone can be misleading because complexity varies.

Indicators of overload include:

- Persistently high active WIP
- High utilization
- Long personal queue time
- Work occurring outside scheduled hours
- High interruption or concurrency
- Increasing SLA breaches and reopen rates
- Large numbers of escalations received

Indicators of underutilization include:

- Low productive utilization despite relevant demand
- Low assignment share compared with equivalent peers
- Skills listed but rarely used
- Idle capacity while another compatible pool has an aging queue

Performance should be case-mix adjusted using regression, survival analysis, or hierarchical models. Results should be used for process and training improvement, not as an unqualified employee ranking system.

---

### 2.5 Correlating assignments with SLA breaches

Construct SLA cohorts such as:

- Skill match versus mismatch
- Zero, one, and multiple reassignments
- Same-tier versus cross-tier transfers
- High versus low workload at assignment
- Correct versus incorrect initial categorization
- Specialist immediately available versus unavailable

Report descriptive measures such as:

- Breach rate by cohort
- Median time lost before correct assignment
- Odds ratio or risk ratio for breach
- Percentage of breached tickets with a prior mismatch
- SLA time remaining at each handover

Then estimate adjusted effects using logistic regression, survival models, or matched comparisons controlling for:

- Priority
- Category and skill
- Complexity
- Channel
- Arrival hour/day
- Customer or service
- Queue state
- Staffing level

A counterfactual attributable measure can be calculated by predicting breach risk under observed assignments and again with the mismatch or transfer factor removed. This estimates the share of breaches plausibly attributable to assignment problems rather than merely associated with them.

## 3. Root Cause Analysis for Assignment Inefficiencies

### 3.1 Likely root-cause categories

#### Assignment rules ignore important constraints

Pure round-robin may balance ticket counts but ignore:

- Required skill
- Proficiency
- Current WIP
- Predicted handling time
- Shift end
- SLA urgency
- Scarcity of specialist capacity

Manual escalation can also produce inconsistent decisions and dependency on personal knowledge of “who is good at what.”

#### Skill profiles are inaccurate

Possible problems include:

- Outdated skills
- Inconsistent naming
- Missing proficiency levels
- Informal expertise not documented
- Certifications recorded without recent practical experience
- Skills updated only in HR systems and not synchronized with ITSM

#### Ticket categorization is poor

Incorrect categories can result from:

- Ambiguous portal forms
- Unstructured descriptions
- Inadequate category taxonomy
- Confusion between symptoms and root causes
- Missing configuration item or affected-service data
- Different practices by channel or dispatcher

#### Workload and availability are not visible

Round-robin may assign work to agents who are:

- Already overloaded
- In training or meetings
- Near the end of a shift
- Working on a major incident
- Unavailable but still shown as active
- Qualified on paper but not currently assigned to that function

#### L1 lacks training, tools, or authority

Excessive escalation may result from:

- Missing knowledge articles
- Limited system access
- Weak diagnostic scripts
- Fear of breaching SLA while troubleshooting
- Escalation incentives
- Lack of coaching feedback from L2/L3
- Procedures requiring escalation even for common resolutions

#### Organizational and queue design problems

Additional causes may include:

- Too many narrowly defined queues
- No clear ownership after escalation
- Specialists acting as default triage points
- Shift coverage that does not match demand
- Reassignments used to protect team-level SLA metrics
- Missing escalation documentation that forces repeated diagnosis

---

### 3.2 Variant-based root cause analysis

Define two case populations:

- **Smooth cases:** resolved by the first qualified owner, no unnecessary transfer, no reopen, SLA met.
- **Problem cases:** multiple reassignments, skill mismatch, long queue delay, breach, or reopen.

Compare them by:

- Priority and category
- Required skill
- Description keywords
- Initial category accuracy
- Channel
- Dispatcher
- First assigned agent/tier
- Time and day
- Queue size and staffing at assignment
- Agent proficiency
- Number of open cases per agent
- Diagnostic activities completed before escalation

Sequence comparison may show, for example, that problem cases frequently contain:

> Assign L1  Wait  Work L1  Escalate L2  Reassign L2  Assign L3

while smooth cases contain:

> Assign L1  Resolve

or:

> Triage  Direct qualified L2  Resolve

The largest differences identify candidate causes and redesign opportunities.

---

### 3.3 Decision mining

Decision mining examines routing choices at points such as:

- L1 versus direct L2
- Resolve at L1 versus escalate
- Which L2 group receives the case
- Whether to reassign or swarm
- Whether a scarce specialist is needed

Models such as decision trees, random forests, or gradient boosting can identify which factors influenced historical decisions. Input features should include only information available at the decision time to avoid hindsight leakage.

Two different model objectives are useful:

1. **Descriptive model:** predicts what assignment was historically made. This reveals current rules and inconsistencies.
2. **Outcome model:** predicts resolution, transfer, SLA breach, or handling time for each eligible assignment. This supports a better prescriptive policy rather than simply reproducing historical mistakes.

Feature importance and explainability methods can reveal, for example, whether assignment decisions are driven more by dispatcher identity than by ticket skill, or whether overload at assignment strongly predicts transfer.

Models should be tested over time to detect seasonal changes and concept drift.

## 4. Data-Driven Resource Assignment Strategies

### Strategy 1: Proficiency-weighted skill-based routing

**Issue addressed:** Tickets are assigned to agents without the necessary skill, while specialists receive inappropriate work.

Create an eligibility matrix linking ticket requirements to agent skills and proficiency. Routing should first exclude unavailable or unqualified agents, then rank eligible agents based on:

- Required skill match
- Proficiency
- Historical success for similar cases
- Reopen and transfer rates
- Experience with the customer/service
- Scarcity of the agent’s other skills

A possible routing score is:

\[
\text{Score}(a,t) =
w_1 P(\text{resolve without transfer})
-w_2 \text{predicted wait}
-w_3 \text{breach risk}
-w_4 \text{transfer risk}
-w_5 \text{scarce-skill opportunity cost}
\]

**Process-mining basis:** Skill-mismatch analysis, discovered roles, handover networks, and historical first-owner resolution rates.

**Required data:**

- Standardized required-skill taxonomy
- Effective-dated agent skills and proficiency
- Availability and calendars
- Historical outcomes by ticket type and agent
- Skill scarcity and queue data

**Expected benefits:**

- Fewer wrong-group assignments
- Lower reassignment rate
- Reduced duplicate effort
- Better use of scarce specialists
- Faster time to the first qualified owner

---

### Strategy 2: Workload-, queue-, and SLA-aware dynamic assignment

**Issue addressed:** Round-robin distributes ticket counts but not effort, urgency, or current workload.

Among qualified agents, assign the ticket using real-time information such as:

- Active WIP
- Predicted remaining work
- Current and expected queue delay
- Shift availability
- P2/P3 SLA time remaining
- Concurrent high-priority work
- Fairness and workload-balancing constraints

The objective can minimize expected resolution cost:

\[
\text{Expected Cost} =
\alpha(\text{wait})
+\beta(\text{breach probability})
+\gamma(\text{transfer probability})
+\delta(\text{workload imbalance})
\]

P1/P2 tickets can receive stronger SLA weights, while routine P4 work can be delayed or routed to flexible capacity.

**Process-mining basis:** Queue-time analysis, workload heatmaps, breach correlation, and skill-pool bottleneck findings.

**Required data:**

- Real-time queue and WIP
- Agent status and schedule
- Estimated service-time distributions
- SLA clocks and pause states
- Skill eligibility
- Current major-incident assignments

**Expected benefits:**

- More even workload
- Lower queue waiting time
- Fewer P2/P3 breaches
- Reduced assignments to unavailable agents
- Better use of underutilized compatible capacity

The algorithm should retain some spare capacity for demand variability rather than attempting to drive every specialist to 100% utilization.

---

### Strategy 3: Predictive triage and resolver-group recommendation

**Issue addressed:** Initial category and required skill are inaccurate or incomplete.

Use structured ticket fields and natural-language processing on descriptions to predict:

- Required skill
- Correct resolver group
- Complexity
- Likelihood of L1 resolution
- Likelihood of escalation
- Expected handling time
- SLA breach risk

The model should recommend—not silently force—routing when confidence is low. High-confidence cases can be automatically routed; ambiguous tickets should be sent to a diagnostic queue or presented with the top candidate groups and explanations.

**Process-mining basis:** Variant analysis and decision mining identify characteristics of tickets that historically reached particular successful resolver groups.

**Required data:**

- Ticket descriptions and keywords
- Category and service
- Configuration item
- Channel
- Historical assignment paths
- Final successful resolver and skill
- Transfer and reopen outcomes

**Expected benefits:**

- Better initial categorization
- Reduced time spent in incorrect queues
- Fewer dispatcher-dependent decisions
- Earlier identification of complex P2/P3 tickets
- More consistent routing across channels

Training labels should not simply use the last resolver as ground truth, because historical routing may itself be inefficient. Successful no-transfer cases, expert-reviewed samples, and resolution quality should be incorporated.

---

### Strategy 4: Refined L1 resolution and escalation policy

**Issue addressed:** L1 escalates tickets that could be resolved safely at first contact, while some specialist cases spend too long in L1.

For ticket types with high historical L1 success:

- Provide targeted knowledge articles and diagnostic prompts
- Grant appropriate access or automation
- Train selected L1 agents in high-volume skills
- Recommend next-best actions
- Set minimum diagnostic information before escalation

For tickets with very low L1 resolution probability and a clear specialist requirement:

- Permit direct L2/L3 routing
- Avoid mandatory but unproductive L1 handling
- Use a short L1 validation step rather than full troubleshooting

Introduce “swarming” for borderline cases: L1 retains ownership while consulting L2, reducing formal handovers and repeated diagnosis.

**Process-mining basis:** L1 resolution propensity by ticket type, time spent before unsuccessful escalation, and common escalation variants.

**Required data:**

- L1 resolution and reopen history
- Diagnostic steps
- Knowledge article usage
- Access limitations
- Escalation reason
- Ticket complexity and skill requirement

**Expected benefits:**

- Higher first-contact resolution
- Less specialist time spent on routine work
- Faster specialist access for genuinely complex cases
- Reduced formal handovers
- Better knowledge transfer between tiers

---

### Strategy 5: Dynamic capacity allocation and cross-skilling

**Issue addressed:** Demand for particular skills varies by time, while staffing is static.

Use arrival patterns and queue forecasts to:

- Schedule more firewall, database, or IAM coverage during peak periods
- Temporarily move cross-skilled agents into high-demand queues
- Create overflow pools for P2/P3 demand
- Protect scarce specialist capacity from routine tickets
- Cross-train agents where recurring capacity gaps are observed

**Process-mining basis:** Time-based demand analysis, skill-load ratios, utilization, and bottleneck queues.

**Required data:**

- Arrival forecasts by skill and priority
- Shift and leave calendars
- Cross-skill eligibility
- Historical service times
- Seasonal and incident-related demand patterns
- Training and proficiency records

**Expected benefits:**

- Reduced skill-specific queue buildup
- More resilient staffing
- Better coverage across shifts
- Lower dependence on a few central specialists
- Improved SLA performance during demand peaks

## 5. Simulation, Implementation, and Monitoring

### 5.1 Evaluate alternatives with business process simulation

Build a discrete-event simulation or process digital twin based on the mined process model. It should include:

- Ticket arrivals by hour, day, priority, category, and skill
- Activity and service-time distributions
- L1/L2/L3 routing probabilities
- Reassignment and escalation probabilities
- Agent skills and proficiency
- Shift calendars and availability
- Queue disciplines
- SLA clocks
- Reopen and rework behavior
- Non-stationary demand and major-incident scenarios

First validate the baseline simulation against a holdout period. It should reproduce observed:

- Queue lengths
- Resolution-time distributions
- Utilization
- Transfer rates
- Tier volumes
- SLA compliance

Then compare scenarios such as:

1. Current round-robin baseline
2. Skill-based routing only
3. Skill plus workload-aware routing
4. Predictive triage with direct specialist routing
5. Improved L1 resolution
6. Additional specialist capacity or cross-skilling
7. Combined strategy

Use multiple Monte Carlo runs and report confidence intervals for:

- P2/P3 SLA compliance
- Mean and percentile resolution time
- First-contact resolution
- Reassignments per ticket
- Queue length and aging
- Specialist utilization
- Workload fairness
- Cost per resolved ticket
- Reopen rate

Stress tests should include demand spikes, staff absence, major incidents, and loss of a key specialist. The preferred strategy should improve SLA and flow without creating excessive utilization or shifting problems to another tier.

---

### 5.2 Phased implementation

A controlled rollout is preferable to an immediate service-wide change.

1. **Data and governance phase**
   - Standardize skills and categories.
   - Correct assignment-event semantics.
   - Define SLA and KPI rules.
   - Establish ownership for agent-profile maintenance.

2. **Shadow-mode phase**
   - Generate routing recommendations without changing assignments.
   - Compare recommendations with actual decisions and outcomes.
   - Review disagreements with dispatchers and technical leads.

3. **Pilot phase**
   - Pilot in one or two high-volume areas, such as CRM and network incidents.
   - Use a stepped-wedge or controlled comparison where possible.
   - Retain manual override with a mandatory reason code.

4. **Scale phase**
   - Extend to other skills and tiers.
   - Automate only high-confidence decisions.
   - Maintain fallback queues and operational guardrails.

5. **Continuous improvement**
   - Retrain predictive models.
   - Update proficiency profiles.
   - Review new variants and routing workarounds.
   - Re-simulate major policy changes.

## Overall Recommendation

TechSolve should replace tier-only round-robin routing with a controlled hybrid model combining:

1. **Skill and proficiency eligibility**
2. **Real-time workload and SLA awareness**
3. **Predictive ticket triage**
4. **Evidence-based L1 escalation rules**
5. **Dynamic skill-capacity planning**

Process mining provides the factual baseline, identifies where assignment decisions create waiting and rework, and enables ongoing conformance and outcome monitoring. Simulation and phased pilots should be used to quantify benefits before full deployment and to ensure that improvements in one queue do not create new bottlenecks elsewhere.
