Here is the DuckDB SQL query to solve this task. It uses Common Table Expressions (CTEs) to break the problem into logical steps: extracting the sequence per case, counting the variants, filtering for the top K, and finally returning the matching events.

```sql
-- Replace :k with the number of top variants you want to keep (e.g., 5)
WITH case_sequences AS (
    -- Step 1: Extract the ordered sequence of activities for each case_id
    SELECT 
        case_id,
        string_agg(activity, ' -> ' ORDER BY timestamp) AS variant
    FROM event_log
    GROUP BY case_id
),
variant_counts AS (
    -- Step 2 & 3: Group by the complete activity sequence and count cases per variant
    SELECT 
        variant,
        COUNT(case_id) AS case_count
    FROM case_sequences
    GROUP BY variant
),
top_k_variants AS (
    -- Step 3: Determine the top K variants by frequency
    SELECT variant
    FROM variant_counts
    ORDER BY case_count DESC
    LIMIT :k
),
filtered_cases AS (
    -- Step 4a: Filter down to cases belonging to the top K variants
    SELECT case_id
    FROM case_sequences
    WHERE variant IN (SELECT variant FROM top_k_variants)
)
-- Step 4b: Return all events from the original log for these filtered cases
SELECT 
    e.case_id,
    e.activity,
    e.timestamp
FROM event_log e
JOIN filtered_cases fc ON e.case_id = fc.case_id
ORDER BY e.case_id, e.timestamp;
```

### How it works:
1. **`case_sequences`**: Groups the events by `case_id` and uses DuckDB's `string_agg` with an `ORDER BY timestamp` clause to concatenate activities into a single string representing the variant path (e.g., `"A -> B -> C"`).
2. **`variant_counts`**: Groups the previously generated sequences by the `variant` string and counts how many `case_id`s follow each path.
3. **`top_k_variants`**: Orders the variants by their count in descending order and limits the result to the top K. *(Note: you can replace `:k` with a specific integer like `5` or parameterize it in your application layer).*
4. **`filtered_cases` & Final SELECT**: Finds all `case_id`s that match the top variants, joins back to the original `event_log` table, and returns the raw events ordered chronologically per case.
