## 1. Normative reference process

For a successful hiring case, the expected sequence is:

```text
Post_Job_Ad
 Screen_Candidates
 Conduct_Interviews
 Make_Hiring_Decision
 Onboard_Employee
 Add_to_Payroll
 Close_Case
```

This assumes that:

- Screening precedes interviewing.
- Both screening and interviewing inform the hiring decision.
- Onboarding occurs only after a positive decision.
- Every onboarded employee is added to payroll.
- Closing occurs after all other work is complete.

Both POWL models can produce this normative trace. Their problems are therefore primarily that they also permit non-normative behavior.

## 2. Analysis of Model 1

Model 1 imposes:

```text
Post  Screen
Screen  Interview
Screen  Decide
Decide  Onboard  Payroll  Close
```

The crucial missing dependency is:

```text
Conduct_Interviews  Make_Hiring_Decision
```

Consequently, `Conduct_Interviews` is unordered with respect to `Make_Hiring_Decision` and all activities following the decision. For example, the following is a valid execution of Model 1:

```text
Post_Job_Ad,
Screen_Candidates,
Make_Hiring_Decision,
Onboard_Employee,
Add_to_Payroll,
Close_Case,
Conduct_Interviews
```

This is a severe anomaly: the organization can make a hiring decision, onboard and pay the employee, and close the case before conducting the interview. Thus, `Close_Case` is also not guaranteed to be the last activity.

### Strengths of Model 1

Despite that major ordering flaw, Model 1 guarantees that:

- Every labeled activity occurs exactly once.
- Screening occurs before the decision.
- The decision occurs before onboarding.
- Onboarding occurs before payroll.
- Payroll is mandatory and occurs before closure.

### Main anomaly

- **High severity:** Interviews are not a prerequisite for the hiring decision or any subsequent activity.

Model 1 can be repaired essentially by adding:

```python
model1.order.add_edge(Interview, Decide)
```

## 3. Analysis of Model 2

The two operators have the following behavior:

```python
loop_onboarding = *(Onboard, skip)
```

means:

```text
Onboard_Employee one or more times
```

because each loop iteration consists of `Onboard_Employee`, optionally followed by the silent transition and another `Onboard_Employee`.

Likewise:

```python
xor_payroll = X(Payroll, skip)
```

means:

```text
either Add_to_Payroll or no payroll activity
```

### Ordering anomalies

Model 2 has:

```text
Post  Screen
Post  Interview  Decide  Onboarding loop  Payroll choice  Close
```

There is no dependency requiring screening before interviewing or before the hiring decision. In fact, `Screen_Candidates` is unordered with the entire downstream chain. For example, this trace is valid:

```text
Post_Job_Ad,
Conduct_Interviews,
Make_Hiring_Decision,
Onboard_Employee,
Add_to_Payroll,
Close_Case,
Screen_Candidates
```

Thus, screening can occur after the interview, after the decision, or even after case closure.

If an organization intentionally performs screening and interviewing in parallel, the model should still require both to finish before `Make_Hiring_Decision`, for example by adding `Screen  Decide`. As written, screening has no influence on the decision.

### Repeated onboarding

The loop permits traces such as:

```text
..., Make_Hiring_Decision,
Onboard_Employee,
Onboard_Employee,
Add_to_Payroll,
Close_Case
```

Repeated onboarding is not normally expected for a single hiring case and could cause duplicate employee records or repeated administrative work. A retry loop could be legitimate, but the silent transition gives no labeled failure, correction, or retry condition. This is therefore at least a moderate anomaly under the stated process semantics.

### Optional payroll

The XOR permits:

```text
..., Make_Hiring_Decision,
Onboard_Employee,
Close_Case
```

with no `Add_to_Payroll`. This is a serious integrity problem because the employee has already been onboarded. If payroll were optional because the candidate was rejected, the model should contain an explicit rejection path before onboarding—not a silent skip after onboarding.

### Strengths of Model 2

Model 2 does correctly enforce:

- At least one interview before the hiring decision.
- A decision before onboarding.
- At least one onboarding occurrence.
- Payroll, when it occurs, before closure.

However, these strengths do not eliminate the optional-payroll, repeated-onboarding, and missing-screening dependencies.

## 4. Direct comparison

| Normative guarantee | Model 1 | Model 2 |
|---|---:|---:|
| Screening before interviewing | Yes | No |
| Interview before decision | No | Yes |
| Screening before decision | Yes | No |
| Decision before onboarding | Yes | Yes |
| Exactly one onboarding | Yes | No |
| Payroll mandatory after onboarding | Yes | No |
| Payroll before closure | Yes | Only if payroll is selected |
| Closure after all other activities | No, interview may follow | No, screening may follow |

## 5. Conclusion

**Model 1 more closely aligns with the normative Hire-to-Retire process.**

Model 1 has one fundamental ordering defect: it fails to require interviews before the hiring decision. This defect is serious and can even allow the interview to occur after closure.

Model 2 has the corresponding early-process defect of not requiring screening before interviews or the decision, but it also introduces two additional semantic deviations:

1. Unbounded repeated onboarding.
2. The ability to close an onboarded employee's case without adding them to payroll.

Although Model 2 correctly requires an interview before the decision, its optional payroll and repeated onboarding weaken process integrity more broadly. Therefore, under the stated successful-hire interpretation, **Model 1 is the closer approximation and requires the smaller correction**.
