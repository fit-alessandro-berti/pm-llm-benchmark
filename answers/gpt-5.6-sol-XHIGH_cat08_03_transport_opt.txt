# 1. Process Discovery and Conformance Checking

## 1.1 Data preparation and integration

A single flat case definition is not sufficient because several processes interact:

- A **vehicle-day/tour** contains many stops and packages.
- A **package journey** can span several vehicle-days if the first attempt fails.
- A **vehicle lifecycle** spans tours, maintenance, breakdowns, and repairs.
- A customer stop may serve several packages simultaneously.

The preferred design is therefore an **object-centric event log**, linking events to vehicle, driver, tour, route, stop, package, and maintenance work order. If the process-mining platform only supports conventional logs, three synchronized views should be created:

| Analysis view | Primary case | Main purpose |
|---|---|---|
| Tour execution | Vehicle-day or route instance | Routing, timing, utilization, overtime |
| Package journey | Package ID | First-attempt success, re-delivery, time-window compliance |
| Vehicle lifecycle | Vehicle ID or maintenance work order | Breakdowns, downtime, maintenance effectiveness |

This prevents common distortions. For example, assigning one travel event to every package delivered at the next stop would multiply travel time and event counts.

### Recommended event-log schema

Each normalized event should contain:

- Unique event ID
- Activity name
- Start and completion timestamp, where applicable
- Tour/vehicle-day ID
- Route ID and **route-plan version**
- Vehicle ID and type
- Driver ID
- Stop and package IDs
- Maintenance work-order ID, if applicable
- Latitude/longitude and mapped road segment or geofence
- Planned stop order, planned arrival, and customer time window
- Actual speed, distance, ignition, and idle status
- Outcome and failure reason
- Source system and data-quality/confidence flag

### Integration steps

1. **Establish a common activity taxonomy.**  
   Map source-specific labels into standard activities such as:

   - Start Shift
   - Route Assigned
   - Scan/Load at Depot
   - Depart Depot
   - Travel
   - Traffic Delay
   - Arrive Customer
   - Find Parking
   - Service Customer
   - Delivery Success
   - Delivery Failed
   - Depart Customer
   - Break
   - Unplanned Stop
   - Vehicle Breakdown
   - Return Depot
   - End Shift
   - Maintenance Start/Complete

2. **Synchronize timestamps.**  
   Convert all timestamps to a consistent time zone, account for daylight-saving changes, correct known device clock offsets, and retain both source and ingestion timestamps.

3. **Resolve master data and identifiers.**  
   Reconcile vehicle, driver, route, stop, and package IDs across systems. Vehicle or driver substitutions during a route must be retained rather than overwritten.

4. **Abstract high-frequency GPS records into operational episodes.**  
   Raw GPS pings should not become thousands of process events. They should be map-matched and summarized into:

   - Moving segments
   - Stationary/idle episodes
   - Customer-stop visits
   - Depot visits
   - Detours
   - Congestion episodes
   - Unplanned stops

   A stop can be associated with a customer using geofences, scanner events, package assignments, and temporal proximity. Travel intervals can be represented by start/complete lifecycle events or as duration attributes on arrival events.

5. **Reconcile GPS and scanner evidence.**  
   Scanner timestamps are authoritative for package outcomes, while GPS is generally better for physical arrival and departure. For example:

   - GPS stationary near an address at 08:23
   - Scanner “Arrive Customer” at 08:25
   - Scanner “Delivery Success” at 08:28
   - GPS movement starts at 08:30

   This can be decomposed into parking/access time, scanner-recorded service time, and post-service dwell.

6. **Version planned routes.**  
   If dispatch changes the plan during the day, each revision must be stored. Otherwise, a legitimate dispatcher-approved reroute will appear to be nonconformance.

7. **Create derived attributes.**  
   Examples include:

   - Actual versus planned travel time
   - Actual versus planned service time
   - Lateness at each stop
   - Actual versus planned distance
   - Remaining packages and capacity
   - Cumulative shift time
   - Idle duration
   - Traffic-delay minutes
   - Time since last maintenance
   - Re-delivery indicator

8. **Apply data-quality controls.**  
   Check for duplicate scans, impossible speeds, missing arrivals/departures, events outside a driver’s shift, incorrect package assignments, incomplete tours, GPS gaps, and inconsistent sequencing. Imputed or inferred events should be marked with a confidence score rather than treated as directly observed.

### Main data challenges

- Different source granularity: GPS every few seconds versus sparse scanner events
- Clock skew and delayed synchronization
- Missing or duplicate scans
- GPS inaccuracy in dense urban areas
- Several packages delivered at one address
- Incomplete or changed route assignments
- Vehicle or driver swaps
- Difficulty separating traffic, parking, breaks, and customer service
- Maintenance episodes spanning multiple days
- Failed deliveries that create cross-day package cases
- Privacy concerns around driver-level location and performance data
- Lack of direct fuel data in the described sources

GPS distance, speed, and idling can support a fuel proxy, but reliable fuel KPIs require CAN-bus, fuel-card, or refueling data.

## 1.2 Discovering the actual delivery process

A layered discovery approach is appropriate.

### First: directly-follows and variant analysis

A directly-follows graph should show:

- Activity and transition frequency
- Median and 90th-percentile duration
- Rework loops
- Unplanned transitions
- Relative frequency of successful and failed variants

This quickly reveals whether the dominant flow resembles:

> Route Assigned  Depart Depot  Travel  Arrive  Service  Outcome  Depart  repeat  Return Depot

and how frequently it contains exceptions such as:

- Late depot departure
- Route reassignment
- Traffic delay
- Long idle or parking search
- Failed attempt
- Reattempt
- Breakdown
- Early return
- Overtime

### Second: structured process models

An **Inductive Miner** is useful for producing a sound, readable process tree or Petri net despite loops and some noise. A Split Miner or filtered directly-follows model can provide a more compact operational view.

Stop IDs and package IDs should normally remain event attributes, not unique activity names; otherwise, the model will become an unreadable “spaghetti” model. The generic customer-stop loop is discovered as process behavior, while stop order is analyzed separately.

### Third: cohort and variant discovery

Separate models should be produced for:

- On-time versus late tours
- Urban versus suburban territories
- Peak versus off-peak periods
- High versus low route density
- Vehicle types
- Routes with and without breakdowns
- First-attempt success versus failed-delivery cases
- High- and low-performing process variants

The process model should be combined with a geographic view showing actual trajectories, congestion, idling, failed-delivery clusters, and unplanned stops.

## 1.3 Conformance checking against the plan

Conformance should be measured at two levels.

### A. Generic process or SOP conformance

A normative model can check whether required activities occur in the right broad order. Examples include:

- Departure before route assignment
- Customer departure without a recorded outcome
- Missing depot return
- Shift ended away from the depot
- Delivery by an unassigned vehicle or driver
- Breakdown without a corresponding operational or maintenance record

Petri-net or process-tree alignments can calculate model fitness and identify missing, inserted, or incorrectly ordered events.

### B. Route-specific conformance

Each dispatch plan should be converted into an expected trace containing:

- Assigned vehicle and driver
- Assigned packages
- Planned stop sequence
- Planned arrival or service times
- Customer time windows
- Planned distance and travel duration
- Vehicle capacity and workload

The actual stop trace is then aligned to the relevant plan version.

Important deviations include:

1. **Sequence deviations**
   - Stops served out of order
   - Stops skipped
   - Stops repeated
   - Failed stops revisited
   - Packages delivered on another tour

2. **Spatial deviations**
   - Actual distance significantly above plan
   - Detours
   - Route overlap between vehicles
   - Unplanned stops outside approved geofences

3. **Temporal deviations**
   - Late depot departure
   - Travel-time overruns
   - Service-time overruns
   - Early or late customer arrival
   - Excessive idle or parking time
   - Late depot return or driver overtime

4. **Capacity and assignment deviations**
   - Over-capacity dispatch
   - Underutilized vehicle
   - Vehicle or driver substitution
   - Undelivered assigned packages

5. **Operational exceptions**
   - Breakdown or warning-light stop
   - Unplanned break
   - Route abandonment
   - Mid-route return to depot

Useful route-conformance measures include:

- Percentage of planned stops completed
- Stop-sequence edit distance or rank correlation
- Number of inserted, skipped, and repeated stops
- Actual/planned distance ratio
- Mean absolute arrival-time deviation
- Time-window conformance
- Alignment cost weighted by business severity

Approved dynamic reroutes should be assessed against the revised plan, not incorrectly counted as driver deviations.

# 2. Performance Analysis and Bottleneck Identification

## 2.1 Core KPIs

KPIs should be defined consistently at package, stop, tour, driver, vehicle, and territory level. Medians and percentiles should accompany averages because last-mile durations are usually skewed.

| KPI | Calculation from the event data |
|---|---|
| **On-Time Delivery Rate** | Packages successfully delivered within the promised window divided by all packages due in that window. Report first-attempt on-time rate separately from eventual on-time delivery. |
| **First-Attempt Success Rate** | Packages successfully delivered on the first attempt divided by packages attempted. |
| **Failed-Delivery Rate** | Failed attempts divided by all attempts, plus a package-level rate for packages whose first attempt failed. |
| **Average Stop Time** | Customer departure minus arrival. Also report median, P90, and components such as parking/access, customer service, and post-service dwell. |
| **Travel-to-Service Ratio** | Total driving time divided by total customer-stop time. Breaks and breakdowns should be reported separately. |
| **Traffic-Delay Frequency and Duration** | Number of road segments where actual travel exceeds a time-of-day baseline by a defined threshold; excess minutes are `actual – expected`. Normalize by 100 km or tour. |
| **ETA Accuracy** | Planned or predicted arrival minus actual arrival. Track bias, mean absolute error, and P90 error by segment and time of day. |
| **Route Adherence** | Planned stops completed in planned order, actual/planned distance, sequence deviations, and unplanned-stop count. |
| **Distance per Delivered Package** | Map-matched route distance divided by successful deliveries. Redelivery distance should be separately identified. |
| **Fuel Efficiency** | Liters per 100 km, liters per delivered package, and fuel used while idling. Direct fuel telemetry is needed for reliable measurement; otherwise, use a clearly labeled model-based estimate. |
| **Capacity Utilization** | Initial package load versus vehicle capacity and, preferably, distance-weighted load factor as packages are delivered. Weight/volume should be used where available rather than package count alone. |
| **Productive Vehicle Utilization** | Time spent traveling or servicing customers divided by available vehicle/shift time. Report idle, depot waiting, breakdown, and maintenance time separately. |
| **Route Completion Rate** | Assigned packages successfully completed on the planned tour divided by assigned packages. |
| **Overtime Rate** | Tours or shift minutes exceeding scheduled/legal working time. |
| **Vehicle Reliability** | In-route breakdowns per 10,000 km, mean time between failures, mean repair time, availability, and unplanned maintenance duration. |
| **Operational Cost per Delivery** | Fuel, labor/overtime, maintenance allocation, and re-delivery cost divided by successful deliveries. Additional cost-source data may be required. |

The SLA timestamp must be explicitly defined. For example, the company must decide whether “on time” means arrival, service start, or completed delivery within the customer window.

---

## 2.2 Bottleneck identification techniques

### Performance-enhanced process models

Overlay activity and transition durations on the discovered model. High-frequency, high-duration transitions deserve priority, especially:

- Route Assigned  Depart Depot
- Depart Stop  Arrive Next Stop
- GPS arrival near address  Scanner arrival
- Arrive Customer  Delivery Outcome
- Outcome  Depart Customer
- Breakdown  Resume/Return
- Arrive Depot  End Shift

Use P90 and variance, not only average duration. A stop with a moderate average but extreme variability can be more damaging to schedule reliability than a consistently slow stop.

### Cumulative delay decomposition

For each aligned stop, lateness can be decomposed approximately as:

> Late depot departure  
> + excess travel time on previous segments  
> + excess service time at previous stops  
> + unplanned-stop duration  
> + impact of changed stop sequence

This identifies the point at which a route first became late and whether it later recovered. It also distinguishes a late delivery caused by the current segment from lateness accumulated earlier in the tour.

### Variant comparison

Compare the “happy path” with late or costly variants:

- Which activities occur only in late tours?
- Do failed deliveries generate repeated travel loops?
- Are high-performing routes more likely to reorder certain stop sequences?
- Do breakdown routes exhibit warning or idling patterns beforehand?
- Is overtime predominantly associated with late departure, traffic, long service, or excessive route load?

### Geographic and temporal analysis

Create heat maps by road segment, geofence, hour, and weekday for:

- Excess travel time
- Low-speed and idling episodes
- Parking/search time
- Failed deliveries
- Long customer dwell
- Breakdown locations
- Route overlap and detours

This distinguishes a route-design issue from a recurring congestion or access issue.

### Resource and cohort analysis

Compare drivers, vehicles, routes, and territories only after normalizing for:

- Number and density of stops
- Package volume and type
- Urban/suburban mix
- Time windows
- Traffic exposure
- Vehicle type and age
- Day of week and season

Raw driver rankings would be misleading if one driver consistently receives the most difficult territory.

### Quantifying impact

For each bottleneck, calculate:

- Total excess minutes
- Percentage of tours affected
- Downstream packages made late
- Excess distance and estimated fuel
- Overtime minutes
- Additional failed attempts or re-delivery kilometers
- Wage and vehicle-cost impact
- Contribution to total lateness or cost

A Pareto analysis can then show, for example, whether most late deliveries are explained by a small number of congestion segments, service-time hotspots, late departures, or breakdown-prone vehicles.

# 3. Root Cause Analysis for Inefficiencies

Process mining identifies associations and process patterns; it does not by itself prove causality. Root-cause hypotheses should be validated with matched comparisons, statistical controls, operational review, and pilots.

## 3.1 Suboptimal or overly static route planning

**Possible evidence:**

- High actual/planned distance ratios
- Routes crossing each other
- Frequent stop-order deviations
- Drivers repeatedly choosing an alternative sequence
- Large workload imbalance between neighboring routes
- Plans that are feasible using average times but fail under realistic P90 conditions

A useful test is to compare matched tours where the planned order was followed with tours where drivers deviated. If consistent deviations reduce distance or improve punctuality after controlling for traffic and workload, the planned sequence is likely poor rather than the drivers being noncompliant.

## 3.2 Inaccurate travel-time estimates

Calculate ETA residuals by:

- Road segment
- Time of day
- Weekday
- Direction of travel
- Urban/suburban area
- Weather or event conditions, if added

Consistent underestimation on particular segments suggests that the dispatch engine uses outdated or overly general travel-time assumptions. The analysis should separate systematic bias from unpredictable incidents.

## 3.3 Traffic congestion

Correlate fleet movement with:

- Low-speed episodes
- Actual-versus-baseline segment times
- External traffic feeds, roadworks, weather, or event calendars
- Similar delays experienced by several vehicles at the same time and location

A single slow vehicle may indicate parking, a break, or a vehicle issue. Multiple vehicles slowing on the same road segment is stronger evidence of traffic congestion.

Recurring congestion should be treated differently from one-off incidents: recurring patterns should influence base route design, while incidents require dynamic routing.

## 3.4 Variable service and access time

Decompose stop time into:

- Parking or access-search time
- Walk-to-address/building-access time
- Scanner-recorded customer interaction
- Signature, payment, identification, or parcel-handling time
- Post-delivery dwell

Analyze dwell-time distributions by address, building type, package count, signature requirement, parking availability, and time of day. If these attributes are not currently collected, the process analysis can identify where additional data is most valuable.

High variability may indicate that the planner applies one standard service time to fundamentally different stop types.

## 3.5 Vehicle breakdowns and maintenance needs

Link operational events to maintenance history:

- Warning or abnormal idle episode
- Unscheduled stop
- Route interruption or early return
- Repair start and completion
- Repeat failure after repair

Compare breakdown-affected tours with similar unaffected tours to estimate downstream lateness, overtime, and undelivered packages.

At vehicle level, examine failure frequency against:

- Kilometers and engine hours
- Idle time
- Vehicle age and type
- Time since last service
- Previous repair category
- Repeated warning-light patterns

With only maintenance timestamps and basic GPS, this supports a basic risk model. Diagnostic codes, odometer readings, and component-level repair data would materially improve predictive maintenance.

## 3.6 Driver behavior and skill differences

After controlling for route difficulty, compare:

- Service-time distribution
- Idling
- Route-sequence choices
- Parking/search time
- Scan compliance
- Late departure patterns
- Fuel or eco-driving measures, if telemetry supports them

Mixed-effects models or matched cohort analysis can estimate whether a persistent driver effect remains after territory, traffic, vehicle, and workload are considered.

Differences may result from route familiarity, scanner usability, training, or dispatch quality—not necessarily poor effort. Results should be used for support and coaching rather than punitive raw rankings.

## 3.7 Failed delivery attempts

Use the package-level process to connect:

> First assignment  first attempt  failure reason  reallocation  re-delivery  final success

Analyze failure rates by:

- Address and customer history
- Time window and actual arrival time
- Notification status
- Day and time
- Building type
- Failure reason
- Driver and route, after normalization

This reveals whether failures are caused primarily by customer absence, inaccurate addresses, arrival outside the requested window, insufficient communication, access problems, or scan-quality issues. The full impact should include the later route slot, additional distance, handling, and customer-service cost.

# 4. Data-Driven Optimization Strategies

## Strategy 1: Rolling, traffic-aware dynamic routing

### Inefficiency targeted
Recurring and incident-based congestion, inaccurate ETAs, growing lateness during the route, and unnecessary detours.

### Root cause addressed
Static routes cannot react to actual traffic, service overruns, failures, or vehicle problems.

### Data and process-mining support
GPS segment histories establish time-dependent travel-time distributions. Conformance analysis identifies where planned estimates repeatedly diverge from actual times. Cumulative delay analysis shows when a route is becoming unrecoverably late.

### Recommended action
Implement a rolling-horizon route optimizer that:

- Updates ETAs from live GPS and traffic
- Reoptimizes remaining stops when lateness risk exceeds a threshold
- Respects customer windows, remaining capacity, breaks, and shift limits
- Freezes the next one or two stops to avoid constant driver disruption
- Prioritizes stops at risk of missing a hard time window
- Logs each revised plan version for later conformance analysis

### Expected KPI impact
- Higher on-time delivery rate
- Lower traffic-delay minutes
- Lower excess distance and fuel per package
- Lower overtime
- Better ETA accuracy

Guardrails should include driver safety, number of route changes, customer notification accuracy, and workload fairness.

---

## Strategy 2: Redesign territories and calibrate base route plans

### Inefficiency targeted
Long or overlapping routes, workload imbalance, excessive planned distance, and chronic route completion failures.

### Root cause addressed
Territories and route sequences may be based on geographic proximity or average assumptions without realistic time-dependent travel and service durations.

### Data and process-mining support
Historical traces reveal:

- Actual travel times by time and road segment
- Actual stop service distributions
- Repeated successful driver deviations
- Route overlap
- Territory-specific failure and congestion patterns
- P90 route completion times and overtime risk

### Recommended action
Periodically redesign delivery territories and daily routes using a capacitated vehicle-routing problem with time windows. The optimizer should use:

- Time-dependent travel-time matrices
- Address-specific or stop-type service times
- Package weight and volume
- Historical first-attempt success risk
- Driver hours and mandatory breaks
- Vehicle compatibility and availability
- Robust buffers based on variability, not only averages

Routes should be balanced by expected workload time, not simply stop count. If process mining shows that time from route assignment or depot scan to departure is a major bottleneck, dispatch cut-off, sorting, and loading procedures should also be redesigned.

### Expected KPI impact
- Lower kilometers per delivered package
- Lower travel-to-service ratio
- More balanced vehicle utilization
- Higher route completion and on-time rates
- Lower overtime and fuel use
- Lower variance in route finish times

---

## Strategy 3: Reduce failed deliveries through risk-based time-window management

### Inefficiency targeted
Failed first attempts, repeated visits, wasted travel, and customer complaints.

### Root cause addressed
Customer absence, poor ETA communication, unrealistic windows, address/access problems, and scheduling high-risk stops at unsuitable times.

### Data and process-mining support
Package journey mining identifies which customer, location, time-window, and failure-reason combinations create the most rework and redelivery cost.

### Recommended action
Introduce:

- Pre-delivery reminders and live ETA notifications
- One-click confirmation or rescheduling
- Alternative safe-place, parcel-locker, or pickup-point options
- Address and access-instruction validation
- Risk scoring for likely failed attempts
- Time-window recommendations based on historical customer availability
- Resequencing of confirmed high-risk deliveries, with customer consent
- A standardized failure-reason taxonomy in the scanner

### Expected KPI impact
- Higher first-attempt success rate
- Higher on-time delivery
- Lower re-delivery kilometers and fuel
- Lower cost per successful package
- Fewer repeated stops and customer complaints

The risk model should be privacy-reviewed and should not unfairly deny service options to particular customer groups.

---

## Strategy 4: Usage- and risk-based predictive maintenance

### Inefficiency targeted
In-route breakdowns, route interruption, vehicle downtime, emergency repairs, and late or undelivered packages.

### Root cause addressed
Maintenance may be based primarily on fixed schedules rather than actual operating severity and warning patterns.

### Data and process-mining support
Vehicle lifecycle traces can relate distance, engine-on time, idling, warning events, maintenance intervals, previous failures, and repair duration to breakdown probability.

### Recommended action
Create a vehicle health-risk score and:

- Inspect vehicles with rising risk before route assignment
- Schedule preventive work during low-demand periods
- Avoid assigning high-risk vehicles to long or time-critical routes
- Keep contingency vehicles available where the breakdown impact is highest
- Analyze repeat repairs and ineffective maintenance variants
- Add diagnostic-code and odometer data if not currently captured

Scheduled manufacturer and safety maintenance must remain hard constraints; predictive models should supplement, not postpone, mandatory work.

### Expected KPI impact
- Fewer in-route breakdowns
- Higher vehicle availability and mean time between failures
- Lower unscheduled downtime and repair cost
- Higher route completion and punctuality
- Lower overtime caused by vehicle substitution or rescue operations

---

## Strategy 5: Targeted driver and stop-practice improvement

### Inefficiency targeted
Excessive idling, high stop-time variability, inefficient parking/access patterns, scan-process errors, and avoidable route deviations.

### Root cause addressed
Differences in route familiarity, scanner usage, parking strategy, eco-driving, and standard operating practices.

### Data and process-mining support
Normalized cohort analysis can identify drivers or teams whose dwell, idling, or route variants differ from comparable peers on similar work.

### Recommended action
Provide targeted interventions rather than general training:

- Route-familiarization support for difficult territories
- Scanner and exception-handling training
- Best-practice sharing from high-performing variants
- Building-access and parking guidance for recurring hotspots
- Eco-driving and anti-idling coaching
- Clear procedures for failed deliveries and breakdown escalation

### Expected KPI impact
- Lower average and P90 stop time
- Lower idling and fuel consumption
- Better scan completeness and conformance
- Lower overtime
- More consistent ETA performance

Safety events, speeding, and employee well-being should be guardrails. Performance should be normalized for route difficulty and used transparently.

# 5. Operational Constraints and Continuous Monitoring

## 5.1 Incorporating operational constraints

The optimization model should distinguish hard constraints from business preferences.

### Hard constraints

- Vehicle weight and volume capacity
- Package/vehicle compatibility
- Legal driver hours
- Mandatory breaks
- Vehicle maintenance and availability
- Road restrictions, access limitations, and low-emission zones
- Hard customer time windows
- Depot opening and return requirements
- Safety requirements

### Soft constraints with penalties

- Overtime
- Early or late service within agreed tolerances
- Excess route changes
- Territory continuity and driver familiarity
- Workload imbalance
- Additional kilometers
- Customer-preferred rather than mandatory windows

The objective should be multi-criteria, minimizing expected lateness, distance, fuel, overtime, failed-delivery risk, and plan instability. It should not optimize route adherence in isolation: strict adherence to a poor plan can reduce performance.

Robust planning should use travel- and service-time distributions, particularly P90 values for critical routes, rather than assuming every stop takes the average time. Dynamic replanning must continuously account for remaining capacity, packages already delivered, driver hours, breaks, and the latest customer commitments.

---

## 5.2 Continuous process-mining monitoring

A monitoring environment should support executive, operational, and diagnostic views.

### Live control-tower dashboard

Track:

- Current vehicle location and remaining route
- Predicted time-window breaches
- Delay accumulated by travel, service, or unplanned stops
- Remaining packages and capacity
- Remaining driver hours and required break
- Prolonged idling or unplanned stationary episodes
- Vehicle-warning or breakdown events
- Current route-plan version and significant deviations

Alerts should be actionable—for example, predicted lateness above a threshold, unplanned stop beyond a defined duration, or risk of exceeding legal hours.

### Daily operations dashboard

Track by depot, route, territory, vehicle, and shift:

- On-time and first-attempt success
- Planned versus actual route map
- Departure delay
- Stop-sequence conformance
- Actual/planned time and distance
- Service-time median and P90
- Traffic-delay minutes
- Failed deliveries and reasons
- Overtime and incomplete routes

Provide trace-level drill-down so an operator can reconstruct a specific tour.

### Weekly process-improvement dashboard

Track:

- Dominant process variants
- New or growing exception variants
- Bottleneck activities and transitions
- Recurring congestion, parking, and failed-delivery hotspots
- ETA bias by segment and time
- Normalized driver and vehicle cohorts
- Redelivery loops
- Dynamic-routing acceptance and effectiveness

### Monthly management and asset dashboard

Track:

- On-time delivery trend
- Cost and fuel per delivered package
- Distance per package
- Vehicle and capacity utilization
- Breakdown frequency, availability, MTBF, and repair duration
- Overtime
- Customer failure and complaint rates
- Benefits realized versus the pre-change baseline

### Data and model health

Monitor:

- GPS coverage and missing intervals
- Scanner completeness
- Clock synchronization
- Unmatched packages or stops
- Percentage of inferred events
- Fuel-data completeness
- Route-plan versioning quality
- ETA and failure-risk model drift

## 5.3 Proving that changes work

Implementation should use controlled pilots:

1. Establish a six-month baseline segmented by season, territory, workload, and vehicle type.
2. Pilot each strategy in matched routes or depots.
3. Compare pilot and control groups using the same KPI definitions.
4. Adjust for volume, traffic, weather, holidays, and route mix.
5. Monitor adverse effects such as unsafe driving, excessive replanning, customer complaints, or workload imbalance.
6. Roll out only when improvements are statistically and operationally credible.
7. Continue conformance and variant monitoring to detect process drift.

This creates a closed improvement loop:

> Discover actual behavior  identify bottleneck  validate cause  implement intervention  monitor conformance and KPIs  recalibrate routes and policies.

The result is not just a one-time route study, but an operational process-mining capability that continuously links dispatch plans, actual vehicle behavior, package outcomes, and vehicle reliability.
