**Explanation of the transformation logic**

**Case identification**  
Cases were defined around the primary work object (the specific document, email conversation, or spreadsheet being manipulated). This produces five coherent process instances:

- `Document1.docx` – drafting / updating a working document (two interrupted sessions).  
- `Annual_Meeting_Email` – the complete handling of one inbound email.  
- `Report_Draft.pdf` – review and annotation of a PDF.  
- `Budget_2024.xlsx` – data update of a spreadsheet.  
- `Quarterly_Report.docx` – work on the main report (brief early activation + later focused editing).

Grouping by the concrete window/document (rather than by pure temporal session or by application alone) yields analyst-friendly cases that correspond to real knowledge-work objects. Interleaved activity is natural: the same case can resume after a gap while other cases run. This is the standard and most useful interpretation for desktop-activity process mining.

**Activity naming**  
Raw low-level system actions were mapped to a small, reusable set of higher-level process steps:

- FOCUS / SWITCH-to-Word or Excel → “Open Document” / “Open Spreadsheet” / “Switch to Document”  
- TYPING → “Edit Document”, “Edit Spreadsheet” or “Compose Reply” (context-dependent)  
- SAVE → “Save Document” / “Save Spreadsheet”  
- CLOSE → “Close Document”  
- CLICK “Open Email \ldots” → “Open Email”  
- SCROLL → “Review Email” / “Review PDF”  
- CLICK “Reply \ldots” → “Reply to Email”  
- CLICK “Send \ldots” → “Send Email”  
- HIGHLIGHT → “Highlight Text”  
- SWITCH events are retained as explicit transition activities so the log remains complete and the hand-over between cases is visible.

The resulting activity vocabulary is consistent across cases, semantically meaningful, and ready for process-discovery, conformance-checking or performance analysis tools (Disco, Celonis, pm4py, ProM, etc.).

**Additional attributes**  
Application, Window and Details (typed text, scroll direction, highlight text, source of switch, \ldots) are kept so that the log remains rich enough for filtering, attribute-based analysis or secondary perspectives while the core triple (Case ID, Activity, Timestamp) satisfies the classic event-log requirements.
