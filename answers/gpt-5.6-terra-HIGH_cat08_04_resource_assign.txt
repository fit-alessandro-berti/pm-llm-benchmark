## 1. Analyze resource behavior and actual assignment patterns

### 1.1 Prepare an analysis-ready event log

Before mining, TechSolve should create a cleaned, enriched incident event log with a consistent event schema:

- **Case ID:** Ticket/incident ID
- **Activity:** Created, Assigned, Work Started, Work Ended, Escalated, Reassigned, Resolved, Closed, Reopened, etc.
- **Timestamp and lifecycle:** Start/complete where available
- **Resource:** Performing agent, dispatcher, system, or team queue
- **Assignment target:** The agent or queue receiving the ticket; this should be a separate field from the person performing the assignment
- **Tier and team:** L1, L2, L3, specialty group
- **Ticket attributes:** Priority, category, channel, affected service, customer group, location, required skill(s), complexity indicator, SLA target
- **Agent attributes:** Skills, proficiency levels, certifications, shift/calendar, tenure, team, capacity
- **Outcome attributes:** Resolved by tier, reassignment count, escalation count, SLA met/breached, reopen status, customer satisfaction if available

Important preparation steps include:

1. **Normalize activities.** For example, “Assign L2,” “Route to L2,” and “Transfer to specialist” may need to map to a standard assignment or escalation event.
2. **Separate assignment actor from assignee.** In the sample, the dispatcher performs “Assign L2,” but the actual recipient is B12 or B15. Both are analytically relevant.
3. **Version skill profiles over time.** Agent skills change. A ticket assigned in April should be compared to the skills held by the agent in April, not their current profile.
4. **Calculate SLA deadlines.** SLA calculations should account for priority, support hours, pauses, customer waiting time, and calendar rules.
5. **Construct queue and work intervals.** For example:
   - Creation to first assignment
   - Assignment to work start
   - Work start to work end
   - Escalation to specialist work start
   - Reassignment to next work start
6. **Flag data-quality issues.** Missing assignment recipients, invalid timestamps, concurrent work events, automated updates, and incomplete skill values can materially distort findings.

The analysis should distinguish between:

- **Elapsed time:** Total calendar time from creation to resolution.
- **Queue/waiting time:** Time assigned but not actively worked.
- **Touch time:** Actual time spent working.
- **Rework time:** Additional work caused by reassignment, reopening, or incorrect routing.

This distinction is essential because SLA breaches are often caused more by waiting and handoffs than by actual technical work.

---

### 1.2 Analyze individual agent and tier performance

The goal is not simply to rank agents, but to understand how resources, skills, workload, and process routing affect outcomes.

#### A. Workload distribution metrics

For each agent, team, skill group, and tier, analyze:

- Number of tickets assigned
- Number of tickets actively worked
- Number resolved
- Open work-in-progress (WIP)
- Average and maximum queue length
- Concurrent active tickets
- Assignment arrival rate by hour/day/week
- Backlog aging
- Percentage of tickets that are reassigned after assignment
- Percentage of tickets escalated
- Percentage of tickets reopened
- Share of P1, P2, P3, and P4 work
- Share of categories and required skills handled

Workload should be adjusted for ticket complexity. An agent handling ten P2 firewall incidents should not be compared directly with an agent handling ten P4 password resets.

Useful views include:

- Heatmaps of ticket arrivals and assignments by day and hour
- Agent-level workload boxplots
- Queue length over time by tier and skill
- Workload distribution by skill group
- Capacity utilization by shift

A key question is whether overloaded agents receive more work despite available agents with equivalent skills.

#### B. Time and productivity metrics

For each agent and tier, calculate:

| Metric | Purpose |
|---|---|
| Assignment-to-start time | Measures queue delay after assignment |
| Active handling/touch time | Measures work effort |
| End-to-resolution time | Measures effectiveness after work begins |
| Total cycle time | Measures end-to-end speed |
| Reassignment delay | Measures delay caused by a handoff |
| Escalation delay | Measures waiting time between tiers |
| Resolution rate | Measures completion effectiveness |
| Reopen rate | Indicates possible quality issues |
| SLA compliance rate | Measures business outcome |
| First-contact resolution rate | Measures L1 effectiveness |

Metrics should be segmented by:

- Priority
- Category
- Required skill
- Channel: phone, email, portal
- Time of day and shift
- Customer group or service
- Agent tier
- Complexity band

For example, an L1 agent may appear slow overall but perform well on high-complexity P2 incidents. Segmenting avoids misleading conclusions.

#### C. L1 first-contact resolution analysis

For L1, TechSolve should measure:

\[
\text{First-Contact Resolution Rate} =
\frac{\text{Tickets resolved by L1 without escalation or reassignment}}{\text{Tickets initially handled by L1}}
\]

This should be broken down by ticket category and required skill. For example:

- Password/access-management tickets may have high L1 resolution.
- Firewall/network incidents may appropriately escalate quickly.
- Certain CRM incidents may be resolvable by L1 if the correct knowledge articles and permissions are available.

Relevant L1 metrics include:

- Percentage resolved at L1
- Average L1 handling time before escalation
- Escalation appropriateness rate
- Repeat escalation patterns by category
- Escalation reason distribution
- SLA impact of attempted L1 resolution versus direct specialist routing

A high escalation rate is not automatically poor. It may be appropriate for complex P1/P2 tickets. The problem is unnecessary or delayed escalation.

### 1.3 Discover actual routing, escalations, and handovers

Process mining can reveal the process TechSolve actually executes, rather than the process described in procedures.

#### A. Process discovery

Using the event log, discover process maps separately for:

- P1/P2 vs. P3/P4 tickets
- Each major category
- Each required skill family
- Tickets resolved at L1
- Tickets escalated to L2/L3
- Tickets with SLA breaches
- Tickets with multiple reassignments

This will show common paths such as:

- Created  Assigned L1  Worked L1  Resolved
- Created  Assigned L1  Escalated L2  Assigned L2  Resolved
- Created  Assigned L1  Escalated L2  Reassigned L2  Escalated L3  Resolved
- Created  Assigned L1  Wait  Reassigned L1  Escalated  Wait  Resolved

The latter paths are likely candidates for assignment redesign.

#### B. Conformance checking against intended routing logic

TechSolve’s intended model may be something like:

1. Ticket is categorized.
2. Ticket is assigned to L1.
3. L1 resolves standard issues or escalates according to defined criteria.
4. L2 or L3 receives tickets matching the appropriate specialty.

Conformance checking compares this intended model with observed behavior. Deviations may reveal:

- Tickets bypassing L1 unexpectedly
- Tickets bouncing between L1 agents
- Repeated L2 reassignments
- Escalations to the wrong specialist group
- Tickets assigned to agents without the required skill
- Unapproved loops, such as L2 returning tickets to L1
- Tickets waiting in unowned queues before assignment

This turns general complaints about “too many transfers” into measurable deviations.

#### C. Resource interaction and handover analysis

A resource handover network can be built where:

- Each node represents an agent, queue, team, or tier.
- Each edge represents a ticket transfer, reassignment, or escalation.
- Edge thickness represents frequency.
- Edge labels show average delay, SLA breach rate, or skill mismatch rate.

Examples of valuable findings:

- A small number of L1 agents may disproportionately escalate to a particular L2 specialist.
- A specific dispatcher may frequently route P2 network tickets to the wrong support group.
- A particular L2 team may be a transfer bottleneck.
- Certain agents may act as informal “go-to” experts, regardless of official team structure.
- Tickets may circulate between the CRM team and database team because skill boundaries are unclear.

Useful social-network measures include:

- **In-degree:** How often an agent receives tickets
- **Out-degree:** How often an agent transfers tickets
- **Betweenness centrality:** Whether an agent acts as a routing bottleneck or informal coordinator
- **Handover delay by edge:** Which transfer relationships create the most waiting
- **Rework-loop frequency:** Which teams repeatedly send tickets back and forth

#### D. Role discovery

Role discovery groups agents based on their actual activity and routing behavior, rather than formal titles.

For example, the log may reveal:

- L1 agents who resolve a high share of Software-App tickets
- L1 agents functioning mainly as dispatchers
- L2 agents specializing in CRM despite being formally grouped as general application support
- L3 specialists routinely completing simple access tickets
- Certain agents receiving exception cases because they have undocumented expertise

This can reveal whether the formal tier/skill structure matches operational reality.

### 1.4 Analyze skill utilization and skill-to-ticket fit

TechSolve should create a **ticket-skill-resource matching matrix**.

For every assignment, determine:

1. What skills were required at that point in the ticket lifecycle?
2. What skills did the assigned agent possess?
3. Was there an exact match, partial match, adjacent skill match, or mismatch?
4. Was the assigned agent more specialized than necessary?
5. Were similarly qualified, less-loaded agents available?

A simple skill-fit classification could be:

| Assignment classification | Meaning |
|---|---|
| Exact match | Agent possesses the required skill at sufficient proficiency |
| Acceptable adjacent match | Agent has a related skill and historically resolves similar cases |
| Under-skilled mismatch | Agent lacks the required skill or proficiency |
| Over-skilled assignment | Specialist handles work resolvable by lower-tier or less-specialized staff |
| Unknown | Required skill or agent skill profile is missing/incomplete |

Examples:

- A ticket requiring `Networking-Firewall` routed to a general desktop support L2 agent is likely a mismatch.
- A simple access reset handled by an IAM specialist may represent over-specialization.
- A CRM ticket routed first to an application generalist and then to a database specialist may suggest incomplete initial skill identification.

Skill utilization metrics should include:

- Ticket volume by required skill
- Available capacity by skill and shift
- Skill demand-to-capacity ratio
- Average queue delay by required skill
- SLA compliance by required skill
- Reassignment rate following a skill mismatch
- Resolution rate by agent-skill pairing
- Specialist utilization on low-complexity work
- Percentage of work completed at the lowest capable tier

A particularly useful measure is:

\[
\text{Skill Mismatch Rate} =
\frac{\text{Assignments where assigned agent lacks required skill}}{\text{Total assignments with a known required skill}}
\]

This should be evaluated by dispatcher, category, priority, shift, and team.

## 2. Identify resource-related bottlenecks and operational issues

### 2.1 Identify skill-capacity bottlenecks

A skill bottleneck occurs when demand for a required skill exceeds the effective available capacity of agents possessing that skill.

For each skill, analyze:

- Incoming ticket volume by hour/day/week
- Number of qualified agents available by shift
- Average handling time
- Queue length and queue aging
- Assignment-to-start delay
- SLA breach rate
- Reassignment rate
- Backlog level

For example, if `Networking-Firewall` tickets have:

- Long assignment-to-start delays,
- High P2 SLA breaches,
- Repeated transfers,
- Limited availability of qualified agents,

then the likely issue is either insufficient firewall capacity, poor routing, or both.

A demand-capacity indicator can be calculated as:

\[
\text{Skill Load Ratio} =
\frac{\text{Incoming workload hours for a skill}}{\text{Available qualified agent hours}}
\]

A sustained ratio above 1 indicates that demand exceeds available capacity.

---

### 2.2 Quantify the impact of reassignments and escalations

Reassignments should be analyzed as explicit process events rather than treated as generic inefficiency.

For every reassignment, measure:

- Time from reassignment to next assignment
- Time from next assignment to work start
- Number of reassignment loops
- Whether required skill changed
- Whether assignee tier changed
- Whether SLA risk increased
- Whether the ticket was ultimately resolved by the final assignee
- Whether the prior assignee had a skill mismatch

A useful metric is:

\[
\text{Average Reassignment Delay} =
\text{Average}(\text{Next Work Start} - \text{Reassignment Timestamp})
\]

Also calculate:

\[
\text{SLA Breach Rate by Reassignment Count}
\]

For example, findings might show:

- Tickets with no reassignment breach SLA 8% of the time.
- Tickets with one reassignment breach SLA 19% of the time.
- Tickets with two or more reassignments breach SLA 42% of the time.

This does not automatically prove that reassignment caused every breach, because complex incidents may both require transfers and take longer. Therefore, comparisons should control for priority, category, complexity, and required skill.

---

### 2.3 Measure the impact of incorrect initial assignment

Initial assignment quality can be assessed using indicators such as:

- Ticket reassigned within a short period, such as 15–30 minutes
- Ticket reassigned before any meaningful work begins
- Required skill changed after initial assessment
- First assigned agent lacked the required skill
- Initial assignment led to escalation that could have been predicted at ticket creation
- Ticket was assigned to a queue with no qualified available resource

For example:

\[
\text{Incorrect Initial Assignment Rate} =
\frac{\text{Tickets reassigned/escalated due to skill or category mismatch}}{\text{Total initially assigned tickets}}
\]

This can be broken down by:

- Dispatcher
- Intake channel
- Category
- Priority
- Time of day
- Ticket origin
- L1 agent
- Service/application

If tickets from the portal have a much higher incorrect-assignment rate than phone tickets, the portal categorization form may need improvement.

---

### 2.4 Identify overloaded and underutilized resources

Overload should be assessed using both workload volume and operational outcomes.

An overloaded agent may show:

- Persistently high assigned WIP
- Long queue delays before work starts
- High number of concurrent cases
- Increased reassignment or escalation behavior
- Lower SLA compliance
- More after-hours work
- Increased reopen rate
- High dependency from other teams

An underutilized agent may show:

- Low assigned workload despite matching skills
- Long idle periods while qualified tickets wait in a queue
- Lower incoming assignment rate than peers
- Capacity available during skill-specific bottlenecks

A useful fairness measure is the variation in workload among agents with equivalent skills. If one CRM-skilled L2 agent consistently has 20 open tickets while another has 5, the routing logic is likely not workload-aware.

However, performance conclusions should be reviewed with team leads. Differences may reflect seniority, mentoring responsibilities, shift patterns, customer assignments, or unrecorded work.

---

### 2.5 Link assignment patterns to SLA breaches

Create an SLA-risk process view that compares compliant and breached tickets.

Analyze breach rates by:

- Number of assignments
- Number of escalations
- Initial skill-match status
- Final skill-match status
- Tier path
- Queue wait time
- Assigned agent workload at assignment time
- Required skill
- Assignment hour/day
- Priority and category
- Channel
- Reopen status

A statistical model can estimate which factors are associated with breach risk. For example:

\[
P(\text{SLA Breach}) =
f(\text{Priority}, \text{Skill Mismatch}, \text{Queue Delay}, \text{Reassignments}, \text{WIP}, \text{Category})
\]

This could reveal findings such as:

- P2 network tickets assigned to non-firewall-skilled agents are three times more likely to breach SLA.
- Tickets reassigned after more than one hour have a significantly higher breach probability.
- P3 CRM tickets assigned during evening shifts have long waits because the relevant skill is unavailable.
- L2 reassignments between CRM and database groups account for a disproportionate share of P3 breaches.

The results should be treated as evidence of operational drivers, not as a basis for punitive individual performance management.

## 3. Root cause analysis for assignment inefficiencies

### 3.1 Likely root causes

Several root causes may coexist.

#### A. Assignment rules ignore skill and workload

Round-robin routing can distribute ticket count evenly while distributing effort and risk unevenly. It may assign a P2 firewall incident to a general L2 agent simply because it is their turn.

Symptoms in the event log:

- Similar agents receive work regardless of skill fit
- High reassignment rates after round-robin assignment
- Long delays before tickets reach a qualified specialist
- Underutilized qualified agents while tickets wait elsewhere

#### B. Incomplete or inaccurate skill profiles

Agent skill records may be outdated, too broad, or not linked to proficiency levels.

For example:

- An agent is listed as “Database-SQL” but only supports reporting databases, not production incidents.
- A technically capable L1 agent has undocumented CRM knowledge.
- A specialist is classified under one team but routinely resolves another category.

The sample incident illustrates why this matters: Agent B12 appears to have both App-CRM and DB-SQL skills, yet the ticket is reassigned for a database need. This could indicate an outdated skill profile, insufficient proficiency, an unrecorded sub-specialty, or an unclear required-skill definition.

#### C. Poor ticket categorization and skill identification

Initial ticket data may be too generic, inaccurate, or incomplete.

Examples:

- “Software issue” is selected instead of “CRM integration database failure.”
- A firewall issue is classified as generic network connectivity.
- A user selects a category based on symptoms rather than the affected underlying service.

Symptoms include:

- Frequent skill changes after L1 investigation
- High reassignment rates for portal-created tickets
- Specific categories having high downstream correction rates
- Different routing outcomes for the same category depending on the agent

#### D. Lack of real-time workload and availability visibility

Even correct skill-based routing can fail if the dispatcher cannot see:

- Whether qualified agents are on shift
- Current queue length
- Active ticket load
- Urgency of open work
- Upcoming SLA deadlines
- Whether an agent is handling a major incident

Symptoms include:

- Tickets waiting despite available qualified resources
- Specialists overloaded while similarly skilled peers are idle
- Assignments to agents who are off shift or unavailable
- Work concentrated on a few informal experts

#### E. Insufficient L1 training, tools, or authority

L1 may escalate tickets that could be resolved at first contact because of:

- Missing knowledge articles
- Lack of diagnostic tools
- No access to reset accounts or perform approved configuration actions
- Lack of confidence with certain ticket types
- Ambiguous escalation rules

Symptoms include:

- High L1 escalation rates for recurring, low-complexity categories
- Large differences in resolution rates among L1 agents for similar tickets
- L2 resolution of tickets with very low touch time after escalation
- Specialist work on routine tasks

---

### 3.2 Variant analysis

Variant analysis compares process paths that produce good outcomes with those that produce poor outcomes.

For example:

**Smooth P3 CRM ticket variant**

> Created  L1 assigned  L1 worked  L2 CRM assigned  L2 resolved

**Problematic P3 CRM ticket variant**

> Created  L1 assigned  L1 worked  L2 generalist assigned  Reassigned  Database team assigned  Wait  L3 assigned  Resolved

Compare the two variants on:

- Ticket attributes
- Initial category and required skill
- Assignment sequence
- Queue delays
- Agent workload at each handover
- Tier path
- Number of reassignments
- SLA outcome
- Final resolving skill

This analysis can identify factors that distinguish successful cases from problematic ones. For example, successful tickets may be initially categorized as “CRM database integration,” while problematic ones are categorized only as “Software-App.”

---

### 3.3 Decision mining

Decision mining examines choices at decision points, such as:

- Assign to L1 or direct to L2?
- Escalate or continue troubleshooting?
- Assign to CRM team or database team?
- Assign to specialist A or specialist B?

A decision model can use historical attributes such as:

- Priority
- Category
- Description keywords
- Affected service
- Required skill
- Channel
- Customer type
- Current workload
- Available skills
- Time of day
- Previous activity results

The model can identify decision rules associated with good outcomes.

Example insight:

> For P2 incidents categorized as Network with keywords “VPN,” “firewall,” or “blocked port,” direct assignment to the firewall-skilled L2 queue results in lower resolution time and fewer reassignments than generic L1-first routing.

Decision mining should not blindly automate past decisions. Historic routing may itself be inefficient. Models should be evaluated against desired outcomes: skill fit, SLA compliance, low rework, and appropriate use of specialist capacity.

## 4. Data-driven resource assignment strategies

TechSolve should adopt a combination of strategies rather than relying on one routing rule.

### Strategy 1: Skill-based routing with proficiency and eligibility rules

#### Issue addressed

- Incorrect initial assignments
- Skill mismatches
- Excessive reassignments
- Specialists receiving tickets outside their expertise
- Delays in reaching the correct L2/L3 group

#### Approach

Implement routing based on a structured skill taxonomy:

- Primary skill: e.g., `Networking-Firewall`
- Related skills: e.g., `Networking-VPN`, `Networking-Routing`
- Proficiency level: basic, intermediate, advanced, expert
- Authorization level: whether the agent is allowed to perform production changes
- Tier eligibility: L1, L2, L3
- Service/application ownership
- Shift availability

An assignment engine should first identify eligible agents who meet minimum skill and authorization requirements. It should not assign a critical firewall incident to an agent who only has generic network knowledge.

A routing score could be calculated as:

\[
\text{Assignment Score} =
w_1(\text{Skill Fit}) +
w_2(\text{Proficiency}) -
w_3(\text{Current WIP}) -
w_4(\text{SLA Risk}) -
w_5(\text{Recent Context Switching})
\]

#### Process mining insight used

Process mining identifies:

- Actual skill-to-resolution relationships
- Historical reassignment paths
- Skills associated with long queues
- Agents who successfully resolve certain ticket types
- Cases in which a specialist was unnecessarily involved

#### Data required

- Agent skill inventory and proficiency levels
- Skill validity dates and training history
- Ticket category, affected service, and required skills
- Historical ticket outcomes
- Assignment and reassignment history
- Agent availability and shift calendar

#### Expected benefits

- Fewer incorrect first assignments
- Reduced reassignment loops
- Faster assignment-to-start time
- Better specialist utilization
- Higher SLA compliance, especially for P2 and P3 tickets

---

### Strategy 2: Workload-aware and SLA-aware assignment

#### Issue addressed

- Uneven workload distribution
- Overloaded specialists
- Idle qualified agents
- Tickets waiting despite available capacity
- SLA breaches caused by queue delay

#### Approach

Replace simple round-robin assignment with dynamic assignment that considers:

- Current active WIP
- Age of assigned tickets
- Ticket priority
- Time remaining to SLA target
- Estimated handling time
- Current queue size
- Agent shift availability
- Skill fit
- Recent workload and context switching
- Planned absences or major incident involvement

The objective should be to assign tickets to the most suitable available qualified agent, not simply the next agent in a rotation.

For example, a P2 ticket may be routed to the qualified agent with the lowest predicted completion time, while a P4 ticket may be placed in a balanced queue.

#### Process mining insight used

The mined log provides:

- Historical service-time distributions by category, skill, and agent tier
- Typical queue delays by team and shift
- Agent workload patterns linked to SLA breaches
- Demand peaks by hour, day, and service

#### Data required

- Near-real-time queue and WIP data
- Agent schedules and availability
- Ticket priority and SLA deadline
- Historical handling times
- Agent skill eligibility
- Current assignment status

#### Expected benefits

- More balanced workload
- Lower waiting times
- Reduced SLA breaches
- Better responsiveness for P2 tickets
- Less dependence on informal “hero” specialists

---

### Strategy 3: Predictive ticket triage and required-skill recommendation

#### Issue addressed

- Poor initial categorization
- Incorrect skill identification
- Delayed specialist routing
- Manual dispatcher inconsistency

#### Approach

Use historical tickets to build a predictive model that recommends:

- Ticket category
- Required skill(s)
- Likely resolver tier
- Estimated complexity
- Estimated resolution time
- Probability of escalation
- Recommended assignment queue or agent group

Inputs may include:

- Free-text description
- Subject line
- Customer-reported symptoms
- Affected application or configuration item
- Channel
- Priority
- Customer group
- Historical incidents from the same service
- Keywords such as “VPN,” “firewall,” “SQL,” “CRM,” “login,” or “access denied”

The recommendation should initially support dispatchers rather than fully automate decisions. Confidence thresholds should determine whether routing is automatic or requires human confirmation.

#### Process mining insight used

Process mining identifies the final resolving team and skill, which can be used as a more accurate training label than the initial category.

For example, if tickets initially categorized as “Software-App” often end in the database team after two transfers, this indicates a pattern suitable for predictive triage.

#### Data required

- Historical ticket descriptions and categories
- Final resolver team and skill
- Assignment path
- Resolution outcome
- Reassignment count
- SLA outcome
- Service and configuration item data

#### Expected benefits

- Improved classification at intake
- More direct routing to appropriate skills
- Reduced L1/L2 transfers
- Faster resolution for recurring issue types
- Lower dispatcher workload

---

### Strategy 4: Evidence-based L1 resolution and escalation rules

#### Issue addressed

- Avoidable L1 escalations
- Excessive specialist involvement in simple work
- Long L1 troubleshooting before inevitable escalation
- Inconsistent L1 escalation decisions

#### Approach

Use historical process data to define category-specific L1 decision rules.

Examples:

- If L1 resolves 85% of standard access-reset cases within 10 minutes, retain these at L1 and provide automation/knowledge support.
- If P2 firewall-related incidents escalate from L1 95% of the time and L1 work adds 25 minutes before transfer, route directly to the appropriate network specialist queue.
- If CRM incidents can be resolved by L1 only when specific diagnostic results are available, create a guided triage checklist before escalation.

The goal is not simply to reduce escalations. It is to make escalations faster and more appropriate.

#### Process mining insight used

Analyze:

- L1 resolution success by category and agent
- L1 time spent before escalation
- L2 touch time following escalation
- SLA outcomes of L1-first versus direct-routing variants
- Recurrent patterns of avoidable escalation

#### Data required

- L1 activity logs
- Escalation reasons
- Resolution tier
- Ticket category and skill
- Knowledge article usage
- Diagnostic results where available
- L2/L3 resolution outcomes

#### Expected benefits

- Better first-call resolution for appropriate ticket types
- Faster direct escalation for specialist-only cases
- Reduced specialist workload on routine cases
- Lower total cycle time
- More consistent L1 behavior

---

### Strategy 5: Dynamic capacity allocation and cross-training

#### Issue addressed

- Recurring skill bottlenecks
- Peak-hour SLA failures
- Underutilized agents with transferable skills
- Over-reliance on a few specialists

#### Approach

Use demand forecasts from the event log to adjust staffing and skills dynamically.

Examples:

- Schedule more firewall-skilled staff during recurring network incident peaks.
- Temporarily shift trained L1 or L2 staff to high-demand categories.
- Create a flexible “surge” support pool for P2/P3 backlogs.
- Cross-train selected L1 agents in high-volume, low-to-medium-complexity CRM or access-management work.
- Maintain backup coverage for scarce skills such as database or IAM support.

#### Process mining insight used

The log reveals:

- Demand peaks by skill, day, and time
- Chronic backlog patterns
- Skills with sustained overload
- Ticket types commonly escalated but rapidly resolved by specialists
- Candidates for cross-training based on demonstrated historical performance

#### Data required

- Arrival volumes by category and skill
- Shift schedules
- Agent skill profiles
- Training records
- Handling times and queue data
- Seasonal and business-cycle patterns

#### Expected benefits

- Lower skill-specific backlog
- Better resilience during demand peaks
- Reduced dependency on individual experts
- Improved SLA compliance
- More efficient use of available capacity

## 5. Simulation, implementation, and continuous monitoring

### 5.1 Use process simulation before implementation

TechSolve should use discrete-event business process simulation based on the mined process model.

The simulation should model:

- Ticket arrival rates by hour, day, priority, category, and channel
- Actual process variants
- L1, L2, and L3 routing paths
- Skill-specific queues
- Agent schedules and availability
- Agent capacity and concurrent work limits
- Historical handling-time distributions
- Escalation probabilities
- Reassignment probabilities
- SLA targets and breach rules
- Priority queue behavior
- Skill eligibility constraints

Scenarios to simulate could include:

1. Current round-robin assignment baseline
2. Skill-based routing only
3. Skill-based plus workload-aware routing
4. Predictive triage plus direct routing for high-confidence cases
5. Enhanced L1 knowledge and revised escalation rules
6. Additional capacity for the most constrained skills
7. Cross-training selected L1/L2 agents

Each scenario should be run multiple times to account for demand variability.

Key simulation outcomes include:

- SLA compliance by priority
- Average and percentile resolution time
- Assignment-to-start delay
- Queue length by skill
- Reassignment rate
- Escalation rate
- Specialist utilization
- L1 first-contact resolution
- Workload balance
- Cost or staffing impact

Simulation is especially valuable because it can reveal unintended consequences. For example, direct-routing more tickets to L2 may reduce transfer time but overload a scarce specialist group unless capacity rules are also adjusted.

---

### 5.2 Implementation approach

A phased rollout is preferable to a large-scale immediate change.

#### Phase 1: Diagnose and establish baseline

- Clean and validate the event log.
- Build process maps and resource dashboards.
- Define baseline KPIs for P2 and P3 performance.
- Validate findings with dispatchers, L1, L2, L3, and service owners.

#### Phase 2: Pilot selected routing changes

Select one or two high-volume categories, such as:

- Access Management
- CRM incidents
- Network/firewall incidents

Pilot skill-based and workload-aware routing for these categories first.

#### Phase 3: Compare pilot outcomes

Use process mining to compare pilot cases against a comparable baseline group, controlling for priority, ticket type, and demand period.

#### Phase 4: Scale and refine

Expand successful routing rules to additional categories, continuously refining skill definitions, thresholds, and escalation criteria.

---

### 5.3 Post-implementation monitoring dashboards

Process mining dashboards should continuously monitor both outcomes and process behavior.

#### A. Assignment quality dashboard

Track:

- Skill-match rate
- Incorrect initial assignment rate
- Reassignment rate
- Number of assignments per ticket
- Direct-to-correct-team routing rate
- Assignment-to-work-start time
- Assignment decisions by dispatcher, queue, and category

#### B. SLA and cycle-time dashboard

Track:

- SLA compliance by priority
- SLA compliance by required skill
- SLA compliance by tier path
- Time remaining to SLA at first assignment
- Queue delay versus touch time
- Resolution-time percentiles, not only averages
- Breach rate by reassignment count

#### C. Workload and utilization dashboard

Track:

- WIP by agent, skill, and tier
- Queue aging
- Skill-specific backlog
- Agent capacity utilization
- Workload distribution among similarly skilled agents
- Overload alerts
- Underutilized qualified capacity
- Specialist time spent on low-complexity work

#### D. Escalation and rework dashboard

- Escalation rate by category and skill
- Escalation appropriateness rate

- Reopen rate

#### E. Process conformance dashboard

- Deviation from intended routing rules

#### F. Predictive-model monitoring

If predictive triage is deployed, monitor:

- Classification accuracy
- Recommendation acceptance rate
- Skill-routing accuracy
- False-routing rate
- Drift in ticket categories or descriptions
- SLA outcomes for model-routed versus manually routed tickets

---

## Overall recommendation

TechSolve should move from a primarily tier-based and round-robin assignment model toward an integrated routing model that considers:

1. **Skill fit and proficiency**
2. **Current workload and availability**
3. **Ticket priority and SLA risk**
4. **Predicted complexity and likely resolver group**
5. **Evidence-based L1 escalation rules**
6. **Dynamic capacity planning by skill demand**

Process mining provides the evidence base for this redesign. It can identify where tickets actually travel, quantify the delay and SLA impact of poor routing, expose skill bottlenecks and informal workarounds, test improvements through simulation, and continuously monitor whether the redesigned assignment logic is delivering faster, more balanced, and more reliable IT support.
