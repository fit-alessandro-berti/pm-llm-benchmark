## Process overview

The process handles a customer request from receipt through validation or feasibility assessment, optional managerial approval, invoicing, and final confirmation. The main distinction is whether the request is **standard** or **custom**:

- A **standard request** follows predefined rules and requires validation, credit and inventory checks, and delivery-date calculation.
- A **custom request** requires a feasibility assessment. If feasible, a custom quotation is prepared; otherwise, the customer is notified and the case ends.

Requests that remain viable eventually converge into a common approval and invoicing stage.

---

## Step-by-step explanation

### 1. Start and request receipt

**Start Event  Task A: “Receive Customer Request”**

This task represents accepting and recording the customer’s request. It may include:

- Capturing customer and order details
- Recording requested products, services, quantities, or customizations
- Checking that enough information exists to classify the request
- Assigning a request or case identifier

The process then determines how the request must be handled.

---

### 2. Request-type decision

**XOR Gateway: “Check Request Type”**

An exclusive, or XOR, gateway selects exactly one outgoing path based on the request type:

- **Standard request  Task B1**
- **Custom request  Task B2**

Because this is an XOR gateway, a single request should not follow both paths. The classification conditions should be mutually exclusive and ideally cover all possible request types.

---

## Standard request path

### 3. Standard validation

**Task B1: “Perform Standard Validation”**

This verifies that the request conforms to established products, policies, and ordering rules. It can include:

- Checking required fields
- Confirming that the requested item is part of the standard offering
- Validating quantities, prices, terms, and customer eligibility
- Detecting policy exceptions

After validation, two independent checks are initiated.

### 4. Parallel checks

**AND Gateway: “Run Parallel Checks”**

A parallel, or AND, gateway activates all outgoing branches. Therefore, both of the following tasks start:

- **Task C1: “Credit Check”**  
  Determines whether the customer has sufficient credit, acceptable payment history, or an appropriate credit limit.

- **Task C2: “Inventory Check”**  
  Determines whether the requested items are available or can be supplied within the required timeframe.

These checks may occur simultaneously because neither necessarily depends on the other.

### 5. Parallel join

**“All Parallel Checks Completed” — AND Join**

The matching parallel join waits until both the credit check and inventory check are complete. The process cannot continue after only one result is received.

This synchronization is important: the delivery date should not be calculated until both commercial and supply-related information are available.

### 6. Delivery-date calculation

**Task D: “Calculate Delivery Date”**

Using inventory availability, lead times, fulfillment capacity, and possibly the outcome of the credit review, the process calculates a proposed or committed delivery date.

Completion of Task D marks the end of the standard-specific processing before the common approval stage.

---

## Custom request path

### 7. Custom feasibility analysis

**Task B2: “Perform Custom Feasibility Analysis”**

This evaluates whether the requested customization can be delivered. The analysis may consider:

- Technical feasibility
- Engineering or design effort
- Production capability
- Required materials and suppliers
- Cost and profitability
- Lead time
- Regulatory, contractual, or operational constraints

### 8. Feasibility decision

**XOR Gateway: “Is Customization Feasible?”**

Exactly one of two paths is selected:

#### If feasible

**Task E1: “Prepare Custom Quotation”**

A tailored quotation is produced, normally including:

- Scope and specifications
- Custom price
- Delivery or implementation schedule
- Assumptions and exclusions
- Commercial terms
- Quotation validity period

After this task, the custom request proceeds to the common approval stage.

#### If not feasible

**Task E2: “Send Rejection Notice”  End Event**

The customer is informed that the customization cannot be offered. The notice may include the reason, alternatives, or suggestions for modifying the request.

This path terminates immediately. It does not proceed to approval, invoicing, or confirmation.

---

## Convergence of the standard and custom paths

The successful branches converge after:

- **Task D** for a standard request, or
- **Task E1** for a feasible custom request.

Because the initial request-type gateway was exclusive, only one of these branches can be active for a given process instance. Therefore, the convergence is an **exclusive merge**, not a parallel synchronization. It should not wait for both Task D and Task E1.

In formal BPMN, this could be shown with an explicit converging XOR gateway, although a simple merge through sequence flows may also be used when the meaning is clear.

---

## Approval stage

### 9. Determine whether approval is required

**XOR Gateway: “Is Approval Needed?”**

This gateway applies business rules to determine whether managerial approval is necessary.

Possible approval triggers could include:

- The order or quotation exceeds a monetary threshold
- A discount exceeds an authorized limit
- Credit risk is high
- Profit margin is below a target
- The delivery commitment is exceptional
- Nonstandard commercial terms are proposed
- The request is custom or carries significant technical risk
- A policy exception has been identified

The exact approval criteria are not specified in the pseudo-model and would need to be defined as business rules.

#### If approval is not needed

The process goes directly to:

**Task G: “Generate Final Invoice”**

#### If approval is needed

The process continues to:

**Task F: “Obtain Manager Approval”**

---

### 10. Manager review

**Task F: “Obtain Manager Approval”**

A manager reviews the proposed transaction, including price, risk, delivery commitments, quotation details, and any exceptions.

The manager’s response is evaluated by another exclusive gateway.

### 11. Approval decision

**XOR Gateway: “Is Approval Granted?”**

There are two possible outcomes:

#### If approval is granted

The process moves to:

**Task G: “Generate Final Invoice”**

#### If approval is not granted

The process moves to:

**Task H: “Re-evaluate Conditions”**

A denied approval is therefore treated as a request for rework rather than an immediate rejection.

---

## Rework and loop behavior

### 12. Re-evaluate conditions

**Task H: “Re-evaluate Conditions”**

This task addresses the reasons for the approval denial. Possible rework includes:

- Revising the price or discount
- Changing payment terms
- Adjusting quantities
- Proposing a different delivery date
- Reducing or changing the customization scope
- Obtaining additional information
- Improving margin or reducing risk
- Correcting errors in the proposal

The rework then returns to a path-specific task:

- For a **custom request**, the process loops back to **Task E1: “Prepare Custom Quotation.”**
- For a **standard request**, it loops back to **Task D: “Calculate Delivery Date.”**

This preserves the original request type. A standard request should not accidentally re-enter the custom quotation path, and vice versa.

After Task E1 or Task D is performed again, the intended interpretation is that the request returns to the common approval logic. The revised result is then reassessed:

1. Determine whether approval is still required.
2. If required, obtain approval again.
3. If approved—or if approval is no longer required—generate the invoice.

This loop can repeat until the request is approved or otherwise resolved. The pseudo-model does not show a maximum number of retries or an abandonment option. In a production model, it may be useful to add an exit such as “Rework unsuccessful,” “Customer declines revised terms,” or “Maximum review attempts reached.”

---

## Finalization

### 13. Generate final invoice

**Task G: “Generate Final Invoice”**

This task creates the final billing document based on the validated standard order or approved custom quotation. It is reached when:

- Approval was not required, or
- Approval was required and granted.

The invoice should reflect the finalized price, terms, scope, quantities, and applicable taxes or charges.

### 14. Send customer confirmation

**Task I: “Send Confirmation to Customer”**

The customer receives confirmation of the accepted request. Depending on the business context, this may include:

- The final invoice
- Confirmed scope or order details
- Delivery date
- Payment instructions
- Reference or tracking number
- Relevant terms and contact information

The process then reaches the final **End Event**.

---

## Summary of gateway meanings

| Gateway | Type | Meaning |
|---|---|---|
| Check Request Type | XOR split | Selects either the standard path or the custom path |
| Run Parallel Checks | AND split | Starts both credit and inventory checks |
| All Parallel Checks Completed | AND join | Waits for both checks before continuing |
| Is Customization Feasible? | XOR split | Selects either quotation preparation or rejection |
| Standard/custom convergence | XOR merge | Combines alternative successful paths without waiting for both |
| Is Approval Needed? | XOR split | Determines whether management review can be bypassed |
| Is Approval Granted? | XOR split | Sends approved work to invoicing or denied work to re-evaluation |

---

## Key differences between standard and custom requests

| Aspect | Standard request | Custom request |
|---|---|---|
| Initial assessment | Standard validation | Feasibility analysis |
| Operational checks | Credit and inventory checks in parallel | Technical/commercial feasibility review |
| Main output before approval | Calculated delivery date | Custom quotation |
| Early termination | Not explicitly modeled | Infeasible customization is rejected |
| Rework target after approval denial | Recalculate delivery date | Revise custom quotation |

---

## Modeling clarifications

A few points would benefit from being explicit in a formal BPMN diagram:

1. **Add an explicit XOR merge before the approval stage.**  
   This makes it clear that Task D and Task E1 are alternative incoming paths, not parallel paths that must both finish.

2. **Make the rework routing explicit.**  
   After Task H, an XOR gateway based on the stored request type could route the process back to Task D or Task E1.

3. **Show the return to approval after rework.**  
   Sequence flows from the repeated Task D or Task E1 should clearly return to “Is Approval Needed?” or directly to a renewed approval review, depending on the business rule.

4. **Define failure outcomes for standard checks.**  
   The model states that credit and inventory checks occur but does not show what happens if credit is unacceptable or inventory is unavailable.

5. **Define a loop exit other than eventual approval.**  
   An end state for unsuccessful rework, customer cancellation, or repeated denial would prevent an unlimited loop.

Overall, the process separates standard and custom handling early, synchronizes independent checks for standard work, terminates infeasible custom requests, and reunifies all viable requests for conditional approval, invoicing, and customer confirmation.
