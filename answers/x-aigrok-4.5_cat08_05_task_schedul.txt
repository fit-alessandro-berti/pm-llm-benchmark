**1. Analyzing Historical Scheduling Performance and Dynamics**

Process mining begins with the MES event log (XES or CSV converted to event log with case ID = Job ID, activity = Task/Event Type + Activity/Task, timestamp, resources = Machine ID / Operator ID, and attributes for priority, due date, planned/actual duration, setup flag, notes). Preprocess to clean timestamps, resolve incomplete cases, enrich with derived attributes (remaining operations from typical routing discovery, job similarity features for setups such as material type or geometry if available in notes/attributes, cumulative progress).

**Reconstruction of flows and machine sequences:**
- Apply process discovery (Inductive Miner, Heuristics Miner, or Fuzzy Miner) on the full log to obtain the actual multi-perspective process model of job routings (cutting  milling  ...). Case-centric views and Directly-Follows Graphs (DFGs) reconstruct end-to-end flows and variants.
- Filter/project the log *per resource* (Machine ID) and mine ordered event sequences. This yields the actual execution sequence (and interleaving) of tasks/setups on each machine, enabling reconstruction of the realized schedule as a Gantt-like timeline or resource lifecycle model. Dotted charts and performance spectra visualize concurrency, queuing, and machine timelines.
- Case-aware and resource-aware perspectives (combined via multi-perspective process mining) link job progress to machine occupancy.

**Specific metrics and techniques:**
- *Job flow times, lead times, makespan distributions*: Case-level cycle time (release to final completion) and sojourn time analysis. Use performance enhancement (annotated DFGs or Petri nets) and statistical process mining (histograms, boxplots, CDFs of lead times). Makespan per planning horizon via aggregation of concurrent cases. Distributional analysis (Mean, median, 95th percentile, coefficient of variation) reveals unpredictability.
- *Task waiting times (queue times)*: Derive from “Queue Entry”  “Setup Start”/“Task Start” timestamps per machine/work center. Bottleneck analysis (e.g., Tª or waiting-time heatmaps) and queue-length traces quantify averages, peaks, and machine-specific waiting. Performance spectra or dotted charts show waiting patterns.
- *Resource utilization (machine/operator)*: Project log on resource activities. Productive time = sum of actual task durations; setup time = sum of Setup Start–End; idle/starvation = periods without occupation (gaps after accounting for breakdowns); availability = total time less breakdowns. Utilization = (productive + setup)/available time. Separate operator attachment if logs allow. Resource profiles and solid/overlay DFGs quantify this per machine class.
- *Sequence-dependent setup times*: For each machine, sort events chronologically, identify consecutive jobs (preceding Case ID from log or reconstructed schedule). Extract Setup duration (actual) wherever Setup Required = TRUE, and associate with from–to job attributes (or previous job note). Build a setup-time matrix/estimator (historical averages or regression on job similarity features: material, dimensions, tooling group). Cluster jobs by setup-similarity and mine conditional distributions. This quantifies both average and sequence-dependent variability beyond the planned 20 min.
- *Schedule adherence and tardiness*: For each case, completion timestamp vs. Order Due Date  lateness, tardiness (max(0, L)), earliness. Aggregate low on-time delivery rate, mean/median tardiness, and weighted tardiness (by priority/penalty). Conformance checking against due-date milestones or simple baseline schedules detects deviations. Frequency of priority changes and their correlation with tardiness.
- *Impact of disruptions*: Filter breakdown Start/End events and “Priority Change”/hot-job releases. Perform impact analysis: (a) before/after performance on affected machines and downstream cases (waiting-time inflation, flow-time increase); (b) causal variant comparison (cases concurrent with breakdown vs. others); (c) cascade detection via process visualization and residual analysis (extra waiting on non-broken resources). Breakdown frequency, MTTR, and urgent-job insertion effects on WIP and makespan distributions are quantified. Concurrency analysis shows how disruptions amplify contention.

These techniques (discovery + performance enhancement + custom projections + statistical aggregation) provide a multi-view reconstruction far richer than local dispatching logs.

**2. Diagnosing Scheduling Pathologies**

Process-mining outputs directly surface pathologies:
- *Bottleneck resources and throughput impact*: Performance DFGs, bottleneck miner, and workload/throughput analysis identify chronic high-utilization/high-waiting machines (e.g., certain CNC mills acting as capacity-constrained resources). Quantify lost throughput by measuring cases waiting upstream and idle time downstream (starvation count). SPECTRA or heatmaps show temporal concentration of queues.
- *Poor task prioritization*: Variant analysis (on-time vs. significantly late jobs; high-priority vs. medium) combined with decision mining or attribute projection reveals frequent inversion: high/urgent jobs delayed behind lower-priority ones under FCFS/EDD mixtures. Lead-time vs. remaining-due analysis and priority-change frequency expose reactive firefighting that creates more delays.
- *Suboptimal sequencing inflating setups*: Resource-sequence mining + setup-time matrix shows many high-cost from–to transitions (long actual setups). Comparative total-setup-time analysis (actual realized vs. potential minimum via historical matrix) quantifies excess setup minutes. Clusters of dissimilar jobs processed consecutively on bottleneck machines are highlighted.
- *Downstream starvation*: Cross-resource timelines and developmental process models reveal periods where bottleneck-delayed jobs cause idle time on flexible downstream resources. Concurrent case analysis shows WIP balloons at bottleneck queues while later stages starve.
- *Bullwhip/WIP variability*: Time-series of queue lengths (from queue-entry events) and WIP (active cases) exhibit oscillating inventory. Correlation with local dispatching choices and disruption events quantifies amplification of variability (scheduling-induced bullwhip).

Variant comparison, bottleneck + performance analysis, and resource-contention period extraction provide quantitative evidence (e.g., “30 % of high-priority jobs finish late despite available capacity; bottleneck queues absorb 45 % of total waiting time”).

**3. Root Cause Analysis of Scheduling Ineffectiveness**

Root causes are isolated by contrasting process-mining evidence of *what happened* against *what the rules and assumptions intended*:
- Static local dispatching (mix of FCFS/EDD) cannot handle dynamic multi-factor trade-offs, sequence-dependent setups, or global state (downstream load, machine health). Evidence: realized sequences deviate systematically from optimal (excess total setups), high-priority cases still queue behind low-priority ones, and large residual variance after accounting for capacity.
- Lack of real-time holistic visibility: machines and queues evolve without coordinated awareness; process mining of concurrent states shows uncoordinated local choices producing global suboptimal points.
- Inaccurate duration/setup estimates: planned vs. actual duration deviation distributions (and task-duration residual analysis conditioned on operator/job type) are large; setup "planned" values ignore sequence dependence. This leads to schedules that are infeasible from the start.
- Ineffective setup handling and work-center coordination: independent local rules ignore learned setup matrices and create starvation (cross-machine timeline evidence).
- Reactive disruption response: priority changes insert “hot jobs” without re-sequencing remaining work or considering cumulative impact; breakdown impact analysis shows no predictive buffering or rerouting, only post-hoc recovery that further disorders sequences.
- Differentiation via process mining: (a) capacity limitations appear as chronic high utilization + waiting even under idealized sequencing; (b) inherent variability as unconditional duration distributions with high CV; (c) pure scheduling logic failures as large performance gaps between realized and *simulated* best-possible sequences using the same capacity (via enhancement/alignment or offline optimization baselines), excess setups relative to the mined matrix, and prioritization inversions independent of load. Conformance to intended routing plus residual performance attribution separates “scheduling logic vs. resource shortage vs. process noise.”

**4. Developing Advanced Data-Driven Scheduling Strategies**

Three complementary strategies, all grounded in the mined models, matrices, distributions, and pathology evidence:

**Strategy 1 – Multi-factor Dynamic Dispatching Rules (Enhanced, Look-ahead Rules)**  
Core logic: At each machine, maintain a real-time queue of ready jobs. Score every candidate job with a weighted composite index and select highest (or discrete choice via softmax for exploring). Factors include:  
- urgency (remaining due-date – expected remaining processing, critical ratio),  
- priority class (explicit weight),  
- estimated processing + *sequence-dependent setup* (lookup from mined matrix or similarity-based predictor using previous job on machine remaining time),  
- downstream load (current queue length or predicted congestion at next resource, obtained from live MES feed or mined typical successors),  
- operator skill match (from historical operator–task duration enhancements).  

Weights/factors are informed by process-mining regression or random-forest importance (feature impact on historical tardiness/WIP) and can be tuned offline via multi-objective simulation. Online, a simple look-ahead simulation of the next few steps (using mean durations) prevents myopic choices.  

Addresses: prioritization failures, excess setups, and starvation. Expected impact: 20–40 % reduction in mean tardiness and weighted tardiness, moderate WIP reduction via better flow, improved bottleneck utilization by reducing non-value setups (lower makespan variance).

**Strategy 2 – Predictive / Proactive Scheduling**  
Core logic: Fit predictive models from logs—conditional duration distributions or ML regressors (gradient boosting / residual nets) for task times given job attributes, operator, machine, and time-of-day; setup predictors; and (if sensor data available) rudimentary predictive-maintenance probabilities from breakdown precursors. Periodically (or event-driven on priority change/breakdown) generate a finite-horizon schedule for bottleneck resources using stochastic earliest-due-date or slack-based dispatching, or a rolling-horizon MILP/CP solver that samples from duration distributions. Maintain buffer times scaled to historical CV of remaining path and forecasted disruption risk. Detect emerging bottlenecks by projecting current queues + predicted arrivals.  

Informed by mined duration/setup distributions, routing variants, and disruption frequency/impact. Addresses inaccurate estimates, disruption cascading, and unpredictable lead times. Expected impact: more realistic due-date quotations, proactive load balancing, 15–30 % lead-time variance reduction, lower tardiness through earlier intervention, higher stable utilization.

**Strategy 3 – Setup-Time Optimization via Intelligent Sequencing / Similarity Batching**  
Core logic: Group jobs into setup-similarity families (from historical clustering of setup matrix transitions or job features). On bottleneck or high-setup machines, apply a dynamic sequencing policy that solves a small TSP/ATSP on the current queue (costs = mined setup times + urgency penalties) or uses a greedy nearest-neighbor + re-sequence trigger. For non-bottlenecks use milder family preference. Allow limited pre-emption only for ultra-hot jobs; otherwise hold “similar” jobs for batching while respecting due-date windows (mined from historical acceptable wait). When hot jobs arrive, constrain re-optimization to keep total extra setup bounded.  

Directly uses the sequence-dependent setup matrix and excess-setup pathology evidence. Addresses inefficient resource use driven by setups and resulting WIP/tardiness. Expected impact: 25–50 % reduction in total setup time on critical machines  higher productive utilization, shorter flow times, lower WIP (less queueing behind long setups), and improved due-date performance especially under load.

The three can be hybridized (predictive durations feed the multi-factor scores and the setup sequencer; setup families become factors).

**5. Simulation, Evaluation, and Continuous Improvement**

**Simulation framework:** Build a discrete-event simulator (Python/SimPy, Arena, or anyDES) whose parameters are *mined*:  
- job arrival processes and routings (variant probabilities + parallel paths from discovery),  
- conditional duration distributions (task + setup) and operator effects,  
- machine failure models (MTBF/MTTR from breakdown events),  
- priority-change intensity,  
- queue disciplines corresponding to baseline (FCFS/EDD mix) and each proposed strategy.  

Validate the model by replaying historical cases (conformance of generated KPIs to mined performance). Then run designed experiments: (a) nominal load; (b) high-load (20–50 % more arrivals); (c) frequent disruptions (elevated breakdown/hot-job rates); (d) mixed priority scenarios. Replicate (Monte-Carlo) to compare distributions of tardiness, WIP, lead time, makespan, utilization, and total setup time. Rank strategies by multi-objective metrics (or weighted utility of KPIs) and perform statistical tests (paired Wilcoxon, bootstrap confidence intervals). Sensitivity analysis identifies robust weight settings or when to switch strategies.

**Continuous monitoring & adaptation:** Deploy streaming process mining on live MES events (daily/weekly discovery and performance refresh in tools such as PM4Py Online, Everflow, or Celonis Execution Management). Track the same KPI dashboards (on-time %, mean tardiness, bottleneck waiting, setup ratio, WIP, utilization). Use concept-drift detectors on lead-time distributions, setup-matrix changes (new product families), or bottleneck shifts. When drift exceeds a threshold or a new pathology (e.g., rising starvation) appears, re-mine durations/setups, re-tune dispatching weights via short simulation campaigns, and push rule updates or predictive-model retraining. Human-in-the-loop review of major model changes. This closes the loop, turning the scheduling system into an adaptive, learning control layer.

Collectively, the approach converts the rich MES log into quantified performance insight, causal diagnosis, and a portfolio of superior, evidence-based scheduling policies that can be stress-tested offline and refined online—directly attacking tardiness, WIP, lead-time unpredictability, and utilization imbalance.
