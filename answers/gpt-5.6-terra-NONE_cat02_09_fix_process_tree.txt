## 1. Issues with the current model

The current model uses an `AND`/`PARALLEL` block for:

- `Create_Purchase_Order`
- `Receive_Goods`
- `Receive_Invoice`
- `Match_Invoice_to_PO`
- `Pay_Invoice`

A parallel operator permits the child activities to be interleaved in arbitrary order. As a result, it allows invalid traces such as:

- `Pay_Invoice` before `Receive_Invoice`
- `Pay_Invoice` before `Match_Invoice_to_PO`
- `Match_Invoice_to_PO` before either the PO or invoice exists
- `Receive_Goods` before `Create_Purchase_Order`
- `Receive_Invoice` before `Create_Purchase_Order`
- `Create_Purchase_Order` occurring after payment

For the simplified standard process described, all activities should occur in one strict sequence:

1. Create Purchase Requisition  
2. Approve Purchase Requisition  
3. Create Purchase Order  
4. Receive Goods  
5. Receive Invoice  
6. Match Invoice to PO  
7. Pay Invoice  
8. Close Case  

No parallelism or choice is necessary if the goal is to allow only this normal path.

## 2. Corrected process tree model

```python
from pm4py.objects.process_tree.obj import Operator, ProcessTree

# Define activities
create_req = ProcessTree(label="Create_Purchase_Requisition")
approve_req = ProcessTree(label="Approve_Purchase_Requisition")
create_po = ProcessTree(label="Create_Purchase_Order")
receive_goods = ProcessTree(label="Receive_Goods")
receive_invoice = ProcessTree(label="Receive_Invoice")
match_invoice = ProcessTree(label="Match_Invoice_to_PO")
pay_invoice = ProcessTree(label="Pay_Invoice")
close_case = ProcessTree(label="Close_Case")

# Corrected model:
# All activities are ordered in one strict sequence.
root = ProcessTree(
    operator=Operator.SEQUENCE,
    children=[
        create_req,
        approve_req,
        create_po,
        receive_goods,
        receive_invoice,
        match_invoice,
        pay_invoice,
        close_case
    ]
)
```

Equivalent tree structure:

```text
SEQUENCE(
    Create_Purchase_Requisition,
    Approve_Purchase_Requisition,
    Create_Purchase_Order,
    Receive_Goods,
    Receive_Invoice,
    Match_Invoice_to_PO,
    Pay_Invoice,
    Close_Case
)
```

## 3. Why the corrected model conforms to the intended process

Using a single `SEQUENCE` operator means that every activity must occur only after all preceding activities have completed.

Therefore, the corrected tree guarantees that:

- A requisition is created before it can be approved.
- Approval occurs before a purchase order is created.
- A purchase order exists before goods or an invoice can be received.
- Goods are received before proceeding to invoice handling in this simplified process.
- The invoice is received before it can be matched.
- Matching occurs before payment.
- Payment occurs before the case is closed.

The model permits only the intended trace:

```text
Create_Purchase_Requisition
 Approve_Purchase_Requisition
 Create_Purchase_Order
 Receive_Goods
 Receive_Invoice
 Match_Invoice_to_PO
 Pay_Invoice
 Close_Case
```

This removes the underfitting behavior caused by the parallel block and prevents invalid event orders such as paying before matching or receiving goods before a purchase order has been created.
