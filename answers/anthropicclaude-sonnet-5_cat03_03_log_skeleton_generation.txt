# Log Skeleton Construction

## Process Logic (Assumptions)

Based on the scenario, I model the process as follows:

- **Backbone (strictly sequential, mandatory):** `RO  CA  RI`
- **After Reserve Items**, two **concurrent blocks** run (their relative order can vary between cases, but each block is internally sequential and never interrupted):
  - **Shipping block:** `PI  QC  PO  GSL  D`
  - **Billing block:** `IC  RP`
- Every activity occurs **exactly once** per case (no rework, no skipping, no cancellation).

This gives a moderately rich skeleton: a strict order for most pairs, but **no ordering constraint** between the shipping-block activities and the billing-block activities (since they are concurrent).

---

## Resulting Log Skeleton

```python
log_skeleton = {

    'activ_freq': {
        'RO': {1}, 'CA': {1}, 'RI': {1}, 'PI': {1}, 'QC': {1},
        'PO': {1}, 'GSL': {1}, 'D': {1}, 'IC': {1}, 'RP': {1}
    },

    'directly_follows': {
        ('RO', 'CA'), ('CA', 'RI'),
        ('PI', 'QC'), ('QC', 'PO'), ('PO', 'GSL'), ('GSL', 'D'),
        ('IC', 'RP')
    },

    'always_before': {
        # RO always precedes everything else
        ('CA','RO'), ('RI','RO'), ('PI','RO'), ('QC','RO'), ('PO','RO'),
        ('GSL','RO'), ('D','RO'), ('IC','RO'), ('RP','RO'),
        # CA always precedes everything after it
        ('RI','CA'), ('PI','CA'), ('QC','CA'), ('PO','CA'), ('GSL','CA'),
        ('D','CA'), ('IC','CA'), ('RP','CA'),
        # RI always precedes both branches
        ('PI','RI'), ('QC','RI'), ('PO','RI'), ('GSL','RI'), ('D','RI'),
        ('IC','RI'), ('RP','RI'),
        # Shipping-block internal order
        ('QC','PI'), ('PO','PI'), ('GSL','PI'), ('D','PI'),
        ('PO','QC'), ('GSL','QC'), ('D','QC'),
        ('GSL','PO'), ('D','PO'),
        ('D','GSL'),
        # Billing-block internal order
        ('RP','IC')
    },

    'always_after': {
        ('RO','CA'), ('RO','RI'), ('RO','PI'), ('RO','QC'), ('RO','PO'),
        ('RO','GSL'), ('RO','D'), ('RO','IC'), ('RO','RP'),
        ('CA','RI'), ('CA','PI'), ('CA','QC'), ('CA','PO'), ('CA','GSL'),
        ('CA','D'), ('CA','IC'), ('CA','RP'),
        ('RI','PI'), ('RI','QC'), ('RI','PO'), ('RI','GSL'), ('RI','D'),
        ('RI','IC'), ('RI','RP'),
        ('PI','QC'), ('PI','PO'), ('PI','GSL'), ('PI','D'),
        ('QC','PO'), ('QC','GSL'), ('QC','D'),
        ('PO','GSL'), ('PO','D'),
        ('GSL','D'),
        ('IC','RP')
    },

    'never_together': set(),   # every activity is mandatory -> nothing is ever "excluded"

    'equivalence': {
        # all activities occur exactly once in every case -> all pairs are equivalent
        ('RO','CA'), ('RO','RI'), ('RO','PI'), ('RO','QC'), ('RO','PO'),
        ('RO','GSL'), ('RO','D'), ('RO','IC'), ('RO','RP'),
        ('CA','RI'), ('CA','PI'), ('CA','QC'), ('CA','PO'), ('CA','GSL'),
        ('CA','D'), ('CA','IC'), ('CA','RP'),
        ('RI','PI'), ('RI','QC'), ('RI','PO'), ('RI','GSL'), ('RI','D'),
        ('RI','IC'), ('RI','RP'),
        ('PI','QC'), ('PI','PO'), ('PI','GSL'), ('PI','D'), ('PI','IC'), ('PI','RP'),
        ('QC','PO'), ('QC','GSL'), ('QC','D'), ('QC','IC'), ('QC','RP'),
        ('PO','GSL'), ('PO','D'), ('PO','IC'), ('PO','RP'),
        ('GSL','D'), ('GSL','IC'), ('GSL','RP'),
        ('D','IC'), ('D','RP'),
        ('IC','RP')
    }
}
```

### Notes on Consistency
- `always_before` and `always_after` are mirror images of each other (35 comparable pairs each), reflecting the fixed partial order `RO < CA < RI < {shippingblock, billingblock}`.
- The **10 pairs** between `{PI, QC, PO, GSL, D}` and `{IC, RP}` are **absent** from both ordering relations, correctly capturing their concurrency.
- `directly_follows` only contains transitions that hold in *every* case — the backbone (`ROCARI`) and the two internal block sequences — since the transition point between blocks is not fixed.
- `never_together` is empty because all activities are mandatory (freq = {1}), so they always co-occur.
- `equivalence` contains all pairs since every activity’s occurrence count is invariably 1.
