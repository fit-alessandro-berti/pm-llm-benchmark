Here is the DuckDB SQL query that implements the required logic:

```sql
WITH OrderedEvents AS (
    SELECT 
        case_id,
        activity,
        timestamp,
        LAG(activity) OVER w AS prev_activity,
        LEAD(activity) OVER w AS next_activity,
        LEAD(timestamp) OVER w AS next_timestamp
    FROM event_log
    WINDOW w AS (PARTITION BY case_id ORDER BY timestamp)
),
CasesToExclude AS (
    -- Identify cases with the exact direct succession and time constraint
    SELECT DISTINCT case_id
    FROM OrderedEvents
    WHERE activity = 'Create Order'
      AND prev_activity = 'Approve Purchase Requisition'
      AND next_activity = 'Confirm Order'
      AND next_timestamp - timestamp > INTERVAL '5 days'
)
-- Return all events excluding the matched cases
SELECT *
FROM event_log
WHERE case_id NOT IN (SELECT case_id FROM CasesToExclude)
ORDER BY case_id, timestamp;
```

### Explanation:
1. **OrderedEvents CTE**: We use the `LAG` and `LEAD` window functions partitioned by `case_id` and ordered by `timestamp` to examine the immediately preceding and succeeding activities for every event. This guarantees that we are looking for events in direct succession (i.e., no other event from the same case occurring in between).
2. **CasesToExclude CTE**: We filter for the middle event of the sequence (`'Create Order'`). We then check if its previous activity is `'Approve Purchase Requisition'` and its next activity is `'Confirm Order'`. Simultaneously, we apply the condition that the elapsed time between the current event (`Create Order`) and the next event (`Confirm Order`) is strictly greater than 5 days using DuckDB's `INTERVAL` arithmetic. We extract the distinct `case_id`s that match this criteria.
3. **Final SELECT**: We query the original `event_log` table and use a `NOT IN` clause to exclude any events belonging to the identified bad cases, ordering the result properly for readability.
