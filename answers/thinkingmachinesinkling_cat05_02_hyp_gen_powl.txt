## 1. Anomalies in the POWL Model

| # | Anomaly | What the Model Permits |
|---|---------|------------------------|
| **A** | **Loop structure on `(E, P)`** (`Operator.LOOP`) | After evaluation (`E`), the process may either exit the loop **or** approve (`P`) and loop back to evaluate (`E`) again. This allows **repeated evaluation–approval cycles** for a single claim, which is not part of the standard linear flow `R  A  E  P  N  C`. |
| **B** | **XOR skip of notification (`N` vs. `skip`)** | The `XOR` gate allows the process to take the silent-transition path (`skip`) instead of notifying the customer (`N`). This means a claim can reach closure (`C`) **without ever producing a notification event**. |
| **C** | **Broken / missing ordering constraints** | The partial order adds `A  C` directly, but **omits** `XOR  C`. Consequently:<br>• `C` can occur immediately after `A`, **before** the loop (`E`/`P`) or the notification (`N`) has executed.<br>• `C` and the `XOR` node are unordered relative to each other, allowing concurrent or out-of-sequence execution (e.g., closing while notification is still pending or skipped). |
| **D** | **Overall effect: premature closure** | Because of (A) + (B) + (C), the model technically permits traces such as `R  A  C` (no evaluation, no approval, no notice) or `R  A  E  P  E  P  C` (infinite/redundant loop followed by abrupt closure). |

## 3. Database Verification Queries (PostgreSQL)

Below are targeted queries against your three tables. They are designed to detect the **actual execution traces** that match the anomalous paths permitted by the POWL model.

### Query 1: Detect the `E–P` Loop (Repeated Evaluation / Approval)
*Tests H1 / H4 — are claims being evaluated and approved multiple times?*

```sql
SELECT 
    claim_id,
    COUNT(CASE WHEN activity = 'E' THEN 1 END) AS evaluation_count,
    COUNT(CASE WHEN activity = 'P' THEN 1 END) AS approval_count,
    COUNT(CASE WHEN activity IN ('E', 'P') THEN 1 END) AS loop_total_events
FROM claim_events
GROUP BY claim_id
HAVING 
    COUNT(CASE WHEN activity = 'E' THEN 1 END) > 1
    OR COUNT(CASE WHEN activity = 'P' THEN 1 END) > 1
ORDER BY loop_total_events DESC;
```

**What to look for:** Any `claim_id` with `evaluation_count > 1` or `approval_count > 1` confirms that the loop is being executed in practice.

### Query 5: Correlation with Adjuster / Resource (Testing H2 & H3)
*Tests whether anomalies cluster by human adjuster vs. system, or by specialization.*

```sql
SELECT 
    adj.specialization,
    adj.region,
    e.resource,
    COUNT(DISTINCT CASE WHEN loop_check.eval_count > 1 THEN e.claim_id END) AS loop_claims,
    COUNT(DISTINCT CASE WHEN skip_check.notify_missing = 1 THEN e.claim_id END) AS skipped_notification_claims,
    COUNT(DISTINCT CASE WHEN premature.close_before_eval = 1 THEN e.claim_id END) AS premature_close_claims
FROM claim_events e
LEFT JOIN adjusters adj ON e.resource = adj.name  -- if resource stores the adjuster's name
LEFT JOIN LATERAL (
    SELECT claim_id, COUNT(*) > 1 AS eval_count
    FROM claim_events
    WHERE activity = 'E'
    GROUP BY claim_id
) loop_check ON e.claim_id = loop_check.claim_id
LEFT JOIN LATERAL (
    SELECT claim_id, 1 AS notify_missing
    FROM claim_events
    WHERE activity = 'C'
    EXCEPT
    SELECT claim_id, 1 FROM claim_events WHERE activity = 'N'
) skip_check ON e.claim_id = skip_check.claim_id
LEFT JOIN LATERAL (
    SELECT c.claim_id, 1 AS close_before_eval
    FROM claim_events c
    JOIN claim_events ce ON c.claim_id = ce.claim_id
    WHERE c.activity = 'C' AND ce.activity = 'E' AND c.timestamp < ce.timestamp
) premature ON e.claim_id = premature.claim_id
WHERE e.activity = 'A'  -- focus on assignment events as the “entry point”
GROUP BY adj.specialization, adj.region, e.resource
ORDER BY loop_claims DESC, skipped_notification_claims DESC;
```

> **Note:** The join `e.resource = adj.name` assumes the `resource` column records the adjuster’s name for human actions. If your system stores `adjuster_id` in `additional_info` or uses a different mapping, adjust the `ON` clause accordingly (e.g., parse from `additional_info` or join via a mapping table).
