# Data-Driven Process Mining and Advanced Scheduling Approach for Precision Parts Inc.

## 1. Analyze Historical Scheduling Performance and Dynamics

The first objective is to create a trustworthy, event-level picture of how work actually moves through the job shop—not how routings or schedules say it should move. The MES log is sufficiently rich to support both process mining and manufacturing scheduling analysis, provided the data is cleaned, standardized, and enriched.

### 1.1 Build a process-mining event model

A standard process-mining event log requires at least:

- **Case ID:** `Job ID` (for example, `JOB-7001`)
- **Activity:** normalized operation and lifecycle event, such as:
  - `Cutting - Queue Entry`
  - `Cutting - Setup Start`
  - `Cutting - Setup End`
  - `Cutting - Processing Start`
  - `Cutting - Processing End`
  - `Milling - Queue Entry`
- **Timestamp**
- **Resource:** machine ID and, where applicable, operator ID

Additional event attributes should be retained:

- Job priority and its changes over time
- Job release date
- Due date
- Routing / required operation sequence
- Product family, material, dimensions, tooling, fixture, and process characteristics where available
- Planned and actual duration
- Setup requirement and setup characteristics
- Shift/calendar
- Breakdown and maintenance status
- Rework, hold, inspection failure, and engineering-change events
- Machine alternatives and assignment decisions

Because a job can have multiple operations and each operation has multiple lifecycle events, the analysis should use several linked views:

1. **Job-level process view**  
   Case = Job ID. Used for end-to-end lead time, routing variants, rework loops, due-date performance, and WIP evolution.

2. **Operation-level process view**  
   Case = Job ID + operation sequence number. Used for queue time, setup time, processing time, transfer delay, and operation-level lateness.

3. **Resource-centric view**  
   Case = Machine ID, ordered by timestamp. Used to reconstruct the actual sequence of jobs processed on each machine and to measure setups, idle periods, breakdowns, queue conditions, and dispatching decisions.

4. **Operator-centric view**  
   Case = Operator ID or operator shift. Used to assess skill constraints, handoff delays, setup performance differences, and labor-related capacity restrictions.

These views should be joined through job, operation, resource, and timestamp keys rather than forced into a single simplistic process model.

### 1.2 Data preparation and event reconstruction

Before mining, establish consistent event semantics.

#### Normalize lifecycle states

Map MES activity labels into a standard lifecycle:

- `Released`
- `Arrived at Queue`
- `Setup Started`
- `Setup Completed`
- `Processing Started`
- `Processing Completed`
- `Blocked`
- `On Hold`
- `Rework Started`
- `Rework Completed`
- `Breakdown Started`
- `Breakdown Ended`
- `Job Completed`

For each job-operation-resource combination, reconstruct:

- Queue-entry timestamp
- Setup-start timestamp
- Setup-end timestamp
- Processing-start timestamp
- Processing-end timestamp
- Departure timestamp
- Next-operation queue-entry timestamp

#### Validate time and data integrity

Important quality checks include:

- Events occurring out of order
- Missing setup start/end records
- Overlapping processing assignments on a non-parallel machine
- Jobs with missing due dates or priorities
- Inconsistent machine IDs
- Jobs transferred to a different machine from the planned route
- Processing occurring during recorded breakdowns
- Negative waiting or setup durations
- Jobs not formally closed in the MES

Missing or unreliable data should not merely be deleted. It should be flagged and incorporated into confidence scores for scheduling models.

#### Derive event intervals

For each operation \(o\) of job \(j\):

- **Queue time**
  \[
  Q_{j,o} = T_{\text{setup start or process start}} - T_{\text{queue entry}}
  \]

- **Setup time**
  \[
  S_{j,o} = T_{\text{setup end}} - T_{\text{setup start}}
  \]

- **Processing time**
  \[
  P_{j,o} = T_{\text{process end}} - T_{\text{process start}}
  \]

- **Transfer time**
  \[
  TR_{j,o} = T_{\text{next queue entry}} - T_{\text{process end}}
  \]

- **Operation flow time**
  \[
  F_{j,o} = Q_{j,o} + S_{j,o} + P_{j,o} + TR_{j,o}
  \]

At job level:

- **Manufacturing lead time**
  \[
  LT_j = T_{\text{job completed}} - T_{\text{job released}}
  \]

- **Total touch time**
  \[
  TT_j = \sum_o(S_{j,o} + P_{j,o})
  \]

- **Total waiting/non-value-added time**
  \[
  WT_j = LT_j - TT_j
  \]

- **Flow efficiency**
  \[
  FE_j = \frac{TT_j}{LT_j}
  \]

A very low flow efficiency is common in job shops, but it directly reveals that improving processing speed alone will not solve lead-time problems.

### 1.3 Process mining techniques for actual job flow and routing analysis

#### Process discovery

Use multiple process-discovery methods because no single method is adequate for a high-mix job shop.

- **Directly-Follows Graphs (DFGs):** Show frequently occurring transitions between operations and expose common routing patterns.
- **Inductive Miner:** Produces structured process models while tolerating variations.
- **Heuristics Miner:** Useful for noisy manufacturing logs and less frequent loops or rework paths.
- **Fuzzy Miner:** Helpful for simplifying highly variable job routes while retaining dominant patterns.
- **Object-centric process mining:** Particularly valuable because jobs, operations, machines, operators, tools, and breakdown events interact simultaneously. It avoids forcing all relationships into a purely job-centric sequence.

The output should distinguish:

- Planned routing versus actual routing
- Normal job variants versus exceptional variants
- Rework loops
- Optional inspection or heat-treatment steps
- Alternate machine usage
- Routing changes caused by capacity shortages or breakdowns

#### Conformance checking

Where a process plan or routing sheet exists, compare actual execution against it using:

- **Token-based replay**
- **Alignment-based conformance checking**
- **Deviation analysis**
- **Route compliance score**

Examples of deviations:

- Operations performed out of sequence
- Unauthorized machine substitutions
- Excessive delays between mandated consecutive operations
- Skipped inspection steps
- Unplanned rework loops
- Jobs waiting at a machine despite alternate machine availability

This identifies whether the issue is execution noncompliance, inadequate routing design, or a schedule that is infeasible in practice.

### 1.4 Metrics for job flow times, lead times, and makespan

At minimum, analyze by:

- Job family
- Customer
- Priority class
- Due-date tightness
- Routing variant
- Product complexity
- Resource group
- Shift
- Month or week
- On-time versus late completion status

Key metrics:

| Metric | Definition | Why It Matters |
|---|---|---|
| Job lead time | Release to completion | Customer-facing delivery performance |
| Operation flow time | Queue entry to operation completion | Identifies where time accumulates |
| Queue time | Queue entry to setup/process start | Measures congestion and scheduling delay |
| Touch time | Setup + processing | Measures direct work content |
| Flow efficiency | Touch time / total lead time | Reveals waiting and coordination waste |
| Makespan | Span from first job release to last completion in a period/batch | Useful for production campaigns or job sets |
| Throughput | Jobs or standard hours completed per period | Capacity and delivery capability |
| WIP | Jobs or standard hours released but not completed | Indicates congestion and inventory exposure |
| Cycle-time variability | Standard deviation, percentiles, coefficient of variation | Critical for reliable due-date promises |

Do not rely only on averages. Analyze distributions and tail behavior:

- Median
- 75th, 90th, 95th percentile
- Standard deviation
- Coefficient of variation
- Probability of exceeding a target lead time
- Conditional lead time by WIP level at release

For example, if median milling queue time is eight hours but the 95th percentile is 72 hours, the issue is not simply “average capacity”; it is variability, congestion, sequencing, and disruption sensitivity.

---

### 1.5 Task waiting-time and queue analysis

For every resource and operation family, calculate:

- Average, median, and percentile queue time
- Queue length at task arrival
- Queue length when task starts
- Queue age distribution
- Workload in queue, measured in estimated processing hours
- Queue composition by urgency and priority
- Number of jobs waiting beyond a threshold
- Queue time by incoming routing source
- Queue time before and after breakdowns
- Queue time by time of day and shift

Useful views include:

- **Heat map:** work center by hour/day, colored by average queue length or queue waiting time.
- **Queue aging chart:** number of jobs waiting 0–4, 4–12, 12–24, 24–48, and over 48 hours.
- **Resource queue scatterplot:** queue workload versus observed waiting time.
- **Cumulative flow diagram:** released, in process, queued, and completed jobs over time.
- **WIP aging report:** identifies “hidden late jobs” that are accumulating before the bottleneck.

A crucial distinction is between:

- A machine being idle because it has no work available: **starvation**
- A machine being idle while eligible work is waiting: **dispatching, setup, tooling, operator, or information failure**
- A job waiting while the target machine is unavailable: **capacity or breakdown constraint**
- A job waiting while alternate capacity exists: **assignment or routing decision failure**

### 1.6 Machine and operator utilization analysis

Machine utilization should not be treated as one number. Decompose the available calendar time into mutually exclusive states:

\[
\text{Available Time} =
\text{Processing} +
\text{Setup} +
\text{Idle-Starved} +
\text{Idle-Queue Present} +
\text{Breakdown} +
\text{Planned Maintenance} +
\text{Blocked} +
\text{Off Shift}
\]

For each resource, calculate:

- Productive processing utilization
- Setup utilization
- Breakdown utilization
- Idle time due to lack of released work
- Idle time despite queued work
- Blocked time due to downstream constraints
- Operator waiting time
- Setup-to-processing ratio
- Mean time between failures
- Mean time to repair
- Availability:
  \[
  A = \frac{\text{Scheduled time} - \text{downtime}}{\text{Scheduled time}}
  \]
- Operational Equipment Effectiveness components where applicable:
  - Availability
  - Performance
  - Quality

Important interpretation: a bottleneck machine operating at 90–95% productive-plus-setup utilization may be expected. However, a non-bottleneck machine with high utilization can still be undesirable if it is producing work that only increases WIP ahead of the real constraint.

Operator analysis should distinguish:

- Operator skill eligibility
- Setup proficiency
- Actual processing performance by operator
- Shift effects
- Delays awaiting an operator despite machine availability
- Operator-machine combinations with systematically longer setups or task durations

---

### 1.7 Sequence-dependent setup-time analysis

Sequence-dependent setups are central to this shop’s scheduling problem. The key is to reconstruct the exact job sequence on every machine.

For each machine \(m\), order jobs by setup start or processing start:

\[
J_{m,1}, J_{m,2}, ..., J_{m,n}
\]

For each consecutive pair:

\[
(J_{m,k-1} \rightarrow J_{m,k})
\]

record:

- Previous job family
- Current job family
- Material and thickness change
- Tooling and fixture change
- Program change
- Operator
- Machine
- Shift
- Setup-required flag
- Actual setup duration
- Planned setup duration
- Whether setup began immediately after prior work or after an idle period

Construct a setup transition matrix:

\[
S_{a,b,m} = E[\text{setup time} \mid \text{previous family}=a, \text{next family}=b, \text{machine}=m]
\]

This can be expanded into a predictive setup model:

\[
\hat{S} = f(\text{previous job attributes}, \text{next job attributes}, \text{machine}, \text{operator}, \text{tooling}, \text{shift})
\]

Methods may include:

- Median setup by transition pair
- Hierarchical Bayesian estimates for sparse transitions
- Gradient-boosting or random-forest regression
- Quantile regression for risk-aware scheduling
- Clustering of job families based on setup-relevant features
- Sequence pattern mining to identify recurring favorable or unfavorable transitions

Useful outputs:

- Setup matrix by machine and product family
- Highest-cost transition pairs
- Setup-time variance by operator or shift
- Setup reduction opportunities from grouping families
- Frequency of unnecessary setup changes
- Total setup hours caused by observed sequence versus a lower-bound or optimized sequence

This transforms setup time from a generic fixed estimate into an explicit scheduling input.

---

### 1.8 Schedule adherence and tardiness analysis

At job level, define:

\[
\text{Lateness}_j = C_j - D_j
\]

where:

- \(C_j\) = actual completion time
- \(D_j\) = committed due date

Tardiness is:

\[
T_j = \max(0, C_j - D_j)
\]

Also calculate:

- Percentage of jobs completed on time
- Mean tardiness
- Median tardiness
- Maximum tardiness
- Tardiness by priority class
- Tardiness by customer, job family, routing variant, and bottleneck exposure
- Weighted tardiness:
  \[
  WT = \sum_j w_j T_j
  \]
  where \(w_j\) reflects customer importance, penalty, contractual risk, or urgency.
- Due-date adherence bands:
  - Early by more than two days
  - Early by 0–2 days
  - On time
  - 1–2 days late
  - 3–5 days late
  - More than five days late

If planned operation start and completion dates are available, calculate schedule deviation at each operation:

\[
\Delta_{j,o}^{start} = \text{Actual Start}_{j,o} - \text{Planned Start}_{j,o}
\]

\[
\Delta_{j,o}^{finish} = \text{Actual Finish}_{j,o} - \text{Planned Finish}_{j,o}
\]

This identifies where schedule slippage first appears and whether it propagates downstream.

---

### 1.9 Impact of disruptions

Breakdowns and urgent priority changes should be treated as first-class process events, not exceptions outside the model.

For each breakdown:

- Machine
- Start and end time
- Duration
- Jobs interrupted
- Jobs queued
- Workload in queue at breakdown start
- Number of jobs affected
- Downstream starvation effect
- Incremental queue time caused
- Incremental tardiness caused
- Recovery time until normal queue/WIP levels return

For hot jobs:

- Time of priority change
- Job’s queue position before and after escalation
- Jobs displaced
- Added setup changes caused by insertion
- Tardiness impact on displaced jobs
- Net customer value gained or lost
- Whether hot-job insertion reduced total weighted tardiness or merely redistributed lateness

Use event-study analysis around disruption windows:

- Compare KPIs before, during, and after breakdowns.
- Measure queue growth and recovery slope.
- Compare actual outcomes to counterfactual expected outcomes based on similar non-disrupted periods.
- Quantify “schedule nervousness”: number of jobs whose planned start or completion changed after a disruption.

## 2. Diagnose Scheduling Pathologies

The objective is to convert descriptive findings into evidence-backed diagnoses. Process mining should identify not only where jobs are late, but why they become late.

### 2.1 Bottleneck identification and impact quantification

A true bottleneck is not simply the highest-utilization machine. It is the resource whose effective capacity most constrains system throughput and whose delays create disproportionate downstream effects.

Evidence for a bottleneck includes:

- High utilization when including processing and setup time
- Persistent workload queue
- Long and highly variable queue times
- Large WIP accumulation upstream
- Downstream starvation following its downtime
- Strong relationship between waiting at that resource and job tardiness
- High proportion of late jobs passing through that resource
- High sensitivity of total lead time to its breakdowns
- Low schedule flexibility due to specialized capability

Process-mining analysis:

1. Create a resource performance dashboard.
2. Compare queue time, utilization, WIP, and tardiness contribution by resource.
3. Run regression or survival analysis:
   \[
   P(\text{late}) = f(\text{queue time at machine}, \text{number of bottleneck visits}, \text{WIP at release}, \text{priority}, \text{job complexity})
   \]
4. Compare on-time and late job variants.
5. Evaluate downstream machine starvation after constrained-resource disruptions.

For example, if 80% of jobs more than two days late spent over 60% of their total lead time waiting for CNC milling, then milling is a primary leverage point even if other machines have similar utilization.

---

### 2.2 Poor prioritization and local dispatching effects

The current FCFS/EDD mixture may create local optimization rather than global job completion.

Evidence of poor prioritization may include:

- Urgent jobs waiting behind low-priority work despite similar setup requirements.
- High-priority jobs consistently receiving better local queue position but still missing due dates because they are late at upstream bottlenecks.
- Jobs with imminent due dates receiving no preference until they reach the final operation.
- Low-priority jobs being processed early, accumulating WIP before constrained resources.
- Hot-job insertions causing disproportionate lateness among other important jobs.
- EDD rules ignoring remaining work content and downstream congestion.

Use a reconstructed decision log. At every machine dispatching point, identify:

- Jobs available in the queue
- Which job was selected
- Alternative eligible jobs
- Their due dates, priority, slack, estimated setup, processing time, and downstream workload
- Whether the actual selected job would be favored by FCFS, EDD, shortest processing time, setup minimization, or another rule

This permits an empirical “decision quality” analysis:

- How often did the machine choose a job with lower urgency than another waiting job?
- How often did the selected job create a large setup when a lower-setup alternative with similar urgency existed?
- How often did local EDD increase total weighted tardiness later?

---

### 2.3 Suboptimal setup sequencing

Indicators include:

- Frequent alternation between incompatible product families.
- High setup hours relative to productive processing time.
- Large setup variance for comparable transitions.
- Repeatable favorable sequences not used consistently.
- Long setups on bottleneck machines during periods of high queue pressure.
- Hot-job insertion causing repeated family switches.

Quantify the loss by comparing actual sequencing to alternative feasible sequences:

- Actual cumulative setup time
- Setup-minimized sequence with same jobs and same time window
- Setup-aware due-date sequence
- Hybrid sequence minimizing weighted tardiness plus setup

For a resource and planning horizon:

\[
\text{Setup Opportunity Loss} =
\text{Actual Setup Time} - \text{Optimized Feasible Setup Time}
\]

This should be reported in both hours and capacity-equivalent job output.

---

### 2.4 Starvation, blocking, and poor coordination between work centers

A job shop may have individual machines that appear underutilized, but the real issue may be that upstream work is not being released or sequenced to feed them.

Use temporal process mining to identify:

- Idle periods with no available work: upstream starvation
- Idle periods despite available work: dispatching, setup, staffing, tooling, or information failure
- Jobs completed upstream but delayed in transfer or inspection
- Downstream machines waiting for particular job families while upstream produces non-urgent work
- Queues growing before bottlenecks while downstream machines experience starvation

A resource dependency graph can show:

- Upstream-to-downstream material flow
- Average transfer delay
- Correlation between upstream completion rate and downstream utilization
- Propagation of breakdown effects

This reveals whether capacity exists but is poorly coordinated.

---

### 2.5 WIP instability and “bullwhip-like” behavior

Although bullwhip is traditionally associated with supply chains, a similar amplification phenomenon can appear inside a job shop: release decisions, hot-job expediting, and local scheduling create sharp WIP swings, which then amplify variability in queues and lead times.

Analyze:

- Daily or shift-level WIP by work center
- Variance of WIP versus variance of releases and completions
- Queue buildup after priority changes or breakdowns
- WIP upstream of bottlenecks
- Aging WIP by due-date risk
- Number of jobs released before capacity exists to process them

A likely finding is that releasing work too early creates high WIP without improving completion dates. This is especially likely where a bottleneck is overloaded and downstream operations must wait for constrained-resource output.

---

### 2.6 Variant analysis: on-time versus late jobs

Create separate process models for:

- On-time jobs
- Moderately late jobs
- Severely late jobs
- Urgent jobs
- Jobs passing through critical bottlenecks
- Jobs with high setup burden
- Jobs affected by breakdowns

Compare:

- Route variants
- Number of operations
- Rework frequency
- Queue time by operation
- Setup time
- Number of priority changes
- Number of machine changes
- Exposure to breakdowns
- WIP level at release
- Time spent waiting for inspection, material, operator, or tooling

This provides evidence such as:

- Late jobs are not necessarily longer jobs; they may spend substantially more time in queues.
- Late jobs may be released when WIP is already excessive.
- Certain routing variants may have structurally unreliable lead times.
- Certain product families may cause setup-intensive sequences at bottleneck resources.

## 3. Root Cause Analysis of Scheduling Ineffectiveness

A key analytical goal is to distinguish scheduling-policy failure from genuine capacity insufficiency, data-quality issues, and unavoidable stochastic variability.

### 3.1 Likely root causes

#### Static dispatching rules in a dynamic system

FCFS and basic EDD are local rules. They generally ignore:

- Remaining processing time
- Sequence-dependent setup costs
- Downstream machine congestion
- Alternate resource availability
- Machine breakdown risk
- Operator and tooling constraints
- Job priority changes
- System-wide WIP
- Whether a job is likely to become late despite immediate processing

EDD can be useful, but it can be harmful when it causes frequent setups or prioritizes a job with a near due date that still has substantial downstream work and no realistic chance of completion without coordinated action.

#### Lack of global shop-floor visibility

Scheduling decisions may be made using only local queue information. This causes machines to process work that looks appropriate locally but is counterproductive globally.

Typical consequences:

- Non-bottleneck resources produce ahead of constrained capacity.
- Jobs move to queues where they will wait for days.
- Urgent jobs are accelerated at one machine but then wait at the next bottleneck.
- Setup decisions are made without considering later machine capacity.
- Resources become starved because upstream dispatching does not feed them appropriately.

#### Inaccurate time estimates

Planned durations may be deterministic, outdated, or insufficiently granular. In high-mix manufacturing, processing times vary with:

- Material and geometry
- Lot size
- Program complexity
- Tooling condition
- Operator experience
- Machine condition
- Rework likelihood
- Setup sequence
- Shift and staffing conditions

If estimated durations systematically differ from actual durations, schedules become infeasible even when the scheduling logic is reasonable.

#### Sequence-dependent setups ignored or oversimplified

A single average setup time is not sufficient. The real setup may depend on the previous job, next job, tooling, fixture, material, machine, and operator.

Ignoring sequence dependence causes:

- Overcommitted schedules
- Excessive family switching
- Underestimation of bottleneck load
- Underestimation of the impact of hot-job insertions
- Incorrect machine assignment choices

#### Poor release control and WIP governance

If jobs are released into the shop without considering bottleneck capacity and current WIP, the system creates long queues and poor flow efficiency. More releases can make delivery performance worse, not better.

#### Weak disruption-response strategy

Breakdowns and hot jobs are treated as ad hoc exceptions rather than modeled scheduling events. Typical issues include:

- No protected capacity for urgent work
- No rule for selecting displaced jobs
- No reoptimization after breakdowns
- No risk buffers near bottlenecks
- No real-time estimated completion-date updates

---

### 3.2 Differentiating scheduling failure from capacity limitations

Process mining supports this distinction through counterfactual and comparative analysis.

| Observed Pattern | Likely Interpretation |
|---|---|
| Persistent high queue, high utilization, little idle time, and limited alternate capacity | Structural capacity bottleneck |
| Long queues while machine is idle and eligible work is available | Dispatching, operator, tooling, or data/coordination failure |
| High tardiness despite low overall utilization | Poor sequencing, poor release control, variability, or route imbalance |
| Planned durations consistently understate actual duration | Estimation/modeling failure |
| Tardiness spikes only around machine failures | Reliability and contingency-planning issue |
| Late jobs disproportionately have many priority changes | Expediting policy is creating instability |
| Setup time varies mainly by job-to-job transition | Sequence-dependent setup is being ignored |
| Downstream resources starve while upstream WIP grows | Flow coordination and bottleneck management failure |

Methods to support this:

- Compare actual schedules against simulated or optimized alternatives under the same resource availability.
- Measure idle time with queue present.
- Test whether jobs were eligible for alternate machines.
- Analyze whether jobs were delayed primarily due to resource downtime, long queues, operator shortages, missing materials, rework, or dispatching choices.
- Model tardiness using explainable predictive methods, such as gradient boosting with SHAP values, logistic regression, or survival models.
- Use conformance checking against feasible routing and scheduling policies.

A strong conclusion should be phrased carefully. For example:

> “Milling capacity is structurally constrained during peak load, but 25% of observed milling delay appears avoidable because the machine was idle while eligible work was waiting, and setup-heavy family switching increased setup hours by an estimated 15% relative to a setup-aware sequence.”

## 4. Advanced Data-Driven Scheduling Strategies

The recommended solution is not one universal rule. Precision Parts should use a layered scheduling architecture:

1. Capacity and release control at the shop level
2. Rolling-horizon scheduling for bottlenecks and critical jobs
3. Dynamic dispatching at work centers
4. Event-triggered rescheduling after breakdowns, material shortages, or hot-job arrivals
5. Predictive completion and tardiness-risk monitoring

Below are four complementary strategies. At least three should be piloted and compared through simulation.

---

### Strategy 1: Dynamic Multi-Factor Dispatching With Global Awareness

#### Core logic

Replace static FCFS/EDD rules with a dynamic dispatching score calculated whenever a machine becomes available or a material/priority event occurs.

For each eligible job-operation \(j,o\) at machine \(m\), calculate a priority score:

\[
Score_{j,o,m} =
w_1 \cdot \text{Urgency}
+
w_2 \cdot \text{Tardiness Risk}
+
w_3 \cdot \text{Downstream Criticality}
+
w_4 \cdot \text{Priority Weight}
-
w_5 \cdot \text{Estimated Setup Cost}
-
w_6 \cdot \text{Expected Blocking Risk}
+
w_7 \cdot \text{Bottleneck Feeding Value}
\]

Possible inputs include:

- **Dynamic slack**
  \[
  Slack_j = D_j - t - \widehat{RPT}_j
  \]
  where \(\widehat{RPT}_j\) is estimated remaining processing, setup, queue, and transfer time.

- **Critical ratio**
  \[
  CR_j = \frac{D_j - t}{\widehat{RPT}_j}
  \]
  A value below one indicates risk of lateness.

- Current job priority and customer penalty weight
- Estimated sequence-dependent setup time from current machine state
- Remaining processing time
- Number and severity of downstream bottleneck visits
- Current and forecast downstream queue workload
- Probability of late completion
- Age in queue
- Availability of alternate machines
- Risk of downstream starvation
- Expected impact on total weighted tardiness

The job with the best score is selected, subject to hard constraints such as material availability, tooling, operator certification, route precedence, and machine eligibility.

#### How process mining informs the strategy

Process mining provides:

- Actual routing patterns
- Queue-time distributions by resource
- Remaining lead-time estimates
- Setup transition models
- Resource-specific bottleneck status
- Historical relationship between features and tardiness
- Operator and machine performance variation
- Frequency and impact of hot-job insertion

Weights should not be chosen only by intuition. They can be:

- Tuned through simulation optimization
- Learned through historical outcome modeling
- Adjusted by resource group
- Recalibrated periodically as product mix changes

#### Pathologies addressed

- Local FCFS/EDD decisions
- Priority blindness to downstream constraints
- Excessive queue time at bottlenecks
- Poor coordination between work centers
- Failure to balance due-date urgency against setup efficiency
- Unnecessary WIP growth

#### Expected KPI impact

Expected impacts include:

- Lower weighted tardiness
- Improved on-time delivery
- Lower queue time at critical resources
- Reduced WIP through better release and sequencing discipline
- Improved predictability of lead times
- Better utilization of flexible resources without overproducing upstream WIP

Potential tradeoff: setup time may increase slightly if due-date risk must override family grouping. This is why the decision score must explicitly balance both objectives.

---

### Strategy 2: Predictive, Rolling-Horizon Scheduling and Tardiness-Risk Management

#### Core logic

Use a rolling-horizon schedule that is recalculated at defined intervals and whenever major disruptions occur. Rather than scheduling with fixed deterministic times, use predicted distributions for:

- Processing durations
- Setup durations
- Transfer and queue times
- Machine downtime risk
- Rework probability
- Operator availability
- Material or tooling constraints

The scheduler should produce:

- Expected completion date
- P50, P80, or P90 completion-date estimates
- Probability of on-time delivery
- Risk-adjusted slack
- Bottleneck workload forecast
- Recommended reallocation, sequencing, or release actions

A job is not considered “safe” merely because its expected completion date is before due date. It should have an acceptable probability of on-time completion.

For example:

\[
P(C_j \le D_j) \ge 0.90
\]

could be required for high-priority jobs.

#### Predictive models

Models can predict:

- Actual processing duration
- Setup duration
- Probability of breakdown
- Expected repair time
- Queue delay at each resource
- Probability of job tardiness
- Expected completion date

Features may include:

- Product family and dimensions
- Material type
- Operation type
- Machine
- Operator
- Tooling
- Shift
- Job routing
- Queue workload
- WIP level
- Setup transition
- Historical machine reliability
- Priority status
- Job release timing
- Remaining operation count

Use model forms appropriate to data maturity:

- Quantile regression for duration ranges
- Survival analysis for waiting time and job completion
- Gradient-boosting models for tardiness classification
- Bayesian models for sparse product families
- Time-series forecasting for incoming workload
- Reliability models for breakdown risk

#### How process mining informs the strategy

The MES log provides labeled historical outcomes:

- Actual task duration versus planned duration
- Setup duration versus planned duration
- Queue-delay patterns
- Breakdown frequency and repair duration
- Routing variants
- Effects of priority changes
- Tardiness outcomes

Process mining also identifies the correct contextual variables and process states required for prediction.

#### Pathologies addressed

- Unrealistic schedules based on average or planned durations
- Lack of proactive tardiness detection
- Late reaction to bottleneck overload
- Inability to estimate effects of breakdowns
- Weak customer promise-date reliability
- Unmanaged variability

#### Expected KPI impact

- More accurate delivery commitments
- Earlier identification of at-risk jobs
- Lower severe tardiness through proactive intervention
- Better disruption response
- Reduced schedule nervousness
- Improved resource allocation and maintenance timing

Potential caution: prediction alone does not improve performance unless its risk signals trigger operational decisions, such as resequencing, alternate-machine assignment, overtime, controlled release, or customer commitment revision.

---

### Strategy 3: Setup-Aware Sequencing and Product-Family Batching at Bottlenecks

#### Core logic

Use the sequence-dependent setup model to optimize job order at bottleneck machines. Instead of treating every setup as fixed, the scheduler evaluates the transition cost from the currently processed job to each candidate job.

For each machine, form job families based on setup-relevant characteristics:

- Material grade
- Thickness or stock size
- Tooling and fixture requirements
- CNC program family
- Heat-treatment recipe
- Surface finish or inspection requirements
- Clamping configuration

Then schedule jobs through a hybrid optimization objective:

\[
\min \left(
\alpha \cdot \text{Total Weighted Tardiness}
+
\beta \cdot \text{Total Setup Time}
+
\gamma \cdot \text{WIP}
+
\delta \cdot \text{Schedule Instability}
\right)
\]

subject to:

- Routing precedence
- Resource eligibility
- Due dates
- Priority constraints
- Operator availability
- Tooling constraints
- Material availability
- Machine calendars
- Hot-job response rules

Possible solution methods:

- Mixed-integer programming for small planning windows
- Constraint programming for complex sequence constraints
- Genetic algorithms or metaheuristics for larger job sets
- Tabu search or simulated annealing
- Dynamic programming for limited family-sequencing cases
- Rolling-horizon heuristic optimization

#### Practical policy design

Pure batching can harm due-date performance. Therefore use controlled batching rules, such as:

- Batch within a product family unless a job’s risk-adjusted slack falls below a threshold.
- Reserve a limited portion of capacity for urgent jobs.
- Do not delay a high-penalty job merely to save setup time.
- Use family campaigns at bottlenecks during stable demand periods.
- Permit controlled family breaks when the expected tardiness penalty exceeds setup savings.
- Freeze near-term sequences where possible to reduce schedule nervousness.

#### How process mining informs the strategy

The historical setup transition matrix identifies:

- Which job families can be grouped effectively
- Setup savings from favorable transitions
- Setups that are unavoidable
- Machine-specific setup behavior
- Operator effects
- Hot-job insertion costs
- The setup-versus-tardiness tradeoff observed historically

#### Pathologies addressed

- Frequent incompatible job switching
- High setup burden at bottlenecks
- Underestimated effective capacity
- Hot-job-driven schedule disruption
- Setup variability and poor sequence discipline

#### Expected KPI impact

- Reduced total setup hours
- Increased effective capacity at bottleneck resources
- Lower queue lengths and queue-time variability
- Improved throughput
- Lower WIP upstream of bottlenecks
- Better on-time performance when setup savings are reinvested in critical work

Potential caution: this strategy must be integrated with due-date risk; otherwise it can improve utilization while worsening customer delivery.

---

### Strategy 4: Bottleneck-Controlled Release and Event-Triggered Rescheduling

#### Core logic

Implement a constrained-resource scheduling approach, similar in spirit to Drum-Buffer-Rope or workload-control systems.

- **Drum:** the primary bottleneck sets the feasible production pace.
- **Buffer:** protect the bottleneck and critical due-date jobs with controlled time or workload buffers.
- **Rope:** release new work to the shop based on bottleneck capacity and buffer status, rather than simply releasing all available orders.

Rather than releasing every job immediately, release a job when:

- Its bottleneck operation can be reached within a target buffer window.
- Required material, tooling, and route information are ready.
- The release will not overload upstream queues beyond a defined workload limit.
- It supports downstream synchronization.

In parallel, use event-triggered rescheduling after:

- Machine breakdown start/end
- Hot-job arrival or priority change
- Significant duration overrun
- Material shortage
- Quality failure/rework
- Unexpected operator absence
- Bottleneck queue crossing a threshold

Rescheduling should focus first on the affected neighborhood of jobs and resources, avoiding unnecessary changes to the entire schedule.

#### How process mining informs the strategy

Process mining identifies:

- True bottlenecks
- Typical routing time to bottlenecks
- Required buffer sizes based on variability
- WIP levels associated with deteriorating lead-time performance
- Recovery patterns after disruptions
- Jobs most likely to create downstream starvation or blocking
- Capacity lost to breakdowns and setups

#### Pathologies addressed

- Excessive WIP release
- Congestion before bottlenecks
- Starvation downstream of critical resources
- Schedule instability after disruptions
- Poor recovery from breakdowns
- Uncontrolled hot-job expediting

#### Expected KPI impact

- Lower overall WIP
- Shorter and more predictable lead times
- Better flow efficiency
- More stable schedules
- Better bottleneck protection
- Improved on-time delivery, particularly under variable demand

Potential caution: controlled release requires discipline from sales, planning, and production. It may initially feel counterintuitive because fewer jobs are released, even though completion performance improves.

## 5. Simulation, Evaluation, and Continuous Improvement

No advanced scheduling policy should be deployed broadly without testing. In a complex job shop, interactions among routing variation, setup dependence, breakdowns, dispatching, and hot-job insertion are too nonlinear for spreadsheet analysis alone.

### 5.1 Build a process-mining-informed discrete-event simulation

Construct a discrete-event simulation or digital twin representing:

- Job arrivals and release patterns
- Job families and routing variants
- Processing-time distributions
- Setup-time transition model
- Machine eligibility and alternative resources
- Operator constraints and shift calendars
- Tooling and fixture constraints where material
- Machine breakdown frequency and repair-time distributions
- Priority changes and hot-job arrivals
- Queue and dispatching logic
- Rework and inspection failure loops
- Transfer delays
- WIP and release-control rules

Parameterize the model from actual MES history rather than assumed averages.

Examples:

| Simulation Input | Process-Mining Source |
|---|---|
| Routing probabilities and variants | Actual job traces |
| Processing-time distributions | Task start/end timestamps |
| Setup matrix | Consecutive job sequences on each machine |
| Breakdown rates and repair times | Breakdown events |
| Queue-time patterns | Queue entry and task-start events |
| Resource calendars | Machine and operator logs |
| Hot-job frequency | Priority-change events |
| Rework rates | Repeat operation / quality events |
| WIP release behavior | Job release records |
| Machine assignment patterns | Actual resource allocation data |

Use distributions rather than only means. For example:

- Lognormal, gamma, Weibull, or empirical distributions for duration
- Weibull or exponential models for failure behavior where appropriate
- Empirical distributions for highly irregular setup and repair times

---

### 5.2 Baseline model validation

Before comparing strategies, validate that the baseline simulation reproduces historical behavior.

Compare simulated and historical values for:

- Throughput
- WIP
- Resource utilization
- Queue time by work center
- Lead-time distribution
- On-time delivery
- Tardiness distribution
- Breakdown impact
- Setup-time share
- Bottleneck queue behavior
- Frequency of starvation and blocking

Validation should include both average behavior and variability. A model that matches average throughput but does not reproduce the long-tail tardiness distribution is not sufficient for due-date decision making.

---

### 5.3 Compare scheduling policies

Test at least:

1. **Current baseline:** FCFS/EDD mix.
2. **Dynamic multi-factor dispatching.**
3. **Predictive rolling-horizon scheduling.**
4. **Setup-aware bottleneck sequencing.**
5. **Bottleneck-controlled release with event-triggered rescheduling.**
6. **Hybrid policy:** controlled release + setup-aware bottleneck scheduling + dynamic dispatching elsewhere.

For each policy, run many replications with different random seeds to account for variation in job arrivals, durations, and breakdowns.

Compare:

- On-time delivery percentage
- Mean and percentile tardiness
- Weighted tardiness
- Total WIP
- WIP aging
- Lead-time median and 90th/95th percentile
- Flow efficiency
- Throughput
- Setup hours
- Productive machine utilization
- Bottleneck utilization and starvation
- Schedule stability
- Number of jobs rescheduled
- Hot-job response time
- Customer-service performance by priority class

Do not choose a policy only by average tardiness. A policy may reduce average tardiness but create a small number of catastrophically late high-value jobs.

---

### 5.4 Stress-test scenarios

The simulation should test realistic and adverse conditions.

#### Demand and load scenarios

- Normal load
- Moderate overload
- Peak-season overload
- Product-mix shift toward setup-intensive jobs
- Increased proportion of jobs requiring the bottleneck machine
- High proportion of short jobs versus long jobs

#### Disruption scenarios

- Frequent breakdowns at the primary bottleneck
- Long repair durations
- Simultaneous breakdowns on alternate machines
- Tooling shortages
- Operator absence
- Quality failure and rework surge
- Material delays

#### Priority scenarios

- Occasional hot jobs
- Frequent hot jobs
- Extremely urgent customer order
- Priority changes after job release
- Multiple competing urgent jobs

#### Data/model uncertainty scenarios

- Underestimated processing times
- Increased setup-time variability
- Forecast error in job arrivals
- Incomplete routing information
- Unexpected job additions

The preferred strategy should be robust, not merely optimal under average conditions.

---

### 5.5 Pilot deployment approach

A staged implementation is recommended.

1. **Diagnostic phase:** Build trusted event log, dashboards, bottleneck analysis, and setup model.
2. **Shadow mode:** Run the advanced scheduler in parallel with current scheduling, without changing operations.
3. **Limited pilot:** Apply the policy to one bottleneck resource group or one product family.
4. **A/B or phased comparison:** Compare performance against matched historical or contemporaneous control periods.
5. **Controlled expansion:** Extend to adjacent work centers and controlled release.
6. **Full closed-loop deployment:** Allow event-triggered rescheduling with planner approval thresholds.
7. **Automated but governed decision support:** Preserve human overrides with reason codes.

Human overrides are valuable data. Require planners to record reasons such as customer commitment, material availability, special tooling, quality concern, or strategic account escalation. These reasons should feed back into model refinement.

---

### 5.6 Continuous process mining and adaptive scheduling framework

The scheduling system should operate as a continuous learning loop:

\[
\text{MES Events}
\rightarrow
\text{Process Mining}
\rightarrow
\text{Predictive Models}
\rightarrow
\text{Scheduling Decisions}
\rightarrow
\text{Execution Outcomes}
\rightarrow
\text{Model and Policy Update}
\]

#### Operational monitoring dashboard

Track at least daily and by shift:

- On-time delivery
- Weighted tardiness
- Number of at-risk jobs
- WIP by work center
- WIP age
- Queue length and queue age
- Queue workload in standard hours
- Lead-time percentiles
- Bottleneck utilization
- Bottleneck starvation and idle-with-queue time
- Setup hours and setup variance
- Breakdown time and recovery time
- Priority changes and expediting impact
- Schedule adherence
- Forecast completion-date accuracy
- Forecast tardiness-risk calibration

#### Drift detection

Automatically monitor for changes in:

- Processing-time distributions
- Setup-time transition matrix
- Machine reliability
- Product mix
- Routing variants
- Operator performance
- WIP levels
- Due-date performance
- Hot-job arrival rate
- Model prediction error

Examples of alerts:

- Setup duration for a transition family exceeds the historical P90.
- Milling queue workload exceeds its historical control limit.
- On-time probability forecasts become poorly calibrated.
- A machine’s mean repair time increases significantly.
- A new routing variant begins appearing frequently.
- A resource that was historically noncritical becomes overloaded.
- Priority changes exceed the control threshold, indicating planning instability.

Use statistical process control methods, change-point detection, and model-performance monitoring. Retrain prediction models on a defined cadence, such as monthly or quarterly, with immediate recalibration after major product or equipment changes.

---

### 5.7 Governance and decision rights

Advanced scheduling should remain transparent and operationally usable.

Recommended governance:

- Planners approve major schedule changes during early deployment.
- The system explains each recommendation:
  - Due-date risk
  - Setup implication
  - Bottleneck impact
  - Expected tardiness reduction
  - Downstream effect
- Override reasons are captured.
- KPIs are reviewed weekly by operations, maintenance, engineering, and customer service.
- Root causes are assigned to process owners:
  - Capacity
  - Reliability
  - Setup reduction
  - Routing engineering
  - Material readiness
  - Scheduling policy
  - Data quality

The goal is not only better schedules; it is a continuously improving operating system for the job shop.

---

## Recommended Integrated Target State

Precision Parts should ultimately adopt a hybrid architecture rather than a single rule:

1. **Process mining layer:** continuously reconstruct actual flow, setups, queueing, disruptions, and routing deviations.
2. **Predictive layer:** estimate task duration, setup duration, breakdown risk, completion date, and tardiness probability.
3. **Planning layer:** use rolling-horizon, constraint-aware scheduling for bottlenecks and critical jobs.
4. **Execution layer:** use dynamic multi-factor dispatching at work centers.
5. **Flow-control layer:** govern job release based on bottleneck capacity and WIP limits.
6. **Resilience layer:** trigger targeted rescheduling after breakdowns, urgent orders, or major execution deviations.
7. **Simulation layer:** test policy changes before implementation.
8. **Continuous-improvement layer:** detect drift, retrain models, refine setup families, and revise scheduling rules.

This approach directly addresses the current weaknesses: it replaces isolated local dispatching with system-wide, data-driven decisions; treats setup dependence and uncertainty explicitly; controls WIP; anticipates disruptions; and uses the MES event data as a continuous source of operational learning.
