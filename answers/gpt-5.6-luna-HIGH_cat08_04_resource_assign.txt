# 1. Analyzing Resource Behavior and Assignment Patterns

## 1.1 Prepare the event log for resource analysis

Before analysis, TechSolve should create a reliable case-level event log in which each ticket has a complete lifecycle, for example:

> Ticket Created  Assigned  Work Started  Work Paused/Ended  Escalated  Reassigned  Resolved  Closed

The current log contains useful information, but several data preparation steps are important:

- Standardize activity names, such as `Assign L1`, `Assign L2`, and `Assign L3`.
- Distinguish the **assigned resource** from the **resource that actually began work**.
- Capture queue-entry and queue-exit timestamps.
- Identify whether a reassignment is:
  - a normal tier escalation,
  - a change of agent within the same tier,
  - a return to a previous agent,
  - a correction of an incorrect assignment, or
  - a transfer caused by shift or availability.
- Record agent skills as they existed at the time of the event, rather than using only the current skill profile.
- Add SLA due dates, business calendars, pause rules, resolution timestamps, reopen events, and customer-impact information.
- Separate productive work time from waiting time and administrative time.

This prevents incorrect conclusions. For example, the time between `Assign L2` and `Work L2 Start` should normally be treated as queue delay, not agent handling time.

## 1.2 Agent and tier performance metrics

Metrics should be calculated by agent, tier, skill, priority, category, channel, shift, and time period. Agent-level results should be risk-adjusted for ticket complexity and priority so that agents receiving more difficult tickets are not unfairly labeled as poor performers.

### Workload and utilization

Useful measures include:

- Number of tickets assigned, started, completed, and escalated.
- Number of tickets handled concurrently.
- Open backlog at the beginning and end of each shift.
- Queue age and oldest-ticket age.
- Productive handling time.
- Waiting time between assignment and work start.
- Utilization:

\[
\text{Utilization} =
\frac{\text{productive work time}}{\text{available working time}}
\]

- Occupancy during peak periods.
- Overtime and after-hours work.
- Workload concentration using the coefficient of variation or Gini coefficient across agents.
- Percentage of work performed by each tier.

A simple workload count can be misleading. One agent resolving ten simple P4 access requests may be less loaded than an agent working on three complex P1 network incidents. Therefore, TechSolve should also calculate a weighted workload score based on priority, estimated complexity, handling time, and required skills.

### Speed and quality

Important measures include:

- Time from ticket creation to first assignment.
- Time from assignment to first work start.
- Time in each tier queue.
- Active handling time by agent and tier.
- End-to-end resolution time.
- Time from escalation to specialist acceptance.
- Time between escalation and actual work start.
- Reopen rate.
- First-call resolution rate for L1.
- Resolution rate without escalation.
- Resolution rate after one assignment versus multiple assignments.
- Customer satisfaction, if available.
- SLA attainment by priority.

A useful L1 first-call resolution definition would be:

\[
\text{L1 FCR} =
\frac{\text{tickets resolved by L1 without escalation or reopen}}
{\text{tickets initially handled by L1}}
\]

The definition should specify an appropriate reopen window, such as seven or fourteen days.

### Skill and ticket-type behavior

For each agent, TechSolve should profile:

- Frequency of handling Hardware, Network, Software-App, Security, and Access Management tickets.
- Number of tickets handled for each required skill.
- Resolution rate by skill and category.
- Average handling and resolution time by skill.
- Escalation rate by ticket type.
- Reassignment rate by ticket type.
- Percentage of tickets handled outside the agent’s documented skills.
- Number of different skills used per agent.
- Whether the agent is being used at, below, or above their documented proficiency level.

Tier-level analysis should identify whether:

- L1 is receiving tickets that should be routed directly to L2 or L3.
- L1 is escalating categories that similarly skilled L1 agents resolve successfully.
- L2 and L3 are spending time on repetitive, low-complexity tasks.
- A small number of specialists are receiving a disproportionate amount of work.
- Some skills have long queues despite apparently available agents.
- One tier is acting as a bottleneck for another.

## 1.3 Process mining views of resource behavior

### Process discovery and performance analysis

A directly-follows graph can show the actual sequence of activities and resources. It should be filtered by:

- Priority.
- Category.
- Required skill.
- Tier.
- Channel.
- SLA outcome.
- Number of reassignments.

For example, a P3 Software-App variant might show:

> L1 Assignment  L1 Work  L2 Escalation  L2 Assignment  L2 Queue  L2 Reassignment  L2 Work  Resolution

The performance overlay can show the average time spent between each transition. This distinguishes whether the main problem is:

- slow initial assignment,
- L1 handling time,
- escalation approval,
- L2 queue waiting,
- skill mismatch,
- or rework after reassignment.

### Resource interaction and handover analysis

A resource social network can be created in which:

- Nodes represent agents, dispatchers, teams, or tiers.
- Edges represent ticket handovers.
- Edge weight represents the number of handovers.
- Edge thickness can represent average delay after a handover.
- Edge color can represent SLA breach rate.

This may reveal:

- Agents who frequently send work to one another.
- A dispatcher who acts as a central routing bottleneck.
- A particular L1-to-L2 handover that produces long delays.
- Specialists who receive work from many teams and have excessive inbound demand.
- Reassignment loops, such as Agent B12  Agent B15  Agent B12.

The network should distinguish legitimate escalation from avoidable rework. A handover from L1 to a firewall specialist may be appropriate; a transfer between two agents with the same qualification may indicate poor queue management or inaccurate assignment.

### Role discovery

Role mining can identify actual operational roles from observed behavior rather than relying solely on job titles. For example, the log may reveal:

- L1 agents who regularly perform advanced application support.
- L2 agents acting as informal dispatchers.
- Agents with high volumes of escalation approval activity.
- A group of “generalist” agents handling many categories.
- A small group of de facto experts who resolve most tickets in a specific skill area.

These observed roles can be compared with the documented model. Differences may indicate that the formal assignment logic is not aligned with how work is actually performed.

### Conformance checking

TechSolve should obtain the intended assignment rules and compare them with the event log. Examples of conformance rules include:

- P1 incidents must be assigned to an appropriately skilled L2 or L3 resource immediately.
- A ticket requiring `Networking-Firewall` cannot be assigned to an agent without that skill.
- L1 may handle a P3 Software-App ticket only if it belongs to an approved application category.
- Escalation to L3 requires a defined trigger or approval.
- Round-robin allocation should occur only among agents who are eligible and available.

Conformance checking can identify:

- Assignments outside the intended tier.
- Assignments to unqualified agents.
- Escalations without sufficient diagnostic information.
- Tickets remaining in a queue after an agent becomes unavailable.
- Reassignments that violate the intended routing logic.
- Cases where the actual process uses manual exceptions more often than expected.

## 1.4 Skill utilization analysis

A skill-capacity model should compare skill demand with qualified supply.

For each skill \(s\), calculate:

\[
\text{Demand}_s =
\text{number of tickets requiring }s
\]

\[
\text{Capacity}_s =
\sum \text{available hours of agents qualified in }s
\]

Also calculate:

- Average queue wait for skill \(s\).
- Backlog aging for skill \(s\).
- Percentage of tickets requiring \(s\) that are initially assigned correctly.
- Average number of qualified agents available per shift.
- Utilization of each qualified agent.
- Specialist workload by priority.
- Percentage of specialist time spent on work below their qualification level.

A “specialist leakage” measure could be defined as:

\[
\text{Specialist leakage} =
\frac{\text{specialist hours spent on low-complexity or non-specialist work}}
{\text{total specialist hours}}
\]

This should be interpreted carefully. A specialist may intentionally handle simple tickets during a low-demand period. The concern is sustained leakage while complex tickets are waiting.

In the example, Agent B12 is documented with `App-CRM` and `DB-SQL`. The first assignment may have been reasonable for `App-CRM`, but the later change to `Database-SQL` should be examined. If B12 already possessed the database skill, the reassignment may indicate:

- an inaccurate skill profile,
- a distinction between basic and advanced SQL proficiency,
- a change in the diagnosis,
- a workload or shift issue,
- or an unnecessary transfer.

The data should not assume that every reassignment is a failure; it should determine why it occurred.

# 2. Identifying Resource-Related Bottlenecks and Issues

## 2.1 Decompose total resolution time

For every ticket, decompose elapsed time into components:

\[
\text{Resolution time} =
\text{assignment delay}
+ \text{queue waiting}
+ \text{active handling}
+ \text{handover delay}
+ \text{rework}
+ \text{customer waiting}
\]

This allows TechSolve to determine whether SLA breaches are primarily caused by insufficient staffing, poor routing, excessive handling time, or process delays.

For example, in the sample:

- INC-1001 has approximately 20 minutes of L1 work.
- It has approximately 25 minutes between L2 assignment and L2 work start.
- It is reassigned after L2 work begins.
- The reassignment itself introduces an additional delay before Agent B15 starts work.

The full-year analysis should calculate these values for all tickets, not rely on a single example.

## 2.2 Locate skill-specific capacity bottlenecks

A skill bottleneck exists when tickets requiring a particular skill spend substantially longer waiting than comparable tickets requiring other skills.

Useful indicators include:

- Median and 90th percentile queue wait by skill.
- Number of open tickets per qualified agent.
- Skill-specific backlog growth.
- SLA breach rate by required skill.
- Number of tickets queued while all qualified agents are busy.
- Ratio of demand to available qualified capacity.
- Average time to identify and assign a qualified resource.
- Percentage of tickets routed first to an unqualified agent.

For example, if `Networking-Firewall` tickets have a 90th percentile assignment delay of two hours while general network tickets wait only fifteen minutes, the issue may be a shortage of firewall-qualified resources or an assignment rule that does not recognize the skill correctly.

## 2.3 Quantify reassignment and escalation impact

The analysis should distinguish:

- **Planned escalation:** L1 correctly escalates a complex ticket to an appropriate specialist.
- **Avoidable escalation:** L1 escalates a ticket that trained L1 agents commonly resolve.
- **Corrective reassignment:** the first agent lacks the required skill.
- **Capacity reassignment:** the first agent is unavailable or overloaded.
- **Administrative reassignment:** movement caused by shift changes or queue ownership.
- **Rework reassignment:** the receiving agent determines that the diagnosis or category was wrong.

Suggested metrics include:

\[
\text{Reassignment rate} =
\frac{\text{tickets with one or more reassignments}}
{\text{total tickets}}
\]

\[
\text{Average reassignments per ticket} =
\frac{\text{total reassignment events}}
{\text{total tickets}}
\]

\[
\text{Handover delay} =
\text{next agent work start}
-
\text{previous agent work end}
\]

The total delay attributable to reassignment should avoid double counting periods already included in queue time. A practical calculation is:

\[
\text{Reassignment delay} =
\sum_{i=1}^{n}
(\text{next work start}_i-\text{handover completion}_i)
\]

TechSolve should report:

- Average and median delay per reassignment.
- 90th percentile reassignment delay.
- Reassignment delay by agent pair, tier, skill, and priority.
- Percentage of tickets with multiple reassignments.
- SLA breach rate for tickets with zero, one, and multiple reassignments.
- Percentage of reassignments caused by documented skill mismatch.

## 2.4 Identify incorrect initial assignments

An initial assignment is potentially incorrect when:

- The assigned agent lacks the required skill.
- The agent is not authorized to handle the ticket’s priority or category.
- The ticket is reassigned before meaningful work begins.
- The receiving agent changes the ticket category or required skill.
- The ticket is escalated shortly after assignment with a standard “wrong queue” reason.
- The assigned agent has no availability during the relevant shift.
- The assignment is inconsistent with historical successful routing.

A useful measure is:

\[
\text{Right-first-assignment rate} =
\frac{\text{tickets not requiring corrective reassignment}}
{\text{total assigned tickets}}
\]

This should be measured separately from FCR. A ticket can be assigned correctly but still require escalation because it is genuinely complex.

## 2.5 Identify overloaded and underutilized resources

Overload can be indicated by:

- Sustained utilization above an agreed threshold.
- Large or aging queues.
- High concurrent ticket count.
- Excessive overtime.
- Long time from assignment to work start.
- High abandonment or missed SLA rates.
- High reassignment-out rate because the agent cannot start work.

Underutilization can be indicated by:

- Low queue occupancy during periods of high demand elsewhere.
- Long idle periods while qualified tickets are waiting.
- Low assignment volume after adjusting for shift duration.
- Skills that are available but not considered by the routing logic.

However, low ticket counts do not automatically imply poor performance. Agents may be working on long-running incidents, project work, major incidents, or administrative activities not captured in the incident log.

## 2.6 Correlate assignment patterns with SLA breaches

TechSolve should compare SLA outcomes across assignment patterns:

- Correct skill match versus mismatch.
- One assignment versus multiple assignments.
- L1 resolution versus escalation.
- Dispatcher assignment versus self-assignment.
- Assignment during normal hours versus off-hours.
- High versus low queue load.
- Specialist routing through a central dispatcher versus direct routing.
- Tickets assigned to the least-loaded agent versus round-robin agent.

A regression, survival analysis, or decision-tree model can estimate the effect of assignment conditions while controlling for priority, category, channel, shift, and complexity. For example:

\[
P(\text{SLA breach}) =
f(\text{priority}, \text{skill match}, \text{queue load},
\text{reassignments}, \text{tier}, \text{channel})
\]

This is more reliable than simply observing that reassignments and breaches occur together.

Potential outputs include statements such as:

- Tickets with an initial skill mismatch have a 2.4 times higher breach risk.
- Each additional handover adds a median of 18 minutes to resolution time.
- P2 tickets routed to the firewall queue after 30 minutes have a substantially higher breach rate.
- P3 application tickets handled by trained L1 agents have a lower total resolution time than those escalated immediately.

The actual numbers should be calculated from the full event log.

# 3. Root Cause Analysis for Assignment Inefficiencies

## 3.1 Potential root causes

### Assignment rules ignore skills

A round-robin rule may distribute tickets evenly across agents without considering:

- Required technical skill.
- Proficiency level.
- Priority.
- Current workload.
- Shift availability.
- Ticket complexity.
- Authorization restrictions.

This creates both skill mismatches and apparent fairness problems: work may be evenly distributed by ticket count but not by effort or complexity.

### Skill profiles are inaccurate or too coarse

The system may record that an agent has `Database-SQL`, but not distinguish:

- Basic versus advanced SQL.
- Development versus production support.
- Specific database platforms.
- Current certification status.
- Maximum authorized priority.
- Whether the agent is currently available for that skill.

Inaccurate profiles can cause both unqualified assignment and unnecessary reassignment.

### Ticket categorization is incomplete

A ticket may be initially categorized as `Software-App`, but the true need may be `Database-SQL`. Causes include:

- Limited information in the initial request.
- L1 selecting a broad category.
- No structured diagnostic questions.
- Customer descriptions using nontechnical language.
- Required skill being inferred only after investigation.

This creates a routing delay even when the correct specialist is available.

### No real-time capacity visibility

The dispatcher may know an agent’s nominal tier but not:

- Active ticket count.
- Current queue.
- Time remaining on an incident.
- Planned absence.
- Actual skill availability.
- Whether an agent is working on a major incident.

Consequently, the system can assign work to an agent who is technically qualified but practically unavailable.

### Excessive or unclear escalation

L1 agents may escalate because:

- The escalation criteria are unclear.
- They are measured on speed rather than resolution.
- They lack diagnostic tools or access rights.
- They are not empowered to resolve certain categories.
- Knowledge articles are incomplete.
- There is no feedback loop from L2 to L1.

Some escalations may therefore reflect training or process deficiencies rather than true complexity.

### Dispatcher and queue ownership issues

A manual dispatcher can become a bottleneck, especially if every escalation must be individually reviewed. Inconsistent decisions among dispatchers can also explain variation in assignment outcomes.

## 3.2 Variant analysis

Variant analysis compares process paths associated with different outcomes. TechSolve could create groups such as:

- No reassignment and SLA met.
- One reassignment and SLA met.
- Multiple reassignments and SLA breach.
- L1-resolved tickets.
- L1-to-L2 tickets resolved on first L2 assignment.
- Tickets that passed through three or more resources.
- Correctly routed versus initially mismatched tickets.

For each variant, compare:

- Priority and category.
- Required skill.
- Initial channel.
- Initial category.
- Agent tier and skill profile.
- Queue length at assignment.
- Time of day and day of week.
- Number of active tickets assigned to the resource.
- Escalation reason.
- Knowledge article usage.
- SLA outcome.

This can reveal patterns such as:

> P3 tickets created through email, categorized as Software-App, assigned by round-robin to general L1 agents, and escalated after a standard troubleshooting script are disproportionately likely to be reassigned to an application specialist.

## 3.3 Decision mining

Decision mining uses event attributes and process outcomes to determine which factors influence routing decisions. It can analyze transitions such as:

> Ticket Created  Assign L1  
> L1 Work End  Escalate L2  
> Escalate L2  Assign Agent

Candidate predictors include:

- Priority.
- Category.
- Required skill.
- Channel.
- Ticket description keywords.
- Agent availability.
- Queue length.
- Time of day.
- Historical success rate of the agent for that category.
- Current concurrent workload.
- Whether the ticket is a known issue.
- Whether a knowledge article was used.

Decision trees, rule mining, or interpretable machine-learning models can identify routing patterns. For example, the analysis may show that dispatchers assign based primarily on tier and round-robin order while largely ignoring the required skill field.

The objective should not be to automate historical behavior blindly. Historical choices may contain the very inefficiencies TechSolve wants to eliminate. The model should be evaluated against desired outcomes such as SLA compliance, first-time assignment accuracy, and resolution quality.

## 3.4 Root-cause validation

Each suspected cause should be validated using a combination of:

- Event-log evidence.
- Dispatcher and agent interviews.
- Observation of live work.
- Configuration review of the ITSM platform.
- Review of skill and queue maintenance processes.
- Comparison of system assignment records with actual work.

For example, a high reassignment rate may appear to indicate skill problems, but interviews may reveal that agents are reassigned automatically at shift end. The solution would then involve shift handover design rather than skill-based routing.

# 4. Data-Driven Resource Assignment Strategies

TechSolve should implement a controlled combination of strategies rather than replacing round-robin with a single complex algorithm.

## Strategy 1: Skill-based and proficiency-based routing

### Description

Route tickets first to eligible agents whose skills match the required capability. Use proficiency, authorization, and historical performance as additional criteria.

A routing score could be based on:

\[
\text{Assignment score} =
w_1(\text{skill match})
+w_2(\text{proficiency})
+w_3(\text{availability})
+w_4(\text{historical success})
-w_5(\text{current workload})
\]

Required controls include:

- Mandatory skill constraints for P1 and sensitive security tickets.
- Proficiency levels, such as basic, intermediate, and advanced.
- Certification and authorization status.
- Skill validity dates.
- Fallback rules when no perfect match is available.
- A clear escalation path when capacity is insufficient.

### Issue addressed

- Incorrect initial assignments.
- Reassignments caused by skill mismatch.
- Long queues for scarce skills.
- Inaccurate use of L2/L3 specialists.

### Process-mining insight used

Use the analysis of:

- Skill mismatch rates.
- Handover networks.
- Skill-specific queue times.
- Historical resolution success by agent and skill.
- Reassignment reasons.

### Required data

- Ticket category and required skill.
- Agent skill and proficiency matrix.
- Certifications and authorizations.
- Agent availability and shift schedule.
- Historical resolution outcomes.
- Priority and SLA due time.
- Escalation rules.

### Expected benefits

- Higher right-first-assignment rate.
- Fewer corrective reassignments.
- Lower time to specialist engagement.
- Better utilization of qualified specialists.
- Improved SLA performance for skill-constrained queues.

The routing system should not use historical success alone, as that could repeatedly send all tickets to a small group of experts. It should balance expertise with workload and provide opportunities for qualified agents to develop.

## Strategy 2: Workload- and SLA-aware assignment

### Description

Among eligible agents, select the agent or queue that can start the work earliest while protecting SLA commitments. The algorithm should consider:

- Current active tickets.
- Queue length.
- Estimated remaining work.
- Agent availability.
- Skill match.
- Ticket priority.
- SLA time remaining.
- Shift end time.
- Current concurrency.

An example priority score might be:

\[
\text{Routing priority} =
\alpha(\text{SLA urgency})
+\beta(\text{ticket priority})
+\gamma(\text{age})
-\delta(\text{available capacity})
\]

Round-robin may still be used, but only among eligible agents with comparable workload and availability.

### Issue addressed

- Overloaded agents.
- Underutilized agents.
- Assignment to technically qualified but unavailable resources.
- P2 and P3 SLA breaches caused by queue waiting.

### Process-mining insight used

Use:

- Queue waiting time by agent and tier.
- Workload distribution and load concentration.
- Time-to-start distributions.
- SLA breach patterns by queue state.
- Peak demand patterns by hour and day.

### Required data

- Real-time agent status.
- Current queue and active work.
- Estimated handling time by ticket type.
- Shift calendars and planned absences.
- SLA clocks and business calendars.
- Skill and proficiency information.

### Expected benefits

- Reduced time from assignment to work start.
- Lower workload variance.
- Reduced backlog aging.
- Fewer breaches caused by overloaded agents.
- Better use of currently underutilized qualified agents.

A practical implementation could initially route only P2 and P3 tickets using workload-aware logic while leaving low-risk P4 tickets on a simpler queue model.

## Strategy 3: Predictive triage and complexity-based routing

### Description

Use ticket text, category, channel, historical activity patterns, and customer information to predict:

- Required technical skill.
- Likely resolution tier.
- Complexity.
- Estimated handling time.
- Probability of escalation.
- Probability of SLA breach.

For example, a ticket categorized broadly as `Software-App` may contain keywords or patterns indicating `App-CRM` and `Database-SQL`.

The prediction should produce a confidence score. High-confidence predictions can be routed automatically; low-confidence cases should be reviewed by L1 or a dispatcher.

### Issue addressed

- Poor initial categorization.
- Incorrect required skill fields.
- Excessive escalation from L1.
- Long delays while the correct skill is discovered.

### Process-mining insight used

Train and validate the prediction using:

- Final required skill after investigation.
- Historical successful resolver.
- Escalation path.
- Reassignment reasons.
- Ticket description and category changes.
- Resolution time and complexity patterns.

### Required data

- Ticket subject and description.
- Category and subcategory.
- Channel.
- Customer or service affected.
- Final resolution code.
- Escalation and reassignment history.
- Required skill after diagnosis.
- Resolution time and SLA outcome.

### Expected benefits

- More accurate first assignment.
- Earlier identification of specialist-required work.
- Reduced time spent in generic L1 queues.
- Better estimates of queue capacity and SLA risk.
- More consistent triage across dispatchers and channels.

The model should be monitored for drift, especially when applications, infrastructure, or ticket terminology changes.

## Strategy 4: Evidence-based L1 empowerment and escalation refinement

### Description

Use process-mining results to identify ticket types that L1 agents frequently resolve successfully and ticket types that should be escalated earlier.

For each category and skill, establish:

- Permitted L1 resolution scope.
- Diagnostic steps.
- Maximum troubleshooting time.
- Required information before escalation.
- Conditions for direct L2 or L3 routing.
- Knowledge articles and automation available to L1.
- Feedback requirements after escalation.

For example, if trained L1 agents resolve a large proportion of standard CRM password or configuration issues without escalation, these should remain in L1. Conversely, if firewall change requests consistently require specialist authorization, they should bypass prolonged L1 troubleshooting.

### Issue addressed

- Unnecessary escalations.
- Inconsistent escalation behavior.
- L2/L3 time spent on routine work.
- Poor-quality escalations lacking diagnostic evidence.

### Process-mining insight used

Use:

- L1 FCR by category and agent.
- Escalation rates by ticket type.
- Escalation-to-resolution time.
- L2 rework caused by incomplete information.
- Successful L1 resolution variants.
- Knowledge article usage.

### Required data

- L1 activities and troubleshooting steps.
- Resolution codes.
- Escalation reasons.
- Reopen rate.
- Knowledge article usage.
- Agent training records.
- Required access and authorization data.

### Expected benefits

- Higher L1 FCR.
- Lower unnecessary L2/L3 demand.
- Better quality of escalated tickets.
- Reduced resolution time for genuinely complex work.
- Improved consistency between L1 agents.

The objective should not be to maximize L1 FCR at the expense of customer experience. Quality, reopen rate, and repeat-contact rate must be included.

## Strategy 5: Dynamic tier balancing and skills-based staffing

### Description

Use demand forecasts and real-time backlog information to move qualified agents temporarily between queues or tiers. This could include:

- Cross-training selected L1 agents for high-volume P3 application work.
- Allowing qualified L2 generalists to handle lower-complexity work during demand peaks.
- Creating virtual skill pools across teams.
- Establishing an on-call specialist rotation.
- Reserving capacity for P1/P2 incidents.
- Scheduling specialists based on historical demand by hour and day.

### Issue addressed

- Skill shortages during particular shifts.
- Uneven workload between tiers.
- Specialist queues that become bottlenecks.
- Fixed staffing models that do not reflect demand variability.

### Process-mining insight used

Use:

- Demand by skill and time period.
- Queue aging heatmaps.
- Capacity-to-demand ratios.
- Historical peak periods.
- Cross-tier handover patterns.
- SLA breach rates by shift.

### Required data

- Forecasted ticket arrivals.
- Skill and proficiency matrix.
- Shift and availability data.
- Queue backlog.
- Cross-training eligibility.
- Estimated handling times.
- Priority reservations.

### Expected benefits

- Greater resilience during peaks.
- Lower skill-specific queue waits.
- Improved SLA compliance.
- Reduced pressure on a small number of specialists.
- Better utilization of cross-trained resources.

# 5. Simulation, Implementation, and Monitoring

## 5.1 Use simulation before implementation

A process simulation model should be built from the mined process model and calibrated using historical data. The model should include:

- Ticket arrival rates by hour and day.
- Distribution of priorities and categories.
- Required skill distribution.
- Agent shifts and availability.
- Handling-time distributions by ticket type and tier.
- Escalation probabilities.
- Reassignment probabilities.
- Queue discipline.
- SLA rules and business calendars.
- Agent concurrency limits.

A discrete-event simulation could compare scenarios such as:

1. Current round-robin plus manual escalation.
2. Skill-based routing only.
3. Skill-based plus workload-aware routing.
4. Predictive triage plus workload-aware routing.
5. Additional cross-training for firewall or CRM support.
6. Direct routing of selected categories to L2.
7. Dedicated P2/P3 capacity during peak periods.

Each scenario should be evaluated using:

- SLA attainment by priority.
- Median and 90th percentile resolution time.
- Queue waiting time by skill.
- Number of reassignments.
- L1 FCR.
- Specialist utilization.
- Workload distribution.
- Backlog size and aging.
- Staffing cost.
- Customer-impact risk.

Simulation should use confidence intervals or repeated runs because ticket arrivals and handling times are variable. It should also test stress conditions, such as a sudden increase in firewall tickets or reduced staffing during holidays.

The simulation should be validated by replaying historical cases and checking whether it reproduces observed queue waits, escalation rates, and SLA breaches. It should be used as a decision-support tool, not as a substitute for operational judgment.

## 5.2 Implementation approach

A staged implementation is safer than an immediate full rollout.

### Phase 1: Establish data and baseline

- Standardize event definitions.
- Validate timestamps and resource identities.
- Build the skill and proficiency matrix.
- Establish baseline KPIs.
- Document current routing rules.
- Identify the highest-impact skills and queues.

### Phase 2: Pilot improved routing

Start with a limited scope, such as:

- P2 and P3 Network tickets.
- CRM application tickets.
- One service desk shift.
- A small set of qualified agents.

Use a shadow mode first, where the proposed algorithm recommends an assignment while the existing dispatcher remains in control. Compare recommended and actual assignments.

### Phase 3: Controlled rollout

- Introduce skill-based routing.
- Add workload and SLA awareness.
- Establish exception handling.
- Train dispatchers and agents.
- Retain manual override capability with a reason code.
- Review outcomes weekly.

### Phase 4: Expand and optimize

- Add predictive triage.
- Extend virtual skill pools.
- Introduce demand-based staffing.
- Retrain models as categories and applications change.
- Periodically review skill profiles and routing constraints.

## 5.4 Governance and safeguards

The new assignment logic should include:

- Manual override with a recorded reason.
- Rules that protect P1 and security-sensitive work.
- Clear fallback behavior when no qualified agent is available.
- Regular skill-profile validation.
- Monitoring for excessive concentration of work on particular specialists.
- Fairness checks across agents and shifts.
- Model-drift monitoring for predictive triage.
- Review of customer-impact and reopen metrics, not only speed.
- Periodic recalibration of routing weights.

The key success criterion is not simply fewer assignments or higher utilization. It is a balanced improvement across SLA compliance, first-time assignment accuracy, resolution quality, customer experience, and sustainable workload.

Overall, process mining should provide TechSolve with both a factual view of how tickets are actually routed and an evidence base for redesigning the assignment mechanism. The strongest target state is a hybrid model: skill-constrained, workload-aware, SLA-sensitive, predictive where reliable, and supported by human exceptions rather than dominated by manual or round-robin decisions.
