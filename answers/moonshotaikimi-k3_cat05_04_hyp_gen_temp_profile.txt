# Temporal Profile Anomaly Analysis: Insurance Claims Process

## 1. Identified Anomalies

### 1.1 Primary Anomalies

| Pair | Avg | StdDev | Anomaly |
|------|-----|--------|---------|
| RP | 90,000s (~25h) | 3,600s (1h) | StdDev implausibly low (~4% coefficient of variation) for a multi-step downstream activity |
| PN | 604,800s (7 days) | 172,800s (2 days) | Extreme delay; notification should be near-instant after approval |
| AC | 7,200s (2h) | 3,600s | Closure 2h after assignment is impossible if evaluation occurs ~23h after assignment |
| EN | 300s (5 min) | 60s | Near-instant, tightly clustered — signature of automation or skipped approval |

### 1.2 Internal Consistency Violations (Critical Finding)

The pairwise averages contradict each other arithmetically, which is often more revealing than any single pair:

1. **Closure before evaluation:** Implied AE = (RE)  (RA)  86,400  3,600 = **~23 hours**, yet AC = **2 hours**. On average, claims are closed ~21 hours *before* they are evaluated. A large subpopulation must be skipping E (and likely P and N) entirely.

2. **Contradictory notification timing:** If the path is EPN, then EN should be  (EP) + (PN)  1h + 7 days. The model says EN = **5 minutes**. At least two distinct notification behaviors coexist.

3. **Statistically impossible variance:** Var(RP) must be  Var(RE) absent strong negative correlation between stages. The model reports StdDev(RE) = 8h but StdDev(RP) = 1h. Variance *shrinks* across a downstream step — this strongly suggests RP times are not organically generated (e.g., a fixed-time batch job) or the model was fitted on a filtered subset.

4. **Minor inconsistency:** EC (60 min) < EN + NC (5 + 30 = 35 min) — again pointing to mixed paths.

**Conclusion:** The profile describes a heterogeneous mixture of process variants, not one stable process.

## 2. Hypotheses

- **H1 — Mixed subpopulations:** A fast-track path (e.g., low-amount auto claims auto-approved/auto-notified) is blended with a manual path, producing contradictory pairwise averages.
- **H2 — Premature closures:** Claims are closed shortly after assignment without evaluation/approval (duplicates, withdrawals, instant denials, fraud flags), explaining AC = 2h and the closure-before-evaluation paradox.
- **H3 — Batch approval job:** Approvals run on a fixed schedule (e.g., a nightly job), compressing observed RP variance and explaining the implausibly low StdDev.
- **H4 — Notification bottleneck:** PN's 7-day delay with high spread suggests manual notification, weekly batching, an external dependency (e.g., physical mail vendor), or understaffing concentrated in specific regions/teams.
- **H5 — Skipped approval:** The 5-minute EN transition indicates some claims notify the customer directly after evaluation, bypassing P — a compliance risk.
- **H6 — Data quality artifacts:** Timestamps back-filled in bulk, defaulted values, or mislabeled activities (E recorded as P) distorting intervals.
- **H7 — Rework/duplicate events:** Multiple occurrences of the same activity per claim skew first/last-timestamp–based interval calculations.
- **H8 — Resource-driven effects:** Specific adjusters, regions, or claim types account for a disproportionate share of the deviations.

## 3. Verification Queries (PostgreSQL)

**Reusable base CTE** — pivots each claim's lifecycle into one row (first occurrence per activity; swap `MIN` for `MAX` to test H7 with last occurrences):

```sql
WITH lifecycle AS (
    SELECT
        claim_id,
        MIN(timestamp) FILTER (WHERE activity = 'R') AS r_ts,
        MIN(timestamp) FILTER (WHERE activity = 'A') AS a_ts,
        MIN(timestamp) FILTER (WHERE activity = 'E') AS e_ts,
        MIN(timestamp) FILTER (WHERE activity = 'P') AS p_ts,
        MIN(timestamp) FILTER (WHERE activity = 'N') AS n_ts,
        MIN(timestamp) FILTER (WHERE activity = 'C') AS c_ts,
        MAX(resource)  FILTER (WHERE activity = 'A') AS assign_resource,
        MAX(resource)  FILTER (WHERE activity = 'E') AS eval_resource
    FROM claim_events
    GROUP BY claim_id
)
```

### Q1 — Recompute the profile from raw data (validate the model itself)

Tests whether the stored profile actually matches the data, or was fitted on a filtered subset (relevant to the variance paradox):

```sql
SELECT
```

### Q2 — Sequence violation detection (tests H2, H5, H6)

```sql
SELECT claim_id,
       (c_ts < e_ts) AS closed_before_eval,
       (n_ts < p_ts) AS notified_before_approval,
       (e_ts < a_ts) AS evaluated_before_assign,
       (e_ts IS NULL AND c_ts IS NOT NULL) AS closed_without_eval
FROM lifecycle
WHERE (c_ts < e_ts) OR (n_ts < p_ts) OR (e_ts < a_ts)
   OR (e_ts IS NULL AND c_ts IS NOT NULL);
```

**Look for:** the volume of out-of-order claims. A high count of `closed_before_eval` confirms the premature-closure subpopulation implied by AC.

### Q3 — Premature closure drill-down (tests H2, H8)

```sql
SELECT c.claim_type, l.assign_resource, COUNT(*) AS premature_closures,
       AVG(EXTRACT(EPOCH FROM (l.c_ts - l.a_ts))/60.0) AS avg_minutes_to_close
FROM lifecycle l
JOIN claims c USING (claim_id)
WHERE l.a_ts IS NOT NULL AND l.c_ts IS NOT NULL
  AND l.e_ts IS NULL                                   -- never evaluated
  AND EXTRACT(EPOCH FROM (l.c_ts - l.a_ts)) < 7200
GROUP BY 1, 2
ORDER BY 3 DESC;
```

**Look for:** concentration by claim type or resource — e.g., one adjuster closing most claims unevaluated (training/fraud issue) vs. an even spread (legitimate withdrawal process).

### Q5 — PN outlier claims with z-scores (tests H4; zeta-factor detection)

```sql
WITH pn AS (
    SELECT claim_id, EXTRACT(EPOCH FROM (n_ts - p_ts)) AS pn_secs
    FROM lifecycle
    WHERE p_ts IS NOT NULL AND n_ts IS NOT NULL AND n_ts > p_ts
),
stats AS (
    SELECT AVG(pn_secs) AS m, STDDEV_SAMP(pn_secs) AS s FROM pn
)
SELECT pn.claim_id, pn_secs / 86400.0 AS days_waiting,
       (pn_secs - m) / NULLIF(s, 0) AS z_score
FROM pn CROSS JOIN stats
WHERE ABS((pn_secs - m) / NULLIF(s, 0)) > 3      -- zeta = 3
ORDER BY days_waiting DESC;
```

### Q6 — Correlate PN delays with segments (tests H4, H8)

```sql
SELECT c.claim_type, adj.region, adj.name AS adjuster,
       COUNT(*)                                       AS claims,
       AVG(EXTRACT(EPOCH FROM (l.n_ts - l.p_ts)))/86400.0 AS avg_days_p_to_n,
       MAX(EXTRACT(EPOCH FROM (l.n_ts - l.p_ts)))/86400.0 AS max_days
FROM lifecycle l
JOIN claims c        USING (claim_id)
LEFT JOIN adjusters adj ON adj.name = l.assign_resource  -- assumes resource stores adjuster name
WHERE l.p_ts IS NOT NULL AND l.n_ts IS NOT NULL AND l.n_ts > l.p_ts
GROUP BY 1, 2, 3
HAVING COUNT(*) >= 10                                  -- avoid small-sample noise
ORDER BY avg_days_p_to_n DESC;
```

**Look for:** whether the 7-day average is uniform (systemic bottleneck) or driven by specific regions/adjusters/claim types (targeted resourcing issue). *(Join assumption: `claim_events.resource` holds the adjuster name; adjust if it stores `adjuster_id` or if the ID lives in `additional_info`.)*

### Q7 — Fast EN transitions with skipped approval (tests H5, H1)

```sql

       COUNT(*) FILTER (WHERE l.p_ts IS NULL)      AS no_approval_at_all,
       COUNT(*) FILTER (WHERE l.p_ts > l.n_ts)     AS approved_after_notification
FROM lifecycle l
JOIN claims c USING (claim_id)
WHERE l.e_ts IS NOT NULL AND l.n_ts IS NOT NULL
  AND EXTRACT(EPOCH FROM (l.n_ts - l.e_ts)) < 300
GROUP BY 1, 2
ORDER BY 3 DESC;
```

**Look for:** if fast EN maps cleanly to one claim type (e.g., auto), that confirms the fast-track subpopulation (H1). If `approved_after_notification` is high, it's a compliance violation pattern (H5).

### Q8 — Bimodality check on RP (tests H1)

```sql
SELECT WIDTH_BUCKET(EXTRACT(EPOCH FROM (p_ts - r_ts)), 0, 300000, 30) AS bucket,
```

### Q9 — Rework / duplicate activity detection (tests H6, H7)

```sql

FROM claim_events
GROUP BY 1, 2
HAVING COUNT(*) > 1

```

**Look for:** repeated R or E events; intervals computed on first-vs-last occurrence will differ substantially for these claims and may be contaminating the averages.
