# Analysis of the DECLARE Model

## 1. Identified Anomalies

### A1 — Hard contradiction: the model makes evaluation impossible
- `existence(C)` states that **every** trace must contain `C` (Close) with support/confidence 1.0.
- `noncoexistence(E, C)` states that `E` (Evaluate) and `C` **can never appear in the same trace**, also with support/confidence 1.0.
- Taken together, these two constraints imply that **`E` can never occur in any conforming trace**. `E` is a *dead activity*.
- Since the reference process requires evaluation as step 3, the model logically forbids the mandatory core of the business process. A model in which no trace can satisfy the intended happy path `RAEPNC` is unsatisfiable with respect to that path.

### A2 — Cascading vacuity of `responded_existence(E  A)`
- Because `E` is unreachable (A1), the constraint "if `E` occurs then `A` must occur" is **vacuously satisfied** in every trace. It contributes nothing and gives a false impression that the adjuster-assignment rule is enforced.
- Even if `E` were reachable, `responded_existence` is the *wrong template*: it only requires co-occurrence, not order. It permits `E` **before** `A` (evaluate first, assign an adjuster afterwards), which inverts the intended control flow.

### A3 — The only ordering constraint is trivially weak
- `precedence(C, R)`: "`R` must occur before `C`". Combined with `init(R)` (which already forces `R` to be the first event), this constraint is **redundant** — it is automatically satisfied by any trace and therefore filters out nothing.
- Result: the model's entire ordering knowledge collapses to "start with R, end (somewhere) with C".

### A4 — Essential steps are completely unconstrained (under-specification)
- There is **no constraint at all** on `A` (Assign), `P` (Approve) and `N` (Notify): no `existence`, no `response`, no `succession`, no `precedence`.
- Therefore the following traces are perfectly *conforming*:
  - `R  C` (claim received and closed, nothing else),
  - `R  P  C` (approved without ever being evaluated or assigned),
  - `R  C  N` (customer notified **after** the claim was closed),
  - `R  A  P  N  C` (approved without evaluation — no four-eyes / no assessment),
  - `R  P  P  P  C` (unbounded repetitions of approval; no cardinality limits).
- Financial-control logic (money may only be approved after an evaluation) and customer-communication logic (notify before closing) are entirely absent.

### A5 — Missing closure/termination semantics
- `existence(C)` guarantees `C` appears, but nothing guarantees it is **last** (`end`/`last` template missing) and nothing forbids activities after `C` (no `nonsuccession(C, *)`). Post-closure evaluation/approval is allowed.

### A6 — Suspicious metric values
- Every constraint carries `support = 1.0` and `confidence = 1.0`. A perfect-support `noncoexistence(E, C)` is only possible if **no** trace in the log contained both `E` and `C`. Combined with `existence(C)` at support 1.0, this implies the mining log contained **no evaluation events whatsoever** — a strong indicator that the metrics were not computed on the full, representative log (or were hand-written).
- A likely intent behind `noncoexistence(E, C)` was a **negative *ordering*** rule (e.g., "no evaluation *after* closing" = `nonsuccession(C, E)`), which was encoded with the wrong, much stronger template.

### Summary table

| # | Constraint(s) involved | Nature of the problem | Effect |
|---|---|---|---|
| A1 | `existence(C)` + `noncoexistence(E,C)` | Logical contradiction | `E` becomes a dead activity; happy path unsatisfiable |
| A2 | `responded_existence(E,A)` | Vacuous + wrong template | Assignment rule not enforced; `E` before `A` allowed |
| A3 | `precedence(C,R)` + `init(R)` | Redundancy | No effective ordering control |
| A4 | absence of rules on `A`,`P`,`N` | Under-specification | Skipping assignment/evaluation/approval/notification is legal |
| A5 | no `end`/`nonsuccession` on `C` | Missing termination semantics | Work possible after closing |
| A6 | all support/confidence = 1.0 | Implausible metrics | Model probably mined on filtered/partial data |

## 2. Hypotheses on the Origin of the Anomalies

**H1 — Wrong template selection during modeling.**
The modeler wanted "evaluation must not happen after the claim is closed" and picked `noncoexistence` instead of `nonsuccession`/`not_chain_succession`. Similarly, `responded_existence` was picked where `precedence`/`succession` was meant. This is a classic DECLARE template-confusion error.

**H2 — Mining on a biased or incomplete event log.**
If the discovery run was executed on a subset containing only *rejected, withdrawn, duplicate or fast-tracked* claims (which are closed without evaluation), the miner would legitimately derive `noncoexistence(E, C)` with support 1.0. The anomaly is then a *sampling artifact*, not a business rule.

**H3 — Evaluation logged in another system / renamed activity.**
Evaluation may have migrated to a separate assessment tool, an outsourced expert, or a new activity label (e.g., `E1`, `ASSESS`, or captured only in `additional_info`). The main log therefore shows `C` without `E`, and the miner "learned" that they exclude each other.

**H4 — Policy change not propagated consistently (concept drift).**
A straight-through-processing (STP) / auto-approval policy for small claims was introduced. Old constraints (evaluation mandatory) were removed, but new guarding constraints (e.g., "evaluation mandatory above a monetary threshold") were never added — leaving the model permissive for *all* claims instead of only small ones.

**H5 — Throughput/KPI pressure.**
Backlog- or cycle-time targets encouraged skipping assignment and evaluation. Practice was retro-fitted into the model, so the model documents shortcuts instead of controls (`RC` allowed).

**H6 — Manual editing / merge of two model versions.**
The redundant `precedence(C,R)` plus `init(R)`, and the absence of any rule for `A`, `P`, `N`, suggest fragments of two models were merged or that constraints were deleted during refactoring without validation.

**H7 — No formal satisfiability/consistency check in the tool chain.**
Hard-coded `support = confidence = 1.0` indicates the metrics were entered by hand or copied. Absence of a conflict/dead-activity checker allowed the contradiction to pass into production.

**H8 — Data-quality issues.**
Missing/duplicated events, unsynchronised clocks or truncated cases (log window cutting off evaluation events) can make legitimate behaviour look mutually exclusive to a miner.

## 3. Verification Strategy (SQL)

### 3.0 Reusable trace projection

```sql
-- One row per claim with its full trace signature and activity flags
CREATE OR REPLACE VIEW v_trace AS
SELECT
    c.claim_id,
    c.customer_id,
    c.claim_type,
    c.claim_amount,
    c.submission_date,
    MIN(e.timestamp)                                                   AS first_ts,
    MAX(e.timestamp)                                                   AS last_ts,
    COUNT(e.event_id)                                                  AS n_events,
    string_agg(e.activity, '->' ORDER BY e.timestamp, e.event_id)      AS variant,
    (array_agg(e.activity ORDER BY e.timestamp, e.event_id))[1]        AS first_activity,
    (array_agg(e.activity ORDER BY e.timestamp DESC, e.event_id DESC))[1] AS last_activity,
    BOOL_OR(e.activity = 'R') AS has_r,
    BOOL_OR(e.activity = 'A') AS has_a,
    BOOL_OR(e.activity = 'E') AS has_e,
    BOOL_OR(e.activity = 'P') AS has_p,
    BOOL_OR(e.activity = 'N') AS has_n,
    BOOL_OR(e.activity = 'C') AS has_c,
    MIN(CASE WHEN e.activity = 'A' THEN e.timestamp END) AS first_a,
    MIN(CASE WHEN e.activity = 'E' THEN e.timestamp END) AS first_e,
    MIN(CASE WHEN e.activity = 'P' THEN e.timestamp END) AS first_p,
    MIN(CASE WHEN e.activity = 'N' THEN e.timestamp END) AS first_n,
    MIN(CASE WHEN e.activity = 'C' THEN e.timestamp END) AS first_c,
    MAX(CASE WHEN e.activity = 'C' THEN e.timestamp END) AS last_c
FROM claims c
LEFT JOIN claim_events e ON e.claim_id = c.claim_id
GROUP BY c.claim_id, c.customer_id, c.claim_type, c.claim_amount, c.submission_date;
```

### V1 — Recompute the real support of every modelled constraint

```sql
SELECT
  COUNT(*) AS total_traces,
  -- init(R)
  ROUND(AVG((first_activity = 'R')::int)::numeric, 4)                       AS supp_init_R,
  -- existence(C)
  ROUND(AVG(has_c::int)::numeric, 4)                                        AS supp_existence_C,
  -- noncoexistence(E,C):  NOT (has_e AND has_c)
  ROUND(AVG((NOT (has_e AND has_c))::int)::numeric, 4)                      AS supp_noncoexist_E_C,
  -- responded_existence(E => A)
  ROUND(AVG((NOT has_e OR has_a)::int)::numeric, 4)                         AS supp_respexist_E_A,
  -- precedence(C,R): if C occurs, R must occur before the first C
  ROUND(AVG((NOT has_c OR (has_r AND first_ts <= first_c))::int)::numeric,4) AS supp_precedence_C_R
FROM v_trace;
```
*Interpretation:* if `supp_noncoexist_E_C` is clearly below 1.0, the constraint is empirically false and A1 is a modeling error, not reality. If it is 1.0, the process really never evaluates closed claims  investigate H2/H3.

### V2 — Claims closed without evaluation (violates intended flow, allowed by the model)

```sql
SELECT claim_id, claim_type, claim_amount, variant, first_c
FROM v_trace
WHERE has_c AND NOT has_e
ORDER BY claim_amount DESC;

-- Aggregated magnitude & financial exposure
SELECT claim_type,
       COUNT(*)                                        AS closed_claims,
       COUNT(*) FILTER (WHERE NOT has_e)               AS closed_without_eval,
       ROUND(100.0*COUNT(*) FILTER (WHERE NOT has_e)/COUNT(*), 2) AS pct,
       SUM(claim_amount) FILTER (WHERE NOT has_e)      AS amount_at_risk
FROM v_trace
WHERE has_c
GROUP BY claim_type
ORDER BY pct DESC;
```

### V3 — Traces where `E` and `C` coexist (direct falsification of `noncoexistence(E,C)`)

```sql
SELECT claim_id, variant, first_e, first_c,
       CASE WHEN first_e < first_c THEN 'E before C' ELSE 'E after C' END AS order_flag
FROM v_trace
WHERE has_e AND has_c
ORDER BY first_c;
```
*If most rows are `E before C`, the intended rule was almost certainly `nonsuccession(C, E)` ("no evaluation after closing"), i.e. only the `E after C` rows are truly problematic.*

```sql
-- ordering violation: E occurs before the first A
```

### V5 — Skipped mandatory steps / illegal shortcuts (A4)

```sql
-- Missing approval or notification before closing
SELECT claim_id, claim_amount, variant,
       (NOT has_a) AS no_assign,
       (NOT has_e) AS no_eval,
       (NOT has_p) AS no_approve,
       (NOT has_n) AS no_notify
FROM v_trace
WHERE has_c AND (NOT has_a OR NOT has_e OR NOT has_p OR NOT has_n);

-- Approval without any preceding evaluation (financial control breach)
SELECT claim_id, claim_amount, first_e, first_p, variant
FROM v_trace
WHERE has_p AND (NOT has_e OR first_e > first_p);

-- Notification after closure
SELECT claim_id, variant, first_n, first_c
FROM v_trace
WHERE has_n AND has_c AND first_n > first_c;
```

### V6 — Direct-follows shortcuts (e.g. `R` immediately followed by `C`)

```sql
WITH df AS (
  SELECT claim_id,
         activity                                                            AS a_from,
         LEAD(activity) OVER (PARTITION BY claim_id ORDER BY timestamp, event_id) AS a_to
  FROM claim_events
)
SELECT a_from, a_to, COUNT(*) AS freq
FROM df
WHERE a_to IS NOT NULL
GROUP BY a_from, a_to
ORDER BY freq DESC;

-- explicit R->C jumps
WITH df AS (
  SELECT claim_id, activity,
         LEAD(activity) OVER (PARTITION BY claim_id ORDER BY timestamp, event_id) AS nxt
  FROM claim_events
)
SELECT DISTINCT claim_id FROM df WHERE activity='R' AND nxt='C';
```

### V7 — Activity after closing (A5) and non-terminal `C`

```sql
SELECT e.claim_id, e.activity, e.timestamp, t.last_c

JOIN v_trace t ON t.claim_id = e.claim_id
```

### V8 — Variant profile (which behaviours actually exist)

```sql
SELECT variant, COUNT(*) AS cases,
       ROUND(100.0*COUNT(*)/SUM(COUNT(*)) OVER (), 2) AS pct,
       ROUND(AVG(claim_amount), 2) AS avg_amount,
       ROUND(AVG(EXTRACT(EPOCH FROM (last_ts-first_ts))/3600), 1) AS avg_hours
```

### V9 — Testing the fast-track / KPI-pressure hypotheses (H4, H5)

```sql
SELECT activity, COUNT(*) AS freq, MIN(timestamp) AS first_seen, MAX(timestamp) AS last_seen
```

### V12 — Resource/organisational conformance (are evaluations done by a qualified, assigned adjuster?)

```sql
-- Evaluations performed by resources that are not registered adjusters
SELECT e.claim_id, e.resource, e.timestamp
FROM claim_events e
LEFT JOIN adjusters a ON a.name = e.resource
WHERE e.activity = 'E' AND a.adjuster_id IS NULL;

-- Specialization mismatch: home claim evaluated by an auto adjuster (and vice versa)
SELECT c.claim_id, c.claim_type, a.name, a.specialization, a.region
FROM claim_events e
JOIN claims   c ON c.claim_id = e.claim_id
JOIN adjusters a ON a.name = e.resource
WHERE e.activity = 'E'
  AND split_part(c.claim_type, '_', 1) <> a.specialization;

-- Evaluator differs from the resource named at assignment time
WITH asg AS (
  SELECT claim_id, resource AS assigned_by, additional_info AS assign_info,
         ROW_NUMBER() OVER (PARTITION BY claim_id ORDER BY timestamp) rn
  FROM claim_events WHERE activity = 'A'
),
ev AS (
  SELECT claim_id, resource AS evaluator,
         ROW_NUMBER() OVER (PARTITION BY claim_id ORDER BY timestamp) rn
  FROM claim_events WHERE activity = 'E'
)
SELECT ev.claim_id, asg.assign_info, ev.evaluator
FROM ev LEFT JOIN asg ON asg.claim_id = ev.claim_id AND asg.rn = 1
WHERE asg.claim_id IS NULL
   OR (asg.assign_info IS NOT NULL AND asg.assign_info NOT ILIKE '%'||ev.evaluator||'%');
```

### V13 — Data-quality checks (H8) before trusting any conclusion

```sql
-- Claims with no events at all, or events referencing unknown claims
SELECT claim_id FROM v_trace WHERE n_events = 0;
SELECT DISTINCT e.claim_id FROM claim_events e
LEFT JOIN claims c ON c.claim_id = e.claim_id WHERE c.claim_id IS NULL;

-- Duplicated / repeated activities and simultaneous timestamps (ordering ambiguity)
SELECT claim_id, activity, COUNT(*) 
FROM claim_events GROUP BY 1,2 HAVING COUNT(*) > 1 ORDER BY 3 DESC;

SELECT claim_id, timestamp, COUNT(*) AS concurrent_events, string_agg(activity, ',')
FROM claim_events GROUP BY 1,2 HAVING COUNT(*) > 1;

-- Events before the claim was even submitted, or NULL fields
SELECT e.* FROM claim_events e JOIN claims c USING (claim_id)
WHERE e.timestamp::date < c.submission_date;
SELECT COUNT(*) FROM claim_events WHERE activity IS NULL OR timestamp IS NULL OR resource IS NULL;

-- Truncated cases (still running) — must be excluded from support computations
SELECT COUNT(*) AS open_cases FROM v_trace WHERE NOT has_c;
```

## 4. How the Findings Drive the Model Repair

| Verification result | Conclusion | Model action |
|---|---|---|
| V3 returns many `E before C` rows | `noncoexistence(E,C)` is wrong template | Replace with `nonsuccession(C, E)`; add `existence(E)` |
| V1 shows `supp_noncoexist_E_C  1.0` and V11 reveals a renamed/external evaluation step | Log/labelling problem (H3) | Fix event mapping, re-mine |
| V2/V5 show closures without `E`/`P`/`N` | Under-specification is real (A4) | Add `succession(R,A)`, `succession(A,E)`, `succession(E,P)`, `succession(P,N)`, `succession(N,C)`, `end(C)` |
| V9 shows skipping only for small amounts | Fast-track policy (H4) | Model two variants / conditional (MP-Declare) constraints on `claim_amount` |
| V10 shows a step change at a date | Concept drift | Version the model per period |
| V4/V12 show evaluations without/by unassigned resources | Control weakness | Add `precedence(E,A)` + resource-assignment rules |
| V13 shows duplicates/timestamp ties | Data-quality issue | Clean log before re-discovery; do not "fix" the model on dirty evidence |

Finally, before deployment the model should be run through an automated **consistency/dead-activity check** (satisfiability of the conjunction of all LTLf constraints), which would have flagged `existence(C)  noncoexistence(E,C)  ¬E` immediately.
