# Temporal Profile Analysis: Insurance Claim Handling Process

## 1. Identified Anomalies

### Anomaly A: RP Suspiciously Rigid Timing
- **Values:** AVG = 90,000s (~25 hours), STDEV = 3,600s (1 hour)
- **Issue:** The coefficient of variation (STDEV/AVG  4%) is extremely low for a process spanning multiple manual steps (Assign, Evaluate). Real-world claim approval timing should show much more variance given adjuster workload, claim complexity, and evaluation depth.

### Anomaly B: PN Extreme Delay with High Variance
- **Values:** AVG = 604,800s (7 days), STDEV = 172,800s (2 days)
- **Issue:** A week-long average delay between approval and customer notification is operationally excessive. The high variance suggests two distinct sub-populations: claims notified quickly and claims stuck in a backlog.

### Anomaly C: AC Premature Closure Risk
- **Values:** AVG = 7,200s (2 hours), STDEV = 3,600s (1 hour)
- **Issue:** Direct Assign-to-Close timing this short implies some claims skip Evaluate/Approve/Notify entirely, or these steps are logged out of order/retroactively.

### Anomaly D: EN Unrealistically Fast Transition
- **Values:** AVG = 300s (5 minutes), STDEV = 60s (1 minute)
- **Issue:** Five minutes between claim evaluation and customer notification is inconsistent with an approval decision-making process in between. This suggests either automated bypass or missing Approve (P) events.

---

## 2. Hypotheses

| Anomaly | Hypothesis |
|---|---|
| RP | Approval timestamps may be auto-generated by a batch job running on a fixed schedule (e.g., nightly at a set offset), rather than reflecting genuine adjuster decision-making. |
| PN | A manual notification queue (e.g., email/mail dispatch team) processes approvals in batches, causing backlog during high-volume periods; the bimodal variance suggests weekday/weekend or staffing-driven delays. |
| AC | A subset of claims are being auto-rejected or withdrawn shortly after assignment (e.g., duplicate claims, fraud flags, customer cancellations) without going through full evaluation — these may be miscategorized as "closed" rather than "denied." |
| EN | Certain claim types (e.g., low-value auto claims) may have an automated straight-through processing path that skips manual Approve logging, or the Approve event is being recorded with a duplicate/near-identical timestamp to Evaluate. |

**Cross-cutting hypothesis:** Certain adjusters, regions, or claim types may systematically bypass steps or introduce delays — resource-specific bottlenecks (e.g., single adjuster covering multiple regions) or system integration issues (e.g., two subsystems writing events with clock skew) could explain both the rigidity in RP and the backlog in PN.

## 3. Verification Queries

### 3.1 Detect Rigid RP Timing Distribution
```sql
-- Check actual distribution of R->P intervals for skew/clustering
WITH r_events AS (
    SELECT claim_id, timestamp AS r_time
    FROM claim_events WHERE activity = 'R'
),
p_events AS (
    SELECT claim_id, timestamp AS p_time
    FROM claim_events WHERE activity = 'P'
)
SELECT r.claim_id,
       EXTRACT(EPOCH FROM (p.p_time - r.r_time)) AS seconds_r_to_p,
       DATE_TRUNC('hour', p.p_time) AS approval_hour_bucket
FROM r_events r
JOIN p_events p ON r.claim_id = p.claim_id
ORDER BY seconds_r_to_p;
```
*Look for clustering at specific hour offsets (e.g., always ~25h mark), indicating batch processing.*

---

### 3.2 Identify Claims with Excessive PN Delay (Outside ZETA-based Threshold)
```sql
-- ZETA = 2 (example threshold), AVG=604800, STDEV=172800
WITH p_events AS (
    SELECT claim_id, timestamp AS p_time FROM claim_events WHERE activity = 'P'
),
n_events AS (
    SELECT claim_id, timestamp AS n_time FROM claim_events WHERE activity = 'N'
)
SELECT p.claim_id,
       EXTRACT(EPOCH FROM (n.n_time - p.p_time)) AS seconds_p_to_n,
       c.claim_type, c.customer_id
FROM p_events p
JOIN n_events n ON p.claim_id = n.claim_id
JOIN claims c ON c.claim_id = p.claim_id
WHERE EXTRACT(EPOCH FROM (n.n_time - p.p_time)) 
      > (604800 + 2 * 172800)  -- exceeds AVG + ZETA*STDEV
   OR EXTRACT(EPOCH FROM (n.n_time - p.p_time)) 
      < (604800 - 2 * 172800)
ORDER BY seconds_p_to_n DESC;
```

### 3.3 Correlate PN Delay with Resource/Adjuster
```sql
-- Join notification delay with the resource who performed the Notify step
WITH p_events AS (
    SELECT claim_id, timestamp AS p_time FROM claim_events WHERE activity = 'P'
),
n_events AS (
    SELECT claim_id, timestamp AS n_time, resource AS notify_resource
    FROM claim_events WHERE activity = 'N'
)
SELECT n.notify_resource,
       COUNT(*) AS num_claims,
       AVG(EXTRACT(EPOCH FROM (n.n_time - p.p_time))) AS avg_delay_seconds,
       STDDEV(EXTRACT(EPOCH FROM (n.n_time - p.p_time))) AS stdev_delay_seconds
FROM p_events p
JOIN n_events n ON p.claim_id = n.claim_id
GROUP BY n.notify_resource
ORDER BY avg_delay_seconds DESC;
```

### 3.4 Find Claims Closed Shortly After Assignment (Skipped Evaluate/Approve)
```sql
-- Claims where Close occurs without an intervening Evaluate or Approve event
WITH a_events AS (
    SELECT claim_id, timestamp AS a_time FROM claim_events WHERE activity = 'A'
),
c_events AS (
    SELECT claim_id, timestamp AS c_time FROM claim_events WHERE activity = 'C'
),
e_events AS (
    SELECT DISTINCT claim_id FROM claim_events WHERE activity = 'E'
),
p_events AS (
    SELECT DISTINCT claim_id FROM claim_events WHERE activity = 'P'
)
SELECT a.claim_id,
       EXTRACT(EPOCH FROM (c.c_time - a.a_time)) AS seconds_a_to_c,
       cl.claim_type, cl.claim_amount
FROM a_events a
JOIN c_events c ON a.claim_id = c.claim_id
JOIN claims cl ON cl.claim_id = a.claim_id
WHERE EXTRACT(EPOCH FROM (c.c_time - a.a_time)) < 7200 + 1*3600  -- within ZETA=1 threshold
  AND (a.claim_id NOT IN (SELECT claim_id FROM e_events)
       OR a.claim_id NOT IN (SELECT claim_id FROM p_events))
ORDER BY seconds_a_to_c ASC;
```

### 3.5 Check EN Transition for Missing Approve Events
```sql
-- Claims where Notify follows Evaluate almost immediately, with no Approve event
WITH e_events AS (
    SELECT claim_id, timestamp AS e_time FROM claim_events WHERE activity = 'E'
),
n_events AS (
    SELECT claim_id, timestamp AS n_time FROM claim_events WHERE activity = 'N'
),
p_events AS (
    SELECT DISTINCT claim_id FROM claim_events WHERE activity = 'P'
)
SELECT e.claim_id,
       EXTRACT(EPOCH FROM (n.n_time - e.e_time)) AS seconds_e_to_n,
       CASE WHEN p.claim_id IS NULL THEN 'Missing Approve' ELSE 'Approve Present' END AS approve_status
FROM e_events e
JOIN n_events n ON e.claim_id = n.claim_id
LEFT JOIN p_events p ON p.claim_id = e.claim_id
WHERE EXTRACT(EPOCH FROM (n.n_time - e.e_time)) < 300 + 1*60
ORDER BY seconds_e_to_n ASC;
```

### 3.6 Segment Anomalies by Adjuster Specialization and Region
```sql
-- Correlate A->C premature closures with adjuster attributes
WITH a_events AS (
    SELECT claim_id, timestamp AS a_time, resource AS adjuster_resource
    FROM claim_events WHERE activity = 'A'
),
c_events AS (
    SELECT claim_id, timestamp AS c_time FROM claim_events WHERE activity = 'C'
)
SELECT ad.specialization, ad.region,
       COUNT(*) AS num_fast_closures,
       AVG(EXTRACT(EPOCH FROM (c.c_time - a.a_time))) AS avg_seconds
FROM a_events a
JOIN c_events c ON a.claim_id = c.claim_id
JOIN adjusters ad ON ad.adjuster_id::VARCHAR = a.adjuster_resource
WHERE EXTRACT(EPOCH FROM (c.c_time - a.a_time)) < 7200
GROUP BY ad.specialization, ad.region
ORDER BY num_fast_closures DESC;
```

### 3.7 Detect Batch-Job Signature in RP (Time-of-Day Clustering)
```sql
-- Test hypothesis of scheduled batch approval job
SELECT EXTRACT(HOUR FROM p_time) AS approval_hour,
       COUNT(*) AS claim_count
FROM (
    SELECT p.claim_id, p.timestamp AS p_time
    FROM claim_events p
    WHERE p.activity = 'P'
) sub
GROUP BY approval_hour
ORDER BY claim_count DESC;
```
*A strong peak at a specific hour (e.g., 2 AM) would confirm automated batch approval rather than organic adjuster decisions.*
