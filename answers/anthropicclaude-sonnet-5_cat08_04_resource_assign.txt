# TechSolve Solutions: Process Mining-Driven Resource Assignment Optimization

---

## 1. Analyzing Resource Behavior and Assignment Patterns

### 1.1 Individual Agent & Tier Performance Metrics

**Workload Distribution Metrics:**
- **Case count per agent/tier per time period** (daily/weekly ticket volume assigned vs. resolved)
- **Concurrent open tickets per agent** (derived by overlapping "Work Start" to "Work End"/reassignment timestamps) — identifies overload
- **Idle time between ticket assignments** — identifies underutilization
- **Gini coefficient or coefficient of variation** across agents within each tier to quantify workload inequality

**Processing Time Metrics:**
- **Activity duration per agent**: `Work [Tier] End`  `Work [Tier] Start`, segmented by Priority, Category, and Required Skill
- **Waiting time before work starts**: `Assign [Tier]`  `Work [Tier] Start` (queue delay)
- **Total handling time per tier** vs. **total ticket lifecycle time** — reveals what % of SLA clock is consumed by queueing vs. actual work

**First-Call Resolution (FCR) Metrics:**
- **L1 FCR Rate** = (Tickets with only one `Work L1 Start/End` pair, no escalation) / (Total L1 tickets)
- Segment FCR by Category and Required Skill to identify categories where L1 consistently fails (e.g., low FCR on `Networking-Firewall` suggests L1 lacks that skill or authority)

**Skill-Utilization Frequency:**
- **Skill-match rate**: % of tickets where `Agent Skills` field contains `Required Skill` at time of assignment
- **Cross-tabulation** of Agent Skills vs. Required Skill actually handled — reveals mismatches (e.g., an agent with `DB-SQL` skill spending 80% of time on generic `Basic-Troubleshoot` tickets)

### 1.2 Process Mining Techniques for Actual Assignment Patterns

**Resource Handover / Social Network Analysis (SNA):**
- Build a **handover-of-work network**: nodes = agents/tiers, edges = frequency of case handoffs (e.g., A05  B12  B15 in INC-1001)
- Apply **SNA metrics**: 
  - *Betweenness centrality* — identifies agents who act as unintended "bottleneck hubs" (frequently receive escalations before correct routing)
  - *Edge weight analysis* — reveals which L1L2 or L2L3 pathways are abnormally frequent, suggesting systemic misrouting (e.g., all `App-CRM` tickets touching `DB-SQL` specialists mid-stream, indicating category tagging is wrong at intake)

**Role Discovery / Organizational Mining:**
- Use **role mining algorithms** (e.g., clustering agents by activity profiles they actually perform) to compare *discovered roles* against *documented tier/skill assignments*. Discrepancies (e.g., an "L1" agent whose discovered role profile matches L2 activity patterns) indicate informal skill drift not captured in HR/skill databases.

**Round-Robin vs. Actual Assignment Comparison:**
- Extract the **sequence of Dispatcher assignments** within a tier and statistically test for uniform distribution (expected under round-robin) vs. observed distribution. Significant deviation (e.g., A02 self-assigning per the log) indicates the "round robin" is being bypassed — possibly by agents cherry-picking easy tickets, worsening the overload problem.

**Escalation Path Mining (Variant Analysis):**
- Filter cases by **escalation count** (0, 1, 2+) and build separate process models (via Directly-Follows Graph or Heuristics Miner) for each cohort. Compare model complexity/loop structures — cases with 2+ escalations often reveal **ping-pong patterns** (L2L1L2) indicating unclear escalation criteria.

### 1.3 Skill Utilization Analysis

- **Specialist "downshifting" analysis**: For each L2/L3 agent, compute % of handled tickets where `Required Skill` is a *basic* skill (e.g., `Basic-Troubleshoot`) rather than their specialized skill. High percentages confirm the reported complaint of specialists doing L1-level work.
- **Skill scarcity heatmap**: Cross-reference `Required Skill` demand volume (from tickets) against the count of agents possessing that skill and their availability windows — reveals structural skill shortages (e.g., only 2 agents company-wide have `Security-IAM`, causing systemic queueing for Security tickets regardless of tier logic).
- **Proficiency inference**: Where multiple agents share a skill tag, compare their average resolution time and reassignment rate for that skill — infers *de facto* proficiency levels not captured in the flat skill list.

## 2. Identifying Resource-Related Bottlenecks and Issues

| Issue | Detection Method | Quantification Example |
|---|---|---|
| **Skill scarcity bottleneck** | Queue time (`AssignWork Start`) segmented by Required Skill; correlate with skill headcount | "Tickets requiring `Networking-Firewall` wait avg. 47 min vs. 12 min overall queue avg — only 4 agents hold this skill across 2 tiers" |
| **Reassignment-driven delay** | Compare cycle time of cases with 0 vs. 1 vs. 2+ reassignments (as in INC-1001's B12B15 handoff) | "Each reassignment adds avg. 55 minutes of dead time (queue re-entry + context loss); cases with 2 reassignments show 3.1x longer total cycle time" |
| **Incorrect initial (L1/Dispatcher) assignment** | Flag cases where `Required Skill` at escalation differs from `Required Skill` at ticket creation (e.g., INC-1001 shifts from App-CRM to Database-SQL) | "22% of L2 reassignments stem from wrong skill tag at intake, not agent incompetence" |
| **Overloaded/underutilized agents** | Concurrent workload distribution (Section 1.1) plotted as box plot per agent | "Top quartile of L2 agents carry 2.4x the average concurrent ticket load; bottom quartile agents are idle 35% of shift" |
| **SLA breach correlation** | Join SLA breach flag (derived from Priority-based SLA thresholds vs. actual resolution timestamp) with: reassignment count, skill-mismatch flag, escalation tier path | "68% of P2 SLA breaches involve at least one reassignment; skill-mismatched first assignments show 2.8x higher breach probability than skill-matched ones" |

**Root-cause attribution via regression/decision tree**: Run a decision tree or logistic regression with **SLA Breach (Y/N)** as target and features = {Priority, Category, initial skill match (Y/N), tier of first assignment, number of reassignments, agent tier of resolver}. This surfaces which factors most strongly predict breaches (e.g., "skill mismatch at first assignment" may emerge as the top splitting feature, explaining 40% of breach variance).

## 3. Root Cause Analysis for Assignment Inefficiencies

**Hypothesized Root Causes, each testable against the log:**

1. **Round-robin ignoring skill/workload**  Test: Do L1 self-assignments (like A02) correlate with subsequent escalation more than dispatcher-assigned tickets? If self-assigned tickets show higher escalation rates, it suggests agents grab tickets outside true competence to appear "active."

2. **Inaccurate skill profiles**  Test: For escalated tickets requiring skill X, check whether receiving L2/L3 agent's documented skills actually list X. If Dispatcher routes to an agent lacking the tag but who resolves successfully anyway (or vice versa), skill data is stale.

3. **Poor initial categorization**  Test: Frequency of `Required Skill` field changing between ticket creation and final resolution (as in INC-1001: App-CRM  Database-SQL). High change frequency by Category indicates intake triage (often L1 or automated categorization) is unreliable for certain categories.

4. **Lack of real-time workload visibility**  Test: Correlate assignment timestamps with agent's concurrent open-ticket count at that moment. If Dispatcher frequently assigns to already-overloaded agents (workload >90th percentile) at similar rates as to idle agents, this confirms assignment is blind to real-time load.

5. **L1 under-empowerment/under-training**  Test: Segment L1 escalation reasons (from Notes/free-text) via text mining/NLP clustering. If a large cluster of escalations cites categories that historically *have* been resolved by other L1 agents (proving it's within L1 capability), this points to training/knowledge-base gaps rather than genuine complexity.

**Variant & Decision Mining Application:**
- **Variant analysis**: Cluster process traces by structural similarity (using trace-alignment or edit-distance clustering). Compare the top 3 "smooth" variants (single assignment, fast resolution) against top 3 "problematic" variants (multiple escalations/reassignments) on shared attributes (Priority, Category, initial agent, time-of-day). This often reveals **temporal patterns** (e.g., problematic variants cluster around shift-change hours, suggesting handover gaps) or **agent-specific patterns** (e.g., a specific dispatcher's assignments disproportionately appear in problematic variants).
- **Decision mining**: At each XOR decision point in the discovered process model (e.g., "Escalate vs. Resolve at L1"), apply decision tree learning using case attributes available *at that point in time* (Priority, Category, agent skill vector, current queue depth) as predictors of the actual path taken. This produces explicit, data-backed decision rules that can be compared against — and used to formalize — the tacit rules agents currently apply inconsistently.

## 4. Data-Driven Resource Assignment Strategies

### Strategy 1: Skill-Based Weighted Routing with Proficiency Scoring

- **Issue Addressed**: Skill mismatches causing reassignments (e.g., B12B15 in INC-1001) and specialists handling below-skill tasks.
- **Process Mining Insight Leveraged**: Skill-utilization heatmap and skill-match rate analysis (Section 1.3) identify which skill-category pairs most need precise routing; proficiency inferred from historical resolution time/reassignment rate per skill.
- **Data Required**: Validated/refreshed skill matrix (multi-level: skill + proficiency score derived from historical performance), real-time ticket `Required Skill` tagging (improved via NLP on ticket description), agent current status.
- **Mechanism**: Route ticket to the *lowest-tier agent* holding the required skill *above a minimum proficiency threshold*, rather than pure round robin. Reserve top proficiency L2/L3 agents for tickets flagged as high-complexity via the decision-tree-derived complexity score.
- **Expected Benefits**: Reduction in reassignment rate (target: cut skill-driven reassignments by 40-60%), freed L2/L3 capacity for genuinely complex work, faster resolution for correctly matched tickets.

### Strategy 2: Real-Time Workload-Aware Dynamic Assignment

- **Issue Addressed**: Uneven workload distribution; assignment blind to current agent queue depth.
- **Process Mining Insight Leveraged**: Concurrent workload analysis (Section 1.1) showing overload/underutilization disparities; correlation between assignment-to-overloaded-agent and subsequent SLA breach.
- **Data Required**: Live feed of each agent's open-ticket count and estimated remaining capacity (derived from historical average handling time per skill), shift schedules.
- **Mechanism**: Replace static round-robin with a **capacity-weighted assignment score** = f(skill match, current load, priority of ticket). Use queueing-theory-based load balancing (e.g., "power of two choices" — compare two least-loaded qualified agents and assign to the lesser-loaded).
- **Expected Benefits**: Reduced variance in agent workload (target Gini coefficient reduction), lower average queue time, especially for P2/P3 tickets currently breaching SLA due to queuing at overloaded agents.

### Strategy 3: Predictive Complexity & Escalation-Likelihood Scoring at Intake

- **Issue Addressed**: Unnecessary escalations/reassignments caused by wrong initial tier assignment; L1 spending time on tickets destined to escalate anyway.
- **Process Mining Insight Leveraged**: Decision mining on the "Escalate vs. Resolve at L1" decision point; text-mining clusters of escalation reasons; historical FCR rate segmented by Category/Skill.
- **Data Required**: Historical labeled dataset of (ticket attributes at creation)  (eventual escalation Y/N, tier that resolved, time to resolve); NLP-derived features from ticket description text.
- **Mechanism**: Train a classification model predicting probability of L1 resolution success. Tickets predicted <30% likely to be L1-resolved are **routed directly to L2/L3** (or fast-tracked with L1 skipped), avoiding wasted L1 handling time and the associated queue delay before eventual escalation — directly targeting the INC-1001-style pattern where a ticket bounces through L1 before reaching the correct specialist.
- **Expected Benefits**: Reduced average number of touches per ticket, reduced total cycle time for tickets that would escalate anyway, improved L1 focus/FCR rate on tickets they retain (since low-probability ones are filtered out).

### (Optional 4th) Strategy 4: Dynamic Cross-Tier Skill Pooling

- **Issue Addressed**: Structural skill scarcity bottlenecks (e.g., only 2 IAM specialists) causing queueing regardless of routing logic quality.
- **Process Mining Insight Leveraged**: Skill scarcity heatmap; demand forecasting from historical ticket volume by Required Skill over time (seasonality/day-of-week patterns).
- **Data Required**: Historical demand time series per skill, cross-training status/certifications of agent pool, cost/time to reassign agents temporarily across tiers.
- **Mechanism**: Create a flexible "skill pool" override where, during predicted demand spikes for scarce skills, secondary agents (with partial/adjacent skills, e.g., `DB-SQL` agents assisting `App-CRM` overflow) are temporarily reassigned, informed by demand forecasting models built on the mined historical patterns.
- **Expected Benefits**: Smoothed demand peaks, reduced scarce-skill queue times without requiring immediate new hiring.

## 5. Simulation, Implementation, and Monitoring

### 5.1 Simulation Before Implementation

- **Build a simulation model** from the mined process (e.g., via Colored Petri Nets or discrete-event simulation tools like CPN Tools, ExtendSim, or PM4Py-based simulation) calibrated with:
  - Discovered process model structure (activity sequences, escalation branches, probabilities from decision mining)
  - Empirical distributions of activity durations per agent/tier/skill (fitted from log, e.g., lognormal for handling times)
  - Real resource calendars (shift patterns, availability)
  - Arrival process of tickets (fitted inter-arrival distribution per Priority/Category, including seasonality)

- **Run "what-if" scenarios**:
  - Baseline (current round-robin logic) vs. Strategy 1 (skill-weighted routing) vs. Strategy 2 (workload-aware) vs. combined
  - Vary parameters (e.g., proficiency threshold, capacity buffer) to find optimal configuration
  - Stress-test with historical peak-load periods to check resilience

- **Output metrics from simulation**: projected SLA compliance %, average cycle time, average reassignment count, agent utilization variance — compared against current-state baseline extracted from the real log, giving management a quantified business case (e.g., "Simulation projects Strategy 1+2 combined reduces P2 SLA breaches from 18% to 6%") before committing to IT/process changes.

- **Sensitivity analysis** to identify which parameter (skill accuracy, real-time data latency, agent count) most influences outcome — guiding where to invest first (e.g., if skill-data quality has the highest sensitivity, prioritize skill-matrix cleanup before algorithm rollout).

### 5.2 Post-Implementation Monitoring Plan

**Continuous Process Mining Dashboard** (using tools like Celonis, Disco, ProM, or custom PM4Py pipelines feeding BI dashboards), refreshed daily/real-time:

**Tier 1 — Headline KPIs:**
- SLA compliance rate by Priority (trend line, target vs. actual)
- Average end-to-end resolution time by Category/Priority
- Reassignment rate (target: <X% of tickets with 1 reassignment)
- First-Contact/First-Tier Resolution Rate by tier

**Tier 2 — Resource Views:**
- Live agent workload heatmap (current concurrent tickets vs. capacity threshold) — flags emerging overload
- Skill-match rate on assignment (% tickets routed to agent with required skill at first assignment)
- Utilization balance index (Gini/variance across agents) — trend over time to confirm workload equalization
- Escalation path Sankey diagram (updated weekly) — visually tracks whether ping-pong/misrouting patterns are diminishing

**Tier 3 — Model Drift & Algorithm Health:**
- Predictive model accuracy tracking (for Strategy 3's escalation-likelihood model) — precision/recall drift over time, triggering retraining
- Comparison of *actual* discovered process variants post-implementation vs. the simulated target model — conformance checking to detect if new routing logic is being followed in practice or bypassed (e.g., are dispatchers overriding the algorithm?)
- A/B or phased rollout comparison: cohort of tickets under new logic vs. legacy logic (if phased) to statistically validate improvement before full-scale deployment

**Governance Loop**: Monthly review comparing dashboard KPIs against simulation-projected targets; feed any negative deviations back into root-cause and decision-mining analysis (Section 3) to refine rules — establishing a **closed-loop, continuously-improving assignment system** rather than a one-time fix.
