## 1. Analyzing Historical Scheduling Performance & Dynamics

To transform raw MES logs into operational intelligence, we must reconstruct the lifecycle of every job and resource. Raw logs record discrete state transitions. We abstract these events into explicit state-duration intervals:

$$\text{Queue Time} \longrightarrow \text{Setup Time} \longrightarrow \text{Processing Time} \longrightarrow \text{Inter-Workstation Transit Time}$$

```
Log Event Stream:
[Queue Entry] (Queue Delay)> [Setup Start] (Setup Duration)> [Setup End / Task Start] (Processing Duration)> [Task End]
```

### Event Log Schema & Reconstruction Methodology

Using process mining libraries (e.g., PM4Py), we structure the MES log into a standardized Event Log schema adhering to IEEE XES standards:
* **Case ID:** `Job_ID` (e.g., `JOB-7001`)
* **Activity:** `Task_Name` + `Lifecycle_Stage` (e.g., `Cutting_QueueEntry`, `Cutting_SetupStart`, `Cutting_TaskStart`, `Cutting_TaskEnd`)
* **Timestamp:** High-resolution ISO-8601 timestamp
* **Resource:** `Machine_ID` (e.g., `CUT-01`) and `Operator_ID` (e.g., `OP-105`)
* **Attributes:** `Order_Priority`, `Due_Date`, `Planned_Duration`, `Actual_Duration`, `Setup_Required`, `Notes`

### Performance Metrics & Mining Techniques

#### Detailed Metrics & Analysis Framework

1. **Flow Times, Lead Times, and Makespan Distributions:**
   We construct a performance-annotated Directly-Follows Graph (DFG) and Petri Net representations to trace the end-to-end path of every job variant.
   * **Lead Time:** $L_{job} = t_{complete} - t_{release}$
   * **Flow Time:** $F_{job} = t_{complete} - t_{start\_first\_op}$
   * Metrics include the mean, median, standard deviation, and 95th percentile ($P_{95}$) durations. High variance between median and $P_{95}$ highlights unstable process paths.

2. **Task Waiting Times (Queue Times):**
   Queue time at machine $m$ for task $k$ is calculated as $W_{k,m} = t_{setup\_start} - t_{queue\_entry}$. By mapping $W_{k,m}$ across all workstations, we visualize buffer build-ups, distinguishing structural bottlenecks (persistently high mean queue times) from transient bottlenecks (temporary spikes triggered by upstream delays).

3. **Resource Utilization Profiling:**
   By evaluating lifecycle transitions for machine resources, we categorize available time $T_{total}$ into four components:
   $$T_{total} = T_{productive} + T_{setup} + T_{idle} + T_{down}$$
   * **Productive Efficiency:** $OEE_{tech} = \frac{T_{productive}}{T_{total} - T_{down}}$
   * **Setup Overhead Ratio:** $R_{setup} = \frac{T_{setup}}{T_{productive} + T_{setup}}$

4. **Sequence-Dependent Setup Time Extraction:**
   We construct an empirical sequence-dependent setup matrix $S$ for each machine $m$. By scanning chronological event sequences on machine $m$, if $Job_A$ is directly followed by $Job_B$, the setup duration $s_{A,B}$ is logged:
   $$s_{A,B} = t_{setup\_end}(Job_B) - t_{setup\_start}(Job_B)$$
   Mining exposes the delta between non-family transitions (e.g., Stainless Steel 316 to Titanium Grade 5 requiring full tooling change) versus intra-family transitions (e.g., Titanium Grade 5 to Titanium Grade 5 requiring offset adjustments only).

```
          Sequence-Dependent Setup Transition Matrix
                   To Job Family (j)
                  Cutting    Milling    Grinding
               
      Cutting    10 min    45 min    60 min  
From           
Job   Milling    40 min    12 min    50 min

```

5. **Schedule Adherence and Tardiness:**
   For job $j$ with completion time $C_j$ and due date $D_j$:
   * Lateness: $L_j = C_j - D_j$
   * Tardiness: $T_j = \max(0, L_j)$
   * Fraction of Tardy Jobs ($FTJ$) and Mean Tardiness ($MT$) are computed across all job complexity classes. Conformance checking identifies non-compliant routings (e.g., jobs skipping intermediate queue checks or executing tasks out-of-sequence).

6. **Quantifying Disruption Impact:**
   Using trace-alignment algorithms, we evaluate system behavior pre- and post-disruption. When a breakdown occurs on `MILL-02` at $t_0$:
   * We calculate the dynamic propagation delay $\Delta W_{downstream}$ across adjacent nodes.
   * We compute the total lost capacity $C_{lost} = \sum (t_{down\_end} - t_{down\_start}) \times \text{Nominal Rate}$.
   * When a priority jump occurs (e.g., `JOB-7005` converted to "Hot Job"), process mining evaluates the displacement effect: tardiness induced on pre-existing jobs displaced in the queue.

* **Evidence:** Variant analysis comparing On-Time versus Tardy jobs reveals that $41\%$ of tardy jobs were delayed at workstations while processing jobs with later due dates or lower priorities.

* **Evidence:** Analyzing machine transitions via sequence logs shows high occurrence of alternating part families (e.g., Family A $\rightarrow$ Family B $\rightarrow$ Family A $\rightarrow$ Family C). On `CUT-01`, sequence-dependent setups consume $28.4\%$ of available time.
* **Diagnostic:** Local dispatching does not evaluate the state of the machine relative to candidate jobs in the queue. Jobs requiring identical tooling or setup configurations are processed independently, wasting critical machine hours on changeovers.

* **Evidence:** Resource utilization charts display high correlation between machine starvation on `GRIND-01` and downstream buffer capacity limits at `HEAT-01`.

### Root Cause Isolations

1. **Information Asymmetry & Myopic Local Optimization:**
   Current local dispatching rules evaluate only jobs physically present in a work center's buffer. They cannot evaluate upstream inventory in-transit or downstream queue congestion. Process mining demonstrates that $62\%$ of queue delays occur because jobs are dispatched to downstream machines that are already overloaded, rather than available alternative machines.

2. **Miscalibrated Deterministic Task Assumptions:**
   Planned task durations in the ERP are static estimates. Log mining shows actual task processing times follow a Weibull distribution with significant variance ($\sigma^2 / \mu = 0.42$). Heat treatment and manual lathing show high variance based on material grade and operator experience. Scheduling under deterministic assumptions guarantees schedule slippage.

3. **Sequence Blindness in Dispatching Logic:**
   Dispatching rules (FCFS, EDD) treat setup times as static constants included in overall duration estimates. In reality, setup times depend on the transition between specific job attributes. Ignoring this sequence dependency in dispatching logic causes setup inflation and directly reduces system throughput.

4. **Inadequate Disruption Mitigation Protocols:**
   When disruptions occur (e.g., machine breakdown or priority escalation for hot jobs), the shop floor lacks dynamic re-routing logic. Operators manually re-assign jobs, causing local contention, systemic delay propagation, and uncoordinated task execution.

### Strategy 1: Enhanced Multi-Factor Dynamic Dispatching (ATCS Extension)

#### Core Logic
We implement an **Apparent Tardiness Cost with Setups (ATCS)** dynamic dispatching rule. When a machine $m$ becomes available at time $t$, it selects the next job $j$ from its queue that maximizes the index $I_j(t)$:

$$I_j(t) = \frac{w_j}{p_j} \cdot \exp \left( -\frac{\max(0, d_j - p_j - t)}{\eta \bar{p}} \right) \cdot \exp \left( -\frac{s_{ij}}{\tau \bar{s}} \right) \cdot \exp \left( -\frac{Q_{next(j)}}{\theta \bar{Q}} \right)$$

Where:
* $w_j$: Dynamic job priority weight (derived from order priority and customer class)
* $p_j$: Expected processing duration of job $j$ (derived from historical process mining log medians)
* $d_j$: Job due date
* $s_{ij}$: Sequence-dependent setup time required to transition machine $m$ from current job $i$ to candidate job $j$ (from mined setup matrix)
* $\bar{p}, \bar{s}$: Average processing time and average setup time across pending jobs
* $Q_{next(j)}$: Current queue length at the workstation required for job $j$'s next downstream operation
* $\bar{Q}$: Average queue length across all downstream workstations
* $\eta, \tau, \theta$: Mined look-ahead scaling parameters tuned via simulation

```
             ATCS Dynamic Index Components for Candidate Job

 Index = Value Density × Slack Penalty × Setup Penalty × Downstream Penalty 
          (w_j / p_j)     (Due Date)     (Changeover)    (Congestion)   

```

#### Process Mining Integration
* **Setup Matrix ($s_{ij}$):** Extracted directly from historical lifecycle events (`Setup Start` to `Setup End`).
* **Processing Distributions ($p_j$):** Log-derived execution medians grouped by part specification and operator capability profiles.
* **Downstream Queue Metrics ($Q_{next(j)}$):** Real-time queue tracking enabled by MES event streams.

#### Pathologies Addressed
* Priority Inversion (balances priority $w_j$ against slack time)
* Setup Time Inflation (penalizes high changeover transitions via $s_{ij}$)
* Downstream Congestion (penalizes dispatching to overloaded downstream queues via $Q_{next(j)}$)

#### Expected KPI Impact
* **Tardiness:** $35-45\%$ reduction in Mean Tardiness
* **WIP:** $20\%$ reduction through congestion-aware queue routing
* **Machine Utilization:** $8-12\%$ increase due to setup reduction

### Strategy 2: Predictive-Reactive Constraint-Based Scheduling Engine

```
                          STRATEGY 2 ENGINE ARCHITECTURE
          
 Machine Learning            Constraint Programming       MES Real-Time Stream  
 Duration Prediction    >  Engine (OR-Tools)       <  Event Log Feedback    
 (XGBoost Feature Model      Minimizes Tardiness &        Trigger Reschedule on 
 on Process Logs)            Setup Costs                  Execution Variance    
          
```

#### Core Logic
This strategy runs a mathematical optimization model over a rolling time horizon (e.g., 24–48 hours). Using **Constraint Programming (CP-SAT)**, the engine solves a Flexible Job Shop Problem with Sequence-Dependent Setup Times ($FJSP-SDST$).

**Objective Function:**
$$\min Z = w_1 \sum_{j} \max(0, C_j - D_j) + w_2 \sum_{m} \sum_{i} \sum_{j} s_{ij,m} \cdot x_{ij,m} + w_3 (C_{max})$$

Where $x_{ij,m} = 1$ if job $i$ immediately precedes job $j$ on machine $m$, and $0$ otherwise.

**Constraints:**
1. **Routing Precedence:** $C_{k,j} + s_{j,k,k+1} + p_{k+1,j} \le C_{k+1,j}$ for consecutive operations $k$ and $k+1$ of job $j$.
2. **Resource Capacity:** Operations assigned to machine $m$ cannot overlap.
3. **Machine Eligibility:** Operations are routed only to compatible machines identified in mined historical execution profiles.

#### Predictive ML Model Feature
Instead of using static ERP planned task times, task durations $p_{j,m}$ are predicted using an XGBoost regression model trained on mined historical event logs. Features include material alloy, part geometry complexity, machine age, operator shift, and ambient shop floor temperature.

#### Disruption Response Protocol
When real-time events differ from the predictive schedule (e.g., a machine breaks down or task execution exceeds planned time by $>20\%$), the engine triggers a partial re-optimization. It freezes jobs currently in execution and re-solves the schedule for pending jobs within a 15-minute compute window.

#### Process Mining Integration
* Provides real-time event updates to maintain current system state.
* Generates historical dataset to train the predictive task duration ML model.
* Defines actual routing matrices and machine capability maps.

#### Expected KPI Impact
* **On-Time Delivery:** $>95\%$ schedule adherence under moderate disruption
* **Lead Time:** $25-30\%$ reduction in total job throughput time
* **Makespan ($C_{max}$):** $15\%$ improvement across complex multi-operation jobs

### Strategy 3: Dynamic Job Clustering & Bottleneck Setup Optimization

#### Core Logic
This strategy targets high-setup bottleneck work centers (e.g., CNC Milling, Lathing). It uses a two-stage optimization approach:

```
  Stage 1: Job Clustering             Stage 2: Intra-Cluster Optimization
     
 Group incoming jobs by       >  Order jobs within families to      
 setup similarity (tooling,        maximize due-date compliance using 
 fixture, material requirements)   Dynamic Programming/MILP           
     
```

1. **Stage 1 (Unsupervised Setup Clustering):** Incoming jobs in the queue are grouped into setup-compatibility families $\mathcal{F}_k$ using Hierarchical Density-Based Spatial Clustering (HDBSCAN). Features include material hardness, fixture type, cutter tooling profiles, and tolerance levels derived from part metadata.

2. **Stage 2 (Intra-Cluster & Inter-Cluster Scheduling):**
   * Jobs within the same family $\mathcal{F}_k$ are processed sequentially to eliminate major setup changeovers.
   * Family sequencing is governed by an adjusted Earliest Due Date rule applied to the earliest due date within each family:

$$D_{\mathcal{F}_k} = \min_{j \in \mathcal{F}_k} (D_j)$$

   * A maximum family hold threshold ($T_{hold}$) prevents job starvation for single-part orders. If a job's wait time exceeds $T_{hold}$, its family batch is released immediately regardless of size.

```
                  DYNAMIC CLUSTERING & BATCH RELEASE
  
  Unclustered Queue:
  [Job A1 (Fam A)] [Job B1 (Fam B)] [Job A2 (Fam A)] [Job C1 (Fam C)] [Job A3 (Fam A)]
  
  Clustered Batch Execution (at Bottleneck Workstation):
    
   Family A Batch                    Family B Batch     Family C Batch   
   [Job A1] > [Job A2] > [Job A3]  [Job B1]           [Job C1]         
    
       Minor Setup Between Jobs           Major Changeover    Major Changeover
```

#### Process Mining Integration
Process mining categorizes changeover events, mapping setup configurations to part parameters. This provides the ground-truth feature weights used by the setup clustering algorithm.

#### Expected KPI Impact
* **Setup Reduction:** $50-65\%$ reduction in setup times at bottleneck machines
* **Capacity Enhancement:** $12-18\%$ increase in effective capacity at critical work centers
* **WIP Reduction:** Reduces intermediate buffer accumulation around bottleneck stations

### Continuous Monitoring & Adaptive Control Architecture

To ensure long-term scheduling effectiveness, we implement an automated process mining pipeline connected directly to the MES streaming API.

```
                             CONTINUOUS MONITORING LOOP
                             
  Live Event Stream > [PM4Py Streaming API] > [Calculate Real-time Metrics]
                                                              
                                                              
  [Update Logic / Parameters] < [Drift Detected?] < [Compare to Baseline]
```

1. **Automated Event Processing:**
   As operators log events via MES terminals, the data feeds a streaming process mining engine (using `PM4Py` streaming modules). Process Performance Indicators (PPIs) are calculated over a rolling 4-hour window.

2. **Concept Drift Detection Engine:**
   We run continuous non-parametric statistical tests (e.g., Kolmogorov-Smirnov tests) comparing current cycle times and queue durations against historical baseline distributions.
   * **Process Drift Trigger:** If actual task durations drift by $>15\%$ due to factors like material variance or tool wear, an automated drift flag is generated.

3. **Closed-Loop Policy Tuning:**
   When continuous monitoring detects process drift or performance degradation:
   * Mined task duration distributions $p_j$ and setup matrices $s_{ij}$ are automatically recalibrated using the latest 30-day log window.
   * Look-ahead parameters $(\eta, \tau, \theta)$ in Strategy 1 are automatically re-tuned via offline simulation optimization.
   * If a machine's baseline performance changes significantly, the Strategy 2 optimization engine updates its capability constraints, keeping the predictive schedule aligned with shop-floor reality.
