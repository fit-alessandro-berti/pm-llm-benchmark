# Process-Mining Approach to Optimize IT Service Desk Resource Assignment

A successful improvement program should treat resource assignment as an end-to-end operational decision rather than simply a dispatching action. The analysis should connect:

- Ticket attributes at creation: priority, category, channel, reported symptoms, required skill, customer/service.
- Assignment and work events: who received the ticket, who actually worked it, handovers, escalations, reassignments.
- Resource attributes: tier, skill inventory, proficiency, schedule, availability, workload.
- Outcomes: resolution, SLA attainment, elapsed time, effort time, reopen rate, customer impact.

The objective is to determine whether tickets are reaching the right person at the right time, whether L1 is being used appropriately, whether specialist capacity is protected for work requiring it, and which assignment decisions create delay or SLA risk.

---

## 1. Analyzing Resource Behavior and Assignment Patterns

## 1.1 Prepare and enrich the event log

Before mining, the event log should be standardized into a case-event-resource structure.

### Core event fields

| Field | Use |
|---|---|
| Case ID / Ticket ID | Process-mining case identifier |
| Activity | Ticket Created, Assigned, Work Start, Work End, Escalate, Reassign, Resolved, Closed, Reopened |
| Timestamp | Event ordering, waiting times, throughput times |
| Lifecycle transition | Start/complete where available |
| Resource | Agent, dispatcher, system |
| Agent tier | L1, L2, L3 |
| Agent skills / proficiency | Resource capability analysis |
| Ticket priority | SLA and routing analysis |
| Ticket category / subcategory | Demand and skill-demand analysis |
| Required skill | Match/mismatch analysis |
| Channel | Phone, web, email; important for first-call resolution |
| SLA target / SLA status | Breach and risk analysis |
| Assignment queue / team | Queue-delay and routing analysis |
| Resolution code / escalation reason | Outcome and root-cause analysis |

### Derived fields

The raw event data should be enriched with derived measures such as:

- Initial assigned agent and initial assigned tier.
- First working agent and resolving agent.
- Number of assignments and distinct agents per ticket.
- Number of reassignments.
- Number of escalations and maximum tier reached.
- First assignment skill match: whether the agent/team had the required skill.
- Resolution skill match: whether the resolver had the required skill.
- L1 handling time, L2 handling time, and L3 handling time.
- Waiting time before first work starts.
- Waiting time between reassignment and next work start.
- Total active work time versus total elapsed calendar time.
- Queue time by tier and by skill queue.
- Time remaining to SLA at each assignment or escalation point.
- Whether a ticket was resolved by L1, escalated appropriately, escalated unnecessarily, or reassigned due to a skill mismatch.
- Workload at the time of assignment, such as open tickets, active tickets, weighted workload, and queued P1/P2 tickets for the assigned agent/team.

This enriched dataset makes it possible to distinguish a genuine specialist requirement from an inefficient routing decision.

---

## 1.2 Analyze individual-agent and tier performance

The analysis should not be used as a simplistic “agent ranking” exercise. It must control for ticket complexity, priority, required skill, customer impact, time of day, and workload. An L3 specialist handling difficult P1 incidents should not appear less productive merely because their cases take longer.

### Agent-level metrics

For each agent, calculate metrics segmented by priority, category, required skill, and complexity band:

| Metric | What it reveals |
|---|---|
| Number of assigned tickets | Assignment volume |
| Number of actively worked tickets | Actual workload, not merely ownership |
| Number of resolved tickets | Resolution contribution |
| Median/mean active handling time | Efficiency, controlling for ticket type |
| Median/mean queue time before work | Capacity or prioritization problem |
| End-to-end resolution time | Customer-facing performance |
| SLA attainment/breach rate | Outcome quality |
| Reassignment-out rate | Tickets the agent could not continue handling |
| Reassignment-in rate | Dependence on agent as a specialist or “rescue” resource |
| Escalation rate | Ability or authority to resolve at current tier |
| First-contact resolution rate | Especially important for L1 |
| Reopen rate | Resolution quality and possible premature closure |
| Skill-match rate | Correctness of assignment |
| Tickets handled below/above skill level | Potential underuse or inappropriate allocation |
| Weighted workload | Workload adjusted for priority and expected complexity |
| Concurrent active cases | Capacity and overload indication |

### Tier-level metrics

For L1, L2, and L3, analyze:

- Ticket volume entering and leaving each tier.
- Percentage resolved at each tier.
- Escalation rate from L1 to L2 and L2 to L3.
- Backward flows, such as L2 returning work to L1 or tickets bouncing between teams.
- Waiting time before work begins at each tier.
- Active handling time at each tier.
- Reassignment frequency within the tier versus across tiers.
- Skill-match rate by tier.
- SLA breach rate by tier, priority, category, and required skill.
- Percentage of specialist time spent on work that historical data shows can be resolved at L1.
- Queue aging distribution, particularly for P2 and P3 tickets.

### L1 first-call resolution analysis

For phone tickets, first-call resolution (FCR) should be defined precisely, for example:

> A ticket is resolved without escalation, reassignment, or reopening within an agreed observation period, and is closed during or shortly after the initial L1 interaction.

Metrics should include:

- Overall L1 FCR rate.
- FCR by category, priority, channel, and L1 agent.
- FCR by skill requirement.
- FCR by time of day/day of week.
- FCR for agents with specific training or certifications.
- Time-to-escalation for tickets not resolved at L1.
- Cases where L1 spends substantial time before escalating but does not add value.

This helps separate productive L1 troubleshooting from avoidable delay before specialist engagement.

## 1.3 Discover actual assignment, escalation, and handover patterns

The documented process may say:

> Ticket  L1  L2 specialist if needed  L3 only for exceptional complexity.

The event log may reveal a materially different process, for example:

> Ticket  L1  generic L2 queue  L2 reassignment  another L2 specialist  L3  resolution.

Process mining can expose this gap.

### Process discovery

Use process-discovery methods, such as directly-follows graphs, inductive mining, or BPMN/Petri-net discovery, to identify:

- Dominant ticket paths.
- High-frequency variants.
- Loops involving reassignment and escalation.
- Activities that occur late in the process, such as recategorization or skill correction.
- Routes associated with long delays or SLA breaches.

The discovery model should be filtered by:

- Priority: P1/P2/P3/P4.
- Ticket category and required skill.
- Channel.
- Support tier.
- Time period.
- SLA-met versus SLA-breached tickets.
- Number of reassignments.
- Ticket complexity segment.

### Resource interaction and handover analysis

Create resource interaction networks using handover relations. A handover edge can be defined as:

- Agent A completes work and Agent B next starts work on the same ticket.
- Agent A escalates and Agent B/team later starts work.
- Agent A reassigns a ticket and Agent B receives the next assignment.

Network measures can reveal:

- **High-volume handovers:** common resource-to-resource or team-to-team transitions.
- **Bottleneck nodes:** agents or teams through which disproportionate numbers of tickets pass.
- **Centrality:** agents functioning as informal triage or escalation hubs.
- **Ping-pong relationships:** repeated transfers between teams or agents.
- **Silos:** groups with limited interaction, potentially causing delays for cross-domain tickets.
- **Single points of failure:** one specialist receiving a disproportionately large share of a required skill type.

For example, if most `Networking-Firewall` P2 tickets route from L1 to a generic L2 agent and then to a particular firewall specialist, the generic L2 assignment may be an unnecessary intermediate step.

### Role discovery

Role discovery groups resources based on actual behavior rather than organizational labels. It can reveal that:

- Some L1 agents consistently solve tickets that other L1 agents escalate.
- Certain L2 agents are effectively acting as skill-based dispatchers.
- A nominal L2 team contains different informal specialist clusters, such as CRM, SQL, firewall, and identity specialists.
- A small number of resources handle most tickets in a technical domain despite a larger official skill pool.

This is important because the formal tier structure may not represent the real operating model.

## 1.4 Analyze skill utilization and skill-to-ticket matching

Skill utilization should be examined at three levels:

1. **Demand:** What skills are required by incoming work?
2. **Supply:** Which agents possess each skill, at what tier and proficiency?
3. **Deployment:** Are tickets actually routed to agents with those skills in a timely way?

### Skill-match measures

For every assignment, calculate:

- Exact required-skill match.
- Related-skill match, such as general networking versus firewall specialization.
- No documented match.
- Overqualification indicator, such as an L3 database expert assigned to a basic access-reset ticket.
- Skill mismatch followed by reassignment.
- Skill mismatch followed by escalation.
- Skill match but long queue time, indicating capacity rather than routing failure.

### Skill utilization matrix

Build a matrix such as:

| Required skill | Demand volume | Available skilled agents | Tickets initially matched | Tickets reassigned for skill | Median queue time | SLA breach rate |
|---|---:|---:|---:|---:|---:|---:|
| Networking-Firewall |  |  |  |  |  |  |
| Database-SQL |  |  |  |  |  |  |
| OS-WindowsServer |  |  |  |  |  |  |
| App-CRM |  |  |  |  |  |  |
| Security-IAM |  |  |  |  |  |  |

This identifies whether a problem is caused by a lack of skill capacity, poor routing, poor ticket classification, or inaccurate skill records.

### Specialist underutilization or misuse

Specialist allocation should be measured by comparing the specialist’s assigned work with the minimum skill and tier historically needed for that type of ticket.

Indicators include:

- Percentage of L2/L3 tickets that could historically have been resolved by L1.
- Percentage of L3 tickets resolved without advanced-tier activities.
- Frequency of specialists handling basic password resets, standard software installs, low-complexity requests, or known-error incidents.
- Percentage of specialist capacity consumed by low-priority/P4 tickets while P2/P3 skill-matched tickets wait.
- Specialist utilization by active effort time, not simply assigned ticket count.
- Number and duration of interruptions caused by reassigned or misrouted work.

The target is not necessarily maximum specialist utilization. Specialist capacity needs deliberate buffering for critical work and escalation demand.

# 2. Identifying Resource-Related Bottlenecks and Issues

## 2.1 Identify skill-capacity bottlenecks

A skill bottleneck exists when tickets requiring a skill consistently wait longer than comparable tickets, even when their initial assignment is correct.

For example, `Networking-Firewall` may show:

- High queue time after assignment to L2.
- Long time from `Assign L2` to `Work L2 Start`.
- High SLA breach rate for P2 network incidents.
- Concentration of work on one or two firewall-skilled agents.
- Peaks in demand that exceed available capacity.
- Frequent reassignment from generic L2 agents to the firewall specialists.

Useful measures include:

- Demand volume by skill and hour/day.
- Available capacity by skill and hour/day.
- Queue aging by skill.
- Utilization of agents with the skill.
- Median and 90th-percentile time from assignment to work start.
- SLA breach rate by skill.
- Ticket arrival rate versus resolution rate by skill queue.

A bottleneck should be differentiated from poor routing. If the skill-matched agent receives tickets immediately but cannot begin work due to overload, the issue is capacity. If the first assignment is usually to someone lacking the skill, the issue is assignment logic.

---

## 2.2 Measure reassignment and escalation delay

Reassignments should be treated as measurable process events with both direct and indirect costs.

### Key reassignment measures

- Reassignments per ticket.
- Percentage of tickets with at least one reassignment.
- Percentage with two or more reassignments.
- Reassignments by priority, category, required skill, tier, team, agent, and channel.
- Reassignment reasons from notes or structured fields.
- Reassignment destination patterns.
- Time from reassignment to next assignment.
- Time from reassignment to next work start.
- Active work performed before reassignment.
- SLA risk at reassignment.
- Resolution outcomes following reassignment.

### Quantifying reassignment cost

For each reassignment, calculate:

\[
\text{Reassignment Delay} =
\text{Timestamp of next work start} -
\text{Timestamp of reassignment}
\]

Then compare tickets with similar priority, category, skill, and complexity:

- Tickets resolved with no reassignment.
- Tickets with one reassignment.
- Tickets with two or more reassignments.

A practical analysis might report:

- Median additional elapsed time per reassignment.
- Additional queue time introduced by reassignment.
- Incremental SLA breach probability after each reassignment.
- Proportion of reassignments caused by skill mismatch.
- Percentage of P2/P3 breaches involving at least one reassignment.
- Difference in handling time before and after the reassignment.

A survival or hazard analysis can also quantify how ticket aging and reassignment count increase breach risk.

---

## 2.3 Detect incorrect initial assignments

An initial assignment is likely incorrect when:

- The assigned agent lacks the required skill.
- The ticket is reassigned shortly after assignment without substantive work.
- The ticket is recategorized or has its required skill changed soon after assignment.
- The agent escalates immediately because the task is outside the tier or skill scope.
- Similar tickets historically resolve faster when routed to another team or skill group.

Relevant measures:

- Initial skill-match rate.
- Initial tier appropriateness rate.
- Early reassignment rate, e.g., within 15 or 30 minutes.
- Assignment-to-first-work delay.
- Percentage of tickets initially assigned to generic queues before reaching the eventual resolver.
- Accuracy of category and required-skill fields at ticket creation.
- Difference between original and final category/skill.

For the sample, INC-1001 appears to be initially routed to an L2 CRM-skilled agent and later reassigned because database/SQL capability became necessary. This could indicate one of several problems:

- The initial required skill was incomplete.
- The ticket classification did not identify database involvement.
- The assignment engine only used primary category (`Software-App`) rather than the full skill requirement.
- The skill profile of Agent B12 was incomplete or did not reflect proficiency.
- A combined CRM-plus-SQL skill requirement was not supported by routing logic.

## 2.4 Identify overloaded, underutilized, and unevenly used resources

Workload should be assessed using time-sensitive measures rather than end-of-day totals.

### Overload indicators

- High number of concurrent active tickets.
- High queue length assigned to an agent/team.
- Long assignment-to-work-start delay.
- High percentage of overdue tickets in the resource’s queue.
- High utilization combined with growing backlog.
- Frequent interruption and reassignment activity.
- Higher-than-peer SLA breach rate after controlling for case mix.
- High inbound handover volume.
- Consistent after-hours or overtime activity.

### Underutilization indicators

- Low active workload during periods where other comparable agents are overloaded.
- Low assignment volume despite relevant skills.
- Unused skill capacity during high demand.
- Low share of tickets in the agent’s documented specialty.
- Long waits in one queue while capable agents work unrelated low-priority cases.

A workload fairness analysis should compare agents with comparable skills and shifts. The goal is not identical volume, but balanced weighted workload and appropriate use of capability.

---

## 2.5 Link assignment patterns to SLA breaches

A breached-versus-met comparison is one of the highest-value analyses.

For each priority, especially P2 and P3, compare:

| Factor | SLA Met | SLA Breached |
|---|---:|---:|
| Median number of reassignments |  |  |
| Initial skill-match rate |  |  |
| Time to first assignment |  |  |
| Time to first work start |  |  |
| Time spent in L1 |  |  |
| Time spent in L2 queue |  |  |
| Number of escalations |  |  |
| Distinct agents involved |  |  |
| Percentage assigned to overloaded agent |  |  |
| Category/skill correction rate |  |  |

Statistical models can estimate the contribution of each factor to breach probability. For example, a logistic regression, survival model, or machine-learning classification model can estimate the incremental risk associated with:

- Initial skill mismatch.
- More than one reassignment.
- Transfer to L2 after a long L1 attempt.
- Assignment during peak demand.
- Assignment to an overloaded resource.
- Specific skill queues.
- Certain ticket categories or channels.

The results should be expressed operationally, for example:

> P2 tickets with an initial skill mismatch and at least one reassignment have a materially higher probability of SLA breach than comparable correctly matched tickets.

This supports prioritizing routing improvements based on business impact rather than anecdote.

# 3. Root Cause Analysis for Assignment Inefficiencies

## 3.1 Likely root causes to test

The process-mining findings should be validated against potential causes rather than assuming that every long ticket reflects poor agent performance.

### A. Round-robin assignment ignores skills and workload

A round-robin method can distribute ticket counts evenly while distributing complexity and capability poorly. It can cause:

- Tickets sent to agents without the required skill.
- Overloading of certain agents because they receive difficult cases after reassignments.
- Delayed specialist involvement.
- Reassignment loops.
- Poor P2/P3 prioritization.

Evidence would include low initial skill-match rates, high early reassignment rates, and a weak relationship between assignment and skill availability.

### B. Skill profiles are inaccurate, incomplete, or too coarse

An agent may be listed as “Database” but not be proficient in SQL Server, Oracle, performance tuning, or application-level database integration. Similarly, a generic “Network” skill may not indicate firewall expertise.

Evidence includes:

- Repeated reassignment from formally skill-matched agents.
- Large performance differences among agents listed with the same skill.
- Assignment patterns based on informal knowledge rather than system profiles.
- A small subset of “go-to” specialists receiving cases despite a broader official skill pool.

### C. Ticket categorization and skill requirement identification are weak

If ticket creation captures only broad categories, such as “Software-App,” the true requirement may only become clear after L1 or L2 diagnosis.

Evidence includes:

- High rate of category changes or required-skill changes.
- Reassignment shortly after ticket review.
- High mismatch rates for tickets from a particular channel, customer group, or intake form.
- Frequent notes such as “wrong queue,” “incorrect category,” or “requires different skill.”

### D. Lack of real-time workload and availability information

Even correct skill routing can fail when the assignment engine does not consider active workload, shift schedules, planned absence, current queue age, or high-priority work already assigned.

Evidence includes:

- Tickets assigned to agents who are not working or are overloaded.
- Other qualified agents remaining underutilized.
- Large variation in waiting time among agents with the same skill.
- P2/P3 tickets waiting behind lower-priority work.

### E. Insufficient L1 training, knowledge, or authority

L1 may escalate tickets that can be resolved through knowledge articles, automation, standard procedures, or access rights.

Evidence includes:

- Large variation in FCR among L1 agents for comparable ticket types.
- Certain categories routinely escalated by some L1 agents but resolved by others.
- High L1-to-L2 escalation rates for repetitive issues.
- Specialist resolution using simple, repeatable actions.
- Long L1 work periods followed by escalation with no clear diagnostic progress.

### F. Escalation rules do not distinguish urgency, complexity, and skill need

A P2 ticket may need immediate skill-based escalation, while a P3 may be appropriate for structured L1 triage. Uniform escalation rules can create both over-escalation and under-escalation.

---

## 3.2 Variant analysis

Variant analysis compares process paths and outcomes.

### Smooth-assignment variants

Identify cases with:

- Correct initial assignment.
- No reassignment.
- Resolution at expected tier.
- Short queue time.
- SLA met.
- Low number of handovers.

### Problem variants

Identify cases with:

- Multiple reassignments.
- Repeated category changes.
- L1  L2  L2  L3 paths.
- Long waits after assignment.
- SLA breach.
- Late escalation.
- Many distinct agents.

Then compare the variants by:

- Priority.
- Category and required skill.
- Channel.
- Intake form completeness.
- Initial assignment team.
- Agent skill match.
- Assigned workload.
- Day/time and staffing level.
- Customer/service/application.
- Notes/reasons for escalation.

This identifies conditions associated with poor routing. For example, a particular category may produce a high-volume path from L1 to generic L2 to database specialists, suggesting that the routing taxonomy should be changed.

---

## 3.3 Decision mining and predictive explanation

Decision mining examines the choices made at gateways or decision points, such as:

- Assign to L1 versus direct specialist routing.
- Escalate versus continue troubleshooting.
- Assign to Agent B12 versus B15.
- Reassign versus retain ownership.
- Route to L2 versus L3.

Decision rules can be inferred from historical cases using decision trees, rule extraction, logistic models, or explainable machine learning.

Potential input variables include:

- Priority.
- Category/subcategory.
- Required skill.
- Ticket description keywords.
- Channel.
- Customer/service.
- L1 diagnosis code.
- Agent workload.
- Agent availability.
- Shift/time of day.
- Historical resolution outcomes for similar cases.
- Skill proficiency.
- SLA time remaining.

The goal is to distinguish historical decisions that worked from those that caused delay. For instance:

> For P2 network tickets containing firewall-related keywords, direct assignment to firewall-skilled L2 agents historically produces lower total resolution time and fewer reassignments than general L2 routing.

Decision mining should guide policy design, but recommendations must remain explainable, auditable, and overrideable by supervisors.

# 4. Data-Driven Resource Assignment Strategies

The following strategies can be introduced independently, but they are most effective as a coordinated routing and workforce-management model.

## Strategy 1: Skill-Based Routing With Proficiency and Tier Eligibility

### Assignment issue addressed

Current round-robin or broad team-based assignment may send tickets to agents who do not have the needed skill, causing reassignments, delays, and unnecessary escalations.

### Proposed approach

Implement a routing engine that matches ticket requirements to agent skills, proficiency, and tier eligibility.

Each ticket should have:

- Primary required skill.
- Optional secondary skill.
- Complexity level.
- Minimum tier.
- Priority and SLA urgency.
- Service/application context.

Each agent should have:

- Verified skills.
- Proficiency level, such as basic/intermediate/advanced.
- Certification or authorization constraints.
- Tier.
- Current assignment eligibility.
- Shift and availability.
- Historical success for the skill/category.

A routing score can combine factors such as:

\[
\text{Routing Score} =
w_1(\text{Skill Match}) +
w_2(\text{Proficiency}) +
w_3(\text{Tier Fit}) +
w_4(\text{Historical Success}) -
w_5(\text{Current Workload}) -
w_6(\text{SLA Risk})
\]

For high-priority tickets, exact skill match and availability should carry greater weight than equal distribution of work.

### Process-mining insight leveraged

- Skill mismatch rates.
- Reassignment patterns by skill.
- Actual resolver profiles.
- Informal role clusters.
- Historical performance of agent-skill-ticket combinations.
- Skills associated with queue delay and SLA breach.

### Required data

- Validated skill inventory.
- Skill proficiency and recency.
- Ticket category/subcategory and required skill.
- Agent tier and authorization data.
- Resolution and reassignment history.
- Agent schedules and availability.
- SLA policy.

### Expected benefits

- Higher initial skill-match rate.
- Fewer reassignments.
- Faster start of specialist work.
- Lower P2/P3 SLA breach rate.
- Better use of specialists.
- Improved transparency in routing decisions.

---

## Strategy 2: Workload-Aware, SLA-Aware Assignment

### Assignment issue addressed

A skill-matched agent may still be a poor assignment if they are overloaded, unavailable, or managing several urgent incidents. Static round-robin does not account for real-time capacity.

### Proposed approach

Assign tickets to the best qualified agent with sufficient capacity, considering both current workload and SLA urgency.

Rather than using raw ticket count, calculate a weighted workload:

\[
\text{Weighted Workload} =
\sum (\text{Priority Weight} \times \text{Complexity Weight} \times \text{Expected Remaining Effort})
\]

Possible inputs include:

- Number of active tickets.
- Number of assigned but unstarted tickets.
- Current queue age.
- P1/P2 workload.
- Estimated effort of each open ticket.
- Time remaining to SLA.
- Shift status, absence, and calendar availability.
- Current utilization and interruption rate.

The logic should also include priority protection. A P2 firewall incident should not be placed behind low-priority routine work, even if the assigned agent has a smaller ticket count.

### Process-mining insight leveraged

- Agent-level queue time.
- Concurrent work patterns.
- Uneven workload distribution.
- SLA breaches linked to waiting time after assignment.
- Capacity patterns by shift, day, and skill.
- Resource utilization and queue-aging trends.

### Required data

- Real-time queue and ticket state.
- Agent availability and schedule.
- Active workload.
- Ticket priority, complexity, and SLA deadlines.
- Historical effort-time estimates.
- Skill eligibility.

### Expected benefits

- Reduced assignment-to-work-start time.
- Better balancing of workload among qualified agents.
- Fewer cases assigned to unavailable or overloaded agents.
- Improved SLA compliance, especially for P2 and aging P3 tickets.
- Reduced burnout and more predictable staffing needs.

---

## Strategy 3: Predictive Ticket Classification and Assignment Recommendation

### Assignment issue addressed

Incorrect categorization and incomplete identification of required skills cause poor first assignment and downstream rework.

### Proposed approach

Use historical ticket data to predict:

- Likely category and subcategory.
- Required primary and secondary skills.
- Expected complexity.
- Probability of L1 resolution.
- Likely resolver tier.
- Expected resolution time.
- Probability of escalation or SLA breach.

Models can use structured fields and text features from:

- Ticket title and description.
- Caller/customer/service details.
- Error codes.
- Attached logs.
- Knowledge article references.
- Channel.
- Historical incident patterns.

The model should not fully replace human judgment initially. It should provide a recommendation, confidence score, and explanation, such as:

> “High likelihood of Networking-Firewall requirement based on keywords, affected service, and similar resolved incidents. Recommended direct routing to Firewall L2 queue.”

Low-confidence cases should go to a triage process rather than be routed automatically.

### Process-mining insight leveraged

- Differences between initial and final classifications.
- Actual skills used by the final resolver.
- High-frequency misrouting variants.
- Historical outcomes for similar tickets.
- L1 resolution probability by ticket features.

### Required data

- Historical ticket descriptions and notes, subject to privacy controls.
- Category/subcategory labels.
- Required and final skills.
- Resolution codes.
- Escalation/reassignment events.
- Agent and team routing history.
- Quality-controlled labels.

### Expected benefits

- Better initial classification.
- Improved first assignment accuracy.
- Less manual dispatcher effort.
- Reduced reassignments due to misclassification.
- Faster routing for P2/P3 tickets.
- More consistent service across channels and shifts.

---

## Strategy 4: Data-Driven L1 Triage and Escalation Rules

### Assignment issue addressed

L1 agents may either escalate tickets too early or spend too long on tickets that clearly require specialist intervention. Both behaviors create delay and inefficient use of higher tiers.

### Proposed approach

Develop category- and skill-specific escalation guidance based on historical outcomes.

Examples:

- Identify ticket types with high L1 FCR and provide L1 with knowledge articles, scripts, automation, and authority to resolve them.
- Identify ticket types where L1 resolution is historically rare and early escalation improves SLA performance.
- Set evidence-based escalation triggers, such as:
  - Escalate immediately for certain P2 security or firewall indicators.
  - Escalate after a defined diagnostic checklist is completed.
  - Escalate if no progress occurs within a category-specific threshold.
  - Route directly to the appropriate L2 skill queue if confidence is high.

This should be paired with knowledge management and targeted training, not merely stricter escalation controls.

### Process-mining insight leveraged

- L1 FCR by ticket type and agent.
- Time spent at L1 before escalation.
- Resolution actions performed at L2/L3.
- Categories where L1 involvement adds value versus delay.
- L1-to-L2 variants associated with SLA breaches.

### Required data

- L1 handling activities and outcomes.
- Escalation reasons.
- Knowledge article usage.
- Ticket category and skill requirement.
- Resolution actions and codes.
- Agent training/certification data.
- SLA outcomes.

### Expected benefits

- Higher L1 FCR where appropriate.
- Faster escalation where L1 resolution is unlikely.
- Reduced specialist workload for routine cases.
- Lower elapsed resolution time.
- More consistent escalation decisions.
- Improved L1 capability development.

---

## Strategy 5: Dynamic Skill-Capacity Management and Cross-Training

### Assignment issue addressed

Some skills may be concentrated in a small number of specialists, creating predictable bottlenecks, while other capable agents are underutilized.

### Proposed approach

Use demand and capacity forecasts derived from the event log to dynamically manage resources.

Actions may include:

- Forecast demand by skill, priority, day, and hour.
- Create dedicated skill queues for recurring bottleneck domains.
- Temporarily move cross-trained agents between L1/L2 functions during demand peaks.
- Reserve advanced specialist capacity for P1/P2 and complex cases.
- Train selected agents in recurring high-demand skills.
- Establish backup coverage for single-expert skills.
- Schedule shifts to align with observed arrival peaks.
- Use “swarming” for critical incidents, but measure whether it reduces or increases elapsed time.

### Process-mining insight leveraged

- Demand patterns by skill and time.
- Queue growth and wait time by skill.
- Specialist concentration and single points of failure.
- Underutilized adjacent skills.
- Seasonal and day-of-week trends.
- Impact of staffing levels on SLA outcomes.

### Required data

- Historical arrivals by skill, category, and priority.
- Agent schedules and capacity.
- Skill matrices and cross-training eligibility.
- Planned absences.
- Resolution effort and queue times.
- Forecasting inputs such as release calendars and business events.

### Expected benefits

- Reduced skill-specific queues.
- Fewer SLA breaches caused by specialist scarcity.
- Greater resiliency to absence and demand spikes.
- More balanced workload.
- Reduced dependence on individual “hero” specialists.
- Better long-term workforce planning.

# 5. Simulation, Implementation, and Monitoring

## 5.1 Use process simulation before implementation

Business process simulation should be used to test assignment policies before changing production routing.

A simulation model should be based on the mined process model and include:

- Ticket arrival patterns by time, priority, category, and channel.
- Routing probabilities and observed process variants.
- Service-time distributions by ticket type, tier, skill, and complexity.
- Agent shifts, availability, and capacity.
- Skill matrices and proficiency levels.
- Queue disciplines and SLA rules.
- Escalation and reassignment probabilities.
- Historical rework and reopening behavior.

### Scenarios to simulate

At minimum, compare:

1. **Current-state baseline**
   - Existing round-robin and manual escalation behavior.

2. **Skill-based routing**
   - Match tickets directly to eligible skill groups.

3. **Skill plus workload-aware routing**
   - Match by skill, then choose the least loaded suitable agent.

4. **Predictive triage**
   - Use classification confidence to route direct-to-skill or to L1 triage.

5. **Enhanced L1 resolution**
   - Model higher FCR for selected categories after training/automation.

6. **Cross-training or additional skill capacity**
   - Test the impact of adding one or more qualified agents to bottleneck skills.

### Simulation outputs

Evaluate each scenario using:

- SLA attainment by P1/P2/P3/P4.
- End-to-end resolution time.
- Queue time by skill and tier.
- Number of reassignments per case.
- Escalation volume by tier.
- L1 FCR.
- Specialist utilization.
- Resource workload distribution.
- Backlog size and queue aging.
- Cost and staffing implications.
- Risk of starving lower-priority tickets.

The simulation should use multiple replications and confidence intervals because incident demand and resolution times vary. It should also test stress scenarios, such as a firewall incident spike, specialist absence, or release-related application incident surge.

## 5.2 Phased implementation plan

### Phase 1: Data foundation and baseline

- Validate event-log completeness and timestamp quality.
- Standardize activity names and lifecycle semantics.
- Reconcile resource IDs, tiers, skills, teams, and schedules.
- Define SLA rules consistently.
- Build baseline dashboards for current assignment performance.
- Validate findings with service desk managers, dispatchers, L1, L2, L3, and workforce planners.

### Phase 2: Pilot a limited routing improvement

Start with a high-volume, measurable scope, such as:

- P2/P3 network tickets.
- CRM and database-related incidents.
- Access-management tickets.
- One support region or shift.

Run the new routing logic in recommendation mode first, comparing recommended versus actual assignment. Then move to controlled automation for high-confidence cases.

### Phase 3: Controlled rollout

- Roll out skill-based and workload-aware routing incrementally.
- Retain manual override capability.
- Capture override reasons to improve routing logic.
- Update knowledge articles and escalation policies.
- Train agents and dispatchers on new procedures.
- Monitor for unintended effects, such as overloading a newly identified specialist group.

### Phase 4: Continuous optimization

- Recalibrate skills and proficiency records.
- Retrain predictive models with recent outcomes.
- Adjust routing weights based on SLA, workload, and quality results.
- Use process mining to identify new variants or emerging bottlenecks.

## 5.3 Post-implementation process-mining dashboards

Dashboards should support executives, service-desk managers, dispatchers, and team leads. They should allow drill-down from aggregate SLA performance to a specific skill, queue, process variant, or resource group.

### Core resource-assignment KPIs

| KPI | Purpose |
|---|---|
| Initial skill-match rate | Measures assignment accuracy |
| Initial tier-appropriateness rate | Identifies avoidable escalation or specialist misuse |
| Assignment-to-work-start time | Detects availability and queue-delay issues |
| Median and 90th-percentile resolution time | Measures customer-facing performance |
| SLA attainment by priority | Main service outcome, especially P2/P3 |
| SLA breach rate by skill/category/tier | Identifies high-risk operational areas |
| Reassignments per ticket | Measures routing quality |
| Early reassignment rate | Detects bad first assignments |
| Escalation rate by category and skill | Identifies L1/L2 capability and rule issues |
| L1 first-call resolution rate | Measures L1 effectiveness |
| Queue age by skill and priority | Detects emerging bottlenecks |
| Skill-specific backlog | Measures demand-capacity imbalance |
| Specialist utilization and low-complexity workload | Ensures specialist capacity is used appropriately |
| Workload balance among qualified agents | Detects overload and underutilization |
| Reopen rate | Protects quality while optimizing speed |
| Routing recommendation acceptance/override rate | Evaluates trust and quality of new routing logic |

### Essential process views

1. **SLA breach journey view**  
   Process map filtered to breached P2/P3 tickets, showing where waiting and reassignments occur.

2. **Assignment quality funnel**  
   Ticket Created  Categorized  Skill Identified  Correctly Assigned  Work Started  Resolved.

3. **Skill demand versus capacity heatmap**  
   Required-skill arrivals, available skilled capacity, queue age, and SLA risk by hour/day.

4. **Handover network**  
   Agent/team handovers with high-frequency, high-delay, or high-breach edges highlighted.

5. **Reassignment root-cause dashboard**  
   Reassignment reasons, source/destination teams, time lost, affected skills, and associated SLA outcomes.

6. **L1 effectiveness dashboard**  
   FCR, escalation timing, handling time, and category-level performance, adjusted for ticket mix.

7. **Specialist utilization dashboard**  
   L2/L3 effort split by complexity, priority, category, and work suitable for lower tiers.

8. **Conformance dashboard**  
   Compares actual routing behavior with the intended assignment rules. Exceptions should be categorized as justified overrides, data-quality problems, or process non-compliance.

## Expected Target State

The desired outcome is an assignment process in which:

- Tickets are classified accurately at intake.
- The required skill and minimum appropriate tier are identified early.
- Tickets are routed to available, qualified agents rather than distributed blindly.
- L1 resolves standardized issues efficiently and escalates complex issues quickly with sufficient diagnostic context.
- L2/L3 specialists spend most of their time on genuinely specialized work.
- Reassignments become exceptions with visible, actionable reasons.
- Staffing and cross-training decisions are based on observed demand by skill and time.
- SLA risk is managed proactively, not analyzed only after breaches occur.

Process mining provides the evidence base for this transformation: it reveals actual routing behavior, quantifies the cost of poor assignments, identifies skill and capacity bottlenecks, tests alternative routing rules through simulation, and continuously monitors whether the redesigned assignment logic produces the expected operational improvements.
