## Process overview

The process receives a customer request, classifies it as **standard** or **custom**, performs the corresponding validation or feasibility work, and then determines whether managerial approval is required. Successful requests proceed to invoicing and customer confirmation. Infeasible custom requests are rejected immediately, while requests denied during approval are reworked and resubmitted.

## Step-by-step explanation

### 1. Receive and classify the request

- **Start Event**  
  Marks the creation of a new process instance.

- **Task A — Receive Customer Request**  
  The organization captures the request and the information needed to evaluate it, such as request type, products, quantities, delivery requirements, and customization details.

- **XOR Gateway — Check Request Type**  
  An exclusive gateway selects exactly one path:
  - **Standard request**, or
  - **Custom request**.

  The two paths are alternatives; they are not performed simultaneously.

---

## 2. Standard-request path

### Task B1 — Perform Standard Validation

The request is checked against predefined rules, such as:

- Completeness of customer and order data
- Product and quantity validity
- Standard commercial terms
- Customer eligibility
- Compliance with ordinary service or order policies

Because this is a standard request, it can generally be evaluated through established procedures.

### AND Gateway — Run Parallel Checks

An AND gateway starts both of the following activities concurrently:

- **Task C1 — Credit Check**  
  Verifies that the customer is creditworthy or within an approved credit limit.

- **Task C2 — Inventory Check**  
  Determines whether the requested products or resources are available.

Unlike an XOR gateway, the AND gateway does not choose one branch. It activates **all** outgoing branches.

### AND Join — All Parallel Checks Completed

The matching parallel join waits until both the credit check and inventory check have completed. The process cannot proceed merely because one check has finished.

### Task D — Calculate Delivery Date

Using inventory availability, capacity, lead time, transportation constraints, and other scheduling information, the organization calculates a delivery date for the standard request.

Task D is the standard path’s point of readiness for the later approval and invoicing stages.

---

## 3. Custom-request path

### Task B2 — Perform Custom Feasibility Analysis

A custom request requires case-specific evaluation. This may include:

- Technical feasibility
- Production or service capacity
- Cost and lead-time estimation
- Resource or supplier availability
- Regulatory constraints
- Compatibility with existing products or processes

This is more extensive than standard validation because the request falls outside predefined offerings or conditions.

### XOR Gateway — Is Customization Feasible?

The feasibility result determines one of two mutually exclusive paths.

#### If feasible: Task E1 — Prepare Custom Quotation

The organization prepares a quotation reflecting the custom scope, expected price, delivery terms, assumptions, and other special conditions. This becomes the custom path’s basis for approval and invoicing.

#### If not feasible: Task E2 — Send Rejection Notice

The customer is informed that the requested customization cannot be fulfilled, potentially with reasons or alternatives.

This path then reaches an **End Event**, meaning the rejected request does not proceed to approval, invoicing, or confirmation.

---

## 4. Convergence of the standard and custom paths

The successful paths converge after:

- **Task D — Calculate Delivery Date** for a standard request, or
- **Task E1 — Prepare Custom Quotation** for a feasible custom request.

Conceptually, this is an **alternative-path merge**: only the branch selected at the request-type gateway arrives here. In formal BPMN, an explicit XOR merge could be shown before the approval decision to make the convergence unambiguous.

The infeasible-customization path does not converge here because it has already ended after the rejection notice.

---

## 5. Approval decision

### XOR Gateway — Is Approval Needed?

This gateway evaluates business rules to determine whether managerial approval is required. Possible approval triggers could include:

- High order value
- Nonstandard pricing or discounts
- Unusual payment terms
- Credit exposure
- Low margins
- Delivery commitments outside normal limits
- Custom technical or contractual risk
- Exceptions to company policy

The pseudo-model does not define the exact rule, so it should be supplied as a gateway condition or decision table.

#### If no approval is needed

The request proceeds directly to:

- **Task G — Generate Final Invoice**

#### If approval is needed

The process continues to:

- **Task F — Obtain Manager Approval**

The manager reviews the relevant delivery, pricing, feasibility, risk, and commercial information.

---

## 6. Approval outcome and rework

### XOR Gateway — Is Approval Granted?

This gateway selects one of two outcomes.

#### If approval is granted

The process proceeds to:

- **Task G — Generate Final Invoice**

#### If approval is not granted

The process moves to:

- **Task H — Re-evaluate Conditions**

This task represents rework rather than immediate termination. The organization examines why approval was denied and revises the proposal. Possible changes include:

- Adjusting the price or discount
- Changing payment terms
- Revising the delivery date
- Reducing scope or quantities
- Changing technical requirements
- Resolving capacity, credit, or inventory concerns

After re-evaluation, the process loops back according to the original request type:

- **Custom request:** return to **Task E1 — Prepare Custom Quotation**
- **Standard request:** return to **Task D — Calculate Delivery Date**

This allows the revised commercial or delivery conditions to be prepared again.

The loop should then flow back into the approval-needed decision, either explicitly or through the same convergence point. This is important because:

- Approval may still be required after revision.
- A revised request may satisfy the conditions without further approval.
- If approval is again required and denied, another rework cycle may occur.

To avoid an endless loop, a real implementation should define limits or escalation rules, such as a maximum number of revisions or termination when acceptable conditions cannot be reached.

---

## 7. Completion

### Task G — Generate Final Invoice

Once approval is either unnecessary or granted, the organization generates the final invoice based on the validated standard request or accepted custom quotation.

In some organizations this artifact might be an order confirmation, pro forma invoice, or final quotation rather than a final invoice if billing occurs only after delivery. The task name should match the organization’s actual accounting policy.

### Task I — Send Confirmation to Customer

The customer receives confirmation of the accepted request, potentially including:

- Final price
- Invoice or payment information
- Confirmed scope
- Delivery date
- Custom terms
- Order or reference number

### End Event

The successful process instance ends after confirmation is sent.

## Gateway summary

| Gateway | Type | Meaning |
|---|---|---|
| Check Request Type | XOR split | Selects either the standard or custom path |
| Run Parallel Checks | AND split | Starts credit and inventory checks simultaneously |
| All Parallel Checks Completed | AND join | Waits for both parallel checks |
| Is Customization Feasible? | XOR split | Selects quotation or rejection |
| Standard/custom convergence | Conceptual XOR merge | Reunites successful alternative paths |
| Is Approval Needed? | XOR split | Selects approval or direct invoicing |
| Is Approval Granted? | XOR split | Selects invoicing or rework |

## Main differences between standard and custom requests

| Standard request | Custom request |
|---|---|
| Uses predefined validation rules | Requires case-specific feasibility analysis |
| Includes parallel credit and inventory checks | Includes an explicit feasibility decision |
| Produces a calculated delivery date | Produces a custom quotation |
| Continues if normal checks are completed | Ends immediately if customization is infeasible |
| Rework returns to delivery-date calculation | Rework returns to quotation preparation |

## Modeling clarifications

For a formal BPMN diagram, the following points should be made explicit:

1. Add an **XOR merge** before “Is Approval Needed?” to show the successful standard and custom paths converging.
2. Preserve the request type as process data so Task H can route rework to Task D or E1.
3. Connect the reworked result back to the approval decision, not directly to invoicing.
4. Define the business rules that determine whether approval is needed.
5. Define what happens if credit or inventory checks fail; the current representation only says they complete.
6. Define loop limits, escalation, or cancellation conditions for repeated approval rejection.
7. Confirm whether “Generate Final Invoice” is truly invoicing or whether “Generate Order Confirmation/Pro Forma Invoice” would be more accurate before fulfillment.
