## Section 0. Prerequisite: Log Preparation and Derived Attributes

Everything below depends on turning the raw log into a *resource-analysis-ready* event log. The snippet already reveals several issues that must be handled first.

**Data quality fixes**

| Issue visible in snippet | Treatment |
|---|---|
| Events not stored in timestamp order (INC-1002 `Work L1 Start` 09:18 appears after 09:36 events) | Sort by (Case, Timestamp); never trust file order. Check for identical timestamps and lifecycle inversions (`END` before `START`). |
| Lifecycle mix (`START` / `COMPLETE`) | Pair START–COMPLETE into activity *instances*  gives true **processing time**; gaps between instances give **waiting time**. Activities with only COMPLETE (Assign, Escalate) are treated as instantaneous transitions. |
| Pseudo-resources `System`, `Dispatcher` | Keep them, but flag as non-human. They must be excluded from workload/utilization metrics but *included* in handover networks (the Dispatcher is a routing hub whose decision quality is exactly what we are auditing). |
| Skill field blanked on `Escalate` events | Impute agent skills from an agent master table (resource dimension), not from the event. |
| `Required Skill` changes mid-case (INC-1001: `App-CRM`  `Database-SQL`) | Store as an *event-level* attribute with versioning; the change itself is a signal (mis-triage) and becomes a feature. |
| Channel buried in free-text `Notes` | Parse into a first-class case attribute. |
| Missing agent calendars, shifts, absence, part-time factors | Import from WFM/HR; utilization without calendars is meaningless. |

**Derived case-level attributes (the analytical backbone)**

- `n_reassignments`, `n_escalations`, `n_de-escalations` (L2L1 returns), `n_distinct_resources`, `tier_path` (e.g. `L1L2L2L3`)
- `first_time_right` = 1 if the first agent who executed `Work *` also executed the resolving activity
- `skill_match_at_assignment`  {exact, partial (skill family), none} — computed by joining `Required Skill` to the assignee's skill profile *as of that date* (skill profiles are slowly-changing dimensions)
- `queue_time_k` = t(`Work k Start`)  t(`Assign k`), and `dispatch_time_k` = t(`Assign k`)  t(`Escalate k`)
- `SLA_target`, `SLA_clock` (business-calendar-adjusted, pause during "Waiting for Customer"), `SLA_slack_at_assignment`
- `WIP_at_assignment(agent)` = number of tickets open and assigned to that agent at the assignment timestamp (reconstructed by replaying the log chronologically) — this is the single most valuable derived variable for diagnosing workload-blind routing.
- `system_load_at_arrival` per skill/tier (queue length at arrival) — needed to separate "bad routing" from "insufficient capacity".

## Section 1. Analyzing Resource Behaviour and Assignment Patterns

### 1.1 Agent- and tier-level performance metrics

I would build a **Resource Profile Cube** (agent × tier × skill × category × priority × time-bucket) with the following metric families. Averages alone are useless for ITSM (heavy right tails), so every duration metric is reported as median / P90 / distribution.

**A. Volume & workload distribution**
| Metric | Definition | Diagnostic use |
|---|---|---|
| Ticket volume per agent | Distinct cases touched / period | Round-robin should produce near-uniform counts *within* a tier — a uniform count with non-uniform *effort* is the classic round-robin failure signature |
| Weighted workload |  (expected handling time per ticket, by category×priority) | Reveals that "equal tickets"  "equal work" |
| Active processing hours |  (COMPLETE  START) per agent | Real effort |
| **Utilization** | Active hours ÷ rostered available hours (calendar-aware) | Target band 65–80%; >85% sustained is a queueing time-bomb (M/M/1 waiting explodes non-linearly) |
| Concurrent WIP profile | Time series of simultaneously open assigned tickets | Multitasking degrades throughput; correlate WIP with per-ticket handling time |
| Gini coefficient of workload per tier | Inequality index | Single number for "uneven distribution" claim; track monthly |

**B. Speed & quality**
| Metric | Notes |
|---|---|
| Processing time per activity per agent, normalized by ticket mix | Raw comparison is unfair — an agent handling only P1 Security looks "slow". Use **case-mix adjustment**: compare agent's actual time vs. expected time from a regression/GBM on (category, priority, required skill, channel, WIP). Report **Performance Index = actual / expected**. |
| **L1 First-Contact Resolution (FCR)** | % of L1-touched tickets closed without `Escalate *`. Compute overall, per category, per skill, and **per agent**. |
| Escalation rate & escalation latency | Time from `Work L1 Start` to `Escalate L2` — long "hold-then-escalate" is pure waste |
| Reassign-out rate | % of tickets an agent receives and passes on without resolving |
| Reopen / de-escalation rate | Quality proxy: work sent back down or reopened after closure |
| Idle-to-pickup latency | `Assign`  `Work Start` per agent (are some agents cherry-picking easy tickets and letting hard ones age?) |
| Cherry-picking index | Correlation between a ticket's predicted difficulty and its pickup latency for that agent |

**C. Skill/scope behaviour**
- **Activity/skill entropy per agent** — how broad is the actual work portfolio vs. the documented profile.
- **Ticket-type coverage matrix** — Agent × Required-Skill counts (raw, and normalized as a share of the skill's total demand).

### 1.2 Discovering the *actual* assignment logic (vs. the intended one)

**(i) Handover-of-work social network.** Build a directed graph where an arc ab exists whenever, within a case, resource *a*'s event is immediately followed by resource *b*'s event. Two variants are essential:
- *Including Dispatcher*: shows the real topology — most likely a star with `Dispatcher` at the centre, meaning routing decisions are centralized and auditable in one place (good news for intervention).
- *Excluding/collapsing Dispatcher* ("transitive handover", ignoring non-human resources): reveals the **agent-to-agent** flow, exposing:
  - **Ping-pong pairs** (strong arcs in both directions, e.g., B12B15) = chronic mis-triage between two skill areas;
  - **Sinks** — agents who receive much and hand over little (true resolvers, likely overloaded, e.g., the only firewall expert);
  - **Bypass arcs** — L1L3 direct, or L3L2 downward handovers that should not exist;
  - **Betweenness centrality** — the few agents every hard ticket passes through = single points of failure ("bus factor 1" skills).

**(ii) Role / organizational mining.** Cluster agents on their *activity-and-skill execution profiles* (Song & van der Aalst's "doing similar work" metric; e.g., k-means or hierarchical clustering on the normalized resource-activity matrix, cosine similarity). Then overlay the nominal tier labels. Typical revelations at an ITSM desk:
- A cluster of "L2s" whose actual work profile is indistinguishable from L1  **tier inflation**;
- L1 agents (e.g., A02, who self-assigns phone tickets) forming their own cluster of "informal L1.5 specialists" who resolve network issues off-book;
- L3 agents split into two clusters: genuine deep engineering vs. "escalation absorbers" doing L2-grade work.
The delta between **discovered roles** and **declared tiers** is the organizational headline finding.

**(iii) Conformance checking against the *intended* rule.** Formalize the official policy as a normative model with resource/data constraints, e.g.:
> R1: Every `Work L2/L3 Start` must be executed by an agent whose profile contains the ticket's `Required Skill`.
> R2: `Escalate L2` may only occur after 1 completed `Work L1` instance and consultation of the KB.
> R3: No more than one `Reassign` per tier.
> R4: Round-robin: within a tier, assignment order follows the availability queue.

Run **data-aware alignment/conformance checking** and rule-based (LTL/Declare) checking. Output: violation frequency per rule, per dispatcher, per shift, per category, and the *cost* (added cycle time) of each violation type. This directly answers "how does actual compare to intended?" — my expectation is that R1 is violated in a substantial minority of assignments and R4 is *satisfied* far too literally (round-robin executed faithfully, which is precisely the problem).

**(iv) Decision mining at routing points.** Treat each `Assign L2` as a classification decision: target = assigned agent (or assigned *skill-cluster*); features = required skill, category, priority, channel, time-of-day, current queue lengths, dispatcher identity. Fit an interpretable model (decision tree / rule list).
- If the tree has **near-zero predictive power** and the assignment distribution is uniform over available agents  confirms blind round-robin.
- If the tree splits on **time-of-day or dispatcher ID** rather than skill  confirms person-dependent, ad-hoc routing.
- Statistical test: ² / mutual information between `Required Skill` and `Assignee Skill Set`. Compare observed match rate to a **random-assignment baseline** (expected match rate if agents were drawn uniformly from the tier). *"Skill-based routing adds only 6 percentage points over random"* is a devastating, quotable finding.

### 1.3 Skill utilization analysis

Construct a **Skill Supply–Demand Matrix**:

| Per skill *s* | Metric |
|---|---|
| Demand | # tickets/month requiring *s*, weighted by expected handling time; arrival seasonality by hour/day |
| Supply |  over agents with *s* of (available hours × share of their time actually spent on *s*) |
| **Coverage ratio** | Supply ÷ Demand — values <1.2 predict queueing |
| **Concentration (HHI / bus factor)** | Share of *s*-work done by top agent; count of agents with 1 resolution of *s* in last 90 days ("live skill", vs. "paper skill") |
| Queue time percentile for *s* | Isolates skill-specific bottlenecks |
| Proficiency spread | Case-mix-adjusted handling time & FTR per agent for *s*  derives a **proficiency score** (see Strategy 1) |

**Over-qualification / skill dilution analysis.** For each work instance by an L2/L3 agent, estimate the **minimum capability tier required**, using historical evidence rather than opinion:
- Label a (category, required-skill, symptom-cluster) combination **L1-resolvable** if X% (e.g., 30%) of historical tickets of that type were actually closed at L1, and the L1-closed instances show no elevated reopen rate.
- **Over-qualification Index (OQI)** for agent *a* = share of *a*'s active hours spent on L1-resolvable or L2-resolvable work.
- Complement with **Skill Depth Utilization**: for each specialist skill (e.g., `Networking-Firewall`), what % of that specialist's time actually required it? An L3 firewall engineer spending 45% of time on password resets and CRM how-to questions is a quantified, board-level finding: *cost of misallocated specialist hours = hours × (L3 rate  L1 rate)*.
- Also detect the inverse: **under-qualification** — junior agents holding tickets far beyond their evidenced capability (long hold, then escalate) = "escalation debt".

## Section 2. Identifying Resource-Related Bottlenecks and Issues

### 2.1 Where does the time actually go? (Waiting-time decomposition)

For every case, decompose end-to-end cycle time into a stacked structure, business-calendar-adjusted:

```
Total cycle =  processing time
            +  dispatch latency  (Escalate  Assign)
            +  queue time        (Assign  Work Start)
            +  inter-touch gaps  (Work End  next event, "ticket sitting")
            +  customer wait     (excluded from SLA clock)
```

Then aggregate the *waiting* components by **the resource that owned the ticket during the wait** and by **the required skill**. Experience says 60–80% of ITSM cycle time is waiting, and the majority of that waiting sits in queues in front of a handful of scarce skills. In INC-1001, note: `Assign L2` 09:40  `Work L2 Start` 10:05 = 25 min queue for a P3; the same pattern on a P2 during peak hours is what breaks SLAs.

**Bottleneck localisation techniques**
- Process map with **performance overlay** (median & P90 waiting on arcs), filtered per priority and per required skill — the P2/Network map will look very different from the P3/Software-App map.
- **Resource-activity dotted chart** (one row per agent, dots = events over time) to see queue build-up, shift-change discontinuities, Monday-morning surges, and vacation-driven skill outages.
- **Queue-length time series per skill pool**, overlaid with SLA breach events — visual and statistically testable (Granger-style lead/lag) coupling.
- **Bottleneck attribution**: for each breached ticket, identify the *single longest waiting interval* and attribute it to a (skill, tier, agent, time-window) tuple. Produce a Pareto: "Top 5 (skill, shift) combinations account for 62% of total P2 breach-causing wait."

### 2.2 Specific problem classes and how to quantify them

**(a) Scarce-skill bottleneck.** Evidence set: coverage ratio <1, HHI high, queue-time P90 for that skill >> other skills, waiting concentrated when the key agent is off-shift.
> *Illustrative finding:* `Networking-Firewall` demand = 210 tickets/month (340 h) vs. effective supply  260 h (coverage 0.76); 3 qualified agents, 71% of volume handled by B08. Median queue time 4.2 h vs. 0.8 h for all other L2 skills. During B08's absence weeks, P2 network breach rate rises from 11%  34%.

**(b) Reassignment and escalation waste.** Quantify with a **matched-cohort / regression** design, not a naive average (tickets with many reassignments are inherently harder — confounding).
- Fit `log(cycle_time) ~ n_reassignments + priority + category + required_skill + arrival_load + channel`, or use propensity-score matching on predicted complexity.
- Report the **marginal causal-ish delay per reassignment** and the **dispatch overhead** (Reassign  Assign  Work Start).
> *Illustrative:* Each reassignment adds a median **3.1 business hours** (P90 = 9.4 h), of which only 12 min is productive work — the rest is re-queueing and re-familiarization ("re-read the ticket" cost, visible as longer first work instance after a handover). 23% of tickets have 1 reassignment; 6% have 2. Total annual waste  23% × 48,000 tickets × 3.1 h  **34,000 ticket-hours**.

**(c) Incorrect initial assignment / mis-triage.** Metrics:
- **Routing accuracy** = % of tickets where the first working agent is the one who resolves.
- **Skill-drift rate** = % of cases where `Required Skill` changes after the first assignment (INC-1001 is exactly this: App-CRM  Database-SQL). Cross-tab with initial category and with the *triaging person* (Dispatcher, self-assigning L1 agent, or web-portal auto-category).
> *Illustrative:* Web-portal tickets have 31% skill-drift vs. 14% for phone tickets (customer-selected categories are unreliable) — and skill-drift tickets are **2.7×** more likely to breach SLA.

**(d) Over/under-loaded agents.** Cross-plot **utilization vs. performance index vs. quality (reopen rate)** per agent, quadrant analysis:
- High utilization + degrading speed = genuine overload (add capacity / re-route);
- Low utilization + long pickup latency = availability/engagement or skill-mismatch issue (they're not receiving work they can do);
- High volume + high reassign-out = a "router disguised as a resolver".
Also test **Little's Law consistency** per pool (WIP = throughput × cycle time) to spot pools where WIP is structurally too high.

**(e) Correlation  attribution of SLA breaches.** Build an interpretable classifier (logistic regression + GBM with SHAP) for `SLA_breach`:
Features: skill match at first assignment (exact/partial/none), n_reassignments, queue length in target pool at assignment, WIP of assignee, assignment made outside business hours, channel, priority, category, dispatcher, initial-category-correct flag, arrival hour.
Report **population-attributable fractions**, not just coefficients.
> *Illustrative attribution of P2/P3 breaches:* skill mismatch at first L2 assignment **28%**; queueing behind an overloaded specialist **24%**; 2 reassignments **17%**; escalation delay (ticket held at L1 >2h before escalating) **13%**; genuinely long technical work **18%**.

This single chart converts a vague complaint ("assignment logic is inefficient") into a prioritized, quantified improvement backlog.

## Section 3. Root Cause Analysis for Assignment Inefficiencies

### 3.1 Candidate root causes and the evidence that confirms or refutes each

| Hypothesized root cause | Confirming evidence from the log | Refuting evidence |
|---|---|---|
| **Round-robin ignores skills** | Decision-mining model has ~no lift over random; skill-match rate  random baseline; near-uniform ticket counts per agent within tier despite wildly different skill profiles | Assignment strongly predicted by required skill |
| **Round-robin ignores workload** | Zero/near-zero correlation between `WIP_at_assignment(agent)` and probability of receiving a ticket; assignments continue to an agent whose queue is 3× the pool median | Negative correlation (load-aware) |
| **Inaccurate/stale skill profiles** | *Phantom skills*: agent has skill *s* on paper but 0 resolutions or high reassign-out rate for *s*. *Hidden skills*: agent repeatedly resolves *s* without it in the profile. Build the "declared vs. revealed skill matrix" — the off-diagonal mass is the measure of profile decay | Matrices align |
| **Poor initial categorization / skill identification** | High skill-drift and category-change rates; portal-vs-phone differential; specific categories (Software-App) with drift >30% | Drift concentrated in genuinely ambiguous incident types only |
| **No real-time load/availability visibility** | Assignments to agents who are off-shift/on leave (assignwork-start gap spanning a full shift); assignment timestamps clustered in dispatcher batches (e.g., every 15 min) rather than continuous | Assignpickup latency uniformly short |
| **Under-trained / under-empowered L1** | L1 FCR varies 3× across agents for the *same* ticket mix; escalations occurring <5 min after `Work L1 Start` (no real attempt) or after >2 h (hold-then-give-up); high volume of L2 work classified as L1-resolvable (OQI) | FCR uniform and near the achievable ceiling |
| **Escalation used as a workload valve** | Escalation rate spikes when L1 queue length or individual WIP is high, controlling for ticket mix (interaction term in the escalation model) | No load sensitivity |
| **Structural capacity shortfall** | Coverage ratio <1 for a skill even under perfect routing (verify by simulation with an oracle router) | Perfect routing removes the queue  it was a routing problem, not a capacity problem |

Critically, the last row is the *discriminating test*: simulation with a hypothetical perfect router tells us how much of the pain is **routing** vs. **capacity/skill supply**. Without it, we risk hiring when we should be re-routing (or vice versa).

### 3.2 Variant analysis

Segment cases into cohorts and compare, **holding ticket mix constant** (stratify by priority × category × required skill):

- **Cohort A "Straight-through"**: `Create  Assign  Work  Resolve`, no reassignment, single tier.
- **Cohort B "One clean escalation"**: L1  L2, no reassignment.
- **Cohort C "Ping-pong"**: 2 reassignments and/or lateral L2L2 handovers.
- **Cohort D "Skipped tier"**: direct-to-L2/L3.

For each cohort, compare distributions of: cycle time, SLA rate, skill-match at first assignment, dispatcher, channel, arrival hour, initial category accuracy, assignee WIP, and whether the ticket description contained certain keywords.

Then run **variant-difference mining** (e.g., a decision tree predicting cohort membership from case attributes known *at assignment time*). The output is the actionable statement: *"Tickets arriving via web portal, category Software-App, with required skill inferred from customer-selected dropdown, assigned between 08:00–09:30 (dispatcher shift change), have a 44% probability of landing in Cohort C — vs. 9% baseline."*

Complement with:
- **Decision mining on the escalate/don't-escalate choice** at L1: what actually drives escalation? If `agent identity` and `current WIP` outrank `ticket complexity` in feature importance, the escalation criterion is *social*, not technical.
- **Root-cause trees on the reassignment event** itself: parse the `Notes` field ("Needs different skill (DB)") into a reassignment-reason taxonomy (wrong skill / overload / shift end / customer request / vacation) — this is often the fastest, highest-confidence root cause source and it is already being captured.
- **Concept drift analysis**: has the mix shifted over the year (e.g., CRM migration created a new demand spike for `App-CRM` + `Database-SQL` combined skills) faster than skill profiles and routing rules adapted? Plot skill demand vs. routing-rule change dates.

## Section 4. Data-Driven Resource Assignment Strategies

I propose five strategies; they are complementary and sequenced. Each is expressed as something that can be implemented in the ITSM tool's routing engine or as an external micro-service that the tool calls.

---

### Strategy 1 — Proficiency-Weighted Skill-Based Routing (replace round-robin)

**Issue addressed:** Blind round-robin  skill mismatch at first assignment (~28% of breaches), lateral reassignments, ping-pong pairs.

**Core idea:** Replace the tier queue with a **capability-scored candidate ranking**. Crucially, "skill" is not the binary HR flag — it is a **mined proficiency score**, refreshed monthly:

For agent *a* and skill *s*:
```
Proficiency(a,s) = w1·Norm(resolution_rate(a,s))
                 + w2·Norm(1 / case-mix-adjusted handling time(a,s))
                 + w3·Norm(1  reassign_out_rate(a,s))
                 + w4·Norm(1  reopen_rate(a,s))
                  w5·RecencyDecay(days since last s-ticket)
```
Only skills with  N recent resolutions count as "live"; phantom skills are demoted automatically. Hidden skills (revealed by the log) are promoted — this *auto-corrects the skill catalogue*, which is itself one of the root causes.

**Leverages PM analysis:** revealed-vs-declared skill matrix, per-skill case-mix-adjusted performance, reassignment-reason taxonomy.

**Data required:** historical resolutions per (agent, skill), reassignment/reopen outcomes, ticket case-mix features for normalization, up-to-date `Required Skill` per ticket, live agent skill catalogue.

**Expected benefits:** first-assignment skill match from ~55%  >90%; reassignment rate 23%  <10%; removal of ping-pong arcs; and, because proficiency-weighted routing implicitly prefers faster resolvers, a 10–20% reduction in L2/L3 handling time.

**Guardrails:** cap the share of any skill's volume going to the top-scored agent (prevents "the good agent gets everything" and preserves the learning pipeline); reserve a deliberate quota of tickets for developing agents (see Strategy 5).

---

### Strategy 2 — Workload- and SLA-Aware Dispatch (multi-objective scoring)

**Issue addressed:** Uneven workload (high Gini), queueing behind overloaded specialists (~24% of breaches), assignments to unavailable agents, P2s stuck behind P3s.

**Core idea:** Rank candidates with a composite score computed at assignment time:

```
Score(a, t) = ·Proficiency(a, s_t)
             ·NormalizedLoad(a)             // WIP weighted by expected remaining work
             ·ExpectedWaitUntilPickup(a)    // from shift calendar + current queue
            + ·UrgencyFit(a, t)              // SLA slack vs. a's predicted handling time
            + ·ContinuityBonus(a, t)         // a has touched this ticket/CI/customer before
             ·ContextSwitchPenalty(a, t)    // batch similar work
```
Assign to `argmax Score`, subject to hard constraints (must hold live skill, must be on shift or ticket queued to a *pool* not a person, must not exceed WIP cap). Combine with **priority-aware queue discipline**: weighted-shortest-expected-processing-time with **SLA-slack aging** (a P3 whose slack drops below threshold gets promoted) — this prevents the classic failure mode where P3s starve and generate the very P3 breaches TechSolve reports.

Key architectural change: **assign to a skill pool, pull by agent** ("push-to-pool, pull-by-agent") rather than push-to-person. Tickets never sit in an absent agent's personal queue.

**Leverages PM analysis:** WIP reconstruction, utilization vs. performance quadrants, queue-length/SLA coupling, Little's Law diagnostics, pickup-latency and cherry-picking metrics.

**Data required (real time):** live WIP per agent, shift/absence calendar, per-(agent,skill,category) expected handling-time model, live SLA clocks, pool queue lengths.

**Expected benefits:** workload Gini from ~0.35  <0.15; P90 queue time reduced 30–50%; elimination of "assigned but nobody is on shift" waits; P2/P3 SLA compliance improvement of several points on its own.

---

### Strategy 3 — Predictive Triage at Intake (skill, complexity, and tier prediction)

**Issue addressed:** Poor initial categorization (skill drift 14–31%), unnecessary L1 touches on tickets L1 can never resolve, and unnecessary escalations of tickets L1 *could* resolve.

**Core idea:** At `Ticket Created`, run an NLP/ML service over the description, subject, customer/CI, category, channel and customer history to predict three targets, each trained on the historical log with *outcome* labels (not the entered labels):

1. **Required skill** (multi-label classifier; label = the skill of the agent who *actually resolved* it)  overrides unreliable customer-selected categories.
2. **P(resolvable at L1)**  if below threshold _low, **skip L1** and route directly to the right L2/L3 pool ("smart bypass"); if above _high, hard-route to L1 with a KB article attached.
3. **Predicted handling time and complexity band**  feeds Strategy 2's scoring and the SLA-risk model.

Add an **SLA-breach risk score** at intake and at each state change; high-risk tickets get priority routing and proactive supervisor alerts.

Every prediction must be exposed with confidence; low-confidence tickets go to a human triage queue rather than being routed badly with false confidence. Predictions are logged so the models are continuously retrained and their *routing* impact is measurable.

**Leverages PM analysis:** skill-drift analysis, L1-resolvability labels derived from historical L1 closures, variant analysis identifying which intake profiles lead to Cohort C, decision mining on escalation.

**Data required:** ticket text (subject/description), historical resolution outcomes and resolver skills, KB article usage, CI/asset and customer master data, model-serving infrastructure.

**Expected benefits:** removes an entire wasted L1 touch (typically 20–45 min + queue) from the 15–25% of tickets that are never L1-resolvable; cuts skill drift by half; feeds better inputs into Strategies 1 & 2 (garbage-in prevention). Direct effect on P2 cycle time is usually the largest single win.

---

### Strategy 4 — Evidence-Based Escalation Gates and L1 Empowerment

**Issue addressed:** Excessive escalation (specialist dilution / high OQI), hold-then-escalate latency (~13% of breaches), escalation used as a workload valve.

**Core idea:** Rebuild escalation from an agent-discretion decision into a **data-defined gate**:
- **Escalate-early rule:** if predicted P(L1 resolves) < _low, the system *requires* immediate escalation — no 2-hour hold. Enforced by a timer: any L1 work instance exceeding the 80th percentile of successful L1 resolution time for that ticket type triggers an automatic escalation prompt.
- **Escalate-late rule:** if the ticket type has a historically high L1 resolution rate, escalation requires a documented reason chosen from the mined taxonomy, plus a KB check — creating clean data for the next analysis cycle.
- **Targeted enablement:** the per-agent × per-category FCR heat map identifies exactly which agents need which micro-training and which KB articles are missing. Prioritize by `volume × (best-in-class FCR  agent FCR) × avg escalation cost`.
- **Swarming for P1/P2**: replace sequential tier escalation with a time-boxed swarm (L1 + relevant specialist jointly) for high-priority tickets — the handover-network analysis shows sequential escalation is where P2 time is lost.
- **Shift-left backlog:** for each ticket type with high OQI, either automate (self-service/runbook), or transfer to L1 with a runbook.

**Leverages PM analysis:** OQI, L1-resolvability labels, escalation-latency distributions, escalation-vs-load interaction model, per-agent FCR heat map.

**Data required:** L1 work-instance durations and outcomes, KB usage events, structured escalation reasons, training records.

**Expected benefits:** L1 FCR from e.g. 42%  55%; specialist hours released for genuinely complex work (directly quantifiable in € as hours × rate differential); reduction in "hold-then-escalate" dead time.

### Strategy 5 — Dynamic Capacity Shaping & Targeted Cross-Training

**Issue addressed:** Structural scarce-skill bottlenecks (bus factor 1), demand seasonality that static rosters cannot absorb, skill-catalogue decay.

**Core idea:** Two loops:
- **Short loop (daily/intra-day):** a demand forecast per skill × hour (from the log's arrival process, with day-of-week/month-end/release-calendar effects) drives **flexible pool membership** — cross-skilled agents are dynamically allocated to the pools with the highest predicted SLA risk. Trigger rules: "if `Networking-Firewall` queue > 5 or predicted breach risk > 20%, activate reserve-skilled agents A17, B03 into that pool."
- **Long loop (quarterly):** a **cross-training investment plan** derived from the supply–demand matrix. Optimize which (agent, skill) pairs to develop by maximizing expected reduction in queueing (marginal value of an extra server in the scarcest pool is highly non-linear — the second firewall-capable agent is worth far more than the sixth CRM-capable one). Explicitly target bus-factor-1 skills and shift-coverage gaps (e.g., no `Security-IAM` skill rostered on night shift). Also fold in shift-pattern redesign aligned to the arrival dotted chart.

**Leverages PM analysis:** skill coverage ratios, HHI/bus factor, arrival-rate seasonality, absence-driven breach spikes, per-skill queue-time elasticity from simulation.

**Data required:** arrival forecasts per skill, rosters and contract flexibility, training cost/duration, simulation model for marginal-value estimation.

**Expected benefits:** removes the residual bottleneck that routing alone cannot fix; reduces breach volatility (variance, not just mean); improves resilience to absence.

## Section 5. Simulation, Implementation, and Monitoring

### 5.1 Discrete-event simulation as the pre-implementation test bed

Changing routing logic on a live service desk is risky — a badly tuned load term can starve P3s or overheat top performers. Simulation lets us test policies at zero operational risk.

**Building a credible model (all components mined, not assumed):**

| Model component | Source from the event log |
|---|---|
| Control flow | Process model discovered (inductive miner on a noise-filtered log), converted to BPMN/Petri net with tier subprocesses |
| Arrival process | Non-homogeneous Poisson per (category, priority, channel), with hour-of-day, day-of-week, month-end and release-calendar seasonality fitted from `Ticket Created` timestamps |
| Processing times | Fitted distributions (typically log-normal / Weibull) per (activity, skill, priority, proficiency band) from START–COMPLETE pairs — *not* a single global mean |
| Branching probabilities | From decision mining: P(escalate), P(reassign), P(reopen) conditioned on ticket attributes and load, so the model reproduces load-induced escalation |
| Resources | Actual agent roster, skill matrices, proficiency scores, shift calendars, absence rates, WIP caps, multitasking behaviour |
| Queue discipline & routing | **Parameterized** — this is the experimental variable (round-robin baseline vs. Strategies 1/2/3/5) |
| Handover overhead | Empirical re-familiarization penalty measured in §2.2(b) |

**Validation before use (non-negotiable):** replay the historical period with the as-is policy and compare simulated vs. actual distributions of cycle time (per priority), SLA compliance, queue lengths, utilization per agent, escalation and reassignment rates. Accept only if key KPIs match within ~5–10% and the *shapes* (not just means) align; use K-S tests on cycle-time distributions. Document known simplifications.

**Experiment design:**
- Scenario matrix: {as-is, S1, S1+S2, S1+S2+S3, S1+S2+S3+S5(+2 FTE firewall skill), …} × demand levels {baseline, +15% volume, key-specialist absent 2 weeks}.
- 30–100 replications per scenario, common random numbers across scenarios for variance reduction, appropriate warm-up removal, confidence intervals on all reported KPIs.
- **Parameter tuning:** sweep the … weights in Strategy 2's scoring function and the  thresholds in Strategy 3; select on a composite objective (SLA compliance × cost) and check robustness — the chosen policy must not be a knife-edge optimum.
- **Sensitivity/stress tests:** what happens if the ML skill prediction is only 80% accurate? If a top specialist resigns? This produces the *risk register* for implementation.
- **Oracle bound:** run a "perfect information" router to establish the theoretical ceiling — this quantifies how much of the gap is routing (fixable by S1–S3) vs. capacity (needs S5).

**Complement with offline policy evaluation:** for the routing rules specifically, counterfactual replay on historical arrivals (queue-simulation on the real arrival stream) is faster and more convincing to stakeholders than a full DES, and can be run nightly.

### 5.2 Implementation approach

1. **Shadow mode (4–6 weeks):** the new routing engine computes and logs its recommendation for every ticket; humans keep deciding. Measure agreement rate and, where they differ, compare outcomes. Zero risk, builds trust, catches data-quality faults.
2. **Champion/challenger pilot:** apply new logic to 2–3 categories or one region (randomized at ticket level where possible, so it's a genuine A/B test rather than a before/after with confounded seasonality). Predefine success criteria and a rollback trigger.
3. **Phased rollout** by category/tier, with the skill catalogue auto-refresh (Strategy 1) running from day one.
4. **Change management:** agents must see *why* a ticket was routed to them (explainability: "you scored highest on App-CRM proficiency and have the shortest queue"). Publish the workload-equity metrics — perceived fairness is the main adoption risk. Escalation-gate changes need L1 supervisors as co-designers.

### 5.3 Continuous monitoring with process mining dashboards

Establish a **living process-mining environment** (daily/near-real-time refresh from the ITSM tool) with three dashboard layers:

**(A) Operational — team leads, intraday**
- Live process map with waiting-time overlay, filtered by priority; queue length and oldest-ticket age per skill pool
- Real-time SLA-risk heat map (tickets ranked by predicted breach probability)
- Agent WIP board and pickup-latency alerts
- Alerts: pool queue > threshold; ticket assigned but not started within X min; skill pool with no on-shift qualified agent

**(B) Tactical — service desk manager, weekly**

| KPI family | Specific KPIs | Target direction |
|---|---|---|
| Assignment quality | First-assignment skill-match rate; routing accuracy (first worker = resolver); skill-drift rate |  /  /  |
| Rework | Reassignments per ticket; ping-pong pair count; reopen rate; de-escalation rate |  |
| Escalation | L1 FCR (overall & per category/agent); escalation rate; escalation latency; % escalations with valid mined reason |  FCR,  others |
| Speed | Cycle time & queue time P50/P90 per priority; waiting-vs-processing ratio |  |
| SLA | Compliance % per priority; breach attribution mix (the §2.2(e) chart, tracked over time) |  |
| Resource | Utilization per agent (band 65–80%); **workload Gini**; over-qualification index (specialist hours on L1-resolvable work); bus factor per skill; skill coverage ratio | balanced |
| Conformance | Violation rate of routing rules R1–R4; % of routing recommendations overridden by humans, and outcome delta of overrides |  violations |
| Model health | Skill-prediction precision/recall; handling-time prediction MAE; calibration of breach-risk score; drift alarms | stable |

**(C) Strategic — quarterly steering**
- Trend of SLA compliance and cost-per-ticket vs. baseline, with the pilot A/B effect isolated
- Realized vs. simulated benefit per strategy (closes the loop on model credibility)
- Skill supply–demand gap forecast  next cross-training investment round
- Specialist hours released and re-deployed (the shift-left value story)

**Key process views to keep permanently:** (i) handover social network — re-run monthly, watch for new ping-pong arcs; (ii) variant explorer with the Cohort A–D classification, tracking the share of Cohort C; (iii) dotted chart per skill pool for seasonality/absence effects; (iv) conformance dashboard against the normative routing model.

**Governance cadence:** weekly ops review on (A)/(B) with a standing "top 3 breach drivers this week" item; monthly model retraining and skill-catalogue refresh; quarterly re-run of the full diagnostic (§1–§3) plus re-calibration of the simulation model against the latest log — because demand mix, technology, and staff drift, an assignment policy tuned once will decay. The end state is a **closed feedback loop**: log  mine  predict  route  log.

### Closing note on expected aggregate impact

Based on the illustrative attribution in §2.2(e), Strategies 1–4 target roughly 80% of identified breach causes. A realistic, simulation-validated target for the first 6–9 months would be: reassignment rate 23%  8%, P2 SLA compliance +10–15 points, P3 +8–12 points, median P2 cycle time 25–35%, specialist over-qualification index halved, and workload Gini below 0.15 — with the *exact* figures to be established by the baseline measurement and the simulation experiments rather than asserted up front. The discipline of quantifying the baseline first, testing in simulation second, and A/B-testing in production third is what separates this from a conventional "implement skill-based routing" recommendation.
