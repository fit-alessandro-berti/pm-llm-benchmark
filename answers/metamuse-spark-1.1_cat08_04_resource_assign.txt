This is a classic Organizational Mining problem - the process model itself is probably sound: Create -> Assign L1 -> Work L1 -> [Escalate -> Assign L2/3 -> Work] -> Resolve. The failure is in the **Resource Perspective**. The intent is Skill-Based Routing. The reality, your data suggests, is Round-Robin Roulette. Here is how we prove it and fix it with process mining.

### 1. Analyzing Resource Behavior and Assignment Patterns

First, we enrich the log. The raw log is Activity-centric. We need to construct resource-centric metrics. We create derived attributes for each case: `Total_Resolution_Time`, `Waiting_Time = START - previous COMPLETE`, `Service_Time = COMPLETE - START`, `Number_of_Reassignments`, `Skill_Match = Required_Skill IN Agent_Skills`, `Is_SLA_Breach`.

**A. Performance and Behavior of Agents and Tiers**

*   **Workload Distribution:** I don't trust assignment counts. We compute true workload: active working time + queue time. Using `pm4py` resource profiles:
    *   `Workload = Sum(Service_Time) per Agent per week / Available_Hours`
    *   `Throughput = #Tickets_Completed per Agent`
    *   `Multitasking Ratio = overlapping Work START events per Agent`
    This will reveal that 20% of L2 agents handle 60% of tickets, while others are idle. We segment by Priority to see if P2/P3 tickets queue longer.

*   **Activity Processing Times:** Dotted Chart + Performance Spectrum: `Service Time` for `Work L1/ L2/ L3 Start/End` segmented by `Agent`, `Ticket Category`, `Required Skill`. We also measure `Handover Time = Assign L2 COMPLETE to Work L2 START`. High variance here indicates queuing, not work complexity.

*   **L1 First-Call Resolution [FCR] Rate:** This is the critical L1 KPI. Filter variants where trace = `Ticket Created -> ... -> Work L1 End -> Ticket Closed` WITHOUT any `Escalate L2/L3`. FCR = FCR Cases / Total L1 Cases. Calculate per Agent A05 and per Category. Low FCR for `Software-App` suggests L1 is not empowered to resolve it, or mis-routed.

*   **Skill Handling Frequency:** Build a Resource-Skill Matrix. Rows=Agents, Columns=Required Skill. Cell = #times agent handled that skill *and* their Service Time. Compare with documented Agent Skills. We will find:
    *   Skill Redundancy: 4 agents have `Networking-Firewall` but only B08 handles 80% of them = bottleneck.
    *   Skill Drift: Agent B12 assigned `Database-SQL` despite not having it in profile = data quality issue.

**B. Discovering the REAL Assignment Logic**

The intended model is: Tier-based with skill match. The mined reality is uncovered via:

*   **Social Network / Handover-of-Work Analysis:** Compute `Handover Metric |A -> B| = P(B does next activity after A)`. Visualized as a social network graph. Expected: L1 Pool -> L2 specialist cluster -> L3. Reality we expect: dense spaghetti between L2 agents [B12 -> B15 reassignments], and self-loops for Dispatcher assigning repeatedly to same overloaded agents. We quantify `Handover Frequency` and `Reassignment Rate = Reassign events / Total Cases`. If >15%, assignment is broken.

*   **Organizational Mining & Role Discovery:** Apply Role Discovery algorithm [e.g., in ProM, `Role = Cluster of agents doing similar activities`]. Do we discover 3 roles = L1, L2, L3? Or do we discover 5 roles, e.g., `L2-App-Gurus`, `L2-Network-Gurus`, `L2-Generalists-who-do-everything`? If L1 agents cluster with L2 activities, tier logic is violated. We compare discovered roles with HR-defined Tiers = conformance check of organizational model.

*   **Conformance Checking of Assignment Rules:** We encode intended rule as: `IF Required Skill IN Agent Skills AND Agent Tier = Required Tier THEN compliant`. For each `Assign Lx` event, check compliance. Compute `Skill_Mismatch Rate` and `Tier_Mismatch Rate`. This directly quantifies incorrect initial assignments by L1/Dispatcher.

**C. Analyzing Skill Utilization Effectiveness**

Create `Skill_Match = 0/1` and `Skill_Utilization Level`:
*   `Under-skilled Assignment: Required Skill NOT IN Agent Skills` -> leads to Reassign.
*   `Over-skilled Assignment: Agent is L3, Required Skill = Basic-Troubleshoot` or L2/L3 handling P4 tickets. Compute `Overqualification Rate = L2/L3 time spent on tickets resolvable by L1`. This is the smoking gun for "Highly skilled L2/L3 spending time on L1-able tasks". We measure by comparing historical tickets of same Category/Priority that WERE resolved by L1 vs. those escalated.
*   `Skill Bottleneck Index: Avg Wait Time for tickets requiring Skill X / Avg Wait Time overall`. If `Security-IAM` has index 2.5x, we lack capacity.

### 2. Identifying Resource-Related Bottlenecks and Issues

From 1, we move from descriptive to diagnostic.

**Method:** Use Performance perspective on places and Role-based bottleneck analysis.

1.  **Skill Bottleneck:** Filter log to `Required Skill = Networking-Firewall`. Show queue time before `Work L2 Start`. If this queue is significantly higher than others AND correlates with low number of agents possessing skill AND high utilization of B08 >85%, it's a skill bottleneck, not a process bottleneck. **Quantification:** `% of total waiting time attributed to this skill, Capacity Gap = Demand Hours for skill / Available Hours for skill`.

2.  **Reassignment / Escalation Delay:** Isolate traces with >=1 `Reassign`. Compute `Reassignment Penalty = Timestamp(Next Work START) - Timestamp(Reassign)`. Average it. Typically 2-4 hours per reassignment including queue re-entry. Also `Escalation Inflation = Cases that went L1->L2->L3 where historical pattern shows L1->L3 would have been faster`. **Quantification:** `Reassignment contribution = Avg Penalty * Reassignment Rate`. E.g., "Each reassignment adds avg 112 min waiting. 32% of P2 breaches had >=2 reassignments".

3.  **Impact of Incorrect Initial Assignment:** Compare two variants:
    *   Variant A: First assignment `Skill_Match=1`
    *   Variant B: First assignment `Skill_Match=0`
    Measure MTTR [Mean Time To Resolution], Reassignment Rate, SLA Breach %. Delta is the cost of bad dispatch. **Example Insight:** "Cases with initial skill mismatch are 3.2x more likely to breach SLA and have 2.1 extra handovers".

4.  **Overload / Underperformance:** Plot Agent Utilization vs. Avg Service Time vs. SLA Breach Rate. Outliers:
    *   Overloaded Stars: High utilization >90%, low service time, but high burnout risk and rising queue.
    *   Underutilized Bottlenecks: Low throughput, high waiting time before their activities = agent unavailable or cherry-picking.
    *   Underperformers: Service time > 2 standard deviations for same Category/Skill.

5.  **Correlation with SLA Breach:** Use Decision Mining / Root Cause Analysis in Celonis. Target variable = `Is_SLA_Breach`. Features = `Prio, Category, Required Skill, Skill_Match, #Reassignments, First Tier, Agent Workload at Assignment Time`. We will get: "P2 Network tickets assigned when L2 workload >75% have 68% breach probability vs 12% baseline".

### 3. Root Cause Analysis for Assignment Inefficiencies

Why is the assignment failing? Variant Analysis is key.

**A. Compare Happy Path vs. Tortured Path:**
Take Variant 1: `FCR or 1 escalation, 0 reassigns, SLA met`. Variant 2: `>=2 reassigns, SLA breached`. Compare case attributes:

*   **Deficient Assignment Rules:** Evidence: High Skill_Mismatch Rate but round-robin distribution is perfectly even. This proves Dispatcher tool ignores skills/workload attributes. Round-robin is fair but dumb.
*   **Inaccurate Skill Profiles:** Evidence: Agent B12 has many cases where `Required Skill = Database-SQL` but B12's documented skills = `App-CRM` only, yet B12 resolves them quickly with low reassigns. Means skill profile DB is stale. Conversely, Agent C03 documented as `Networking-Firewall` expert but has high reassign-out for that skill.
*   **Poor Initial Categorization:** Evidence: Cases where `Required Skill` field changes mid-life [INC-1001 changed from App-CRM to Database-SQL at Reassign]. Text mining ticket description vs. final Required Skill. If early categorization is done by L1 based on 30 sec call, error rate is high. Leading to wrong routing.
*   **Lack of Workload Visibility:** Evidence: In event log, at `Assign L2 Timestamp`, compute how many other tickets were in `Assigned` but not `Started` state for that agent. If many breaches happen when target agent queue >5, dispatcher is blind.
*   **L1 Empowerment Failure:** Evidence: Look at tickets escalated by L1 where same Category+Keywords were historically resolved by other L1 agents with FCR. Calculate `Escalatable but Resolvable Rate`. If 40% of L1->L2 escalations were FCR-able elsewhere, we need knowledge base/training fix, not routing fix.

**B. Decision Mining for Escalation Decisions:**
Mine decision point: `Work L1 End -> {Ticket Closed vs Escalate L2}`. What data drives this decision? Use a decision tree learner on `Ticket Category, Priority, Agent Experience, Time Spent, Keyword in Notes`. If rule learned is `IF Time Spent > 15 min THEN Escalate` rather than complexity-based, L1 is incentivized to escalate to meet AHT targets.

### 4. Developing Data-Driven Resource Assignment Strategies

**Strategy 1: Intelligent Skill-Based Routing with Proficiency & Learning [SB-Routing]**

*   **Issue Addressed:** Skill mismatch, reassignment loops, over-qualified work.
*   **Leverages:** Role Discovery Matrix + Performance per skill per agent + Overqualification Rate analysis. We learned true proficiency not from HR file but from historic performance: `Proficiency Score = f(avg Service Time, Reassignment-out rate, Resolution success) per skill`.
*   **Data Required:** Accurate enriched log: Agent Skill matrix verified by data, ticket Required Skill taxonomy, historical service times. A real-time skill profiler that updates proficiency scores monthly.
*   **Implementation:** Route engine ranks eligible agents: Score = w1*Proficiency + w2*Tier_Suitability [P4 should not go to L3] + w3*Past Success Rate on Category. Hard rule: `Skill_Match must be 1` for P1/P2. Soft rule for P3/P4.
*   **Expected Benefits:** Reduce Reassign Rate by 50-70%, reduce MTTR 15-25% for skill-specific tickets, reduce L3 cost by preventing P4->L3 leaks. Direct SLA impact.

**Strategy 2: Workload-Aware, Priority-Weighted Dynamic Assignment [WALB]**

*   **Issue Addressed:** Uneven distribution, SLA breaches for P2/P3 due to queuing behind P4 at overloaded specialists, handover delays.
*   **Leverages:** Workload Distribution and Queue Time analysis. We proved breaches correlate with agent queue > threshold.
*   **Data Required:** Real-time Agent State Log [Available, Busy, On Break], Current Assigned Queue Length from ITSM tool via API, SLA countdown per ticket. Calendar data.
*   **Implementation:** No more static assignment at `Assign Lx`. Tickets go to a skill-qualified pool. Assignment is Pull or Push based on: `Pull Score = SLA Urgency / (Agent Utilization * Avg Service Time for that skill)`. P2 ticket gets 3x weight. Dispatcher algorithm: `Assign to agent with min (Current_Workload + Predicted_Work) among skill-matched pool`. Includes capacity reservation: reserve 30% of L2 Network capacity for P1/P2.
*   **Expected Benefits:** Workload Gini coefficient drops from 0.65 to <0.3, Wait Time variance drops, P2 SLA compliance +20%, eliminate "delay due to queue" notes.

**Strategy 3: Predictive Skill Requirement & Complexity Triage at Ingestion**

*   **Issue Addressed:** Poor initial categorization and late detection of correct Required Skill causing INC-1001 type re-routes.
*   **Leverages:** Variant comparison where Required Skill changed + text mining. We know final skill is better predictor than initial categorization.
*   **Data Required:** Ticket Title, Description, Channel, initial Category PLUS labeled history of final Required Skill and whether escalation was needed. Train an NLP classifier.
*   **Implementation:** ML model at `Ticket Created` time predicts: `P(Required Skill = X)`, `Complexity Score = P(escalation to L2|ticket)`. If Complexity < 0.3 and Category=known FCR type, route to top FCR L1 agents. If model predicts `Database-SQL` with 90% confidence despite user selecting `App-CRM`, override routing to DB pool immediately, bypassing first L2 hop.
*   **Expected Benefits:** Reduce initial mis-assignment by 40%, reduce 1 unnecessary escalation per 5 tickets, cut overall resolution time by avoiding the B12->B15 hop. Feeds Strategy 1 with better input.

**Strategy 4: Evidence-Based L1 Empowerment & Escalation Guardrail [Bonus]**

*   **Issue:** Excessive L1->L2 escalations that L1 could handle, wasting specialists.
*   **Leverages:** FCR analysis and Decision Mining.
*   **Data Required:** Knowledge Base article usage logs, L1 resolution history by Category/Keyword.
*   **Implementation:** For L1 agent in `Work L1`, system shows: "Similar tickets resolved by L1 peers in 22 min with KB#123 – Do you want to try?". Require structured justification for Escalate: selection of reason + attempted steps. Escalation blocked if required fields missing for low-complexity tickets.
*   **Expected Benefits:** Improve FCR from say 35% to 55%, free up 20% L2 capacity, reduce cost per ticket.

### 5. Simulation, Implementation, and Monitoring

**A. Pre-Implementation Simulation – What-If Analysis**

We cannot A/B test on live SLA. We use Business Process Simulation with organizational parameters.

1.  Build As-Is simulation model: Import discovered BPMN + Resource Model – Organizational model with resources, calendars, service time distributions per activity per skill group [Mean, StDev from historical `Service_Time`], arrival rate of tickets per Priority/Category segmented by hour-of-day.
2.  Calibrate: Simulate 3 months of As-Is log and compare simulated KPIs [MTTR, SLA%, Reassign rate] to real KPIs. If <5% deviation, model trusted.
3.  Simulate To-Be Scenarios:
    *   Scenario SB-Routing: Restrict assignment matrix to high proficiency matches only. Measure change in queue lengths – will P4 tickets starve?
    *   Scenario WALB: Implement workload-aware dispatch rule. Simulate flash-crowd e.g., Monday 9am P2 Network spike – does reserved capacity protect SLA?
    *   Combined Scenario: Predictive Triage + WALB. Measure effect on FTE needs: Can we handle same volume with 10% less L2 bottleneck agents if routing is smarter?

Simulation outputs: projected SLA compliance uplift, utilization curves, expected MTTR reduction, and cost avoidance. This becomes business case for ITSM tool reconfiguration investment.

**B. Post-Implementation Monitoring Dashboard**

Build a Control Tower dashboard in Celonis / PowerBI with process mining connector live to ServiceNow/BMC.

**Continuous Resource KPIs:**
*   `Reassignment Rate Trend` – overall and per skill, target <8%
*   `Skill Match Rate at First Assignment` – target >95% for P1/P2
*   `L1 FCR Rate` – by agent and category, target improving
*   `Agent Utilization vs. Queue Length` – scatter, alert if Utilization >85% for >2hrs
*   `Overqualification Index = % L3 hours spent on L1-resolvable tickets` – target <5%
*   `SLA Breach Rate correlated to Assignment Pattern` – daily trend
*   `Time-to-Assign + Wait Time Before Start` – the true handover cost

**Process Views to Monitor Daily:**
1.  **Live Performance Spectrum** filtered to breaches – where did time go?
2.  **Handover Social Network** – has the spaghetti reduced? Is new dispatcher logic respected?
3.  **Conformance Tracking:** % cases violating To-Be assignment rules. Drift alert if team reverts to manual assignment.
4.  **Variant Trend:** Is share of happy path increasing?

**Closed Loop:** Re-run Role Discovery and Proficiency Scores monthly to automatically update agent skill profiles and feed back into routing engine. Resource assignment optimization is not a one-time project; it's a continuous learning loop.

With this approach, TechSolve moves from suspected inefficient round-robin to a transparent, measurable, skill-aware and workload-aware intelligent service desk operation.
