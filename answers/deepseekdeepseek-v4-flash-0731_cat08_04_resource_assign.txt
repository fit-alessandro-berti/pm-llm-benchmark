We will use a **process-mining-driven approach** to analyze TechSolve’s resource assignment logic. The event log contains case IDs, activities, resources, agent tiers, skills, ticket attributes, and timestamps—this is sufficient to reconstruct the actual end-to-end incident handling process and to quantify where, why, and for whom assignments break down.

## 1. Analyzing Resource Behavior and Assignment Patterns

### 1.1 Event Log Preparation and Enrichment

Before analysis, I would transform the event log into an interval-based process-mining-ready format:

- Pair `Work L1/L2/L3 Start` and `Work L1/L2/L3 End` events to compute **active processing time**.
- Compute `waiting time` as the time between an assignment event and the next work start.
- Treat `Ticket Created`, `Assign L1`, `Escalate L2`, `Assign L2`, `Reassign` as discrete activities.
- Add derived attributes:
  - `required_skill`
  - `agent_skills`
  - `agent_tier`
  - `priority`
  - `category`
  - `day_of_week`, `time_of_day`, `shift`
  - `queue_depth_at_assignment`—computed from the number of open tickets already assigned to that agent at the moment of assignment.

This enables both process control-flow analysis and detailed resource-level performance analysis.

---

### 1.2 Metrics for Individual Agents and Tiers

I would compute a balanced set of resource-related KPIs from the event log.

#### Workload Distribution
- Number of tickets handled per agent per period.
- Total active processing time per agent.
- Number of concurrently open tickets per agent.
- Average queue length at the moment a ticket is assigned to an agent.
- Workload imbalance index, e.g., coefficient of variation of active work across agents. High variation suggests uneven distribution.

#### Performance and Productivity
- Average and median **active processing time** per agent and per tier.
- Average **waiting time** after assignment.
- Average **end-to-end cycle time** per ticket assigned to the agent.
- **SLA breach rate** by agent and tier.
- **Rework rate**: how often an agent’s work is followed by a Reassign, Escalate, or another Work Start for the same ticket.

#### Quality and First-Contact Resolution
- **FCR for L1**: percentage of L1-handled tickets that are resolved without escalation.
- **Reassignment rate**: percentage of tickets handled by an agent that are later reassigned.
- **Escalation rate** per L1 agent and per category.

#### Skill and Ticket Type Mix
- Proportion of tickets by category and required skill per agent.
- Frequency of an agent working on tickets requiring a skill that **is not** in their documented skill profile.
- Frequency of an agent working on tickets **below** their tier or skill level, indicating over-qualified assignment.

These metrics provide a baseline of who does what, how well, and with what workload.

### 1.3 Process Mining Techniques to Reveal Actual Assignment Patterns

#### Process Discovery and Conformance Checking
I would discover the **as-is process model** using algorithms like inductive miner or heuristic miner. This will visually show the dominant flows and loops.

Then I would build a **normative model** from TechSolve’s documented assignment process—for example:

- L1 receives all tickets.
- If L1 cannot resolve, escalate to L2/L3 based on required skill.
- Specialists resolve within their skill area and only escalate if needed.

Conformance checking between the normative model and discovered model would reveal:

- Unnecessary loops: e.g., `Escalate L2` followed by `Reassign`, then another `Escalate L3`.
- Reassignment loops within the same tier.
- Cases where tickets jump directly to L2/L3 without L1.
- Cases where L1 works on tickets that should have gone to L2.

This answers: **does actual behavior match intended logic?**

#### Social Network / Handover Analysis
I would build a **handover graph** for each ticket, where nodes are agents or tiers and edges represent transfer of the ticket from one resource to another.

This reveals:

- Frequent transfer pairs: e.g., Agent A05 often escalates to Agent B08.
- “Ping-pong” behavior: tickets moving A  B  A  C.
- Dispatcher behavior: whether the dispatcher assigns by skill or simply round-robin.
- Agents who are “sinks” (they resolve many tickets) and agents who are “pass-throughs” (they rarely resolve, always reassign).

The handover graph can be filtered to show only reassignments, which directly surfaces **reassignment chains** and **unnecessary handovers**.

#### Role Discovery
Using process-mining role discovery, I would cluster agents based on the actual activities they perform, ticket types they handle, skills they use, and duration profiles.

This may reveal, for example:

- Some L1 agents are effectively performing L2 work.
- Some L2 agents mostly handle L1-level tasks.
- Some agents with `Database-SQL` skill are almost never handling DB tickets, despite high demand.

This helps distinguish **official tier labels** from **actual working patterns**.

### 1.4 Skill Utilization Analysis

I would construct a **skill demand vs. supply matrix**:

- Rows: required skills, e.g., `Networking-Firewall`, `Database-SQL`, `App-CRM`.
- Columns: agents.
- Cells: number of tickets requiring the skill and how many were assigned to agents with that skill.

Then I would calculate:

- **Skill match rate** = % of assignments where assigned agent has the required skill.
- **Skill utilisation** = % of an agent’s processing time spent on tickets requiring their documented skills.
- **Over-skilling** = amount of time L2/L3 specialists spend on tickets requiring only `Basic-Troubleshoot` skills.
- **Under-utilisation** = number of tickets requiring a scarce skill that were assigned to an agent without that skill, leading to reassignment.

These metrics show whether specialized skills are being used effectively.

## 2. Identifying Resource-Related Bottlenecks and Issues

Once the log is analyzed, I would pinpoint resource-related issues using a combination of performance mining, queue analysis, and statistical correlation.

### 2.1 Bottlenecks Caused by Skill Shortages

I would identify cases where:

- A ticket requires a skill, but no available agent has that skill.
- The ticket waits in an assignment queue.
- It is eventually assigned to an agent without the skill, who then escalates/reassigns it.
- A later agent with the correct skill completes it.

I would quantify:

- **Average waiting delay caused by skill scarcity.**
- **Number and percentage of SLA breaches occurring when a ticket’s required skill is scarce.**
- **Specific skills with the highest backlog.**

For example, if `Database-SQL` tickets wait twice as long as average and are reassigned more often, this indicates a shortage of agents with that skill.

### 2.2 Delays from Reassignments and Escalations

I would treat each reassignment as a potential source of delay:

1. Time wasted by the initial agent’s partial work.
2. Waiting time while the ticket is in the assignment queue again.
3. Time for the next agent to understand the ticket context.

From the log, I can compute:

- **Number of reassignments per ticket.**
- **Average delay per reassignment**, measured as:
  - Time from previous work end to next work start after reassignment.
- **Percentage of tickets with 2+ reassignments.**
- **Escalation rate** from L1 to L2, and L2 to L3, by category and priority.

I would also identify **“hot potato” variants**, where the same ticket passes through three or more agents before resolution. These variants typically have much higher cycle times and SLA breach rates.

---

### 2.3 Incorrect Initial Assignments

I would flag tickets where:

- The first assigned agent did not have the required skill.
- The first assigned tier was incorrect based on actual resolution tier.
- The ticket was reassigned without any meaningful work being done.

These are **initial assignment errors**.

Quantification would include:

- **% of tickets initially assigned to a wrong skill.**
- **% of tickets escalated because the initial L1 agent lacked knowledge/training.**
- **Average additional cycle time caused by incorrect first assignment.**

---

### 2.4 Overloaded and Underutilized Agents

I would combine workload metrics with performance metrics:

- **Overloaded agents**: long queue length, high number of open tickets, high active time, and high waiting time before starting tickets.
- **Underutilized agents**: low backlog, high idle time, or low ticket count relative to their skill set.

I would compute a **resource load map**—a scatterplot of utilization vs. average handling time. This shows:

- Busy but efficient agents.
- Busy but slow agents.
- Idle but high-skill agents.
- Idle low-skill agents.

This directly addresses the complaint that some agents are overloaded while others are underutilized.

### 2.5 Correlation Between Assignment Patterns and SLA Breaches

I would segment cases by:

- Number of reassignments.
- Skill match at first assignment.
- Tier path (L1-only, L1L2, L1L2L3, L1L2ReassignL3).
- Waiting time at each stage.

Then I would compute SLA breach rates per segment.

Illustrative metrics to extract:

- **SLA breach rate for tickets with no reassignment vs. 1 reassignment vs. 2+ reassignments.**
- **SLA breach rate for tickets where initial agent lacked required skill vs. those where skill matched.**
- **SLA breach rate by assigning dispatcher or assignment pattern.**

This quantifies the operational impact of poor assignment decisions.

## 3. Root Cause Analysis for Assignment Inefficiencies

After identifying the bottlenecks, I would perform a systematic root cause analysis. The event log alone cannot prove human intent, but process mining can strongly indicate likely causes.

### 3.1 Deficiencies in Current Assignment Rules

The current logic is described as:
- Round-robin within tiers.
- Manual escalation decisions.

Process mining would reveal whether the actual assignment sequence follows that logic. For example:

- If many tickets requiring `App-CRM` are assigned to L2 agents without `App-CRM`, this suggests the routing logic ignores required skill.
- If tickets are assigned evenly across agents regardless of skill, the round-robin rule is likely dominant.
- If specific dispatchers consistently assign better matches than others, manual decision-making is inconsistent.

I would use **decision mining** on the `Assign L1`, `Assign L2`, and `Reassign` decisions to see what features actually drive assignments.

Example decision rules might emerge:

- `Category = Network`  always L2 (even if L1 could resolve).
- `Required Skill = Database-SQL`  assigned to next agent in round-robin, not necessarily a DB specialist.
- `Priority = P2`  assigned immediately to first available agent, regardless of match.

These are **assignment rule deficiencies**.

---

### 3.2 Inaccurate or Incomplete Agent Skill Profiles

The event log may show:

- Agents successfully resolving tickets for skills **not listed** in their documented profile.
- Agents listed as having a skill, but tickets assigned to them for that skill are frequently reassigned or escalated—implying **low proficiency** or outdated skill records.
- Some skills are overrepresented or underrepresented in documented profiles compared to actual performance.

I would compare:
- Documented skill profile vs. skills required by tickets that the agent successfully resolves.
- Documented skill profile vs. tickets that the agent fails to resolve.

This provides evidence that skill data must be updated or supplemented with proficiency levels.

---

### 3.3 Poor Initial Ticket Categorization or Skill Requirement Identification

Some tickets are created with a category or required skill that is too generic or incorrect.

For example:
- A ticket is categorized as `Software-App` when the actual issue is a database problem.
- A ticket is marked as requiring `App-CRM`, but later reassignment shows it required `Database-SQL`.

I would use **variant analysis** to compare:

- Tickets with a smooth single-assignment path.
- Tickets with a long reassignment path.

Key attributes like category, required skill, channel, and ticket description text would be compared. If certain categories are overrepresented in reassignment-heavy variants, the initial categorization workflow is likely flawed.

---

### 3.4 Lack of Real-Time Visibility into Agent Workload and Availability

If agents are selected without considering current backlog, process mining would show:

- Tickets assigned to agents who already have many open tickets.
- Long waiting times for those tickets.
- Underutilized agents with open capacity receiving fewer tickets.

A workload analysis at assignment time would reveal whether this is systemic.

I would reconstruct the historical queue state using event-log timestamps, then calculate:

- **How often a ticket was assigned to an agent with 3+ open tickets while an idle agent with the same skill was available.**
- **Average waiting time impact of such assignments.**

This supports the root cause: no real-time workload-aware routing.

---

### 3.5 Insufficient L1 Training or Empowerment

If L1 escalates tickets that L2/L3 resolve quickly with minimal additional work, those tickets may have been **resolvable at L1**.

I would compute:

- **L1 first-contact resolution rate by category.**
- **Escalation rate by L1 agent.**
- **Tickets escalated from L1 and resolved at L2 within a short time**—indicating L1 could have handled them with better documentation/training.

For example:
- 70% of escalated `Software-App` tickets are resolved by L2 in under 10 minutes.
- Some L1 agents resolve these tickets successfully while others always escalate.

This suggests training or knowledge gaps rather than ticket complexity.

## 4. Developing Data-Driven Resource Assignment Strategies

Based on the root causes, I propose four complementary strategies. Each is directly supported by insights from process mining and can be evaluated via simulation before full implementation.

---

### Strategy 1: Skill-Based Routing with Proficiency Scoring

| Item | Description |
|------|-------------|
| **Assignment issue addressed** | Skill mismatch, frequent reassignments, and incorrect tier assignment. |
| **How it leverages process mining** | The log provides the actual skill demand, which agents successfully resolve which skills, and which agents cause rework for certain skills. This can be turned into an **agent proficiency score per skill**. |
| **Data required** | Agent skill profiles; proficiency or certification levels; historical ticket outcomes by agent and required skill; ticket priority and category. |
| **Expected benefits** | Fewer reassignments, higher first-assignment resolution rate, lower average handling time, improved SLA compliance. |

Implementation:
- Replace round-robin with a routing matrix:
  - Match required skill to eligible agents.
  - Filter by tier and priority.
  - Rank by proficiency score and historical success rate.
- If no perfect match exists, route to the nearest skill profile and flag for early escalation.

---

### Strategy 2: Workload-Aware Intelligent Assignment

| Item | Description |
|------|-------------|
| **Assignment issue addressed** | Uneven workload, overloaded agents, underutilized agents, queue delays. |
| **How it leverages process mining** | The log reveals average processing times, current ticket load, and queue length per agent over time. A **workload estimator** can be built from these durations. |
| **Data required** | Real-time agent availability; current open tickets; predicted remaining processing time from historical distributions; agent skills; shift schedules. |
| **Expected benefits** | Balanced workload, reduced waiting times, better utilization of all agents, lower SLA breaches. |

Implementation:
- Assign tickets not to the first available agent, but to the **most suitable agent with the lowest predicted workload**.
- Use this rule:
  - Candidate set = agents with required skill and appropriate tier.
  - Score = predicted remaining work + current queue length + number of active tickets.
  - Choose the agent with the lowest score.
- Re-run the scoring in real time or when a ticket reaches assignment.

This prevents overloaded specialists from receiving more work while low-utilization agents remain idle.

---

### Strategy 3: Predictive Assignment Using Ticket Classification

| Item | Description |
|------|-------------|
| **Assignment issue addressed** | Poor initial categorization, vague required skill, incorrect first assignment. |
| **How it leverages process mining** | Historical logs contain successful assignment paths. By comparing tickets with smooth resolution vs. reassignment-heavy tickets, we can train a classifier to predict required skill, complexity, and optimal tier directly from ticket creation data. |
| **Data required** | Ticket title/description, category, channel, priority, timestamps, historical resolution outcome, final handling agent, required skill labels from completed tickets. |
| **Expected benefits** | Accurate first-time routing, fewer reassignments, shorter cycle time, less reliance on dispatcher intuition. |

Implementation:
- Train a supervised text classification model on historical tickets:
  - Input: ticket category, description text, channel, priority.
  - Output: predicted required skill.
- For each ticket, assign a confidence score.
  - High confidence  auto-route.
  - Low confidence  manual dispatcher review.
- Additionally, predict **ticket complexity**:
  - If historically similar tickets are resolved at L1, route to L1.
  - If not, route directly to L2/L3 specialist.

This reduces the initial assignment error rate at the source.

---

### Strategy 4: Dynamic Tier and Escalation Refinement

| Item | Description |
|------|-------------|
| **Assignment issue addressed** | Excessive L1 escalations, over-qualified specialists doing L1 work, rigid tier boundaries. |
| **How it leverages process mining** | The log shows which L1 agents are successful for which categories, and which L2/L3 agents spend significant time on low-complexity work. It also reveals categories where L1 escalation almost never adds value. |
| **Data required** | Historical L1 resolution rates by agent/category; escalation rates; actual handling times; workload by tier; success rates of L2/L3 agents on escalated tickets. |
| **Expected benefits** | Lower escalation rates, faster resolution, better use of specialists, reduced cost, improved SLA compliance. |

Implementation:
- Use mined data to define a **dynamic escalation matrix**:
  - If an L1 agent has a proven success rate >80% for a given category, encourage resolution before escalation.
  - If historical L1 resolution for that category is <20%, allow immediate L2/L3 routing.
- Build a **cross-tier flexible pool**:
  - L3 specialists may handle complex L2 work when demand spikes.
  - L1 agents with demonstrated L2 skill proficiency can be temporarily promoted during overload periods.
- Re-train the escalation model regularly using process mining results.

This optimizes the **right level** of support, not just the official tier.

## 5. Simulation, Implementation, and Monitoring

### 5.1 Business Process Simulation for Before/After Evaluation

Before changing the live routing system, I would use **process simulation** to test proposed strategies.

#### Build the As-Is Simulation Model
- Use the discovered process model as the baseline.
- Calibrate with:
  - Ticket arrival rates by priority/category.
  - Activity durations by tier and skill.
  - Queue and waiting distributions.
  - Agent availability patterns.
  - Current routing logic (round-robin + manual escalation).

Run the simulation and compare its output with historical performance. If the simulation reproduces SLA rates, reassignment counts, and utilization close to actual, it is reliable.

#### Define To-Be Scenarios
Then I would simulate:

1. **Skill-based routing only**.
2. **Skill-based + workload-aware routing**.
3. **Predictive classification + skill-based + workload-aware routing**.
4. **Dynamic escalation + cross-tier staffing**.

For each scenario, I would vary:

- Ticket volume.
- Priority mix.
- Absence rates.
- Skill shortages.

Metrics compared:

- SLA compliance by priority.
- Average cycle time.
- Reassignment rate.
- Agent utilization.
- Queue lengths.
- Bottleneck waiting times.

This allows TechSolve to choose the best strategy with evidence rather than guesswork.
