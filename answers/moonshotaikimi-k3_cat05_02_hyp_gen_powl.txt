## 1. Anomaly Identification

The ideal flow is a strict sequence **R  A  E  P  N  C**. The POWL model deviates in several ways:

**A1 — Approval is optional (loop semantics).** `LOOP(children=[E, P])` has POWL loop semantics: execute the *do* part `E`, then either exit or execute the *redo* part `P` and loop back to `E`. The **minimal trace of the loop is just `E`** — a claim can pass through the loop without ever being approved.

**A2 — Repeated evaluations and approvals.** The loop permits `E, E-P-E, E-P-E-P-E, …`, so a claim can be evaluated and approved an arbitrary number of times, contradicting the single-approval ideal.

**A3 — Approval is never the final step of the loop.** Because `P` is the redo part, every occurrence of `P` is necessarily followed by another `E`. The loop always ends with `E`, i.e., an approval is *always* re-evaluated — there is no "final approval" state.

**A4 — Customer notification is skippable.** `XOR(N, skip)` with a `SilentTransition` lets a claim complete with no notification at all.

**A5 — Premature closure (partial-order anomaly).** The edge `A  C` is added, but there is **no edge `xor  C`** (and no `loop  C`). Transitive closure gives `R < A < loop < xor` plus `A < C`, leaving `C` **unordered (concurrent) with respect to both the loop and the XOR**. So `C` can fire at any point after assignment.

**A6 — Out-of-order notification.** Because `C` and `xor` are concurrent, `N` may also occur *after* `C` — notifying a customer about an already-closed claim.

Concretely, all of the following are valid traces of the model:

| Trace | Why it's anomalous |
|---|---|
| `R A C` | Closed immediately after assignment — no evaluation, approval, or notification |
| `R A E C` | Closed after evaluation, never approved, never notified |
| `R A E N C` | Never approved |
| `R A E P E C` | Approved once, but always re-evaluated; never notified |
| `R A E C N` | Customer notified *after* closure |
| `R A E P E P E N C` | Multiple approvals for a single claim |

The only model-conformant trace resembling the ideal is `R A E P E N C`, and even it contains a spurious trailing evaluation.

---

## 2. Hypotheses for Root Causes

**H1 — Business rule changes, partially implemented**
- A "rework/appeal" requirement (re-evaluate after approval, e.g., for QA audit or disputed claims) was encoded as a loop, but no exit condition, iteration cap, or distinct activity labels were added (A1–A3).
- A policy change made notification optional (e.g., "notify only on denial," or notification moved to an external CRM), implemented as the silent XOR branch without updating process documentation (A4).
- A "fast-track" rule for small claims (close right after assignment) was requested, and the modeler added the `A  C` edge but forgot to guard it with a condition on `claim_amount` (A5).

**H2 — Miscommunication between departments**
- The modeling team misunderstood POWL loop semantics, believing `LOOP(E, P)` means "E then optionally P," when it actually means "E, optionally redo via P" (A1, A3).
- The claims department assumes approval is mandatory and notification is always logged; the IT/workflow team built in a skip path assuming notifications are handled by phone/email outside the system (A4).
- The closure step may be owned by a different team (back office) whose system triggers closure independently of the adjusters' evaluation workflow — mirrored in the model as concurrency between `C` and the loop (A5, A6).

**H3 — Technical errors in the workflow system**
- A misconfigured state machine enables the "Close" button as soon as an adjuster is assigned (A5).
- Retry/idempotency bugs generate duplicate `P` or `E` events (A2).
- Event-driven integration fires `N` asynchronously, occasionally after closure (A6).

**H4 — Inadequate constraints in the modeling tool**
- The modeler may have intended a sequence but drew only the edges they remembered; the tool doesn't flag that `C` is not ordered after `xor`, or that the loop permits zero approvals.
- The silent transition may have been a "to be implemented" placeholder that was never replaced.

**H5 — Deliberate circumvention (worth ruling out)**
- Premature closure paths could be exploited to close claims without payout scrutiny; repeated approvals could mask duplicate payments. These should show up as resource- or region-specific patterns.

## 3. Verification via Database Queries

Notes: `"timestamp"` is quoted because `timestamp` is a reserved word in PostgreSQL. Activity codes (`'R'`, `'A'`, `'E'`, `'P'`, `'N'`, `'C'`) may need to be replaced with full labels (`'Receive Claim'`, …) depending on how events are logged.

**Shared per-claim summary CTE** (used by most queries below):

```sql
WITH claim_summary AS (
  SELECT
    ce.claim_id,
    MIN(ce."timestamp") FILTER (WHERE ce.activity = 'E') AS first_eval,
    MIN(ce."timestamp") FILTER (WHERE ce.activity = 'P') AS first_approval,
    MIN(ce."timestamp") FILTER (WHERE ce.activity = 'N') AS first_notify,
    MAX(ce."timestamp") FILTER (WHERE ce.activity = 'N') AS last_notify,
    MIN(ce."timestamp") FILTER (WHERE ce.activity = 'C') AS first_close,
    COUNT(*) FILTER (WHERE ce.activity = 'E') AS eval_count,
    COUNT(*) FILTER (WHERE ce.activity = 'P') AS approval_count,
    COUNT(*) FILTER (WHERE ce.activity = 'N') AS notify_count,
    COUNT(*) FILTER (WHERE ce.activity = 'C') AS close_count
  FROM claim_events ce
  GROUP BY ce.claim_id
)
```

**Q1 — Variant discovery (general conformance check).** Reconstruct each claim's trace and compare against the ideal `R->A->E->P->N->C`:

```sql
WITH traces AS (
  SELECT claim_id,
         STRING_AGG(activity, '->' ORDER BY "timestamp", event_id) AS variant
  FROM claim_events
  GROUP BY claim_id
)
SELECT variant,
       COUNT(*) AS claims,
       ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) AS pct
FROM traces
GROUP BY variant
ORDER BY claims DESC;
```

**Q2 — Claims closed without proper evaluation or approval (tests A1, A5):**

```sql
SELECT s.claim_id, c.claim_amount, c.claim_type, s.first_close
FROM claim_summary s
JOIN claims c ON c.claim_id = s.claim_id
WHERE s.first_close IS NOT NULL
  AND (s.first_eval IS NULL          -- never evaluated
    OR s.first_approval IS NULL      -- never approved
    OR s.first_close < s.first_eval      -- closed before evaluation
    OR s.first_close < s.first_approval); -- closed before approval
```

**Q3 — Claims approved (or evaluated) multiple times (tests A2):**

```sql
SELECT s.claim_id, s.eval_count, s.approval_count, c.claim_amount
FROM claim_summary s
JOIN claims c ON c.claim_id = s.claim_id
WHERE s.approval_count > 1 OR s.eval_count > 1
ORDER BY s.approval_count DESC, s.eval_count DESC;

-- Distribution view: how common is each approval count?
SELECT approval_count, COUNT(*) AS claims
FROM claim_summary
GROUP BY approval_count
ORDER BY approval_count;
```

**Q4 — The redo pattern `P  E` (tests A3 — is approval always followed by re-evaluation?):**

```sql
WITH ordered AS (
  SELECT claim_id, activity,
         LAG(activity) OVER (PARTITION BY claim_id ORDER BY "timestamp", event_id) AS prev_act
  FROM claim_events
)
SELECT COUNT(DISTINCT claim_id) AS claims_with_P_then_E
FROM ordered
WHERE activity = 'E' AND prev_act = 'P';
```

**Q5 — Notification skip rate (tests A4), overall and by segment:**

```sql
SELECT c.claim_type,
       COUNT(*) AS closed_claims,
       COUNT(*) FILTER (WHERE s.notify_count = 0) AS not_notified,
       ROUND(100.0 * COUNT(*) FILTER (WHERE s.notify_count = 0) / COUNT(*), 2) AS pct_skipped
FROM claim_summary s
JOIN claims c ON c.claim_id = s.claim_id
WHERE s.close_count > 0
GROUP BY c.claim_type
ORDER BY pct_skipped DESC;
```

**Q6 — Notification after closure (tests A6):**

```sql
SELECT s.claim_id, s.first_close, s.last_notify
FROM claim_summary s
WHERE s.last_notify > s.first_close;
```

**Q7 — Who performs premature closes (discriminates H2/H3/H5 — human vs. system, localized vs. widespread):**

```sql
WITH premature AS (
  SELECT claim_id FROM claim_summary
  WHERE first_close IS NOT NULL
    AND (first_eval IS NULL OR first_close < first_eval)
)
SELECT ce.resource, a.region, a.specialization,
       COUNT(*) AS premature_close_events,
       COUNT(DISTINCT ce.claim_id) AS affected_claims
FROM claim_events ce
JOIN premature p ON p.claim_id = ce.claim_id
LEFT JOIN adjusters a ON a.name = ce.resource   -- resource may be a name or 'SYSTEM'
WHERE ce.activity = 'C'
GROUP BY ce.resource, a.region, a.specialization
ORDER BY premature_close_events DESC;
```

**Q8 — When did anomalies start (tests H1/H3 — rule change or system migration):**

```sql
SELECT DATE_TRUNC('month', c.submission_date) AS month,
       COUNT(*) AS claims,
       COUNT(*) FILTER (
         WHERE s.first_close IS NOT NULL
           AND (s.first_eval IS NULL OR s.first_close < s.first_eval)
       ) AS premature_closes,
       COUNT(*) FILTER (WHERE s.close_count > 0 AND s.notify_count = 0) AS no_notification,
       COUNT(*) FILTER (WHERE s.approval_count > 1) AS multi_approval
FROM claims c
JOIN claim_summary s ON s.claim_id = c.claim_id
GROUP BY 1
ORDER BY 1;
```

**Q9 — Fast-track hypothesis (tests H1: are premature closes mostly small claims?):**

```sql
SELECT CASE
         WHEN s.first_close IS NOT NULL
          AND (s.first_eval IS NULL OR s.first_close < s.first_eval)
         THEN 'premature_close' ELSE 'standard' END AS path,
       COUNT(*) AS claims,
       AVG(c.claim_amount) AS avg_amount,
       percentile_cont(0.5) WITHIN GROUP (ORDER BY c.claim_amount) AS median_amount
FROM claims c
JOIN claim_summary s ON s.claim_id = c.claim_id
GROUP BY 1;
```

**Q10 — Context in free-text fields (tests H1 — is the loop legitimate rework?):**

```sql
SELECT activity, additional_info, COUNT(*) AS events
FROM claim_events
WHERE activity IN ('E', 'P') AND additional_info IS NOT NULL
GROUP BY activity, additional_info
ORDER BY events DESC;
```

## Interpreting the Results

| Observation in data | Hypothesis supported |
|---|---|
| Anomaly rates jump at a specific date (Q8) | H1 rule change or H3 system migration |
| Premature closes concentrated in one resource/region (Q7) | H2 miscommunication/training, or H5 circumvention |
| Premature closes have systematically lower `claim_amount` (Q9) | H1 deliberate fast-track, missing its guard condition |
| `PE` pairs carry `additional_info` like "appeal"/"rework" (Q10) | H1 legitimate rework loop, poorly modeled |
| Duplicate approvals with near-identical timestamps, resource = `SYSTEM` (Q3, Q7) | H3 retry/idempotency bug |
| Notification skips uniform across all claim types and time (Q5, Q8) | H1/H4 notification intentionally optional or placeholder never fixed |
| Skips cluster by `claim_type` or adjuster specialization (Q5, Q7) | H2 department-specific practice |

Together, the variant table (Q1) gives the overall conformance rate, while Q2–Q6 confirm whether the model's anomalous traces actually occur in production, and Q7–Q10 discriminate among the candidate root causes.
