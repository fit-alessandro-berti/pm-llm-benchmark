# 1. Process Discovery and Conformance Checking

## 1.1 Build an integrated event log

The first step is to create a reliable event log that represents both the operational route and the lifecycle of each package. A single case definition is unlikely to be sufficient, because Speedy Parcels has several related process perspectives.

### Recommended case and object structure

A useful design is an object-centric event log with the following objects:

- **Vehicle-day:** one vehicle operating on one date, such as `V12-20241205`
- **Route or trip:** the dispatch assignment for that vehicle-day
- **Stop:** a planned or actual customer visit
- **Package:** the individual parcel
- **Driver:** the assigned driver
- **Maintenance episode:** a scheduled or unscheduled maintenance event

This supports two complementary process views:

1. **Vehicle-day view:** depot departure, travel, customer stops, unplanned stops, maintenance, return to depot, and overtime.
2. **Package view:** assigned, loaded, attempted, successfully delivered, failed, reattempted, and finally completed or returned.

Using only `Vehicle-Day` as the case ID could cause problems. For example, all 35 package deliveries would be placed in one case, making package-level behavior difficult to analyze. Conversely, using only `Package ID` would lose the route-level context. An object-centric approach, or at least linked vehicle-day and package event logs, is preferable.

### Common event schema

Each event should contain fields such as:

| Field | Example |
|---|---|
| Case/object IDs | Vehicle-day, route, stop, package |
| Activity | Depart Depot, Travel Leg, Arrive Customer, Delivery Success |
| Event timestamp | Local time standardized to a common timezone |
| Start and end time | For travel, service, and maintenance episodes |
| Vehicle and driver | V12, D105 |
| Location | Coordinates and matched geofence or road segment |
| Planned attributes | Planned sequence, ETA, time window |
| Actual attributes | Actual sequence, arrival time, departure time |
| Source system | GPS, scanner, dispatch, maintenance |
| Data quality flag | High, medium, or low confidence |
| Exception information | Failed delivery reason, warning light, traffic event |

### Source-specific processing

#### GPS data

GPS records are normally too granular to be used directly as process activities. The raw points should be:

- Time-normalized and sorted by vehicle.
- Map-matched to the road network where possible.
- Assigned to depot, customer, maintenance, or other geofences.
- Aggregated into meaningful movement episodes.
- Used to derive events such as:
  - Depart depot
  - Travel from stop A to stop B
  - Arrive at customer geofence
  - Vehicle stopped
  - Long idle
  - Traffic or congestion episode
  - Unplanned detour
  - Return to depot

A “low speed detected” event should not automatically be treated as a process activity. It may represent congestion, parking, a maneuver, or poor GPS quality. A more meaningful event could be “traffic delay episode,” defined using speed, road segment, duration, and comparison with expected or free-flow speed.

#### Scanner data

Scanner events provide the strongest evidence of delivery milestones:

- Arrive Customer
- Delivery Success
- Delivery Failed
- Depart Customer
- Reattempt
- Return to depot, if applicable

The event definitions need to be standardized. For example, an “Arrive Customer” scan may occur after the driver has parked, while GPS may indicate arrival at the address several minutes earlier. That discrepancy should be retained as a measurable interval rather than silently corrected.

#### Dispatch data

Dispatch data should provide:

- Planned stop sequence
- Planned arrival and departure times
- Customer time windows
- Assigned vehicle and driver
- Package list
- Vehicle capacity
- Route version and any subsequent route updates

The route version is important. If dispatch dynamically changes the route during the day, the revised plan should be retained. Otherwise, an authorized change may incorrectly appear as a process deviation.

#### Maintenance data

Maintenance records should be linked to the vehicle-day and, where possible, to the route and GPS location. They should distinguish:

- Scheduled maintenance before or after a shift
- Unscheduled repair during a route
- Warning-light or fault episode
- Tow or recovery
- Vehicle replacement

The duration between maintenance start and end should be represented explicitly, and the operational impact should be measured as both direct downtime and downstream delivery delay.

### Data quality and integration challenges

Important challenges include:

- Different clocks, time zones, and timestamp precision.
- GPS drift, missing points, or inaccurate customer geocoding.
- Duplicate scanner events or late-uploaded scans.
- Missing “Depart Customer” or “Arrive Customer” events.
- Different definitions of arrival across GPS, scanner, and dispatch.
- A vehicle being assigned to a route but being replaced during the day.
- Driver changes during a shift.
- Multiple packages being delivered at the same customer address.
- Failed deliveries that are followed by a later successful attempt.
- Maintenance records that overlap with GPS activity.
- Inconsistent vehicle, driver, and package identifiers.
- Planned routes that contain stops which were subsequently cancelled.
- Event ordering issues caused by delayed mobile synchronization.

The integrated log should preserve the original source event and add a confidence or provenance field. A missing scanner event should not automatically be interpreted as a failed operational step; it may be a data capture problem.

## 1.2 Discover the actual delivery process

After cleaning the data, process discovery can be applied to reveal what actually happens rather than what is assumed to happen.

A high-level discovered vehicle-day process may look like:

```text
Start Shift
   -> Route Assigned
   -> Load/Prepare
   -> Depart Depot
   -> Travel
   -> Arrive Customer
   -> Delivery Success
   -> Depart Customer
   -> Travel
   -> Arrive Customer
   -> Delivery Failed
   -> Reattempt or Continue
   -> Unplanned Stop / Maintenance
   -> Travel
   -> Arrive Depot
   -> End Shift
```

The actual model may reveal:

- Repeated visits to the same customer.
- Deliveries occurring out of planned sequence.
- Long idle periods between arrival and delivery scan.
- Stops without a corresponding package event.
- Customer arrivals after the promised window.
- Unplanned maintenance loops.
- Routes ending in overtime.
- Vehicles returning to the depot before all packages are delivered.
- Packages delivered by a different vehicle or driver than planned.

### Suitable discovery techniques

Several process mining techniques can be used:

- **Directly-Follows Graphs:** useful for an initial overview of frequent transitions.
- **Heuristic Miner:** useful when the data contains noise, missing events, and infrequent exceptions.
- **Inductive Miner:** useful for producing sound process models and identifying loops such as failed delivery followed by reattempt.
- **Process trees or Petri nets:** useful when a formal, executable model is required.
- **Performance-enhanced process models:** overlay average and percentile durations on each activity and transition.
- **Geospatial process visualization:** display route variants, detours, traffic hotspots, and unplanned stops on a map.
- **Object-centric process mining:** analyze how packages, vehicles, drivers, and maintenance episodes interact.

The model should initially be filtered to avoid a “spaghetti model.” For example, it may be useful to show the most common 80–90% of behavior and analyze rare exceptions separately.

## 1.3 Conformance checking against planned routes

The planned route should be transformed into a planned event structure. If dispatch only provides a sequence of customer IDs and planned ETAs, planned travel legs can be generated using a routing engine or road-network estimates.

The planned and actual processes can then be compared using alignment-based conformance checking.

### Deviations to identify

#### Sequence deviations

- Customer stop visited earlier or later than planned.
- Stops visited in a different order.
- Planned stops skipped.
- Unplanned stops inserted.
- Repeated visits to a customer.
- A package delivered from another route.
- A route ending before all planned packages are completed.

#### Timing deviations

- Late departure from the depot.
- Excessive time between route assignment and departure.
- Travel time significantly longer than planned.
- Arrival outside the customer time window.
- Excessive service time.
- Late return to the depot.
- Overtime caused by accumulated delay.

#### Resource deviations

- Wrong vehicle or driver used.
- Vehicle capacity exceeded.
- Vehicle changes during a route.
- Unscheduled maintenance using the assigned vehicle.
- Driver working beyond planned or permitted hours.

#### Exception deviations

- Unplanned repair or warning-light stop.
- Traffic detour.
- Failed delivery attempt.
- Customer unavailable.
- Address or access issue.
- Return to depot before route completion.

Conformance results can be expressed as:

- Percentage of routes fully compliant with the plan.
- Average number of inserted, skipped, or reordered stops.
- Average planned-versus-actual arrival deviation.
- Total minutes of delay attributable to each deviation type.
- Alignment cost by route, driver, vehicle, depot, or time period.

It is important to distinguish between:

- **Unacceptable deviations**, such as avoidable route violations.
- **Necessary deviations**, such as an authorized real-time reroute.
- **Data deviations**, such as a missing scanner event.

# 2. Performance Analysis and Bottleneck Identification

## 2.1 Key performance indicators

The following KPIs should be calculated at package, stop, route, vehicle, driver, depot, and daily levels.

### On-Time Delivery Rate

For a delivery with a promised window \([W_s, W_e]\):

\[
OTD = \frac{\text{Deliveries completed within the promised window}}{\text{Deliveries due}}
\]

The company should define whether “on time” means:

- Arrival at the customer;
- Successful delivery scan;
- Departure after successful delivery; or
- Any time within the promised window.

The definition should be consistent and reported separately if necessary. A package that arrives on time but is delivered late because of a long service interaction should not be indistinguishable from a package that arrived late due to traffic.

Useful variants include:

- On-time arrival rate.
- On-time completion rate.
- Early delivery rate.
- Late delivery rate by delay band, such as 1–15, 16–30, and more than 30 minutes.

### Average Time per Delivery Stop

For a stop:

\[
StopTime_i = DepartureTime_i - ArrivalTime_i
\]

Report the mean, median, and P90 or P95. The percentile is especially important because a small number of long stops may create much of the route delay.

Service time should be separated into:

- Parking or access time.
- Time waiting to gain access.
- Customer interaction and handover.
- Scanning or administrative time.
- Departure preparation.

### Travel Time versus Service Time

For a route:

\[
TravelServiceRatio =
\frac{\text{Travel time}}{\text{Customer service time}}
\]

Travel time should be measured from departure from one stop to arrival at the next, while service time is measured between customer arrival and departure.

This helps distinguish:

- Poor route geometry or congestion;
- Excessive dwell time at customers;
- Depot or loading delays;
- Idle time unrelated to either travel or delivery.

### Fuel Consumption

If direct fuel or telematics data is available:

\[
FuelPerKm = \frac{\text{Fuel consumed}}{\text{Distance traveled}}
\]

\[
FuelPerPackage = \frac{\text{Fuel consumed on route}}{\text{Packages delivered}}
\]

If the current data does not contain fuel consumption, an estimate can be built using:

- GPS distance;
- Idling duration;
- Speed profile;
- Vehicle type;
- Engine and fuel model;
- Traffic and stop frequency.

These estimates should be clearly labeled as estimates until validated against fuel-card or vehicle telemetry data.

### Vehicle Utilization

Possible definitions include:

\[
VehicleUtilization =
\frac{\text{Time vehicle is actively assigned and operating}}{\text{Available shift time}}
\]

Other useful measures include:

- Kilometers per vehicle-day.
- Packages delivered per vehicle-hour.
- Productive stop time divided by total route time.
- Capacity utilization:

\[
CapacityUtilization =
\frac{\text{Loaded volume or weight}}{\text{Vehicle capacity}}
\]

High vehicle utilization is not automatically desirable if it causes excessive overtime or poor service reliability. Utilization should therefore be viewed together with on-time performance and safety.

### Traffic Delay

For each travel leg:

\[
TrafficDelay_i =
ActualTravelTime_i - ExpectedTravelTime_i
\]

Expected travel time should ideally be based on the same road segment, time of day, day of week, and traffic conditions. A free-flow baseline may be used as a second comparison.

Additional measures include:

- Percentage of route time spent in congestion.
- Number and duration of low-speed episodes.
- Traffic delay by road segment and time of day.
- Delay propagation from one late stop to subsequent stops.

### Failed Delivery Rate

\[
FailedDeliveryRate =
\frac{\text{Failed delivery attempts}}{\text{Total delivery attempts}}
\]

This should be segmented by reason:

- Customer not home.
- Incorrect or inaccessible address.
- Business closed.
- Customer refusal.
- Damaged or missing parcel.
- Driver or process error.

Also measure:

- Reattempt rate.
- Cost and time of reattempts.
- Percentage of failed attempts eventually successful.
- Additional kilometers caused by reattempts.
- On-time performance impact of inserting reattempts into later routes.

### Additional useful KPIs

- Depot departure delay.
- Route adherence percentage.
- Planned versus actual route distance.
- Overtime minutes per route.
- Unscheduled maintenance events per 1,000 vehicle-hours.
- Maintenance downtime per vehicle.
- Packages delivered per driver-hour.
- First-attempt delivery success rate.
- Percentage of routes completed within working-hour limits.
- Average and P95 end-to-end package lead time.
- Scan completeness and event data quality.

## 2.2 Bottleneck analysis

Process mining can identify bottlenecks by combining process structure, timestamps, resources, and context.

### Performance overlays

A performance-enhanced process model can show:

- Average and P90 duration for each activity.
- Average waiting time between activities.
- Frequency of each transition.
- Percentage of cases experiencing a transition.
- Number of late deliveries after a particular activity.

For example, the transition from “Arrive Customer” to “Delivery Success” may have a high P95 duration, indicating customer service or access problems.

### Variant analysis

Routes can be grouped by:

- Planned stop sequence.
- Depot.
- Route area.
- Number of packages.
- Driver.
- Vehicle type.
- Day of week.
- Departure time.
- Customer mix.
- Traffic conditions.

The high-performing and low-performing variants can then be compared for travel time, service time, failed deliveries, and overtime.

### Process cubes and drill-downs

A process cube can slice the process by dimensions such as:

- Route ID.
- Driver ID.
- Vehicle age and type.
- Customer neighborhood.
- Hour of day.
- Weather or traffic condition.
- Delivery window.
- Package count.
- Maintenance status.

This helps answer questions such as:

- Are late deliveries concentrated on a particular route family?
- Does the first route departure after 8:00 have disproportionately poor performance?
- Are certain vehicle types associated with higher idle fuel use?
- Do particular customer areas produce excessive parking time?

### Bottleneck quantification

The effect of a bottleneck can be quantified using:

\[
ExcessTime =
ObservedTime - BenchmarkTime
\]

For a stop or route, the benchmark might be the median or the 25th percentile for comparable conditions.

Then calculate:

\[
TotalImpact =
ExcessTime \times NumberOfAffectedEvents
\]

For example, if a route has 12 minutes of excess service time over 20 stops, that produces 240 minutes of potential route delay, although some of the delay may be absorbed by schedule slack.

The analysis should distinguish:

- **Direct delay:** time spent in the bottleneck.
- **Propagated delay:** additional lateness caused at later stops.
- **Cost impact:** additional labor, fuel, overtime, and reattempt cost.
- **Customer impact:** affected packages and time-window failures.

A critical-path view is particularly useful. A 10-minute delay on a route with substantial spare capacity may have little customer impact, while a 10-minute delay early in a tightly scheduled route may cause multiple late deliveries.

# 3. Root Cause Analysis for Inefficiencies

Finding that a route is late is not sufficient. Process mining should be combined with operational and statistical analysis to determine why it is late.

## 3.1 Suboptimal route planning

### Possible evidence

- Actual distance consistently exceeds planned distance.
- Frequent stop reordering.
- Repeated backtracking on the map.
- Low route adherence on particular route families.
- High travel time despite low traffic.
- Packages assigned to geographically distant clusters.
- Reattempts being inserted inefficiently.

### Analysis

Compare planned and actual stop sequences using alignment cost and geographic distance. Calculate:

- Planned versus actual distance.
- Planned versus actual travel time.
- Number of route crossings or backtracking movements.
- Area compactness of each route.
- Delay by planned stop position.

A variant analysis can compare routes with similar package counts and delivery windows. If some route variants consistently perform better, their sequence or territory design can provide a benchmark.

## 3.2 Inaccurate travel-time estimates

A planned ETA may be based on a generic average and may not account for:

- Time of day.
- Day of week.
- School or business traffic.
- Parking difficulty.
- Road restrictions.
- Seasonal conditions.
- Urban versus suburban road characteristics.

Compare actual travel times with planned estimates by road segment, hour, and weekday. Persistent positive error indicates that the planning model is systematically optimistic.

The analysis should distinguish travel time from parking and access time. A route may appear to have a travel-time problem when the actual issue is that drivers cannot park close to the delivery address.

## 3.3 Traffic congestion

GPS-derived speed profiles can identify:

- Repeated low-speed segments.
- Time-of-day traffic patterns.
- Congestion that starts before a route enters a particular area.
- Delays that propagate across later stops.

The best analysis combines GPS data with external traffic data or historical road-speed data. Correlation can be examined between traffic delay and:

- Delivery lateness.
- Route departure time.
- Stop sequence.
- Road segment.
- Weather and weekday.

Traffic should not be assumed to be the root cause merely because a vehicle recorded low speed. A vehicle moving at 5 km/h may be in a traffic jam, searching for parking, or moving through a pedestrian zone. Location and duration are needed to distinguish these cases.

## 3.4 Variability in customer service time

Measure:

\[
ServiceTime =
DeliveryEventTime - ArrivalEventTime
\]

and, where possible:

\[
AccessTime =
GPSStopTime - GPSArrivalAtCustomerArea
\]

Large service-time variation may be caused by:

- Multiple packages at one address.
- Apartment access.
- Business reception procedures.
- Signature or identity checks.
- Cash-on-delivery processes.
- Inadequate delivery instructions.
- Large or heavy parcels.
- Poor scanner usability.

Compare service time by customer, building, delivery type, number of packages, driver, and time of day. High P95 service time is often more operationally important than the average.

## 3.5 Vehicle breakdowns and maintenance

Link maintenance episodes to:

- Vehicle age and mileage.
- Prior warning or diagnostic events.
- Route duration.
- Temperature or operating conditions.
- Previous maintenance history.
- Driver-reported defects.

Compare vehicles with and without unscheduled stops. Useful measures include:

- Unscheduled stops per 1,000 km.
- Average route delay caused by each fault type.
- Number of affected deliveries.
- Overtime and recovery cost.
- Probability of a breakdown following a known warning pattern.

The example route has an unscheduled stop for an engine warning at 11:05. The analysis should determine whether this was an isolated event or part of a recurring pattern for V12 or a particular vehicle class.

## 3.6 Driver behavior and skill differences

Process mining can identify differences in:

- Depot preparation and departure delay.
- Route adherence.
- Idle duration.
- Average travel speed by road type.
- Service time.
- Failed delivery rate.
- Scan completeness.
- Frequency of unplanned stops.
- Overtime.

However, driver comparisons must control for context. A driver assigned to difficult urban routes should not be directly compared with one assigned to easy suburban routes. Comparison should use matched routes, similar package counts, customer mix, traffic conditions, and vehicle types.

The analysis should be used for coaching and process improvement rather than unsupported individual blame. Some apparent “driver behavior” may be caused by poor route plans, vehicle defects, or difficult delivery locations.

## 3.7 Failed delivery attempts

Failed deliveries should be analyzed as a separate process loop:

```text
Assigned
 -> Attempted
 -> Failed
 -> Replanned or Reattempted
 -> Successful or Returned
```

Compare failure rates by:

- Customer and address.
- Time window.
- Day of week.
- Driver.
- Delivery area.
- Delivery type.
- Notification status.
- Package size.
- Previous delivery history.

If “customer not home” failures are concentrated in narrow delivery windows, pre-delivery communication, better time-window design, or pickup alternatives may be more effective than simply asking drivers to drive faster.

A key distinction is whether the failure is caused by customer availability or operational execution. This can be validated by comparing failure rates for the same customer across different routes and drivers.

# 4. Data-Driven Optimization Strategies

The following strategies are complementary and should be implemented in stages, using process mining as the baseline and monitoring mechanism.

## Strategy 1: Dynamic, traffic-aware route reoptimization

### Targeted inefficiency

- Traffic-related travel delay.
- Route lateness propagating from early stops.
- Excessive detours and backtracking.
- Routes that become infeasible after an incident or maintenance event.

### Root cause addressed

Static route plans may use average travel times and cannot respond to real-time congestion, road closures, or unexpected delays.

### Proposed approach

Implement rolling route reoptimization using:

- Current GPS position.
- Traffic data.
- Remaining packages.
- Customer time windows.
- Current service-time estimates.
- Vehicle capacity.
- Driver hours and break constraints.
- Priority or service-level commitments.

Reoptimization should not constantly change the route. Use operational rules such as:

- Freeze the next one or two stops.
- Recalculate only when predicted lateness exceeds a threshold.
- Reoptimize after a major incident, breakdown, or failed delivery.
- Preserve customer commitments and route familiarity where possible.

### Process mining support

Use conformance and performance analysis to identify:

- Road segments with repeated delay.
- Route positions at which lateness begins.
- Routes that become infeasible under normal traffic.
- The number of minutes that could have been saved by alternative sequences.

### Expected KPI impact

- Higher on-time delivery rate.
- Lower traffic delay.
- Lower excess route distance.
- Lower fuel per kilometer and per package.
- Reduced overtime.
- Fewer failed deliveries caused by arrival outside the customer window.

---

## Strategy 2: Redesign territories, stop sequences, and travel-time estimates

### Targeted inefficiency

- Repeated route backtracking.
- Poor geographic clustering.
- Overloaded routes.
- Systematically optimistic planned ETAs.
- Excessive variation between routes serving similar areas.

### Root cause addressed

Historical plans may be based on fixed territories or simple geographic allocation without considering actual service times, parking difficulty, or time-window feasibility.

### Proposed approach

Use historical process data to create more robust route plans:

1. Cluster customers using actual travel times rather than straight-line distance alone.
2. Incorporate historical service times by customer or building type.
3. Use time-dependent travel-time matrices.
4. Place difficult or highly time-sensitive stops earlier where appropriate.
5. Add route-specific buffers based on P80 or P90 travel and service times.
6. Separate high-failure customers or difficult access locations for special handling.
7. Balance routes using total expected workload, not just package count.

An important design principle is to avoid optimizing solely for the shortest distance. A slightly longer route with lower parking and service-time variability may produce better punctuality and lower total cost.

### Process mining support

Compare high-performing route variants with low-performing variants having similar volumes. Identify:

- Sequences with lower delay propagation.
- Route areas that produce repeated lateness.
- Customers with consistently high dwell times.
- Planned stops whose actual time requirements are systematically underestimated.

### Expected KPI impact

- Higher route adherence.
- Lower travel time and distance.
- Lower P90 stop and route duration.
- Improved on-time delivery.
- Reduced overtime.
- More predictable driver workloads.

---

## Strategy 3: Reduce failed deliveries through customer communication and time-window management

### Targeted inefficiency

- Customer-not-home failures.
- Reattempt mileage and labor.
- Late deliveries caused by inserting reattempts into already busy routes.

### Root cause addressed

Customer availability may not match the assigned delivery window, or customers may lack accurate delivery information.

### Proposed approach

Use historical delivery outcomes to identify high-risk deliveries and apply targeted interventions:

- Send a pre-delivery notification with a narrower ETA.
- Allow customers to confirm, change, or redirect the delivery.
- Offer lockers, pickup points, safe-place delivery, or neighbor delivery where appropriate.
- Assign more realistic time windows.
- Schedule high-risk deliveries during periods with better historical success.
- Give drivers better access instructions and contact information.
- Use a second attempt policy that avoids inefficient route insertion.

A predictive model can estimate failure risk using customer history, time window, building type, weekday, and delivery area. That prediction should drive operational actions rather than merely produce a report.

### Process mining support

Analyze the package lifecycle and identify:

- Customers with repeated failure loops.
- Time windows associated with high failure rates.
- The additional time and distance generated by reattempts.
- Whether failures occur disproportionately on particular route positions.
- Whether proactive customer contact reduces failure rates.

### Expected KPI impact

- Higher first-attempt success rate.
- Lower failed delivery rate.
- Lower reattempt kilometers and fuel.
- Fewer late deliveries caused by reattempts.
- Lower customer service and redelivery costs.

---

## Strategy 4: Predictive maintenance and vehicle assignment

### Targeted inefficiency

- Unscheduled route stops.
- Breakdown-related delays.
- Vehicle replacement and route disruption.
- Excess fuel use due to poor vehicle condition.

### Root cause addressed

Maintenance may be scheduled by calendar rather than actual usage, vehicle condition, fault history, or predicted failure risk.

### Proposed approach

Build a vehicle health and maintenance model using:

- Vehicle age and mileage.
- Previous faults.
- Warning-light events.
- Unscheduled stop patterns.
- Route kilometers and operating hours.
- Idle and harsh operating behavior, if available.
- Maintenance completion history.

Use this model to:

- Schedule maintenance before high-risk shifts.
- Avoid assigning high-risk vehicles to long or time-critical routes.
- Keep reserve vehicles available during high-risk periods.
- Group maintenance with existing depot downtime.
- Trigger inspection after specific warning patterns.

### Process mining support

Compare vehicle-day traces before and after maintenance events. Identify whether a warning event commonly precedes:

- A route interruption.
- A long idle period.
- Reduced speed.
- An unscheduled return to depot.
- Significant overtime or missed deliveries.

### Expected KPI impact

- Fewer unscheduled stops.
- Lower maintenance-related downtime.
- Lower overtime.
- Higher on-time delivery.
- Improved vehicle utilization.
- Potentially lower fuel consumption.

---

## Strategy 5: Targeted driver and delivery-process improvement

### Targeted inefficiency

- Excessive idle time.
- Long or highly variable service times.
- Poor scan completeness.
- Avoidable route deviations.
- High fuel use in similar operating conditions.

### Root cause addressed

Drivers may lack consistent procedures, local parking knowledge, or training for difficult delivery types. However, the analysis must first establish that the difference is not caused by route or vehicle assignment.

### Proposed approach

Create a fair benchmarking system using matched conditions. Provide targeted coaching on:

- Efficient depot preparation.
- Parking and access procedures.
- Scanner usage.
- Customer interaction and proof-of-delivery steps.
- Eco-driving and avoidance of unnecessary idling.
- Handling failed deliveries.
- Use of route updates and exception codes.

Best-performing drivers can be used to identify operating practices that are transferable to other teams.

### Process mining support

Use variant analysis and process performance comparisons to identify drivers who, under similar conditions, have:

- Lower P90 service time.
- Fewer unplanned stops.
- Higher first-attempt success.
- Lower route lateness.
- Better scan completeness.

### Expected KPI impact

- Lower service-time variability.
- Lower idle fuel use.
- Better data quality.
- Lower failed delivery rates.
- Improved on-time delivery.
- Reduced overtime.

# 5. Operational Constraints and Continuous Monitoring

## 5.1 Incorporating operational constraints

Optimization must improve performance without producing an operationally infeasible plan.

### Driver working hours

Routes should respect:

- Maximum shift length.
- Legally required breaks.
- Overtime rules.
- Driver availability.
- Depot start and end requirements.
- Time needed for loading, vehicle checks, and administration.

A route with a high theoretical delivery count is not useful if it regularly exceeds the legal or practical shift limit.

### Vehicle capacity

The routing model should consider:

- Number of packages.
- Package weight and volume.
- Vehicle compartment constraints.
- Package loading sequence.
- Refrigerated or special-handling requirements, if relevant.

Capacity should be checked both at route assignment and after inserting reattempts or same-day additions.

### Customer time windows

Any dynamic route change must maintain:

- Promised delivery windows.
- Priority or premium-service commitments.
- Restrictions on early delivery.
- Business opening hours.
- Special access times.

Time-window feasibility should be calculated using realistic P80 or P90 travel and service times, not only average values.

### Other constraints

The design should also consider:

- Restricted roads and vehicle access regulations.
- Parking and loading restrictions.
- Depot loading capacity.
- Vehicle availability.
- Weather and seasonal conditions.
- Driver familiarity with areas.
- Safety requirements.
- Customer preferences and privacy.

Optimization should use a cost function that balances punctuality, distance, fuel, overtime, failed deliveries, and route instability. A plan that minimizes distance but causes many late deliveries is not optimal.

---

## 5.2 Continuous monitoring with process mining dashboards

Process mining should continue after implementation. It should be used to verify whether changes produce sustained improvement and to identify new problems.

### Executive dashboard

Track weekly and daily:

- On-time delivery rate.
- First-attempt success rate.
- Failed delivery rate.
- Average and P90 route duration.
- Fuel per kilometer and package.
- Overtime minutes.
- Unscheduled maintenance events.
- Route conformance.
- Packages delivered per vehicle-hour.
- Customer complaints, if available.

Display both overall results and comparisons against:

- Six-month baseline.
- Target values.
- Prior week and prior month.
- Similar depots or route families.

### Operational control-tower dashboard

Provide live or near-real-time views of:

- Routes currently at risk of missing time windows.
- Vehicles experiencing long idle or low-speed episodes.
- Unplanned stops.
- Routes with large planned-versus-actual divergence.
- Failed deliveries requiring action.
- Vehicles likely to exceed driver hours.
- Capacity or package-assignment problems.

### Process views

Useful views include:

1. **Actual route map:** planned and actual stop sequences, detours, idle points, and traffic delays.
2. **Performance-enhanced process model:** duration and frequency on each transition.
3. **Planned-versus-actual alignment view:** skipped, inserted, and reordered stops.
4. **Package lifecycle view:** successful deliveries, failures, reattempts, and returns.
5. **Maintenance overlay:** vehicle routes affected by faults or repairs.
6. **Variant view:** common route patterns and their performance.
7. **Heat maps:** service time, traffic delay, failed deliveries, and parking-related dwell by geography.
8. **Driver and vehicle benchmarking:** controlled comparisons rather than raw rankings.

### Alerts and thresholds

Examples include:

- Route predicted to miss a promised window by more than 15 minutes.
- Vehicle stopped outside a planned customer or depot location for more than a defined threshold.
- Repeated failed deliveries at a customer or building.
- Vehicle showing a fault pattern associated with breakdown.
- Route forecast to exceed working hours.
- Excessive divergence from the approved route.
- Unusually high scan omissions.
- P90 service time exceeding the route planning assumption.

### Evaluation after implementation

Changes should be evaluated using:

- Before-and-after comparisons.
- Pilot routes and control routes.
- Matched-route comparisons.
- Statistical process control charts.
- Seasonal and day-of-week adjustment.
- KPI decomposition by route, driver, vehicle, and customer segment.

For example, a dynamic routing pilot should be judged not only by average distance reduction, but also by:

- On-time delivery.
- P90 lateness.
- Route stability.
- Driver workload.
- Failed deliveries.
- Fuel consumption.
- Overtime.
- Customer complaints.

The company should also watch for unintended effects. Improving on-time delivery by skipping difficult stops, reducing scan quality, increasing driver speed, or increasing failed deliveries would not represent a genuine improvement.

Finally, the event log and process models should be refreshed regularly. Changes in traffic patterns, customer behavior, vehicle fleet, or delivery policy can make a previously accurate route model obsolete. Continuous process mining provides Speedy Parcels with a feedback loop: discover the actual process, compare it with the plan, identify causes of deviation, implement targeted interventions, and verify whether performance improves sustainably.
