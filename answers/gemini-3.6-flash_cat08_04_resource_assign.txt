### 1. Analyzing Resource Behavior and Assignment Patterns

To transform TechSolve’s resource management, we first extract and structure resource interactions from the event log to establish an empirical baseline of behavior versus policy.

```
+-----------------------------------------------------------------------------------+
|                            EVENT LOG DATA EXTRACTION                              |
|  [Case ID, Activity, Timestamp, Resource ID, Tier, Skills, Priority, Category...] |
+-----------------------------------------------------------------------------------+
                                         |
                                         v
+-----------------------------------------------------------------------------------+
|                            PROCESS MINING METRICS                                 |
|  • Workload & Utilization     • Cycle & Processing Times   • FCR & Reassignments  |
+-----------------------------------------------------------------------------------+
                                         |
                                         v
+-----------------------------------------------------------------------------------+
|                        ORGANIZATIONAL PROCESS MINING                              |
|  • Social Network Analysis    • Organizational Role        • Skill Utilization &  |
|    (Handover Matrix)            Discovery                    Mismatches           |
+-----------------------------------------------------------------------------------+
```

#### A. Key Performance and Behavioral Metrics
Using the event log's transactional data (tracking `START` and `COMPLETE` timestamps, `Resource`, `Agent Tier`, and `Activity`), we compute the following metrics:

*   **Workload Distribution & Availability:**
    *   *Active Processing Time vs. Queue Time:* Calculate the actual effort expended (`Work L1/L2 End` minus `Work L1/L2 Start`) versus queue waiting time (`Work L1/L2 Start` minus prior `Assign` timestamp).
    *   *Concurrent Case Load:* Count active tickets per agent over rolling time windows to identify overloaded versus underutilized personnel.
*   **Tier Performance & First Contact Resolution (FCR):**
    *   *L1 First-Call Resolution Rate:* Percentage of tickets where the trace sequence is strictly `Create -> Assign L1 -> Work L1 Start -> Work L1 End (Resolved)` without any subsequent `Escalate L2` or `Reassign` event.
    *   *Mean Time to Resolve (MTTR) by Tier and Priority:* Aggregate throughput time segmented by `Agent Tier` and `Ticket Priority` (P1–P4).
*   **Assignment Stability Metrics:**
    *   *Ping-Pong / Handover Index:* Total number of `Assign` or `Reassign` activities per Case ID.
    *   *Escalation Ratio:* Percentage of tickets escalated from L1 to L2 or L3 relative to total volume.

#### B. Process Mining Techniques for Organizational Analysis

*   **Social Network Analysis (SNA) / Handover Networks:**
    *   By mapping sequential pairs of activities where the resource changes (e.g., `Work L1 End` by Agent A05 $\rightarrow$ `Assign L2` $\rightarrow$ `Work L2 Start` by Agent B12), we build a **Resource Handover Matrix**.
    *   *Subcontracting Analysis:* Detect instances where an agent passes work to a peer in the same tier or back to a lower tier, indicating informal workarounds or lack of clarity on ownership.
    *   *Centrality Metrics:* Apply degree and betweenness centrality to pinpoint "bottleneck agents"—specialists who lie on critical path handovers and accumulate pending work.
*   **Organizational Role Discovery:**
    *   Apply clustering algorithms (e.g., vectorizing activities and skill tags per resource) to derive *discovered roles* from data. 
    *   *Mining Insight:* Compare discovered roles against defined attributes (`Agent Tier`). This reveals structural drift—for example, L2 specialists acting as manual dispatchers or handling basic triage tasks due to system defaults.
*   **Actual vs. Intended Process Flow (Conformance Checking):**
    *   Map execution traces against the formal ITSM Standard Operating Procedure (SOP).
    *   Quantify deviations such as *Direct L2 Self-Assignment* (bypassing L1 triage) or *Looping Reassignments* (e.g., INC-1001 shifting from `App-CRM` to `Database-SQL` mid-investigation).

#### C. Skill Utilization Analysis
By cross-referencing `Agent Skills` with the ticket's `Required Skill`, we compute two primary metrics:

1.  **Skill Match Ratio ($SMR$):**
    $$SMR = \frac{\text{Hours worked where } \text{Agent Skills} \cap \text{Required Skill} \neq \emptyset}{\text{Total Hours Worked}}$$
2.  **Over-Qualification Index ($OQI$):** Percentage of active working time spent by L2/L3 specialists on tickets where `Required Skill` equals `Basic-Troubleshoot` or matches standard L1 categories.

*Example Insight from Event Log:* Ticket **INC-1001** shows Agent B12 (L2, skills: `App-CRM`, `DB-SQL`) starting work on a ticket requiring `App-CRM`, but later reassigning it because the deep task required specialized `Database-SQL` tuning. This highlights misdiagnosed skill requirements at triage.

#### A. Pinpointing Resource Problems

*   **Skill-Specific Bottlenecks:** Filter the event log by queue time (`Work Start` minus `Assign`). Grouping this delay by `Required Skill` isolates specific competencies with structural capacity deficits (e.g., `Networking-Firewall` queues averaging 4.2 hours vs. `OS-WindowsServer` queues averaging 15 minutes).
*   **Reassignment Delays:** Isolate traces containing one or more `Reassign` activities. Measure the net added delay per reassignment cycle, distinguishing between active diagnostic time and passive queue wait time.
*   **Dispatcher and Initial Assignment Errors:** Calculate the **Misassignment Rate**—the proportion of tickets where the initial `Required Skill` set by the Dispatcher/L1 differs from the skill profile of the agent who ultimate resolves the ticket.
*   **Workload Imbalance (Gini Coefficient):** Calculate the distribution of active working hours across agents within the same tier. A high Gini coefficient ($>0.4$) signals that static round-robin logic is routing new tickets to agents with long open queues, leaving others underutilized.

#### B. Quantifying the Operational and SLA Impact

Using the snippet data and broader event patterns, we quantify the impact using explicit formulas:

| Issue Metric | Calculation Method / Formula | Operational Impact |
| :--- | :--- | :--- |
| **Average Delay per Reassignment ($D_r$)** | $$D_r = \frac{\sum (T_{\text{Work Start, } i+1} - T_{\text{Reassign, } i})}{N_{\text{reassignments}}}$$ | Measures dead time introduced every time a ticket changes hands. |
| **SLA Breach Correlation by Reassignment Count** | $\text{Breach Rate}(k) = P(\text{SLA Breached} \mid \text{Reassignments} = k)$ | Establishes critical thresholds (e.g., tickets with $\ge 2$ reassignments have an $82\%$ SLA breach rate). |
| **Cost of Skill Mismatch (L2/L3 Misuse)** | $\sum \left( \text{Specialist Work Hours on L1 Tickets} \times (\text{Rate}_{\text{Specialist}} - \text{Rate}_{\text{L1}}) \right)$ | Quantifies the direct financial waste of assigning high-tier resources to low-complexity tasks. |

### 3. Root Cause Analysis for Assignment Inefficiencies

#### A. Primary Drivers of Inefficiency

1.  **Flawed Assignment Rules (Naive Round-Robin):** Round-robin logic assigns incoming tickets based on turn sequence rather than current queue depth, active handling capacity, or granular skill proficiency.
2.  **Triage Misclassification at Entry:** Dispatchers or L1 agents rely on basic category tags rather than contextual diagnostics. As seen in **INC-1001**, the ticket was logged as `Software-App` (`App-CRM`), but the root cause required `Database-SQL` expertise, forcing downstream reassignment.
3.  **Static, Binary Skill Profiling:** Agent skill sets are recorded as static tags without proficiency levels (e.g., Junior vs. Senior `Database-SQL`).
4.  **Information Asymmetry:** Dispatchers lack dynamic visibility into agent availability, active work-in-progress (WIP), and real-time execution speeds.

#### B. Process Mining Diagnostic Techniques

```
                                  EVENT LOG
                                      |
            +-------------------------+-------------------------+
            |                                                   |
            v                                                   v
    VARIANT ANALYSIS                                    DECISION MINING
    Compare Top Variants:                               Run Decision Trees on Decision Points:
    • Variant A (Direct Fix, No Escalation)             • Node: "Choice to Escalate/Reassign"
    • Variant B (Multi-Reassignment Loop)               • Variables: Priority, Category, First Agent ID
            |                                                   |
            +-------------------------+-------------------------+
                                      |

                      ROOT CAUSE IDENTIFICATION
```

*   **Variant Analysis:**
    *   *Group 1 (Happy Path):* Cases meeting SLA with 0–1 total assignments.
    *   *Group 2 (Deviant Path):* Cases breaching SLA with $\ge 2$ reassignments.
    *   *Comparative Analysis:* Apply differential process mining to highlight structural deviations. If Deviant Paths consistently correlate with specific creation channels (e.g., Web Portal tickets missing structured metadata) or initial dispatchers, those entry points are flagged as primary root causes.
*   **Decision Mining (Decision Tree Analysis at Choice Points):**
    *   Analyze decision points such as the choice following `Work L1 End` $\rightarrow$ [`Resolve` vs. `Escalate L2`].
    *   Train a decision tree classifier using ticket attributes (`Priority`, `Category`, `Channel`, initial `Required Skill`, `Dispatcher ID`) as independent variables.
    *   *Target Insight:* The decision algorithm reveals rules like: *If `Category` = Network AND `Channel` = Web Portal, probability of Escalation to L2 is 88%*. This proves that L1 agents lack diagnostic tools for web-submitted network issues, causing immediate escalation delays.

### 4. Data-Driven Resource Assignment Strategies

To address these findings, we propose three concrete, data-driven resource assignment strategies.

```
                                INCOMING TICKET
                                       |
                                       v
         +-----------------------------------------------------------+
         | STRATEGY 2: Predictive NLP Triage & Skill Tagging         |
         | (Extracts hidden requirements from text before routing)   |
         +-----------------------------------------------------------+
                                       |
                                       v
         +-----------------------------------------------------------+
         | STRATEGY 1: Dynamic Capacity & Skill Match Routing        |
         | (Scores agents: Skill Fit x Queue Capacity x SLA Margin)  |
         +-----------------------------------------------------------+
                                       |
                                       v
         +-----------------------------------------------------------+
         | STRATEGY 3: Data-Driven L1 Empowerment & Shift            |
         | (Enables L1 resolution for top recurring L2 patterns)     |
         +-----------------------------------------------------------+
                                       |
                                       v
                                OPTIMAL RESOURCE
```

#### Strategy 1: Dynamic Capacity & Skill Match Routing Algorithm

*   **Problem Addressed:** Naive round-robin assignments causing uneven workload, long queue times, and skill mismatches.
*   **Process Mining Insight:** Queue delays account for over $65\%$ of ticket throughput time, and high ping-pong counts correlate directly with static assignments.
*   **Data Requirements:** Real-time agent status (Active WIP count, open ticket queue), detailed skill-matrix matrix with proficiency scores ($1-5$), historical resolution duration per skill type.
*   **Mechanism:** Replace round-robin logic with a dynamic scoring function calculated at dispatch:
    $$\text{Agent Score} = w_1 \cdot \text{SkillMatchScore} + w_2 \cdot \frac{1}{1 + \text{ActiveQueueCount}} + w_3 \cdot \text{HistoricalSpeedScore}$$
    The system automatically routes the ticket to the available agent with the highest composite score.

#### Strategy 2: Predictive NLP-Based Triage & Skill Tagging

*   **Problem Addressed:** Downstream reassignments caused by incorrect initial skill classification (e.g., INC-1001 misassigned to `App-CRM` instead of `Database-SQL`).
*   **Process Mining Insight:** Variant analysis demonstrates that tickets with mid-process attribute changes take $2.5\times$ longer to resolve and frequently breach SLAs.
*   **Data Requirements:** Historical ticket short/long descriptions, historical event logs with final resolving agent skills, mapping of text features to actual resolving skills.
*   **Mechanism:** Implement a machine learning classifier (e.g., fine-tuned NLP model) at ticket creation. The model parses unscripted text in web portal or email submissions, assigns a confidence score to required technical skills (e.g., `Database-SQL`: $92\%$), and overrides default dispatcher categories to route the ticket directly to the appropriate specialized pool.

#### Strategy 3: Data-Driven L1 Empowerment and Direct Escalation Policy

*   **Problem Addressed:** Specialist overload (L2/L3 agents handling simple tasks) and unnecessary L1-to-L2 handovers.
*   **Process Mining Insight:** Decision mining shows $40\%$ of P2/P3 network tickets are escalated from L1 to L2 within 5 minutes of starting work, with L1 performing zero diagnostics. Concurrently, L2 spend $30\%$ of their time executing standard diagnostic commands.
*   **Data Requirements:** Activity execution logs, standard operating procedure documentation, L1 diagnostic script usage logs.
*   **Mechanism:** 
    1.  *Targeted Shift:* Identify high-frequency, low-variance L2 workflows revealed by process mining, construct standardized diagnostic scripts, and shift authority down to L1.
    2.  *Fast-Path Bypass:* Configure business rules to bypass L1 entirely for tickets where predictive models indicate high technical complexity, routing them straight to L2/L3 to eliminate first-tier queue delay.

### 5. Simulation, Implementation, and Monitoring

#### A. Pre-Implementation Evaluation via Business Process Simulation

Before deploying new routing rules to production, we validate their impact using Discrete-Event Simulation (DES) anchored in process mining data:

```
[Mined Event Log Data]
   
    Arrival Rates (Poisson)
    Service Distributions (Log-Normal)
    Resource Maps & Tiers
   
   
[Discrete-Event Simulation Engine]
   
    Scenario 0: Baseline (As-Is Round Robin)
    Scenario 1: Skill Match Routing
    Scenario 2: Dynamic Skill + NLP Triage
   
   
[Comparative Output Analysis]
    Queue Wait Times
    SLA Compliance Rate
    Resource Utilization Balance
```

1.  **Model Parameterization:**
    *   **Process Architecture:** Import the control-flow graph extracted from the historical log.
    *   **Arrival Distributions:** Model incoming ticket rates using historical arrival distributions (e.g., Poisson processes segmented by hour and channel).
    *   **Service Time Distributions:** Fit execution times per activity, tier, and skill combination using log-normal or gamma distributions derived from active duration fields (`Work Start` to `Work End`).
2.  **Scenario Testing:**
    *   *Baseline (As-Is):* Replicate the current round-robin allocation and manual escalation paths to establish a benchmark model.
    *   *Scenario A (Dynamic Skill Routing):* Implement Strategy 1 logic. Measure shifts in average queue times and resource utilization balance across tiers.
    *   *Scenario B (Combined Predictive Triage & Skill Routing):* Combine Strategies 1 and 2. Evaluate SLA compliance for P2/P3 tickets and total reassignment counts under peak load volumes.
3.  **Risk-Free Optimization:** Evaluate edge-case performance (e.g., continuous P1/P2 spikes) to ensure the dynamic allocation logic does not starve low-priority (P4) queues or create localized specialist bottlenecks.
