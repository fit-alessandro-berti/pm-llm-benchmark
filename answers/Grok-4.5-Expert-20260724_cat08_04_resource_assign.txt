**1. Analyzing Resource Behavior and Assignment Patterns**

Process mining starts from the event log’s case ID (Ticket ID), activity, timestamp, resource (Agent ID), and attributes (Agent Tier, Agent Skills, Ticket Priority, Ticket Category, Required Skill, Timestamp Type). These enable multi-perspective analysis of resources alongside the control-flow and data perspectives.

**Individual agent and tier performance metrics** are extracted by filtering or projecting the log on the resource and tier attributes:
- Workload distribution: number of cases handled, total active working time, concurrent cases, and percentage of time spent in “Work Lx Start/End” activities per agent and per tier. This immediately surfaces overload versus under-utilization.
- Processing times: mean, median, and distribution of activity durations (Work L1, Work L2, Work L3) stratified by agent, tier, priority, and required skill. Waiting times between “Assign” and “Work Start” quantify queue delays.
- First-call resolution (FCR) rate for L1: percentage of cases that reach a “Resolved/Closed” state after only L1 work activities, without subsequent “Escalate” or “Reassign”.
- Skill/ticket-type frequency: count and relative frequency of cases each agent handles for each Required Skill and Category. This reveals specialization versus generalist behavior.
- Escalation and reassignment rates per agent/tier: proportion of an agent’s cases that end with “Escalate L2/L3” or “Reassign”.

**Process-mining techniques that reveal actual assignment patterns**:
- Handover-of-work social network analysis constructs a directed graph where nodes are agents (or tiers) and edges represent the frequency or average delay of a case moving from one resource to another (e.g., L1 agent → L2 agent via “Escalate” then “Assign L2”). Edge thickness and delay annotations expose preferred (or forced) escalation paths and frequent reassignment loops.
- Role discovery (e.g., via clustering or organizational mining) groups agents by the sets of activities and skills they actually perform, independent of the documented tier or skill profile. This often reveals “shadow roles” or agents who effectively operate outside their nominal tier.
- Resource interaction and dotted charts ordered by resource show chronological patterns of assignment, idle time, and multitasking.
- Directly-follows graphs or process maps filtered by resource attributes make the intended versus actual flow visible: the designed logic is typically “L1 → (optional Escalate) → L2 → (optional Escalate) → L3” with round-robin inside tiers; the discovered model frequently shows additional “Reassign” loops, cross-tier jumps, and skill-mismatched handovers.

**Skill utilization analysis** is performed by joining the Required Skill attribute of each case with the Agent Skills attribute of the assigned resource. Metrics include:
- Match rate: percentage of work intervals where the assigned agent’s skill set contains the Required Skill.
- Over-skilling: frequency with which L2/L3 agents possessing rare skills (e.g., Networking-Firewall, Security-IAM) perform activities whose Required Skill is only “Basic-Troubleshoot” or a lower-tier skill.
- Under-utilization of specialists: idle time of high-skill agents concurrent with queues of matching tickets.

These analyses are typically produced with commercial or open-source process-mining tools (Disco, Celonis, ProM, pm4py) that support attribute filtering, resource graphs, and performance dashboards.

**2. Identifying Resource-Related Bottlenecks and Issues**

The metrics and models above directly locate concrete problems:
- Skill-shortage bottlenecks appear as long waiting times before “Work Start” for tickets whose Required Skill is possessed by only a small number of agents, visible both in the waiting-time distribution and in the social-network edges that funnel many cases toward the same specialist.
- Reassignment and escalation delays are quantified by the average duration of each “Reassign” or “Escalate → Assign” cycle and by the total time lost across all such cycles. Cases with ≥2 reassignments typically show significantly higher end-to-end cycle time.
- Incorrect initial assignments surface as high FCR failure rates for certain L1 agents or as frequent “Escalate” immediately after short L1 work intervals, especially when the Required Skill was already known at ticket creation.
- Overloaded versus under-utilized agents are identified by combining active-time percentage with concurrent-case counts; agents whose utilization consistently exceeds a threshold (e.g., 85 %) while others remain below 40 % indicate imbalance.
- Correlation with SLA breaches is established by annotating each case with an SLA-violation flag (computed from Priority and timestamps) and then computing the conditional probability of breach given the presence of skill mismatch, number of reassignments, or particular escalation paths. Process cubes or multi-dimensional filtering make the association statistically visible.

Impact can be expressed in concrete figures once the full log is available, for example: “Average delay introduced by each reassignment = X minutes; Y % of P2/P3 SLA breaches occur on cases that experienced at least one skill-mismatch reassignment; Z % of L3 specialist time is spent on tickets whose Required Skill is covered by L1 or L2 agents.”

**3. Root Cause Analysis for Assignment Inefficiencies**

Potential root causes are tested against the log rather than assumed:
- Assignment rules that ignore skills and current workload (pure round-robin or simple tier pools) produce the observed random handovers and skill mismatches.
- Incomplete or stale skill profiles appear when the documented Agent Skills attribute does not match the activities an agent actually performs successfully (role-discovery clusters diverge from official profiles).
- Poor initial categorization or skill identification is visible when the Required Skill attribute changes after the first “Work L1” activity or when L1 agents frequently escalate tickets whose category should have been solvable at L1.
- Lack of real-time visibility manifests as long queue times even when suitable agents are idle (detectable by comparing agent availability windows with assignment timestamps).
- Insufficient L1 empowerment or training is indicated by systematically low FCR rates for particular categories even when historical data show that other L1 agents resolve the same category successfully.

**Variant analysis** partitions the log into “happy-path” variants (few or no reassignments, short cycle time, SLA met) versus “problematic” variants (≥2 reassignments, escalations, SLA breach). Comparing the two sets of cases on attributes (Priority, Category, Required Skill, initial agent, time-of-day) isolates the conditions under which assignment decisions go wrong.

**Decision mining** (or decision-tree induction on the attributes present at each “Assign” or “Escalate” decision point) recovers the actual decision logic used by dispatchers or L1 agents and quantifies how often that logic differs from an ideal skill-and-workload-aware rule.

**4. Developing Data-Driven Resource Assignment Strategies**

Three concrete strategies grounded in the mined insights:

**Strategy A – Skill-based routing with proficiency weighting**  
Addresses skill mismatch and over-utilization of specialists.  
A matching score is computed at assignment time: intersection of Required Skill with Agent Skills, weighted by a proficiency level derived from historical resolution success rates and average handling times for that skill (extracted from the log). Tickets are offered first to the highest-scoring available agent inside the appropriate tier; only if no match exists does the ticket escalate.  
Data required: current Agent Skills and proficiency scores (periodically refreshed from the log), Required Skill (or predicted skill—see Strategy C), real-time availability.  
Expected benefits: reduction in reassignments, shorter resolution times for skilled tickets, higher utilization of L1 for routine work, measurable improvement in P2/P3 SLA compliance.

**Strategy B – Workload-aware assignment with dynamic load balancing**  
Addresses uneven workload and queue delays.  
At each assignment decision the algorithm evaluates both skill match and a load index (current open cases + predicted remaining work time based on historical activity durations per agent). A multi-objective score selects the agent that minimizes expected waiting time while respecting a skill threshold.  
Data required: real-time case queues per agent, historical processing-time distributions (from process mining), agent calendars.  
Expected benefits: more even utilization, reduced maximum queue length, lower variance in cycle time, fewer SLA breaches caused by overloaded agents.

**Strategy C – Predictive skill-and-complexity routing + refined L1 escalation criteria**  
Addresses incorrect initial assignment and excessive escalation.  
A predictive model (trained on historical ticket attributes, free-text descriptions if available, and final Required Skill / resolution tier) estimates the most likely Required Skill and the probability that an L1 agent can resolve the ticket. Tickets with high L1-success probability are preferentially assigned to L1 agents who historically succeed on that category; low-probability tickets are routed directly to the matching L2/L3 skill pool. Escalation rules are tightened to those patterns that historically lead to successful L1 resolution.  
Data required: historical cases with final skill, resolution tier, and outcome; ticket category, priority, and any textual features; continuously updated model.  
Expected benefits: higher FCR, fewer unnecessary escalations, earlier correct assignment of complex tickets, reduced total reassignment volume.

All three strategies can be combined: the predictive model feeds both the skill-matching and the workload-aware components.

**5. Simulation, Implementation, and Monitoring**

**Business-process simulation** uses the discovered process model (control-flow + resource perspective), the empirical activity-duration distributions, the resource calendars, and the skill profiles extracted from the log as the baseline “as-is” simulation model. Each proposed assignment strategy is encoded as a new resource-allocation rule inside the simulator. Multiple what-if scenarios are run with the same arrival patterns (or with forecasted ticket volumes). Key output metrics—average cycle time, SLA compliance per priority, number of reassignments, agent utilization histograms, and skill-match rate—are compared statistically against the as-is baseline. Sensitivity analysis on skill-profile accuracy and arrival-rate peaks quantifies robustness before any live change.

**Post-implementation monitoring** is realized through continuously refreshed process-mining dashboards fed by the live event stream:
- Resource KPIs: utilization per agent/tier, skill-match rate, average waiting time after assignment, FCR rate, reassignment count per case, SLA breach rate stratified by skill mismatch.
- Process views: real-time social network of handovers (to detect emerging bottlenecks), dotted chart of agent activity, process map filtered by “cases with reassignment,” and a performance spectrum showing cycle-time distributions for skill-matched versus mismatched cases.
- Alerting thresholds: e.g., any agent utilization >90 % for >2 h, skill-match rate dropping below a target, or sudden increase in “Reassign” frequency trigger investigation.
- Periodic role-discovery and decision-mining runs detect drift in agent behavior or in the effectiveness of the new rules, feeding back into model retraining (especially for Strategy C).

This closed-loop approach—mine, diagnose, design, simulate, deploy, monitor, re-mine—ensures that resource assignment continuously improves on the basis of actual process behavior rather than assumed logic.
