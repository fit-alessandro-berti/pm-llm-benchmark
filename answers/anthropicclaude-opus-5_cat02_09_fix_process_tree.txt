## 1. What is wrong with the current model

The model is correct only for the first two and the last activity. Everything else is thrown into a **PARALLEL (AND) block**, and an AND block in a process tree means *interleaving in any order*. With 5 children, the AND block admits 5! = 120 orderings, of which only **one** is domainvalid.

Concrete violations the current model permits:

| Unwanted behaviour allowed | Why it is impossible in reality |
|---|---|
| `Pay_Invoice` before `Receive_Invoice` | You cannot pay a document you have not received. |
| `Pay_Invoice` before `Receive_Goods` | Payment without goods receipt (no 3way match)  control/fraud violation. |
| `Match_Invoice_to_PO` before `Create_Purchase_Order` | Nothing to match against. |
| `Match_Invoice_to_PO` before `Receive_Invoice` | Nothing to match. |
| `Receive_Goods` / `Receive_Invoice` before `Create_Purchase_Order` | Goods/invoice arrive without a PO ("maverick buying"). |
| `Pay_Invoice` before `Match_Invoice_to_PO` | Payment without validation. |

So the **causal dependencies** that must be enforced are:

```
Create_Purchase_Requisition  Approve_Purchase_Requisition  Create_Purchase_Order
Create_Purchase_Order  Receive_Goods
Create_Purchase_Order  Receive_Invoice
{Receive_Goods, Receive_Invoice}  Match_Invoice_to_PO  Pay_Invoice  Close_Case
```

Only **Receive_Goods** and **Receive_Invoice** have no logical ordering between them (an invoice may legitimately arrive before or after the physical delivery). Everything else is strictly sequential.

## 2. Corrected process tree

### Variant A — strict sequence (exactly the prescribed order)

```python
from pm4py.objects.process_tree.obj import Operator, ProcessTree

# --- Activities -----------------------------------------------------------
create_req      = ProcessTree(label="Create_Purchase_Requisition")
approve_req     = ProcessTree(label="Approve_Purchase_Requisition")
create_po       = ProcessTree(label="Create_Purchase_Order")
receive_goods   = ProcessTree(label="Receive_Goods")
receive_invoice = ProcessTree(label="Receive_Invoice")
match_invoice   = ProcessTree(label="Match_Invoice_to_PO")
pay_invoice     = ProcessTree(label="Pay_Invoice")
close_case      = ProcessTree(label="Close_Case")

# --- Fixed model: one single SEQUENCE, no PARALLEL at all -----------------
root = ProcessTree(operator=Operator.SEQUENCE, children=[
    create_req,
    approve_req,
    create_po,
    receive_goods,
    receive_invoice,
    match_invoice,
    pay_invoice,
    close_case
])

for child in root.children:
    child.parent = root

# print(root)
# -> ->( 'Create_Purchase_Requisition', 'Approve_Purchase_Requisition',
#        'Create_Purchase_Order', 'Receive_Goods', 'Receive_Invoice',
#        'Match_Invoice_to_PO', 'Pay_Invoice', 'Close_Case' )
```

This language contains **exactly one trace**:
`Create_Purchase_Requisition, Approve_Purchase_Requisition, Create_Purchase_Order, Receive_Goods, Receive_Invoice, Match_Invoice_to_PO, Pay_Invoice, Close_Case`

### Variant B — recommended, domainrealistic (goods/invoice receipt unordered)

Keeps *one* small, deliberately justified AND block, because the arrival order of the delivery and the supplier invoice is not controllable:

```python
# Goods receipt and invoice receipt may interleave, but both must be finished
# before matching can start.
receipt_block = ProcessTree(operator=Operator.PARALLEL,
                            children=[receive_goods, receive_invoice])
for c in receipt_block.children:
    c.parent = receipt_block

root = ProcessTree(operator=Operator.SEQUENCE, children=[
    create_req,
    approve_req,
    create_po,
    receipt_block,        # AND of exactly the two truly concurrent steps
    match_invoice,
    pay_invoice,
    close_case
])
for c in root.children:
    c.parent = root

# -> ->( 'Create_Purchase_Requisition', 'Approve_Purchase_Requisition',
#        'Create_Purchase_Order',
#        +( 'Receive_Goods', 'Receive_Invoice' ),
#        'Match_Invoice_to_PO', 'Pay_Invoice', 'Close_Case' )
```

Language = 2 traces (goodsfirst and invoicefirst). Use Variant A if the specification is to be read literally; use Variant B if you want a model that still fits real logs without allowing any control violation.

*(Optional realistic extension, if the log requires it: wrap the matching/payment part in a loop or add an XOR with a `Cancel/Block_Invoice` branch for pricemismatch rework — `*( ->( 'Match_Invoice_to_PO', ... ),  )`. Do this only when the event log evidences it, otherwise you reintroduce underfitting.)*

## 3. Why the fix removes the unwanted behaviour

1. **SEQUENCE imposes total order on its children.** In processtree semantics, `(A, B)` means every activity in the subtree `A` must complete before any activity in `B` starts. By replacing the AND block with sequence nodes, all the causal constraints listed in §1 become structurally enforced — they can no longer be violated by *any* trace the model generates.

2. **Behavioural space collapses from 120 orderings to 1 (or 2).** The AND block's footprint contained `||` (parallel) relations between e.g. `Pay_Invoice` and `Receive_Invoice`; in the fixed model those cells become strict `` relations. Precision (the metric that penalises model behaviour not seen in the log) rises to 1.0, while fitness on wellbehaved logs stays 1.0 — i.e. the underfitting is removed without introducing overfitting on the *conforming* part of the log.

3. **Control objectives are guaranteed, not merely likely.** Because `Receive_Goods`, `Receive_Invoice` and `Match_Invoice_to_PO` all precede `Pay_Invoice` in the sequence, the model can no longer produce a "payment without threeway match" trace. Similarly, "goods/invoice without PO" and "match without PO" are impossible since `Create_Purchase_Order` precedes the whole receipt/matching block.

4. **No choices were added.** No XOR or LOOP operators are introduced, so the model does not allow skipping `Approve_Purchase_Requisition`, skipping the match, or repeating payment. Every case must execute all eight activities exactly once, ending with `Close_Case`, which remains the last child of the root sequence and therefore the mandatory final event.

5. **Diagnostic side benefit.** Because the fixed model is tight, conformance checking (alignments / token replay) on the original log will now *surface* the deviating cases (e.g. paybeforereceive) as logmove/modelmove deviations instead of silently accepting them — which is exactly what you want for audit and compliance analysis.
