6. **Authorize_Contract_Terms** – Final approval of the loan.

### 2. Step-by-Step Explanation with Constraint Mapping

#### Stage 1: Intake and Initiation
- **`init` (Receive_Application)** and **`existence` (Receive_Application, Gather_Additional_Documents)**  
  Every case must begin with the application intake. The process cannot start with a credit check, a document request, or a fund transfer. The existence rule also guarantees that document collection is never omitted; every trace must contain a **Gather_Additional_Documents** event.

- **`response` (Receive_Application  Preliminary_Credit_Check)**  
  Once the application is received, a preliminary credit check is obligatory. This prevents a loan from sitting in the system unaudited and stops staff from skipping risk screening.

- **`exactly_one` (Preliminary_Credit_Check)**  
  The credit check must occur **once and only once**. In practice, this prevents redundant checks (waste, customer frustration) and also prevents “check shopping,” where an applicant might be run through multiple assessments to game the system.

#### Stage 2: Documentation and Risk Sequencing
- **`succession` (Preliminary_Credit_Check  Gather_Additional_Documents)**  
  This is a strict two-way gate:  
  - If the preliminary check happens, document gathering must eventually follow.  
  - If documents are gathered, the preliminary check must have already occurred.  
  **Practical effect:** You cannot ask the customer for pay stubs and IDs before knowing whether they pass basic credit screening. This saves operational effort and prevents customers from submitting sensitive documents for loans that will be immediately rejected.

- **`coexistence` (Gather_Additional_Documents  Authorize_Contract_Terms)**  
  These two activities are bound together: if one occurs, the other must occur, and vice versa.  
  **Practical effect:** Final contract authorization is impossible without the supporting documentation having been collected, and conversely, if docs are gathered, the process is expected to move all the way to authorization (preventing “orphaned” document folders).

#### Stage 3: Offer Preparation and Validation
- **`responded_existence` (Assemble_Loan_Offer_Package  Quality_Assurance_Review)**  
  Whenever the loan package is assembled, a QA review is triggered.  
  **Practical effect:** You cannot build a loan offer—complete with terms, interest rates, and conditions—without it being verified afterward. This stops “draft” offers from reaching the customer.

- **`altsuccession` (Gather_Additional_Documents  Quality_Assurance_Review)**  
  The document-gathering phase and the QA review are linked in an alternating succession. Between a document-collection event and the QA event, no duplicate document-gathering or duplicate QA events can occur.  
  **Practical effect:** This creates a clean hand-off: documents are collected, then immediately and exactly once, they are reviewed—no repetitive “gather, review, gather again” loops.

- **`chainsuccession` (Quality_Assurance_Review  Assemble_Loan_Offer_Package)**  
  QA and package assembly are chained adjacent to one another in the dependency graph.  
  **Practical effect:** The package is built to be reviewed, and the review feeds directly back into finalizing the package. There is no “dead air” where an offer sits unverified.

- **`precedence` (Quality_Assurance_Review  Authorize_Contract_Terms)**  
  Authorization can only happen if QA has already taken place.  
  **Practical effect:** Internal controls prevent an underwriter or manager from signing off on terms that have not been quality-checked, reducing the risk of non-compliant or erroneous contracts.
