# Temporal Profile Anomaly Analysis

## Identified Anomalies

1. **R to P (Receive to Approve)**: Average of 25 hours with extremely low standard deviation (3600 seconds = 1 hour) suggests a rigid approval schedule rather than natural process variation.

2. **P to N (Approve to Notify)**: Average 7-day delay (604800 seconds) with high standard deviation (172800 seconds = 2 days) indicates inconsistent notification practices, possibly due to backlogs or resource constraints.

3. **A to C (Assign to Close)**: 2-hour average with 1-hour standard deviation is unusually fast for a process that should involve evaluation and approval steps, suggesting premature closures.

4. **E to N (Evaluate to Notify)**: Only 5 minutes average with 1-minute standard deviation is unrealistically quick, potentially indicating skipped steps or automation errors.

5. **R to E (Receive to Evaluate)**: 1-day average with 8-hour standard deviation may be too short given the complexity of insurance evaluation processes.

## Hypotheses on Anomaly Causes

1. **Rigid Approval Schedule (R to P)**:
   - Fixed daily approval batch processing creating artificial timing patterns
   - System-enforced deadlines rather than natural business flow
   - Possible data entry errors causing timestamp inconsistencies

2. **Delayed Notifications (P to N)**:
   - Manual notification process creating bottlenecks
   - Resource constraints in customer service teams
   - System integration issues between approval and notification systems
   - Selective notification practices for certain claim types

3. **Premature Closures (A to C)**:
   - Adjusters closing claims without proper evaluation
   - System errors closing claims automatically
   - Fraudulent or test claims in the system
   - Inadequate workflow enforcement

4. **Rapid Evaluation-Notification Transitions (E to N)**:
   - Automated notifications immediately after evaluation
   - System errors skipping notification step
   - Test data or system-generated events
   - Different workflow for specific claim types

5. **Short Receive-Evaluate Times**:
   - Insufficient time for proper claim assessment
   - Complex claims being marked as simple
   - Geographic or specialization bottlenecks

## SQL Verification Queries

```sql
-- 1. Identify claims with unusually fast R to P transitions
WITH activity_times AS (
    SELECT 
        ce.claim_id,
        MIN(CASE WHEN ce.activity = 'R' THEN ce.timestamp END) AS receive_time,
        MIN(CASE WHEN ce.activity = 'P' THEN ce.timestamp END) AS approve_time
    FROM claim_events ce
    GROUP BY ce.claim_id
    HAVING 
        MIN(CASE WHEN ce.activity = 'R' THEN ce.timestamp END) IS NOT NULL
        AND MIN(CASE WHEN ce.activity = 'P' THEN ce.timestamp END) IS NOT NULL
)
SELECT 
    claim_id,
    EXTRACT(EPOCH FROM (approve_time - receive_time)) AS r_to_p_seconds,
    EXTRACT(EPOCH FROM (approve_time - receive_time))/3600 AS r_to_p_hours
FROM activity_times
WHERE EXTRACT(EPOCH FROM (approve_time - receive_time)) < 7200  -- Less than 2 hours
ORDER BY r_to_p_seconds;
```

```sql
-- 2. Find claims with extremely long P to N delays
WITH activity_times AS (
    SELECT 
        ce.claim_id,
        MIN(CASE WHEN ce.activity = 'P' THEN ce.timestamp END) AS approve_time,
        MIN(CASE WHEN ce.activity = 'N' THEN ce.timestamp END) AS notify_time
    FROM claim_events ce
    GROUP BY ce.claim_id
    HAVING 
        MIN(CASE WHEN ce.activity = 'P' THEN ce.timestamp END) IS NOT NULL
        AND MIN(CASE WHEN ce.activity = 'N' THEN ce.timestamp END) IS NOT NULL
)
SELECT 
    claim_id,
    EXTRACT(EPOCH FROM (notify_time - approve_time)) AS p_to_n_seconds,
    EXTRACT(EPOCH FROM (notify_time - approve_time))/86400 AS p_to_n_days
FROM activity_times
WHERE EXTRACT(EPOCH FROM (notify_time - approve_time)) > 1209600  -- More than 14 days
ORDER BY p_to_n_seconds DESC;
```

```sql
-- 3. Identify claims closed very quickly after assignment
WITH activity_times AS (
    SELECT 
        ce.claim_id,
        MIN(CASE WHEN ce.activity = 'A' THEN ce.timestamp END) AS assign_time,
        MIN(CASE WHEN ce.activity = 'C' THEN ce.timestamp END) AS close_time
    FROM claim_events ce
    GROUP BY ce.claim_id
    HAVING 
        MIN(CASE WHEN ce.activity = 'A' THEN ce.timestamp END) IS NOT NULL
        AND MIN(CASE WHEN ce.activity = 'C' THEN ce.timestamp END) IS NOT NULL
)
SELECT 
    claim_id,
    EXTRACT(EPOCH FROM (close_time - assign_time)) AS a_to_c_seconds,
    EXTRACT(EPOCH FROM (close_time - assign_time))/3600 AS a_to_c_hours
FROM activity_times
WHERE EXTRACT(EPOCH FROM (close_time - assign_time)) < 7200  -- Less than 2 hours
ORDER BY a_to_c_seconds;
```

```sql
-- 4. Check for claims missing expected activities in sequence
SELECT 
    c.claim_id,
    c.claim_type,
    STRING_AGG(ce.activity, ' -> ' ORDER BY ce.timestamp) AS activity_sequence,
    COUNT(*) AS event_count
FROM claims c
LEFT JOIN claim_events ce ON c.claim_id = ce.claim_id
GROUP BY c.claim_id, c.claim_type
HAVING 
    COUNT(*) < 6  -- Should have at least 6 activities
    OR STRING_AGG(ce.activity, ' -> ' ORDER BY ce.timestamp) LIKE '%A%C%'  -- Assign followed immediately by Close
    OR STRING_AGG(ce.activity, ' -> ' ORDER BY ce.timestamp) LIKE '%P%N%' IS NULL;  -- Approved but not notified
```

```sql
-- 5. Correlate anomalies with adjusters and regions
WITH activity_metrics AS (
    SELECT 
        ce.claim_id,
        ce.resource,
        a.region,
        a.specialization,
        MIN(CASE WHEN ce.activity = 'R' THEN ce.timestamp END) AS receive_time,
        MIN(CASE WHEN ce.activity = 'P' THEN ce.timestamp END) AS approve_time,
        MIN(CASE WHEN ce.activity = 'N' THEN ce.timestamp END) AS notify_time,
        MIN(CASE WHEN ce.activity = 'C' THEN ce.timestamp END) AS close_time
    FROM claim_events ce
    JOIN claims c ON ce.claim_id = c.claim_id
    JOIN adjusters a ON ce.resource = a.adjuster_id::TEXT
    GROUP BY ce.claim_id, ce.resource, a.region, a.specialization
)
SELECT 
    region,
    specialization,
    AVG(EXTRACT(EPOCH FROM (approve_time - receive_time))/3600) AS avg_r_to_p_hours,
    STDDEV(EXTRACT(EPOCH FROM (approve_time - receive_time))/3600) AS stddev_r_to_p_hours,
    COUNT(*) AS claim_count
FROM activity_metrics
WHERE receive_time IS NOT NULL AND approve_time IS NOT NULL
GROUP BY region, specialization
HAVING STDDEV(EXTRACT(EPOCH FROM (approve_time - receive_time))/3600) < 1  -- Very low variability
ORDER BY avg_r_to_p_hours;
```

```sql
-- 6. Examine E to N transitions for anomalies
WITH activity_times AS (
    SELECT 
        ce.claim_id,
        MIN(CASE WHEN ce.activity = 'E' THEN ce.timestamp END) AS evaluate_time,
        MIN(CASE WHEN ce.activity = 'N' THEN ce.timestamp END) AS notify_time
    FROM claim_events ce
    GROUP BY ce.claim_id
    HAVING 
        MIN(CASE WHEN ce.activity = 'E' THEN ce.timestamp END) IS NOT NULL
        AND MIN(CASE WHEN ce.activity = 'N' THEN ce.timestamp END) IS NOT NULL
)
SELECT 
    claim_id,
    EXTRACT(EPOCH FROM (notify_time - evaluate_time)) AS e_to_n_seconds,
    EXTRACT(EPOCH FROM (notify_time - evaluate_time))/60 AS e_to_n_minutes
FROM activity_times
WHERE EXTRACT(EPOCH FROM (notify_time - evaluate_time)) < 300  -- Less than 5 minutes
ORDER BY e_to_n_seconds;
```

```sql
-- 7. Analyze claim types with timing anomalies
SELECT 
    c.claim_type,
    COUNT(*) AS total_claims,
    AVG(CASE WHEN ce_r.timestamp IS NOT NULL AND ce_p.timestamp IS NOT NULL 
        THEN EXTRACT(EPOCH FROM (ce_p.timestamp - ce_r.timestamp))/3600 
        ELSE NULL END) AS avg_r_to_p_hours,
    AVG(CASE WHEN ce_p.timestamp IS NOT NULL AND ce_n.timestamp IS NOT NULL 
        THEN EXTRACT(EPOCH FROM (ce_n.timestamp - ce_p.timestamp))/86400 
        ELSE NULL END) AS avg_p_to_n_days
FROM claims c
JOIN claim_events ce_r ON c.claim_id = ce_r.claim_id AND ce_r.activity = 'R'
JOIN claim_events ce_p ON c.claim_id = ce_p.claim_id AND ce_p.activity = 'P'
JOIN claim_events ce_n ON c.claim_id = ce_n.claim_id AND ce_n.activity = 'N'
GROUP BY c.claim_type
ORDER BY avg_r_to_p_hours DESC, avg_p_to_n_days DESC;
```
