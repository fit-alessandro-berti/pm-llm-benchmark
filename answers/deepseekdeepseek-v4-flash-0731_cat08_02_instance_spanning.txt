# Comprehensive Strategy to Address Instance-Spanning Constraints in Order Fulfillment

## 1. Identifying Instance-Spanning Constraints and Their Impact

The event log is the core asset for detecting and quantifying instance-spanning constraints. Since these constraints involve dependencies **between** different order instances, traditional single-case process discovery is not enough. We need to combine process mining with resource-level and batch-level analysis.

### 1.1 How to Identify Each Constraint from the Event Log

#### A. Shared Cold-Packing Stations

**Identification approach:**

- Filter all orders where `Requires Cold Packing = TRUE`.
- Use the `Resource (Staff/Station ID)` field to identify cold-packing stations, e.g., `Station C1`–`C5`.
- Build time intervals for every packing activity:
  - Start time = `Packing START`
  - End time = `Packing COMPLETE`
- Overlay all cold-packing intervals on a global timeline to see:
  - When all cold stations are occupied.
  - How many orders are waiting for a cold station.
  - How long each order waits between the previous activity completion and `Packing START`.

From the conceptual log, for example, `ORD-5002` requires cold packing and starts packing at `10:22:50` on `Station C2`. We can infer whether a station was already occupied by another order at that time by comparing against all active packing intervals.

**Impact metrics:**

| Metric | Description |
|---|---|
| Cold-packing queue length | Number of cold orders waiting for a station at any time |
| Cold-packing waiting time | Time from order ready for packing until `Packing START` |
| Cold-packing station utilization | Percentage of time each cold station is occupied |
| Cold-packing service time | `Packing COMPLETE - Packing START` for cold orders |
| Peak contention periods | Times of day when all 5 stations are busy |
| Order-to-order delay caused by cold-packing | Additional waiting time attributable to station unavailability |

#### B. Batching for Shipping

**Identification approach:**

- Use the resource field in `Shipping Label Gen.`, e.g., `System (Batch B1)`.
- Group cases by batch ID.
- For each batch, determine:
  - The first order ready for shipping.
  - The last order that completes the batch.
  - The label generation timestamp for each order.
- Compute the waiting time between `Quality Check COMPLETE` (or `Packing COMPLETE`, if QC is not required) and `Shipping Label Gen. COMPLETE`.

**Impact metrics:**

| Metric | Description |
|---|---|
| Batch formation time | Time from first order entering the batch until batch closes |
| Batch size | Number of orders in each batch |
| Batch waiting time per order | Time an order waits at the shipping label step for the batch to complete |
| Dispatch frequency | Number of batches dispatched per day / per destination |
| Fill rate | Actual batch size / target batch size |
| "Overdue batch" count | Batches that take longer than a target threshold to form |

In the conceptual log, `ORD-5001` finishes QC at `10:35:15`, but shipping label generation completes at `10:45:50`, and the notation explicitly says "Waited for batch". This is a direct instance-spanning waiting time.

#### C. Priority Order Handling

**Identification approach:**

- Separate orders by `Order Type = Express` vs `Standard`.
- Detect resource overlaps:
  - If an express order starts using a resource while a standard order is still active on that same resource, the standard order may have been delayed or preempted.
- For non-preemptive cases:
  - Compare the queue position of standard orders before and after express orders arrive.
  - Quantify how often express orders overtake standard orders in the queue.
- For preemptive cases:
  - If an express order uses a station between the start and complete timestamps of a standard order on the same station, the standard order was likely paused.
  - In the event log, if no explicit "Pause" or "Resume" event exists, we can infer this by reconstructing the sequence of resource usage.

**Impact metrics:**

| Metric | Description |
|---|---|
| Express order cycle time | Order received to shipping label generation |
| Standard order delay due to express orders | Extra waiting/interruption time caused by express priority |
| Preemption count | Number of times a standard order is interrupted |
| Interruption duration | Time between standard order pause and resume |
| Priority "overtaking" events | Number of times express orders bypass standard orders in a queue |
| SLA attainment | Percentage of express orders completed within target |

#### D. Hazardous Material Limits

**Identification approach:**

- Filter orders where `Hazardous Material = TRUE`.
- Build intervals for:
  - `Packing` activity
  - `Quality Check` activity
- At every timestamp, count how many hazardous orders are simultaneously in `Packing` or `Quality Check`.
- Compare the maximum simultaneous count against the regulatory limit of 10.
- Identify periods when the count reaches 10, because these are the times when the constraint blocks new hazmat orders from starting.

**Impact metrics:**

| Metric | Description |
|---|---|
| Active hazmat count | Concurrent number of hazardous orders in Packing or QC |
| Limit violation count | Number of times the active count exceeds 10 |
| Time at limit | Duration when active hazardous count = 10 |
| Waiting time due to hazmat cap | Time a hazardous order is ready to start Packing/QC but must wait because the limit has been reached |
| Hazmat throughput | Number of hazardous orders completed per hour/day |
| Headroom | `10 - current active hazardous count` |

### 1.2 Differentiating Within-Instance vs Between-Instance Waiting

It is essential to separate delays caused by the order itself from delays caused by interactions with other orders.

- **Within-instance factors**:
  - Activity duration, e.g., `Picking COMPLETE - Picking START` for a large order.
  - Complexity of the order itself, such as number of items, packaging requirements, or special instructions.
  - Quality check duration due to product-specific checks.

- **Between-instance factors**:
  - Waiting for a shared cold-packing station occupied by another order.
  - Waiting for other orders in the same shipping batch.
  - Delay caused by a higher-priority express order.
  - Waiting due to the hazardous-material active-order limit.

In the event log, we can compute:

- **Processing time** = activity `COMPLETE` - activity `START`.
- **Waiting time** = next activity `START` - previous activity `COMPLETE`.

Then, for each waiting segment, we assign the waiting time to a root cause:

1. If the next required resource is unavailable because other orders are using it, classify as **resource contention wait**.
2. If the resource is available but the next activity is a batch-related step and the batch has not formed, classify as **batch wait**.
3. If an express order overtakes or interrupts the current order, classify as **priority/preemption delay**.
4. If the next activity cannot start because the hazmat active count is already at 10, classify as **regulatory/compliance wait**.
5. If none of these apply, classify as **other/unknown wait** for further investigation.

This decomposition provides a direct measurement of the negative operational impact of each instance-spanning constraint.

## 2. Analyzing Constraint Interactions

The constraints do not act in isolation. They interact in ways that can amplify delays or create new bottlenecks.

### 2.1 Priority Handling + Shared Cold-Packing

If express orders requiring cold packing are always allowed to jump the queue, they will repeatedly push standard cold-packing orders later. Over a peak period, this can cause:

- Longer wait times for standard cold orders.
- Higher cold-station utilization by express orders.
- Potential SLA failures for standard perishable orders, even though cold-packing capacity exists.

Conversely, if all cold-packing orders are treated equally, express orders may miss delivery targets. Therefore, any scheduling policy must balance express priority with fairness and overall throughput.

### 2.2 Batching + Hazardous Material Limits

Suppose ten hazardous orders are all destined for the same region. To form a shipping batch quickly, the system may naturally process them around the same time. This creates a burst of hazardous orders entering Packing and QC simultaneously, likely hitting the 10-order regulatory limit.

As a result:

- Some hazardous orders cannot start packing even though stations are available.
- Batch formation becomes delayed because the batch depends on those same orders.
- The batching logic unintentionally worsens the hazmat constraint.

A smarter batching strategy would spread hazardous-order release into Packing/QC, even if that means slightly delaying the formation of a batch.

### 2.3 Hazardous Material Limit + Shared Cold-Packing

If many hazardous orders also require cold packing, the same limited five stations are used by orders that are also constrained by the hazmat active count. In this case:

- The cold-packing queue is driven by physical station capacity.
- The hazmat limit adds another layer of queueing.
- A hazardous order may be ready for packing and a cold station may be free, but the hazmat cap may still prevent it from starting.

This interaction shows that capacity expansion of cold stations alone may not solve the problem. The regulatory cap must be managed jointly.

### 2.4 Priority Handling + Batching

Express orders should not wait for standard batch formation. If express orders are batched with standard orders using the same batch trigger, their speed advantage is lost. Priority dispatch logic must allow express orders to be batched more quickly, possibly with smaller batch sizes.

### Why This Matters for Optimization

Optimizing one constraint in isolation can easily make another constraint worse. For example:

- Increasing cold-packing capacity may push more orders into QC faster, causing the hazmat active count to hit its limit.
- Reducing batch size may improve shipping wait times but can increase shipping costs and reduce route efficiency.
- Always prioritizing express orders may reduce their lead time but severely degrade standard order performance.

Thus, any optimization strategy must be **constraint-aware** and tested against the combination of all constraints simultaneously.

### Strategy 1: Dynamic Priority-Aware Scheduling for Cold-Packing and Bottleneck Resources

#### Primary Constraints Addressed

- Shared cold-packing stations
- Express priority handling

#### Proposed Changes

1. Replace naive First-Come-First-Served scheduling with **deadline-based scheduling** at all bottleneck resources.
   - Each order receives a deadline based on its delivery SLA.
   - At a packing station, the next order to process is the one with the earliest deadline, not necessarily the one that arrived first.

2. Introduce **dynamic preemption rules**:
   - Express orders can interrupt a standard order only when the express order is at risk of missing its SLA.
   - Do not interrupt a standard order if it is nearly complete. For example, if the standard order is more than 80% packed, let it finish.
   - If preemption is necessary, pause the standard order at a safe point and resume it immediately after the express order is completed.

3. Use a **reservation mechanism**:
   - Reserve one cold-packing station for high-priority cold/express orders during peak hours.
   - If no express order arrives, the reserved station can be released for standard orders.

4. Adjust staffing dynamically:
   - Use historical data to predict peak demand for cold-packing.
   - Shift cross-trained staff to cold-packing during predicted peak periods.

#### Data and Analysis Leveraged

- Historical event log analysis provides:
  - Arrival rates of express cold orders by hour.
  - Cold-packing duration distributions by order type.
  - SLA deadlines and required lead times.
  - Frequency and cost of preemption events.

#### Expected Positive Outcomes

- Reduced waiting time for cold-packing orders.
- Express orders meet their SLAs more consistently.
- Standard orders experience fewer unnecessary interruptions.
- Higher overall utilization of cold-packing stations.
- Better balance between priority handling and throughput.

### Strategy 2: Dynamic Batch Formation and Decoupling of Label Generation from Batch Closure

#### Proposed Changes

   - Use different batch triggers for express orders, allowing smaller and faster batches.

2. **Decouple label generation from batch completion**:
   - Generate the shipping label for an order immediately after it passes Quality Check.
   - Store it in a virtual batch queue.

3. **Coordinate batching with hazmat release control**:
   - If multiple hazardous orders are destined for the same region, avoid processing them simultaneously.
   - The release-to-packing schedule should consider both the shipping batch deadline and the hazmat active-count limit.
   - The goal is to form the batch without creating a spike in the active hazmat count.

4. **Use predictive analytics**:
   - Forecast order arrivals by destination region and time of day.
   - Set batch triggers dynamically to balance waiting time and truck fill rate.

#### Data and Analysis Leveraged

- Historical batch wait times by destination.

- Relationship between batch size and shipping cost.
- Patterns of hazmat order arrivals by region.

#### Expected Positive Outcomes

- Reduced waiting time at the shipping label generation step.
- Faster dispatch for express orders.
- Better utilization of truck capacity without causing excessive waiting.
- Fewer hazmat limit violations because batch-induced order bursts are smoothed.

1. Quantify the impact of shared cold-packing, batching, priority handling, and hazmat limits.
2. Understand how these constraints interact.
3. Implement constraint-aware scheduling, dynamic batching, and hazmat release control.
4. Validate all changes with simulation.
5. Monitor the process continuously with constraint-specific dashboards.

By adopting this approach, the fulfillment center can improve on-time delivery performance, increase throughput, and maintain regulatory compliance—even during peak seasons.
