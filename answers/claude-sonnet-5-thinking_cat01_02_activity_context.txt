# Analysis & Renaming of Recurring Activities

## Step 1: Identify Recurring Activities

Three activities recur within the same case, each carrying different meaning depending on position and context:

| Activity | Occurrences | Contextual Variation |
|----------|-------------|----------------------|
| **Verify Documents** | 2x in C001, C003; 1x in C002 | First occurrence = initial verification; second occurrence = re-verification after new info/adjustment |
| **Call Customer** | 1–2x per case | Purpose varies: requesting missing docs, clarifying discrepancies, confirming adjustments, or requesting customer's physical return |
| **Adjust Account** | 1x in C002, C003 | Consistent meaning (internal correction), but triggered by different upstream events |

## Step 4: Justification for Naming Choices

**"Verify Documents – Initial Check" vs. "– Re-verification"**
- The *first* instance in every case occurs immediately after "Initiate Request" and serves as the baseline identity/document check.
- The *second* instance (in C001 and C003) occurs **after** an intervening event (new document submission or account adjustment), indicating it is a **confirmatory re-check**, not a fresh verification. This distinction is critical for process mining, since treating both as identical "Verify Documents" would obscure a rework loop.

**"Call Customer" – four distinct sub-types**
The additional context column reveals the call serves fundamentally different business purposes:
- *Request Missing Documents* (C001): triggered by incomplete verification, aims to close a document gap.
- *Clarify Discrepancy* (C002): triggered by a data/account inconsistency needing customer input.
- *Confirm Adjustment* (C002): a follow-up call **after** internal correction, purely confirmatory — a different function from the first call in the same case.
- *Request Customer Return* (C003): a logistical/physical call (branch context), unrelated to document or data issues.

Since "Call Customer" recurs within C002 with two clearly different intents (clarify vs. confirm), collapsing them into one label would hide the sequential logic (problem-identification  resolution-confirmation). Splitting them exposes the actual sub-process pattern: **Call (Issue)  Adjust Account  Call (Confirmation)**.

**"Adjust Account – Internal Correction"**
- Although only appearing once per case, it was still explicitly labeled for clarity and consistency, since it is the pivot point between the two differently-purposed "Call Customer" events in C002, and between two "Verify Documents" instances in C003. Naming it explicitly reinforces that it is an **internal, backend correction step** rather than a customer-facing action, distinguishing it clearly from the surrounding customer-interaction activities.

## Summary of Value Added

By disambiguating recurring labels using **position in sequence** and **contextual purpose**, the revised log now enables:
- Accurate process discovery (e.g., detecting rework loops via "Re-verification").
- Clearer root-cause analysis of calls (document issues vs. discrepancies vs. logistics).
- Better conformance checking against expected sub-processes (e.g., CallAdjustCall confirmation pattern in C002).
