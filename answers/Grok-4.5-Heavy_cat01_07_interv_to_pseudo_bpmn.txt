**Invoice Approval Process – BPMN-like Textual Model**

**1. Process Overview**  
This model consolidates the accounts from five stakeholder interviews (AP Clerk Mary, Purchasing Officer Dan, Department Manager Carlos, AP Supervisor Rita, and Supplier Relationship Manager Karen) into a coherent, BPMN-compatible description of the invoice approval and payment-scheduling process. It captures the typical sequence, decision points, roles, data objects, and exception paths while noting residual ambiguities. The process is primarily sequential with exclusive (XOR) gateways; exception handling returns control to the main flow after resolution. Payment execution itself lies outside the modelled scope.

**2. Participants / Lanes**  
- **Accounts Payable Clerk** (Mary) – primary process executor  
- **Accounts Payable Supervisor** (Rita) – exception handler  
- **Purchasing Officer** (Dan)  
- **Department Manager** (Carlos)  
- **Supplier Relationship Manager** (Karen) – ad-hoc support only  
- **Supplier** (external participant)  
- **Accounting System** (IT system lane / automated tasks)

**3. Start Event**  
Message Start Event: Invoice received (normally by email) by the Accounts Payable Clerk.

**4. Main Sequence Flow (Happy Path)**  

1. **Task [AP Clerk]**: Check whether the invoice is associated with a valid Purchase Order (PO) number.  

   **Exclusive Gateway (XOR): Valid PO present?**  
   - **No** → Exception Path A (Missing/Invalid PO)  
   - **Yes** → Continue  

2. **Task [AP Clerk]**: Log the invoice into the accounting system.  

3. **Task [AP Clerk]**: Forward the invoice to the Purchasing Officer requesting confirmation that the goods or services were received and verification against the PO.  
   *(Message flow: Invoice + request → Purchasing)*  

4. **Task [Purchasing Officer]**: Review invoice details against the PO (quantities, prices, delivery charges) and confirm receipt of goods/services.  

   **Exclusive Gateway (XOR): Invoice matches PO and goods/services confirmed received?**  
   - **No** → Exception Path B (Discrepancy Resolution)  
   - **Yes** → Continue  

5. **Task [Purchasing Officer]**: Send confirmation email/notification to the Accounts Payable Clerk.  
   *(Message flow: Confirmation → AP)*  

6. **Task [AP Clerk]**: Perform formal line-item match of the invoice against the PO in the accounting system (using the Purchasing confirmation).  

   **Exclusive Gateway (XOR): Line items fully match (no remaining discrepancies)?**  
   - **No** → Exception Path B (or escalate if clarification already attempted)  
   - **Yes** → Continue  

7. **Intermediate Event / Automated Task [Accounting System]**: Automatically generate and send notification/email to the Department Manager requesting approval (triggered only after receipt confirmation + successful match).  
   *(Message flow: System notification → Manager)*  

8. **Task [Department Manager]**: Review the invoice details, associated PO, and Purchasing confirmation in the system.  

   **Exclusive Gateway (XOR): Approve?**  
   - **Yes** → Approve in the system → Continue  
   - **No** (suspicious total vs budget, unexpected items – rare, approximately once every couple of months) → Exception Path C (Manager Investigation/Rejection)  

9. **Task [AP Clerk]**: Schedule the approved invoice for payment / add it to the next payment cycle.  

**End Event (Happy Path)**: Invoice scheduled for payment.

**5. Exception / Alternative Paths**  

**Exception Path A – Missing or Invalid PO**  
- **Task [AP Clerk]**: Return the invoice to the Supplier requesting additional details or a revised invoice that includes a valid PO number.  
  *(Message flow to Supplier; optionally notify/involve Karen for supplier outreach.)*  
- Wait for revised invoice (message intermediate event). Upon receipt, loop back to Step 1 (Check PO).  
- If the case is known to be informal/services with no prior PO, or if attempts to obtain a PO remain unresolved → Escalate to AP Supervisor (Rita).  
  - **Task [Rita]**: Coordinate with relevant department heads; create a retrospective PO if appropriate, or decide to reject the invoice. May contact the Supplier directly.  
  - If retrospective PO is created → Return to main flow at Step 2 (Log) or the next logical point.  
  - If rejected → End Event: Invoice Rejected.  

**Exception Path B – Discrepancy** (pricing, quantities, missing/extra items, delivery charges, or terms mismatch)  
Triggered during Purchasing verification or AP system matching.  
- **Task [Purchasing Officer and/or AP Clerk]**: Communicate for clarification. Purchasing may contact the Supplier directly for a corrected invoice or instruct AP to hold the invoice until a corrected version arrives.  
- Optionally invoke **Karen** (Supplier Relationship Manager): Reach out to the Supplier, check the governing contract for correct pricing/terms, and inform AP/Purchasing of the resolution. Karen does not perform system approvals.  
- If easily resolved (clarification or corrected invoice received) → Loop back to the relevant verification or matching step (Step 4 or 6).  
- If the discrepancy cannot be resolved easily → Escalate to AP Supervisor (Rita).  
  - **Task [Rita]**: Contact suppliers, coordinate across departments, clear the exception (or decide rejection).  
  - Once cleared → Return to main flow at the confirmation/match stage, then proceed to Manager approval and payment scheduling.  

**Exception Path C – Manager Rejection or Investigation**  
- **Task [Department Manager]**: Reject the invoice in the system or request that the AP Clerk hold it and investigate further.  
- Investigation may involve AP Clerk, Purchasing, Rita, and/or Karen as needed.  
- If satisfactorily resolved → Return to Manager review (or re-approval).  
- If permanently rejected → End Event: Invoice Rejected / Not Paid.  

**6. Data Objects / Artifacts**  
- Invoice (incoming email/document; revised versions possible)  
- Purchase Order (PO)  
- Goods/Services receipt confirmation (email from Purchasing)  
- Accounting-system records (logged invoice, match results)  
- System notification / approval request  
- Payment-schedule entry  
- Contracts (referenced by Karen for pricing/terms verification)

**7. Message Flows (key interactions)**  
- Supplier → AP Clerk: Original or revised invoice  
- AP Clerk → Purchasing: Forwarded invoice + confirmation request  
- Purchasing → AP Clerk: Confirmation email  
- Accounting System → Department Manager: Automatic approval notification  
- AP ↔ Purchasing ↔ Rita ↔ Karen ↔ Supplier: Clarification, escalation, and resolution communications  

**8. Notes on Ambiguities, Variations, and Modelling Decisions**  
- Matching is modelled as a practical 3-way match (Invoice + PO + Receipt Confirmation). Purchasing performs the primary business verification and receipt confirmation; AP Clerk performs the subsequent formal system line-item match. This respects both Mary’s and Dan’s accounts without contradiction.  
- Exact decision criteria distinguishing “return to Supplier” versus “escalate immediately to Rita for retrospective PO” on missing-PO cases are not fully specified; the model therefore presents both routes, with return as the default and escalation for special/informal cases or unresolved attempts.  
- Karen’s involvement is purely ad-hoc/supportive and is never a mandatory sequential task.  
- No formal separate Goods Receipt Note (GRN) document is mentioned; Purchasing’s confirmation email serves this evidentiary role.  
- Exception frequency is low, but the paths are essential for completeness. After any exception is cleared, the process returns to the normal flow (Purchasing confirmation → Manager approval → scheduling).  
- Permanent rejection or unresolved return to Supplier constitutes alternative end states.  
- The model contains only exclusive gateways and sequential flow; no parallel multi-instance or inclusive gateways are evidenced in the interviews.  

This textual representation is structured so that another person can convert it directly into a visual BPMN diagram (swimlanes, message start/end events, user and service tasks, XOR gateways, message flows, intermediate events for system notifications and waits, and either expanded exception paths or a collapsed exception subprocess with resume links).
