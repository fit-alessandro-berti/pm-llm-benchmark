## 1. Identifying Instance-Spanning Constraints and Their Impact

### 1.1 Prepare and enrich the event log

Before analysis, I would standardize the log into an event table containing:

- Case/order ID
- Activity and lifecycle transition
- Start and completion timestamps
- Resource and resource type
- Order type and due date
- Destination region
- Cold-packing requirement
- Hazardous-material flag
- Batch ID and batch creation/release timestamps
- Interruption, resume, and priority-change events, where available

The event log should be checked for missing lifecycle events, overlapping activity intervals, inconsistent timestamps, and cases that start or end outside the observation period.

A process-mining model should then be built using:

- **Directly-Follows Graphs** to identify common paths and deviations
- **Performance analysis** to decompose cycle time into processing and waiting time
- **Resource-centric analysis** to detect contention and utilization
- **Conformance checking** against operational rules, such as cold-station capacity or hazardous-material limits
- **Object-centric process mining**, if possible, because orders, packing stations, batches, staff, and regulatory capacity are separate but related objects rather than a single case-centered process

### 1.2 Shared cold-packing stations

For each cold-packing station, reconstruct the station occupancy interval:

\[
[\text{Packing start}, \text{Packing complete}]
\]

Then identify orders that are ready for cold packing while all eligible cold stations are occupied.

Useful metrics include:

- Average and percentile queue waiting time for cold packing
- Maximum queue length over time
- Cold-station utilization
- Number of intervals in which all five stations were occupied
- Number of orders waiting while at least one station was unavailable
- Waiting time by order type, region, and arrival period
- Express-order waiting time compared with standard-order waiting time
- Lost or delayed throughput attributable to cold-packing capacity
- Blocking caused by downstream Quality Check capacity

A resource-contention episode can be identified when:

1. An order completes its predecessor activity.
2. It does not start cold packing immediately.
3. All suitable cold stations are occupied, or the order is prevented by a scheduling rule.
4. Another order completes packing and the waiting order then starts.

This allows waiting to be assigned to cold-station contention rather than simply reported as unexplained queue time.

### 1.3 Shipping batches

The log should be joined to batch records using batch IDs or inferred batch membership. For every order, measure:

\[
\text{Batch wait} =
\text{Shipping-label start or release time}
-
\text{Order ready time}
\]

where “ready time” is the completion of the preceding activity, normally Quality Check.

Important metrics include:

- Average and percentile waiting time for batch formation
- Number of orders waiting in each batch
- Batch size and batch fill rate
- Time from first order ready to batch release
- Percentage of batches released on a time trigger versus a size trigger
- Percentage of orders missing their planned dispatch window because of batching
- Waiting time by region, day, and peak period
- Percentage of orders whose processing time is low but total cycle time is high because of batching

A useful counterfactual is to compare actual release time with:

- Immediate label generation
- A maximum waiting-time rule
- The planned route departure time

This quantifies the delivery benefit of batching against its service-time cost.

### 1.4 Priority handling and interruptions

Express orders require analysis of both their own performance and their effect on other orders.

For each activity, reconstruct:

- Queue position before and after an express arrival
- Standard-order processing intervals interrupted or preempted
- Time between express readiness and express activity start
- Delay to standard orders that were displaced
- Additional setup or restart time caused by interruptions
- Number and duration of preemptions by resource and shift

Metrics include:

- Express waiting time and deadline adherence
- Standard-order delay attributable to express priority
- Number of preemptions per 100 orders
- Mean interruption duration
- Resource utilization lost to preemption and restart
- Express service-level improvement versus standard-service-level degradation
- Priority inversions, where an express order still waits behind avoidable standard work

Priority effects should be analyzed by activity. For example, express handling at picking may create a later cold-packing queue, while express handling at packing may delay standard orders and potentially create a Quality Check wave.

### 1.5 Hazardous-material limit

The regulation applies to orders undergoing Packing or Quality Check. The event log must therefore be treated as interval data, not just point events.

For every hazardous order, create intervals:

- Hazardous Packing: packing start to packing completion
- Hazardous Quality Check: QC start to QC completion

At any time \(t\), calculate:

\[
H(t) = \text{number of hazardous orders in Packing or Quality Check at }t
\]

Then measure:

- Maximum observed \(H(t)\)
- Number and duration of intervals at or near the limit of 10
- Number of attempted starts that were delayed because \(H(t)=10\)
- Hazardous-order waiting time attributable to the limit
- Packing and QC utilization for hazardous orders
- Throughput of hazardous orders per hour
- Compliance violations or near misses
- Effect on nonhazardous orders if capacity is reserved or blocked
- Number of orders simultaneously occupying both stages, if the rule counts orders rather than activity instances

The limit should be enforced as a capacity constraint in a resource or state-based conformance model. If the event log shows a start while the count was already 10, this is a compliance exception requiring investigation.

### 1.6 Separating within-instance and between-instance waiting

For each case, total cycle time can be decomposed as:

\[
\text{Cycle time}
=
\text{Activity processing time}
+
\text{Within-process waiting}
+
\text{Between-instance waiting}
+
\text{Other delay}
\]

Examples of **within-instance** delay include:

- Long picking or packing duration
- Rework
- Quality-check failure
- Missing information
- Internal handoff delay when no external resource is constrained

Examples of **between-instance** delay include:

- Waiting for a cold station occupied by another order
- Waiting for a packing or QC capacity slot because the hazardous limit is reached
- Waiting for other orders to complete a shipping batch
- Waiting behind a priority order or being preempted
- Waiting for a shared staff member or station

The distinction can be made using timestamp and state reconstruction:

1. Calculate the time from predecessor completion to activity start.
2. Check whether the required resource was occupied.
3. Check whether the relevant batch was incomplete.
4. Check the hazardous concurrent-order count.
5. Check whether an express order arrived or caused a priority change.
6. Assign the interval to the first applicable blocking cause, or split it among causes if several were active.

Where the log lacks explicit queue or interruption events, I would infer causes using resource calendars, overlap detection, batch IDs, and order attributes, and label the result as inferred rather than observed.

## 2. Analyzing Constraint Interactions

The constraints should not be optimized independently because an improvement in one area can transfer congestion to another.

### Cold packing and express priority

An express cold-packed order may jump ahead of standard cold orders. This can improve express performance but:

- Increase the standard cold-packing queue
- Cause standard orders to miss a shipping batch
- Create a later wave of standard packing
- Increase cold-station utilization toward saturation
- Generate more preemptions and lost setup time

If express orders are frequently released in bursts, strict preemption may be worse than reserving a small capacity share or using a short non-preemptive service rule.

### Batching and hazardous-material limits

If many hazardous orders for one region are batched together:

- They may wait for one another before label generation.
- Their Packing and QC intervals may overlap and approach the limit of 10.
- A full hazardous queue can delay completion of a route batch.
- Releasing too many hazardous orders together can create a regulatory bottleneck.
- Holding hazardous orders for batching may increase their total dwell time even when Packing and QC are available.

Batching policy therefore needs to consider both geographical efficiency and hazardous workload profile, not only destination.

### Hazardous limits and priority handling

An express hazardous order may be unable to start even if staff and stations are free because the facility is already at the regulatory limit. Conversely, prioritizing it may displace a standard hazardous order and prolong the queue.

A priority rule must therefore be:

1. Compliance-safe,
2. Capacity-aware,
3. Deadline-aware.

Priority cannot override the hazardous-material limit.

### Cold packing and batching

A cold order may finish Packing and Quality Check but then wait for a regional batch. During peak demand, the cold station is freed, but downstream batch waiting can hide the benefit of additional cold capacity. Conversely, accelerating batch release may expose a later bottleneck in shipping or route capacity.

### Why interaction analysis matters

A simple KPI such as average packing time may improve while end-to-end delivery worsens. Interaction analysis identifies bottleneck migration and trade-offs between:

- Express service and standard service
- Batch efficiency and order lateness
- Regulatory compliance and throughput
- Resource utilization and queue stability

I would use stratified performance analysis, time-dependent queue plots, causal exploration, and discrete-event simulation to evaluate these effects jointly.

## 3. Constraint-Aware Optimization Strategies

### Strategy 1: Dynamic, constraint-aware allocation of cold-packing capacity

**Primary constraints addressed:** Cold-packing contention, express priority, batching.

#### Proposed changes

- Introduce a scheduling policy based on due date, remaining slack, order type, and batch departure time.
- Use a limited reservation window for express cold orders rather than unrestricted preemption.
- Apply a non-preemptive rule once a standard order has passed a defined packing point, avoiding excessive restart loss.
- Reserve a small flexible capacity portion for express demand only when forecast demand justifies it.
- Move eligible nonperishable work away from cold stations whenever possible.
- Schedule cold orders whose completion is required for an imminent regional batch.

A suitable priority score could combine:

\[
\text{Priority score}
=
w_1(\text{deadline urgency})
+
w_2(\text{express flag})
+
w_3(\text{batch departure proximity})
+
w_4(\text{cold-station waiting time})
-
w_5(\text{preemption cost})
\]

#### Use of data

Historical logs can estimate:

- Cold-order arrival rates by hour
- Express demand by shift
- Average service time by order profile
- Probability of missing a batch if an order is delayed
- Impact of preemption on packing duration

#### Expected outcomes

- Lower cold-packing queue time
- Better express deadline adherence
- Fewer unnecessary interruptions
- Reduced standard-order lateness caused by indiscriminate priority handling
- Better alignment between cold-packing completion and batch departure

Additional capacity should be considered only after confirming that cold packing is the sustained bottleneck. Options include temporary mobile cold stations, cross-training, or extending operating hours during forecast peaks.

---

### Strategy 2: Replace fixed batching with dynamic, deadline-aware batching

**Primary constraints addressed:** Batch waiting, delivery deadlines, hazardous-order accumulation, cold-resource synchronization.

#### Proposed changes

Use a hybrid batching rule:

- Release when the batch reaches a target size,
- Or when a maximum waiting time is reached,
- Or when the next route departure is approaching,
- Or when the earliest order’s remaining delivery slack falls below a threshold.

Batches should also be segmented using operational attributes such as:

- Destination region
- Carrier or route
- Temperature requirement
- Hazardous-material handling requirements
- Service priority

A hazardous order should not be held indefinitely solely to improve batch utilization. A batch can be divided into compliant sub-batches if necessary.

#### Use of data

Historical data can estimate the trade-off between:

- Batch size and transport efficiency
- Batch waiting time and lateness
- Regional order arrival variability
- Hazardous-order concentration
- Route departure reliability

The target batch size and maximum wait should vary by region and time of day rather than being globally fixed.

#### Expected outcomes

- Reduced waiting for batch completion
- Improved on-time dispatch
- Better route utilization without excessive order dwell
- Less accumulation of hazardous orders in Packing and QC
- Fewer cases where one late order holds an otherwise ready batch

---

### Strategy 3: Integrated schedule for express priority and hazardous capacity

**Primary constraints addressed:** Priority handling and hazardous-material limit.

#### Proposed changes

Implement a central dispatching rule for Packing and Quality Check that treats the hazardous limit as a hard constraint.

Before starting a hazardous order, the system checks:

\[
H(t) < 10
\]

If the limit is reached, the order remains queued regardless of express status. Among feasible orders, priority can be determined by:

1. Regulatory feasibility
2. Express status
3. Due-date slack
4. Batch departure urgency
5. Estimated processing time and downstream impact

Use a look-ahead window so the system does not start a large number of standard hazardous orders immediately before an express hazardous order is expected. This avoids a full-capacity condition that blocks the urgent order.

Where permitted, reduce the number of hazardous orders concurrently in QC by scheduling hazardous QC more evenly rather than allowing large waves from Packing.

#### Use of data

Use arrival forecasts and historical transition times to predict:

- Hazardous workload over the next hour
- Expected express arrivals
- Completion of hazardous Packing and QC
- Probability of reaching the regulatory ceiling

#### Expected outcomes

- Continued full regulatory compliance
- Lower hazardous-order queue time
- Improved express performance without unsafe overrides
- Fewer abrupt stops caused by reaching the limit
- More stable use of Packing and QC capacity

A compliance dashboard and automated start-control mechanism should be implemented so the rule is enforced operationally, not only analyzed retrospectively.

---

### Strategy 4: Decouple shipping-label generation from physical batch completion

**Primary constraints addressed:** Batching delay and bottleneck migration.

#### Proposed changes

Where operationally and legally feasible:

- Generate provisional or order-level labels when an order passes Quality Check.
- Finalize route manifests at batch release.
- Allow ready orders to be staged while waiting for the route batch.
- Use a maximum staging dwell time and temperature-control rules for cold goods.
- Separate administrative label generation from the physical movement of all orders in a batch.

This reduces the amount of process work blocked by batch formation while retaining route consolidation.

#### Use of data

Analyze whether label generation itself is a true bottleneck or merely a synchronization point. Compare:

- Time to generate labels
- Time waiting for the batch
- Time from label generation to carrier handoff
- Rate of route or batch changes after early label generation

#### Expected outcomes

- Lower apparent cycle time
- Earlier visibility and staging readiness
- Fewer orders blocked by one incomplete batch
- Better separation between fulfillment work and transportation consolidation

---

### Strategy 5: Peak-period capacity and workload smoothing

**Primary constraints addressed:** All four, particularly peak congestion.

#### Proposed changes

- Forecast cold, express, hazardous, and regional batch demand by time interval.
- Use wave release controls to smooth arrivals into Packing and QC.
- Cross-train staff for cold-packing and hazardous-compatible QC where permitted.
- Add temporary cold capacity or shifts during forecast peaks.
- Stagger hazardous-order release so the concurrency ceiling is not reached suddenly.
- Schedule standard work earlier when express and hazardous demand is forecast to rise.

#### Expected outcomes

- Lower maximum queue lengths
- Reduced need for preemption
- More stable hazardous concurrency
- Improved utilization without sustained saturation
- Better resilience during seasonal peaks

## 4. Simulation and Validation

A discrete-event simulation should be built from the mined process model before implementation.

### Model inputs

The model should be calibrated using the three-month log:

- Interarrival distributions by order type and region
- Activity duration distributions
- Resource calendars and availability
- Number of standard and cold stations
- Staff skills and shift patterns
- Express-order arrival patterns
- Batch formation and route departure rules
- Hazardous-order proportions
- Rework and exception probabilities

Empirical or distribution-fitting methods should be used rather than relying only on averages, since peak behavior and variability drive queues.

### Constraint representation

The simulation must explicitly represent:

1. **Cold-packing stations**  
   A finite capacity of five, with eligibility rules for cold orders and queue disciplines.

2. **Batching**  
   Orders grouped by region and potentially other attributes, with size triggers, time triggers, departure times, and incomplete-batch behavior.

3. **Priority and interruption**  
   Express orders should be modeled with the proposed preemption or reservation rules, including setup, restart, and lost time.

4. **Hazardous-material limit**  
   A shared state variable \(H(t)\) must be maintained across all Packing and QC activities. A hazardous activity cannot start when \(H(t)=10\).

5. **Interactions**  
   The model must allow an order to consume multiple constrained resources over time and must preserve causal relationships between them.

### Scenarios to compare

At minimum, simulate:

- Current-state policy
- Dynamic cold-station priority
- Hybrid batch-release rules
- Integrated express and hazardous scheduling
- Decoupled label generation
- Additional cold capacity or staffing
- Combined strategy

Each scenario should be tested under:

- Normal demand
- Peak demand
- Express surges
- High hazardous-order volume
- Regional demand imbalance
- Resource absence or equipment downtime

### KPIs

Compare scenarios using:

- End-to-end order cycle time
- On-time shipment and delivery proxy
- Express service-level attainment
- Standard-order lateness
- Cold-packing queue time and maximum queue
- Cold-station utilization
- Batch waiting time and batch fill rate
- Hazardous-order waiting time
- Maximum hazardous concurrency and violation count
- Packing and QC throughput
- Number and duration of preemptions
- Work-in-process inventory
- Resource utilization
- Compliance exceptions

Results should include confidence intervals from multiple simulation replications. A strategy should not be accepted merely because it improves average cycle time; it must also avoid unacceptable tail lateness, service inequity, or compliance risk.

## 5. Monitoring Post-Implementation

A process-mining control tower should combine case, resource, batch, and constraint views.

### End-to-end performance

Monitor:

- Median, 90th, and 95th percentile order cycle time
- On-time shipment rate
- On-time rate by order type and region
- Express SLA attainment
- Standard-order lateness
- Work-in-process by activity
- Age of the oldest waiting order

### Cold-packing dashboard

Track:

- Current and historical cold-station utilization
- Queue length by station and shift
- Average and percentile cold-packing wait
- Number of all-stations-busy intervals
- Waiting time by express versus standard orders
- Preemptions and restart losses
- Forecast demand versus available capacity

### Batching dashboard

Track:

- Orders waiting for a batch
- Batch age, size, and fill rate
- Time from first ready order to batch release
- Maximum batch wait breaches
- Orders held past their service threshold
- Batch performance by region and departure window
- Percentage of labels generated early versus at batch release

### Hazardous-material compliance dashboard

Track in near real time:

- Current hazardous count in Packing plus QC
- Maximum count during each shift
- Time spent at 8, 9, and 10 concurrent orders
- Blocked hazardous starts
- Compliance violations or near misses
- Hazardous queue age and throughput
- Hazardous workload forecast for the next planning interval

The count should be calculated from active intervals, not from event counts alone.

### Priority and fairness dashboard

Monitor:

- Express waiting time by activity
- Standard delay caused by express handling
- Number of preemptions
- Average preemption and restart duration
- Priority inversions
- Service-level difference between express and standard orders

### Continuous process mining and alerts

Use conformance rules and alerts such as:

- Cold queue exceeds threshold
- All cold stations occupied for a sustained period
- Batch wait exceeds regional maximum
- Hazardous count reaches 9, triggering a warning
- A start event would violate the hazardous limit
- Express order has insufficient remaining slack
- Standard-order delay caused by repeated priority interruptions exceeds tolerance

Performance should be segmented by shift, weekday, peak period, region, order type, and resource. Monthly reviews should compare observed results with simulation forecasts and update process models as operating conditions change.

The central principle is to monitor not only whether individual activities are fast, but whether orders are being delayed by the shared states of the facility. That is the key to managing instance-spanning constraints without simply moving the bottleneck elsewhere.
