- **First-Call Resolution (FCR) Rate**: Percentage of L1 tickets resolved without escalation, broken down by agent, ticket category, and required skill. This pinpoints L1 agents who either over-escalate or possess untapped expertise.
- **Ticket Type Specialization Index**: For each agent, calculate the Herfindahl-Hirschman Index (HHI) of ticket categories/skills handled. A low HHI indicates generalization; a high HHI suggests specialization. Comparing this against official skill profiles reveals mismatches.
- **Escalation & Reassignment Frequency**: Count of escalations and reassignments per agent, per ticket, and per required skill. This creates a "reassignment cost" profile.

**Process Mining Techniques for Actual vs. Intended Patterns:**

This directly contradicts the intended flat assignment logic.
- **Role Discovery**: By clustering agents based on their activity footprints (e.g., using trace clustering on agent-level logs), I can discover emergent roles. ## 3. Root Cause Analysis for Assignment Inefficiencies

If the tree splits primarily on "time of creation" rather than "required skill," it confirms the round-robin hypothesis.
- **Inaccurate Skill Profiles**: Agents' documented skills don't match their actual resolution capabilities. **Diagnostic**: Perform **Conformance Checking** between the "Required Skill" attribute and the "Agent Skills" attribute at the moment of "Work Start." A high mismatch rate (e.g., 40% of tickets handled by agents lacking the required skill) indicates profile inaccuracy. Cross-reference with resolution success to identify "hidden skills."
- **Poor Initial Ticket Categorization**: The web portal's category selection is often wrong. **Diagnostic**: Use **Variant Analysis**. Cluster cases into two variants: (1) "Smooth" (CreatedAssignWorkResolve) and (2) "Turbulent" (CreatedAssignWorkReassignWorkResolve). Compare the distribution of "Ticket Category" and "Channel" between variants. If "Web Portal" tickets are 3x more likely to be turbulent, the root cause is poor self-service categorization.
- **Lack of Real-Time Workload Visibility**: Dispatchers assign based on static rules, not live queue lengths. **Diagnostic**: Analyze the "Assign L2" timestamp against the assignee's concurrent load at that moment. If assignments frequently go to agents already at >5 concurrent cases, the dispatcher lacks visibility.
- **Insufficient L1 Training/Empowerment**: L1 agents escalate prematurely. **Diagnostic**: For each L1 agent, calculate their "Escalation Rate by Required Skill." Compare this against the "L1 Resolution Rate for that Skill" across all agents. If Agent A05 escalates 90% of "App-CRM" tickets but the L1 average is 40%, Agent A05 is either undertrained or lacks confidence. This is a training gap, not a skill gap.

## 4. Data-Driven Resource Assignment Strategies

### Strategy 1: Skill-Proficiency Weighted Routing (SPWR)

**Issue Addressed**: Current round-robin ignores skill match and proficiency, causing specialists to handle basic tickets and novices to flounder on complex ones.

**PM Insights Leveraged**: The Skill-Required vs. Skill-Matrix and Specialization Efficiency Scores identify which agents are true experts (high resolution rate for skill S) vs. those with only nominal certification.

**Data Required**:
- Historical resolution success rate per agent per required skill (from event log).
- Agent skill proficiency levels (derived from FCR rate for that skill, e.g., "Expert" if >70% FCR, "Intermediate" if 40-70%, "Novice" if <40%).
- Real-time queue length per skill type.

**Implementation**: Replace round-robin with a routing engine that calculates a **Routing Score** for each available agent: `Score = (Proficiency_Weight × Skill_Level) + (1/Current_Queue_Length)`. Tickets are assigned to the agent with the highest score. For P1 tickets, the Proficiency_Weight is increased to prioritize expertise over speed.

**Expected Benefits**: 25-40% reduction in reassignments, 15% improvement in FCR for L1, and 20% reduction in MTTR for P2 tickets as they reach true experts faster.

### Strategy 2: Predictive Skill & Complexity Tagging (PSCT)

**Issue Addressed**: Incorrect initial categorization by users/dispatchers leads to wrong skill tags and subsequent rework.

**PM Insights Leveraged**: Variant analysis shows that tickets with certain keywords in notes (e.g., "VPN," "locked out") have high reassignment rates because they're miscategorized as "Network" when they're actually "Security-IAM."

**Data Required**:
- Historical ticket descriptions/notes (text data).
- Final resolved skill tag (ground truth from event log).
- NLP model trained on historical data to predict required skill and complexity tier (L1/L2/L3) from initial description.

**Implementation**: Integrate a lightweight ML model into the ticket creation workflow. When a ticket is submitted, the model predicts the required skill and suggests a complexity tier. The dispatcher sees this prediction alongside the user's category selection. If they disagree, the system logs this as a "disagreement event" for continuous model refinement.

**Expected Benefits**: 30-50% reduction in miscategorized tickets, leading to a direct 20% decrease in reassignments and a 10% improvement in SLA compliance for P3 tickets that no longer bounce between tiers.

### Strategy 3: Dynamic Escalation Thresholds & L1 Empowerment (DETLE)

**Issue Addressed**: Excessive escalations by L1 agents due to rigid time-based rules or lack of confidence, overloading L2.

**PM Insights Leveraged**: Decision mining reveals that L1 agents escalate based on time-elapsed rather than skill-mismatch. Analysis of "L1 Resolution Rate by Skill" shows that some L1 agents can resolve certain "L2 skills" successfully.

**Data Required**:
- L1 agent resolution rate per skill (from event log).
- Time-to-escalate distribution per agent.
- SLA clock status at escalation moment.

**Implementation**: Implement **Dynamic Escalation Thresholds**. Instead of a fixed 30-minute rule, the system calculates a personalized "Escalation Recommendation" for each L1 agent: "You have resolved 65% of App-CRM tickets in the past. This ticket has similar characteristics. Recommend: Attempt resolution for 15 more minutes." Simultaneously, create an **L1 Skill Extension Program**: Identify L1 agents with >50% FCR for a specific L2 skill and provide targeted micro-training to formalize this skill, expanding the L2-capable pool.

**Expected Benefits**: 20% reduction in escalations to L2, freeing L2 capacity for true P1/P2 issues. L1 job satisfaction improves as they handle more complex work. Overall SLA compliance improves as tickets are resolved at the first point of contact.

### Strategy 4: Real-Time Workload Balancing with Skill Overflow (RWB)

**Issue Addressed**: Uneven workload distribution where some specialists are idle while others are overwhelmed, even within the same skill group.

**PM Insights Leveraged**: Concurrent Case Load analysis reveals that Agent B08 (Networking-Firewall) has 8 tickets while B11 (same skill) has 2, purely due to round-robin assignment.

**Data Required**:
- Real-time concurrent case load per agent.
- Agent skill set and current status (available, busy, break).
- Ticket priority and SLA time remaining.

**Implementation**: Implement a **Workload-Aware Overflow Mechanism**. When a new ticket requires "Networking-Firewall," the system first checks if any agent with that skill is below the 75th percentile concurrent load. If all are above, it triggers a "Skill Overflow" protocol: the ticket is offered to L2 agents with adjacent skills (e.g., "Networking-General") who have capacity, paired with a senior mentor (via chat) for guidance. This is logged as a "stretch assignment" for skill development.

**Expected Benefits**: 30% improvement in workload equity (measured by Gini coefficient of concurrent load), 15% reduction in queue wait times for bottleneck skills, and accelerated skill development across the team.
