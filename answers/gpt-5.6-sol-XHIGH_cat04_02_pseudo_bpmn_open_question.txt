A strong redesign would treat “standard” and “custom” not as permanently exclusive paths, but as collections of work that can be activated based on request attributes. A custom request may still need standard credit and inventory checks, while an apparently standard request may contain one non-standard feature.

## 1. Proposed future-state process

```text
Start
  -> Capture and Normalize Request
  -> Gateway: Is Required Information Complete?
       [No]  -> Request Missing Information
                -> Wait for Customer Response
                -> Timer/Escalation if no response
                -> Revalidate Information
       [Yes] -> Continue

  -> Parallel:
       - Enrich Customer and Product Data
       - Apply Hard Business Rules
       - Predict Customization, Complexity, and SLA Risk
     -> Join

  -> Gateway: Is Routing Confidence Sufficient?
       [No]  -> Human Triage
       [Yes] -> Continue

  -> Inclusive Gateway: Which Work Packages Are Required?
       - Standard Validation
       - Credit/Compliance Check
       - Inventory/Capacity Check
       - Custom Feasibility Analysis
       - Specialist Review
     -> Join only the activated work packages

  -> Gateway: What Is the Feasibility Outcome?
       [Feasible]
       [Feasible with Changes] -> Generate Alternatives / Customer Clarification
       [Uncertain]             -> Specialist Escalation
       [Not Feasible]          -> Offer Alternatives
                                  -> If rejected/no alternative: Rejection Notice -> End

  -> Parallel:
       - Calculate Predictive Delivery Date
       - Prepare Price/Quotation
     -> Join

  -> Gateway: Approval Policy
       [Auto-approved / No approval required]
       [Single manager approval]
       [Specialist or multi-level approval]

  -> If Human Approval:
       Dynamically Assign Approver
       -> Boundary Timer: Reassign/Escalate if SLA at risk
       -> Gateway: Approved, Conditionally Approved, or Rejected
            [Conditional] -> Apply Conditions and Recalculate Affected Items
            [Rejected]    -> Structured Remediation Subprocess
                              -> Gateway: Remediation Possible?
                                   [Yes] -> Rerun only affected work
                                   [No]  -> Offer Alternative or Close

  -> If Customer Acceptance Required:
       Send Proposal
       -> Event-Based Gateway:
            [Accepted]
            [Change Requested] -> Rerun affected work
            [Timeout]          -> Reminder/Escalation/Close

  -> Generate Final Invoice or Order
  -> Send Confirmation
  -> End
```

A non-interrupting monitoring subprocess can operate throughout the process to detect SLA risk, integration failures, stalled tasks, or changes in customer priority.

## 2. Changes to the existing tasks

| Existing element | Proposed redesign |
|---|---|
| **Task A: Receive Customer Request** | Replace simple receipt with omnichannel digital intake. Use APIs, structured forms, OCR or language extraction for email and attachments, duplicate detection, and immediate field validation. Automatically acknowledge receipt and expose status through a portal. |
| **Check Request Type XOR** | Replace the binary gateway with a rules-plus-predictive triage service. Produce scores such as probability of customization, expected effort, feasibility risk, and probability of missing an SLA. Use a confidence gateway: high-confidence requests route automatically; low-confidence requests go to human triage. |
| **Task B1: Standard Validation** | Convert deterministic checks into a business-rules service. Requests satisfying all rules move through touchlessly; only exceptions create human tasks. Rules should be versioned outside the process model, for example through a decision table. |
| **Task C1: Credit Check** | Call the credit service asynchronously and reuse recent valid results where policy permits. Skip the check for prepaid or otherwise exempt orders. Route marginal or unavailable results to an exception queue rather than blocking every request. |
| **Task C2: Inventory Check** | Use real-time available-to-promise information, including warehouse, supplier, and production capacity. Optionally reserve scarce inventory for high-probability orders and suggest substitutions or split deliveries when stock is inadequate. |
| **Parallel Check Gateway** | Use an inclusive gateway rather than always running every check. Activate only checks required by product, payment method, geography, value, and risk. Required checks can still run in parallel. |
| **Task D: Calculate Delivery Date** | Replace static lead-time calculations with predictive ETA calculation based on inventory, supplier reliability, production workload, geography, and current backlog. Return a confidence range and alternative dates rather than a single potentially unreliable date. |
| **Task B2: Custom Feasibility Analysis** | Turn this into a modular subprocess. In parallel, evaluate engineering constraints, capacity, supplier availability, regulatory requirements, cost, and delivery impact. A product configurator or constraint engine can automatically resolve common variations, leaving novel cases to specialists. |
| **Is Customization Feasible?** | Expand the binary gateway to four outcomes: feasible, feasible with modification, uncertain, and infeasible. “Feasible with modification” should generate viable alternatives; “uncertain” should trigger specialist review. |
| **Task E1: Prepare Custom Quotation** | Integrate configure-price-quote functionality. Automatically assemble configuration, cost, margin, lead time, terms, and reusable quote text. Pricing outside margin or discount guardrails should trigger approval; ordinary quotations should not. |
| **Task E2: Send Rejection Notice** | Make rejection a last resort. First generate alternative configurations, delivery dates, or quantities. Any adverse or sensitive decision should receive human review. Notices should contain understandable reasons and next-step options. |
| **Is Approval Needed?** | Replace the static decision with a risk-based approval policy. Inputs can include order value, margin, discount, customer risk, customization novelty, contractual deviation, and predicted failure probability. Low-risk work can be auto-approved; higher-risk work can be routed to the appropriate authority level. |
| **Task F: Obtain Manager Approval** | Prepopulate the approval task with all relevant evidence and a recommended action. Assign it through a skills- and capacity-based resource broker rather than a fixed role. Add timers for reminder, delegation, reassignment, and escalation. |
| **Is Approval Granted?** | Add “conditionally approved” and “expired” outcomes. Conditional approval should identify exactly what must change, allowing only affected calculations to be rerun. |
| **Task H: Re-evaluate Conditions** | Replace the unstructured loop with a reason-coded remediation subprocess. A rejected price should rerun pricing, while a delivery issue should rerun capacity and ETA. Limit the number of iterations and escalate repeated failures to avoid infinite loops. |
| **Task G: Generate Final Invoice** | Generate the final invoice or order automatically through the ERP after all internal approvals and, where applicable, customer acceptance. Validate tax, currency, billing address, and contract terms before posting. |
| **Task I: Send Confirmation** | Make communication continuous rather than only final. Send acknowledgment, missing-information requests, approval or delay updates, proposal notifications, and final confirmation through the customer’s preferred channel. |

## 3. Dynamic resource allocation

Human tasks should be placed in shared, skill-based queues. A resource-allocation service can rank candidates using:

- Required product, engineering, regulatory, or language skills
- Current workload and estimated task duration
- Request age and contractual SLA
- Customer value and urgency
- Predicted complexity and escalation probability
- Continuity, such as assigning a returning request to the previous analyst

Boundary timers should automatically reassign tasks when the expected completion time exceeds the remaining SLA. However, pure priority optimization can starve low-value or complex work, so aging rules and maximum wait thresholds are necessary.

Workforce planning can also use predicted arrival volume and complexity to schedule custom-analysis specialists before demand peaks.

## 4. Predictive analytics and controls

Useful models include:

1. **Customization propensity:** Identifies requests likely to need non-standard handling from text, product combinations, requested dates, attachments, and customer history.
2. **Complexity and effort prediction:** Estimates specialist time and selects the appropriate resource pool.
3. **Feasibility prediction:** Prioritizes likely feasible cases but should not independently reject a request.
4. **SLA-breach prediction:** Detects requests likely to become late and triggers early escalation or customer communication.
5. **Approval prediction:** Helps assemble evidence and route approval, but formal rules should remain authoritative where compliance is involved.
6. **Delivery-date prediction:** Produces a date range based on current operational conditions.

The routing model should operate behind hard policy rules. High-confidence predictions may be applied automatically; low-confidence cases should be reviewed. Every override and final outcome should be captured as feedback for model improvement.

Models also require monitoring for drift, false-routing rates, unfair outcomes, and deteriorating accuracy. Protected or sensitive attributes should not be used to disadvantage customers, and no rejection should be based solely on an opaque prediction.

## 5. Expected effects

### Turnaround time

The largest reductions should come from:

- Straight-through processing for ordinary requests
- Detecting missing information immediately
- Running independent checks in parallel
- Skipping checks that do not apply
- Routing complex work correctly on the first attempt
- Removing approval from low-risk cases
- Recalculating only affected outputs after a change
- Reassigning stalled human tasks before an SLA breach

Both median time and tail performance should be measured; optimization that improves the average but leaves difficult requests waiting is insufficient.

### Customer satisfaction

Customers should receive faster acknowledgment, more reliable delivery estimates, proactive status updates, and alternatives instead of generic rejections. Self-service configuration and quotation can further reduce delays. Conversely, incorrect predictive routing or unexplained automated decisions can reduce trust, so transparency and easy access to human review are important.

### Operational complexity

The redesigned process is more technically complex. It requires:

- Reliable integrations with CRM, ERP, inventory, credit, and pricing systems
- Event correlation for asynchronous responses
- Versioned business rules
- Model deployment and monitoring
- Exception and compensation handling
- Audit trails for automated decisions
- Data-quality and security controls

This complexity can be contained by implementing each major capability as a reusable subprocess or service rather than embedding all logic in one BPMN model.

## 6. Measures of success

The redesigned process should be evaluated using:

- Median and 90th/95th percentile cycle time
- Percentage of requests processed touchlessly
- First-time-right routing rate
- Human touches per request
- Approval waiting time
- Custom-feasibility turnaround time
- Rework and loop frequency
- SLA attainment
- Delivery-date prediction accuracy
- Quote acceptance and conversion rate
- Customer satisfaction
- Routing-model precision, recall, override rate, and fairness indicators
- Queue aging and resource utilization

A practical rollout would begin with data capture, rules automation, and process instrumentation; add dynamic queues next; and introduce predictive routing initially in “shadow mode” before allowing high-confidence cases to route automatically.
