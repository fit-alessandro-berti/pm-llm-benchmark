A redesigned version of the process should move from a mostly sequential, rule-driven flow to an **intelligent case-management process**: simple requests are handled touchlessly, while uncertain or high-value requests are dynamically routed to the right people and tools early.

## 1. Redesigned High-Level Flow

```text
Start
  --> Receive Request through portal/API/email ingestion
  --> Extract and validate request data automatically
  --> Enrich request with customer, product, inventory, credit, and historical data
  --> Predict request type / customization likelihood / risk / expected effort
  --> Gateway: Is request complete and sufficiently confident?
       --> No: Automated request-for-information or exception work queue
       --> Yes:
            --> Gateway: Route request
                 --> Touchless Standard Lane
                 --> Assisted Standard Lane
                 --> Custom Fast-Track Lane
                 --> Complex Custom Case Subprocess
  --> Generate quote / delivery commitment / invoice as appropriate
  --> Risk-based approval decision
  --> Send confirmation and track fulfillment
  --> Capture outcome data for continuous model and rule improvement
End
```

Rather than treating “standard” versus “custom” as a fixed customer-provided classification, the redesigned process uses data and predictive analytics to determine the likely path as early as possible.

# 2. Changes to Individual Tasks and Process Stages

## Task A: Receive Customer Request

### Current state
The process begins when a request is received, but it does not specify how data is captured, validated, or standardized.

### Proposed redesign
Replace Task A with an automated **Request Intake and Data Normalization subprocess**.

Possible capabilities:

- Web portal forms with mandatory fields and guided questions.
- API integration for major customers submitting requests from their own procurement systems.
- OCR and natural-language processing for requests received by email or uploaded documents.
- Automatic extraction of:
  - Customer ID
  - Product/service requested
  - Quantity
  - Delivery location
  - Requested due date
  - Customization requirements
  - Contract terms
  - Technical specifications
- Duplicate-request detection.
- Automatic validation against customer master data and product catalogs.
- Real-time indication to the customer if information is missing.

### New gateway: “Is Request Data Complete?”
- **Yes:** Continue to automated enrichment and routing.
- **No:** Trigger an automated clarification request or put the request into a “missing information” queue.
- For high-value or time-sensitive requests, assign a customer-service specialist immediately rather than waiting for the customer to respond.

### Effect
This reduces delays caused by incomplete requests and avoids spending specialist time manually interpreting routine requests.

## 3. Replace “Check Request Type” with Intelligent Classification

## Current XOR Gateway: “Check Request Type”

The original model assumes the request can be classified simply as Standard or Custom. In practice, many requests fall into a middle category: mostly standard but requiring a small exception, alternative delivery date, unusual quantity, or limited configuration.

### Proposed redesign
Introduce a **Request Classification and Predictive Routing Engine** before selecting the process path.

The engine can use:

- Product and configuration rules
- Customer history
- Historical quotation outcomes
- Text analysis of free-form request descriptions
- Prior technical exceptions
- Inventory availability
- Margin expectations
- Requested delivery dates
- Previous customizations requested by similar customers

### Predictive outputs
For each request, calculate:

- Probability that customization is required
- Probability that the request can be fulfilled from standard inventory
- Expected complexity/effort score
- Expected approval risk
- Likelihood of rejection
- Expected delivery-date confidence
- Customer priority or churn risk
- Estimated revenue and margin

### New gateway: “What Is the Best Fulfillment Path?”

Possible routes:

1. **Touchless Standard Path**  
   High confidence that the request is standard, valid, available, and within commercial rules.

2. **Assisted Standard Path**  
   Mostly standard, but requires a human check—for example, unusual delivery timing or a moderate credit concern.

3. **Custom Fast-Track Path**  
   Customization is likely, but the request closely matches a pre-approved custom template or known configuration.

4. **Complex Custom Case Subprocess**  
   New engineering work, nonstandard commercial terms, large quantities, or high technical uncertainty.

5. **Exception / Information Needed Path**  
   Request lacks enough data, violates a rule, or has low model confidence.

### Effect
This avoids sending every apparently custom request through the same costly feasibility process. It also identifies custom work earlier, preventing late-stage rework.

# 4. Standard Validation Path

## Task B1: Perform Standard Validation

### Current state
Standard validation is a distinct manual-looking task followed by credit and inventory checks.

### Proposed redesign
Automate most validation through a **Rules-Based Standard Order Validation subprocess**.

Automated checks could include:

- Product code and configuration validity
- Customer eligibility
- Contract pricing
- Minimum order quantity
- Delivery-region restrictions
- Regulatory or export restrictions
- Customer credit status
- Order value thresholds
- Existing open-order limits
- Availability of required capacity or stock

### New gateway: “Can the Request Be Automatically Accepted?”
- **Yes:** Generate a committed quote or order confirmation directly.
- **No, but resolvable exception:** Send to an assisted-standard work queue.
- **No, likely custom:** Reclassify and send to the Custom Fast-Track or Complex Custom subprocess.
- **No, impossible or prohibited:** Automatically produce a structured rejection or alternative-offer workflow.

### Dynamic resource allocation
The assisted-standard queue can be prioritized by:

- Customer service-level agreement
- Revenue/margin potential
- Requested delivery date
- Customer strategic tier
- Risk score
- Queue age
- Specialist availability

Work should be allocated based on skill rather than first-in/first-out assignment. For example, export exceptions go to export specialists, pricing exceptions to commercial analysts, and delivery exceptions to supply-planning staff.

# 5. Parallel Checks: Credit, Inventory, and Additional Real-Time Checks

## Current state
The standard path runs Credit Check and Inventory Check in parallel.

### Proposed redesign
Keep the parallel concept, but expand it into an event-driven **Real-Time Fulfillment Assessment subprocess**.

Possible parallel checks:

- Credit and payment-risk check
- Inventory availability check
- Production-capacity check
- Supplier lead-time check
- Delivery and logistics capacity check
- Contract-pricing validation
- Regulatory/compliance screening
- Margin validation
- Customer-specific service-level validation

### Improvement: avoid waiting for every check when unnecessary
Not every request requires all checks. A decision/rules engine can determine which checks apply.

For example:

- Existing low-risk customers may not require a full credit review.
- Stocked products may not require a production-capacity calculation.
- Domestic orders may not require export compliance checks.
- Contract customers may bypass standard price validation.

### New gateway: “Are Any Blocking Exceptions Found?”
- **No:** Continue automatically.
- **Resolvable exception:** Route to the appropriate expert queue.
- **Critical exception:** Offer alternatives, request customer changes, or reject.

### Predictive enhancement
Inventory and capacity forecasting can identify likely shortages before they become blocking failures. If a product is likely to be unavailable by the requested date, the process can automatically propose:

- An alternative product
- Split delivery
- A different delivery date
- A substitute fulfillment location
- Expedited production, if economically justified

### Effect
The process becomes faster because simple requests need fewer checks, while complex requests receive more targeted analysis.

# 6. Task D: Calculate Delivery Date

## Current state
Delivery-date calculation occurs after all standard parallel checks are complete.

### Proposed redesign
Convert Task D into a **Dynamic Available-to-Promise / Capable-to-Promise service**.

Instead of providing a static calculation, the service should consider:

- Current inventory
- Reserved inventory
- Production schedules
- Supplier lead times
- Transportation constraints
- Warehouse capacity
- Customer priority
- Promised dates for existing orders
- Probability of delay based on historical patterns

### Predictive analytics
A predictive delivery model can provide:

- Most likely delivery date
- Confidence range, such as “delivery expected between 10–12 June”
- Delay risk score
- Recommended fulfillment source
- Suggested alternative dates or split-shipment options

### New gateway: “Can the Requested Date Be Met?”
- **Yes:** Continue with the confirmed date.
- **No:** Automatically generate options:
  - Alternative date
  - Partial shipment
  - Alternative product or site
  - Premium expedite option
- If the customer’s acceptance is needed, issue a customer decision request rather than holding the process internally.

### Effect
Customers receive more realistic commitments, reducing later disappointments and inbound status inquiries.

# 7. Custom Feasibility Path

## Task B2: Perform Custom Feasibility Analysis

### Current state
All custom requests are routed to one feasibility analysis task.

### Proposed redesign
Replace this with a tiered **Customization Assessment subprocess**.

## Tier 1: Configuration-Based Customization
For requests that match known product options:

- Use a product configurator.
- Apply engineering and commercial rules automatically.
- Calculate pricing and lead time automatically.
- Generate a quote without full engineering involvement.

## Tier 2: Similarity-Based Customization
For requests that are not directly configurable but resemble previous work:

- Use historical case retrieval.
- Recommend prior designs, bills of materials, pricing, lead times, and risks.
- Route to a specialist with experience in similar requests.

## Tier 3: Full Engineering Feasibility
For genuinely new or high-risk requests:

- Create a cross-functional case.
- Assign engineering, supply chain, finance, sales, and compliance tasks in parallel where possible.
- Use a shared digital workspace rather than handoffs through email.
- Apply deadlines and escalation rules.
- Allow asynchronous review rather than waiting for every stakeholder in sequence.

### New gateway: “Customization Complexity Level?”
- **Low:** Automated configuration and quotation.
- **Medium:** Specialist review with system recommendations.
- **High:** Full engineering/change-control subprocess.

### Dynamic resource allocation
Assign complex customization requests based on:

- Technical domain expertise
- Current workload
- Historical success rate with similar requests
- Geographic/customer knowledge
- Required certifications
- Urgency and expected value

This is more effective than assigning work only by organizational department.

# 8. Task E1: Prepare Custom Quotation

### Current state
Quotation preparation follows feasibility approval.

### Proposed redesign
Use a **Quotation Generation and Optimization service**.

The service can automatically assemble:

- Configured product/service scope
- Bill of materials or service estimate
- Price based on cost, margin, contract, and market rules
- Delivery date with confidence level
- Assumptions and exclusions
- Approval conditions
- Alternative options, such as “standard,” “modified standard,” and “fully custom”
- Digital acceptance workflow

### Predictive and decision-support capability
The quotation tool can recommend:

- Price likely to maximize win probability and margin
- Discount limits based on customer history
- Suggested alternative configurations
- Whether a customer is likely to accept a longer delivery date
- Whether the request has a high chance of becoming unprofitable

Human commercial review remains appropriate for high-value or strategically important quotes.

### Effect
Quotation time drops significantly, while sales staff focus on negotiating and relationship management rather than document creation.

---

# 9. Task E2: Send Rejection Notice

### Current state
Infeasible customization leads to rejection and process termination.

### Proposed redesign
Do not treat infeasibility as only a rejection scenario. Create an **Alternative Resolution subprocess**.

### New gateway: “Is an Alternative Offer Available?”
- **Yes:** Offer:
  - A standard product alternative
  - A modified requirement
  - A later delivery date
  - A different quantity
  - A premium engineering option
  - A partner or substitute product
- **No:** Send a transparent rejection with a reason code and, where appropriate, a suggestion to contact an account representative.

### Effect
This can convert otherwise rejected opportunities into revenue and improves the customer experience by providing actionable alternatives.

---

# 10. Approval Process Redesign

## Current state
A generic “Is Approval Needed?” gateway is followed by manager approval and then a separate approval-granted decision.

### Proposed redesign
Replace generic approval with a **risk-based approval matrix**.

Approval requirements can depend on:

- Discount level
- Margin below threshold
- Credit risk
- Contract deviation
- Delivery commitment risk
- Engineering complexity
- Regulatory exposure
- Total order value
- Customer strategic importance
- Predicted probability of failure or rework

### New gateway: “Does the Request Exceed an Approval Threshold?”
- **No:** Straight-through processing.
- **Yes:** Route to the required approver or approval group.
- **Urgent/high-value:** Start approval tasks in parallel where permissible.

### Improve Task F: Obtain Manager Approval
Use a mobile-friendly approval workflow with:

- A summarized decision packet
- Recommended action from the analytics engine
- Financial, operational, and customer-impact data
- Deadline/escalation rules
- Delegated approvers when managers are unavailable

### Improve Task H: Re-evaluate Conditions
Instead of looping broadly back to Task E1 or Task D, capture the explicit reason for rejection:

- Price/margin issue
- Delivery-date issue
- Credit issue
- Engineering feasibility issue
- Contract/compliance issue

### New gateway: “What Must Be Reworked?”
Route only to the relevant task:

- Pricing issue  Quotation optimization
- Delivery issue  Delivery promise recalculation
- Technical issue  Custom feasibility team
- Credit issue  Payment terms or finance review
- Missing business justification  Sales owner

This avoids unnecessary rework and prevents repetitive loops.

# 11. Task G: Generate Final Invoice

### Current state
Invoice generation occurs after approval.

### Proposed redesign
Separate the commercial commitment from invoicing where appropriate.

For many businesses, the immediate next step after approval should be:

1. Generate final quote/order confirmation.
2. Obtain customer acceptance, if necessary.
3. Create the sales order.
4. Trigger fulfillment.
5. Generate invoice according to contractual billing milestones.

For example, custom work may require:

- Deposit invoice at order acceptance
- Progress invoice after design approval
- Final invoice at shipment or completion

### Automation opportunities
- ERP integration for order and invoice creation.
- Automatic tax calculation.
- Contract-based payment terms.
- Electronic invoicing.
- Validation that approved terms match invoiced terms.

### Effect
The process becomes financially accurate and better aligned with real operational fulfillment.

# 12. Task I: Send Confirmation to Customer

### Current state
A confirmation is sent only near the end of the process.

### Proposed redesign
Use proactive, milestone-based customer communication.

Possible automated messages:

- Request received
- Missing information required
- Request classified as custom and under review
- Quote available
- Alternative proposal available
- Approval pending, if appropriate to disclose
- Order accepted
- Estimated delivery date
- Delivery-date change detected
- Shipment dispatched
- Invoice issued

Customers should have a self-service portal showing request status, assumptions, documents, delivery confidence, and available actions.

### Effect
Even if internal processing time cannot always be reduced, transparency improves perceived speed and customer satisfaction.

# 13. Suggested New Subprocesses

## A. Intelligent Intake and Triage Subprocess
Handles extraction, validation, enrichment, duplicate detection, and initial routing.

## B. Exception Management Subprocess
Handles incomplete data, policy violations, unusual terms, low-confidence classification, and failed automated checks.

## C. Customization Assessment Subprocess
Uses low-, medium-, and high-complexity paths rather than one universal feasibility task.

## D. Alternative Offer Subprocess
Produces substitute products, revised dates, split deliveries, or modified specifications when the original request is infeasible.

## E. Risk-Based Approval Subprocess
Uses thresholds and decision rules rather than sending all exceptions to a generic manager.

## F. Continuous Learning and Process Monitoring Subprocess
Captures outcomes such as:

- Whether classification was correct
- Whether the quote was accepted
- Actual versus promised delivery date
- Actual margin versus estimated margin
- Approval outcome
- Rework reason
- Customer satisfaction score
- Time spent in each queue

This data improves both predictive models and operational rules over time.

# 14. Operational Performance Impact

## Turnaround time
Turnaround time should improve primarily through:

- Straight-through processing for low-risk standard requests.
- Early identification of missing information.
- Selective rather than universal validation checks.
- Parallel execution of necessary checks.
- Automated quotation and delivery-date calculation.
- Faster routing to the right specialist.
- Targeted rework instead of broad process loops.

A mature implementation can move many standard requests from hours or days to minutes.

## Resource utilization
Specialists spend less time on repetitive work and more time on exceptions, engineering judgment, negotiations, and strategic customers.

Dynamic allocation also reduces bottlenecks. For example, when one feasibility team has excess workload, requests can be routed to another qualified team rather than waiting in a static departmental queue.

## Customer satisfaction
Customer experience improves through:

- Faster responses
- More accurate delivery promises
- Fewer requests for missing information
- More consistent quotations
- Proactive status updates
- Alternatives instead of simple rejection
- Better handling of unique requirements

## Revenue and margin
Predictive routing and pricing guidance can improve conversion rates while protecting margin. The business can identify high-value custom opportunities earlier and avoid investing engineering effort in requests with a low likelihood of conversion or poor profitability.

# 15. Added Operational Complexity and Risks

The redesign also introduces complexity that must be managed.

## Integration complexity
The process will likely need integration with:

- CRM
- ERP
- Inventory and warehouse systems
- Production planning systems
- Pricing engine
- Credit-risk service
- Product configurator
- Document management tools
- Customer portal
- Workflow/case-management platform

## Data quality dependency
Predictive routing is only as reliable as the underlying data. Missing product data, inaccurate inventory data, inconsistent reason codes, or poor historical records can produce incorrect recommendations.

## Model governance
Predictive models should be monitored for:

- Accuracy drift
- Bias toward certain customers or request types
- Excessive false positives for “custom” classification
- Inappropriate pricing or credit recommendations
- Lack of explainability for high-impact decisions

High-risk decisions should retain human review and provide an explanation of why the model made its recommendation.

## Change management
Employees may resist automated routing or recommendations if they believe expertise is being replaced. The implementation should position automation as decision support and workload reduction, particularly for complex work that benefits from human judgment.

# 16. Recommended BPMN Logic in Practice

A strong target design would use three major lanes:

1. **Automated processing lane**  
   Intake, classification, validation, enrichment, quote generation, status notifications, and routine order creation.

2. **Specialist exception lane**  
   Handles unclear, nonstandard, low-confidence, or policy-exception requests.

3. **Complex custom case lane**  
   Handles engineering-intensive, high-value, high-risk, or strategically significant requests.

The central design principle is:

> Automate the predictable, escalate the uncertain, and actively manage the valuable.

This produces a process that is faster for routine customers, more responsive for non-standard requests, and more scalable as request volume and product complexity grow.
