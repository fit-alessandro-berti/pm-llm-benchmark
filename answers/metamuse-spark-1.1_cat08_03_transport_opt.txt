As a Process Mining Consultant for Speedy Parcels, I propose a multi-level, end-to-end mining approach. The key is not treating this as one flat process, but as an interacting set of processes: **Vehicle-Day, Driver Shift, and Package Journey**.

### 1. Process Discovery and Conformance Checking

#### A. Preprocessing and Event Log Integration

The raw data is not ready for mining. We need a unified, semantically enriched event log.

**Step 1: Definition of Case Notions - Multi-Perspective Log**
A single case ID will not work. I will create a multi-dimensional Event Store and then project three logs:
*   **Case ID 1: Vehicle-Day `V12-20241205`** - This is the primary operational case. Start: `Start Shift / Depart Depot`, End: `Arrive Depot / End Shift`. All events for that vehicle that day belong to it.
*   **Case ID 2: Package Journey `P9876`** - Tracks end-to-end parcel lifecycle: `Route Assigned -> Loaded -> Arrive Customer -> Delivery Success/Failed -> [Re-attempt]`. This allows failed delivery analysis.
*   **Case ID 3: Tour Segment** - To analyze micro-behavior, I will segment GPS.

**Step 2: Data Fusion Pipeline**

1.  **Time Synchronization & Cleaning:** Normalize all timestamps to UTC. GPS trackers often drift. Align scanner events, which are human-triggered and more reliable for service time, as ground truth anchors.
2.  **GPS Enrichment and Abstraction:** Raw GPS is too low-level: 1 ping every 10-15 seconds = 3000+ events/day. This creates spaghetti models. We abstract:
    *   Geofencing: Depot, Customer locations, Fuel Stations.
    *   Activity Inferencing: Use speed < 5km/h for >3min + Ignition On = `Traffic Jam / Idle`. Speed 0 + Ignition Off = `Unscheduled Stop`. Speed profile + map-matching = `Travel Segment` with distance calculated via Haversine.
    *   Convert continuous trace into discrete events: `Travel Started`, `Traffic Delay Start/End`, `Idle - Parking Search`.
3.  **Semantic Mapping:** Map all systems to a standard XES schema: `case_id, activity, timestamp, resource [Driver/Vehicle], attributes [PackageID, Lat/Lon, Speed, Reason Code]`.
4.  **Log Enrichment:** Join Dispatch data as case attributes: Planned Sequence, Planned ETA, Customer Time Window, Package Weight/Volume.

**Challenges to Anticipate:**
*   **Granularity Mismatch:** GPS is high-frequency, scanner is low-frequency. Abstraction is essential or discovery algorithms will fail.
*   **Data Quality:** Scanner events missed when driver forgets to scan; GPS gaps in dense urban canyons; Maintenance logs may be entered days later. Need to flag incomplete cases.
*   **Correlation Problem:** A single `Arrive Customer` scanner event at 08:25 must be correlated with the preceding GPS `Unscheduled Stop` to calculate true `Parking + Walking Time`.
*   **Noise:** `Low Speed Detected` is an interpretation, not an event. Must filter false positives.

#### B. Process Discovery - Visualizing the *Actual* Process

A simple Directly-Follows Graph [DFG] will show spaghetti due to deviations. My approach:

1.  **Baseline Discovery with Filters:** Use **Heuristics Miner or Inductive Miner - Infrequent [IMf 20%]** in PM4Py/Celonis to discover the 80% happy path: `Start Shift -> Route Assigned -> Depart Depot -> [Travel -> Arrive Customer -> Delivery Success -> Depart Customer] loop -> Arrive Depot -> End Shift`.
2.  **Hierarchical Discovery:** Mine two layers:
    *   **High-Level Tour Model:** At Vehicle-Day level to see deviations like `Travel -> Unscheduled Stop -> Maintenance` or loops: `Delivery Failed -> Re-attempt later same day`.
    *   **Low-Level Service Model:** At stop level: `Arrive Customer [GPS] -> Search Parking -> Walk -> Scan Arrive -> Handover Attempt -> Scan Success/Fail -> Walk back -> Depart`. Dwell time will be calculated between `Arrive Customer [GPS]` and `Depart Customer [Scanner/GPS]`.
3.  **Variant Analysis:** This is critical. Cluster cases by trace variant. We will likely see: Variant 1 - Perfect Tour 38%, Variant 2 - Tour with 1+ Failed Deliveries 25%, Variant 3 - Tour with Unscheduled Stop + Overtime 12%, etc.

#### C. Conformance Checking - Planned vs. Actual

We will treat the **Dispatch System Planned Route** as the reference model. This is not a BPMN model but a sequence with constraints.

1.  **Technique:** Use **Alignment-based Conformance Checking**. Create a reference model for each Vehicle-Day: Planned sequence `C1->C2->C3...` plus constraints `C1 must be before C1's Time Window End`.
2.  **Deviations to Quantify:**

    *   **Control-Flow:** Sequence deviations - Driver did C3 before C2 [route violation]. Skipped stop `[log move]`. Added unplanned stop `Engine Warning` or `Fuel Stop` or `Personal Stop` `[model move]`.
    *   **Temporal:** `Punctuality Deviation = Actual Arrival - Planned ETA`. `Service Time Deviation = Actual Dwell - Planned Service Time [e.g., 3 min]`. Use token replay to show time overruns on edges.
    *   **Geographic:** Map-match actual GPS vs planned route polyline. Detect detours: `Distance Actual / Distance Planned > 1.2`.
3.  **Output:** A conformance rate per tour, driver, and district. Visualized as a **Conformance Heatmap** on the discovered model - e.g., red edges where drivers consistently deviate from planned sequence around 14:00 in inner city.

### 2. Performance Analysis and Bottleneck Identification

#### Key KPIs Calculable from the Fused Log:

| Category | KPI | Calculation from Event Log |
| :--- | :--- | :--- |
| **Punctuality** | On-Time Delivery Rate, Late Delivery Rate, Avg. Delay | Count of `Delivery Success` where `Arrive Customer <= Time Window End` / Total. Avg `Arrive - Planned ETA` |
| **Efficiency** | Avg. Time per Stop | `Depart Customer - Arrive Customer [GPS]` |
| **Efficiency** | Travel vs Service Ratio | `Sum[Travel Time] / Sum[Service Time]` per Vehicle-Day. High ratio = inefficient routing. |
| **Cost** | Fuel per km / Idling % | Fuel proxy: `Sum[Travel Distance * speed-based factor] + Idle Duration`. Idle % = `Time with Speed<5 & Ignition On / Total Tour Time` |
| **Utilization** | Vehicle Utilization Rate, Packages / Tour | `Actual Packages Delivered / Vehicle Capacity from Dispatch` or `Active Time [Moving+Service] / Shift Duration` |
| **Quality** | Failed Delivery Rate, First Time Right | Count `Delivery Failed` / Count `Delivery Success+Failed`. Requires Package case. |
| **Reliability** | Traffic Delay Time, Breakdown Impact | `Sum[Traffic Delay End - Traffic Delay Start]`. Downtime from `Unscheduled Stop - Maintenance` |

#### How to Find Bottlenecks:

1.  **Performance Spectrum & Dotted Chart:** Plot all `Travel Segment` events by time of day on X-axis and duration on Y-axis, colored by Vehicle. Bottlenecks appear as horizontal thick lines of high duration. This instantly reveals traffic hotspots at 08:00-09:00 and 16:30-18:00.
2.  **Bottleneck Detection in Model:** Overlay average waiting/service time on the discovered process map. Activities with high `sojourn time` will be red. Example: `Arrive Customer -> Delivery Success` [Service Time] may average 7.2 min vs planned 3 min. Is it `Parking Search` or `Customer Interaction`?
3.  **Process Cube Slicing:** Slice the log by dimensions: Time, Driver, Vehicle Type [Diesel Van vs e-Van], District, Weather. Compare KPI: Do tours in District 50.75 have 30% higher `Travel Time per km`? Do junior drivers [D105] have 2x `Service Time` vs senior drivers?
4.  **Statistical Impact:** For each bottleneck activity, calculate its contribution to total tour delay using critical path analysis on the Vehicle-Day case. e.g., "Traffic delays account for 18% of total overtime, Failed Deliveries account for 22%."

### 3. Root Cause Analysis for Inefficiencies

Identifying *where* is not enough. We validate *why*.

**Hypotheses and Process Mining Validation:**

**a) Suboptimal Static Routing & Inaccurate Travel Time Estimation:**
If Dispatch uses static average speeds, we will see systematic late arrivals in specific geofences after 15:00. **Validation:** Correlate `Conformance Deviation - Late Arrival` with historical `Travel Segment` duration for that exact O-D pair at that hour. Build a **Performance-based Travel Time Matrix** from GPS log to prove planned ETA is 25% optimistic in urban core.

**b) Traffic Congestion Patterns:**
**Validation:** Cluster GPS `Low Speed Detected` + `Idle` events spatially. Process mining will reveal rework loops: `Arrive near customer -> Loop around block -> Arrive again`. This is classic parking search behavior, not visible in scanner data.

**c) High Service Time Variability:**
Why does one stop take 2 min and another 12 min? **Validation:** Variant analysis on Package case. Split by `Failed vs Success`, `Apartment vs House [from customer master]`, `COD vs Prepaid`. Calculate `Parking Search Time = Scanner Arrive - GPS Arrive`. We may find 40% of service time is parking, not customer handover.

**d) Vehicle Breakdown Impact:**
**Validation:** Analyze pattern `Unscheduled Stop -> Maintenance Log Start`. Does breakdown frequency correlate with `Vehicle ID` age, `Total km`, or `Idle %`? Does `Idling` precede engine warnings? This links process behavior to maintenance need.

**e) Driver Behavior Differences:**
**Validation:** Compare Driver D105 vs D110 on same district. Use Dotted Chart + Service Time Boxplots. Driver A may have higher `Harsh Braking` inferred from GPS deceleration and higher `Fuel proxy`, while Driver B has higher `Failed Delivery` due to short waiting time before scanning Fail. Use Decision Tree mining on `Failed Delivery` as target, with features like `Driver Experience, Time of Day, Service Time`.

**f) Failed Deliveries Creating Rework:**
**Validation:** In Package Journey model, trace `Delivery Failed -> Re-assigned -> Second Attempt Travel`. Calculate extra km and time cost. Often this is the biggest hidden cost: 15% failure rate can mean 15% extra tour distance for re-deliveries.

### 4. Data-Driven Optimization Strategies

**Strategy 1: Dynamic Territory & Sequence Optimization with Data-Driven Time Windows**
*   **Targeted Inefficiency:** High Travel vs Service Ratio, Sequence Deviations, Systematic Lateness in PM hours.
*   **Root Cause:** Static routing based on Euclidean distance and static travel time factors, not reality.
*   **Data Support:** Our analysis will produce: 1) Real travel time cube by Geofence-hour, 2) Real service time by location type, 3) Conformance map showing where drivers *always* deviate - they know better.
*   **Proposal:** Feed discovered performance spectrum back to Dispatch. Re-cluster delivery zones not by zip code but by discovered travel-time isochrones. Change routing objective to minimize predicted tour time using machine learning model trained on event log features. Replace fixed 3-min service time with location-specific time: 6 min for dense inner-city apartment blocks, 2.5 min for suburban.
*   **Expected KPI Impact:** On-Time Delivery Rate +15-20%, Avg Time per Delivery -12%, Fuel per km -8% by reducing detours, overtime -25%.

**Strategy 2: Proactive Failed Delivery Prevention Program**
*   **Targeted Inefficiency:** High Rate of Failed Deliveries [e.g., 12%] leading to re-delivery travel and customer dissatisfaction.
*   **Root Cause:** Customer not home + narrow uncommunicated time windows + driver not waiting enough.
*   **Data Support:** Mine package variant: Failed Deliveries cluster at 10:00-14:00 residential, dwell time < 1.5 min before fail scan = driver didn't wait. Text mining of `Notes: Customer Not Home`.
*   **Proposal:** Implement: 1) Predictive ETA using live GPS + historical performance, send customer 30-min notification SMS, 2) Process change: Allow driver to select `Neighbor Drop` or `Safe Place` with photo, 3) Business rule: If first attempt fails, do not return next day automatically; trigger customer to select locker.
*   **Expected KPI Impact:** Failed Delivery Rate from 12% to <5%, packages per tour +7% because time saved not wasted, customer NPS up.

**Strategy 3: Predictive Maintenance & Fuel-Efficient Driving Program**
*   **Targeted Inefficiency:** Rising Fuel & Maintenance Cost, Unscheduled Stops causing late deliveries.
*   **Root Cause:** Reactive maintenance; excessive idling and harsh driving hidden in GPS.
*   **Data Support:** Correlate `Unscheduled Stop - Engine Warning` cases with preceding patterns: high `Idle %` over last 10 days + age. Also calculate fuel proxy per driver. Ideal idling is <8%; observed is 18% in winter.
*   **Proposal:** 1) Build predictive model: When a vehicle accumulates >120 min idle + 250 km in last 3 days without moving, trigger `Preventive Check` before breakdown. Schedule maintenance based on actual engine-on hours from GPS, not just km. 2) Targeted driver coaching: Dashboard per driver showing `Idle Time, Harsh braking events, Parking Search Loop`. Gamify best performers.
*   **Expected KPI Impact:** Unscheduled Stop frequency -40%, Fuel Consumption per km -10-12%, Maintenance Cost -15% due to prevention vs repair, Late Deliveries due to breakdown -80%.

### 5. Considering Operational Constraints and Monitoring

**Handling Constraints in Optimization:**
Any new routing must satisfy constraints; process mining helps quantify them:

*   **Driver Working Hours [e.g., EU 10h max]:** Our Vehicle-Day case has `End Shift - Start Shift`. We must add a constraint: `Predicted Tour Duration + Buffer < Remaining Shift Time`. If DPM shows overtime logged on 45% of days >30 min, territories must shrink.
*   **Vehicle Capacity [Volume/Weight]:** Join Dispatch package weight. Utilization KPI will show if we are volume-constrained. No proposal can assign 50 stops of large parcels to a small van.
*   **Customer Time Windows:** Conformance checking must treat these as hard constraints for some customers. Performance analysis should be segmented into `[TW Customers]` vs `[No TW]`. Optimization must not improve average at expense of TW violations.
*   **Dynamic Feasibility:** Real-time re-routing must respect remaining packages in van.

**Continuous Monitoring Plan - The Closed Loop:**

Post-implementation, move from one-off analysis to operational Process Intelligence Dashboard in e.g., Celonis.

**Dashboard Views:**
1.  **Operational Control Tower [Real-time]:** Live map of all tours, alert if `Actual Arrival > Planned ETA + 20 min` or `Unscheduled Stop > 10 min`. Token moving on model.
2.  **Daily Performance View:** KPIs trended: OTD Rate, Failed Delivery Rate, Fuel Proxy per km, Conformance %. Concept Drift detection: alert if process model suddenly changes [e.g., many new routes] due to road construction.
3.  **Weekly Root Cause View:** Dotted Chart for bottlenecks, Variant comparison High-Performers vs Low-Performers, Driver Scorecard.
4.  **Strategic View:** Monthly cost: Travel vs Service ratio, Maintenance cost per Vehicle. Used to validate if Strategy 1-3 delivers ROI.

**Sustainability:** Set up automated alerts on process mining: If a new geofence shows `Avg Travel Time +30% for 3 days`, flag as emerging traffic hotspot and update routing matrix. This ensures optimizations remain effective and we catch new issues before customers do.

This approach turns your integrated event logs from a storage cost into your most powerful asset for continuous, fact-based logistics excellence.
