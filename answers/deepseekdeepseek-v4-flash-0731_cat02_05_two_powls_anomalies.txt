## Normative baseline

For the listed activities, the expected standard order is:

`Post_Job_Ad`  `Screen_Candidates`  `Conduct_Interviews`  `Make_Hiring_Decision`  `Onboard_Employee`  `Add_to_Payroll`  `Close_Case`

In particular:

- Screening should happen before interviews.
- Interviews should happen before the hiring decision.
- Onboarding should happen after the hiring decision.
- Payroll should happen after onboarding.
- The case should be closed only after onboarding and payroll are complete.

## Model 1 analysis

Model 1 has these dependencies:

- `Post_Job_Ad`  `Screen_Candidates`
- `Screen_Candidates`  `Make_Hiring_Decision`
- `Screen_Candidates`  `Conduct_Interviews`
- `Make_Hiring_Decision`  `Onboard_Employee`
- `Onboard_Employee`  `Add_to_Payroll`
- `Add_to_Payroll`  `Close_Case`

The main anomaly is that **there is no edge from `Conduct_Interviews` to `Make_Hiring_Decision`**.

Because `Conduct_Interviews` and `Make_Hiring_Decision` are both successors of `Screen_Candidates` but are otherwise unordered, the model permits a hiring decision — and even onboarding, payroll, and case closure — to happen before the interviews are conducted.

For example, this is a valid execution order under Model 1:

`Post_Job_Ad  Screen_Candidates  Make_Hiring_Decision  Onboard_Employee  Add_to_Payroll  Close_Case  Conduct_Interviews`

That clearly violates hiring-process logic: a candidate should not be hired, onboarded, and have the case closed before the interviews have happened.

So Model 1’s anomaly is **serious**, but it is mainly a missing precedence constraint: `Conduct_Interviews` should be required to happen before `Make_Hiring_Decision`.

## Model 2 analysis

Model 2 has these dependencies:

- `Post_Job_Ad`  `Screen_Candidates`
- `Post_Job_Ad`  `Conduct_Interviews`
- `Conduct_Interviews`  `Make_Hiring_Decision`
- `Make_Hiring_Decision`  `loop_onboarding`
- `loop_onboarding`  `xor_payroll`
- `xor_payroll`  `Close_Case`

There are several anomalies.

### 1. Screening is not connected to interviews or the hiring decision

There is no edge from `Screen_Candidates` to `Conduct_Interviews`, nor from `Screen_Candidates` to `Make_Hiring_Decision`.

So under Model 2, candidates can be interviewed and hired without first being screened. Even worse, because `Screen_Candidates` has no outgoing dependencies, it could be scheduled after the decision, after onboarding, or even after `Close_Case`.

For example, this is a valid execution order if the payroll XOR chooses the silent skip:

`Post_Job_Ad  Conduct_Interviews  Make_Hiring_Decision  Onboard_Employee  Close_Case  Screen_Candidates`

That is a serious violation: screening is a prerequisite for the rest of the hiring process, but Model 2 does not enforce it.

### 2. Onboarding can be repeated

`loop_onboarding = LOOP(Onboard, skip)` means:

- `Onboard_Employee` is executed first.
- Then the process can either exit the loop or execute the silent skip and execute `Onboard_Employee` again.

So `Onboard_Employee` can happen one or more times. Normatively, onboarding is a one-time activity for a new hire. Repeating it is not part of a standard Hire-to-Retire process.

### 3. Payroll can be skipped

`xor_payroll = XOR(Payroll, skip)` means the process can either execute `Add_to_Payroll` or do nothing silently.

This makes `Add_to_Payroll` optional. A valid execution can close the case without the employee ever being added to the payroll system. That is a severe integrity violation, because payroll should be mandatory before the case is closed.

**Model 1 is closer to the normative Hire-to-Retire process.**

Model 2 has multiple, more fundamental deviations:

- screening is not required before interviews or the hiring decision;
- onboarding can be repeated;
- payroll can be skipped entirely.

Because Model 2 allows cases to be closed without screening or payroll, and allows repeated onboarding, it is less aligned with the normative process. Its anomalies affect not just ordering, but also the mandatory nature and integrity of core hiring activities.
