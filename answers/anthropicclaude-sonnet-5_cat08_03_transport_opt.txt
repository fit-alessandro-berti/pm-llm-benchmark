# Speedy Parcels: Process Mining Analysis & Optimization Strategy

---

## 1. Process Discovery and Conformance Checking

### 1.1 Data Preprocessing and Integration

**Building the Unified Event Log**

The four data sources must be merged into a single, structured event log with the standard process mining schema: **Case ID, Activity, Timestamp, Resource, and Attributes**.

**Proposed Case Notion Strategy (Multi-level):**
- **Primary Case ID:** `Vehicle-Day` (e.g., V12-20241205) — captures the full operational shift, ideal for route-level and vehicle-level bottleneck analysis.
- **Secondary Case ID:** `Package ID` — enables a package-centric view to analyze individual delivery lifecycles (useful for failed delivery analysis and SLA compliance).
- I would maintain **both logs in parallel** (a technique called "convergence/divergence handling") since a single case notion cannot answer all questions. The vehicle-day log answers "how efficient was this route/shift?" while the package log answers "was this specific delivery on time?"

**Integration Steps:**
1. **Timestamp normalization:** Align all sources to a single timezone/format; GPS logs are high-frequency (seconds), scanner/dispatch events are discrete — need to decide granularity (e.g., aggregate GPS pings into derived events like "Idle Period Start/End," "Speed Drop Event").
2. **Entity resolution:** Match Vehicle ID + Driver ID + approximate timestamp windows across systems (e.g., matching a GPS "stop" location/time to a Scanner "Arrive Customer" event within a tolerance window).
3. **Event abstraction:** Convert raw GPS traces into meaningful discrete activities (e.g., "Driving," "Idle - Traffic," "Idle - Parking Search") using speed/status thresholds and clustering (e.g., DBSCAN on stop locations to distinguish customer stops from traffic stops).
4. **Enrichment:** Attach dispatch plan data (planned sequence, time windows) as case/event attributes to each corresponding real event for later conformance checking.
5. **Deriving missing events:** Not all activities are explicitly logged (e.g., "Searching for Parking" isn't a scanner event) — must be inferred from GPS patterns (low speed, circling behavior, stop-start cycles near a delivery point before "Arrive Customer").

**Key Challenges:**
- **Granularity mismatch:** GPS pings every few seconds vs. scanner events only at milestones — risk of event log explosion or information loss.
- **Clock drift/sync issues** between handheld scanners and vehicle telematics units.
- **Missing/incomplete data:** GPS signal loss in urban canyons, drivers forgetting to scan.
- **Case correlation ambiguity:** A "Package ID" may span multiple vehicle-days if redelivery occurs after failure — requires careful case linking to avoid convergence problems.
- **Noise filtering:** GPS jitter near customer stops can create false "stop" events.
- **Label inconsistency:** Ensuring "Delivery Failed," "Failed Attempt," "Not Home" etc., are standardized into one controlled vocabulary before mining.

### 1.2 Process Discovery

Using an **Inductive Miner** or **Fuzzy Miner** (preferred for noisy, unstructured logistics logs with many infrequent variants), I would discover the actual end-to-end process model per vehicle-day case.

- **Inductive Miner:** Good for producing a sound, block-structured process tree/BPMN model — useful for a "clean" high-level view (Depot Departure  [Travel  Arrive Customer  Service  Depart Customer]*  Return Depot).
- **Fuzzy Miner:** Better for the messy reality — retains high-frequency paths as clear edges while abstracting low-frequency/noisy paths (e.g., rare maintenance detours), producing a more interpretable map for operations managers.
- **Directly-Follows Graph (DFG) with performance overlay:** Annotate each edge with average/median duration and frequency — this immediately visualizes where time is consumed (e.g., long edges between "Depart Customer" and next "Arrive Customer" indicate travel/traffic issues).

The discovered model should reveal loop structures (repeated failed delivery attempts), parallel/concurrent branches (multiple activities logged near-simultaneously by different systems), and rare paths (unscheduled maintenance stops, route re-sequencing).

### 1.3 Conformance Checking

Compare the discovered/actual model against the **normative model derived from the Dispatch System's planned route**.

**Techniques:**
- **Token-based replay** or **alignment-based conformance checking**: replay actual event sequences against the planned route model to compute fitness scores per case and pinpoint exact deviation points.
- **Trace alignment:** identify the optimal alignment between the actual trace and planned trace, surfacing "skip," "insert," or "swap" moves.

**Types of Deviations to Look For:**
| Deviation Type | Example | Business Implication |
|---|---|---|
| **Sequence deviations** | Stops delivered out of planned order | Driver deviates for efficiency or due to traffic — may indicate planning is suboptimal |
| **Unplanned activities** | "Unscheduled Stop – Engine Warning," personal stops | Cost/time leakage, potential vehicle health issue |
| **Missing activities** | Planned stop never attempted | Route abandonment, overload, driver error |
| **Timing deviations** | Planned travel time 10 min vs. actual 35 min | Poor time estimation model in dispatch system |
| **Rework/loops** | Delivery Failed  re-attempt later in the day or next day | Root cause investigation needed (see Section 3) |
| **Capacity violations** | More packages scanned "out for delivery" than vehicle capacity allows | Dispatch system configuration error |

Conformance results should be aggregated into a **fitness/precision dashboard per driver, per route-template, and per vehicle**, enabling ranking of "most compliant" vs. "most deviating" routes for targeted follow-up.

## 2. Performance Analysis and Bottleneck Identification

### 2.1 Key Performance Indicators (KPIs)

| KPI | Definition | Calculation from Event Log |
|---|---|---|
| **On-Time Delivery Rate (OTDR)** | % of deliveries within customer time window | Compare `Delivery Success` timestamp vs. Dispatch time window attribute; aggregate per case/package |
| **Average Time per Stop** | Mean duration of `Arrive Customer`  `Depart Customer` | Timestamp delta averaged across all stops |
| **Travel Time vs. Service Time Ratio** | Ratio of driving time to customer-facing time | Sum(DepartArrive next) / Sum(ArriveDepart) per case |
| **Fuel Consumption per km/package** | Cost efficiency metric | If fuel sensor data available, join with GPS distance traveled per case; else estimate via idle time + distance model |
| **Vehicle Utilization Rate** | % of shift time vehicle is moving/productive vs. idle | (Total Shift Time  Idle/Unscheduled Stop Time) / Total Shift Time |
| **Traffic Delay Frequency/Duration** | Count & duration of "Low Speed Detected" events | Count and sum duration of low-speed segments per case, clustered by geolocation |
| **Failed Delivery Rate** | % of attempts resulting in "Delivery Failed" | Count(Delivery Failed) / Count(Total Attempts) |
| **Overtime Rate** | Frequency/duration of shifts exceeding planned hours | (End Shift  Start Shift)  Planned Shift Duration, flagged when Notes = "Overtime logged" |
| **Maintenance Downtime Impact** | Time lost to unscheduled stops | Sum of Unscheduled Stop durations correlated with delivery delays afterward |

### 2.2 Bottleneck Identification Techniques

1. **Performance-annotated DFG / Heatmaps:** Overlay average waiting/transition times on the process map — edges/nodes with disproportionately high durations are immediate bottleneck candidates (e.g., "Arrive Customer  Delivery Success" taking unusually long at certain stops = service time bottleneck).

2. **Variant Analysis:** Cluster vehicle-day traces into variants (e.g., using trace clustering by sequence similarity or performance similarity). Compare high-performing variants (on-time, low cost) vs. low-performing variants to isolate structural differences (extra loops, different stop order, more idle events).

3. **Geospatial Bottleneck Mapping:** Plot "Low Speed Detected" and long-duration idle events on a map — cluster analysis (e.g., DBSCAN) reveals traffic hotspots or parking-scarce zones recurring across multiple vehicle-days.

4. **Time-based Segmentation:** Slice the log by hour-of-day/day-of-week and recompute KPIs — reveals whether bottlenecks are tied to rush-hour windows, specific days, or specific dispatch batch timing.

5. **Resource Performance Mining:** Group by Driver ID and Vehicle ID to test whether bottlenecks correlate with specific drivers (behavioral) or specific vehicles (mechanical/maintenance-related).

6. **Social/Organizational Mining Adaptation:** Although typically for human resources, apply the same principle to Vehicle IDs — build a "vehicle handover/performance network" to see if certain vehicles consistently underperform (age, model, maintenance history).

**Quantifying Impact:** For each identified bottleneck, calculate:
- **Frequency** (how many cases affected),
- **Average delay contribution** (minutes added to case duration),
- **Downstream cascading effect** (e.g., a 20-min delay at stop 5 pushes back stops 6-35 — measurable via cumulative lateness curve per case).

This allows ranking bottlenecks by **total minutes lost fleet-wide per month**, translating directly into a prioritized action list.

## 3. Root Cause Analysis for Inefficiencies

Process mining shows *where* delays occur; root cause analysis (RCA) requires layering additional statistical/correlation techniques on top of the discovered models.

| Suspected Root Cause | Process Mining / Analytical Technique | Validation Approach |
|---|---|---|
| **Suboptimal static route planning** | Compare planned sequence (Dispatch) vs. actual optimal sequence (derived via travel-time minimization on GPS data) | If actual driver deviations from plan consistently *outperform* the plan (shorter total time), this proves the planning algorithm is suboptimal, not the driver |
| **Inaccurate travel time estimation** | Compare Dispatch's planned inter-stop duration vs. actual GPS-derived duration, segmented by time-of-day | Systematic bias (e.g., planned times too optimistic during 8-9am) validates model recalibration need |
| **Traffic congestion patterns** | Correlate "Low Speed Detected" event geolocations/timestamps with external traffic data (if available) or internal historical frequency | High recurrence at same geo-cluster + time window = confirmed hotspot, not random |
| **High service time variability** | Statistical distribution analysis (variance, IQR) of "ArriveDepart" duration per stop/customer segment (e.g., residential vs. commercial) | High variance in specific customer segments/buildings (e.g., apartment complexes requiring buzzer access) confirms location-specific service root cause |
| **Vehicle breakdowns/maintenance** | Cross-reference Maintenance Logs with Vehicle IDs showing frequent "Unscheduled Stop" events; survival analysis on time-since-last-maintenance vs. breakdown occurrence | If breakdown frequency correlates with mileage/hours since last service, supports predictive maintenance case |
| **Driver behavior/skill differences** | Variant + performance analysis grouped by Driver ID, controlling for route/vehicle | Consistent performance gaps across different routes/vehicles for same driver isolates behavioral factor from environmental factor |
| **Failed delivery re-work impact** | Trace the package lifecycle log: measure loop length (Failed  re-attempt), additional distance/time incurred | Quantify total redelivery cost fleet-wide; check correlation with time-window mismatches (e.g., failures cluster around specific hours suggesting customers unavailable during standard delivery windows) |

**Key RCA principle:** Use **confounding variable control** — e.g., before blaming a driver for slow service times, verify it's not simply because they're assigned the routes with more apartment/high-friction deliveries. Process mining's ability to filter/segment logs by multiple dimensions simultaneously (driver × route-type × vehicle × time-of-day) is essential to isolate true causal factors from correlation.

## 4. Data-Driven Optimization Strategies

### Strategy 1: Dynamic, Traffic-Aware Route Re-Optimization

- **Target Inefficiency:** Recurring "Low Speed Detected" bottlenecks and systematic travel-time underestimation in dispatch planning.
- **Root Cause Addressed:** Static route planning that doesn't account for time-of-day traffic patterns; inaccurate travel time models.
- **PM Insight Support:** Geospatial clustering of low-speed events + comparison of planned vs. actual travel durations shows specific corridors/time-windows are systematically underestimated.
- **Implementation:** Feed historical process-mined travel-time distributions (segmented by hour/day/road segment) into the dispatch system's routing engine; enable real-time re-sequencing when GPS detects live congestion (integrate with traffic APIs).
- **Expected KPI Impact:**  On-Time Delivery Rate,  Travel Time/Service Time ratio,  Fuel Consumption (less idling in traffic).

### Strategy 2: Time-Window Optimization & Proactive Customer Communication

- **Target Inefficiency:** High Failed Delivery Rate causing redelivery loops and wasted stops.
- **Root Cause Addressed:** Mismatch between assigned delivery time windows and actual customer availability patterns.
- **PM Insight Support:** Package-lifecycle log analysis reveals failed deliveries cluster at specific times/locations (e.g., residential zones, weekday mornings). Loop analysis quantifies the redelivery cost (extra km, extra shift-hours).
- **Implementation:** Use historical success/failure patterns per customer/zone to recommend optimal delivery windows; add automated SMS/app notifications with live ETA (derived from real-time GPS + process-mined stop-duration predictions) 30-60 min before arrival, allowing customers to reschedule proactively.
- **Expected KPI Impact:**  Failed Delivery Rate,  redelivery-related distance/fuel cost,  OTDR (fewer disruptions to route continuity).

### Strategy 3: Predictive Maintenance Scheduling

- **Target Inefficiency:** Unscheduled Stops mid-shift (e.g., "Engine Warning Light") causing cascading delays to all downstream deliveries.
- **Root Cause Addressed:** Reactive (not predictive) maintenance model; maintenance scheduled by fixed calendar intervals rather than actual usage/stress patterns.
- **PM Insight Support:** Cross-referencing Maintenance Logs with GPS-derived usage intensity (mileage, idle-time, hard-braking frequency, engine-hours) via survival analysis identifies vehicles at elevated breakdown risk before failure occurs.
- **Implementation:** Build a predictive model flagging vehicles nearing statistically-derived risk thresholds; schedule maintenance during low-impact windows (e.g., overnight, weekends) rather than mid-route.
- **Expected KPI Impact:**  frequency/duration of Unscheduled Stops,  Vehicle Utilization Rate,  cascading lateness impact on OTDR,  long-term maintenance costs (preventive cheaper than emergency repair).

### Strategy 4 (Bonus): Targeted Driver Coaching via Variant Benchmarking

- **Target Inefficiency:** Performance variance between drivers on comparable routes (e.g., some consistently longer service times or more idle/detour behavior).
- **Root Cause Addressed:** Inconsistent driving/service practices — not systemic route or traffic issues, but individual behavior (e.g., inefficient parking search, slower scan-to-scan handling).
- **PM Insight Support:** Variant analysis + driver-segmented KPI comparison controlling for route/vehicle isolates skill-based inefficiency; specific activity-level bottleneck (e.g., "finding parking" inferred from GPS circling pattern before Arrive Customer) pinpoints exact coaching topic.
- **Implementation:** Create driver-specific performance scorecards from process mining dashboards; pair low performers with best-practice route "playbooks" derived from top-performing variants (e.g., specific parking spots, optimal stop sequencing within a cluster).
- **Expected KPI Impact:**  Average Time per Stop,  variance in delivery duration,  overall fleet OTDR.

## 5. Operational Constraints and Continuous Monitoring

### 5.1 Respecting Operational Constraints

- **Driver Working Hours:** Any dynamic re-routing algorithm must incorporate hard constraints on maximum shift length and mandatory breaks (labor law compliance) — encode as constraints in the optimization model, and use process-mined "Start Shift/End Shift" data to validate compliance post-implementation (avoid solving delays by simply creating more overtime).
- **Vehicle Capacity:** Route re-optimization and territory redesign must respect package volume/weight limits per vehicle — validate using Dispatch System capacity attributes already present in the log; conformance checks should flag capacity violations as a distinct deviation category.
- **Customer Time Windows:** Dynamic routing must treat customer-committed windows as either hard constraints (contractual SLAs) or soft constraints (weighted penalty) depending on customer tier — process mining KPI dashboards should segment OTDR by SLA tier to ensure premium customers aren't deprioritized by cost-driven optimization.
- **Balance principle:** Optimization should be framed as a **multi-objective problem** (minimize cost/time while maintaining constraint feasibility), not a pure cost-minimization exercise — use the discovered conformance violations as a guardrail metric (i.e., don't let dynamic optimization increase constraint violations even if average KPIs improve).

### 5.2 Continuous Monitoring Plan (Post-Implementation)

**Dashboard Architecture (Operational Process Mining):**

1. **Real-Time Operational View (Daily):**
   - Live DFG overlay showing current day's in-progress routes vs. planned routes (conformance deviation alerts triggered in real time).
   - Active alerts for Unscheduled Stops, Low Speed clusters, and predicted late deliveries (based on running-case time-remaining prediction models).

2. **Weekly Tactical Dashboard:**
   - Trending OTDR, Failed Delivery Rate, Average Time per Stop — broken down by route/zone/driver/vehicle.
   - Variant distribution shifts — are new inefficient variants emerging (early warning of process drift)?
   - Conformance fitness score trend — is compliance with the (updated) planned model improving or degrading?

3. **Monthly Strategic Review:**
   - KPI trend vs. baseline (pre-optimization) — quantify realized savings (fuel cost/km, overtime hours, maintenance cost).
   - Root-cause recurrence check — are the same bottlenecks resurfacing (indicating a fix didn't hold) or new ones appearing (indicating a shifted constraint, e.g., new customer density in a zone)?
   - Predictive maintenance model accuracy review — false positive/negative rate on breakdown predictions, recalibrate as needed.

**Feedback Loop:** Treat this as a continuous **Process Mining PDCA cycle (Plan-Do-Check-Act)** — each optimization strategy's assumptions (e.g., predicted traffic patterns, predicted maintenance risk thresholds) should be re-validated quarterly against fresh event log data, since seasonal patterns (e.g., holiday volume surges) will shift the underlying process behavior and may require re-discovery of the process model rather than assuming static process stability.

**Early Warning Indicators to Watch For:**
- Sudden increase in "unseen variants" (process drift) — signals either external disruption or an unintended consequence of the optimization.
- Divergence between conformance fitness score and OTDR (e.g., high conformance but still late = plan itself still flawed, not execution).
- Any KPI improvement that correlates with a constraint-violation increase (e.g., OTDR up, but driver overtime also up) — signals a cost being shifted rather than eliminated.
