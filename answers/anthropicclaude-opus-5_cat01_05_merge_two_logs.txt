## 1. Merging Method (rules applied)

**Normalization.** Event names were normalized before comparison (lowercase, strip spaces/camelcase): `OrderReceived  order received`, `OrderValidation  order validation  order validated`, `Shipping  item shipped`, `PaymentCheck  payment processed (?)`.

**Matching key.** `order_id` (identical for all records: `Order#1234`) **+** normalized activity name **+** timestamp proximity. All events belong to one case, so timing and semantics carry the whole matching burden.

**Timestamp tolerance.** Base tolerance = **2 s**, applied *asymmetrically*: because Log A records *receipt* time, `t_A  t_B` is expected and treated as normal; a Log B timestamp *later* than Log A by more than the tolerance is treated as suspicious (it would mean the event was recorded downstream before it happened upstream).

**Primary timestamp choice.** For merged records, the **Log B timestamp is used as `primary_timestamp`** (it is closer to the actual occurrence/start of the activity), with the Log A timestamp retained as `received_timestamp`. For singlesource events, that log's timestamp is primary. Both timestamps are always preserved — nothing is discarded.

## 4. Conflict resolution summary

- **Naming conflicts:** a `unified_activity` label was introduced (Log A's vocabulary preferred, since A is the primary timeline); original `name_A` / `name_B` are retained for traceability.
- **Timestamp conflicts:** never overwritten. `primary_timestamp` (B when available = closest to real occurrence) drives ordering; `ts_A` is kept as the "recorded/received" time, and `delta_sec` documents the discrepancy. This preserves auditability of both systems.
- **Attribute conflicts:** none occurred — Log A contributed no attributes that Log B also carried (beyond `order_id`, which agreed). Had they conflicted, the rule would be: Log B wins for descriptive/resource attributes (richer, closer to source), Log A wins for case identity.
- **Ordering effect of the choice:** using B timestamps moves `Order Received` before 10:00:00 but does not change the relative order of any activity, so the control-flow view is unaffected.

## 5. Caveats & recommendations

1. **E3/E4 is the key open item.** If System B's `PaymentCheck` is known to be the *same* activity, the two records should be collapsed into one merged event (`primary_timestamp = 10:02:00Z`, enriched with `u12`, `r99`, "Payment gateway delay"). Resolving this requires a mapping table or a shared correlation/transaction ID — timing alone is not sufficient here.
2. **Clock skew.** Two events show B *after* A by up to 2 s while others show the reverse, suggesting a sub-second-to-few-second unsynchronized offset between systems. Measuring the median offset over many cases and applying a correction before matching would make the 2 s tolerance far more reliable.
3. **Coverage gaps are systematic, not errors:** System B lacks post-hand-off events (`Item Delivered`); System A lacks internal shop-floor events (`Quality Check`). The merged log is therefore richer than either input and should be the basis for any process-mining analysis.
4. **Better matching in future:** ask both systems to emit a shared `event_uuid` or `correlation_id`, plus explicit `start`/`complete` lifecycle transitions, which would eliminate timestamp-tolerance guesswork entirely.
