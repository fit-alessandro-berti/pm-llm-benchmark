## Assumptions & Data Quality Notes

1. **Picking granularity**: One event per order line was chosen because each line has a distinct picker and timestamp. If a coarser log is preferred, collapse these into a single "Items Picked" event per order using `MAX(item_picking_date)` (e.g., 1001  2024-01-02T11:00:00Z).
2. **Payment linkage**: Payments have no direct `order_id`; they are joined to cases via `invoice_id  Invoice.order_id`.
3. **Payment resource**: No actor is recorded for payments (they are customer-initiated/external), so the Resource field is left blank rather than inferred.
4. **Order 1004**: Trace ends at "Item Picked" — no delivery, invoice, or payment records exist. This is treated as an **incomplete/in-progress case**, not a data error; the two known events are still included.
5. **Order 1002 split shipment**: The backorder produced two deliveries and two invoices (400.00 + 100.00). Chronology is respected: the second arrival (Jan 8, 10:00) precedes the first invoice (Jan 8, 10:15).
6. **Carrier as resource**: For dispatch/arrival events, the carrier is treated as the responsible resource since no driver-level actor exists.
7. **Ordering**: Events are grouped by Case ID and sorted chronologically within each case; no timestamp conflicts or impossible sequences (e.g., arrival before dispatch) were detected.
