# Speedy Parcels: Process Mining Analysis & Optimization Strategy

---

## 1. Process Discovery and Conformance Checking

### 1.1 Data Preprocessing and Integration

**Building the Unified Event Log**

To create a process-mining-ready event log, I would transform the four source systems into a standardized format with these mandatory attributes: `Case ID`, `Activity`, `Timestamp`, `Resource` (Driver/Vehicle), and contextual attributes (Location, Package ID, Notes).

**Case ID Strategy — Multi-Level Approach:**
Rather than a single case notion, I'd build a **multi-perspective event log**:
- **Vehicle-Day Case ID** (e.g., `V12-20241205`) — for analyzing the full operational shift, sequencing, and vehicle-level bottlenecks (maintenance, idle time, route adherence).
- **Package-Level Case ID** (e.g., `P9876`) — for analyzing delivery lifecycle (dispatch  attempt  success/fail  re-delivery), which is critical for punctuality and failed-delivery root cause analysis.

Both views should be linked via shared attributes (Vehicle ID, Timestamp) so analysts can pivot between "vehicle journey" and "package journey" perspectives — this is essential because a single Vehicle-Day case conflates 35 different delivery sub-processes.

**Integration Steps:**
1. **Timestamp normalization** — align all systems to a single timezone/format; GPS data is often high-frequency (seconds) while scanner/dispatch data is event-based (minutes) — need a common granularity.
2. **Event abstraction** — GPS produces thousands of raw pings; these must be abstracted into meaningful activities (e.g., "Low Speed Detected," "Depart Depot," "Idle > 5 min") using rule-based or trajectory-segmentation logic (e.g., speed = 0 for >X minutes  "Stopped" event).
3. **Entity resolution/joining** — match records across systems using Vehicle ID + Driver ID + time proximity (e.g., join a GPS "stop" event with a Scanner "Arrive Customer" event within a 2-minute window and matching approximate GPS coordinates).
4. **Enrichment** — attach planned data (expected route sequence, promised time windows) from the Dispatch system as case/event attributes to enable conformance checking.
5. **Noise filtering** — remove GPS jitter (spurious speed fluctuations at traffic lights) that could be misclassified as "delay" events.

**Key Challenges:**
- **Granularity mismatch**: GPS pings (seconds) vs. scanner events (discrete milestones) — risk of event log explosion or information loss.
- **Clock drift/sync issues** across independent devices (handheld scanner vs. vehicle telematics).
- **Missing/incomplete scans**: drivers may forget to scan "Depart Customer," creating gaps that look like anomalies but are actually data quality issues.
- **Ambiguous case correlation**: an "Unscheduled Stop" event has no Package ID — is it a break, a breakdown, or a failed navigation attempt? Requires supplementary rules (e.g., cross-reference with Maintenance Log timestamps) to correctly classify.
- **Geospatial noise**: GPS coordinate drift near tall buildings (urban canyon effect) may falsely suggest route deviations.
- **Privacy/labor concerns**: driver behavior data must be aggregated carefully to avoid punitive misuse and resulting data manipulation by drivers.

### 1.2 Process Discovery

Using algorithms suited to noisy, real-life logistics logs — **Inductive Miner (for guaranteed sound, block-structured models)** or the **Fuzzy Miner (for a more abstracted, frequency-weighted map)** — I would discover the actual "as-is" process at two levels:

- **Macro-level model (Vehicle-Day case)**: Start Shift  Route Assigned  Depart Depot  [repeating pattern: Travel  Arrive Customer  (Delivery Success | Delivery Failed)  Depart Customer]  [possible: Unscheduled Stop/Maintenance]  Arrive Depot  End Shift.
- **Micro-level model (Package case)**: Assigned  Arrive Customer  Delivery Attempt  (Success | Failed  Re-attempt next day) — useful to discover rework loops.

The discovered model should be annotated with **frequency and performance metrics** (using a Directly-Follows Graph/Heuristic Miner overlay) to visually show which paths are common vs. rare, and where average transition times are largest — immediately highlighting candidate bottlenecks (e.g., a thick, slow edge between "Arrive Customer" and "Delivery Success" at certain stops).

### 1.3 Conformance Checking

I would encode the **planned route** (sequence and expected timing of stops from the Dispatch system) as a normative process model (or simply an ordered reference sequence per case), then apply:

- **Token-based replay** or **alignment-based conformance checking** to replay actual event traces against the planned model, quantifying **fitness** (how well reality matches the plan) and **precision**.

**Deviations to specifically detect:**
1. **Sequence deviations** — stops delivered out of planned order (may indicate driver improvisation due to traffic, or poor initial route optimization).
2. **Unplanned activities** — "Unscheduled Stop," "Low Speed Detected" segments, personal stops not in the dispatch plan.
3. **Skipped/rescheduled stops** — planned stops that don't appear in that day's case (rolled over to next day).
9. **Timing deviations** — using alignments enriched with time, flag stops where actual arrival deviates significantly (>X minutes) from the planned ETA — this is the direct driver of late-delivery complaints.
5. **Missing milestones** — e.g., no "Depart Customer" scan recorded — data quality flags that also often correlate with rushed drivers skipping steps.
6. **Extra dwell/idle time** — segments where GPS shows "moving" status delayed by low speed/idle events not linked to any customer or maintenance activity (possible parking search, traffic, or personal stops).

## 2. Performance Analysis and Bottleneck Identification

### 2.1 Key KPIs and Calculation from Event Log

| KPI | Definition | Calculation from Log |
|---|---|---|
| **On-Time Delivery Rate (OTDR)** | % of deliveries within promised time window | Compare `Delivery Success` timestamp vs. Dispatch `time window` attribute; count within-window / total |
| **Average Service Time per Stop** | Time spent at customer location | `Depart Customer`  `Arrive Customer`, averaged per stop/route/driver |
| **Travel Time vs. Service Time Ratio** | Efficiency of route vs. delivery execution | Sum(inter-stop travel durations) / Sum(service durations) per case |
| **Failed Delivery Rate** | % of attempts resulting in failure | Count(`Delivery Failed`) / Count(all delivery attempt events) |
| **Fuel Consumption per km/package** | Cost efficiency | Requires fuel-sensor data (if available) or proxy via idle-time + distance from GPS, normalized by packages delivered |
| **Vehicle Utilization Rate** | % of shift time vehicle is active (moving/delivering) vs. idle | (Shift duration  Idle/Unscheduled Stop duration) / Shift duration |
| **Traffic Delay Frequency/Duration** | Impact of congestion | Count and sum duration of `Low Speed Detected` events per route/time-of-day |
| **Overtime Rate** | Cost and scheduling health | Compare `End Shift` timestamp vs. planned shift end from Dispatch |
| **Maintenance-Induced Downtime** | Unplanned stop impact | Duration between `Unscheduled Stop` and resumption of movement, aggregated per vehicle |

### 2.2 Bottleneck Identification Techniques

1. **Performance-annotated DFGs / Process Maps**: Overlay average/median transition times on the discovered graph edges — visually surfaces the slowest transitions (e.g., "Arrive Customer  Delivery Success" taking unusually long at specific stop clusters = possible parking/access issues).

2. **Variant Analysis**: Cluster Vehicle-Day traces into "variants" (unique sequences). Compare **frequent, on-time variants** vs. **frequent, late variants** to isolate structural differences (e.g., late variants disproportionately contain an "Unscheduled Stop" or a specific stop order).

3. **Dotted Chart / Time-based Scatter Analysis**: Plot events across time-of-day and case to visually detect **temporal bottleneck clustering** — e.g., systematic slowdowns during 08:00–09:00 and 16:00–18:00 rush hours across many vehicles, pointing to structural traffic-pattern bottlenecks rather than isolated incidents.

4. **Geospatial Process Mining**: Overlay GPS coordinates of "Low Speed Detected" and long-dwell events on a map to identify **physical traffic/parking hotspots** — recurring geographic clusters indicate infrastructure-related (not process-related) bottlenecks.

5. **Resource Performance Analysis**: Compare KPIs (service time, punctuality, failed-delivery rate) grouped by **Driver ID** and **Vehicle ID** — using social network/resource-handover mining adapted to identify whether bottlenecks correlate with specific drivers, specific vehicle models (e.g., older vans = more breakdowns), or specific routes/territories.

6. **Quantifying Impact**: For each bottleneck candidate, compute the **aggregate delay contribution** — e.g., "Traffic-related low-speed events account for an average of 42 minutes of delay per shift across Route Zone B, contributing to 60% of late deliveries in that zone" — enabling prioritization by cost/impact.

## 3. Root Cause Analysis for Inefficiencies

Identifying *where* delays occur is insufficient; root causes must be validated with targeted analyses:

| Suspected Root Cause | Process Mining Validation Technique |
|---|---|
| **Suboptimal/static route planning** | Compare planned stop sequence (Dispatch) vs. actual sequence via conformance checking; if drivers frequently deviate from the plan *and* those deviations correlate with better performance, the planning algorithm itself is a root cause (not driver error). |
| **Inaccurate travel time estimation** | Compare Dispatch's assumed inter-stop travel time vs. actual GPS-derived travel time distribution; systematic underestimation (e.g., planned 5 min, actual median 12 min) indicates the ETA model needs recalibration, directly explaining chronic lateness. |
| **Traffic congestion patterns** | Correlate `Low Speed Detected` event frequency/duration with time-of-day and geolocation; cross-reference with external traffic APIs if available to confirm causal (not coincidental) relationship. |
| **High variability in service time** | Compute variance/std-dev of service time per stop/customer segment (residential vs. commercial); high variance at specific customer types suggests need for differentiated time allocations, not driver fault. |
| **Vehicle breakdowns/maintenance** | Join Maintenance Log with Vehicle-Day cases; check whether vehicles with shorter intervals since last maintenance show higher "Unscheduled Stop" frequency — validates a **predictive maintenance** hypothesis. |
| **Driver behavior/skill variability** | Variant analysis + resource-based performance comparison controlling for route/vehicle — if two drivers on statistically similar routes show significantly different punctuality/service times, this isolates a genuine skill/behavior factor (e.g., navigation efficiency, customer interaction style). |
| **Failed delivery attempts** | Analyze the Package-level case log: what fraction of "Delivery Failed" events lead to costly re-delivery trips the next day? Correlate failure reasons (from Notes) with time-of-day (e.g., failures cluster at times when customers are unlikely home) — suggests time-window/communication root cause rather than routing. |

**Key Principle**: Use **comparative variant analysis** (high-performers vs. low-performers, controlling for confounds like route/vehicle) as the primary validation mechanism — this moves from correlation ("late deliveries happen here") to causal hypothesis testing ("removing X factor improves Y KPI in comparable cases").

## 4. Data-Driven Optimization Strategies

### Strategy 1: Dynamic, Traffic-Aware Route Re-Sequencing

- **Targets**: High "Low Speed Detected" frequency/duration bottleneck concentrated in specific zones and time windows (from geospatial + dotted chart analysis).
- **Root Cause Addressed**: Static route planning that doesn't account for recurring, predictable congestion patterns discovered in historical logs.
- **PM Evidence**: The performance-annotated process map and geospatial overlay show congestion is systematic (recurring same zone/time), not random — making it predictable and thus optimizable.
- **Action**: Integrate real-time/historical traffic pattern data into the dispatch system's routing engine to dynamically reorder stops (e.g., avoid the identified congestion corridor during 8–9 AM by resequencing nearby stops).
- **Expected KPI Impact**:  On-Time Delivery Rate,  Travel Time/Service Time ratio,  fuel consumption from reduced idling.

### Strategy 2: Recalibrated ETA Models & Time-Window Renegotiation

- **Targets**: Systematic gap between planned vs. actual inter-stop travel and service times (validated in Section 3).
- **Root Cause Addressed**: Inaccurate baseline assumptions in the dispatch system's time estimation, causing cascading lateness across a route once the first few stops run behind.
- **PM Evidence**: Conformance checking's timed-alignment deviations show consistent, directional bias (not random noise) — i.e., an estimation bias correctable via a data-driven update.
- **Action**: Recalibrate the dispatch system's ETA model using actual historical travel/service time distributions (segmented by zone, customer type, time-of-day) instead of static averages; also renegotiate unrealistic customer time windows identified as chronically infeasible.
- **Expected KPI Impact**:  OTDR,  Overtime Rate, more realistic customer expectations ( complaints even if actual delivery time is similar).

### Strategy 3: Failed-Delivery Reduction via Predictive Attempt Scheduling

- **Targets**: High Failed Delivery Rate and its downstream cost (re-delivery trips consuming future capacity).
- **Root Cause Addressed**: Delivery attempts scheduled at times customers are statistically unlikely to be present (validated via Package-case analysis of failure Notes correlated with time-of-day).
- **PM Evidence**: Process mining on the Package-level log reveals failure clustering by time-of-day/customer segment, and quantifies the "rework loop" cost (extra Vehicle-Day capacity consumed by re-attempts).
- **Action**: Use historical success/failure patterns per customer/area to predict optimal delivery windows; implement proactive SMS/app notifications with narrower, data-informed ETAs to increase presence likelihood; prioritize re-delivery attempts at the empirically best time rather than next available slot.
- **Expected KPI Impact**:  Failed Delivery Rate,  effective vehicle capacity (fewer wasted trips),  OTDR indirectly (less rework congestion on subsequent days).

### Strategy 4 (Bonus): Predictive Maintenance Scheduling

- **Targets**: Unplanned "Unscheduled Stop" (breakdown) events causing mid-shift disruption and cascading lateness for all subsequent stops.
- **Root Cause Addressed**: Reactive (not predictive) maintenance triggering breakdowns during active routes.
- **PM Evidence**: Correlation between vehicle mileage/engine-hours since last Maintenance Log entry and probability of "Unscheduled Stop" — a survival-analysis-style validation on the joined log.
- **Action**: Shift specific high-risk vehicles to maintenance during off-peak/planned downtime based on predictive thresholds derived from the log, rather than fixed calendar intervals.
- **Expected KPI Impact**:  Unscheduled Stop frequency,  cascading lateness,  long-term maintenance cost (preventive cheaper than emergency repair).

## 5. Operational Constraints and Continuous Monitoring

### 5.1 Respecting Operational Constraints

- **Driver working hours**: Any dynamic re-routing algorithm (Strategy 1) must be constrained to keep projected shift completion within legal/contractual working-hour limits — the optimization model should treat "Estimated End Shift Time  Max Shift Duration" as a hard constraint, validated against historical `Start Shift`/`End Shift` data to avoid systematically inducing overtime.
- **Vehicle capacity**: Re-sequencing or territory reassignment (Strategy 1/2) must preserve load-feasibility — package assignment shouldn't be altered without checking capacity data from the Dispatch system; process mining can validate this by checking if past capacity-related delivery failures existed.
- **Customer time windows**: Strategy 2's ETA recalibration must operate within a two-way negotiation — the system should flag customers whose windows are historically infeasible for review rather than unilaterally violating commitments; strategy 3's proactive notification approach directly turns this constraint into a lever rather than a limitation.
- **Union/labor considerations**: Predictive maintenance rescheduling (Strategy 4) should be planned to avoid conflicting with driver shift assignments and vehicle availability needs.

### 5.2 Continuous Monitoring Plan (Post-Implementation)

Establish a **live process mining dashboard** (e.g., using tools like Celonis, ProM, or Disco integrated with a streaming data pipeline) tracking:

1. **Trend KPIs over time**: OTDR, Failed Delivery Rate, Average Service Time, Overtime Rate — plotted weekly to confirm sustained improvement (not just short-term Hawthorne effect).
2. **Conformance dashboard**: Ongoing fitness/precision scores between actual and planned routes — a declining fitness score signals the planning model is drifting out of sync with reality again (e.g., new traffic patterns emerging), triggering re-calibration.
3. **Bottleneck heatmap**: Continuously updated geospatial/time-of-day overlay of low-speed/dwell events to catch **new** emerging congestion hotspots (e.g., from urban construction or new competitor traffic).
4. **Variant drift detection**: Automated alerts when new frequent process variants emerge that weren't present in the baseline model — early warning of new deviation patterns (e.g., a new driver's non-standard behavior, or a new failure mode).
5. **Resource performance panel**: Ongoing per-driver/per-vehicle KPI comparison to catch both regressions (e.g., a vehicle needing maintenance sooner than predicted) and identify best-practice drivers whose techniques could be scaled into training.
6. **Root-cause-specific control charts**: e.g., a control chart on "predicted vs. actual maintenance-free interval" to statistically validate that the predictive maintenance model remains well-calibrated over time.

This creates a **closed-loop optimization cycle**: Discover  Diagnose  Optimize  Monitor  Re-discover, ensuring the process model and interventions evolve alongside the real-world operational environment rather than becoming stale static solutions.
