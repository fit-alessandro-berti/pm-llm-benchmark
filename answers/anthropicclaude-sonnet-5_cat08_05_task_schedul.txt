# Precision Parts Inc.: A Process Mining–Driven Approach to Advanced Manufacturing Scheduling

---

## 1. Analyzing Historical Scheduling Performance and Dynamics

### 1.1 Reconstructing the Actual Process

The MES log is rich but must be transformed into event logs suitable for process mining at **multiple case-notion levels**, since job-shop scheduling problems live at both the job level and the resource level:

- **Job-level log**: Case ID = Job ID; events = Queue Entry, Setup Start/End, Task Start/End across all activities in sequence. This reconstructs the **actual routing** (as opposed to the planned routing) per job, revealing rework loops, skipped steps, or expedite paths.
- **Resource-level log**: Case ID = Machine ID; events = every task/setup executed on that machine, ordered by timestamp. This reconstructs the **actual dispatching sequence** realized at each work center — the ground truth of what the "FCFS/EDD mix" actually produced, which can then be compared to what an idealized rule would have produced.
- **Operator-level log**: Case ID = Operator ID, to examine operator-dependent duration variance and shift effects.

From these logs I would build:
- **Directly-Follows Graphs (DFGs) / performance-annotated process maps** per job family and per machine, showing actual transition frequencies and average/percentile durations (not just means — job shops are heavy-tailed).
- **Variant analysis**: cluster job routings into variants (by task sequence and machine assignment) to see how much routing heterogeneity exists — critical because sequence-dependent setups interact with routing variant mix.

### 1.2 Key Metrics and Techniques

**Flow time, lead time, makespan distributions**
- Compute per-job flow time (Job Released  last Task End) and per-operation flow time.
- Use **survival analysis / empirical CDF and percentile bands (P50/P90/P95)** rather than averages, since job-shop lead times are typically right-skewed with a long tardy tail.
- Decompose flow time into **touch time vs. non-touch (waiting) time** per job — this ratio is usually the single most diagnostic KPI in job shops (often <10-20% touch time).

**Task waiting/queue times**
- For every (Job, Task) pair: `WaitTime = TaskStart  QueueEntry`.
- Aggregate by machine to build **queue-time distributions per work center**, and by (machine, hour-of-day/day-of-week) to detect congestion cycles.
- Plot **queue length over time** (derived by simulating token counts from Queue Entry/Task Start events) to visualize WIP buildup dynamics.

**Resource utilization**
- For each machine, partition the timeline into: Productive (Task StartEnd), Setup (Setup StartEnd), Idle (no activity, resource available), Down (Breakdown StartEnd).
- Utilization = Productive / (Total shift time); Setup ratio = Setup / (Productive+Setup) — a direct indicator of setup inefficiency.
- Build **resource Gantt/timeline reconstructions** from the resource-level log to visually and statistically confirm which machines are near 100% (bottlenecks) vs. which show fragmented idle periods (starvation).

**Sequence-dependent setup time analysis**
- For each machine, extract triplets `(PreviousJob attributes, CurrentJob attributes, Setup Duration)` using the "Previous job" note field (or by ordering the resource-level log and joining consecutive tasks).
- Construct a **setup-time matrix/heatmap** by job family or key attributes (material, tool, fixture) — rows = previous job type, columns = next job type — populated with mean/variance of actual setup durations.
- Compare **planned vs. actual setup duration** distributions to quantify estimation bias (e.g., "planned 20 min, actual 23.5 min," systematically underestimated by X%).
- Run **correlation/regression analysis** between setup duration and job attributes (family change, tool change, material change) to build a predictive setup-time model (essential input for Strategy 3 and simulation).

**Schedule adherence and tardiness**
- `Tardiness = max(0, CompletionTime  DueDate)`; also track **Lateness** (can be negative) and **Earliness**.
- Report tardiness as a distribution: % of jobs late, mean tardiness of late jobs, tardiness by priority class, and **Conformance Checking** against a "planned schedule" model (if a formal schedule/ERP plan exists) using alignment-based conformance to quantify where and how much actual execution deviates from plan (which task, which machine, how much delay contributes downstream).
- Use **Critical Ratio trend** `(DueDate  Now)/(RemainingWork)` sampled at each queue entry to see whether jobs are entering queues already in a "behind schedule" state (a sign of upstream scheduling failure vs. downstream).

**Impact of disruptions**
- Treat Breakdown Start/End and Priority Change events as **interventions**; use **before/after comparison (event-conditioned analysis)** — compare queue time and tardiness distributions for jobs in-process at the time of a breakdown vs. unaffected jobs (matched by machine/period).
- Quantify **propagation delay**: for a breakdown on Machine X, measure the increase in queue time at X and at downstream machines fed by X in the following N hours (cascading effect / bullwhip).
- For hot jobs: measure the **induced tardiness on other jobs** queued behind the machines the hot job jumps ahead of (opportunity cost of priority overrides).

## 2. Diagnosing Scheduling Pathologies

**a) Bottleneck identification and quantification**
- Rank machines by utilization, average queue length, and **queue time contribution to total job flow time** (Little's Law: WIP  Throughput × Cycle Time, applied per station to detect where WIP accumulates disproportionately).
- Confirm bottlenecks via **sensitivity**: correlate machine utilization with overall makespan/tardiness across jobs that pass through it vs. those that don't (e.g., MILL-02/03 likely bottleneck given repeated breakdown and queueing evidence in the log).
- Use **theory-of-constraints framing**: the bottleneck's idle time (any idle time on a true bottleneck is lost throughput) becomes a headline KPI.

**b) Poor prioritization evidence**
- **Variant/cohort comparison**: split completed jobs into "On-time" vs. "Late" cohorts and compare their queue-time profiles, priority class, and time-in-queue-at-each-station. If High-priority jobs show queue times statistically similar to Medium/Low priority jobs at certain stations, this proves the FCFS component of the local dispatching rule is overriding EDD/priority intent.
- Check **priority inversion events**: cases where a lower-priority job with a later due date started before a higher-priority/earlier-due job that was already queued at the same machine (directly detectable by ordering the resource-level log against queue-entry timestamps and due dates).

**c) Suboptimal sequencing / setup inflation**
- Compare the **actual sequence of jobs on a machine** against a hypothetical resequencing that groups similar setups (using the setup-time matrix from 1.2), computing the **"excess setup time"** = actual total setup time  optimal-sequence total setup time for the same job set in the same period. This directly monetizes the cost of FCFS/EDD ignoring setups.

**d) Starvation of downstream resources**
- Identify machines with **long idle gaps immediately preceded by "Queue Entry" absence** (i.e., no jobs arriving) that correlate with upstream bottleneck congestion or upstream breakdowns — this is starvation caused by upstream scheduling, not lack of demand.
- Cross-reference with the breakdown log: e.g., MILL-02 breakdown  does Grinding or Heat Treatment show idle gaps shortly after, consistent with starvation cascading downstream?

**e) Bullwhip effect in WIP**
- Plot WIP-in-queue time series at each station; test for **amplification of variance** downstream vs. upstream (variance of queue length at station N+1 vs. station N). A growing variance pattern along the routing confirms bullwhip dynamics driven by batching, setup-driven sequencing changes, and disruption-triggered re-prioritization.

## 3. Root Cause Analysis of Scheduling Ineffectiveness

| Diagnosed Pathology | Candidate Root Cause | How Process Mining Distinguishes Logic vs. Capacity Issues |
|---|---|---|
| Bottleneck overload | Insufficient capacity **or** poor loading decisions upstream | Compare theoretical minimum makespan (given true processing+setup times, computed via simulation of an optimal schedule) against actual. If actual utilization is already ~95-100% and even optimal sequencing barely improves throughput  **capacity problem**. If large gaps exist between actual and theoretical-optimal makespan despite <85% utilization  **scheduling-logic problem**. |
| Priority inversion | Static rule can't weigh multiple factors dynamically; no real-time queue visibility | Rule is deterministic and local — logs show it applies the *same* logic regardless of global state (no correlation between machine's local decision and other machines' queue lengths) — a purely **logic/coordination** issue, not capacity. |
| Setup inflation | Rule ignores setup dependency; no batching/sequencing optimization; inaccurate setup time estimates in planning | The setup-time matrix reveals huge setup variance by sequence; the ordering in resource-level log frequently alternates between high-setup-cost families  clearly a **sequencing-logic** deficiency, and the planned-vs-actual gap (23.5 vs 20 min) reveals **estimation-accuracy** deficiency, both independent of capacity. |
| Downstream starvation | Lack of shop-wide visibility, no synchronization/pull mechanism, batch-and-push release policy | If job release rate at "Job Released" event is roughly constant regardless of downstream WIP/queue state, this is evidence of a **push system without feedback**, a coordination/visibility root cause rather than capacity. |
| Disruption fragility | No dynamic rescheduling/re-optimization triggers; hot jobs inserted via simple priority override rather than re-optimized sequence | Compare tardiness increase per breakdown-minute vs. theoretical unavoidable loss (breakdown duration itself). If actual induced tardiness >> breakdown duration, the **rescheduling response**, not the breakdown itself, is the primary cause. |

Process mining's real value here is the **counterfactual comparison**: by simulating "what an optimal/near-optimal schedule would have achieved with the *same* resource capacities, breakdown occurrences, and job arrivals" (via a calibrated DES, see Section 5), we cleanly separate **capacity-constrained loss** (irreducible without capital investment) from **schedule-induced loss** (addressable via better logic) — this is essential for justifying investment priorities to management.

## 4. Advanced Data-Driven Scheduling Strategies

### Strategy 1 — Multi-Factor Dynamic Dispatching (Composite Priority Index, CPI)

**Core logic:** Replace static FCFS/EDD with a real-time composite index recalculated whenever a machine becomes free and multiple jobs are queued:

```
CPI(job, machine) = w1·(1/CriticalRatio) + w2·PriorityWeight
                   + w3·(1/EstSetupTime(prev_jobjob, machine))
                    w4·DownstreamCongestionIndex(next_station)
                   + w5·SlackTime_inverse
```

- **CriticalRatio** = (DueDate  Now)/RemainingProcessTime, mined from historical routing/duration data to compute realistic remaining work (not the static planned times).
- **EstSetupTime** pulled from the mined setup-time matrix (Section 1.2) — this is the key innovation: the rule *looks ahead* at the setup cost of each candidate job given the machine's current setup state, effectively an ATC-with-Setups (Apparent Tardiness Cost) rule.
- **DownstreamCongestionIndex** derived from live queue-length/utilization at the next station (enabled by real-time MES + process-mining-derived thresholds for "congested" states), preventing a machine from starving/flooding a downstream bottleneck.
- **Weights (w1..w5)** are not arbitrary: they are tuned via the historical variant analysis (Section 2) — e.g., if analysis shows setup excess is the largest controllable loss, w3 is increased; if tardiness of high-priority jobs is the dominant pain point, w2 dominates. Weights can be further tuned via simulation-based optimization (Section 5).

**Addresses:** priority inversion, setup inflation, downstream starvation.
**Expected impact:** Reduced tardiness variance and mean tardiness (especially for high-priority jobs), reduced total setup time (10-30% typical in literature for setup-aware rules vs. FCFS/EDD), better balanced WIP across stations, slightly reduced peak utilization at bottleneck due to smarter sequencing (more usable capacity).

### Strategy 2 — Predictive, Simulation-Informed Scheduling (Digital Twin Approach)

**Core logic:** Instead of scheduling against static planned durations, build a **rolling predictive schedule**:
1. Mine **empirical duration distributions** per (Task, Machine, Operator, Job-family) combination — not single-point estimates — including the systematic bias observed (planned 60 min vs actual 66.4 min).
2. Fit **predictive models** (e.g., regression or gradient-boosted trees) using job attributes, operator, and machine as features to forecast expected duration and its uncertainty band for each yet-unstarted operation.
3. Feed these forecasts into a **rolling-horizon finite-capacity scheduler** (e.g., simulation-based or optimization-based, re-run every shift or upon major events) that projects each job's expected completion time with confidence intervals, and flags jobs at risk of tardiness *before* they miss due dates (proactive expediting rather than reactive hot-jobbing).
4. Incorporate **predictive maintenance signals** — mine breakdown logs for patterns (e.g., breakdown frequency increasing with machine run-hours since last maintenance, or specific job types causing more wear) to probabilistically derate available capacity on at-risk machines in the schedule, and to recommend proactive maintenance windows during naturally low-demand periods identified from historical queue data.

**Addresses:** unpredictable lead times, inaccurate duration estimation, disruption fragility (reduces breakdown surprise), enables proactive customer due-date commitments (quoting P90 lead times instead of static planned times).
**Expected impact:** Lead-time predictions with quantified confidence (enabling realistic due-date quoting), earlier detection of at-risk jobs (reduces reactive "hot job" firefighting by addressing risk before due-date breach), reduced unplanned downtime impact.

### Strategy 3 — Setup-Aware Batching & Bottleneck Sequence Optimization

**Core logic:**
1. From the mined setup-time matrix, derive a **similarity/clustering structure** among job types (e.g., group jobs by fixture, tool, or material family that share low mutual setup cost) — essentially reconstructing a **Group Technology** classification from data rather than assumption.
2. At **identified bottleneck machines only** (to avoid over-constraining flexible machines), apply a **short-horizon sequencing optimization** (solving a small Traveling-Salesman-Problem-like model over the current queue, minimizing total setup time subject to due-date constraints — e.g., a constrained lexicographic optimization: first ensure no due-date violation beyond a tolerance, then minimize setup) rather than pure batching, since pure batching can starve due-date-critical jobs.
3. Where feasible, propose **lot-sizing/order consolidation** recommendations upstream (e.g., release planning) informed by mined co-occurrence of job families arriving close in time, to intentionally create batching opportunities without inflating WIP or violating due dates — validated first via simulation (Strategy 2 infrastructure).
4. Continuously update the setup matrix (it's a living model) as new machine/tooling changes occur — detected via process mining drift analysis (Section 5).

**Addresses:** excess setup time pathology, bottleneck throughput loss (since setup time directly steals capacity from the constrained resource — a minute saved at the bottleneck is a minute of extra system throughput, per Theory of Constraints).
**Expected impact:** Direct increase in effective bottleneck capacity (studies in setup-heavy job shops typically show 5-20% capacity gains from setup-aware sequencing alone), reduced average setup ratio, indirect tardiness reduction via increased bottleneck throughput.

## 5. Simulation, Evaluation, and Continuous Improvement

### 5.1 Discrete-Event Simulation (DES) Calibrated from Process Mining

Build a DES model of the shop where every stochastic element is parameterized directly from mined data rather than assumptions:
- **Arrival process**: empirical/fitted distribution of Job Released events (including seasonality, priority mix).
- **Routing**: probabilistic routing model from variant analysis (including rework probabilities if observed).
- **Processing times**: empirical distributions per (task, machine, operator) — capturing the planned-vs-actual bias, not just planned times.
- **Setup times**: the full sequence-dependent setup matrix, including variance, not just means.
- **Breakdowns**: fitted time-to-failure and repair-time distributions from Breakdown Start/End events (e.g., Weibull for TTF).
- **Hot-job injection**: empirical frequency/timing distribution of Priority Change events.

**Validation:** Run the baseline (current FCFS/EDD mix) DES and statistically compare its output KPI distributions (tardiness %, WIP, flow time) against the *actual historical* KPI distributions (e.g., via Kolmogorov-Smirnov tests) to confirm the model is a valid digital twin before using it to test new strategies.

**Scenarios to test:**
1. **Baseline replication** (sanity check).
2. **Strategy 1/2/3 individually and combined**, under identical random-number streams (common random numbers for variance reduction) for fair A/B comparison.
3. **High-load stress test**: increase arrival rate by X% to find the breaking point of each policy and identify the true bottleneck capacity ceiling.
4. **High-disruption test**: increase breakdown frequency/duration to test robustness/resilience of each dispatching logic.
5. **Hot-job surge test**: inject bursts of urgent orders to evaluate the impact of Strategy 1's dynamic reprioritization vs. baseline's static override, measuring collateral tardiness on other jobs.
6. **Setup-matrix sensitivity**: perturb setup-time estimates to test Strategy 3's robustness to forecasting error.
7. **Mixed-strategy scenarios**: e.g., Strategy 1 dispatching + Strategy 3 setup optimization at bottleneck only, to find the best combination (factorial experimental design across strategies).

Evaluate using consistent KPIs: mean/percentile tardiness, % jobs late, WIP levels (mean and variance — bullwhip check), machine utilization (bottleneck and non-bottleneck), average setup ratio, lead-time predictability (variance of quoted vs actual).

### 5.2 Continuous Monitoring and Adaptive Framework

Deploy an **online/streaming process mining layer** on top of the live MES feed to sustain and evolve the chosen strategy:
- **Real-time dashboards**: live queue lengths, utilization, tardiness-at-risk jobs (using the predictive model from Strategy 2), updated continuously.
- **Rolling KPI control charts**: statistical process control on tardiness %, setup ratio, WIP — trigger alerts when metrics drift beyond control limits (indicating either process drift, e.g., new job mix, or rule staleness).
- **Concept drift detection**: periodically re-mine the setup-time matrix and duration distributions (e.g., monthly) and statistically test for distributional shift (e.g., new tooling reduces/increases setup times, new operators change duration profiles) — automatically flag when the CPI weights or predictive models need retraining.
- **Closed-loop weight tuning**: use a periodic re-optimization (e.g., Bayesian optimization or simple grid search within the DES twin, re-calibrated with the latest 3-6 months of data) to re-tune the CPI weights (w1-w5) and reassess whether newly bottlenecked resources have emerged, keeping the digital twin as a living decision-support tool rather than a one-time project.
- **Governance loop**: establish a monthly "scheduling performance review" using process-mining generated variant/root-cause reports (as in Sections 1-3) to keep human planners in the loop for exception handling (e.g., truly novel hot-job patterns) while the automated system handles routine dynamic dispatching.

This creates a **self-reinforcing cycle**: MES logs  process mining insight  simulation-validated strategy  deployment  new MES logs capturing the new (improved) behavior  renewed mining to detect the next-order inefficiency — turning scheduling from a static rule set into a continuously learning system appropriate for Precision Parts Inc.'s highly dynamic, disruption-prone job-shop environment.
