# BPMN-Like Textual Process Model: Invoice Approval and Payment Scheduling

Based on the interview transcripts, the following textual model represents the invoice approval process. It is structured so that it can be converted into a BPMN diagram.

---

## 1. Participants / Lanes

| Participant | Role in Process |
|---|---|
| **Supplier** | External sender of invoices, corrected invoices, and PO information. |
| **Accounts Payable (AP) Clerk** | Receives invoice, checks PO, logs invoice, performs match, schedules payment. |
| **Purchasing Officer** | Verifies goods/services receipt and invoice details against PO; confirms or rejects. |
| **Department Manager** | Final approver of matched invoices. |
| **AP Supervisor** | Handles escalated exceptions, coordinates resolution, can decide to reject invoices or create retrospective POs with department heads. |
| **Supplier Relationship Manager** | Supports exception handling by contacting suppliers and checking contracts. |
| **Accounting System** | Stores invoice/PO data, sends automatic approval requests, supports payment scheduling. |
| **Department Head** | Involved only in exception handling when a retrospective PO is created. |

---

## 2. Data Objects / Artifacts

- **Invoice** – arrives by email; central input to the process.
- **Purchase Order (PO)** – source of reference data for verification.
- **Receipt/Goods Receipt Confirmation** – provided by Purchasing to confirm goods/services were received.
- **Invoice-PO Match Result** – system/AP check that invoice line items align to the PO.
- **Approval Request / Notification** – automatically sent to the Department Manager.
- **Payment Schedule** – output after AP schedules the invoice for payment.
- **Revised Invoice / Supplier Correction** – created when suppliers correct discrepancies.
- **Retrospective PO** – created in exception cases for informal service purchases.
- **Contract** – used by Supplier Relationship Manager to validate pricing in disputes.

## 3. Main Process Flow

### Start
- **StartEvent_InvoiceReceived**  
  Invoice arrives at Accounts Payable by email.

### PO Reference Check
- **Task_CheckPOReference** *(AP Clerk)*  
  Check whether the invoice has a valid purchase order number.

- **XGW_POExists** *(Exclusive Gateway)*  
  - **Yes**  Proceed to **Task_LogInvoice**.
  - **No**  Proceed to **Task_RequestPOInfo**.

### No PO Handling
- **Task_RequestPOInfo** *(AP Clerk, sometimes Supplier Relationship Manager)*  
  Send invoice back to supplier / ask for valid PO number or revised invoice.

- **Event_SupplierResponse** *(waiting for supplier response)*  
  Supplier either provides PO information/revised invoice or indicates that no formal PO exists.

- **XGW_POResolved** *(Exclusive Gateway)*  
  - **Valid PO / revised invoice provided**  Proceed to **Task_LogInvoice**.
  - **No formal PO exists / informal service**  Proceed to **Subprocess_ResolveException**.
  - **Unable to resolve**  Proceed to **Subprocess_ResolveException**.

### Invoice Logging and Forwarding
- **Task_LogInvoice** *(AP Clerk)*  
  Log the invoice into the accounting system.

- **Task_ForwardToPurchasing** *(AP Clerk / Accounting System)*  
  Forward the invoice to Purchasing for receipt and PO verification.

### Purchasing Verification
- **Task_VerifyReceiptAndPO** *(Purchasing Officer)*  
  Verify that goods/services were received and compare invoice quantities, prices, and delivery charges to the PO.

- **XGW_VerificationOK** *(Exclusive Gateway)*  
  - **Yes**  Proceed to **Task_SendReceiptConfirmation**.
  - **No**  Proceed to **Task_RequestCorrection**.

### Purchasing Discrepancy
- **Task_RequestCorrection** *(Purchasing Officer, with Supplier Relationship Manager if needed)*  
  Contact the supplier directly or ask AP to hold the invoice until a corrected version is sent.

- **Event_CorrectionReceived** *(waiting for supplier correction)*  
  Corrected invoice or clarification is received.

- **XGW_CorrectionResolved** *(Exclusive Gateway)*  
  - **Yes**  Return to **Task_VerifyReceiptAndPO** for re-verification.
  - **No / cannot resolve**  Proceed to **Subprocess_ResolveException**.

### Purchasing Confirmation
- **Task_SendReceiptConfirmation** *(Purchasing Officer)*  
  Send confirmation back to Accounts Payable that the invoice matches the PO and goods/services were received.

### AP Three-Way Match
- **Task_MatchInvoicePO** *(AP Clerk)*  
  Match invoice line items against the PO in the accounting system.

- **XGW_MatchOK** *(Exclusive Gateway)*  
  - **Yes**  Proceed to **Task_RequestManagerApproval**.
  - **No**  Proceed to **Task_ClarifyWithPurchasing**.

### AP Match Discrepancy

- **XGW_ClarificationResolved** *(Exclusive Gateway)*  
  - **Yes**  Return to **Task_MatchInvoicePO**.
  - **No**  Proceed to **Subprocess_ResolveException**.

### Manager Approval

- **Task_ManagerReview** *(Department Manager)*

- **XGW_ManagerApproves** *(Exclusive Gateway)*

  - **No**  Proceed to **Task_SendBackForInvestigation**.

### Manager Rejection / Hold

### Payment Scheduling

## 4. Exception Handling Subprocess

### Subprocess_ResolveException
Used when:
- No valid PO exists or supplier cannot provide one.
- Purchasing verification fails and cannot be corrected.
- AP three-way match fails and Purchasing cannot clarify.
- Manager rejects or holds the invoice for investigation.

**Participants involved:**
- AP Supervisor
- Purchasing Officer
- Supplier Relationship Manager
- Department Head
- Supplier

**Actions:**
- Contact supplier to obtain missing information or a revised invoice.
- Check contract terms to confirm correct pricing.
- Coordinate between AP and Purchasing.
- Create a retrospective PO with the relevant Department Head for informal service purchases.
- Reject the invoice if it cannot be legitimately resolved.

**Outcome:**
- **If resolved**  The invoice re-enters the main flow at the applicable point:
  - If a PO was missing/retro PO created  return to **Task_LogInvoice**.
  - If purchasing verification failed  return to **Task_VerifyReceiptAndPO**.
  - If AP match failed  return to **Task_MatchInvoicePO**.
  - If manager held/rejected  return to **Task_ManagerReview** after resolution.
- **If rejected**  **EndEvent_InvoiceRejected**.
