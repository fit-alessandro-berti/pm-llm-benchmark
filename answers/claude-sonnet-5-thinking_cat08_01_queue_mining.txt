# Data-Driven Queue Mining Analysis for Outpatient Clinic Optimization

## 1. Queue Identification and Characterization

### Calculating Waiting Times from Event Log Data

Waiting time (queue time) is defined as the elapsed time between the **COMPLETE** timestamp of one activity and the **START** timestamp of the next activity in the same case (patient visit), where no value-adding work is occurring — the patient is idle, waiting for a resource to become available.

**Calculation logic:**
```
For each Case ID, sort activities chronologically by COMPLETE timestamp.
For each consecutive pair (Activity A  Activity B):
    Waiting_Time(AB) = START_timestamp(B)  COMPLETE_timestamp(A)
```

Using the snippet: For V1001, waiting time between Nurse Assessment (COMPLETE 09:25:10) and Doctor Consultation (START 09:45:55) = **20 min 45 sec**. This is distinct from **service time** (activity duration = COMPLETE  START of the *same* activity), which should never be confused with queue time.

**Important nuances:**
- **Batching/parallel activities**: If a patient has multiple pending orders (e.g., blood test ordered but ECG happens first), waiting time must be calculated per logical "handoff," not just log order — this may require defining an activity precedence model (a reference process map) rather than pure chronological adjacency.
- **Multitasking resources**: A "waiting" period may overlap with a resource being busy elsewhere — this feeds into resource utilization analysis (Section 2).
- **Censored cases**: Visits still in progress at log extraction should be excluded or handled separately to avoid bias.

### Key Metrics for Queue Characterization

For each **queue point** (i.e., each transition between activity pairs, e.g., "Registration  Nurse Assessment", "Doctor Consultation  ECG Test"), compute:

| Metric | Purpose |
|---|---|
| **Mean waiting time** | Overall central tendency, but sensitive to outliers |
| **Median waiting time** | Robust central tendency, better represents "typical" patient experience |
| **Standard deviation / IQR** | Captures variability/unpredictability of the queue |
| **90th/95th percentile wait** | Captures worst-case experience — critical for SLA/patient satisfaction, since dissatisfaction is driven more by tail experiences than averages |
| **Max waiting time** | Identifies extreme outliers worth individual investigation |
| **Queue frequency (occurrence rate)** | How often this transition occurs across cases (some queues may be rare but severe) |
| **% of cases exceeding threshold** (e.g., >15 min) | Operationally meaningful — "how many patients had a bad experience here" |
| **Total waiting time contribution** | Sum of wait time at this queue across all cases — shows aggregate impact on clinic-wide throughput |
| **Time-of-day / day-of-week variation** | Reveals whether queues are structural or demand-driven (peak-hour congestion) |
| **Segmented metrics** by Patient Type / Urgency / Specialty | Detects inequity or misallocation (e.g., Urgent patients queuing as long as Normal) |

### Identifying Critical Queues

I would rank queue points using a **composite prioritization score**, not a single metric, since focusing on only "longest average wait" can miss high-frequency, moderate queues that dominate total patient-time lost. Criteria:

1. **Total time impact** = (mean wait) × (frequency) — identifies where the *aggregate* patient-hours lost are largest (this is analogous to "impact" in bottleneck theory).
2. **Tail severity (90th/95th percentile)** — identifies queues causing the worst individual experiences, which correlate most strongly with satisfaction complaints.
3. **Variability (SD/IQR)** — high-variance queues indicate unpredictable/uncontrolled processes, harder for patients to tolerate even if average is acceptable.
4. **Urgency-weighted impact** — a 10-minute wait for an Urgent patient before Doctor Consultation is more critical than the same wait for a Follow-up Normal patient. Apply weights based on clinical risk/triage class.
5. **Downstream propagation** — use process mining "critical path" analysis to check whether delays at a queue point cascade and delay the entire visit (i.e., is this queue on the case's critical path, or does the process have slack/parallelism absorbing it?).

Queues scoring high on multiple dimensions (e.g., "Doctor Consultation  Diagnostic Test" with high frequency, high total time impact, and high variance) become priority targets.

## 2. Root Cause Analysis

Identifying *where* queues occur is necessary but insufficient — we need to explain *why* they occur, using event log enrichment and cross-referencing with resource/organizational data.

### a) Resource Bottlenecks
- **Resource utilization analysis**: For each resource (Dr. Smith, Nurse 1, Room 3, Tech X), compute utilization = (total busy time)/(total available/shift time) within time windows. A queue before "Doctor Consultation (Cardio)" that correlates with Dr. Smith's utilization >90% during 10am–12pm strongly implicates *capacity* as root cause.
- **Resource contention**: Check if multiple activities compete for the same resource (e.g., Tech X handles both ECG and X-Ray) — log analysis can reveal if ECG queues coincide with X-Ray demand spikes.

### b) Activity Dependencies & Handovers
- **Handover analysis**: Examine whether queue time correlates with *resource changes* (e.g., Nurse  Doctor handover) versus same-resource continuations. High wait specifically at cross-role handovers suggests coordination/communication gaps (e.g., doctor not notified nurse assessment is complete) rather than pure capacity issues.
- **Batching effects**: Check if certain activities are processed in batches (e.g., doctor sees a backlog of "ready" patients only after finishing rounds), inflating wait time artificially.

### c) Variability in Service Times
- **Service time distribution analysis** per activity, per resource, per patient type. High variance in "Doctor Consultation" duration (e.g., some visits 10 min, others 45 min) creates downstream queue unpredictability for subsequent patients — a classic queueing theory insight (variability, not just average load, drives queue length, per Kingman's formula).

### d) Scheduling Policies
- Compare **scheduled appointment times** (if available) vs. actual arrival/start times. If multiple patients are scheduled at the same slot ("block scheduling"), this directly explains registration/nurse queues each morning.
- **Variant analysis**: Use process discovery (e.g., inductive miner) to detect if certain process variants (e.g., patients requiring 2+ diagnostic tests) have structurally longer paths, and whether scheduling fails to account for this complexity.

### e) Patient Arrival Patterns
- **Arrival rate analysis**: Plot check-in timestamps by hour/day. Peaks (e.g., Monday mornings) causing queue spikes indicate a demand-capacity mismatch rather than a process design flaw.

### f) Patient Type / Urgency Segmentation
- Segment all above analyses by Patient Type and Urgency. E.g., discover if "New" patients queue longer at Registration (more paperwork) or if "Urgent" patients are *not* actually fast-tracked in practice despite policy — a compliance/process conformance issue detectable via **conformance checking** against the intended clinical pathway.

### Techniques Summary
| Technique | Root Cause Insight |
|---|---|
| Resource utilization & workload analysis | Staffing bottlenecks |
| Handover/social network analysis | Coordination failures |
| Service time distribution analysis | Variability-driven queuing |
| Variant/conformance analysis | Non-standard paths, policy deviations |
| Arrival pattern & scheduling analysis | Demand-capacity mismatch |
| Segmented (patient type/urgency) analysis | Equity and prioritization failures |

## 3. Data-Driven Optimization Strategies

### Strategy 1: Dynamic Resource Reallocation (Staggered Nurse/Doctor Shifts)
- **Target queue**: Nurse Assessment  Doctor Consultation (Cardio), especially 10am–12pm window.
- **Root cause addressed**: Resource utilization analysis shows Dr. Smith at >90% utilization in this window while another specialist is under-utilized; queue is a capacity mismatch, not a systemic process flaw.
- **Data support**: Utilization heatmaps by hour and resource show a clear peak-load imbalance; arrival pattern analysis confirms patient inflow is front-loaded in the morning.
- **Action**: Stagger doctor shift start times or float an additional resource (e.g., a second cardiologist or PA) during peak windows; alternatively, smooth appointment scheduling to spread arrivals more evenly.
- **Expected impact**: Reducing peak utilization from ~90% to ~75% could (per queuing theory, M/M/1 approximation) reduce average wait time at this queue by 40–60%, since wait time grows non-linearly (exponentially) as utilization approaches 100%.

### Strategy 2: Parallelizing Diagnostic Tests with Consultation Ordering
- **Target queue**: Doctor Consultation  ECG/Blood Test.
- **Root cause addressed**: Sequential dependency — tests are only ordered *after* seeing the doctor, causing a "stop-and-wait" pattern even when test capacity (Room 3/Tech X) is available.
- **Data support**: Variant analysis shows for a large subgroup (e.g., Cardiology follow-ups), tests are near-always ordered — predictable from visit reason/history. Process redesign can front-load ordering.
- **Action**: For predictable visit types (based on referral reason or patient history), enable nurses to pre-order standard tests (e.g., ECG for cardiology visits) during Nurse Assessment, so the test can run in parallel with/before the doctor consultation, rather than strictly after.
- **Expected impact**: Could eliminate the ECG waiting queue entirely for ~50-70% of cardiology visits, shortening total visit duration by 10-20 minutes for those patients.

### Strategy 3: Real-Time Queue Visibility & Automated Handover Notification System
- **Target queue**: All handover-related queues (Nurse  Doctor, Doctor  Test, Test  Check-out).
- **Root cause addressed**: Handover analysis reveals queue time is inflated not by resource unavailability but by *notification lag* (doctor unaware patient is ready).
- **Data support**: Cases where the same resource handles consecutive steps show much shorter transition times than cross-resource handoffs, isolating communication delay as the driver.
- **Action**: Implement a lightweight real-time dashboard/patient-tracking system (e.g., digital board or RTLS) that automatically flags "patient ready" status to the next resource, replacing manual communication.
- **Expected impact**: Based on similar hospital RTLS implementations, handover-related queue times typically drop by 20-30% with minimal capital cost.

### Additional strategy (optional 4th): Differentiated Fast-Track Lane for Urgent/Simple Cases
- **Target queue**: Registration and Nurse Assessment queues for Urgent patients.
- **Root cause**: Conformance checking reveals Urgent patients are not being prioritized in practice (FIFO handling despite policy).
- **Action**: Implement/enforce a triage-based priority queue (e.g., separate physical or virtual queue) with staff training and system-enforced flagging.
- **Expected impact**: Reduces 90th percentile wait for Urgent patients significantly, improving clinical safety margins.

## 4. Trade-offs and Constraints

| Strategy | Potential Trade-off |
|---|---|
| Staggered shifts / added resource | Increases labor cost; may just shift bottleneck downstream (e.g., more patients now queue for tests instead of doctor) |
| Pre-ordering tests | Risk of unnecessary tests being ordered before clinical judgment confirms need (overtreatment/cost/quality risk); requires clear protocols to avoid clinically inappropriate parallelization |
| Real-time notification system | Upfront technology investment and staff training/adoption curve; possible alert fatigue if poorly designed |
| Fast-track for urgent cases | May increase wait times for Normal/Follow-up patients (queue reprioritization is zero-sum in a fixed-capacity system) |

**Balancing conflicting objectives:**
- Use **simulation modeling** (e.g., discrete-event simulation calibrated from the event log) *before* full rollout to predict how a change at one queue point affects downstream queues — avoiding a "whack-a-mole" bottleneck shift.
- Apply a **phased pilot approach**: implement one strategy in a single specialty/department, measure impact on both wait times *and* cost/quality proxies (e.g., test-ordering appropriateness rate, staff overtime hours) before clinic-wide rollout.
- Establish **guardrail metrics** alongside target metrics — e.g., track "unnecessary test rate" alongside "ECG queue time" for Strategy 2, to ensure clinical thoroughness isn't sacrificed for speed.
- Use **cost-per-minute-saved** as a joint criterion: prioritize strategies with the best ratio of wait-time reduction to incremental operating cost, rather than optimizing wait time alone.

## 5. Measuring Success

### KPIs Post-Implementation
| Category | KPI |
|---|---|
| **Primary (Wait Time)** | Mean/median/90th percentile waiting time per queue point (before/after comparison) |
| **Throughput** | Total visit duration (registration to check-out), cases/day processed |
| **Utilization** | Resource utilization rates (ensure balanced, not just shifted overload) |
| **Equity** | Wait time distribution segmented by Urgency/Patient Type (ensure Urgent patients consistently see lower wait) |
| **Quality/Safety proxy** | Test appropriateness rate, revisit/complication rate (to catch negative side effects of speed-focused changes) |
| **Cost** | Staff overtime hours, resource idle time, cost per patient visit |
| **Patient Experience** | Patient satisfaction survey scores, complaint volume related to waiting |
| **Process conformance** | % of cases following intended fast-track/parallel pathways as designed |

### Ongoing Monitoring Approach
- Maintain the **same event log schema** (Case ID, Activity, Timestamp, Resource, Patient Type, Urgency) as a continuous data feed, enabling a live process mining dashboard (e.g., using tools like Celonis, ProM, or custom queue-mining scripts).
- Set up **automated control charts / statistical process control (SPC)** on key queue metrics to detect drift or regression (e.g., if the 90th percentile wait creeps back up after 3 months, signaling reversion to old behavior or new bottleneck emergence).
- Conduct **periodic re-mining** (e.g., monthly) to re-run root cause analysis, ensuring newly emergent bottlenecks (potentially created by the optimization itself) are caught early — closing the loop into a continuous improvement (PDCA) cycle rather than a one-time fix.
- Use **A/B comparison** where feasible (e.g., one clinic location/department using new protocol vs. control) to isolate causal impact of interventions from seasonal/external variation.
