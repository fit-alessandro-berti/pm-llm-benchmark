## 0. Preliminaries: Making the Log Fit for ISC Analysis

Standard process mining is *case-centric*: it explains delay within a trace. ISCs are, by definition, invisible in a single trace — they only emerge when you look at the log as a **timeline of concurrent cases competing for shared state**. So the first step is a set of transformations that turn the case-centric log into a **system-state log**.

**0.1 Data quality checks first** (the snippet already reveals issues):
- `Shipping Label Gen.` appears with only a `COMPLETE` timestamp  no measurable duration; batch waiting must be inferred, not read.
- Rows are not globally time-ordered (ORD-5001's label row precedes ORD-5002's QC row)  re-sort; never trust log order.
- `System (Batch B1)` mixes resource and batch identity  split into `resource` and `batch_id` columns. If no batch ID exists, it must be *mined* (see §1.3).
- Verify each activity has matched START/COMPLETE pairs per (case, activity, occurrence); flag orphans; check clock skew between station scanners and the WMS.
- Confirm whether "Requires Cold Packing" and "Hazardous" are case-level static attributes (they appear to be)  promote to a case attribute table.

**0.2 Derived event-log columns (the analytical backbone):**

| Derived field | Definition | Purpose |
|---|---|---|
| `enable_time(c,a)` | completion time of the directly preceding activity in case *c* (per discovered/normative model) | separates *waiting* from *service* |
| `wait(c,a)` = `start  enable_time` | queueing/blocking time | the quantity to be explained |
| `service(c,a)` = `complete  start` | pure processing | within-instance component |
| `resource_class` | STD-pack / COLD-pack / QC / Picker | maps resources to constrained pools |
| `batch_id` | mined or logged | batching analysis |
| `hazmat_state_count(t)` | # cases with hazmat=TRUE currently in Packing  QC | regulatory constraint state |
| `cold_busy(t)` | # of the 5 cold stations occupied | resource constraint state |

**0.3 Build state time-series.** From START/COMPLETE pairs, construct step functions over the three months for: cold-station occupancy, standard-station occupancy, QC staff occupancy, hazmat-in-scope count, per-region "orders awaiting label" count. These five series are the *shared state variables* that create inter-case dependencies. Everything in §1 is essentially: *join each waiting interval against these state series.*

## 1. Identifying Instance-Spanning Constraints and Quantifying Their Impact

I use the ISC taxonomy from the literature (Fdhila/Indiono/Rinderle-Ma) to classify what we have, because each class demands a different detection method:

| Scenario feature | ISC class | Shared state |
|---|---|---|
| 5 Cold-Packing stations | **Limited resource / capacity constraint** | station pool |
| Regional shipping batches | **Batching / synchronization constraint** | batch membership set |
| Express preemption | **Ordering & priority constraint** | resource claim + preemption right |
| 10 hazmat in Packing  QC | **Simultaneity (cardinality) constraint over a set of activities** | facility-wide counter |

### 1.1 Baseline: control-flow and performance discovery
Run Inductive Miner (infrequent, ~0.8) on the full log to establish the normative model and confirm the 5-step happy path plus rework loops (e.g., QC  Packing rework, which *doubles* hazmat token holding time). Then compute a **performance spectrum** (Denisov & Fahland): plot every hand-off (e.g., Picking-complete  Packing-start) as a line segment from source time to target time. This visualization is the single most effective diagnostic for ISCs because:
- **Fan-in convergence to a single point** = batching (many lines terminate at one timestamp).
- **Horizontal "plateaus" / thickening bands** = queueing at a saturated resource.
- **Line crossings** = overtaking  priority/preemption.
- **Sudden band widening at specific times** = a cardinality cap becoming binding.

This gives qualitative confirmation; the rest is quantification.

### 1.2 Shared Cold-Packing stations (capacity ISC)

**Detection.**
- Identify the cold-station pool from the resource dictionary (`Station C*`) and validate: every case with `Requires Cold Packing = TRUE` should only ever be packed on a C-station. Any violation is either a data error or an undocumented workaround — both are findings.
- Reconstruct `cold_busy(t)`  {0..5}. Confirm the effective capacity is truly 5 (max observed concurrency); if max observed is 4, one station may be chronically out of service — a hidden capacity loss.

**Quantification metrics.**
- **Blocking probability** `P(cold_busy = 5)` overall, and conditioned on hour-of-day / day-of-week / peak-vs-normal season.
- **Contention-attributable wait**: for each cold case, `W_cont = min(t  enable : cold_busy(t) < 5)  enable_time`, i.e., the time the order provably could not have started because no station existed. The remainder (`wait  W_cont`) is *dispatch inefficiency* (a station was free but nobody moved the order) — an important, separately actionable finding.
- **Queue length** `L_q(t)` = number of cold-eligible orders with `enable_time  t < start`. Report mean, p95, and the daily peak curve.
- **Aggregate loss**:  `W_cont` over all cases  "cold-contention case-hours per week". Convert to business terms: *X% of missed SLAs had  Y minutes of cold-contention wait.*
- **Erlang/queueing cross-check**: fit  (cold-order arrival rate at packing) and  (1/mean cold service time). Compare observed W_q with M/M/5 predictions. A large positive gap indicates scheduling policy loss, not raw capacity loss — this determines whether the fix is "buy stations" or "schedule better".
- **Utilization vs. contention curve**: plot  against p95 wait to locate the knee. This is the evidence you need to justify a 6th or 7th station.

### 1.3 Shipping batching (synchronization ISC)

**Batch mining.** If `Batch B1`-style IDs exist, use them. If not, mine batches: cluster label-generation events by (destination region, timestamp within  seconds). Cases sharing region and a near-identical label timestamp constitute a batch (this is the classic batch-detection pattern of near-zero-variance completion timestamps across cases).

**Quantification metrics.**
- **Batch waiting time per case**: `W_batch(c) = label_time(c)  QC_complete(c)`. Decompose per case into *unavoidable* (system processing) and *synchronization wait*.
- **First-mover penalty**: `max(W_batch)  min(W_batch)` within a batch; and the distribution of "who suffers" — is it always the same region (e.g., low-volume regions like "West" wait far longer than "North")?
- **Batch size / span / fill-rate**: distribution of batch cardinality, batch span (last QC-complete  first QC-complete), and whether batches close on a *time trigger* or a *size trigger* (bimodality in size distribution reveals the rule in use).
- **Region-level Little's Law**: `L_region = _region × W_batch_region`  shows how much WIP is parked purely for consolidation.
- **SLA attribution**: % of late orders where `W_batch > slack_at_QC_completion`. This isolates orders that were *on time until batching*.
- **Cost trade-off baseline**: correlate batch size with (proxied) transport cost per order, so any batching change can be evaluated against the logistics saving it exists to produce.

### 1.4 Priority handling / express preemption (ordering ISC)

**Detection of preemption.** Preemption leaves distinct fingerprints:
1. A standard case's Packing has a START, then a *second* START (or a resume event) on the same resource, with an express case's START/COMPLETE nested inside the gap.
2. Or: unusually long `service` for a standard order on a station that simultaneously logged another case (overlapping intervals on a single resource — physically impossible unless interrupted/parallelized). Detect via **resource-interval overlap analysis**.
3. **Overtaking analysis**: for pairs (s, e) enabled on the same resource pool, count `enable(s) < enable(e)`  `start(e) < start(s)`. The overtaking rate by order type quantifies de-facto priority even without explicit preemption events.

**Quantification metrics.**
- **Number/rate of preemptions** per week, per resource pool.
- **Displacement cost**: for each express arrival, the extra wait imposed on standard orders =  over displaced cases of (actual start  start they would have had under FIFO among the enabled set). Computed by replaying the enabled-set queue under a counterfactual FIFO discipline.
- **Resumption overhead**: `resume_start  interrupt_time` minus the queue-clearing time = pure setup/switch loss. Cold stations likely have sanitation/temperature-recovery setup — measurable as elevated inter-case gaps on C-stations.
- **Express benefit**: express p50/p95 cycle time vs. counterfactual FIFO cycle time. Compare *benefit gained by express* to *cost imposed on standard*: if 1 minute saved for express costs 4 minutes across standard orders, the policy is value-destroying unless express SLA penalties are 4×.
- **Fairness/starvation**: p99 waiting time of standard orders during express surges; count of standard orders preempted more than once.

### 1.5 Hazardous-material cardinality limit (simultaneity ISC)

**Detection.** Compute `hazmat_state_count(t)` = |{c : hazmat(c)  t  [start,complete] of Packing or QC}| — careful: the constraint spans **two activities**, so the counter must union both intervals per case and handle QC-rework loops (a case may re-enter the counted set).

**Quantification metrics.**
- **Compliance check first** (this is a conformance question, not a performance one): `max_t hazmat_state_count(t)`. Any t with count > 10 is a *regulatory violation* — report immediately, with the exact cases and timestamps. Also report near-misses (count = 10) as risk exposure.
- **Binding fraction**: `%time(count = 10)`, overall and by shift/season.
- **Blocked case-hours**: for hazmat cases, `W_haz = min(t  enable : count(t) < 10)  enable_time` — provable regulatory wait.
- **Token dwell time**: average time a hazmat order *holds* a slot = (QC complete  Packing start), including the *idle* interval between Packing complete and QC start. If that inter-activity gap is large, the cap is being consumed by queueing rather than by work — a huge, cheap improvement lever (see Strategy 3).
- **Throughput ceiling**: theoretical hazmat throughput = 10 / mean token dwell time (Little's Law). Compare against actual hazmat arrival rate to see how close the facility is to a hard structural ceiling.
- **Spillover**: does the cap delay *non*-hazmat orders? (It shouldn't directly, but blocked hazmat orders occupying conveyors/staging space can create secondary blocking — test by correlating non-hazmat packing wait with `count(t)`.)

### 1.6 Differentiating Within-Instance vs. Between-Instance Waiting

This is the analytical crux. I apply a **deterministic attribution cascade** to every waiting interval `[enable(c,a), start(c,a))`, evaluated against the reconstructed state series:

```
for each waiting interval, at each sub-interval boundary:
  1. Is it a batching step and batch not yet closed?          -> BETWEEN: batch synchronization
  2. hazmat(c) AND hazmat_count = 10?                          -> BETWEEN: regulatory blocking
  3. All eligible resources of the required class busy
     with OTHER cases?                                         -> BETWEEN: resource contention
        3a. ...and the occupying case is Express while c is
            Standard, and c was enabled first                   -> BETWEEN: priority displacement
  4. Eligible resource free, but c not started?                 -> WITHIN/ORG: dispatch delay,
                                                                   shift change, no staff on duty
  5. Case-specific hold (address check, stock-out event)        -> WITHIN: case exception
```

Key points:
- Attribution is **time-sliced**, not whole-interval: one wait can be 6 min hazmat-blocked, then 4 min cold-contention, then 2 min dispatch. Report a **stacked waiting-time decomposition** per activity and per case cohort.
- **Service time** (`complete  start`) is by definition within-instance — *except* when preemption inflates it. So preemption-inflated service must be re-classified: `service_effective` = sum of active sub-intervals; the interruption gap is reclassified as between-instance (priority displacement).
- Resource calendars matter: a "free" station outside shift hours is *not* free. Mine calendars from resource activity patterns before applying rule 4, otherwise night-time gaps pollute the "dispatch delay" bucket.
- **Validation of the attribution**: regress total case cycle time on the decomposed components; the components should explain the bulk of variance. A large unexplained residual means a constraint you haven't modeled (e.g., conveyor capacity, tote availability) — treat that as a discovery signal.

**Headline deliverable of §1:** a waterfall chart per order cohort (Standard/Express × Cold/Ambient × Hazmat/Non-hazmat):
`Cycle time =  service + within-instance wait + cold contention + batch sync + priority displacement + hazmat blocking + dispatch residual`

That single chart tells management exactly how many minutes each ISC costs, and it is the ranking mechanism for §3.

## 2. Analyzing Constraint Interactions

ISCs are not additive; they couple through shared state and through the same cases. The analysis method is: (a) build a **constraint co-occurrence matrix** — for every waiting interval, record which constraints were simultaneously binding; (b) run **conditional impact analysis** — mean wait under constraint A alone vs. A  B; (c) where confounding is likely, use matched-cohort / counterfactual replay rather than raw correlation.

### 2.1 Express priority × Cold-packing scarcity (the sharpest interaction)
Express + cold-required orders (like ORD-5002) compete for a pool of only **5**. With few servers, priority pre-emption has a disproportionate effect: in an M/M/1-like regime the low-priority class absorbs almost the entire variance. Quantify with:
- Conditional wait: standard-cold waiting time when `express_cold_arrivals` in the prior 30 min is high vs. low.
- **Convoy effect**: a burst of express-cold orders can push standard-cold waits into a self-reinforcing queue that persists long after the burst (measure queue decay half-life).
- Preemption on a *cold* station is more expensive than on a standard station (re-chilling/sanitation setup), so preemption cost is *resource-class dependent* — a fact that must drive the policy design.

### 2.2 Batching × Hazmat cap
Multiple hazmat orders bound for the same region get batched together. Consequences:
- The hazmat cap throttles *how fast* they can clear Packing/QC  batch closure is delayed  the whole batch (including non-hazmat members) waits for the slowest hazmat members. **A regulatory constraint on 2 activities silently propagates into a delay for unrelated, compliant orders.** Detect by testing whether batch span correlates with the number of hazmat members in the batch.
- Conversely, if a batch trigger fires and orders are *rushed* into Packing to make the cutoff, they collide at the hazmat cap  the batching policy manufactures its own bottleneck. Look for periodic spikes in `hazmat_count` synchronized with batch cutoff times (cross-correlate the two time series; a peak at lag  (pack+QC duration) is the smoking gun).

### 2.3 Hazmat cap × Express priority
An express hazmat order arriving at a saturated hazmat counter **cannot be expedited by preemption** — preempting a standard order frees a *station*, but the freed order does not necessarily release its regulatory token (it may be sitting between Packing and QC, still counted). This is the classic case where a priority mechanism fails silently because it acts on the wrong resource. Quantify: express-hazmat orders' wait vs. express-non-hazmat orders' wait; if the gap is large, priority policy is not constraint-aware.

Worse: preempting a standard hazmat order *mid-Packing* may extend its residence in the counted set, **reducing** hazmat throughput. Preemption can be net-negative here.

### 2.4 Cold-packing × Hazmat cap (double constraint)
An order that is both cold and hazmat needs a token *and* one of 5 stations. Joint availability probability is much lower than either marginal — these orders are structurally the worst performers. Verify by cohort cycle-time analysis; they typically show p95 delays several times the average.

### 2.5 Batching × Cold-packing
Cold orders that finish QC early then sit waiting for a batch may need refrigerated staging space. If staging is limited, a *downstream* batching delay creates *upstream* blocking of cold stations (classic blocking-after-service). Test: correlate cold-station idle-but-unavailable time with regional batch queue depth.

### 2.6 Why interactions matter for optimization
- **Local optimization backfires.** Adding a 6th cold station reduces cold waits but pushes more flow into Packing/QC  hazmat cap binds more often  net throughput gain is a fraction of expectation. Only a joint model reveals this.
- **The binding constraint moves.** Under peak load the bottleneck may shift from cold stations (morning) to the hazmat cap (afternoon) to batch cutoffs (evening). Static policies are therefore structurally suboptimal; this argues for the *dynamic* policies in §3.
- **Interactions define the correct improvement sequence.** If batching is the dominant source of missed SLAs, spending capital on cold stations optimizes a non-binding constraint. The co-occurrence matrix produces the priority ordering.

## 3. Constraint-Aware Optimization Strategies

I propose four strategies (three core + one enabling), each explicitly designed around the inter-case dependency rather than the individual case.

### Strategy 1 — Predictive, Reservation-Based Cold-Packing Allocation with Express Reserve
**Primarily addresses:** Cold-packing capacity ISC × Express priority ISC (interaction 2.1).

**Changes proposed:**
1. **Replace preemption with a reservation/priority-queue discipline on cold stations.** Cold stations become non-preemptive (packing runs are short; the setup cost of preemption exceeds the benefit — validate with the measured resumption overhead from §1.4). Express orders instead get a *place at the head of the queue* plus a reserved-capacity rule.
2. **Threshold-based express reserve**: keep *k* of the 5 stations available for express when the predicted express-cold arrival rate in the next horizon exceeds a threshold; set *k* = 0 in quiet periods so no capacity is wasted. This is a state-dependent reservation policy, tuned by simulation (§4).
3. **Look-ahead reservation from Picking.** When a cold order *starts* Item Picking, the WMS forecasts its packing-ready time (distribution learned from historical picking durations conditioned on item count/zone) and **soft-books** a cold station slot. Orders whose predicted slot is unavailable are *held or resequenced at picking*, not left to queue at packing.
4. **Decoupling redesign:** introduce *n* "cold-capable" conversion kits (insulated liners + gel packs staged at standard stations) for the lowest-complexity cold orders, converting a hard capacity constraint into a soft, elastic one at low cost.

**Data/analysis leverage:** arrival-rate forecasting per hour/day-of-week/season from three months of history; service-time distributions per station; the utilization-vs-p95-wait knee from §1.2 to size *k* and *n*; the M/M/5 gap to prove how much is policy loss vs. capacity loss.

**Expected outcomes:** p95 cold-packing wait down materially; elimination of preemption setup losses on cold stations; express cold-order cycle time protected *without* the convoy effect on standard orders; the look-ahead reservation moves waiting **upstream** to picking, where an order occupies no constrained resource (waiting in a cheap queue instead of blocking an expensive one).

**Risks/guardrails:** reserved capacity can idle stations — monitor "reserve idle minutes" and auto-decay *k* if express arrivals under-materialize.

---

### Strategy 2 — Deadline-Aware Dynamic Batching with Label/Physical Decoupling
**Primarily addresses:** Batching ISC; interacts with hazmat (2.2) and cold staging (2.5).

**Changes proposed:**
1. **Replace the fixed batch rule with a triple trigger**: close a regional batch when **(a)** target size reached, **OR** **(b)** the *minimum remaining slack* across batch members drops below a safety margin (`min_c (due_time(c)  now  remaining_transit) < `), **OR** **(c)** a maximum dwell cap is hit. Trigger (b) is the key innovation: it makes the batch respond to the *most at-risk case*, so batching never causes an SLA breach.
2. **Decouple label generation from physical consolidation.** Label generation is an information activity with near-zero cost; there is no functional reason for it to wait for the batch. Generate the label at QC completion; perform *physical* consolidation at the sortation/staging area. This converts a hard synchronization ISC into a soft, downstream sorting operation and removes it from the critical path entirely for label-timestamp-driven SLAs.
3. **Adaptive region clustering.** Low-volume regions suffer the worst first-mover penalty (§1.3). Use historical volume-by-region-by-hour to merge slow regions into composite batches, or attach them to a scheduled carrier cutoff rather than a size trigger.
4. **Hazmat-aware batch admission** (interaction fix): when forming a batch, cap the number of hazmat members released into Packing simultaneously, and *stagger* their release so the batch's hazmat members flow through the cap smoothly rather than colliding at the cutoff.

**Data/analysis leverage:** batch-size vs. transport-cost curve to set the size target; per-region volume/inter-arrival distributions to set dwell caps; historical slack distributions at QC completion to calibrate ; cross-correlation of batch cutoffs with `hazmat_count` peaks to size the stagger.

**Expected outcomes:** batch synchronization wait removed from the SLA-critical path (decoupling) or bounded by design (slack trigger); first-mover penalty reduced sharply for low-volume regions; WIP parked for consolidation (Little's Law, §1.3) reduced; secondary benefit of freeing refrigerated staging.

---

### Strategy 3 — Hazmat "Token" Semaphore with Dwell-Time Compression and Admission Control
**Primarily addresses:** Hazmat cardinality ISC; interacts with priority (2.3) and batching (2.2).

**Changes proposed:**
1. **Make the constraint explicit and machine-enforced.** Today the limit is presumably managed by human judgement (hence the near-miss risk). Implement a **counting semaphore of 10 tokens** in the WMS: a hazmat order acquires a token at Packing START and releases it at QC COMPLETE. No token  order is not released to Packing. This *guarantees* compliance (a hard requirement) and simultaneously generates clean event data on token acquisition/wait.
2. **Compress token dwell time — the highest-leverage move.** From §1.5, a token is held across Packing, the PackingQC gap, and QC. If the gap is significant, the cap is being spent on *queueing, not work*. Countermeasures: (a) **pull-based QC** — reserve a QC slot at the moment a hazmat token is granted, so QC never queues; (b) co-locate a QC station adjacent to hazmat packing to remove transport time; (c) prioritize hazmat orders in the QC queue (they are the only ones holding a scarce global token). Effective capacity rises by `10/dwell_new  10/dwell_old` orders per hour *with zero capital spend and zero change to the regulatory limit.*
3. **Constraint-aware priority:** for express hazmat orders, priority must act on the **token queue**, not on the station. Express hazmat orders get first claim on released tokens. Explicitly forbid preempting a standard hazmat order mid-Packing (it holds a token either way and preemption extends dwell — see 2.3).
4. **Admission/release control upstream:** hold hazmat orders at picking when the token pool is saturated and predicted release times are distant, preventing physical congestion at the packing area (avoids the secondary blocking found in §1.5).

**Data/analysis leverage:** measured token dwell decomposition (packing service / inter-activity gap / QC service) to target the largest component; hazmat arrival forecasting to set release thresholds; Little's-Law ceiling (10 / dwell) to communicate the hard throughput limit and justify the co-location investment.

**Expected outcomes:** **100% guaranteed compliance** with an auditable trail (a hard, non-negotiable KPI); hazmat throughput increase proportional to dwell-time compression; hazmat blocking wait reduced; elimination of the batch-cutoff hazmat collision.

---

### Strategy 4 (enabling) — Constraint-Aware Order Release & Sequencing at Picking
**Primarily addresses:** all four ISCs jointly, via load levelling.

**Changes proposed:** replace FIFO/pick-path-only sequencing at Item Picking with a scoring function that considers the *downstream constraint state*:
`score(c) = w·slack(c) + w·express(c) + w·P(cold station free at predicted ready time) + w·P(hazmat token free) + w·batch_affinity(c)`
Orders whose downstream constraints are predicted to be saturated are deferred; orders that fit the current gap are pulled forward. Effectively CONWIP-style release with constraint-aware dispatching.

**Rationale grounded in the ISC analysis:** every minute of waiting is cheaper *before* an order enters the constrained zone. This strategy converts contention-in-the-bottleneck (expensive, causes blocking and preemption) into scheduled-wait-upstream (cheap, invisible to the customer).

**Expected outcomes:** smoother `cold_busy` and `hazmat_count` profiles (lower variance  lower queueing by Kingman's formula), fewer preemptions needed, higher effective utilization of the constrained resources.

The analysis in §1.2 (utilization knee) plus §4 (scenario testing) is exactly the evidence needed for that capital decision.

## 4. Simulation and Validation

Because these strategies change *inter-case* behaviour, A/B testing in production is risky (regulatory exposure) and analytical queueing models can't capture the coupling. **Discrete-event simulation (DES) with a data-driven, mined model is the right validation instrument** — ideally implemented as a Colored Petri Net or an agent/resource-based DES (SimPy, AnyLogic, Simul8) rather than a naive token-per-case simulator.

### 4.1 Model construction (mined, not assumed)
- **Control flow** from the discovered model (including QCPacking rework probabilities, which materially affect hazmat token dwell).
- **Case arrivals**: non-stationary Poisson process with hourly/daily/seasonal rates mined from `Order Received`; peak-season profile fitted separately.
- **Case attribute generation**: sample (order type, region, cold flag, hazmat flag) from the *joint* empirical distribution, not independently — correlations (e.g., coldexpress) drive the worst-case interactions.
- **Service times**: fitted distributions per activity × resource class × attribute cohort (log-normal typically fits picking/packing), *using de-preempted effective service times* from §1.4 — otherwise preemption inflation is baked in as "normal" work.
- **Resource calendars & availability**: shift patterns, breaks, station downtime mined from resource idle-gap analysis.

### 4.2 Explicitly modelling the ISCs (the critical part)
A generic process simulator will *not* reproduce these behaviours; each must be coded as first-class shared state:

| ISC | Simulation construct |
|---|---|
| Cold stations | Resource pool of capacity 5 with a **configurable queue discipline** (FIFO / priority / reservation with parameter *k*) — the discipline must be a swappable strategy object for experimentation |
| Hazmat limit | **Counting semaphore (10)** acquired at Packing start, released at QC complete, spanning both activities and surviving rework loops. Must include the inter-activity holding period. |
| Batching | Batch-assembly block with **all three triggers** (size / slack / dwell), plus per-region parameters; must model the physical vs. informational split for Strategy 2 |
| Priority/preemption | Preemptive-resume *or* non-preemptive priority queue, with an explicit **setup-time penalty on resume** parameterized from measured resumption overhead |
| Secondary blocking | Finite staging/buffer capacity (especially refrigerated staging) so blocking-after-service is reproduced |

### 4.3 Validation before experimentation
Never trust an unvalidated simulation of ISCs:
1. **Baseline replication**: run the as-is model over the same three months; compare against the real log on (a) cycle-time distributions per cohort (two-sample KS test / Wasserstein distance, not just means), (b) resource utilizations, (c) **the ISC-specific state distributions** — the distribution of `cold_busy(t)` and `hazmat_count(t)` must match, and `%time at cap` must match. If mean cycle time matches but the occupancy distributions don't, the model is right for the wrong reasons and will mispredict every intervention.
2. **Queue-length and batch-size distribution matching** as additional acceptance criteria.
3. **Out-of-sample backtest**: calibrate on months 1–2, validate on month 3.
4. **Face validation** with packing supervisors on animated peak-hour runs.

### 4.4 Experimental design
- **Scenarios**: baseline; each strategy alone; all combinations (2 factorial or a screening design) — because interactions between *strategies* mirror interactions between *constraints* (e.g., Strategy 2's decoupling changes the load pattern that Strategy 1 must handle).
- **Load scenarios**: normal, peak season (+X% arrivals), express-mix surge, hazmat-mix surge. Peak is where ISCs bind, so it is the decisive test.
- **Statistical rigour**: warm-up period determination (Welch's method), 30 replications, **common random numbers** across scenarios to reduce variance in comparisons, confidence intervals on all KPI deltas.
- **Parameter optimization**: use the simulation as the objective function for tuning *k* (express reserve),  (slack trigger), batch size targets, and release thresholds — e.g., via OptQuest/Bayesian optimization over the policy parameters.
- **KPIs**: p50/p95 end-to-end cycle time per cohort; on-time delivery %; throughput/day; cold-station utilization and p95 queue; hazmat blocked case-hours; batch sync wait; preemption count; **and a hard constraint check: max hazmat concurrency must be 10 in every replication** (any violation invalidates that policy outright).
- **Sensitivity/robustness**: how do gains degrade if arrival rates are 20% above forecast or a cold station fails? Prefer robust policies over fragile optima.

## 5. Post-Implementation Monitoring

Implementation should be **phased** (e.g., Strategy 3's semaphore first — it is a compliance control; then Strategy 2's decoupling; then Strategy 1) with the process mining pipeline re-run continuously as an **operational digital twin / online conformance monitor**.

### 5.1 Dashboard architecture (four layers)

**Layer 1 — Outcome KPIs (executive):**
- On-time delivery % overall and by cohort (Standard/Express × Cold × Hazmat × Region).
- p50/p95/p99 end-to-end cycle time, with **statistical process control charts** and pre/post change-point annotations.
- Throughput (orders/day) and cost per order.

**Layer 2 — ISC-specific control panels (the core of ISC monitoring):**

| Constraint | Live metrics | Alert condition |
|---|---|---|
| Cold packing | `cold_busy(t)` heatmap by hour/day; blocking probability; queue length p95; express-reserve idle minutes; contention wait vs. dispatch-delay split | blocking prob > target for 2 consecutive hours |
| Batching | batch sync wait p95 per region; batch fill rate; trigger-type mix (size vs. slack vs. dwell); first-mover penalty; **% batches closed by slack trigger** (rising = system under stress) | slack-trigger share > threshold; any batch member breaching SLA |
| Priority | preemption count/day; overtaking rate; **displacement cost** (standard-order minutes lost per express order); express vs. standard p95 ratio; standard-order starvation count (p99) | displacement cost per express order exceeds the express SLA value |
| Hazmat | live `hazmat_count(t)` gauge; **max concurrency (must be 10)**; %time at cap; token dwell time decomposed into pack / gap / QC; blocked case-hours | **any** reading > 10  immediate compliance incident; sustained cap-binding  capacity review |

**Layer 3 — Waiting-time decomposition trend:** the §1.6 stacked waterfall, tracked weekly. This is the single best evidence of whether ISC management improved: the *between-instance* segments should shrink while service times stay constant. If total cycle time fell only because service times fell, the ISC strategies did not work.

**Layer 4 — Diagnostics:** live performance spectrum for the key hand-offs (PickingPacking, QCLabel), variant analysis, resource productivity, and **rework rate** (QC failures inflate hazmat token dwell and cold-station load).

### 5.2 Tracking that the ISCs specifically are managed better
- **Constraint conformance checking**: encode each ISC as a monitorable rule (semaphore 10; cold concurrency 5; express-before-standard-within-pool; batch dwell  cap) and run automated conformance over the streaming log. Report **violation count = 0** as a compliance KPI and log every near-miss.
- **Before/after distributional comparison** (not just means): KS tests on cold-queue length, batch sync wait, hazmat blocked case-hours, pre- vs. post-implementation, controlling for volume mix (the gains must survive the fact that volume may have changed).
- **Counterfactual baseline**: keep the calibrated simulation running with the *old* policies against the *actual current arrivals*. The difference between simulated-old and observed-new is a continuously updated, mix-adjusted estimate of realized benefit — far more defensible than a naive year-on-year comparison.
- **Drift detection**: monitor arrival mix (express %, cold %, hazmat %, regional split) and service-time distributions. Policy parameters (*k*, , batch targets) were tuned to a specific mix; when drift is detected, trigger automatic re-optimization via the simulation. Peak season should trigger a pre-scheduled parameter switch, validated in advance.
- **Predictive monitoring**: use the state variables as live features to predict SLA breach risk per open order (e.g., "orders currently waiting on a hazmat token with slack < 30 min"), enabling operational intervention rather than post-hoc reporting.

### 5.3 Governance
Monthly review comparing realized vs. simulated benefits; a documented feedback loop where deviations trigger model re-calibration; and a standing rule that the hazmat compliance metric is a **veto KPI** — any optimization that improves flow at the cost of a single breach is reverted immediately.

## Summary

The defining insight is that in this facility, **most of the delay is not in the activities — it is in the couplings between cases.** Standard case-centric process mining will therefore attribute delay to the wrong causes. The approach above (i) reconstructs the facility's shared state as time series, (ii) attributes every waiting minute to a specific inter-case mechanism, (iii) maps how those mechanisms amplify each other, (iv) designs policies that act on the *shared state* (reservations, semaphores, slack-driven triggers, constraint-aware release) rather than on individual cases, (v) validates them in a simulation that reproduces the state distributions — not just the averages — and (vi) monitors the constraints themselves as first-class KPIs, with regulatory compliance as an inviolable guardrail.
