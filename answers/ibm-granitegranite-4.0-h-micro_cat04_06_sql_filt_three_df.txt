To accomplish the task described, we need to write a DuckDB query that filters out events from cases that contain the specific sequence of activities and meet the timing condition, and return all other events. Here's a step-by-step approach to achieve this:

### Step 1: Identify Cases with the Specific Sequence and Timing Condition

We need to first identify cases that contain the exact sequence of activities 'Approve Purchase Requisition', 'Create Order', and 'Confirm Order' in that order, with the time between 'Create Order' and 'Confirm Order' being more than 5 days.

### Step 2: Exclude Identified Cases

After identifying these cases, we need to exclude all events belonging to those cases from our final result set.

### DuckDB Query

Here is the SQL query that achieves the above requirements:

```sql
WITH filtered_cases AS (
    SELECT DISTINCT case_id
    FROM event_log
    WHERE activity = 'Approve Purchase Requisition'
    AND EXISTS (
        SELECT 1
        FROM event_log e2
        WHERE e2.case_id = event_log.case_id
          AND e2.activity = 'Create Order'
          AND e2.timestamp > DATEADD(day, 5, e1.timestamp) -- 5 days after 'Approve Purchase Requisition'
          AND e2.activity = 'Confirm Order'
    )
)
SELECT *
FROM event_log
WHERE case_id NOT IN (SELECT case_id FROM filtered_cases);
```

### Explanation

1. **CTE `filtered_cases`**:
   - This common table expression (CTE) identifies cases that contain the specific sequence of activities.
   - It uses a `WHERE` clause to filter for rows where the activity is 'Approve Purchase Requisition'.
   - The `EXISTS` subquery checks for the presence of 'Create Order' within 5 days of 'Approve Purchase Requisition' and then 'Confirm Order' immediately after 'Create Order' within the same case.
   - `DISTINCT` ensures each case is listed only once in the result.

2. **Final SELECT**:
   - The main `SELECT` statement retrieves all rows from `event_log`.
   - The `WHERE` clause excludes any rows where the `case_id` is in the `filtered_cases` CTE, effectively removing events from cases that matched our criteria.

### Assumptions and Notes

- The query assumes that the `event_log` table is indexed appropriately on `case_id`, `activity`, and `timestamp` to optimize the performance of the query.
- DuckDB handles `DATEADD` similar to SQL Server. If your DuckDB version or setup uses a different syntax for date arithmetic, you might need to adjust the `DATEADD` function accordingly.
- This query assumes that the `timestamp` column is of a datetime type, allowing for direct comparisons with date arithmetic (e.g., `DATEADD`).
