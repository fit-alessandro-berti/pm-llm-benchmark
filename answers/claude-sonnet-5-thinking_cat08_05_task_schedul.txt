# Precision Parts Inc.: Data-Driven Scheduling Transformation

## 1. Analyzing Historical Scheduling Performance and Dynamics

### 1.1 Process Reconstruction

The first step is transforming the flat MES event log into a structured process view suitable for mining:

- **Case notion**: Job ID (JOB-7001) as the primary case identifier for job-centric analysis; secondarily, Resource ID (e.g., MILL-03) as a case identifier for a *resource-centric* view (reconstructing the "life story" of each machine — its sequence of setups, jobs, idle periods).
- **Event abstraction**: Collapse paired events (Setup Start/End, Task Start/End, Queue Entry/Exit) into interval-based events with duration attributes, rather than treating each log line as an atomic event. This gives us an **interval log** amenable to duration-based analytics rather than only control-flow discovery.
- **Two complementary process models**:
  - **Job-flow model** (via Directly-Follows Graph / Heuristic/Inductive Miner) showing the *actual* routing variants jobs took through work centers — critical in a high-mix shop where routings differ per job type.
  - **Resource-schedule model** — a Gantt-like reconstruction per machine showing actual sequences of setups/tasks/idle gaps, which is the artifact needed to analyze sequencing and setup efficiency.

### 1.2 Techniques and Metrics

**Flow times, lead times, makespan**
- Compute per-job **lead time** = Job Completed timestamp  Job Released timestamp.
- Decompose into **touch time** (sum of Task StartEnd durations) vs. **queue time** (sum of Queue EntryTask Start durations) vs. **setup time**. This decomposition (a core process-mining technique — "time in state" analysis) usually reveals that touch time is a small fraction (often <20%) of total lead time in job shops.
- Build **lead time distributions** segmented by job type/routing variant, priority class, and order size, using box plots and survival curves to expose variance, not just averages — variance is what destroys due-date predictability.
- **Makespan analysis**: for batches/weeks, reconstruct the achieved completion time of the last job in a cohort vs. theoretical minimum (critical path through the routing graph) to quantify "schedule slack" being lost.

**Task waiting (queue) times per work center**
- For every (Case, Activity, Resource) triple, compute Queue EntrySetup/Task Start delta.
- Aggregate into **queue time distributions per resource**, and plot **queue length over time** (reconstructed by counting overlapping Queue Entry–Task Start intervals) — this is effectively deriving a WIP-per-station time series from event data, akin to a "token count" replay in Petri-net terms.
- Correlate queue time with time-of-day/day-of-week and with upstream completion bursts to detect **batch-arrival-induced congestion**.

**Resource utilization**
- For each machine: partition the observation window into **Productive (Task execution) / Setup / Idle-Starved (no job waiting) / Idle-Blocked (job waiting but resource down or unavailable) / Breakdown** states.
- This requires reconciling Task, Setup, and Resource (Breakdown) event streams onto the same timeline per resource — a resource-log replay.
- Compute **utilization ratio**, **setup ratio** (setup time / total busy time), and **OEE-like composite score** per machine to rank criticality.

**Sequence-dependent setup time analysis**
- Using the "Previous job" attribute (or inferring it from resource-sorted event order), construct a **setup-time matrix**: rows = previous job family/type, columns = next job family/type, cells = mean/median observed setup duration (Actual, not Planned).
- Apply **clustering on job attributes** (material, tool, geometry class) to see if setup time correlates with specific attribute transitions (e.g., material changeover requiring cleaning) — this produces a **setup-time similarity/distance model** usable later for sequencing optimization.
- Compare **Planned vs. Actual setup duration** to quantify estimation bias (e.g., systematic 15-20% underestimation, as seen in the sample: 20 min planned vs 23.5 actual) — this bias itself degrades any schedule built on planned times.

**Schedule adherence and tardiness**
- Tardiness = max(0, Completion  Due Date); Lateness allows negative values (early completion) for symmetric analysis.
- Compute **tardiness rate** (% jobs late), **mean tardiness**, **tardiness distribution tail** (P90/P95 — the "bad surprises"), and **Days-Late-per-Priority-Class**.
- Use **Conformance checking**: define an idealized/reference model (e.g., planned routing + planned durations) and replay actual traces against it to quantify **deviation events** (extra queue time, rework loops, unplanned resequencing) and their contribution to tardiness via **root-cause attribution regression** (task-level delay contribution to case-level tardiness).

**Impact of disruptions**
- Treat Breakdown Start/End and Priority Change events as **exogenous shock events**. 
- Use **before/after windowing**: compare KPI distributions (queue time, tardiness) for jobs in-flight during a breakdown window at the affected resource vs. jobs unaffected, using a difference-in-differences style comparison.
- For hot-job insertions, trace the **downstream ripple effect**: measure the change in waiting time for jobs queued behind the affected resource within the following N hours, to quantify **disruption propagation distance and decay**.

## 2. Diagnosing Scheduling Pathologies

### 2.1 Bottleneck Identification and Quantification
- Rank machines by a **composite bottleneck score**: utilization × average queue length × contribution to case-level critical path (from replaying jobs against the resource-schedule model and identifying which resource visit lies on the critical path most often, analogous to critical-path analysis in project scheduling but applied per-case then aggregated).
- Quantify: "Machine MILL-02 is on the critical path for 62% of late jobs, and its average queue length is 3.4x that of MILL-03, despite similar theoretical capacity" — this converts intuition ("we know X is a bottleneck") into an auditable, ranked, quantified statement.

### 2.2 Poor Prioritization Evidence
- **Variant/cohort comparison**: split jobs into On-Time vs. Late, and High-Priority vs. others; compare their queue time distributions at each resource.
- If High-Priority jobs show *similar or worse* queue-time distributions than Medium-Priority jobs at a given station, that is direct evidence that the local FCFS/EDD rule is not effectively respecting priority — because it's applied *locally* without shop-wide visibility, a high-priority job can sit behind several medium jobs simply because it arrived later at that queue.
- Compute a **priority-inversion rate**: % of instances where a lower-priority job started before a higher-priority job was in queue and eligible.

### 2.3 Suboptimal Sequencing / Setup Time Inflation
- Compare **actual sequence realized** (from resource-log replay) vs. **theoretical minimum setup path** (solved as a small TSP/sequencing problem using the mined setup-time matrix from 1.2) for the same set of jobs processed in a shift/day/week window.
- The gap = "excess setup time due to poor sequencing." E.g., "Grinding station incurred 145 hrs of setup time in Q1 vs. an estimated 95 hrs achievable minimum for the same job mix — 34% is avoidable through resequencing alone."

### 2.4 Starvation of Downstream Resources
- Detect periods where a downstream resource is Idle-Starved (waiting, no queue) immediately following periods where its upstream feeder resource has high queue/utilization — a lag correlation between upstream busy-state and downstream starved-state.
- This distinguishes true **capacity imbalance** (downstream faster than upstream permanently) from **scheduling-induced starvation** (upstream has capacity but is prioritizing wrong jobs / doing unnecessary setups, causing intermittent starvation bursts).

### 2.5 Bullwhip / WIP Variability
- Reconstruct **WIP-over-time series** per station (from queue entry/exit event counts) and compute variance/amplitude; compare the amplification of variance from upstream to downstream stations (classic bullwhip signature: variance of WIP at downstream stations exceeds variance of arrivals from immediate upstream due to batching/lot-sizing behavior and reactive dispatching).
- Correlate WIP spikes with hot-job insertion events and breakdown events to attribute a portion of WIP variability directly to disruption-handling policy (or lack thereof) rather than pure demand variability.

## 3. Root Cause Analysis of Scheduling Ineffectiveness

| Diagnosed Pathology | Candidate Root Causes | How Process Mining Discriminates |
|---|---|---|
| Bottleneck overload | (a) genuine capacity shortage vs. (b) bad job routing/sequencing sending avoidable work to it | Compare theoretical minimum load (sum of *necessary* processing time for jobs that *must* use this resource) vs. actual load including setup inflation and any misrouted/reworked jobs. If theoretical-necessary load already exceeds capacity  true capacity issue; if actual load >> theoretical-necessary  scheduling/setup issue. |
| Priority inversions | Local FCFS/EDD rule has no visibility beyond its own queue | Priority-inversion rate quantifies frequency; conformance checking against a "should-have-been-prioritized" reference schedule isolates rule limitation from data unavailability. |
| Setup time inflation | Rule doesn't consider setup at all (pure FCFS/EDD ignores changeover) | The gap between actual sequence and TSP-optimal sequence (2.3) directly measures this; if the rule considered setups, the gap would trend to zero over time — persistence of the gap over the full year of data indicates a structural rule deficiency, not random noise. |
| Downstream starvation | Upstream local optimization (e.g., always processing longest job first) starves the line | Lag-correlation and Granger-causality-style testing between upstream dispatching decisions and downstream idle bursts. |
| Disruption sensitivity | No re-optimization mechanism after breakdown/hot-job — the system just resumes the static rule, causing large ripple delays | Compare recovery time (time to return WIP/queue metrics to pre-disruption baseline) across disruption events; long, high-variance recovery times without decreasing trend over the year suggest no learning/adaptive mechanism exists — a rule-design issue, not capacity. |
| Inaccurate duration estimates | Planned vs Actual systematic bias (as in the 20min23.5min setup example) | Direct comparison of Planned vs Actual fields across thousands of instances; a consistent bias (not just variance) implicates the estimation/planning process itself as a root cause feeding bad schedules downstream. |

**Key discriminator — capacity vs. logic vs. variability:**
Construct a simple queueing-theoretic sanity check: for each resource, compute utilization  from *actual necessary* workload. If  is close to or exceeds 1, queueing theory predicts large, high-variance queues *regardless* of dispatch rule sophistication — meaning capacity investment (or work re-routing/off-loading) is required, not just better rules. If  is moderate (e.g., 0.75–0.85) yet queues/tardiness are still severe, that strongly implicates **scheduling logic and setup inefficiency** as the dominant root cause, since queueing theory would predict much better performance at that utilization under a good policy. This -based triage should be done per-resource, since the shop likely has both true and false bottlenecks.

## 4. Advanced Data-Driven Scheduling Strategies

### Strategy 1: Multi-Factor Dynamic Dispatching (Enhanced Priority Index)

**Core logic:** Replace static FCFS/EDD with a real-time composite priority score computed at each dispatch decision point for every job waiting at a resource:

```
Score(j) = w1 · UrgencyFactor(j) + w2 · CriticalRatio(j) 
          w3 · SetupPenalty(j, last_job_on_machine) 
         + w4 · DownstreamCongestionFactor(j) 
         + w5 · PriorityWeight(j)
```

Where:
- **UrgencyFactor** = 1 / slack time remaining (Due Date  Now  Remaining Process Time), mined from historical routing to estimate remaining process time per job type.
- **CriticalRatio** = (Due Date  Now) / (Remaining Work Content) — classic but now populated with *mined, actual* (not planned) processing time distributions per operation type/operator.
- **SetupPenalty** = looked up directly from the mined **setup-time matrix** (Section 1.2) — this is the key innovation: the dispatch rule becomes setup-aware by consulting empirical changeover data, effectively a greedy, myopic version of the sequencing optimization in Strategy 3.
- **DownstreamCongestionFactor** = current/predicted queue length at the *next* station in this job's routing (requires real-time queue-length feed, validated against the WIP-time-series reconstruction methodology from Section 1) — this prevents starving/overloading downstream and reduces bullwhip.
- **PriorityWeight** = nonlinear boost for High/Urgent jobs calibrated so the priority-inversion rate (measured in 2.2) approaches zero in simulation.

**Weight calibration**: Use historical logs to *back-test* candidate weight vectors — replay historical arrival streams through a simulated dispatcher using various weights and select weights that minimize a cost function (tardiness + WIP holding cost + setup cost) on held-out historical periods, essentially a form of offline policy optimization / imitation-learning-lite using the event log as ground truth for demand and duration distributions.

**Addresses**: priority inversions, avoidable setup inflation, downstream starvation, bullwhip amplitude.
**Expected impact**: Reduced tardiness rate and P90 tardiness (fewer priority inversions), reduced setup hours (setup-aware dispatch), smoother WIP (congestion-aware dispatch), modest utilization improvement from reduced non-value-add setup time.

---

### Strategy 2: Predictive, Distribution-Aware Scheduling

**Core logic:** Move from deterministic/planned-time scheduling to a **stochastic schedule generation** approach:

1. **Duration modeling**: For each (Activity, Machine, Operator, Job-family) combination, fit empirical distributions (or parametric — lognormal/gamma typically fit processing times well) from Actual Duration data mined from the log, rather than using single-point Planned Duration. Segment by operator (skill effects visible in logs) and by job complexity attributes.
2. **Predictive completion time**: Use these distributions in a rolling-horizon simulation (or analytically via convolution/Monte Carlo) to generate a **probabilistic completion time forecast** for each in-progress and queued job — giving Sales/Planning a due-date **confidence interval** ("85% likely to complete by...") instead of a single deterministic promise, directly addressing the "unpredictable lead times" pain point.
3. **Proactive bottleneck/delay prediction**: Continuously re-simulate the shop state (current WIP snapshot + these distributions) several hours/days ahead to flag jobs at high risk of tardiness *before* they're actually late, triggering early intervention (expediting, overtime, re-sequencing) — analogous to predictive process monitoring in the PM literature.
4. **Predictive maintenance integration**: If breakdown events show precursor signatures (e.g., elevated Actual vs Planned duration variance on a machine in the weeks before a breakdown — detectable via mining trend lines in the duration data per resource over time), incorporate a **rising breakdown-risk score** into the schedule generator to preemptively reduce load/reschedule non-critical jobs off at-risk machines, or schedule maintenance windows during naturally low-WIP periods (also identifiable from the WIP time series).

**Addresses**: unpredictable lead times, reactive (rather than proactive) disruption handling, poor duration estimation propagating into schedule infeasibility.
**Expected impact**: Improved due-date reliability perception even before tardiness itself improves (confidence intervals), earlier interventions reduce realized tardiness magnitude, fewer surprise breakdowns disrupting the schedule (or better-absorbed when they occur).

---

### Strategy 3: Setup-Time-Optimized Sequencing / Intelligent Batching

**Core logic:** At identified bottleneck/high-setup resources, don't dispatch strictly job-by-job on urgency alone — periodically solve a **constrained sequencing sub-problem** over the current queue:

- Formulate as a **Sequence-Dependent Setup Time TSP/scheduling problem** (minimize total setup time subject to due-date/priority constraints as hard or soft constraints) using the mined setup-time matrix as the cost matrix.
- Solve via lightweight heuristics suitable for real-time re-optimization (nearest-neighbor with due-date-feasibility filtering, or a metaheuristic like a Genetic Algorithm/Tabu Search run on a rolling window of the next N queued jobs at that resource, re-triggered whenever the queue changes materially) — full optimal TSP not needed given problem size and time constraints; near-optimal heuristics informed by real setup data still capture most of the savings identified in the gap analysis in 2.3.
- **Attribute-based batching**: Using the clustering from 1.2 (job attribute transitions that drive high setup cost, e.g., material family changes), group same-family jobs into micro-batches at the bottleneck resource wherever due-date slack allows, converting several small setups into fewer larger ones, but capped by a **priority override**: no urgent job waits behind a batch purely for setup convenience beyond its slack tolerance — this constraint is what differentiates this from naive batch-and-queue strategies that reintroduce tardiness risk.
- **Setup-aware release timing**: Feed insight back upstream — release/sequence decisions at *upstream* stations can be informed by anticipated downstream setup savings (e.g., releasing jobs of the same family together when slack permits) — a form of coordinated, look-ahead scheduling rather than isolated per-station decisions, directly counteracting the "poor coordination between work centers" root cause.

**Addresses**: excess setup time, bottleneck effective-capacity loss (since reducing setup time is equivalent to adding capacity at a bottleneck), some tardiness (bottleneck throughput increases).
**Expected impact**: Directly recoverable setup-hours (quantified gap from 2.3, e.g., the 34% excess) translating into effective capacity gain at the bottleneck, which cascades into reduced queue times shop-wide and improved on-time delivery, without added machine investment.

## 5. Simulation, Evaluation, and Continuous Improvement

### 5.1 Discrete-Event Simulation (DES) Design

**Model parameterization directly from mined data** (this is the critical link — the simulation must reflect *actual* observed behavior, not idealized planning assumptions):
- **Arrival process**: mined inter-arrival time distribution of new jobs (Job Released events) per job family/priority mix.
- **Routing**: empirical routing-variant probabilities from the process model in Section 1.1 (not just the "designed" routing, but the actual observed variants including any rework loops).
- **Processing/setup times**: fitted distributions per (Activity, Machine, Operator) from Section 1.2/4.2, not single-point planned estimates.
- **Breakdowns**: mined MTBF/MTTR distributions per machine from Breakdown Start/End events.
- **Priority changes/hot jobs**: mined frequency and timing distribution of Priority Change events, injected stochastically into the simulation.

**Test scenarios:**
1. **Baseline replay**: validate the simulation by replaying historical arrival streams under the *current* dispatching logic and confirming simulated KPIs match historically observed KPIs within acceptable error — a calibration/validation step essential before trusting the simulator for "what-if" comparisons.
2. **Strategy comparison** (each of the three strategies vs. baseline) under identical stochastic input streams (common random numbers technique for fair variance-controlled comparison).
3. **Stress scenarios**:
   - **High-load**: scale arrival rate up (e.g., +20%, +40%) to find the load level at which each strategy's tardiness/WIP degrades unacceptably — establishing effective capacity headroom per strategy.
   - **High-disruption**: increase breakdown frequency/duration and hot-job injection rate to test resilience and recovery time of each strategy.
   - **Bottleneck-shift scenarios**: perturb the job mix to see if a different resource becomes the bottleneck, and verify strategies are not overfit to the currently-identified bottleneck (important since Strategy 1's downstream-congestion factor and Strategy 3's batching should generalize).
4. **Sensitivity analysis** on weight parameters (Strategy 1) and batching thresholds (Strategy 3) to find robust operating settings, not just point optima that might overfit historical data.

**Output**: Full KPI distribution comparison (not just means) — tardiness rate, P90 tardiness, WIP levels/variance, utilization, effective bottleneck capacity gain, setup-hours recovered — across all strategies and scenarios, supporting a data-backed go/no-go and strategy-selection decision, potentially combining elements (e.g., Strategy 1's dispatching + Strategy 3's setup optimization) since they are not mutually exclusive.

### 5.2 Continuous Monitoring & Adaptation Framework

Deploy an **online process-mining monitoring layer** operating on the live MES stream (not just periodic offline analysis):

- **Real-time KPI dashboards**: rolling-window tardiness rate, WIP-per-station, utilization, setup-hours, refreshed continuously, with control-chart-style thresholds (e.g., statistical process control limits derived from historical KPI variance) to flag **drift** — e.g., queue time at a station trending outside its historical control band signals either demand mix shift or a new inefficiency.
- **Automatic conformance checking against the "designed" scheduling policy**: continuously compare actual dispatch decisions/sequences to what the deployed rule *should* have chosen given the state at decision time — divergence indicates either a bug, an override, or a scenario the rule wasn't designed for.
- **Periodic re-mining of setup-time matrix and duration distributions**: schedule quarterly (or trigger-based, e.g., after new tooling/material introduction) re-estimation, since a static setup-time matrix will drift as product mix evolves — feed updated matrices automatically into Strategy 1/3 logic.
- **Concept drift detection on duration distributions**: statistical tests (e.g., Kolmogorov-Smirnov) comparing rolling recent duration samples per (Activity, Machine) against the baseline distribution used in the simulation model; significant drift triggers model re-calibration and re-validation via simulation before adjusting live weights.
- **Feedback loop governance**: establish a cadence (e.g., monthly) where diagnosed pathologies (Section 2 methodology, re-run on latest data) are reviewed against current strategy performance, closing the loop between live process mining and scheduling-logic refinement — turning this from a one-time project into an ongoing analytics-driven operations capability.

---

**Summary of the analytical chain**: Event Log  Reconstructed Process/Resource Models  Quantified KPIs & Distributions  Diagnosed Pathologies (bottleneck, priority inversion, setup waste, starvation, bullwhip)  Root-Cause Attribution (capacity vs. logic vs. variability)  Three Complementary Data-Driven Strategies (dispatching, predictive, setup optimization)  Simulation-Validated Selection  Continuously Monitored, Self-Correcting Deployment. This closes the loop from raw MES data to a living, adaptive scheduling system rather than a one-off fix.
