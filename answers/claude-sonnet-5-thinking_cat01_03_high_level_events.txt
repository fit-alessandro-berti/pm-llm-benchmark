# High-Level Process Step Aggregation

## Analysis Approach

I examined the event sequences for both cases (A1, B2) and found they follow an identical pattern of 12 low-level events. I grouped events based on three criteria:
1. **Functional cohesion** – events that contribute to the same physical/logical outcome
2. **Resource continuity** – events performed by the same resource or resource type (e.g., Operator A, Heating Units)
3. **Temporal proximity** – events clustered tightly in time with natural gaps indicating phase transitions

This produces **4 high-level process steps**, with a clear time gap (~40 sec) between material prep and welding, and tight sub-clusters within each phase.

---

## Proposed High-Level Activities

### **1. Material Preparation**
**Low-level events grouped:**
- Retrieve raw metal sheet
- Scan barcode
- Place metal sheet on table
- Align metal sheet
- Preheat metal sheet

**Rationale:**
These five events all occur within the first ~15-20 seconds, and collectively serve one purpose: *getting the raw material identified, positioned, and thermally conditioned for the next stage*. Even though three different resources are involved (Operator A, Robot Arm #2, Heating Unit #1), they act sequentially on the **same physical object** (the metal sheet) without any intervening quality check or tool change — a natural "handoff chain" within a single preparation phase. The barcode scan is a traceability/tracking action tied to material identification, not a separate step.

**Proposed Name:** `Material Preparation`
**Key Resources:** Operator A, Robot Arm #2, Heating Unit #1
**Typical Duration:** ~15-20 seconds

---

### **2. Welding / Assembly**
**Low-level events grouped:**
- Pick up welding tool
- Weld corner A
- Weld corner B

**Rationale:**
This cluster starts with a tool acquisition event immediately followed by two weld actions performed by the **same resource** (Operator B). This is the core value-adding transformation step — physically joining/assembling the component. Grouping tool pickup with the weld actions reflects the "prepare-tool  execute-task" pattern common in assembly steps. The gap before this cluster (~40 sec) suggests a queue/wait before the operator engages, marking a clear phase boundary.

**Proposed Name:** `Welding / Assembly`
**Key Resource:** Operator B
**Typical Duration:** ~15 seconds

---

### **3. Quality Inspection (Weld)**
**Low-level events grouped:**
- Measure weld integrity

**Rationale:**
Although a single event here, this is functionally distinct from assembly — it's an automated verification step performed by a **sensor**, not a human/robot actor, immediately following the weld to confirm output quality before proceeding to coating. I keep it separate rather than merging into Assembly or Coating because it represents a **decision/checkpoint activity** (could branch to rework in a fuller log) rather than a value-adding transformation.

**Proposed Name:** `Weld Quality Check`
**Key Resource:** Quality Sensor #1
**Typical Duration:** ~5-10 seconds

*(Note: In the full log, if rework/failure branches appear after this event, this step should remain isolated as a decision gate.)*

---

### **4. Surface Finishing & Final Inspection**
**Low-level events grouped:**
- Apply protective coating
- Dry coating
- Visual check

**Rationale:**
These three events represent the **finishing phase** of the product: applying a protective layer, curing/drying it, and performing a final human visual verification. They are tightly clustered in time (~15-30 sec), involve dedicated finishing resources (Coating Unit, Heating Unit #2), and culminate in a pass/fail check — mirroring a natural "treat  cure  verify" finishing pattern distinct from the earlier weld-quality checkpoint.

**Proposed Name:** `Surface Finishing & Final Inspection`
**Key Resources:** Coating Unit #3, Heating Unit #2, Operator C
**Typical Duration:** ~20-35 seconds

## Notes on Scalability

- If the full log contains **rework loops** (e.g., failed integrity scores triggering re-welding, or failed visual checks triggering recoating), the **Weld Quality Check** and **Visual Check** events should remain as separate decision-gate nodes rather than being absorbed into neighboring steps — this preserves visibility into process branching/loops in process mining models.
- If different PartIDs (M-045, M-046, ...) show variation in step durations or resource assignments, this aggregation schema should still hold, since grouping is based on **activity semantics and sequence position**, not case-specific attribute values.
- This 4-step model (**Prep  Assembly  Weld QC  Finishing/Final QC**) likely represents a **repeating subprocess per unit**; if the log includes batch-level or shift-level events, an additional top-level layer (e.g., "Batch Processing") could wrap multiple case instances.
