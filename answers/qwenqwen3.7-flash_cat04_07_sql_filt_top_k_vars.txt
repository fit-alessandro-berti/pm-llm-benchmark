Here is a complete, production-ready DuckDB SQL query that fulfills all four requirements. It uses Common Table Expressions (CTEs) to logically separate each step while maintaining high performance through DuckDB's query optimizer.

```sql
WITH CaseVariants AS (
    -- Step 1: Extract the ordered activity sequence per case
    SELECT 
        case_id,
        string_agg(activity, '->' ORDER BY timestamp) AS variant_sequence
    FROM event_log
    GROUP BY case_id
),
VariantFrequencies AS (
    -- Step 2 & 3: Count cases per variant sequence
    SELECT 
        variant_sequence,
        COUNT(case_id) AS variant_count
    FROM CaseVariants
    GROUP BY variant_sequence
),
TopKVariants AS (
    -- Step 3: Determine the top K variants by frequency
    SELECT variant_sequence
    FROM VariantFrequencies
    ORDER BY variant_count DESC
    LIMIT :k  --  Replace :k with your desired integer (e.g., 5, 10, 100)
),
TargetCases AS (
    -- Map the top K variants back to their corresponding case_ids
    SELECT DISTINCT cv.case_id
    FROM CaseVariants cv
    INNER JOIN TopKVariants tkv
      ON cv.variant_sequence = tkv.variant_sequence
)
-- Step 4: Return all original events belonging only to these target cases
SELECT 
    e.case_id, 
    e.activity, 
    e.timestamp
FROM event_log e
WHERE e.case_id IN (SELECT case_id FROM TargetCases)
ORDER BY e.case_id, e.timestamp;
```

###  How It Works (Mapping to Your Requirements)

| Requirement | Implementation in Query |
|-------------|-------------------------|
| **1. Ordered sequence per case** | `string_agg(activity, '->' ORDER BY timestamp)` builds the exact execution path for each `case_id`, respecting temporal order. |
| **2. Group & count variants** | `VariantFrequencies` groups by the generated sequence and uses `COUNT(case_id)` to tally how many cases follow that exact path. |
| **3. Top K by frequency** | `TopKVariants` sorts by `variant_count DESC` and applies `LIMIT :k` to isolate the most frequent paths. |
| **4. Filter & return events** | `TargetCases` extracts the `case_id`s of the top K variants. The final `SELECT` joins back to `event_log` using an `IN` clause, returning only relevant events. |

###  Usage Notes & Best Practices
1. **Parameter Substitution**: Replace `:k` with your actual integer (e.g., `LIMIT 10`). In programmatic environments (Python, Java, etc.), bind this as a standard query parameter.
2. **Delimiter Choice**: `'->'` is used as a separator to prevent sequence collisions (e.g., avoiding `A,B` being misread as `AB`). Choose a delimiter that cannot appear in your `activity` names.
3. **Tie Handling**: If multiple variants share the exact frequency at the `K`-th rank, `LIMIT :k` will arbitrarily pick some. If you want **all** tied variants included, replace `LIMIT :k` with:
   ```sql
   QUALIFY RANK() OVER (ORDER BY variant_count DESC) <= :k
   ```
   (DuckDB's `QUALIFY` clause filters after window functions.)
4. **Performance**: For very large logs (>10M rows), consider indexing `(case_id, timestamp)` on `event_log` to accelerate the initial `GROUP BY` and final `JOIN`. DuckDB's columnar engine typically handles this natively without indexes, but it helps for repeated executions.
