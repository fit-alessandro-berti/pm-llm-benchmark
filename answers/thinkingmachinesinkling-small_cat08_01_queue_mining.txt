## 1. Queue Identification and Characterization

### 1.1 Defining and Calculating Waiting Time (Queue Time)
In this event log, each patient visit (Case ID / Visit ID) is a sequence of completed activities. Because each activity carries both a **START** and a **COMPLETE** timestamp, we can distinguish **service time** (the time the patient is actively being served) from **waiting time** (the time they are idle in the system).

For any consecutive pair of activities in a case’s actual execution path:
- **Service Time (Activity A)** = `COMPLETE(A)`  `START(A)`
- **Inter-Activity Waiting Time (Transition T)** = `START(B)`  `COMPLETE(A)`  
  where Activity B immediately follows A in the case’s observed sequence.

If the clinic also tracks a “Check-in/Arrival” event (or if the first timestamp is Registration START), we can compute an initial queue time: `START(Registration)`  `Arrival` (if arrival is recorded separately).

**What constitutes “waiting time”?** It is the non-value-added idle interval for the patient between the completion of one care step and the commencement of the next, plus any queue time before the first service step. It does *not* include clinical interaction time.

**Calculation Methodology:**
1. **Sequence Reconstruction:** For each Case ID, sort events chronologically by START/COMPLETE. Reconstruct the actual process path (discover the “as-is” flow).
2. **Interval Derivation:** For each adjacent pair in the reconstructed path, compute the gap. Aggregate by transition type (e.g., Registration  Nurse Assessment, Nurse Assessment  Doctor Consultation (Cardio), Doctor  ECG, ECG  Check-out).
3. **Queue Mining Metrics:** For each transition *t*, compute:
   - Average Waiting Time: `_t`
   - Median Waiting Time: `m_t`
   - Maximum / 90th / 95th Percentile: `max_t`, `P90_t`
   - Queue Frequency: `n_t` (count of cases making that transition)
   - Proportion of Excessive Waits: `% of cases where gap > clinical threshold` (e.g., >15 min for registration, >20 min for specialist consultation).

### 1.2 Key Characterization Metrics
To characterize the queue ecosystem, we calculate:
- **Per-Transition Statistics:** Mean/median/p90 wait and frequency (as above).
- **Visit-Length Decomposition:** For each case, `Total Visit Time` = Sum(Service Times) + Sum(Waiting Times). This reveals whether delays are due to slow service or long queues.
- **Waiting-Time-to-Service-Time Ratio:** `W/S` per transition. A high ratio (e.g., >2:1) indicates that wait dominates value-added time.
- **Queue Buildup Index (Approximate):** Using Little’s Law concept, if we calculate arrival rates per hour (``) and average service rates (``), estimated average queue length  ` × W_t`. This helps identify physical congestion risks (e.g., waiting room overflow).

### 1.3 Identifying Critical Queues
Not every long wait is critical. A priority matrix should evaluate each transition on:
1. **Magnitude:** High average/p90 waiting time.
2. **Frequency:** High case volume (`n_t`).
3. **Clinical Urgency Impact:** Queues preceding high-stakes steps (e.g., Doctor Consultation for Urgent patients, Diagnostic Tests needed for treatment decisions) are more damaging.
4. **Downstream Cascade:** A delay at Step 2 delays Step 3, 4, etc. We measure **Path Criticality**—if the transition lies on the critical path for 80%+ of cases, it receives priority.

**Justification:** A queue with moderate wait but very high frequency (e.g., Registration  Nurse Assessment for all 200 daily patients) creates more aggregate dissatisfaction than a rare, long wait. Conversely, a long wait before an Urgent patient’s specialist consultation is a safety/quality issue. Thus, we rank by a **Critical Queue Index** such as:  
`Priority = (P90 Wait × Daily Frequency) / (Resource Flexibility)`  
where resource flexibility is low for fixed specialists.

- **Arrival Patterns:** Peak morning arrivals that exceed initial resource capacity (e.g., 3 clerks vs. 15 patients in 15 minutes).
