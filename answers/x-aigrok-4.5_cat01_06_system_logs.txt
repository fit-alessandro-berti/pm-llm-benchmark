**Explanation of Transformation Logic**

**Case Identification:**  
Events were grouped into 5 cases based on the logical work unit / primary artifact being handled (following the guidance to treat cold document editing, email handling, or PDF review as natural case boundaries):
- **DOC_001**: All interactions with `Document1.docx` (initial drafting session interrupted by email/PDF/budget, then later resume to insert budget reference and close). This captures interleaved multi-tasking as a single process instance with concurrency.
- **EMAIL_001**: The full handling of the “Annual Meeting” email (open  read  reply  send), which forms a clean, self-contained sub-process.
- **PDF_001**: Interaction with `Report_Draft.pdf` (open  review  annotate).
- **BUDGET_001**: Work on `Budget_2024.xlsx` (open  edit values  save).
- **QR_001**: Interaction with `Quarterly_Report.docx` (initial focus, later resume to draft executive summary + save/close). The early focus is retained as the “Open” event; the later session is “Resume”.

This produces concurrent yet analyst-friendly cases instead of one giant chronological bag or every window switch as a new case. Temporal proximity + focus changes + shared document identity determine membership. The result still reflects the user’s real multi-tasking flow (Draft  Email interruption  PDF review  Budget update  Return to draft  Final report edit).

**Activity Naming:**  
Raw low-level system events (FOCUS, TYPING, SCROLL, CLICK, SAVE, SWITCH, HIGHLIGHT, CLOSE) were lifted to standardized, process-oriented labels that remain comparable across cases:
- Document/Spreadsheet activities  `Open Document` / `Open Spreadsheet`, `Edit Content` / `Edit Spreadsheet`, `Save …`, `Close Document`, `Resume Document`.
- Email activities  `Open Email`, `Read Email`, `Compose Reply`, `Write Reply`, `Send Email` (+ the context SWITCH).
- PDF activities  `Open PDF`, `Review PDF`, `Annotate PDF`.

Consecutive similar micro-events of the same type on the same window (two successive TYPING actions, SCROLL followed immediately by related actions) were merged into a single higher-level activity; the earliest timestamp of the group is used and the content of the actions is preserved in `Additional_Info`. This yields clean traces suitable for discovery algorithms, conformance checking, or performance analysis while still retaining original timestamps and useful context attributes.

**Additional Attributes:**  
`Application`, `Window`, and free-text `Additional_Info` (email subject, typed snippets, highlighted text) are retained so that later filtering, dashboards, or multi-perspective process mining remain possible. The log is ready for import into standard tools (Disco, ProM, Celonis, pm4py, etc.) as a CSV/XES event log with the classic Case-Activity-Timestamp core.
