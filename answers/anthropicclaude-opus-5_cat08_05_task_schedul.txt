# Data-Driven Scheduling Transformation for Precision Parts Inc.
## A Process-Mining-Led Program for a High-Mix / Low-Volume Job Shop with Sequence-Dependent Setups

---

## 0. Data Foundation: Turning the MES Log into a Schedulable Object

Before any analysis, the raw log must be engineered into three *complementary* event log views, because a job shop scheduling problem is not observable from a single case notion.

| Log view | Case ID | Purpose |
|---|---|---|
| **Job view** | JOB-ID | Routing discovery, flow time, tardiness, WIP, variant analysis |
| **Machine (resource) view** | Machine ID | Reconstructing the *realized dispatch sequence*, setup matrices, utilization decomposition, idle/starvation analysis |
| **Task-instance view** | (JOB, Activity, Machine) | Duration modelling, queue mining, plan-vs-actual regression |
| **Operator view** | Operator ID | Skill/speed effects, shift constraints, handover networks |

**Required derived attributes per task instance** (from lifecycle events `Queue Entry  Setup Start  Setup End  Task Start  Task End`):

- `t_queue_in`, `t_setup_start`, `t_setup_end`, `t_proc_start`, `t_proc_end`
- `W = t_setup_start  t_queue_in` (waiting), `S = t_setup_end  t_setup_start` (setup), `P = t_proc_end  t_proc_start` (processing), `Sojourn = W + S + P`
- `pred_job` = last job whose `Task End` occurred on that machine before this setup (from the machine view)  enables the **(from-job, to-job)** setup pair
- Job attributes: material, alloy grade, part family, geometry class, tolerance band, fixture/tooling ID, program ID, weight/size, priority, due date, promised vs. actual release
- Calendar attributes: shift, day of week, machine state (up/down), operator on duty

**Data quality gates** (non-negotiable, and typically where 3–6 weeks of the project go): missing `Setup Start` events (hidden setups appearing as inflated queue time), events recorded at shift boundaries in batches (timestamp granularity), overlapping task intervals on one machine (impossible in a single-capacity resource  indicates unlogged interruptions), and jobs that "teleport" between work centers without a queue-entry event. Each anomaly is quantified and either repaired (interpolation, interval reconstruction) or flagged and excluded, with the exclusion rate reported so that downstream conclusions carry known confidence.

## 1. Analyzing Historical Scheduling Performance and Dynamics

### 1.1 Reconstructing the Actual Flow and the Actual Dispatch Sequence

**Routing discovery (job view).** Because routings are unique per order, a single monolithic process model is meaningless. Instead:

- **Directly-Follows Graph (DFG) at the work-center level** with frequency and performance annotations  reveals the *aggregate material flow network*, dominant arcs, and re-entrant flows (e.g., Milling  Grinding  Milling).
- **Trace clustering** (on activity-sequence edit distance + job attributes) to reduce hundreds of routings to 8–15 **routing archetypes**. Each archetype is then mined with the **Inductive Miner (infrequent)** to yield an interpretable model, and archetypes become the routing families used later in simulation and scheduling.
- **Re-entrancy and rework detection**: loops involving Quality Inspection  upstream activity quantify hidden capacity loss (rework consumes bottleneck time that scheduling never planned for).

**Realized dispatch sequence (machine view).** This is the crucial and often-skipped step: for each machine, sort task instances by `t_setup_start` to obtain the **actual sequence** $\sigma_m = \langle j_1, j_2, \ldots \rangle$. From this we reconstruct a full **historical Gantt chart** (a "schedule replay"), which is the object we can compare against counterfactual schedules. We also derive, at every dispatch decision point, the **queue snapshot** — the set of jobs physically waiting at that machine at the moment of selection. This queue snapshot is the single most valuable derived artifact: it lets us evaluate *what the shop chose versus what it could have chosen*.

### 1.2 Flow Time, Lead Time, Makespan

- **Flow time** $F_j = C_j - R_j$ (completion minus release); **lead time** $L_j = C_j - O_j$ (from order acceptance, includes pre-release dwell).
- Report full **distributions**, not means: median, p85, p95, and coefficient of variation, segmented by routing archetype, priority class, and load regime. Predictability is a distributional property; a shop with CV(F) = 0.8 cannot quote reliable dates regardless of its average.
- **Flow efficiency** $\eta_j = \sum(S+P)/F_j$. In job shops this is typically 5–15%; the number frames the entire business case, because 85–95% of lead time is queue and is therefore *scheduling-addressable*, not capacity-addressable.
- **Makespan** is measured per rolling window (e.g., weekly order batch) and per bottleneck to support "campaign" evaluation.
- **WIP** via time-stamped inventory counting and cross-checked with **Little's Law** ($\overline{WIP} = \lambda \cdot \overline{F}$) — a systematic mismatch indicates log incompleteness or unrecorded scrap.
- **Dotted chart** over the year to expose seasonality, load waves, and release batching (e.g., all jobs released Monday morning — an immediate finding).

### 1.3 Queue-Time (Waiting) Analysis

- Per machine and work center: waiting-time distribution, and **queue length time series** $Q_m(t)$ derived by replaying queue-entry/dispatch events.
- **Queue mining**: estimate for each arriving job the *queue-time predictor* and, more importantly, compute **overtaking counts** — how many jobs arrived after job *j* at machine *m* yet were processed before it. Overtaking is the direct fingerprint of dispatching policy; a distribution of overtaking counts with a long right tail proves priority inversion, not congestion.
- **Performance spectrum** (segment-level visualization of every hand-off between two consecutive activities over time): visually separates FIFO segments (parallel lines), LIFO segments (crossing lines), and batching (fan-in/fan-out). This single visualization typically reveals that "we use FCFS/EDD" is false in practice.
- Decomposition of waiting into: *waiting for machine busy*, *waiting for operator*, *waiting for machine down*, *waiting despite machine idle* (a pure scheduling/visibility failure), *waiting for tooling/fixture*.

### 1.4 Resource Utilization Decomposition

For each machine, partition calendar time into: **productive processing / setup / idle-with-queue (starved of decision) / idle-empty (starved of work) / down (breakdown) / blocked / off-shift / operator-unavailable**. Present as a stacked time-band chart per machine per week. Then compute:

- $U^{prod}_m$, $U^{setup}_m$, and the critical ratio $U^{setup}_m/(U^{prod}_m+U^{setup}_m)$ — the **setup burden**. Bottlenecks with 25–40% setup burden are where Strategy 3 pays.
- **Effective capacity** = calendar  off-shift  down  setup, giving the true available processing capacity used for load/capacity checks.
- Operator dimension: **handover-of-work social network** and **resource–activity matrix** to identify skill silos (only OP-105 and OP-112 can run CUT-01 setups  hidden capacity constraint), plus **speed factors** (operator effect on P and S estimated via mixed-effects model).
- **Shifting bottleneck detection** (Roser-style *active period* method): a machine is momentarily the bottleneck when it has the longest uninterrupted non-starved active period. Aggregating over the year gives **bottleneck share per machine per month** and reveals *bottleneck migration* — the reason static rules fail.

### 1.5 Quantifying Sequence-Dependent Setup Times

This is the analytical core. From the machine view we have, for each setup instance, the tuple $(m, \text{pred\_job } i, \text{job } j, S_{ijm}, \text{operator}, \text{shift})$.

1. **Empirical setup matrix**: aggregate $S$ by (machine, predecessor part family, successor part family)  mean, median, p80, count. Sparsity is the challenge (high-mix shop  most pairs unobserved).
2. **Attribute-based generalization (the fix for sparsity)**: model setup as a function of *attribute changes* rather than job identities:
$$\hat{S}_{ijm} = f\big(\Delta\text{material}, \Delta\text{fixture}, \Delta\text{tooling set}, \Delta\text{program}, \Delta\text{tolerance}, \Delta\text{size}, m, \text{operator}, \text{shift}\big)$$
   Fit with (a) an interpretable **linear/mixed-effects model** to obtain additive setup drivers (e.g., "fixture change = +38 min; material-class change = +12 min; same program = 25 min"), and (b) a **gradient-boosted / quantile-regression model** for predictive accuracy including interactions. Report both: the additive model drives operational understanding and family definition; the ML model feeds the dispatching rule.
3. **Validate the sequence dependence itself**: ANOVA / variance decomposition showing what fraction of setup variance is explained by the *predecessor* (sequence-dependent component) vs. the job alone (sequence-independent) vs. operator vs. noise. If the predecessor explains <10%, Strategy 3 is not worth pursuing — this test must be run, not assumed.
4. **Setup waste quantification (counterfactual lower bound)**: for each machine and each historical time window, take the realized set of jobs and compute the minimum total setup via an **asymmetric TSP / sequencing relaxation** on $\hat{S}$. The gap
$$\text{Setup Waste}_m = \sum_{\text{realized}} S - \text{TSP-LB}(\hat S)$$
   expressed in hours/month on the bottleneck, is a hard, defensible number — typically 8–20% of bottleneck capacity in shops like this. It converts directly into recoverable throughput.
5. **Hidden setups**: compare `t_proc_start  t_setup_end` and unexplained gaps; detect setups that were performed but not logged (they inflate "queue" and corrupt duration models).

### 1.6 Schedule Adherence and Tardiness

- Lateness $L_j = C_j - d_j$; tardiness $T_j = \max(0, L_j)$; **%tardy**; **conditional mean tardiness** $E[T|T>0]$; **weighted tardiness** $\sum w_j T_j$ with $w_j$ from priority class and penalty terms; **earliness** (a WIP and cash cost, often ignored).
- **Due-date reliability curve**: cumulative distribution of $L_j$  supports date-quoting policy (e.g., "quoting at p90 of predicted flow time yields 90% OTD").
- **Slack erosion trajectories**: for each job, plot slack $d_j - t - \text{RPT}_j(t)$ (remaining processing time) over its life. Clustering these trajectories reveals *where* jobs lose their due date — typically a single queue (the bottleneck) or a specific hand-off. This localizes tardiness causation far better than aggregate statistics.
- **Plan-vs-actual conformance**: treat the intended dispatching rule as a normative model and measure **priority inversion rate** — the share of dispatch decisions where a strictly more urgent job (by the shop's own stated rule) was in the queue but not selected. Also **Spearman rank correlation** between due-date order and processing order per machine (a compact "EDD compliance" score per machine, per shift, per operator).

### 1.7 Impact of Disruptions

- **Breakdowns**: extract per machine MTBF/MTTR distributions, dependence on utilization/season, and repair-resource waiting. Then run **event-window difference analysis**: compare KPIs (queue growth, tardiness of jobs in the machine's queue, WIP at downstream stations) in the 72 h after each breakdown versus matched control windows (same machine, same load level, no breakdown) — a difference-in-differences estimate of **breakdown cost in tardy-hours per incident**.
- **Hot jobs**: for each priority-change event, identify the **cascade set** — jobs that were subsequently overtaken — and compute the induced delay $\sum \Delta C$. This yields the *true cost of expediting*, typically 3–8 displaced jobs per hot job, and reveals whether expediting is self-inflicted (hot jobs created because a normal job was already late  a vicious cycle detectable as a feedback loop in the log).
- **Schedule nervousness**: count of re-sequencing changes per shift; correlate with tardiness. High nervousness with high tardiness indicates reactive thrash, not responsiveness.

## 2. Diagnosing Scheduling Pathologies

| # | Pathology | Process-mining evidence | Typical quantified finding |
|---|---|---|---|
| P1 | **Shifting bottleneck, unmanaged** | Active-period bottleneck detection over time; utilization decomposition; queue-length series | e.g., MILL-03 is bottleneck 62% of the time, GRIND-02 24%; bottleneck idles 11% of available time *with jobs waiting* due to operator/tooling gaps |
| P2 | **Bottleneck starvation and blocking** | Idle-empty periods on bottleneck coinciding with WIP piled upstream; performance spectrum showing burst arrivals | Bottleneck starved 6–9% of shift while 14 jobs wait two stations upstream  pure release/sequencing failure |
| P3 | **Priority inversion / poor urgency handling** | Overtaking distributions; priority-inversion rate; slack-erosion clusters; variant analysis late vs. on-time | 31% of dispatch decisions inverted priority; High-priority jobs wait *longer* than Medium at two work centers (FCFS dominance in practice) |
| P4 | **Setup-blind sequencing** | Setup matrix + TSP lower bound; realized-vs-optimal setup gap; observation that consecutive jobs rarely share fixture/material | 130 h/month avoidable setup on the two bottlenecks  9% capacity |
| P5 | **Over-batching (the opposite failure)** | Performance spectrum fan-in patterns; correlation between batch size and tardiness of small urgent jobs | Informal operator batching of same-material jobs saves setup but adds 2.4 days to urgent jobs — uncontrolled trade-off |
| P6 | **Push release / WIP bullwhip** | Release-rate vs. WIP correlation; variance amplification ratio $CV^2(\text{departures})/CV^2(\text{arrivals})$ per stage; autocorrelation of $Q_m(t)$ | WIP variance amplifies 1.8× from Cutting to Grinding; Monday release spikes propagate as 3-day queue waves |
| P7 | **Planned durations systematically biased** | Regression of actual on planned duration by machine/job family/operator | Actual/planned = 1.11 mean with CV 0.28; bias worst for new part families  schedules infeasible at birth |
| P8 | **Expediting feedback loop** | Hot-job cascade analysis; share of hot jobs that were already tardy before promotion | 47% of hot jobs are recovery actions for previously delayed jobs — the system generates its own disruptions |
| P9 | **Due-date setting disconnected from capacity** | Compare quoted allowance $d_j - O_j$ against contemporaneous predicted flow time distribution and shop load | 28% of orders are accepted with allowances below the p50 flow time at the prevailing load  tardy at acceptance |

**Variant analysis is the workhorse for P3/P9**: split the job population into on-time vs. tardy cohorts and compare (i) routing archetype, (ii) number of bottleneck visits, (iii) waiting time distribution per station, (iv) overtaking counts, (v) release-to-first-operation delay, (vi) load level at release, (vii) number of breakdowns encountered. A logistic / survival model on these features yields **attributable contribution to tardiness**, e.g.: bottleneck queue 41%, release timing 19%, setup burden 14%, breakdowns 12%, routing complexity 8%, other 6%. That decomposition is what determines where strategy effort is spent.

## 3. Root Cause Analysis of Scheduling Ineffectiveness

**Causal chain (from symptom to root):**

1. **Myopic, local, static rules.** FCFS/EDD optimize nothing beyond the local queue. EDD ignores remaining work (a job due in 2 days with 6 operations left is *not* less urgent than one due in 3 days with one operation left) and ignores setup entirely; FCFS ignores urgency. Neither sees downstream load, so upstream stations happily feed already-congested queues. Evidence: negative or zero correlation between a job's *slack per remaining operation* and its dispatch position.
2. **No lookahead / no global objective.** Decisions are made one job at a time with no evaluation of consequences, so the shop cannot trade a 30-minute setup saving against a 4-hour tardiness increase — because it never computes either.
3. **Absence of real-time visibility.** The MES records events but doesn't *serve* state. Operators cannot see downstream queue lengths, upcoming machine downtime, or a job's true criticality. Evidence: idle-with-queue periods, and dispatch choices explainable by *physical proximity* of the pallet rather than any job attribute (testable: correlation between selection and queue-entry recency = LIFO, i.e., "top of the stack").
4. **Unreliable input data for planning.** Planned durations biased and un-updated (P7); setup times not modelled at all as sequence-dependent (routing sheets carry a single fixed setup allowance). A scheduler fed wrong parameters produces a schedule that dies within hours, which destroys trust and reinforces informal local decision-making — a self-fulfilling loop.
5. **Ineffective sequence-dependent-setup handling.** Setup knowledge lives in operators' heads, applied opportunistically (P5) but without regard to due dates, and it stops at the machine boundary — nobody sequences *upstream* to deliver setup-friendly families *to* the bottleneck.
6. **No coordination mechanism between work centers.** No pull signal, no buffer targets, no workload control. Release is order-driven, not capacity-driven (P6).
7. **Reactive-only disruption handling.** Breakdowns trigger ad-hoc re-queuing; hot jobs trigger unconstrained pre-emption with no accounting of collateral damage (P8). No degraded-mode plan, no re-optimization, no protective buffering of the constraint.
8. **Organizational incentives.** Local efficiency measures (machine utilization, operator output) reward setup avoidance and running whatever is convenient — visible in the log as high utilization on non-bottlenecks and long campaigns of similar low-priority work.

### Separating "bad scheduling" from "insufficient capacity" and "inherent variability"

This is the most important analytical discipline in the engagement, and it is answered with three independent tests:

**Test A — Load vs. capacity (capacity question).** Per machine and per month compute offered load $\rho_m = \lambda_m E[S+P]/(\text{effective capacity})$ using mined durations, setups, breakdown losses, and shift calendars. If $\rho_m \ge 0.95$ persistently, no scheduling logic can fix it: the answer is capacity, outsourcing, shifts, or order acceptance. If $\rho_m \approx 0.75$–0.85 while queues are days long, the loss is variability/policy.

**Test B — Queueing benchmark (variability question).** Apply **Kingman's approximation**
$$E[W_m] \approx \left(\frac{C_a^2 + C_s^2}{2}\right)\left(\frac{\rho_m}{1-\rho_m}\right)E[S+P]$$
with $C_a^2, C_s^2$ measured from the log. This is the waiting time explained by *utilization + variability alone under a fair (FCFS) policy*. Then:
- **Actual  Kingman  policy/coordination loss** (e.g., bad sequencing, blocking, operator unavailability, batching-induced arrival bursts).
- **Kingman decomposition  variability loss**, further split into arrival variability (release policy — controllable) and service variability (setup dispersion, breakdowns, duration variance — partly controllable).
- Extra sub-test: measure $C_a^2$ at the bottleneck *inlet*. If it is much larger than at order release, the shop is manufacturing its own variability upstream — a scheduling problem, not a demand problem.

**Test C — Offline optimality gap (the decisive counterfactual).** Replay each historical week: take the exact job set, exact realized durations, exact breakdown windows, exact release times, and solve the resulting deterministic job-shop-with-setups problem (CP-SAT / MIP with time limit, or a strong metaheuristic) minimizing weighted tardiness. The gap between realized and optimal-with-hindsight is the **maximum scheduling-addressable improvement**; a second solve using only *information available at decision time* (stochastic/rolling horizon) gives the **realistically attainable share**. Typical outcome in such shops: hindsight-optimal reduces weighted tardiness 45–65%; information-constrained dynamic policies capture 25–40%. Everything else is capacity or variability — and this cleanly ends the internal "we just need another mill" argument, or confirms it with evidence.

## 4. Advanced Data-Driven Scheduling Strategies

### Strategy 1 — Dynamic, Multi-Factor, Setup-Aware Composite Dispatching (ATCS-DD++)

**Core logic.** Replace local rules with a single scoring function evaluated in real time over the actual queue at machine *m*, extending the **Apparent Tardiness Cost with Setups (ATCS)** rule with congestion and load-balancing terms. For each waiting job *j* with predecessor *i* currently on the machine:

$$
\pi_j = \underbrace{\frac{w_j}{\hat p_{jm}}}_{\text{weighted SPT}}\cdot
\underbrace{\exp\!\left(-\frac{\max(0,\;d_j - t - \widehat{RPT}_{j})}{k_1 \bar p}\right)}_{\text{slack urgency}}\cdot
\underbrace{\exp\!\left(-\frac{\hat S_{ijm}}{k_2 \bar S_m}\right)}_{\text{setup avoidance}}\cdot
\underbrace{\left(\frac{1}{1+\alpha\, \widetilde Q_{next(j)}}\right)}_{\text{downstream congestion}}\cdot
\underbrace{\beta_j}_{\text{constraint/bottleneck boost}}
$$

where $\hat p_{jm}$ = predicted processing time (§S2 model), $\widehat{RPT}_j$ = predicted *remaining* flow time including expected queues (not just processing), $\hat S_{ijm}$ = predicted sequence-dependent setup, $\widetilde Q_{next(j)}$ = normalized workload (in hours, not job count) at *j*'s next machine, $\beta_j > 1$ if *j*'s route still visits the current constraint (protect the constraint) or if *j* is starving a downstream bottleneck.

**Safeguards learned from the diagnosis:** (i) an **anti-starvation escalation**: any job whose slack falls below zero, or whose wait exceeds the p95 of historical waits at that station, gets an overriding lexicographic priority — this bounds the tail that destroys OTD; (ii) **setup avoidance is capped** so no job is deferred more than *N* consecutive decisions for setup reasons (prevents P5); (iii) if the machine is *not* the bottleneck and downstream is congested, the rule may deliberately idle rather than push WIP.

**How process mining informs it.** Every term is parameterized from the log, not from theory: $w_j$ from realized penalty/priority data; $\hat S$ from the §1.5 attribute model; $\bar S_m$, $\bar p$ from measured distributions; $\widehat{RPT}$ from the queue-mining/quantile model; $\alpha, k_1, k_2, \beta$ **tuned per machine via simulation-based optimization** (§5) — critically, $k_2$ should be large only on machines where §1.5 proved high sequence-dependence and §1.4 showed high setup burden, and $k_1$ tightens as measured due-date allowance tightens. Variant analysis (§2) sets initial weights: if bottleneck queue explains 41% of tardiness, $\beta$ and the downstream term dominate.

**Pathologies addressed:** P3 (priority inversion), P4 (setup blindness), P2/P6 (starvation, WIP waves), P1 (constraint protection).

**Expected impact:** the highest benefit-to-effort option; deployable as a ranked "pick list" on shop-floor terminals with no optimization engine. Realistic targets: weighted tardiness 20 to 35%, mean flow time 10 to 20%, bottleneck setup hours 5 to 12%, with modest WIP reduction. It remains myopic (single-decision lookahead), which is why Strategies 2 and 3 are needed.

### Strategy 2 — Predictive, Rolling-Horizon Stochastic Scheduling with Reliability-Aware Date Quoting

**Core logic.** A three-layer predictive-reactive architecture:

1. **Prediction layer.** Mine **conditional duration distributions** per (activity, machine, part family, operator, batch size) — fit lognormal/gamma or use **quantile gradient boosting** to produce $p_{50}, p_{80}, p_{95}$ per operation, plus a setup predictor (§1.5). Fit **breakdown hazard models** per machine (Weibull TTF with covariates: cumulative run hours since maintenance, load, spindle-hours, recent micro-stoppage frequency mined from the log)  time-varying availability. Fit a **remaining-flow-time (ETA) model** per in-process job: survival/quantile regression using current position, remaining route, live queue loads, priority mix, and shop congestion.
2. **Optimization layer.** Every shift (or on trigger), solve a **rolling-horizon** scheduling problem (CP-SAT / MIP for the bottleneck neighborhood, metaheuristic for full shop) minimizing $\sum w_j T_j + \gamma \cdot \text{setup} + \delta \cdot \text{instability}$, using **robust duration inputs** ($p_{70}$–$p_{80}$ rather than means — mining shows mean-based plans fail ~50% of the time by construction) and **planned maintenance windows / risk-adjusted availability** instead of assuming perpetual uptime. A **frozen window** (e.g., next 4–8 h) plus an explicit **stability penalty** $\delta$ prevents the nervousness diagnosed in §1.7. Time buffers are placed *in front of the constraint*, sized from the measured p85 of upstream arrival variability (a data-driven Drum-Buffer-Rope).
3. **Reactive layer.** Event-triggered re-optimization on: breakdown, hot job, duration overrun beyond p90, material shortage. Between triggers, Strategy 1's rule executes the schedule locally, so the shop is never blocked waiting for an optimizer.

**Proactive delay management and date quoting.** The ETA model produces a completion-time distribution per job; jobs whose $P(\text{late}) > \tau$ appear on an **at-risk radar** hours-to-days early, with a recommended intervention (overtime on a specific machine, resequencing, alternative routing, split lot). New orders are quoted at a chosen service level ($d_j = O_j + F^{-1}_{\text{predicted}}(0.90)$ *given current and forecast load*) — converting due dates from wishes into commitments and directly attacking P9 and the expediting loop P8.

**Pathologies addressed:** P7 (biased durations), P8 (reactive expediting), P9 (infeasible dates), P1 (bottleneck migration — the optimizer sees whichever machine binds), breakdown impact.

**Expected impact:** the largest structural gains — tardiness 35 to 55% (combined with S1/S3), lead-time predictability (p95/p50 ratio) improved 25–40%, quoted-date reliability to 90%+, and a measurable drop in hot-job creation rate. Cost: MES integration, master-data discipline, and planner trust-building (run in *shadow mode* first, comparing its recommendations against actual decisions and showing hindsight regret).

### Strategy 3 — Setup-Optimized Family Campaigns with Tardiness-Bounded Batching

**Core logic.** Explicitly manage the setup/tardiness trade-off instead of leaving it to operators.

1. **Family formation.** Cluster jobs into **setup families** using the *learned setup distance* $\hat S_{ijm}$ as the similarity metric (hierarchical clustering / spectral clustering on the setup matrix), validated by the additive driver model: families are defined by whatever actually drives setup (fixture group, material class, tooling kit, program family) — not by engineering intuition. Output: a **family taxonomy plus intra/inter-family setup times** per bottleneck machine.
2. **Cyclic campaign plan at bottlenecks.** From mined family mix and arrival rates, design a **rotation cycle** (analogous to the Economic Lot Scheduling / product-wheel logic): e.g., MILL-03 runs Family A  B  C  D with cycle length chosen so that the maximum wait for any family is compatible with the p10 of due-date allowance for that family. Cycle length is optimized by simulation: short cycles = low tardiness, high setup; long cycles = the reverse. The optimum is computed, not guessed.
3. **Tardiness-bounded dynamic batching.** Within a campaign, admit an additional same-family job only if $\hat S_{\text{saved}} \ge \theta \cdot \Delta\!\!\sum w_j T_j$ estimated from live slack of the deferred jobs — i.e., a job is added to a batch only when the setup saving dominates the marginal tardiness risk it creates. This formalizes the good instinct behind P5 while eliminating its harm. Hard caps: max campaign length, and immediate break for any job with negative slack.
4. **Upstream synchronization ("family-aware feeding").** Upstream stations sequence to *deliver* the family the bottleneck will need next — a pull signal derived from the campaign plan. This is where the DFG/flow analysis pays off: it identifies which upstream stations feed the constraint and with what lead time, so feeding can be timed.
5. **Setup reduction beyond sequencing.** The additive driver model ranks setup contributors; the top drivers become SMED/tooling projects (e.g., "fixture change = 38 min × 210 occurrences/yr = 133 h"  duplicate fixture business case). Also mine **operator setup-speed variance**: if the p20 operator is 40% faster than the p80 on the same setup type, standardize the method — a training intervention identified purely from the log.

**Pathologies addressed:** P4 (setup waste), P5 (uncontrolled batching), P1 (bottleneck capacity recovery), and indirectly P6 (steadier bottleneck output smooths downstream waves).

**Expected impact:** setup hours on bottlenecks 25 to 45%, equivalent to +5 to +10% effective bottleneck capacity — which, at $\rho \approx 0.9$, has a *nonlinear* effect on queues via the $\rho/(1-\rho)$ term (a 5-point utilization reduction can halve waiting time). This is the strategy that makes the capacity argument moot.

### Strategy 4 (enabling layer) — Workload-Controlled Order Release (CONWIP / Load-Based ORR)

None of the above works if the shop is flooded. Using mined bottleneck capacity and routing archetypes, implement **load-based release**: an order enters the floor only when the aggregate projected load it adds to each bottleneck over its planned horizon stays under a mined norm, and total WIP stays under a CONWIP cap set from the Little's Law analysis (cap chosen at the knee of the mined throughput-vs-WIP curve, i.e., the characteristic-curve point beyond which added WIP buys lead time and no throughput). **Directly targets P6 (bullwhip) and WIP**, cuts flow time 15–30% with *no* change in throughput, and — importantly — it is the cheapest and fastest-to-deploy intervention, so it should go first.

### Strategy 5 (frontier option) — Learned Dispatching Policy (Offline RL / Imitation + Simulation Fine-Tuning)

Where the composite rule's weights prove state-dependent, train a policy $\pi(\text{state}) \rightarrow \text{job}$ using the log-derived state–action–outcome triples: **behavioral cloning of the best-performing historical decisions** (identified by hindsight regret from Test C), then **policy-gradient / DQN fine-tuning inside the calibrated simulator** with reward $-(\sum w_j T_j + \gamma\,\text{setup} + \eta\,\text{WIP})$. State features: queue contents (attention over job embeddings), machine states, downstream loads, slack distribution, predicted setups. Deploy only with the Strategy-1 rule as a *guardrail/fallback* and with explainability (feature attribution per decision), since operators will not follow a black box. Realistic positioning: a phase-3 upside of a further 5–15% over the tuned composite rule, not a starting point.

## 5. Simulation, Evaluation, and Continuous Improvement

### 5.1 Building a Credible Digital Twin from the Log

| Model element | Mined parameterization |
|---|---|
| Job arrivals | Trace-driven replay of historical orders (primary) + fitted arrival process with mix/seasonality for stress tests |
| Routings | Routing archetypes with attribute-conditioned probabilities; rework loops with mined probabilities |
| Processing times | Conditional distributions per (activity, machine, family, operator); mixtures where bimodality observed |
| Setups | The $\hat S_{ijm}$ model (predictive mean + residual noise), preserving asymmetry |
| Breakdowns | Weibull TTF (covariate-dependent) + lognormal TTR, per machine; micro-stoppages separately |
| Resources | Machine calendars, shift patterns, operator skill matrix and availability, tooling/fixture pools |
| Disruptions | Hot-job arrival process with mined frequency and lead-time demands |
| Baseline policy | The *reconstructed actual* dispatching behavior (fitted from the machine view — e.g., a probabilistic mix of FCFS/EDD/LIFO/setup-avoidance per station), not the nominal policy |

**Validation protocol (mandatory before any conclusion):** replay the historical year and compare simulated vs. actual on flow-time distribution (Kolmogorov–Smirnov / Wasserstein distance), tardiness rate, WIP time series, utilization decomposition per machine (target within ±3–5 pp), setup hours, and queue-length percentiles. Add **face validation**: overlay simulated vs. actual Gantt charts with planners and operators. Document warm-up (Welch), replication count for desired CI width, and use **common random numbers + paired comparisons** so that policy differences aren't drowned in noise.

### 5.2 Experimental Design

Compare: **Baseline** | **S4 (release control) only** | **S1** | **S1+S3** | **S1+S3+S4** | **S2 full predictive-reactive** | **S5**, across scenarios:

1. **Nominal load** (historical mix and volume).
2. **High load** (+15%, +30% volume; also +30% with mix shifted toward bottleneck-heavy families) — tests whether gains survive as $\rho \to 1$.
3. **Disruption-intensive**: MTBF halved, MTTR doubled, hot-job rate doubled.
4. **Tight due dates**: allowance reduced 20% — tests robustness of date-quoting logic.
5. **Prediction-degradation**: inject 20–40% error into duration/setup predictions and stale state information (e.g., 30-min data latency) — *the critical test*, because Strategies 1–3 depend on model quality; a strategy that collapses under realistic prediction error must be rejected.
6. **Resource loss**: bottleneck down for a full shift; key operator absent (tests skill-silo exposure).
7. **New-product introduction**: 15% of jobs from unseen families (no setup history) — tests generalization of the attribute-based setup model.
8. **Mix/seasonality shift** to check bottleneck migration handling.

**Outputs:** for every scenario × policy, full distributions of weighted tardiness, %tardy, p95 flow time, WIP, bottleneck utilization/setup share, throughput, and **schedule stability**; then Pareto fronts (tardiness vs. setup vs. WIP), statistical significance (paired *t* / Wilcoxon with multiplicity correction), and **robustness ranking** (worst-case and CVaR across scenarios, not just mean performance). Simulation-optimization (OptQuest / Bayesian optimization / CMA-ES) tunes $k_1, k_2, \alpha, \beta, \gamma, \delta$, campaign cycle lengths, buffer sizes, and WIP caps — this is also where each parameter's sensitivity is measured, so we know which need tight control in reality.

**Deployment path:** shadow mode (recommendations logged, not enforced, regret measured)  pilot at the primary bottleneck and its immediate feeders  phased shop-wide rollout with explicit fallback to the current practice, and a pre-registered success criterion per phase.

### 5.3 Continuous Monitoring and Adaptation (Closing the Loop)

**A. KPI cockpit with statistical control.** Automated nightly ETL from MES into the process-mining layer; **EWMA/CUSUM control charts** on weighted tardiness, p95 flow time, WIP, bottleneck setup share, priority-inversion rate, and prediction error (MAPE/pinball loss of duration, setup, and ETA models). Statistical signals — not opinions — trigger investigation.

**B. Conformance checking against the schedule.** Treat the released schedule as the normative model and continuously measure **schedule adherence** (sequence deviations, start-time deviations) per machine, shift, and operator. Persistent, *localized* non-conformance is diagnostic: either the schedule is infeasible there (bad parameters, unmodelled constraint such as tooling or fixture availability) or the operator has knowledge the model lacks. Both are learning opportunities; log every override with a reason code and mine the reasons quarterly — this is how the unmodelled constraints get discovered.

**C. Concept-drift detection.** Run **ADWIN / Page-Hinkley** on residual streams of the duration and setup models; **DFG/model drift detection** on routing and hand-off structures; distribution monitoring (PSI/KL) on job-mix, family shares, and order-allowance features. Detect **bottleneck migration** automatically by monitoring the rolling active-period bottleneck share — a change in the ranked bottleneck triggers re-tuning of $\beta$, buffer placement, and campaign plans.

**D. Automated retrain/re-tune pipeline.** Drift or performance-degradation triggers: (1) retrain duration/setup/ETA models on a rolling window with backtesting; (2) re-validate the digital twin against the latest quarter; (3) re-run simulation-optimization for rule weights and campaign cycles; (4) promote via **champion/challenger** — the challenger runs in shadow for a defined period and is promoted only on statistically significant improvement across the robustness scenario set. Full model registry, versioning, and rollback.

**E. Governance cadence.**
- *Per shift:* at-risk-job radar, dispatch lists, exception review.
- *Weekly:* KPI control charts, adherence and inversion rates, hot-job cascade cost, top-5 setup-waste sequences.
- *Monthly:* bottleneck share and load/capacity ($\rho$) review, WIP-cap and buffer re-sizing, due-date-quoting service level vs. achieved OTD.
- *Quarterly:* full re-mining, drift audit, re-tuning, offline-optimality-gap recomputation (Test C) to see how much *remaining* scheduling upside exists — the honest measure of whether further scheduling investment or capital capacity is the right next move; plus SMED/tooling and cross-training pipeline refresh.

**F. Guarding against the failure modes of this program itself.** Three risks must be monitored explicitly: (i) **data-quality decay** (missing setup events silently degrade the setup model — monitor event-completeness rates per machine as a first-class KPI); (ii) **metric gaming** (setup minimization at the expense of small urgent orders — hence tardiness and inversion rate are always reported alongside setup savings); (iii) **trust erosion** (if the schedule is visibly infeasible once, adherence collapses — hence robust $p_{70/80}$ inputs, frozen windows, and stability penalties are design requirements, not refinements).

The through-line: process mining supplies the *evidence* (what actually happens, and how much of the loss is scheduling-addressable versus capacity or variability), simulation supplies the *safe test bed*, and the scheduling strategies — release control, setup-aware dynamic dispatching, family campaigns, and predictive rolling-horizon optimization — supply the *mechanism*.
