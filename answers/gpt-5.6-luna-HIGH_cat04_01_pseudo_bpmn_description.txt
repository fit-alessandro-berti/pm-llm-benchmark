## 1. Overall process purpose

The process handles a customer request from initial receipt through validation or feasibility analysis, commercial approval, invoicing, and customer confirmation.

The process has two primary request types:

- **Standard request:** Follows routine validation, parallel credit and inventory checks, and delivery-date calculation.
- **Custom request:** Requires a feasibility analysis. If feasible, a custom quotation is prepared; if not, the request is rejected and the process ends.

Once the applicable standard or custom work is complete, both paths converge into a common approval and invoicing sequence.

---

## 2. Process flow by step

### Start Event

The process begins when a customer request is received.

### Task A: Receive Customer Request

This task records and initializes the request. Typical activities might include:

- Capturing customer and product information
- Recording requested quantities and dates
- Identifying whether the request is standard or custom
- Creating a process or order case for subsequent work

The request is then routed to the first decision point.

---

## 3. Initial XOR gateway: Check Request Type

This is an **exclusive gateway**, represented as an XOR gateway. It selects exactly one path based on the request classification:

- **Standard**
- **Custom**

A request should not normally follow both paths. The classification may be based on product type, configuration, service requirements, pricing rules, or whether the request falls within an approved catalog.

---

## 4. Standard-request path

### Task B1: Perform Standard Validation

For a standard request, the organization verifies that the request satisfies normal business rules. This may include checking:

- Customer account status
- Product availability rules
- Pricing and contractual eligibility
- Required order information
- Credit or payment terms
- Standard service constraints

After this validation, the process reaches an AND gateway.

### AND gateway: Run Parallel Checks

This is a **parallel gateway**, represented as an AND split. It starts both checks at the same time because they are independent or can be performed concurrently.

#### Task C1: Credit Check

This evaluates whether the customer is financially eligible to proceed. It might check:

- Credit limit
- Outstanding balances
- Payment history
- Account status
- Required payment terms

#### Task C2: Inventory Check

This determines whether the requested products or materials are available. It might assess:

- Current inventory
- Reserved stock
- Expected replenishment
- Warehouse availability
- Quantity constraints

### Parallel join: All Parallel Checks Completed

The corresponding AND join waits until **both** the credit check and inventory check have completed.

This is important: the process should not calculate a delivery date based on only one of the two results. Both results are required before continuing.

### Task D: Calculate Delivery Date

Using the validation results, inventory status, operational capacity, and possibly transportation information, the process calculates or confirms the expected delivery date.

The standard path then converges with the successful custom path and proceeds to the common approval stage.

---

## 5. Custom-request path

### Task B2: Perform Custom Feasibility Analysis

For a custom request, the organization determines whether it can fulfill the requested customization. This may involve:

- Technical analysis
- Engineering review
- Manufacturing or operational assessment
- Resource and capacity analysis
- Risk evaluation
- Cost and lead-time estimation
- Compliance or regulatory review

The outcome is evaluated by the next XOR gateway.

### XOR gateway: Is Customization Feasible?

This exclusive decision has two possible outcomes.

#### Feasible: Task E1 — Prepare Custom Quotation

If the customization is feasible, a quotation is prepared. This may include:

- Custom price
- Scope and specifications
- Delivery estimate
- Terms and conditions
- Assumptions and exclusions
- Any special implementation requirements

The successful custom path then converges with the standard path before the approval decision.

#### Not feasible: Task E2 — Send Rejection Notice

If the customization cannot be supported, the customer is sent a rejection notice.

This is a terminal path in the representation:

```text
Task E2 --> End Event
```

Therefore, a rejected custom request does not proceed to:

- Approval
- Invoice generation
- Customer confirmation through Task I

The rejection notice is the final customer communication shown for that path.

---

## 6. Convergence of standard and custom paths

After either of the following activities:

- **Task D:** Calculate Delivery Date for a standard request
- **Task E1:** Prepare Custom Quotation for a feasible custom request

the two paths converge into the common decision:

> Is Approval Needed?

This convergence means that the downstream approval and invoicing logic is shared rather than duplicated for each request type.

The paths are not necessarily being synchronized as parallel work. The initial request-type gateway is exclusive, so only one route is active. The convergence is therefore conceptually an **exclusive merge** or simple path merge, not an AND join.

---

## 7. XOR gateway: Is Approval Needed?

This gateway determines whether the request must receive managerial approval before an invoice can be generated.

The decision may depend on business rules such as:

- Order value
- Discount level
- Customer risk
- Customization complexity
- Margin thresholds
- Delivery commitments
- Exception to standard terms
- Credit or inventory concerns
- Contractual requirements

### No approval needed

If approval is not required, the process proceeds directly to:

### Task G: Generate Final Invoice

The invoice is generated using the relevant information:

- For a standard request, the validated request and calculated delivery date
- For a custom request, the approved quotation and custom terms

The process then moves to customer confirmation.

### Approval required

If approval is required, the process moves to:

### Task F: Obtain Manager Approval

A manager or authorized approver reviews the request. The review may cover:

- Commercial terms
- Pricing and discounts
- Feasibility assumptions
- Delivery commitments
- Credit exposure
- Profitability
- Exception handling

The result is assessed by a second XOR gateway.

---

## 8. XOR gateway: Is Approval Granted?

This gateway selects one of two outcomes.

### Approval granted

If the manager grants approval, the process proceeds to:

### Task G: Generate Final Invoice

The approval allows the organization to finalize the commercial transaction and issue the invoice.

Although Task G is shown once in the diagram, it is reachable through two routes:

1. No approval was needed
2. Approval was required and granted

This is a common reuse of a shared task.

### Approval not granted

If the manager does not approve the request, the process proceeds to:

### Task H: Re-evaluate Conditions

This task represents rework or corrective action. The organization may need to reconsider:

- Price or discount
- Product or service scope
- Delivery date
- Payment terms
- Credit exposure
- Customization requirements
- Quantity
- Available inventory
- Other exception conditions

The goal is to revise the request so that it may become acceptable for approval.

---

## 9. Loop-back behavior after rejected approval

After Task H, the representation loops back differently depending on the original request type:

- **Custom request:** Loop back to Task E1, “Prepare Custom Quotation”
- **Standard request:** Loop back to Task D, “Calculate Delivery Date”

### Custom loop

For a custom request, the revised conditions are used to prepare an updated quotation. The revised quotation then proceeds again to the “Is Approval Needed?” gateway.

For example, a manager might reject a custom quotation because the price is too low or the delivery date is too aggressive. The quotation can be revised and resubmitted.

### Standard loop

For a standard request, the process returns to delivery-date calculation. This may reflect a changed delivery commitment, revised inventory assumption, or adjustment to operational conditions.

After recalculation, the process again checks whether approval is needed. It may then:

- Bypass approval and generate the invoice
- Return to managerial approval
- Be rejected again and enter another rework cycle

The model therefore allows repeated iterations until the request is approved or another termination condition is introduced.

---

## 10. Task I: Send Confirmation to Customer

After the final invoice is generated, the organization sends a confirmation to the customer.

This may communicate:

- Confirmation that the request has been accepted
- Final price or invoice information
- Expected delivery date
- Order or transaction reference
- Applicable terms
- Any relevant next steps

The process then reaches the normal End Event.

The confirmation task is only reached for requests that:

1. Passed the standard or custom processing path,
2. Did not terminate through custom rejection,
3. Either did not require approval or received approval,
4. Completed invoice generation.

---

## 11. Meaning of the gateway types

### XOR gateway — exclusive choice

An XOR gateway selects exactly one outgoing path.

Examples in this process include:

- Standard versus custom request
- Customization feasible versus infeasible
- Approval needed versus not needed
- Approval granted versus not granted

Only one branch should be active for each decision.

### AND gateway — parallel split and join

The AND gateway starts multiple branches concurrently and later waits for all of them to complete.

In this process:

```text
Credit Check
Inventory Check
```

run in parallel, and the process cannot continue to delivery-date calculation until both are complete.

### Merge of standard and custom paths

The standard and successful custom paths converge before the approval decision. Since only one request type is selected at the initial XOR gateway, this convergence should be understood as an exclusive merge rather than a synchronization point waiting for both paths.

---

## 12. Summary of the main paths

### Standard request, no approval required

```text
Receive Request
--> Standard Validation
--> Credit Check + Inventory Check in Parallel
--> Calculate Delivery Date
--> No Approval Needed
--> Generate Final Invoice
--> Send Confirmation
--> End
```

### Standard request, approval granted

```text
Receive Request
--> Standard Validation
--> Parallel Credit and Inventory Checks
--> Calculate Delivery Date
--> Approval Needed
--> Obtain Manager Approval
--> Approval Granted
--> Generate Final Invoice
--> Send Confirmation
--> End
```

### Standard request, approval rejected

```text
...
--> Obtain Manager Approval
--> Approval Not Granted
--> Re-evaluate Conditions
--> Calculate Delivery Date
--> Reassess Approval
```

This loop may repeat.

### Feasible custom request, no approval required

```text
Receive Request
--> Custom Feasibility Analysis
--> Feasible
--> Prepare Custom Quotation
--> No Approval Needed
--> Generate Final Invoice
--> Send Confirmation
--> End
```

### Feasible custom request, approval rejected

```text
...
--> Obtain Manager Approval
--> Approval Not Granted
--> Re-evaluate Conditions
--> Prepare Custom Quotation
--> Reassess Approval
```

### Infeasible custom request

```text
Receive Request
--> Custom Feasibility Analysis
--> Not Feasible
--> Send Rejection Notice
--> End
```

---

## 13. Modeling clarification

The loop-back points are meaningful but slightly narrow:

- A custom request rejected during approval loops to **Prepare Custom Quotation**, not back to the feasibility analysis.
- A standard request rejected during approval loops to **Calculate Delivery Date**, not back through standard validation or the credit and inventory checks.

That means the model assumes that approval rejection requires only a revised quotation or delivery date. If a rejection could require rechecking feasibility, credit, or inventory, the loop should instead return to an earlier activity, such as:

- **Task B2** for renewed custom feasibility analysis
- **Task B1** or the parallel checks for renewed standard validation
- Or a dedicated rework gateway that determines which checks must be repeated

The diagram also does not show a maximum number of approval attempts, a final escalation path, or a customer cancellation option. Those could be added if repeated rework should eventually terminate rather than continue indefinitely.
