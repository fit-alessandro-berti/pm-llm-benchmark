**DuckDB SQL query to extract events belonging only to the top-K process variants**

```sql
WITH params AS (
  SELECT 5 AS k   -- << set the desired top-K value here
),

-- 1. Build the ordered activity sequence (process variant) for every case
case_variants AS (
  SELECT
    case_id,
    list(activity ORDER BY timestamp) AS variant
  FROM event_log
  GROUP BY case_id
),

-- 2 + 3. Identify the unique variants, rank them by frequency,
--         and keep only those whose rank is ≤ K
--         (RANK includes all ties at the boundary)
top_variants AS (
  SELECT variant
  FROM case_variants
  GROUP BY variant
  QUALIFY RANK() OVER (ORDER BY COUNT(*) DESC) <= (SELECT k FROM params)
),

-- Cases that follow one of the top-K variants
top_cases AS (
  SELECT case_id
  FROM case_variants
  WHERE variant IN (SELECT variant FROM top_variants)
)

-- 4. Return every original event that belongs to those cases
SELECT el.*
FROM event_log el
WHERE el.case_id IN (SELECT case_id FROM top_cases)
ORDER BY el.case_id, el.timestamp;
```

### Why this satisfies the requirements

1. **Ordered sequence per case**  
   `list(activity ORDER BY timestamp)` produces a deterministic ordered sequence for each `case_id`. Using the native `LIST` type avoids any delimiter-collision issues that a string separator (`'->'`, etc.) could create.

2. **Grouping into process variants**  
   Grouping by the `LIST` value directly yields the distinct process variants.

3. **Top-K by frequency (with proper tie handling)**  
   - Frequency is obtained with `COUNT(*)`.  
   - `RANK() OVER (ORDER BY COUNT(*) DESC)` ranks the variants.  
   - `QUALIFY … ≤ K` retains every variant whose rank is at most K (all variants that share the same frequency as the K-th are kept).  
   - The value of K is isolated in a single, easy-to-edit `params` CTE (illustrated with 5).

4. **Filter the original event log**  
   Only the `case_id`s that belong to the retained variants are kept; the final `SELECT` returns every original row of those cases (ordered for readability and determinism).

The query is fully self-contained, uses only DuckDB-supported features (`list` / `list_agg`, `QUALIFY`, window functions, complex-type equality), and can be turned into a prepared statement by replacing the literal `5` with a parameter if desired.
