Here's a DuckDB SQL query that accomplishes this using window functions (`LEAD`) to detect the three-activity sequence and measure the time gap between `Create Order` and `Confirm Order`:

```sql
WITH ordered_events AS (
    SELECT
        *,
        LEAD(activity, 1) OVER (PARTITION BY case_id ORDER BY timestamp) AS next_activity,
        LEAD(timestamp, 1) OVER (PARTITION BY case_id ORDER BY timestamp) AS next_timestamp,
        LEAD(activity, 2) OVER (PARTITION BY case_id ORDER BY timestamp) AS next_next_activity,
        LEAD(timestamp, 2) OVER (PARTITION BY case_id ORDER BY timestamp) AS next_next_timestamp
    FROM event_log
),
flagged_cases AS (
    SELECT DISTINCT case_id
    FROM ordered_events
    WHERE activity = 'Approve Purchase Requisition'
      AND next_activity = 'Create Order'
      AND next_next_activity = 'Confirm Order'
      AND (next_next_timestamp - next_timestamp) > INTERVAL '5 days'
)
SELECT e.*
FROM event_log e
WHERE e.case_id NOT IN (SELECT case_id FROM flagged_cases)
ORDER BY e.case_id, e.timestamp;
```

### How it works:

1. **`ordered_events` CTE**  
   For every event, we compute the *next* and *next-next* activity and timestamp within the same `case_id`, ordered chronologically by `timestamp`. This lets us check, row-by-row, whether an event and its two immediate successors match the target sequence:
   - Current row  `'Approve Purchase Requisition'`
   - Next row  `'Create Order'`
   - Next-next row  `'Confirm Order'`

2. **`flagged_cases` CTE**  
   From the annotated events, we filter to rows where:
   - The sequence matches exactly (`Approve Purchase Requisition`  `Create Order`  `Confirm Order`), in direct succession (no other event in between, since we use `LEAD(...,1)` and `LEAD(...,2)`).
   - The time difference between `Create Order`’s timestamp and `Confirm Order`’s timestamp exceeds `5 days`.
   
   We then take the **distinct** `case_id`s that satisfy both conditions — these are the cases to be excluded.

3. **Final SELECT**  
   We return all events from `event_log` **except** those whose `case_id` appears in `flagged_cases`. This ensures we exclude entire cases (not just the specific events) that match the sequence and timing condition.

4. **Ordering**  
   The final result is ordered by `case_id` and `timestamp` for clarity and consistent presentation, though this can be adjusted or removed depending on your needs.

### Notes:
- This query assumes each case's events are properly timestamped in true chronological order, and ties in timestamp (if any) won't cause the `LEAD()` order to break the intended sequence. If ties are common, you might need a secondary ordering key (e.g., an event ID) to guarantee determinism.
- If activities can repeat or overlap in complex ways, and you want *all* possible starting points of the pattern within a case (not just the first), the `LEAD` approach still works correctly because it checks every row as a potential start of the sequence.
- `INTERVAL '5 days'` comparison works directly on two `TIMESTAMP` columns in DuckDB, returning an interval type that can be compared to another interval.
