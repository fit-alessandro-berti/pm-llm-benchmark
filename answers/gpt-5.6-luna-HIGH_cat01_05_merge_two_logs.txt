## Matching policy

- Normalize event names for comparison, while retaining the original names.
- Match only events for the same `order_id`.
- Use a timestamp tolerance of **up to and including 2 seconds**. This treats the 2-second differences in the received and shipping events as recording offsets.
- Use event semantics in addition to timing. Events more than 2 seconds apart, or with ambiguous semantics, remain separate.
- For merged events, use the Log A timestamp as `primary_timestamp`, since Log A is the primary timeline. Both source timestamps are retained.

## Matching decisions

1. **Order Received / OrderReceived**
   - Matched because the names are clear variants of the same activity.
   - Timestamp difference: 2 seconds.
   - The Log A timestamp is used as the primary timestamp.

2. **Order Validated / OrderValidation**
   - Matched based on equivalent meaning and the 1-second timestamp difference.
   - Attributes from Log B, including `user_id`, `resource_id`, and `notes`, were added.

3. **Payment Processed / PaymentCheck**
   - Kept as separate records.
   - Although the names are related, the timestamps differ by 5 seconds, exceeding the selected tolerance.
   - `PaymentCheck` may represent a gateway check or an intermediate step rather than the completed payment event. The note about gateway delay further supports retaining it as a distinct event.

4. **Quality Check**
   - Included as a B-only event because no corresponding event exists in Log A.

5. **Item Shipped / Shipping**
   - Matched because the names describe the same activity and the timestamps differ by exactly 2 seconds.

6. **Item Delivered**
   - Included as an A-only event because Log B contains no corresponding delivery event.

All source-specific attributes were preserved, and no conflicting values were present for the shared `order_id`.
