### 1. Issues with the Current Underfitting Model

The current tree correctly starts with **Create Purchase Requisition  Approve Purchase Requisition**, but then places all remaining steps inside a single **`PARALLEL` (AND)** block followed by **Close Case**.

Because `PARALLEL` allows its children to occur in any interleaved or concurrent order (as long as each eventually happens), the model permits many domain-invalid behaviors, such as:

| Unwanted Behavior | Why it violates P2P logic |
|---|---|
| **Pay Invoice** before **Receive Invoice** or **Match Invoice to PO** | Payment requires an invoice to exist and be verified against the PO. |
| **Match Invoice to PO** before **Create Purchase Order** or **Receive Invoice** | Matching needs both the PO and the invoice to be present. |
| **Receive Goods** or **Receive Invoice** before **Create Purchase Order** | The PO should be established before goods/invoice are received against it. |
| **Close Case** happening in the middle (implicitly) or steps occurring after it | The tree puts `Close Case` after the parallel block, but inside the block there is no ordering, so conceptually nothing prevents “late” steps from being conceptually misplaced relative to prerequisites. |

In short, the parallel block **removes all causal and temporal ordering** among the core fulfillment, invoicing, and payment activities.

---

### 2. Corrected Process Tree Model

The standard “Procure-to-Pay” flow is strictly linear in this simplified view: each step is a prerequisite for the next, with no branching, loops, or optional steps required. Therefore, we replace the `PARALLEL` block with a flat (or nested) **`SEQUENCE`** of all eight activities.

```python
from pm4py.objects.process_tree.obj import Operator, ProcessTree

# Activities (unchanged)
create_req      = ProcessTree(label="Create_Purchase_Requisition")
approve_req     = ProcessTree(label="Approve_Purchase_Requisition")
create_po       = ProcessTree(label="Create_Purchase_Order")
receive_goods   = ProcessTree(label="Receive_Goods")
receive_invoice = ProcessTree(label="Receive_Invoice")
match_invoice   = ProcessTree(label="Match_Invoice_to_PO")
pay_invoice     = ProcessTree(label="Pay_Invoice")
close_case      = ProcessTree(label="Close_Case")

# Fixed model: strict sequential order enforcing normal P2P logic
root = ProcessTree(operator=Operator.SEQUENCE, children=[
    create_req,
    approve_req,
    create_po,
    receive_goods,
    receive_invoice,
    match_invoice,
    pay_invoice,
    close_case
])
```

*No `XOR` (choice) or `LOOP` operators are necessary here:* the domain logic specifies a single, mandatory path from requisition through to case closure.

---

### 3. How the Updated Tree Ensures Conformance

The corrected tree uses a single **`SEQUENCE`** root (with all eight children in order). In process-tree semantics, this means:

- **Exactly-once, in-order execution:** Every child must execute once, and child *i* must finish before child *i+1* can start.
- **No concurrency:** Because there is no `PARALLEL` node, activities can never overlap or interleave.
- **No out-of-order execution:** The tree physically encodes the dependency chain:
  1. Requisition is created and approved.
  2. Only then can the **PO** be created.
  3. Only then can **Goods** be received (against that PO).
  4. Only then can the **Invoice** be received.
  5. Only then can the invoice be **Matched** to the existing PO.
  6. Only then can the invoice be **Paid**.
  7. Finally, the **Case** is closed.

This structure **prevents all unwanted behaviors** identified in part 1: it is impossible to pay before matching, match before receiving the invoice/PO, or close the case before payment has occurred. The model is now **fitting** for the intended “Procure-to-Pay” domain logic—allowing only the normal, correct trace of events.
