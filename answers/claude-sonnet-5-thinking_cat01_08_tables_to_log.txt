# Integrated Process Mining Event Log

## Assumptions & Design Notes

1. **Case ID** = `order_id` (the natural process instance identifier spanning order  pick  ship  invoice  pay).
2. **One event per row** — multiple order lines, deliveries, invoices, and payments each generate **separate events** (not summarized), since each has a distinct actor/timestamp and is meaningful for process mining (e.g., detecting split shipments, partial invoicing, batch picking).
3. **Activity naming convention**:
   - `Order Created` – from Orders table
   - `Item Picked` – from Order Lines table (one event per line item)
   - `Order Dispatched` / `Order Arrived` – two distinct events per Delivery record (dispatch and arrival treated as separate lifecycle events, not one span)
   - `Invoice Issued` – from Invoice table
   - `Payment Received` – from Payments table, joined to `order_id` via `invoice_id`
4. **Resource enrichment** — resource IDs resolved to human-readable names/roles using the Resources table.
5. **Order 1004** has no Delivery, Invoice, or Payment records in the source data — this is preserved as a gap (possibly an open/in-progress or abandoned order). No synthetic events were invented.
6. Timestamps are kept in original UTC ISO format; sorting is done by `order_id`, then chronologically by timestamp.
7. `Other Attributes` column carries context-specific details (quantities, amounts, carriers, payment refs, notes, etc.).

## Summary of Key Design Decisions

| Aspect | Decision | Rationale |
|---|---|---|
| Multiple picks per order | Kept as separate `Item Picked` events | Preserves granularity for bottleneck/batch analysis in picking |
| Multiple deliveries per order (e.g., 1002) | Split into distinct Dispatch/Arrival events per delivery_id | Reflects real split-shipment behavior, useful for logistics analysis |
| Multiple invoices per order (e.g., 1002) | Each invoice = separate event | Enables analysis of partial billing patterns |
| Payment  Order linkage | Done via `invoice_id  order_id` lookup | Payments table lacks direct order_id; invoice acts as bridge key |
| Missing Resource for Payments | Left as "—" | Payments table has no actor/resource field (could be automated system) |
| Order 1004 incomplete lifecycle | Explicitly flagged, no fabricated events | Avoids introducing bias/noise into process mining discovery |
| Timestamp ordering | Verified per case to ensure logical flow: Create  Pick  Dispatch  Arrive  Invoice  Pay | Ensures valid process traces for tools like Celonis/ProM/Disco |

This event log is now ready to be imported into a process mining tool (e.g., Disco, Celonis, PM4Py) using:
- **Case ID** = `order_id`
- **Activity** = `Activity Name`
- **Timestamp** = `Timestamp`
- **Resource** = `Resource/Actor`
- Additional columns retained as event attributes for filtering/analysis (e.g., by carrier, item category, payment method).
