3. **Gateway (XOR): "Check Request Type"**  
   - **Purpose**: A decision point that branches the process based on the type of request received. XOR (Exclusive Choice) gateways require that only one outgoing flow is taken. This means the process will either classify the request as Standard or Custom, but not both.

     - If the request type is Standard, it proceeds to Task B1.
     - If the request type is Custom, it proceeds to Task B2.

5. **Gateway (AND): "Run Parallel Checks"**  
   - **Purpose**: Another decision point, but unlike the XOR gateways, AND gateways allow all outgoing flows to be taken simultaneously. This is useful for running multiple checks in parallel (e.g., credit check and inventory check) to expedite the process.

6. **Task C1: "Credit Check"**

### Convergence and Looping

- **Convergence**: The process converges at several gateways, primarily at the XOR decision points. These points are crucial for branching the workflow into Standard or Custom paths and for determining the need for manager approval.
- **Looping**: The process incorporates loops primarily through conditional branching. If a customer request is found not to be feasible (Custom Path) or if manager approval is not granted (either path), the process loops back to reassess the request (Task E2 or Task D). This ensures that the process remains dynamic and adaptable to changing circumstances or requirements.

### Differences Based on Request Type

- **Standard Requests**: These are processed through a straightforward, parallel validation and inventory check mechanism. They generally do not require managerial approval unless specified by organizational policy. The process culminates in generating a delivery date and sending a confirmation to the customer.
  
- **Custom Requests**: These involve a more complex evaluation process. They require checking the feasibility of customization, potentially involving manager approval, and generating a quotation instead of a delivery date. The process includes additional steps for custom feasibility analysis and potential rework if approval is not granted or if the request is deemed unfeasible.

### Conditions Triggering Approvals or Rework

- **Approval Needed**: The process triggers manager approval when the request type is custom or when the customization feasibility is uncertain. This ensures that high-value or complex requests are reviewed by a competent authority before proceeding.
  
- **Rework Steps**: Rework is triggered when:
  - A custom request is found not feasible, leading to a rejection notice.
  - Manager approval is not granted, causing the process to loop back for reevaluation or potentially to terminate the request if the decision is firm.
