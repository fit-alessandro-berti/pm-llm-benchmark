# Data-Driven Process Mining and Advanced Scheduling Approach for Precision Parts Inc.

Precision Parts should treat its MES log not merely as a reporting source, but as the foundation for a continuously updated operational “digital twin” of the job shop. The objective is to move from local, static dispatching to a closed-loop scheduling system that:

1. Reconstructs how work actually flows.
2. Identifies where and why jobs wait.
3. Predicts likely delays before they occur.
4. Makes scheduling decisions using current shop-floor state, due-date risk, setup implications, and downstream constraints.
5. Learns and adapts from outcomes.

A critical principle is that process mining should not be used only to produce process maps. In this environment, it must be combined with resource-centric analysis, queueing analysis, predictive modeling, optimization, and discrete-event simulation.

---

## 1. Analyzing Historical Scheduling Performance and Dynamics

## 1.1 Create a manufacturing event-log model

The MES data should first be transformed into an analysis-ready event log. The raw records shown in the example are useful, but scheduling analysis requires consistent lifecycle reconstruction.

### Core entities

The data model should contain at least four linked objects:

- **Job/order object:** `Job ID`, customer, order priority, due date, release date, promised quantity, product family, material, complexity, engineering revision.
- **Operation/task object:** job-operation instance, routing sequence, activity type, planned duration, actual duration, status, predecessor/successor operations.
- **Resource object:** machine, work center, operator, tooling, fixture, setup state.
- **Disruption object:** breakdown, repair, planned maintenance, material shortage, quality hold, priority change, operator absence.

Because a single job has many operations and a machine processes many jobs, the analysis should preferably use an **object-centric event log** rather than a simple case-centric log. Traditional process mining treats one “case” as one job; object-centric process mining additionally captures relationships among jobs, tasks, machines, operators, and disruptions.

### Normalize event lifecycle states

For each operation, construct a standardized lifecycle such as:

1. Job released
2. Operation ready / queue entry
3. Setup start
4. Setup complete
5. Processing start
6. Processing complete
7. Inspection start/end, if applicable
8. Move/queue entry for next operation
9. Job complete

For each resource, construct a resource-state timeline:

- Available and idle
- Setup
- Processing
- Waiting for material/job
- Waiting for operator/tooling
- Blocked by downstream issue
- Planned maintenance
- Breakdown/repair
- Off-shift/unavailable

This distinction is essential. A machine that appears “idle” may actually be starved because upstream operations did not feed it, or blocked because completed work cannot move downstream.

### Data-quality checks before analysis

Before using the log for performance or scheduling conclusions, validate:

- Missing or duplicated start/end timestamps.
- Negative or impossible durations.
- Operations completed without recorded start events.
- Jobs with incomplete routing records.
- Machine IDs that changed names or were entered inconsistently.
- Setup events not linked to a specific machine/job.
- Overlapping tasks assigned to the same machine or operator.
- Time-zone, shift-calendar, and non-working-hour inconsistencies.
- Due dates stored as dates rather than precise timestamps.
- Changes in planned schedule that overwrite prior plans.

For schedule-adherence analysis, it is especially important to preserve **schedule snapshots**. If the MES overwrites the original planned start/end date after each reschedule, the company cannot distinguish poor initial planning from later recovery actions.

## 1.2 Reconstruct actual job flow and machine execution sequences

### Job-centric process reconstruction

For each job, sort events chronologically and reconstruct the actual route:

\[
\text{Job Released} \rightarrow \text{Cutting} \rightarrow \text{Milling} \rightarrow \text{Lathing} \rightarrow \text{Grinding} \rightarrow \text{Heat Treatment} \rightarrow \text{Inspection}
\]

In reality, some jobs may skip operations, revisit machines, undergo rework, wait for inspection, or follow different routings. Therefore, process discovery should identify actual variants rather than assume that all jobs follow the nominal routing.

Useful process mining techniques include:

- **Directly-Follows Graphs (DFGs):** Show frequent transitions between operations.
- **Inductive Miner:** Produces interpretable process models while handling optional and parallel activities.
- **Heuristics Miner:** Useful when logs are noisy and contain loops or rework.
- **Process variant analysis:** Identifies the most common routing patterns and unusual variants.
- **Conformance checking/alignment:** Compares actual execution with the planned routing or ERP routing definition.

Questions answered include:

- Which operation sequences are most common?
- Which jobs deviate from the planned route?
- How often does rework occur?
- Which routing variants have the highest tardiness?
- Are high-priority jobs following different paths or receiving special treatment?
- Which process paths are associated with long lead times?

### Resource-centric reconstruction

For each machine, sort all setup, processing, breakdown, and idle events chronologically. This produces a resource execution timeline similar to a Gantt chart:

| Machine | Start | End | State | Job | Operation |
|---|---:|---:|---|---|---|
| CUT-01 | 09:15 | 09:39 | Setup | JOB-7001 | Cutting |
| CUT-01 | 09:39 | 10:45 | Processing | JOB-7001 | Cutting |
| CUT-01 | 10:45 | 11:10 | Idle/Starved | — | — |
| CUT-01 | 11:10 | 11:35 | Setup | JOB-7008 | Cutting |

This makes it possible to identify the actual sequence of jobs on every resource, not just the sequence intended by the scheduler.

For every processed operation, determine:

- Which job immediately preceded it on the machine.
- Whether there was an intervening breakdown or idle period.
- The setup state left by the previous job.
- Whether the next job required a family/tool/material/fixture change.
- Whether an urgent job interrupted an existing sequence.

This reconstruction is the foundation for setup-time analysis, resource contention analysis, and schedule sequencing optimization.

## 1.3 Measure flow times, lead times, makespan, and WIP

### Job lead time and flow time

Several time measures should be tracked because they answer different management questions.

| Metric | Definition | Managerial meaning |
|---|---|---|
| Customer lead time | Job completion  order receipt | Customer-facing responsiveness |
| Manufacturing lead time | Job completion  job release | Internal production responsiveness |
| Job flow time | Completion of final operation  start of first operation | Time spent actively moving through production |
| Queue time | Operation start  operation ready/queue entry | Delay caused by capacity or scheduling |
| Touch time | Sum of processing and setup times | Time during which resources are working on the job |
| Total waiting time | Lead time  touch time  transport/hold time | Hidden delay in the system |
| Makespan | Completion of a job set  release of first job in the set | Time to complete a batch, order portfolio, or planning horizon |

For each metric, calculate:

- Mean and median.
- Standard deviation.
- 50th, 75th, 90th, and 95th percentiles.
- Distribution by product family, customer, priority, routing type, and machine path.
- Trend by week/month.
- Comparison of on-time versus late jobs.

The median alone is insufficient. Job shops typically have highly skewed distributions: many jobs may complete reasonably quickly, while a smaller group experiences extreme delays.

### WIP analysis

WIP should be measured at:

- Entire shop level.
- Work-center level.
- Machine level.
- Product family level.
- Priority class level.
- Queue before bottleneck resources.
- Queue before downstream finishing/inspection operations.

A time-series WIP chart should be constructed from queue-entry and task-start/end events. The company should apply Little’s Law as a diagnostic relationship:

\[
\text{WIP} \approx \text{Throughput Rate} \times \text{Flow Time}
\]

If WIP rises while throughput remains flat, flow time should rise. This relationship helps quantify whether excess WIP is a cause or consequence of poor scheduling performance.

## 1.4 Measure task waiting times and queue behavior

For each operation instance:

\[
\text{Queue Time} =
\text{Task Start or Setup Start} -
\text{Queue Entry / Operation Ready Time}
\]

Depending on the business definition, it may be useful to separate the queue time into:

\[
\text{Total Queue Time} =
\text{Machine Waiting Time} +
\text{Operator Waiting Time} +
\text{Tooling/Material Waiting Time} +
\text{Administrative Hold Time}
\]

For example, an operation may be ready at 10:46 but unable to start until 14:00 because:

- MILL-03 is busy for two hours.
- The operator is unavailable for 30 minutes.
- The fixture is unavailable for 20 minutes.
- The job is held for quality review for 24 minutes.

Without separating these causes, “queue time” becomes too broad to drive improvement.

Useful analyses include:

- Queue-time distribution by machine and operation.
- Queue time by priority class.
- Queue time by product family.
- Queue length at time of arrival.
- Queue length versus eventual tardiness.
- Waiting time before and after a breakdown.
- Queue behavior during high-load periods.
- Queue time for hot jobs versus normal jobs.

A particularly useful visualization is a **heat map of queue delay by machine and hour/day**, which often reveals recurring overload patterns, shift effects, or gaps caused by poor handoffs.

---

## 1.5 Measure machine and operator utilization

Resource utilization should not be represented as one simplistic percentage. The utilization composition matters.

For each machine:

\[
\text{Available Time} =
\text{Scheduled Calendar Time} -
\text{Planned Downtime}
\]

Then partition available time into:

\[
\text{Available Time} =
\text{Processing Time} +
\text{Setup Time} +
\text{Breakdown Time} +
\text{Idle-Starved Time} +
\text{Idle-Blocked Time} +
\text{Idle-Other Time}
\]

Key metrics include:

\[
\text{Productive Utilization} =
\frac{\text{Processing Time}}{\text{Available Time}}
\]

\[
\text{Setup Utilization} =
\frac{\text{Setup Time}}{\text{Available Time}}
\]

\[
\text{Technical Availability} =
\frac{\text{Available Time} - \text{Breakdown Time}}{\text{Scheduled Time}}
\]

\[
\text{Overall Busy Utilization} =
\frac{\text{Processing Time} + \text{Setup Time}}{\text{Available Time}}
\]

A machine with 95% busy utilization may be a bottleneck, but it may also be suffering from excessive setup time. Conversely, a resource with only 60% productive utilization may still create delays if it is intermittently unavailable at critical moments.

For operators, examine:

- Machine assignments per shift.
- Setup versus processing effort.
- Operator-specific setup and processing variability.
- Operator qualification constraints.
- Multi-machine assignments and overlapping workload.
- Performance differences by product family or machine type.

Care is required when interpreting operator utilization. An operator may supervise multiple automated machines, so operator “busy time” should not always be summed in the same way as machine time.

## 1.6 Analyze sequence-dependent setup times

Sequence-dependent setups are a central scheduling issue for Precision Parts.

For each operation on a machine, identify the immediately preceding completed job on that same machine. Define a setup transition:

\[
(\text{Previous Setup State}) \rightarrow (\text{Next Setup State})
\]

The setup state should be based on meaningful features, not merely job IDs. Relevant features may include:

- Material type.
- Material thickness or diameter.
- Product family.
- Part geometry.
- Fixture type.
- Tooling package.
- Machine program family.
- Heat-treatment recipe.
- Tolerance class.
- Surface finish requirement.
- Operator skill level.

For each transition, calculate:

\[
\text{Actual Setup Duration} =
\text{Setup End} - \text{Setup Start}
\]

Construct a setup transition matrix for each machine:

| Previous Family | Next Family | Median Setup | P90 Setup | Sample Size |
|---|---:|---:|---:|---:|
| A | A | 8 min | 12 min | 120 |
| A | B | 32 min | 48 min | 44 |
| B | A | 28 min | 43 min | 37 |
| B | C | 55 min | 80 min | 12 |

This enables the company to determine:

- Which job-family transitions create the longest setup times.
- Whether some setup transitions are asymmetrical.
- Which machines are especially sensitive to job sequencing.
- Whether urgent jobs cause expensive sequence breaks.
- Whether setup performance varies significantly by operator or shift.
- Whether planned setup times underestimate actual setup durations.

Statistical or machine-learning models can be developed to estimate:

\[
E[\text{Setup Time} \mid \text{Machine}, \text{Previous State}, \text{Next State}, \text{Operator}, \text{Shift}]
\]

The model should provide not only a mean estimate, but uncertainty ranges such as median, P75, or P90 setup duration.

---

## 1.7 Measure schedule adherence and tardiness

### Due-date adherence

For each job:

\[
\text{Lateness} = \text{Completion Time} - \text{Due Date}
\]

\[
\text{Tardiness} = \max(0, \text{Completion Time} - \text{Due Date})
\]

Key indicators include:

- Percent of jobs completed on time.
- Average tardiness.
- Median tardiness.
- P90 and P95 tardiness.
- Maximum tardiness.
- Tardiness weighted by customer priority or penalty cost.
- Tardiness by customer, product family, routing, and priority.
- Number of jobs completed excessively early, which can indicate unnecessary WIP.

A weighted measure may be useful:

\[
\text{Weighted Tardiness} =
\sum_j w_j \cdot \max(0, C_j - d_j)
\]

where \(w_j\) reflects order priority, contractual penalties, customer strategic importance, or revenue impact.

### Schedule adherence

Due-date performance is not the same as adherence to the production schedule. If planned schedule snapshots are available, calculate:

\[
\text{Start Deviation} =
\text{Actual Start} - \text{Planned Start}
\]

\[
\text{Completion Deviation} =
\text{Actual Completion} - \text{Planned Completion}
\]

Analyze adherence by:

- Job.
- Operation.
- Resource.
- Shift.
- Priority.
- Product family.
- Scheduler revision cycle.
- Disruption type.

This will reveal whether jobs are late because they were planned unrealistically from the beginning, because they were delayed during execution, or because the schedule was continually disrupted and revised.

---

## 1.8 Quantify disruption impact

Breakdowns, hot jobs, quality holds, and priority changes should be treated as process events rather than anecdotal exceptions.

For each disruption, measure:

- Start time and duration.
- Affected resource(s).
- Number of jobs waiting at the time of disruption.
- WIP level immediately before and after disruption.
- Jobs that were processing, queued, or downstream-dependent.
- Added queue time for affected jobs.
- Tardiness generated or increased after the disruption.
- Recovery time until the system returns to normal queue levels.

Useful methods include:

### Event-study analysis

Compare performance in time windows before and after a breakdown:

- Queue length before versus after failure.
- Tardiness risk before versus after failure.
- Resource utilization during recovery.
- Degree of schedule reshuffling.
- Delay propagation to downstream work centers.

### Matched-job analysis

Compare jobs affected by a breakdown with similar jobs that were not affected, controlling for:

- Product family.
- Routing.
- Priority.
- Due-date slack.
- Job size.
- Machine load at release.

### Survival or hazard analysis

Model the probability that a job will miss its due date as its waiting time, queue position, exposure to breakdowns, and downstream congestion increase.

Process mining alone identifies associations and patterns; simulation and statistical controls are needed before asserting that a specific disruption caused a specific performance outcome.

# 2. Diagnosing Scheduling Pathologies

The analysis above should be translated into evidence-based diagnoses rather than broad statements such as “the shop is overloaded.”

## 2.1 Identify true bottlenecks

A bottleneck should not be identified solely by the highest utilization. A true bottleneck generally exhibits several of the following:

- Persistently high busy utilization.
- Long and growing queue lengths.
- High queue-time percentiles.
- Frequent starvation or blocking in downstream resources linked to it.
- Strong association between waiting at that resource and job tardiness.
- High sensitivity of shop throughput to capacity changes at that resource.
- Frequent schedule resequencing around that resource.
- Large setup burden or high breakdown impact.
- Long recovery time after disruptions.

For example, CNC Milling may be a bottleneck if MILL-03 has:

- 90–95% busy utilization.
- A median queue of 25 jobs.
- Long setup transitions between part families.
- A strong correlation between milling queue time and final job tardiness.
- Downstream grinding and inspection starvation after milling delays.

A useful bottleneck-impact analysis estimates:

\[
\Delta \text{Shop Throughput} / \Delta \text{Available Capacity at Resource } r
\]

This can be estimated using simulation or historical periods with different resource availability.

---

## 2.2 Detect poor prioritization

The current FCFS/EDD mix may fail because it does not consider:

- Remaining processing time.
- Setup implications.
- Downstream bottlenecks.
- Actual job progress.
- Resource availability.
- Risk of future disruption.
- Priority changes.
- Queue lengths and WIP levels.

Evidence of poor prioritization may include:

- High-priority jobs waiting longer than lower-priority jobs.
- Near-due jobs being delayed behind jobs with more slack.
- Jobs with very short remaining work waiting behind long jobs.
- Hot jobs inserted repeatedly, causing many normal jobs to become late.
- Early jobs consuming bottleneck capacity while urgent jobs accumulate.

Process mining can compare the queue position, priority, due-date slack, and eventual tardiness of jobs dispatched at each machine. For example:

- Compare jobs selected first under FCFS with the jobs that would have been selected under critical-ratio or slack-based logic.
- Analyze whether low-priority jobs were processed while high-priority jobs were waiting.
- Identify priority inversions: a lower-priority job started while a higher-priority, ready job waited.

---

## 2.3 Identify setup-driven sequencing inefficiency

Suboptimal sequencing is likely if the event log shows frequent high-cost setup transitions even when similar jobs were already waiting.

Evidence may include:

- Repeated family switching such as A  B  A  B.
- Excessive setup time at bottleneck machines.
- Large setup-time variability by sequence.
- Urgent job insertion causing expensive sequence changes.
- Similar jobs processed far apart in time despite both being ready.
- Setup-heavy machines with low productive processing ratios.

A setup transition graph can show where avoidable setup losses occur. For example, a machine may repeatedly move from Family A to Family C and then back to Family A, each transition requiring 45 minutes, even though another Family A job was already in the queue.

The analysis should distinguish between:

- **Necessary setup changes**, driven by actual order mix or due-date constraints.
- **Avoidable setup changes**, caused by poor dispatching or lack of batching logic.
- **Unavoidable disruptions**, caused by hot jobs, breakdowns, or material/tooling availability.

---

## 2.4 Detect downstream starvation and blocking

A resource can appear underutilized not because capacity is excessive, but because upstream work arrives irregularly.

Indicators of downstream starvation include:

- Long idle intervals while upstream bottleneck queues remain high.
- Repeated idle periods immediately after upstream breakdowns.
- Large variation in inter-arrival times of jobs to downstream machines.
- Downstream resources waiting for specific job families or tooling.
- High utilization upstream and low utilization downstream.

Conversely, blocking occurs when completed work cannot proceed due to downstream constraints such as inspection backlog, unavailable heat treatment, or limited staging space.

A resource-flow analysis should connect:

\[
\text{Upstream Release Pattern}
\rightarrow
\text{Downstream Arrival Pattern}
\rightarrow
\text{Downstream Idle/Blocked Time}
\]

This often reveals that local optimization at one work center is damaging overall flow.

---

## 2.5 Identify WIP volatility and “bullwhip” behavior

In a job shop, WIP can fluctuate dramatically when local dispatching decisions, hot jobs, and breakdowns interact.

Signs of scheduling-driven WIP instability include:

- Sharp queue spikes after priority changes.
- Repeated release of work into already overloaded work centers.
- Large differences in queue size across adjacent operations.
- Periodic starvation followed by overload.
- Excessive expediting and rescheduling.
- Increased WIP without proportional throughput growth.

Process mining can visualize WIP levels over time at each work center. A cross-correlation analysis can show whether upstream queue growth predicts downstream congestion several days later.

---

## 2.6 Variant analysis: on-time versus late jobs

One of the most powerful analyses is to compare on-time jobs with late jobs.

Possible comparison dimensions:

| Dimension | On-Time Jobs | Late Jobs |
|---|---|---|
| Routing complexity | Fewer operations | More loops/rework |
| Bottleneck queue time | Lower | Higher |
| Setup exposure | Lower | Higher |
| Number of priority changes | Lower | Higher |
| Breakdown exposure | Lower | Higher |
| Planned versus actual duration error | Lower | Higher |
| Number of machine changes | Lower | Higher |
| Downstream congestion | Lower | Higher |

This can identify patterns such as:

- Late jobs wait disproportionately at Milling and Inspection.
- Jobs requiring certain heat-treatment recipes suffer high setup and queue delays.
- Hot-job insertion disproportionately harms medium-priority jobs.
- Jobs with high planned-versus-actual duration variance are systematically scheduled too aggressively.

# 3. Root Cause Analysis of Scheduling Ineffectiveness

The observed symptoms may arise from poor scheduling logic, insufficient capacity, poor data quality, inherent variability, or a combination of all four.

## 3.1 Static dispatch rules in a dynamic environment

FCFS and simple EDD rules are easy to implement but are insufficient for a complex high-mix job shop.

Their limitations include:

- They are local rather than shop-wide.
- They ignore remaining processing time.
- They ignore downstream bottlenecks.
- They ignore sequence-dependent setup time.
- They do not account for current WIP or congestion.
- They do not respond intelligently to breakdowns.
- They may overreact to urgent jobs.
- They may create unnecessary setups.
- They do not balance due-date performance against throughput and WIP.

For example, EDD may process a near-due job that requires a long setup, while delaying a group of similar jobs that could be processed efficiently. FCFS may process jobs in queue order even when a later-arriving job has almost no due-date slack or would avoid a costly setup.

---

## 3.2 Lack of real-time shop-floor visibility

If dispatchers cannot see real-time information such as machine state, queue lengths, actual progress, tool availability, and current setup state, they cannot make effective decisions.

Process mining can reveal this issue indirectly when it finds:

- Jobs routed to unavailable or broken machines.
- Jobs released into queues that are already excessive.
- Decisions inconsistent with the current due-date risk.
- Long delays between an event occurring and the scheduling response.
- Priority changes that do not result in timely changes on the shop floor.

The future scheduling system should operate on a current-state model, not on an outdated plan created at the start of the shift or day.

---

## 3.3 Inaccurate duration and setup-time estimates

If planners use deterministic average durations, schedules will become unreliable when actual durations vary materially by:

- Job family.
- Material.
- Tolerance requirements.
- Operator.
- Machine condition.
- Shift.
- Tool wear.
- Rework likelihood.
- Batch size.

The process-mining analysis should compare:

\[
\text{Actual Duration} - \text{Planned Duration}
\]

by machine, operation, product family, operator, and complexity class.

If actual durations systematically exceed planned durations at one resource, this suggests planning-data problems. If the variance is very high but unbiased, robust scheduling with buffers and probabilistic duration models is needed.

---

## 3.4 Inadequate treatment of sequence-dependent setups

A major root cause is likely that setup time is either:

- Not modeled at all.
- Modeled as a fixed value.
- Based only on the next job, not the previous job.
- Ignored during dispatching.
- Not considered in hot-job insertion decisions.

This creates schedules that appear feasible in planned processing hours but are infeasible when real setup transitions are included.

Process mining can test this by comparing the schedule’s assumed setup time with actual sequence-dependent setup time. If the difference is large at bottleneck machines, it is a strong root cause of tardiness and unstable schedules.

---

## 3.5 Poor inter-work-center coordination

A job shop cannot be optimized by independently optimizing each machine.

Examples of poor coordination include:

- Releasing work to Cutting without considering Milling congestion.
- Completing large batches upstream that create downstream queue spikes.
- Scheduling an operation without confirming downstream capacity.
- Maximizing machine utilization even when it increases WIP.
- Producing non-critical jobs early while urgent jobs wait at bottlenecks.

Process mining can reveal cross-work-center dependencies through resource-flow analysis, queue propagation, and analysis of upstream/downstream starvation patterns.

---

## 3.6 Weak response to breakdowns and urgent jobs

Breakdowns and hot jobs are unavoidable, but their impact depends on how the schedule reacts.

Poor response patterns include:

- Immediate insertion of every hot job regardless of setup impact.
- No protected capacity at bottlenecks.
- No rescheduling after a breakdown.
- Rescheduling only the affected machine but not downstream operations.
- Repeatedly expediting the same jobs while neglecting others.
- No rules for deciding which jobs should be delayed after disruption.

The analysis should separate disruptions that are truly unavoidable from delays caused by ineffective recovery decisions.

---

## 3.7 Distinguishing scheduling-logic problems from capacity limitations

This distinction is essential.

### Evidence of a capacity limitation

A resource is likely capacity constrained if:

- It has sustained high productive utilization.
- Its queue remains high even under good sequencing.
- Demand exceeds available capacity over long periods.
- Its processing load cannot be absorbed within the planning horizon.
- Simulation shows persistent tardiness even with optimized scheduling.

Possible remedies include overtime, cross-training, subcontracting, faster machines, preventive maintenance, or process redesign.

### Evidence of poor scheduling logic

Scheduling logic is likely the main problem if:

- Similar demand periods produce very different performance outcomes.
- Machines have idle time while jobs wait elsewhere.
- High-cost setup transitions occur unnecessarily.
- Jobs are processed in an order inconsistent with due-date risk.
- Bottleneck resources are interrupted by low-value work.
- Simulation shows major improvement without adding capacity.
- Rescheduling decisions after disruptions create avoidable delays.

### Evidence of inherent process variability

Variability may be dominant if:

- Actual duration distributions are highly variable even under similar conditions.
- Breakdown occurrence is unpredictable and severe.
- Rework rates vary materially by product family.
- Material shortages or engineering changes are frequent.

In that case, robust scheduling, buffers, predictive models, and flexible capacity are more important than simply changing dispatching rules.

# 4. Advanced Data-Driven Scheduling Strategies

The following strategies should be treated as complementary. Precision Parts should not select one in isolation; the most effective future-state design may combine them.

---

## Strategy 1: Dynamic Multi-Factor Dispatching Rules

### Core logic

Replace FCFS/EDD with a dynamic dispatch score calculated whenever a machine becomes available or a major event occurs.

For each eligible job \(j\) at machine \(m\), calculate a priority score such as:

\[
Score_{jm} =
w_1 \cdot Urgency_j +
w_2 \cdot Priority_j +
w_3 \cdot DownstreamRisk_j +
w_4 \cdot RemainingWork_j -
w_5 \cdot SetupCost_{jm} -
w_6 \cdot QueueImpact_j
\]

Possible components include:

- **Due-date slack:** due date minus predicted remaining completion time.
- **Critical ratio:** time remaining until due date divided by remaining processing time.
- **Order priority:** customer/service class.
- **Remaining processing time:** short jobs may reduce WIP and improve flow.
- **Downstream bottleneck load:** avoid releasing jobs into already saturated resources unless necessary.
- **Estimated sequence-dependent setup time:** based on current machine state and candidate job family.
- **Predicted tardiness risk:** probability that the job will miss its due date.
- **Queue age:** prevent indefinite waiting or starvation.
- **Hot-job override:** but subject to explicit cost and impact rules.

A possible urgency component is:

\[
Urgency_j =
\frac{1}{\max(\epsilon, \text{Due Date}_j - \text{Predicted Completion}_j)}
\]

where \(\epsilon\) prevents division by zero for already late jobs.

### How process mining informs it

Process mining provides:

- Actual queue-time patterns by resource.
- Machine-specific bottleneck behavior.
- Historical processing-time distributions.
- Setup transition costs.
- Relationships between queue time and tardiness.
- Historic performance of priority classes.
- Effects of dispatch choices on downstream congestion.

The weighting factors should be calibrated using historical replay, optimization, or simulation rather than chosen solely by expert opinion.

### Pathologies addressed

- Poor due-date prioritization.
- Priority inversions.
- Failure to account for setup cost.
- Ignoring downstream congestion.
- Local optimization that increases total WIP.
- Excessive hot-job disruption.

### Expected impact

- Reduced weighted tardiness.
- Improved on-time delivery rate.
- Lower queue times at bottleneck resources.
- More stable WIP.
- Fewer unnecessary setups.
- Better customer-priority performance.

### Practical controls

The rule should include guardrails:

- Maximum allowed wait time to avoid starving low-priority jobs.
- Limits on hot-job insertion.
- Minimum batch size only where it does not create due-date risk.
- Frozen short-term schedule window for operations already in setup or processing.
- Event-triggered re-evaluation after breakdowns or major priority changes.

---

## Strategy 2: Predictive, Rolling-Horizon Scheduling

### Core logic

Use historical MES data to predict task duration, setup duration, breakdown risk, and job completion risk. Generate a rolling-horizon schedule that is updated whenever significant shop-floor conditions change.

Instead of assuming one deterministic duration, estimate a distribution:

\[
ProcessingTime \sim f(
\text{Machine},
\text{Product Family},
\text{Material},
\text{Complexity},
\text{Operator},
\text{Shift}
)
\]

Similarly:

\[
SetupTime \sim g(
\text{Previous State},
\text{Next State},
\text{Machine},
\text{Operator}
)
\]

The scheduler can then use robust or probabilistic constraints such as:

\[
P(C_j \leq d_j) \geq 0.90
\]

for high-priority jobs, meaning there should be at least a 90% probability that completion occurs before the due date.

The scheduling engine can use:

- Constraint programming.
- Mixed-integer optimization.
- Metaheuristics such as genetic algorithms or tabu search.
- Reinforcement learning only after extensive simulation and governance.
- Rolling-horizon heuristics for faster real-time decisions.

### Predictive models

Potential predictive models include:

- Task-duration regression models.
- Gradient-boosted trees or random forests for tardiness risk.
- Survival models for breakdown hazard.
- Classification models for quality/rework risk.
- Queue-delay prediction models.
- Machine-specific setup-time models.

The model output should be interpretable enough for supervisors to understand why a job is being prioritized.

### How process mining informs it

The event log supplies:

- Actual duration distributions.
- Routing variants.
- Breakdown frequencies and repair-time distributions.
- Setup transition history.
- Queue congestion patterns.
- Operator and shift effects.
- Rework probabilities.
- Historical recovery behavior after disruptions.

### Pathologies addressed

- Unrealistic deterministic schedules.
- Inaccurate processing and setup estimates.
- Failure to anticipate bottleneck congestion.
- Reactive rather than proactive handling of breakdowns.
- Poor visibility of at-risk jobs.

### Expected impact

- More realistic customer promise dates.
- Earlier identification of late-job risk.
- Reduced schedule volatility.
- Better recovery after disruptions.
- Improved due-date reliability.
- Reduced expediting and firefighting.

### Practical implementation

The scheduler should re-optimize on events such as:

- Machine breakdown or repair.
- New hot-job release.
- Major duration overrun.
- Setup completion significantly earlier or later than expected.
- Queue exceeding a control threshold.
- Operator absence.
- Material shortage resolution.

However, constant full rescheduling can create chaos. Use a rolling horizon with:

- A short frozen window, perhaps 1–4 hours.
- A flexible medium-term horizon, perhaps 1–5 days.
- A longer planning horizon for capacity and promise-date decisions.

## Strategy 3: Setup-Aware Sequencing and Intelligent Family Batching

### Core logic

For setup-sensitive resources, especially bottleneck machines, sequence jobs to minimize total setup time while respecting due dates and priority commitments.

This is not simple batching. It is a constrained sequencing problem:

\[
\min \left(
\alpha \cdot \text{Weighted Tardiness}
+
\beta \cdot \text{Total Setup Time}
+
\gamma \cdot \text{WIP}
\right)
\]

subject to:

- Machine capacity.
- Precedence constraints.
- Job release times.
- Due dates.
- Priority commitments.
- Tooling and operator availability.
- Non-preemption restrictions.
- Maximum allowable delay for lower-priority jobs.

The system should identify “compatible” job groups based on setup state. For example:

- Same material family.
- Same fixture.
- Same tool package.
- Similar program family.
- Similar heat-treatment recipe.
- Similar part diameter or thickness range.

### How process mining informs it

Historical sequence analysis provides:

- Setup transition matrix.
- Estimated transition time distributions.
- Frequent high-cost sequence changes.
- Setup-performance differences by operator.
- Families that naturally batch well.
- Families where batching causes due-date harm.
- Typical batch sizes and duration trade-offs.

### Pathologies addressed

- Excessive setup loss.
- Frequent A  B  A switching.
- Bottleneck capacity lost to avoidable setup.
- Hot-job insertion that destroys efficient sequences.
- Underestimation of setup impact.

### Expected impact

- Lower total setup time.
- Higher productive capacity at bottleneck machines.
- Better throughput.
- Lower queue time at setup-intensive work centers.
- Lower WIP and lead time.
- Improved due-date performance if sequencing is constrained by urgency.

### Important caution

Setup minimization alone can damage customer service. A pure family-batching rule may make a low-urgency family run efficiently while a near-due urgent job waits too long.

Therefore, batching should be governed by rules such as:

- Do not delay a job past a due-date risk threshold to avoid a setup.
- Permit sequence interruption only for high-value or high-risk jobs.
- Limit maximum batch duration.
- Re-evaluate the batch when urgent work enters the system.
- Protect capacity for high-priority work on bottlenecks.

## Strategy 4: Bottleneck-Controlled Release and Dynamic WIP Management

### Core logic

Introduce a shop-wide release control mechanism rather than releasing every job as soon as it is available.

A practical approach is a data-driven version of:

- **Drum-Buffer-Rope**, centered on the primary bottleneck.
- **CONWIP**, where total WIP is capped.
- **Workload Control**, where jobs are released only when downstream workload permits.

The bottleneck schedule acts as the “drum.” Upstream releases are timed to ensure that bottleneck capacity is fed without creating excessive queues.

### How process mining informs it

Historical analysis identifies:

- True bottleneck resources.
- Typical queue-time buffers needed before the bottleneck.
- WIP levels associated with good versus poor throughput.
- Release patterns causing downstream overload.
- Routing-dependent workload requirements.
- Starvation patterns at constrained machines.

### Pathologies addressed

- Excessive WIP.
- Upstream overproduction.
- Downstream starvation.
- Congestion caused by indiscriminate job release.
- Long and unpredictable lead times.

### Expected impact

- Lower total WIP.
- More stable lead times.
- Better bottleneck utilization.
- Reduced queue volatility.
- Improved throughput without necessarily adding capacity.
- More reliable due-date promises.

This strategy is especially useful if Precision Parts discovers that the primary problem is not only dispatching order, but excessive release of jobs into a capacity-constrained system.

# 5. Simulation, Evaluation, and Continuous Improvement

## 5.1 Build a process-mining-based discrete-event simulation model

Before changing live scheduling policy, Precision Parts should build a discrete-event simulation model calibrated from MES data.

The simulation should include:

- Actual routing variants.
- Job arrival patterns.
- Product mix.
- Processing-time distributions.
- Setup-time transition models.
- Machine calendars and shift patterns.
- Operator qualifications and availability.
- Breakdown frequency and repair-time distributions.
- Planned maintenance.
- Queue and buffer capacities.
- Rework loops.
- Priority changes.
- Hot-job arrivals.
- Material/tooling constraints where data is available.

Rather than using a single average duration, simulate distributions estimated from historical data.

For example:

\[
\text{Milling Duration} \sim \text{Lognormal}(\mu,\sigma)
\]

or a conditional empirical distribution based on product family and complexity.

Similarly, machine failures can be modeled using empirical failure distributions or hazard-based models.

---

## 5.2 Compare baseline and proposed policies

The model should compare:

1. Current FCFS/EDD hybrid.
2. Dynamic multi-factor dispatching.
3. Predictive rolling-horizon scheduling.
4. Setup-aware sequencing.
5. Bottleneck-controlled release.
6. Hybrid combinations of the above.

Each policy should be evaluated through many replications with confidence intervals.

### Key KPIs

- On-time delivery percentage.
- Weighted tardiness.
- Mean and P90 tardiness.
- Lead-time median and variability.
- WIP by work center.
- Queue-time percentiles.
- Throughput.
- Productive machine utilization.
- Setup time as a share of available time.
- Bottleneck utilization and starvation.
- Number of schedule changes.
- Number of hot-job interventions.
- Operator overtime.
- Service performance by priority class.
- Fairness for non-priority jobs.

A policy that reduces average tardiness but causes a small group of low-priority jobs to become extremely late should not automatically be accepted.

---

## 5.3 Test realistic disruption scenarios

The simulation should include stress tests such as:

### Normal operating conditions

- Typical job mix.
- Typical breakdown rates.
- Normal hot-job frequency.
- Current staffing levels.

### High-load scenario

- Demand 10–25% above normal.
- Higher bottleneck utilization.
- Large queue accumulation risk.

### Frequent breakdown scenario

- Increased failure rate on critical machines.
- Longer repair times.
- Simultaneous maintenance events.

### Hot-job surge scenario

- Multiple urgent customer jobs arriving in a short period.
- High-priority due-date compression.

### High setup-complexity scenario

- More product-family transitions.
- Greater mix variability.
- Larger setup-time uncertainty.

### Capacity-loss scenario

- Operator absence.
- Machine taken offline.
- Tooling shortage.
- Heat-treatment capacity reduction.

### Duration-underestimation scenario

- Actual durations systematically exceed planned durations.
- Higher variance in processing time.

The goal is not just to find the policy with the best average performance, but the one that remains robust under disruption.

---

## 5.4 Pilot deployment and shadow mode

Before full deployment:

1. Run the new scheduler in **shadow mode** for several weeks.
2. Let it generate recommendations without controlling the shop floor.
3. Compare its recommendations with actual dispatcher decisions.
4. Measure projected outcomes using replay and simulation.
5. Collect supervisor feedback on feasibility.
6. Identify constraints that were missing from the data model.
7. Deploy first to a limited work center or product family.
8. Use clear override rules for supervisors.

Human override should remain possible, but every override should be logged with a reason code. Those override events become valuable process-mining data for improving the scheduling model.

---

## 5.5 Continuous process-mining monitoring framework

The future-state system should continuously monitor both operational KPIs and process drift.

### Daily or shift-level operational dashboard

Track:

- Jobs at risk of tardiness.
- Current queue lengths by work center.
- Bottleneck state and expected next available time.
- WIP by priority class.
- Breakdown status.
- Hot-job impact.
- Setup transitions planned versus actual.
- Resource starvation and blocking.
- Schedule adherence.

### Weekly/monthly process-mining review

Track:

- Flow-time trends.
- Tardiness trends.
- Routing variant changes.
- Rework trends.
- Setup-time trend by transition.
- Breakdown rate changes.
- Operator/machine performance changes.
- Queue-time distribution shifts.
- Bottleneck migration from one resource to another.

### Drift detection

Automated alerts should trigger when there is meaningful change in:

- Actual versus predicted task duration.
- Actual versus predicted setup duration.
- Breakdown frequency or repair duration.
- Product mix.
- Routing behavior.
- Queue-time distribution.
- On-time delivery rate.
- Machine utilization profile.
- Tardiness probability calibration.

Examples of drift indicators include:

- A sustained increase in P90 milling duration.
- A new product family causing previously unseen setup transitions.
- Increased inspection rework.
- A bottleneck moving from Milling to Heat Treatment.
- A priority policy change creating excessive disruption to normal jobs.

When drift is detected, the company should:

1. Revalidate the root cause.
2. Retrain predictive models if necessary.
3. Recalibrate dispatch weights.
4. Update setup matrices.
5. Re-run simulation under the new conditions.
6. Adjust release limits, batching rules, or capacity plans.

# Recommended Implementation Sequence

A practical implementation roadmap would be:

### Phase 1: Data and diagnostic foundation

- Clean and standardize MES event logs.
- Build job, operation, resource, and disruption timelines.
- Develop dashboards for queue time, WIP, utilization, setup, and tardiness.
- Identify bottlenecks and major late-job patterns.
- Quantify setup transition costs.

### Phase 2: Simulation and policy design

- Build a discrete-event simulation model.
- Test dynamic dispatching, setup-aware sequencing, and bottleneck release control.
- Calibrate rules using historical replay and simulation.
- Select policy combinations by KPI performance and robustness.

### Phase 3: Controlled deployment

- Operate in shadow mode.
- Pilot at the most impactful bottleneck or a contained product family.
- Train dispatchers and supervisors.
- Establish override governance and feedback capture.

### Phase 4: Predictive and adaptive scheduling

- Add duration and tardiness prediction.
- Add breakdown-risk and setup-time prediction.
- Implement rolling-horizon rescheduling.
- Continuously monitor process drift and revise policy parameters.

# Conclusion

Precision Parts’ scheduling problem is not simply a matter of choosing a better dispatching rule. It is a system-level problem involving variable routings, sequence-dependent setups, bottleneck capacity, unpredictable disruptions, competing priority classes, and poor coordination between work centers.

Process mining provides the factual basis for understanding how the shop actually behaves: where jobs wait, how machines are sequenced, how disruptions propagate, which routing variants cause delays, and which resources truly constrain flow. That evidence should then drive a combination of dynamic dispatching, predictive scheduling, setup-aware sequencing, and bottleneck-controlled WIP release.

The expected result is not merely higher machine utilization. The target state is more reliable due-date performance, lower and more stable WIP, reduced setup losses, fewer schedule firefights, more predictable lead times, and better use of constrained shop-floor capacity.
