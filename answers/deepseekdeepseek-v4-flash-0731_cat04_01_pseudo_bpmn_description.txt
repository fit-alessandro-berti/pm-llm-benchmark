The pseudo-BPMN represents a **customer request handling process** for what appears to be a sales, quotation, or order-delivery workflow. It handles two main request types — **standard** and **custom** — and includes parallel work, decision points, and a possible approval/rework loop.

Below is a detailed explanation of the process.

---

## 1. Overall Business Process Purpose

The process starts when a customer submits a request and ends either:

- With a **successful outcome**: a final invoice is generated and a confirmation is sent to the customer, or
- With a **rejection outcome**: a custom request that is not feasible receives a rejection notice.

So the process covers:

- Request intake
- Standard vs custom classification
- Validation / feasibility assessment
- Parallel checks
- Delivery date or quotation creation
- Managerial approval, if required
- Final invoicing and customer confirmation

---

## 2. Step-by-Step Walkthrough

### Start Event  Task A: “Receive Customer Request”

The process begins when a customer request arrives.

**Task A** captures the initial request details, such as:

- Customer identity
- Requested product or service
- Quantity
- Special requirements
- Contact and delivery information

This is the entry point of the process.

---

### Gateway: “Check Request Type” – XOR

This is an **exclusive gateway**. It means **only one path is taken**, based on whether the request is **standard** or **custom**.

- If the request is **Standard**  the process follows the standard path.
- If the request is **Custom**  the process follows the custom path.

---

## 3. Standard Path

### Task B1: “Perform Standard Validation”

This step validates the standard request against normal business rules.

Example checks:

- Is the request complete?
- Are the requested items part of the standard catalogue?
- Are the quantities realistic?
- Are all required documents provided?

If validation passes, the process continues.

---

### Gateway (AND): “Run Parallel Checks”

This is a **parallel gateway**, also called an **AND fork**.

It does **not** choose between paths. Instead, it **splits the process into two concurrent flows**. This means both checks happen at the same time.

---

### Task C1: “Credit Check”

This checks the customer’s creditworthiness.

Purpose:

- Determine whether the customer has good enough credit to proceed.
- Identify payment risk.
- Possibly define payment terms or limits.

---

### Task C2: “Inventory Check”

This checks whether the requested products are available.

Purpose:

- Confirm stock availability.
- Identify whether items need to be back-ordered.
- Help calculate a realistic delivery date.

---

### “All Parallel Checks Completed” – AND Join

After C1 and C2 finish, the two flows must **wait for both to complete**.  
This is an **AND join**: the process continues only after **both** the credit check and inventory check are finished.

---

### Task D: “Calculate Delivery Date”

Using the results of the credit check and inventory check, the process calculates an expected delivery date.

For example:

- If inventory is available and credit is approved, the delivery date may be soon.
- If inventory is low or credit is uncertain, the delivery date may be later or subject to conditions.

This task completes the standard path.

---

## 4. Custom Path

### Task B2: “Perform Custom Feasibility Analysis”

For custom requests, the process first checks whether the request is technically and commercially feasible.

This may involve:

- Engineering or design review
- Cost estimation
- Resource availability
- Supplier feasibility
- Risk assessment

---

### Gateway: “Is Customization Feasible?” – XOR

This is another **exclusive gateway**. Only one branch is chosen.

---

#### If Yes  Task E1: “Prepare Custom Quotation”

If the custom request can be fulfilled, the process prepares a formal quotation.

The quotation typically includes:

- Price
- Delivery timeline
- Technical description of the custom work
- Payment terms

---

#### If No  Task E2: “Send Rejection Notice”  End Event

If the custom request is not feasible, the customer is sent a rejection notice, and the process **ends**.

This is a terminating path. No invoice, approval, or confirmation is generated.

---

## 5. Converging Point: “After Standard or Custom Path Tasks Completed”

After either:

- Task D (standard path), or
- Task E1 (custom path)

...the successful paths converge at a shared continuation point.

This is where the process asks:

> Is approval needed?

In proper BPMN, this point should be an explicit merge/join before the approval gateway. Conceptually, it joins the standard and custom feasible paths into one common flow.

---

## 6. Approval and Rework Logic

### Gateway: “Is Approval Needed?” – XOR

This is a decision point that asks whether managerial approval is required.

Approval may be needed because of:

- High order value
- Discounts or special pricing
- Non-standard terms
- Elevated credit risk
- Unusual delivery conditions

The exact condition is not specified in the pseudo-model, but it is an **exclusive choice**:

- If **No approval needed**  the process jumps directly to Task G: “Generate Final Invoice”.
- If **Yes, approval is needed**  the process moves to Task F.

---

### Task F: “Obtain Manager Approval”

A manager reviews the request and makes a decision.

The manager might consider:

- The credit check result
- The delivery date
- The custom quotation
- Profitability
- Customer importance

---

### Gateway: “Is Approval Granted?” – XOR

After the manager’s decision, the process branches again:

- If **Yes**  approval is granted  move to Task G.
- If **No**  approval is rejected  move to Task H.

---

### Task H: “Re-evaluate Conditions”

This task is a **rework step**. It is triggered only when:

- Approval was needed, and
- The manager did not approve the request.

The purpose is to adjust the conditions so that the request can become approvable.

Examples:

- Change the delivery date
- Adjust the quotation price
- Modify custom scope
- Offer different payment terms
- Recalculate feasibility assumptions

After re-evaluation, the flow loops back to:

- **Task D** for standard requests  
   to recalculate the delivery date.
- **Task E1** for custom requests  
   to prepare a revised custom quotation.

Then the process flows again to the approval decision. This creates an **approval/rework loop**.

---

### Important note on the loop

As written, the loop can repeat if the manager keeps rejecting the updated conditions.

The pseudo-BPMN does not define:

- A maximum number of attempts
- An escalation path
- A final rejection step after repeated failed approvals

In a real process, you would likely add a condition such as:

- “After 3 attempts, send final rejection”
- Or “Escalate to senior management”
- Or “Allow customer to cancel”

---

## 7. Final Invoice and Customer Confirmation

### Task G: “Generate Final Invoice”

This is reached either:

- Directly when no approval is needed, or
- After the manager approves the request.

The invoice is the commercial commitment to the customer.

---

### Task I: “Send Confirmation to Customer”

After the invoice is generated, the customer receives a confirmation.

This confirms:

- The order or quotation has been accepted
- The invoice has been issued
- The delivery date or custom solution is confirmed

---

### End Event

The process ends after the confirmation is sent.

---

## 8. Summary of Gateways

| Gateway | Type | Meaning |
|---|---|---|
| Check Request Type | XOR | Choose either standard or custom path, not both |
| Run Parallel Checks | AND | Fork: run credit check and inventory check simultaneously |
| All Parallel Checks Completed | AND join | Wait for both checks to finish |
| Is Customization Feasible? | XOR | Choose between preparing a quotation or sending rejection |
| Is Approval Needed? | XOR | Choose whether manager approval is required |
| Is Approval Granted? | XOR | Choose whether to proceed to invoicing or re-evaluate conditions |

---

## 9. Standard vs Custom Paths – Key Differences

| Aspect | Standard Request | Custom Request |
|---|---|---|
| Initial task | Perform Standard Validation | Perform Custom Feasibility Analysis |
| Parallel checks | Credit Check + Inventory Check | Not shown in the custom path |
| Output | Calculate Delivery Date | Prepare Custom Quotation |
| Possible early rejection | Not shown | Yes, if customisation is not feasible |
| Approval loop target | Task D | Task E1 |

So a standard request is a more routine, repeatable process.  
A custom request is more analytical and may end early if it is not feasible.

## 10. Potential BPMN Issues / Improvements

The pseudo-model is useful, but it has a few points that should be clarified in a real BPMN diagram:

1. **“After Standard or Custom Path Tasks Completed”** is not a standard BPMN element.  
   It should be an explicit merge/join gateway.

2. The **AND join** after the parallel checks should be shown as a proper AND gateway.

3. The **loop back** from Task H should be conditional:
   - If the original request was standard  go to Task D.
   - If it was custom  go to Task E1.

4. There is no **exit condition** for the approval/rework loop.  
   This could cause an infinite loop if the manager keeps rejecting.

5. The custom path does not include credit or inventory checks in the pseudo-model.  
   If custom requests also need these checks, the model should include them.

---

## Final Summary

The process is a **request-to-invoice workflow** with:

- A decision between standard and custom handling
- Parallel credit and inventory checks for standard requests
- A feasibility check for custom requests
- An optional managerial approval step
- A rework loop when approval is denied
- A final invoice and customer confirmation for successful requests
- A rejection notice for infeasible custom requests

The gateways make the process **flexible**: XOR gateways allow the process to choose one path, while AND gateways allow independent checks to happen in parallel. The approval loop ensures that rejected requests are not simply discarded; they are re-evaluated and potentially revised before being resubmitted for approval.
