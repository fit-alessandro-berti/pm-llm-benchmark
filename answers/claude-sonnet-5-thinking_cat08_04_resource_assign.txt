# TechSolve Solutions: Data-Driven Resource Assignment Optimization

## Section 1: Analyzing Resource Behavior and Assignment Patterns

### 1.1 Individual Agent and Tier Performance Metrics

**Workload Distribution Metrics:**
- **Ticket volume per agent/day-week**: Count of `Assign` events per Agent ID, segmented by tier
- **Concurrent ticket load**: At any timestamp, count of tickets in "Work Start" but not yet "Work End" per agent
- **Work-in-Progress (WIP) time series**: Plot WIP per agent over time to detect overload periods
- **Utilization rate**: (Sum of Work Start-to-End duration) / (Total shift/available time)

**Processing Time Metrics:**
- **Activity duration per agent**: `Work [Tier] End timestamp - Work [Tier] Start timestamp`, segmented by:
  - Priority (P1-P4)
  - Category
  - Required Skill
- **Queue time (waiting)**: `Work Start timestamp - Assign timestamp` — reveals dispatcher/queue delays
- **Total ticket lifecycle time**: `Last activity - Ticket Created`, broken down by tier contribution

**First-Call Resolution (FCR) Rate:**
- For L1: Count of cases where `Work L1 End` is immediately followed by `Ticket Closed` (no escalation) ÷ Total L1-handled tickets
- Segment FCR by agent, by category, and by required skill to identify which agents/skill areas have low FCR (candidates for training or skill-gap issues)

**Skill-Ticket Alignment Frequency:**
- Cross-tabulate `Agent Skills` vs. `Required Skill` for each assignment
- Calculate **Skill Match Rate** = (Assignments where Required Skill  Agent Skills) / Total Assignments
- Track how often agents work outside their documented skill set (indicates skill profile gaps or emergency overrides)

### 1.2 Process Mining Techniques for Actual vs. Intended Patterns

**Resource-Activity Matrix (Discovery):**
Build a matrix of Agents × Activities to reveal:
- Which agents perform which activities most frequently
- Deviations from the "intended" tier boundaries (e.g., L2 agents doing L1-type basic troubleshooting)

**Handover-of-Work Social Network Analysis (SNA):**
- Construct a directed graph where nodes = agents/tiers, edges = handover frequency (Agent A  Agent B via Escalate/Reassign)
- **Edge weight** = frequency; **edge attribute** = average delay introduced by that handover
- This reveals:
  - **Escalation hubs**: Specific L1 agents who escalate almost everything (possible skill/confidence gap)
  - **Ping-pong patterns**: Ticket bouncing between two agents/tiers repeatedly (e.g., L2L2 reassignment due to skill mismatch, as seen in INC-1001: B12B15)
  - **Bypass patterns**: Direct L1L3 escalations skipping L2 (may indicate correctly identified complexity, or L2 avoidance)

**Role Discovery / Organizational Mining:**
- Apply clustering (e.g., correlation-based role mining) on the Agent × Activity matrix to discover *de facto* roles
- Compare discovered roles against documented tier/skill assignments
- **Mismatch indicator**: If clustering reveals an L2 agent behaving like an L1 generalist, this signals misallocation

**Comparing Actual vs. Intended Logic:**
- Intended: Round-robin within tier + skill-based escalation
- Actual test: For a sequence of tickets requiring "Networking-Firewall," check if assignment order follows round-robin (sequential Agent IDs) or skews toward specific agents — deviations indicate informal "shadow routing" (e.g., dispatchers manually favoring known-good agents, bypassing round-robin)

### 1.3 Skill Utilization Analysis

**Over-qualification Detection:**
- For each L2/L3 assignment, compare `Required Skill` complexity/rarity against `Agent Skills` breadth
- Flag cases where a multi-skilled specialist (e.g., "App-CRM, DB-SQL, Security-IAM") is assigned to a ticket resolvable by a single-skill L1/L2 generalist
- **Specialist Utilization Index** = (Time spent on tickets matching top-tier skill) / (Total time logged) — low index signals misuse of scarce expertise

**Skill Scarcity Analysis:**
- Count agents possessing each skill tag across the entire pool
- Cross-reference with ticket volume requiring that skill
- **Skill Coverage Ratio** = (Number of agents with Skill X) / (Ticket volume requiring Skill X per week)
- Skills with low ratios (e.g., only 2 agents know "Database-SQL" but it's required in 15% of P2 tickets) are structural bottleneck candidates

## Section 2: Identifying Resource-Related Bottlenecks and Issues

### 2.1 Bottleneck Identification Methods

**A. Skill Scarcity Bottlenecks**
- Filter cases where `Work [Tier] Start` is significantly delayed after `Assign`
- Correlate delay duration with `Required Skill`
- **Finding pattern**: If "Networking-Firewall" and "Database-SQL" tickets show consistently longer queue times (AssignStart gap) than "Basic-Troubleshoot" tickets, this confirms a skill-availability bottleneck

**B. Reassignment/Escalation Delay Impact**
- For every `Reassign` or `Escalate` event, calculate the time delta to the *next* `Work Start`
- **Reassignment Penalty** = Average(Time between Escalate/Reassign event and subsequent Work Start)
- Using the INC-1001 example: Escalate L2 (09:36:00)  Work L2 Start (10:05:50) = **29 min 50 sec** queue delay just from escalation handling — multiply this pattern across all escalated tickets to quantify systemic cost

**C. Incorrect Initial Assignment Impact**
- Identify cases with **multiple escalations within the same tier** (e.g., L2L2 reassignment as in INC-1001, B12B15) — this indicates the *first* L2 assignment didn't match the actual required skill (App-CRM vs. Database-SQL)
- **Misrouting Rate** = (Cases with >1 assignment at the same tier) / (Total cases reaching that tier)

**D. Overloaded/Underutilized Agent Detection**
- Plot WIP-over-time per agent; agents with sustained WIP above 90th percentile = overloaded
- Agents with WIP below 10th percentile despite matching skills available in the queue = underutilized
- Cross-reference with escalation-target frequency (SNA) — if overloaded agents are also the most frequent escalation targets, this creates a reinforcing bottleneck loop

**E. SLA Breach Correlation**
- Tag each case as SLA-met/SLA-breached (based on Priority-specific SLA thresholds)
- Run a **decision tree or logistic regression** with breach as target variable and features:
  - Number of reassignments
  - Number of escalations
  - Skill match at first assignment (Y/N)
  - Assigned agent's tier/queue load at assignment time
  - Category/Required Skill
- This produces **feature importance rankings** quantifying which resource factors most predict breaches

### 2.2 Quantification Examples (Illustrative Methodology)

| Metric | Calculation | Hypothetical Insight |
|---|---|---|
| Avg delay per reassignment | Mean(Time to next Work Start post-reassignment) | 32 min average delay per reassignment event |
| % SLA breaches with skill mismatch | Breached cases with skill-mismatch flag / Total breaches | 47% of P2 breaches involved 1 skill mismatch |
| Escalation-driven delay contribution | Sum(escalation delays) / Total case duration | Escalation handling adds ~18% to average P3 lifecycle time |
| Specialist misuse rate | L2/L3 tickets resolvable by L1 (based on activity complexity proxy) / Total L2/L3 tickets | 22% of L3 "Database-SQL" tickets involved only basic query fixes |

## Section 3: Root Cause Analysis for Assignment Inefficiencies

### 3.1 Hypothesized Root Causes

1. **Round-robin ignoring skill/workload**: Confirmed if SNA shows sequential/cyclic assignment patterns uncorrelated with `Required Skill` match rates or current WIP
2. **Inaccurate skill profiles**: If Agent Skills field rarely updates but reassignment reasons frequently cite "needs different skill" (as in INC-1001 notes), the documented profile is likely stale or incomplete
3. **Poor initial categorization**: If `Required Skill` value at ticket creation frequently changes between first and second assignment at the same tier (e.g., App-CRM  Database-SQL), root cause lies in **triage/categorization accuracy**, not agent competence
4. **Lack of real-time visibility**: If dispatcher assignments show no correlation with agent's current WIP (i.e., busy agents keep receiving new tickets), this confirms dispatchers lack live workload data
5. **L1 under-empowerment**: If FCR is low specifically for categories where required troubleshooting complexity is objectively low (e.g., password resets under Access Management), root cause may be insufficient L1 training/permissions rather than genuine complexity

### 3.2 Variant Analysis

- Use a process discovery algorithm (e.g., Inductive Miner, Fuzzy Miner) to extract **case variants** based on activity sequences
- **Segment variants into:**
  - **Smooth-flow variants**: Created  Assign  Work Start  Work End  Closed (single tier, no reassignment)
  - **Complex variants**: Multiple Escalate/Reassign loops
- **Compare attribute distributions** between the two groups:
  - Do complex variants correlate with specific dispatchers, specific initial categorization errors, specific times of day (shift changes?), or specific ticket categories?
- This comparison isolates *which conditions* precede inefficient paths — e.g., "P3 Software-App tickets created after 5 PM show 3x more reassignment loops"  points to shift-handover root cause

### 3.3 Decision Mining

- Treat each `Assign` decision point as a classification problem
- Input features at decision time: Ticket Priority, Category, Required Skill, current agent workloads/availability, time of day
- Output: Which agent/tier was chosen
- Train a decision tree to **replicate the assignment logic actually used**
- **Compare discovered rules to policy documentation**: If the tree splits primarily on "Agent ID modulo N" (round robin) rather than skill/workload features, this empirically proves the round-robin bias
- Additionally, build a *second* decision tree predicting **optimal assignment** (i.e., which assignment historically led to fastest resolution/no reassignment) — the gap between actual and optimal trees defines the improvement opportunity

## Section 4: Data-Driven Resource Assignment Strategies

### Strategy 1: Proficiency-Weighted Skill-Based Routing

**Issue Addressed**: Skill mismatches causing reassignments (Section 2C) and specialist misuse (Section 1.3)

**Process Mining Insight Leveraged**: Skill Match Rate analysis and Specialist Utilization Index reveal that binary skill-tagging (has/doesn't have) is insufficient — need proficiency levels

**Mechanism**:
- Extend agent skill profiles from binary tags to a **proficiency matrix** (e.g., Novice/Intermediate/Expert per skill), derived retroactively from historical resolution time and reassignment-avoidance data per agent per skill
- Route tickets by matching `Required Skill` to the *minimum sufficient proficiency level* (avoid over-assigning experts to simple tickets)
- Implement a **skill-decay/reinforcement model**: proficiency scores update based on ongoing resolution outcomes

**Data Required**:
- Historical resolution time and FCR outcomes segmented by agent-skill pairs
- Real-time required-skill tagging (improved via NLP on ticket descriptions — see Strategy 3)

**Expected Benefits**:
- Reduced within-tier reassignment rate (target: cut misrouting rate identified in 2.1C by 50%+)
- Better utilization of scarce specialists (raise Specialist Utilization Index)

---

### Strategy 2: Real-Time Workload-Aware Dynamic Assignment

**Issue Addressed**: Uneven workload distribution, overloaded agents becoming escalation bottlenecks (Section 2D)

**Process Mining Insight Leveraged**: WIP time-series analysis and SNA showing escalation targets are frequently the same overloaded agents

**Mechanism**:
- Replace static round-robin with an algorithm that scores each eligible agent using:
  `Score = w1*(SkillMatch) + w2*(1/CurrentWIP) + w3*(AvgHistoricalResolutionSpeed for this ticket type) - w4*(RecentEscalationBurden)`
- Assign to highest-scoring available agent
- Set dynamic caps on concurrent WIP per agent tier, triggering automatic queue redistribution when thresholds are breached

**Data Required**:
- Live WIP counters (requires real-time event stream, not just batch log)
- Historical resolution speed benchmarks per agent-category combination

**Expected Benefits**:
- Flatten workload distribution curve (reduce variance in WIP across agents)
- Reduce SLA breaches tied to queue delays (target reduction proportional to the AssignStart gap identified in 2.1A)

---

### Strategy 3: Predictive Triage & Auto-Categorization at Ticket Creation

**Issue Addressed**: Poor initial categorization causing skill mismatches discovered only after L1/L2 handling (Section 2C, Root Cause 3.1.3)

**Process Mining Insight Leveraged**: Frequent `Required Skill` changes between first and second assignment at same tier; correlation between category-creation accuracy and downstream reassignment loops (from variant analysis)

**Mechanism**:
- Train an ML classifier (using historical Category, free-text description, and eventual *actual* Required Skill as labels) to predict true required skill and complexity tier **at ticket creation**, before human triage
- Route P1/P2 tickets directly to correctly-skilled L2/L3 pool when model confidence is high, bypassing unnecessary L1 touch (reducing escalation delay for genuinely complex tickets)
- Flag low-confidence predictions for manual dispatcher review

**Data Required**:
- Historical ticket descriptions with confirmed final Required Skill (ground truth from resolved tickets)
- Feedback loop to retrain model as new resolutions occur

**Expected Benefits**:
- Fewer escalation cycles for inherently complex tickets (cut top-tier reassignment rate)
- Faster time-to-correct-resource for high-priority tickets, directly improving P1/P2 SLA compliance

---

### Strategy 4: Evidence-Based L1 Escalation Criteria Refinement

**Issue Addressed**: Excessive/premature L1 escalations reducing FCR (Section 1.1, Root Cause 3.1.5)

**Process Mining Insight Leveraged**: FCR segmented by category shows specific categories with abnormally low L1 resolution despite low objective complexity (per resolution time distribution analysis)

**Mechanism**:
- Mine successful L1 resolution patterns (activity sequences, time spent, sub-steps) for categories currently over-escalated
- Build **decision-support checklists or automated diagnostic scripts** embedded in L1 tooling for these categories, based on the mined successful-resolution playbooks
- Set category-specific escalation thresholds (e.g., "attempt X standard steps before escalating") rather than agent discretion alone

**Data Required**:
- Detailed sub-activity logs of successful vs. escalated L1 attempts for the same category
- L1 agent training records (to correlate with performance)

**Expected Benefits**:
- Raised FCR rate in targeted categories
- Reduced L2/L3 inbound volume, freeing specialist capacity (compounds benefits of Strategy 1)

## Section 5: Simulation, Implementation, and Monitoring

### 5.1 Simulation Approach

**Model Construction**:
- Use the process model discovered via Inductive/Fuzzy Miner as the **control-flow backbone**
- Enrich with **resource simulation parameters** extracted from the log:
  - Agent-specific service time distributions (per activity, per skill)
  - Arrival rate patterns (tickets per hour/day, by priority/category, including seasonality)
  - Current vs. proposed assignment logic as configurable routing rules

**Simulation Tooling**: CPN Tools, ProM's simulation plugins, or commercial suites (Celonis Action Flows simulation, Signavio Process Simulator) parameterized with the above.

**Experiments to Run**:
1. **Baseline replay**: Validate the simulation reproduces current SLA breach rates and reassignment frequencies (calibration check)
2. **What-if Strategy 1 (skill-weighted routing)**: Replace routing logic, measure simulated reassignment rate and resolution time changes
3. **What-if Strategy 2 (workload-aware)**: Inject live WIP-based scoring, measure workload variance and SLA compliance under peak-load scenarios
4. **Combined strategy stress test**: Run all strategies together under simulated demand spikes (e.g., simulate a P1 surge) to check for unintended bottlenecks (e.g., does workload-awareness undermine skill-matching under pressure?)
5. **Sensitivity analysis**: Vary weighting parameters (w1-w4 in Strategy 2's scoring function) to find optimal balance before live deployment

**Output**: Projected KPI deltas (expected SLA compliance %, reassignment rate reduction, agent utilization balance) with confidence intervals, forming the business case for rollout.

### 5.2 Post-Implementation Monitoring Plan

**Dashboard Architecture** (built on continuous process mining platform, e.g., Celonis/Disco/ProM feeding from live event stream):

**Tier 1 — Executive KPIs (weekly view):**
- SLA compliance rate by Priority (P1-P4), trended pre/post implementation
- Overall reassignment rate (target: sustained reduction trend)
- Average end-to-end resolution time by category

**Tier 2 — Operational KPIs (daily/real-time view):**
- Live WIP heatmap per agent/tier (flag overload in real time)
- Skill Match Rate at first assignment (target >90%)
- Escalation rate by category (watch for Strategy 4 impact)
- Queue time (AssignStart) distribution per skill category

**Tier 3 — Model Health / Drift Monitoring:**
- Predictive triage model accuracy (Strategy 3) — precision/recall on skill prediction, retrained monthly
- Proficiency score drift per agent (Strategy 1) — ensure scores stay current with actual performance
- Routing algorithm override frequency (how often dispatchers manually override automated assignment — high override rates signal algorithm miscalibration)

**Continuous Feedback Loop**:
- Monthly variant analysis re-run to check whether new "problem variants" (e.g., new ping-pong patterns) emerge under the new logic
- Quarterly SNA re-run to confirm handover patterns have flattened (fewer hub-and-spoke overload patterns)
- A/B comparison capability retained for at least 2 quarters (route a control-group percentage through old logic) to statistically validate sustained improvement versus natural variation

**Governance**: Establish an alert threshold system — e.g., if weekly reassignment rate exceeds a control limit, trigger automatic root-cause variant analysis re-run rather than waiting for scheduled review.
