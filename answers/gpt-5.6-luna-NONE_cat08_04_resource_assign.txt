# 1. Analyzing Resource Behavior and Assignment Patterns

## 1.1 Prepare the event log for resource analysis

The primary case identifier is the ticket ID. Each event should contain, where available:

- Timestamp
- Activity
- Agent or resource
- Agent tier
- Agent skill and proficiency
- Ticket priority and category
- Required skill
- Assignment source: dispatcher, self-assignment, automated routing
- Assignment start and end times
- Escalation and reassignment reason
- SLA target and breach status
- Channel and complexity indicators
- Resolution outcome

Before analysis, the log should be normalized so that:

- `Work Start` and `Work End` events can be paired reliably.
- Assignment waiting time is separated from active handling time.
- Escalations and reassignments are distinguishable.
- Agent changes are represented as handovers.
- Skill requirements are captured at both creation and subsequent reassignment.
- Missing, contradictory, or stale agent-skill data is identified.

The result should support both a standard process-mining view and resource-aware analysis.

---

## 1.2 Agent and tier performance metrics

### Workload distribution

For each agent and tier, calculate:

- Number of tickets assigned
- Number of tickets actively worked
- Number of open tickets at any point in time
- Concurrent workload
- Work hours by priority and category
- Queue time before work starts
- Active handling time
- Total elapsed resolution time
- Percentage of work performed outside the agent's primary tier
- Overtime, after-hours, and shift coverage

Workload should be measured using both ticket counts and effort-weighted workload. For example, one complex P1 incident may represent more demand than several simple P4 requests.

Useful indicators include:

\[
\text{Utilization} =
\frac{\text{productive handling time}}{\text{available working time}}
\]

and:

\[
\text{Workload imbalance} =
\frac{\text{agent workload}}{\text{average workload of comparable agents}}
\]

This should be segmented by shift, day of week, priority, and skill.

### Speed and productivity

For each agent and tier:

- Mean and median time to accept
- Time from assignment to work start
- Active handling time
- Time between work periods
- Average resolution time
- Tickets completed per working hour
- Queue age at assignment
- SLA attainment rate

Median and percentile values are more useful than averages because a small number of long-running tickets can distort the mean.

### Quality and effectiveness

For L1, particularly important metrics are:

- First-call or first-contact resolution rate
- Percentage escalated to L2 or L3
- Escalation rate by category, priority, and agent
- Reopen rate
- Repeat-contact rate
- Correct escalation rate
- Percentage of tickets escalated after avoidable delay
- Percentage of tickets requiring reassignment after escalation

For L2 and L3:

- Resolution rate after first specialist assignment
- Reassignment rate
- Specialist queue waiting time
- Resolution time by skill
- Percentage of work that could have been handled by L1
- Percentage of tickets returned to a previous tier

The analysis should avoid treating a high escalation rate as automatically negative. Some L1 agents may receive more complex tickets. Escalation rates should therefore be risk-adjusted for priority, category, complexity, and required skill.

---

## 1.3 Ticket and skill handling patterns

Create a matrix of:

- Agent versus ticket category
- Agent versus required skill
- Tier versus required skill
- Priority versus assigned tier
- Skill versus resolution time
- Skill versus reassignment rate
- Skill versus SLA breach rate

For example, a skill utilization matrix might show that:

- Agent B12 handles many CRM tickets but is frequently reassigned when database work is required.
- Agent B15 resolves Database-SQL tickets quickly but receives them late in the lifecycle.
- L1 agents are frequently assigned tickets requiring Networking-Firewall skills despite lacking those skills.
- L2 specialists spend significant time on routine password or endpoint tasks.

A useful measure is the skill-fit ratio:

\[
\text{Skill-fit ratio} =
\frac{\text{tickets assigned to an agent with the required skill}}
{\text{all tickets assigned to that agent}}
\]

This can be refined by proficiency:

\[
\text{Weighted skill fit} =
\frac{\sum \text{proficiency score for assigned skill}}
{\text{number of assignments}}
\]

Also calculate specialist utilization:

\[
\text{Specialist utilization on appropriate work} =
\frac{\text{specialist time spent on tickets requiring specialist skills}}
{\text{total specialist productive time}}
\]

This identifies both underuse of specialists and inappropriate use of their time.

## 1.4 Process mining views of resource behavior

### Directly follows graphs and performance maps

A process model can be filtered by:

- Agent
- Tier
- Category
- Priority
- Required skill
- Assignment source
- SLA outcome

The model will show paths such as:

`Ticket Created  Assign L1  Work L1  Escalate L2  Assign L2  Work L2`

It may also expose undesirable variants such as:

`Assign L1  Work L1  Assign L2  Reassign  Assign L2  Reassign  Assign L3`

Coloring transitions by waiting time or SLA breaches helps identify where resource decisions create delay.

### Resource interaction and handover analysis

Construct a handover network in which:

- Nodes represent agents, teams, or tiers.
- Edges represent transfers of tickets.
- Edge weight represents number of transfers, elapsed time, or breach impact.

This can reveal:

- Agents who act as escalation hubs
- Recurrent handovers between the same agents
- Excessive L1-to-L2 transfers
- Tickets moving backward between tiers
- Teams that receive work but have long waiting times
- Informal routing patterns not represented in the official process

For example, if many tickets move from L1 to B12 and then from B12 to B15, this suggests that the initial skill requirement is not being identified correctly.

### Social network analysis

Social network measures include:

- In-degree: how many tickets an agent receives from others
- Out-degree: how many tickets an agent hands over
- Betweenness centrality: whether an agent acts as a routing bottleneck
- Network density: how complex the handover structure is
- Average number of handovers per case
- Handover concentration by agent or team

A high-betweenness specialist may be a critical bottleneck even if their total ticket volume appears reasonable.

### Role discovery and organizational mining

Role discovery can identify actual operational roles, such as:

- First-line triage agents
- Queue coordinators
- CRM specialists
- Firewall specialists
- Approval or access-management agents
- Informal escalation coordinators

This can be compared with the formal L1/L2/L3 structure and documented responsibilities. If an L1 agent routinely performs L2 work, or a dispatcher frequently makes technical decisions, the actual organization differs from the intended operating model.

### Conformance checking

Compare observed assignments with intended rules, for example:

- P1 tickets must be assigned to an available qualified agent.
- Networking-Firewall tickets should go to agents with the firewall skill.
- L1 should attempt defined basic troubleshooting before escalation.
- Tickets should not be reassigned more than once without a documented reason.

Conformance deviations can be categorized as:

- Skill mismatch
- Incorrect tier
- Excessive waiting before assignment
- Unauthorized self-assignment
- Missing escalation rationale
- Repeated assignment to unavailable or overloaded agents

# 2. Identifying Resource-Related Bottlenecks and Issues

## 2.1 Skill-capacity bottlenecks

For each skill, compare demand with capacity:

\[
\text{Skill load ratio} =
\frac{\text{required effort for the skill}}
{\text{available qualified capacity}}
\]

This should be calculated by time interval, not just annually. A skill may appear adequately staffed in aggregate while being unavailable during evenings or peak periods.

Indicators include:

- Number of qualified agents by shift
- Demand by skill and hour
- Queue time for each skill
- Backlog age
- Assignment failure rate
- Number of tickets awaiting a qualified resource
- SLA breach rate by required skill

A high queue time for Networking-Firewall tickets combined with low qualified capacity would suggest a genuine skill bottleneck. A high queue time with many qualified but idle agents would instead indicate a routing or visibility problem.

---

## 2.2 Reassignment and escalation delays

For every reassignment, calculate:

- Time from previous work end to reassignment
- Time from reassignment to next work start
- Number of reassignments per case
- Total delay attributable to transfers
- Whether the new agent had a missing skill
- Whether the reassignment changed tier, team, skill, or only individual agent

A ticket-level transfer delay can be calculated as:

\[
\text{Transfer delay} =
\text{next work start}
-
\text{previous work end}
\]

Aggregate:

\[
\text{Transfer delay share} =
\frac{\text{time caused by assignment and handover waiting}}
{\text{total case elapsed time}}
\]

The analysis should distinguish productive reassignment from avoidable reassignment. A transfer to a correctly qualified specialist may be necessary; a transfer caused by an incorrect skill profile is avoidable.

---

## 2.3 Incorrect initial assignments

Compare the initial assignment with the eventual successful resolver:

- Was the initial agent qualified?
- Was the ticket assigned to the appropriate tier?
- Did the ticket require escalation within the expected time?
- Did the first assignment result in a reassignment?
- Was the initial category or required skill later changed?

For example, INC-1001 shows that:

1. The ticket was initially handled by L1.
2. It was escalated to L2 for App-CRM.
3. The first L2 agent later identified a Database-SQL requirement.
4. The ticket was reassigned to another L2 agent.

This suggests either an incomplete initial skill assessment, an overly broad CRM skill label, or insufficient visibility into cross-domain dependencies.

Metrics should include:

- Percentage of initial assignments later changed
- Percentage of initial assignments lacking the required skill
- Percentage of escalations that result in another reassignment
- Average time lost before correct skill assignment
- Correct-first-assignment rate

---

## 2.4 Overloaded and underutilized resources

Use time-based workload reconstruction to identify:

- Sustained utilization above a defined threshold
- Large queues assigned to particular agents
- Excessive concurrent tickets
- Long periods of inactivity during demand periods
- Agents receiving disproportionate numbers of high-priority tickets
- Specialists working on low-complexity tickets while qualified lower-tier staff are available

Agent comparisons must account for:

- Shift length
- Part-time status
- Leave and training
- Ticket complexity
- Priority mix
- Support channel
- Planned non-ticket duties

A simple workload chart can be misleading if one agent handles many short password-reset tickets and another handles fewer but very complex security incidents.

---

## 2.5 Correlation with SLA breaches

Build a case-level breach model with explanatory variables such as:

- Initial tier
- Initial agent
- Required skill
- Skill mismatch indicator
- Assignment wait time
- Number of reassignments
- Number of escalations
- Queue age at each transfer
- Agent utilization at assignment
- Priority and category
- Channel
- Time of day
- Complexity
- Presence of specialist backlog

Useful analyses include:

- SLA breach rate by agent, tier, skill, and assignment rule
- Breach rate by number of handovers
- Breach rate for correctly versus incorrectly skilled initial assignments
- Logistic regression or survival analysis
- Decision trees to identify combinations associated with breach
- Pareto analysis of breach causes

For example:

\[
\text{Breach risk} =
f(\text{priority}, \text{skill mismatch}, \text{initial wait}, \text{handover count}, \text{queue load})
\]

Avoid attributing causality solely to individual agents. A high breach rate may result from an overloaded queue, poor routing rules, or ticket complexity rather than poor individual performance.

# 3. Root Cause Analysis for Assignment Inefficiencies

## 3.1 Weak assignment rules

A round-robin rule treats agents as interchangeable. It ignores:

- Required technical skill
- Skill proficiency
- Current workload
- Ticket complexity
- Priority
- Shift availability
- Historical resolution performance
- Queue commitments
- Planned absence

This can produce technically incorrect assignments and overload specialists who happen to be included in a routing pool.

Manual escalation adds inconsistency. Similar tickets may follow different paths depending on the dispatcher or L1 agent.

---

## 3.2 Inaccurate skill profiles

Possible data problems include:

- Skills not maintained after training or role changes
- No distinction between beginner and expert proficiency
- Skills recorded at too broad a level, such as “CRM” instead of “CRM configuration” or “CRM database integration”
- No expiry or certification date
- Skills stored in a separate system and not synchronized with the service desk
- Informally acquired expertise not documented

The event log can expose this when assignments repeatedly contradict recorded skills or when a supposedly qualified agent frequently hands tickets to another specialist.

---

## 3.3 Poor categorization and skill identification

Ticket categories may be too general. A “Software-App” ticket may require:

- Application configuration
- Database troubleshooting
- Authentication
- Network connectivity
- Security permissions

If the required skill is assigned only after troubleshooting begins, the first assignment is likely to be inefficient.

Analyze:

- Category changes during the case
- Required-skill changes
- Keywords in descriptions versus final resolver skill
- Categories with high reassignment rates
- Categories with unusually high escalation or breach rates

---

## 3.4 Limited workload and availability visibility

A dispatcher may assign based on static tier membership rather than:

- Current queue length
- Active workload
- Time remaining in shift
- Current high-priority incidents
- Agent presence state
- Work already reserved for scheduled tasks
- Skill-specific availability

This creates overload concentration and avoidable waiting.

---

## 3.5 L1 capability and knowledge gaps

Excessive escalation may reflect:

- Inadequate knowledge articles
- Limited diagnostic tools
- Insufficient training
- Strict escalation policies
- Lack of authority to perform routine fixes
- Poor feedback from L2 to L1
- L1 being measured on speed rather than resolution quality

Compare L1 agents handling similar tickets. If some achieve high first-contact resolution while others escalate rapidly, analyze their knowledge use, ticket types, tenure, and escalation timing.

---

## 3.6 Variant analysis

Divide cases into groups such as:

- Zero-reassignment cases
- One-reassignment cases
- Multiple-reassignment cases
- SLA-compliant cases
- SLA-breached cases
- Correct-first-assignment cases
- Skill-mismatch cases

Compare the variants on:

- Priority
- Category
- Required skill
- Initial tier
- Initial agent
- Queue load
- Time of day
- Channel
- Number and timing of escalations
- Agent proficiency
- Ticket description features

A variant analysis may show, for example, that tickets with a Software-App category and Database-SQL requirement are much more likely to be reassigned when initially routed through a generic CRM queue.

---

## 3.7 Decision mining

Decision mining examines what information influenced a routing or escalation decision. For each assignment or escalation, model the outcome using features such as:

- Priority
- Category
- Required skill
- Customer or application
- Initial description terms
- Agent tier
- Skill match
- Queue length
- Availability
- Time of day
- Existing assignment load

The target may be:

- Whether the ticket was reassigned
- Whether it breached SLA
- Whether L1 resolved it
- Whether escalation was appropriate
- Which tier ultimately resolved it

The resulting decision tree or predictive model can reveal hidden rules, such as:

- Dispatchers favor certain agents regardless of workload.
- P2 Network tickets assigned during a particular shift are often routed to agents without firewall expertise.
- Certain keywords strongly predict database involvement but are not reflected in the initial skill label.

---

# 4. Data-Driven Resource Assignment Strategies

## Strategy 1: Skill- and proficiency-based routing

### Assignment issue addressed

This addresses:

- Skill mismatches
- Reassignments caused by incorrect expertise
- Delayed access to scarce specialists
- Incorrect tier selection

### Approach

For every ticket, identify one or more required skills and match it to agents using:

- Skill presence
- Proficiency level
- Certification status
- Recent successful experience
- Tier eligibility
- Availability
- Priority capability

A scoring function could be:

\[
\text{Assignment score} =
w_1(\text{skill match})
+w_2(\text{proficiency})
+w_3(\text{availability})
-w_4(\text{queue load})
+w_5(\text{historical success})
\]

The system should support primary and secondary skill requirements. For example, an App-CRM ticket with likely database involvement should be routed to an agent who has both App-CRM and Database-SQL skills, or to a coordinated pair where appropriate.

### Required data

- Current agent-skill matrix
- Proficiency and certification data
- Shift and availability status
- Ticket category and predicted skill
- Historical resolution and reassignment outcomes
- Skill-specific SLA requirements

### Expected benefits

- Higher correct-first-assignment rate
- Fewer transfers
- Lower specialist waiting time
- Reduced time to resolution
- Improved use of specialist capability
- Better SLA performance for skill-constrained tickets

---

## Strategy 2: Workload-aware assignment

### Assignment issue addressed

This addresses:

- Uneven workload
- Overloaded agents
- Underutilized agents
- Queue-related delays
- Blind round-robin routing

### Approach

Within the qualified-agent pool, assign work using real-time capacity rather than simple rotation. The algorithm should consider:

- Current open-ticket count
- Weighted workload by priority and complexity
- Active handling time
- Queue age
- Remaining shift time
- Agent availability
- Work in progress
- Reserved or planned work

A practical policy is:

1. Filter to agents with the required skill and tier eligibility.
2. Remove agents who are unavailable or over a defined workload limit.
3. Rank remaining agents by predicted completion time and current capacity.
4. Reserve capacity for P1 and P2 work.
5. Rebalance queues when demand changes.

### Required data

- Real-time presence and availability
- Agent schedules
- Active ticket states
- Estimated effort by category and priority
- Queue lengths
- Historical handling-time distributions
- Priority-specific capacity rules

### Expected benefits

- Reduced assignment waiting time
- More even utilization
- Fewer overload-driven SLA breaches
- Better response during demand spikes
- Less dependence on manual dispatcher judgment

Workload-aware routing should not assign a technically unsuitable ticket to an idle agent. Skill eligibility remains the first constraint.

---

## Strategy 3: Predictive ticket classification and assignment

### Assignment issue addressed

This addresses:

- Incomplete initial categorization
- Late discovery of required skills
- Incorrect tier assignment
- Repeated reassignment of ambiguous tickets

### Approach

Use historical tickets to predict:

- Category
- Required skill
- Complexity
- Likely resolver tier
- Expected handling time
- Probability of escalation
- SLA breach risk

Inputs may include:

- Ticket description
- Subject
- Channel
- Customer or application
- Error codes
- Priority
- Historical category
- Similar resolved tickets
- Attachments or structured form fields

The model can recommend a skill bundle rather than a single skill. For example:

`Software-App + CRM + Database-SQL`

The prediction should provide confidence. Low-confidence tickets can be sent to a triage queue rather than automatically routed incorrectly.

### Required data

- Historical ticket text and metadata
- Final resolver and final skill
- Reassignment history
- Resolution outcome
- SLA outcome
- Knowledge article usage
- Feedback from agents

### Expected benefits

- More accurate first assignment
- Fewer “hidden dependency” reassignments
- Faster access to the correct tier
- Better prioritization of complex cases
- Improved consistency across channels

The model should be monitored for drift and reviewed when applications, products, or support procedures change.

---

## Strategy 4: Evidence-based escalation and L1 enablement

### Assignment issue addressed

This addresses:

- Excessive L1 escalations
- Premature escalation
- Repeated escalation of tickets that L1 could resolve
- Inconsistent escalation decisions

### Approach

Mine successful L1 cases to identify:

- Ticket types commonly resolved at L1
- Diagnostic steps associated with successful resolution
- Maximum reasonable troubleshooting time
- Required knowledge articles
- Indicators that genuinely predict escalation

Create category-specific escalation rules. For example:

- Permit L1 to resolve known CRM access issues using an approved procedure.
- Escalate immediately when a ticket contains database corruption indicators.
- Require a diagnostic checklist before escalation for routine network issues.
- Route P2 tickets according to an expedited path while preserving skill fit.

Use the rules as decision support rather than rigid automation.

### Required data

- L1 activities and knowledge articles used
- Resolution outcomes
- Escalation reasons
- Reopen and repeat-contact data
- Ticket complexity and priority
- L2 feedback on escalation quality

### Expected benefits

- Higher first-contact resolution
- Lower unnecessary L2 workload
- Better quality escalations
- Faster handling of genuinely complex incidents
- Improved L1 capability through targeted training

---

## Strategy 5: Dynamic cross-tier capacity management

### Assignment issue addressed

This addresses:

- Tier-specific demand peaks
- Idle capacity in one tier while another is overloaded
- Specialist queues during predictable periods
- Inflexible staffing arrangements

### Approach

Use demand forecasts and process-mining metrics to define controlled flex capacity. For example:

- Cross-train selected L1 agents for high-volume, low-risk L2 activities.
- Allow qualified L2 agents to handle urgent L1 backlog during quiet specialist periods.
- Create virtual skill pools across teams.
- Trigger temporary reallocation when queue age or SLA risk exceeds thresholds.
- Reserve L3 capacity for high-complexity incidents.

Reallocation must preserve authorization and skill requirements.

### Required data

- Demand by hour, day, and skill
- Forecast ticket arrivals
- Agent proficiency and cross-training status
- Queue age and SLA risk
- Shift and schedule data
- Historical success of cross-tier handling

### Expected benefits

- Better response to demand volatility
- Reduced queues at constrained tiers
- Improved overall capacity utilization
- Lower SLA breach risk
- Reduced dependency on a small number of specialists

# 5. Simulation, Implementation, and Monitoring

## 5.1 Simulation before implementation

A process simulation should be built from the mined process model and historical resource behavior. It should include:

- Ticket arrival distributions
- Priority and category mix
- Processing-time distributions
- Agent calendars and shifts
- Skill and proficiency constraints
- Queue disciplines
- Escalation rules
- Assignment delays
- SLA targets
- Absence and demand variability

The baseline model should reproduce historical measures such as:

- Average resolution time
- SLA breach rate
- Assignment waiting time
- Reassignment rate
- Workload by tier
- Queue lengths
- Number of escalations

Once validated, test alternative scenarios:

1. Current round-robin logic
2. Skill-based routing only
3. Skill-based plus workload-aware routing
4. Predictive classification plus skill-based routing
5. Additional L1 training
6. Cross-tier flex staffing
7. Increased staffing for scarce skills
8. Different escalation thresholds

Compare scenarios using:

- SLA attainment
- P2 and P3 breach rate
- Mean and percentile resolution time
- Correct-first-assignment rate
- Reassignment rate
- Transfer delay
- Agent utilization
- Specialist time spent on appropriate work
- Cost or staffing requirement
- Robustness during demand peaks

Simulation should test sensitivity. For example, a routing algorithm that performs well under average demand may fail when one firewall specialist is absent.

---

## 5.2 Phased implementation

A suitable implementation sequence is:

### Phase 1: Measurement and data quality

- Standardize event definitions.
- Validate timestamps and case identifiers.
- Establish the agent-skill master.
- Define SLA and reassignment reason codes.
- Create baseline dashboards.

### Phase 2: Decision support

- Introduce skill-fit recommendations.
- Show workload and queue visibility to dispatchers.
- Provide escalation guidance to L1.
- Capture dispatcher overrides and reasons.

### Phase 3: Controlled automation

- Automate routing for high-confidence ticket types.
- Use human review for ambiguous or high-risk cases.
- Introduce workload balancing within qualified pools.
- Monitor outcomes against the baseline.

### Phase 4: Continuous improvement

- Retrain predictive models.
- Update skills and proficiency records.
- Review exceptions and overrides.
- Adjust staffing and cross-training based on demand patterns.

---

- Skill-fit ratio
- Percentage of assignments later changed
- Assignment wait time
- Reassignment rate
- Average handovers per ticket
- Reassignment reason distribution
- Percentage of automated versus manual assignments
- Dispatcher override rate

### SLA and flow performance

Track by priority, tier, category, skill, and channel:

- SLA attainment
- P2 and P3 breach rate
- Time to first response
- Time to first work
- Resolution time
- Queue waiting time
- Escalation delay
- Transfer delay
- Backlog age
- Cases at risk of breach

### Agent and tier performance

Track:

- Utilization
- Weighted workload
- Active concurrent tickets
- Queue size
- Handling time
- Resolution rate
- L1 first-contact resolution
- Escalation rate
- Reopen rate
- Specialist time on appropriate work
- Workload variation across comparable agents

### Skill-capacity monitoring

Track:

- Demand by skill
- Qualified capacity by skill
- Skill load ratio
- Number of tickets awaiting qualified agents
- Skill-specific queue age
- Skill-specific SLA breaches
- Coverage by shift

### Process and interaction views

Maintain:

- Decision-tree view of breach and reassignment drivers
- Cohort comparisons before and after routing changes

---

## 5.4 Governance and safeguards

Resource optimization should include controls to prevent harmful automation:

- P1 and security incidents require explicit routing safeguards.
- Agents must be assigned only work they are authorized to perform.
- Predictive models should provide confidence and an explanation.
- Manual overrides must be logged.
- Individual metrics should be interpreted in operational context.
- Staffing decisions should use team-level evidence, not isolated rankings.
- Skill data should have an owner, review cycle, and audit trail.

The central objective is not merely to maximize utilization. It is to assign the right ticket to the right qualified resource at the right time, while minimizing avoidable waiting and preserving service quality.

A successful program would therefore combine process mining, skill-based routing, workload visibility, predictive triage, targeted L1 enablement, and continuous simulation-based monitoring.
