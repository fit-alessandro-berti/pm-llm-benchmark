Below is a complete, selfcontained DuckDB SQL query that fulfills all four requirements. It uses CTEs (Common Table Expressions) to make each step explicit and easy to follow.

```sql
-- Replace {K} with the desired number of top variants, e.g. 5
WITH 

-- Step 1: Build the ordered activity sequence (the "variant") for every case
case_sequences AS (
    SELECT
        case_id,
        LIST(activity ORDER BY timestamp) AS activity_sequence
    FROM event_log
    GROUP BY case_id
),

-- Step 2: Group cases that share the exact same sequence -> unique variants
--         and collect the case_ids that belong to each variant
variant_counts AS (
    SELECT
        activity_sequence,
        COUNT(*)            AS case_count,
        LIST(case_id)       AS case_ids
    FROM case_sequences
    GROUP BY activity_sequence
),

-- Step 3: Rank variants by frequency and keep only the top K
top_variants AS (
    SELECT
        activity_sequence,
        case_count,
        case_ids
    FROM variant_counts
    ORDER BY case_count DESC
    LIMIT {K}
),

-- Step 4a: Flatten the list of case_ids belonging to the top-K variants
top_case_ids AS (
    SELECT UNNEST(case_ids) AS case_id
    FROM top_variants
)

-- Step 4b: Return the full set of events for those cases only
SELECT e.*
FROM event_log e
JOIN top_case_ids t
    ON e.case_id = t.case_id
ORDER BY e.case_id, e.timestamp;
```

### How it works

| Step | CTE | Purpose |
|------|-----|---------|
| 1 | `case_sequences` | For every `case_id`, builds an ordered list of activities using `LIST(activity ORDER BY timestamp)`, which respects the chronological order of events within the case. |
| 2 | `variant_counts` | Groups all cases sharing an identical `activity_sequence` (i.e., the same process variant), counts how many cases follow it (`case_count`), and also keeps track of which `case_id`s belong to it. |
| 3 | `top_variants` | Sorts variants by `case_count` in descending order and limits the result to the top **K** variants — the most frequent process paths. |
| 4a | `top_case_ids` | Uses `UNNEST` to expand the list of `case_id`s from the topK variants into individual rows, giving a simple list of qualifying case IDs. |
| 4b | Final `SELECT` | Joins back to the original `event_log` table to retrieve **all** events (not just aggregated data) for cases that belong to one of the topK variants, while excluding all other cases. |

### Notes
- **`LIST(... ORDER BY ...)`** in DuckDB acts like `ARRAY_AGG` with ordering — it guarantees that the sequence of activities reflects the true chronological order of events per case.
- Grouping by a list (`GROUP BY activity_sequence`) works in DuckDB since list types support equality comparison, allowing identical sequences to be merged into one group naturally.
- The final join ensures **all columns** from `event_log` (not just `case_id` and `activity`) are preserved for the qualifying cases, satisfying the requirement to return full events, not just variant summaries.
- Replace `{K}` with an integer literal (e.g., `5`) or bind it as a parameter if using a parameterized query interface.

This structure cleanly separates **variant discovery**, **frequency ranking**, and **event filtering**, making it straightforward to adapt (e.g., using `STRING_AGG` instead of `LIST` if you prefer string-based variant representation, or adjusting `K` dynamically).
