## 1. Anomalies in the DECLARE model

### A. `E` and `C` cannot coexist

The `noncoexistence` constraint between `E` and `C` means that a claim trace cannot contain both an evaluation and a closing event.

Because `C` is mandatory (`existence(C)`), every completed claim is effectively prohibited from having an evaluation.

This conflicts with the intended lifecycle, where a claim should normally be evaluated before it is closed.

**Practical consequence:** a trace such as:

```text
R  A  E  P  N  C
```

is invalid under the model because it contains both `E` and `C`.

---

### B. Evaluation is not mandatory

`responded_existence(E, A)` means:

> If an evaluation occurs, an assignment must occur somewhere in the same trace.

It does not mean that evaluation itself must occur. Since `E` is not required by an `existence` rule, the model can permit a claim to proceed without evaluation.

Combined with `noncoexistence(E, C)` and mandatory `C`, the model strongly favors traces without evaluation.

A minimal trace potentially allowed by the model is:

```text
R  C
```

assuming the precedence rule is interpreted as “`R` occurs before `C`.”

---

### C. Assignment is not required unless evaluation occurs

There is no `existence(A)` constraint. Therefore, an assignment is optional unless an evaluation is recorded.

As a result, the model can allow claims to be closed without any adjuster assignment:

```text
R  C
```

This undermines the intended requirement that claims should be assigned before they are evaluated or processed.

---

### D. `responded_existence(E, A)` does not enforce ordering

Even where both `E` and `A` occur, responded existence only requires their coexistence. It does not guarantee that assignment happens before evaluation.

Thus, the following may satisfy the declared relationship even though it is operationally questionable:

```text
R  E  A  C
```

A precedence or response-precedence rule would be needed to require `A` before `E`.

---

### E. Possible reversed precedence between `C` and `R`

The meaning of:

```python
"precedence": {
    "C": {"activities": ["R"]}
}
```

depends on the convention used by the implementation.

If it means:

```text
precedence(C, R)
```

then every `R` must be preceded by `C`. This directly conflicts with `init(R)`, because `R` must be the first event while also requiring a prior `C`.

With strict precedence semantics, this would make the model unsatisfiable for any non-empty trace.

If instead the representation means “`R` must precede `C`,” then the rule is consistent with the intended start/end ordering. The model definition should be checked to confirm the argument direction.

---

### F. Approval and notification are unconstrained

There are no constraints requiring:

- `P` to occur,
- `N` to occur,
- `E` to precede `P`,
- `P` to precede `N`,
- `N` to precede `C`.

Therefore, the following traces may be accepted:

```text
R  C
R  A  C
R  P  C
R  N  C
R  A  P  C
```

The model does not enforce the intended full process sequence.

---

### G. Activities may be repeated

No constraints prevent repeated activities. For example, the model may permit:

```text
R  A  A  C
R  C  C
R  E  E
```

unless the event-log interpretation or external system rules prevent duplicates.

---

## 2. Possible explanations for the anomalies

1. **Constraint direction was reversed during model construction**  
   The precedence relation may have been encoded with the activity arguments in the wrong order.

2. **Incomplete translation of business rules**  
   Requirements such as “every claim must be evaluated before approval” may have been discussed operationally but not translated into DECLARE constraints.

3. **Process variants were combined into one model**  
   Some claims may legitimately skip evaluation, while standard claims require it. Combining both variants without conditional rules can create overly permissive or contradictory constraints.

4. **Data-mining artifacts**  
   The model may have been discovered from incomplete event data. For example:
   - evaluation events may be missing from certain systems;
   - closing events may be recorded automatically;
   - assignment events may be stored in another application;
   - event timestamps may be inaccurate or delayed.

5. **Policy changes were only partially applied**  
   A later policy may have introduced mandatory closure or changed evaluation handling, while earlier constraints were retained.

6. **Activity-code inconsistency**  
   Some evaluation or approval actions may be recorded under activity codes other than `E` or `P`, causing the discovered model to infer incorrect relationships.

7. **Exceptional claims were not modeled separately**  
   Withdrawn, duplicate, fraud-related, or immediately rejected claims may follow a shorter path. If these are mixed with ordinary claims, the model may appear to allow premature closure.

8. **Automation and manual work were conflated**  
   System-generated closure events may occur even when a human evaluation exists elsewhere, making `E` and `C` appear unrelated in the recorded data.

---

## 3. SQL investigation strategies

The following queries use `event_id` as a deterministic tie-breaker when timestamps are equal.

---

### A. Find claims that were closed without evaluation

```sql
SELECT
    c.claim_id,
    c.customer_id,
    c.claim_type,
    c.claim_amount,
    c.submission_date
FROM claims c
WHERE EXISTS (
    SELECT 1
    FROM claim_events ce
    WHERE ce.claim_id = c.claim_id
      AND ce.activity = 'C'
)
AND NOT EXISTS (
    SELECT 1
    FROM claim_events ce
    WHERE ce.claim_id = c.claim_id
      AND ce.activity = 'E'
)
ORDER BY c.claim_id;
```

This identifies closed claims whose event history contains no evaluation event.

---

### B. Find claims where evaluation and closure coexist

These claims violate the `noncoexistence(E, C)` constraint.

```sql
SELECT
    c.claim_id,
    MIN(e."timestamp") AS first_evaluation_time,
    MIN(cl."timestamp") AS first_closure_time
FROM claims c
JOIN claim_events e
    ON e.claim_id = c.claim_id
   AND e.activity = 'E'
JOIN claim_events cl
    ON cl.claim_id = c.claim_id
   AND cl.activity = 'C'
GROUP BY c.claim_id
ORDER BY c.claim_id;
```

---

### C. Find all claims that have no closing event

This checks whether the mandatory `existence(C)` constraint holds in practice.

```sql
SELECT
    c.claim_id,
    c.customer_id,
    c.claim_type,
    c.submission_date
FROM claims c
WHERE NOT EXISTS (
    SELECT 1
    FROM claim_events ce
    WHERE ce.claim_id = c.claim_id
      AND ce.activity = 'C'
)
ORDER BY c.submission_date, c.claim_id;
```

---

### D. Check whether the first recorded activity is `R`

This validates the `init(R)` rule.

```sql
WITH first_events AS (
    SELECT DISTINCT ON (ce.claim_id)
        ce.claim_id,
        ce.activity,
        ce."timestamp",
        ce.event_id
    FROM claim_events ce
    ORDER BY ce.claim_id, ce."timestamp", ce.event_id
)
SELECT
    c.claim_id,
    fe.activity AS first_activity,
    fe."timestamp" AS first_activity_time
FROM claims c
LEFT JOIN first_events fe
    ON fe.claim_id = c.claim_id
WHERE fe.activity IS DISTINCT FROM 'R'
ORDER BY c.claim_id;
```

This returns both:

- claims whose first recorded event is not `R`;
- claims with no event history.

---

### E. Find claims where `C` occurs without a prior `R`

Use this if the intended precedence is:

```text
R before C
```

```sql
SELECT
    cl.claim_id,
    cl.event_id AS close_event_id,
    cl."timestamp" AS close_time
FROM claim_events cl
WHERE cl.activity = 'C'
  AND NOT EXISTS (
      SELECT 1
      FROM claim_events r
      WHERE r.claim_id = cl.claim_id
        AND r.activity = 'R'
        AND (r."timestamp", r.event_id) < (cl."timestamp", cl.event_id)
  )
ORDER BY cl.claim_id, cl."timestamp", cl.event_id;
```

---

### F. Find claims where `R` occurs without a prior `C`

Use this to test the alternative interpretation in which the declared precedence rule means:

```text
C before R
```

```sql
SELECT
    r.claim_id,
    r.event_id AS receive_event_id,
    r."timestamp" AS receive_time
FROM claim_events r
WHERE r.activity = 'R'
  AND NOT EXISTS (
      SELECT 1
      FROM claim_events cl
      WHERE cl.claim_id = r.claim_id
        AND cl.activity = 'C'
        AND (cl."timestamp", cl.event_id) < (r."timestamp", r.event_id)
  )
ORDER BY r.claim_id, r."timestamp", r.event_id;
```

If `R` must be the initial event, nearly every normal claim will appear in this result, demonstrating that this precedence direction is incompatible with `init(R)`.

---

### G. Find evaluations with no assignment anywhere in the same claim

This checks the formal responded-existence relationship between `E` and `A`.

```sql
SELECT DISTINCT
    e.claim_id
FROM claim_events e
WHERE e.activity = 'E'
  AND NOT EXISTS (
      SELECT 1
      FROM claim_events a
      WHERE a.claim_id = e.claim_id
        AND a.activity = 'A'
  )
ORDER BY e.claim_id;
```

---

### H. Find evaluations that occurred before assignment

This is not necessarily a violation of responded existence, but it violates the expected operational order.

```sql
SELECT
    e.claim_id,
    e.event_id AS evaluation_event_id,
    e."timestamp" AS evaluation_time
FROM claim_events e
WHERE e.activity = 'E'
  AND NOT EXISTS (
      SELECT 1
      FROM claim_events a
      WHERE a.claim_id = e.claim_id
        AND a.activity = 'A'
        AND (a."timestamp", a.event_id) < (e."timestamp", e.event_id)
  )
ORDER BY e.claim_id, e."timestamp", e.event_id;
```

---

### L. Identify repeated lifecycle activities

```sql
SELECT
    ce.claim_id,
    ce.activity,
    COUNT(*) AS occurrence_count,
    MIN(ce."timestamp") AS first_occurrence,
    MAX(ce."timestamp") AS last_occurrence
FROM claim_events ce
WHERE ce.activity IN ('R', 'A', 'E', 'P', 'N', 'C')
GROUP BY ce.claim_id, ce.activity
HAVING COUNT(*) > 1
ORDER BY ce.claim_id, ce.activity;
```

---

### M. Find evaluation events performed by resources not found in `adjusters`

This assumes `claim_events.resource` stores the adjuster name.

```sql
SELECT
    e.claim_id,
    e.event_id,
    e."timestamp",
    e.resource AS evaluation_resource
FROM claim_events e
LEFT JOIN adjusters a
    ON a.name = e.resource
WHERE e.activity = 'E'
  AND a.adjuster_id IS NULL
ORDER BY e.claim_id, e."timestamp", e.event_id;
```

This can identify evaluations performed by unknown resources, systems, misspelled names, or unregistered adjusters.

---

### N. Find evaluations where the evaluator specialization does not match claim type

This example maps `home_insurance` to `home` and `auto_insurance` to `auto`.

```sql
SELECT
    c.claim_id,
    c.claim_type,
    e.resource AS evaluator_name,
    a.specialization,
    e."timestamp" AS evaluation_time
FROM claims c
JOIN claim_events e
    ON e.claim_id = c.claim_id
   AND e.activity = 'E'
JOIN adjusters a
    ON a.name = e.resource
WHERE a.specialization <> CASE c.claim_type
    WHEN 'home_insurance' THEN 'home'
    WHEN 'auto_insurance' THEN 'auto'
    ELSE a.specialization
END
ORDER BY c.claim_id, e."timestamp";
```

The mapping should be expanded if additional claim types exist.

---

### O. Produce a compact trace view for manual investigation

```sql
SELECT
    ce.claim_id,
    STRING_AGG(
        ce.activity || ' @ ' ||
        TO_CHAR(ce."timestamp", 'YYYY-MM-DD HH24:MI:SS'),
        ' -> ' ORDER BY ce."timestamp", ce.event_id
    ) AS activity_trace
FROM claim_events ce
GROUP BY ce.claim_id
ORDER BY ce.claim_id;
```

This query is useful for reviewing individual claim traces and confirming whether apparent anomalies are caused by process exceptions, timestamp quality issues, or incorrect activity coding.
