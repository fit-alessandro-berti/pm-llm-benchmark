# 1. Anomaly Identification

## 1.1 What each constraint actually says

| Constraint | Semantics |
|---|---|
| `init(R)` | Every trace must begin with activity R. |
| `existence(C)` | Every trace must contain at least one C. |
| `responded_existence(E  A)` | If A occurs in a trace, E must occur somewhere in the same trace. |
| `precedence(C  R)` | Every occurrence of C must be preceded by an occurrence of R. |
| `noncoexistence(E, C)` | E and C must never appear in the same trace (symmetric). |

## 1.2 Direct contradictions

**A1 — `existence(C)` vs. `noncoexistence(E, C)`: evaluation is logically banned.**
Every trace must contain C, and no trace may contain both E and C. Taken together, this means **no compliant trace can ever contain an evaluation**. A mandatory activity (C) and an essential business activity (E) are declared mutually exclusive.

**A2 — Knock-on contradiction via `responded_existence(E  A)`: assignment is banned too.**
Since A implies E (responded existence), and E is impossible in any trace containing C (A1), then by contraposition **no trace containing A can ever be closed compliantly**. Any trace that contains *both* A and C is unsatisfiable: A forces E in, C forces E out. In other words, the model cannot represent a claim that is both assigned and closed — which describes virtually every real claim.

**A3 — The model contradicts the intended process itself.**
The ideal flow `R  A  E  P  N  C` contains E and C together, so the *reference process violates the model*. Conversely, the only traces that satisfy all constraints are degenerate ones: R, then optionally P and/or N (both unconstrained), then C — never A or E. Model compliance and process compliance are mutually exclusive.

## 1.3 Underspecification and undesired paths

**A4 — `precedence(C  R)` is far too weak.**
C is gated only by R, not by N (or the full chain). A trace `(R, C)` — claim received and immediately closed — is fully compliant. The intended gate should be "C only after N."

**A5 — P (Approve) and N (Notify) are completely unconstrained.**
Nothing requires approval to be preceded by evaluation, so `(R, P, C)` — **approval without evaluation** — is allowed. Nothing requires N before C, so customers can be left uninformed. Nothing requires P or N to occur at all.

**A6 — Missing existence and ordering constraints.**
There is no `existence` for A, E, P, N, and no response/succession chain RAEPNC. The model's only "happy path" is the shortest possible one.

**A7 — Meta-anomaly: support = confidence = 1.0 on mutually contradictory rules.**
Perfect-confidence constraints that jointly exclude the core process indicate the model was never consistency-checked, or was machine-discovered from a biased event log without validation against domain knowledge.

```sql
  AND (first_r IS NULL OR first_c < first_r);
```

**Q4 — `responded_existence` violations: assigned but never evaluated**
```sql
SELECT claim_id
FROM claim_events
GROUP BY claim_id
HAVING BOOL_OR(activity = 'A')
   AND NOT BOOL_OR(activity = 'E');
```

**Q5 — `noncoexistence` violations: E and C in the same trace**
```sql
SELECT claim_id
FROM claim_events
GROUP BY claim_id
HAVING BOOL_OR(activity = 'E')
   AND BOOL_OR(activity = 'C');
```
> Interpretation: if this returns *most* traces, reality follows the intended process and the **constraint** is wrong (supports H1/H3/H4). If it returns almost none, the log genuinely lacks evaluations for closed claims (supports H2/H4/H5).

## 3.3 Root-cause analysis (testing the hypotheses)

**Q11 — One-shot anomaly prevalence dashboard**
```sql
WITH flags AS (
    SELECT claim_id,
           BOOL_OR(activity = 'R') AS has_r,
           BOOL_OR(activity = 'A') AS has_a,
           BOOL_OR(activity = 'E') AS has_e,
           BOOL_OR(activity = 'P') AS has_p,
           BOOL_OR(activity = 'N') AS has_n,
           BOOL_OR(activity = 'C') AS has_c
    FROM claim_events
    GROUP BY claim_id
)
SELECT
    COUNT(*)                                            AS total_traces,
    COUNT(*) FILTER (WHERE has_e AND has_c)             AS e_and_c_coexist,
    COUNT(*) FILTER (WHERE has_c AND NOT has_e)         AS closed_without_eval,
    COUNT(*) FILTER (WHERE has_a AND NOT has_e)         AS assigned_never_evaluated,
    COUNT(*) FILTER (WHERE has_e AND NOT has_a)         AS evaluated_without_assignment,
    COUNT(*) FILTER (WHERE has_p AND NOT has_e)         AS approved_without_eval,
    COUNT(*) FILTER (WHERE has_c AND NOT has_p)         AS closed_without_approval,
    COUNT(*) FILTER (WHERE has_c AND NOT has_n)         AS closed_without_notification,
    COUNT(*) FILTER (WHERE has_a AND has_c)             AS assigned_and_closed
FROM flags;
```
This single result quantifies every anomaly and shows which side — model or practice — dominates.

**Q12 — Stratification by claim type and time (tests H2, H3, H5)**
```sql
WITH flags AS (
    SELECT claim_id,
           BOOL_OR(activity = 'E') AS has_e,
           BOOL_OR(activity = 'C') AS has_c
    FROM claim_events
    GROUP BY claim_id
)
SELECT c.claim_type,
       DATE_TRUNC('month', c.submission_date) AS submission_month,
       COUNT(*) AS claims,
       COUNT(*) FILTER (WHERE f.has_c AND NOT f.has_e) AS closed_no_eval,
       ROUND(100.0 * COUNT(*) FILTER (WHERE f.has_c AND NOT f.has_e)
             / COUNT(*), 1) AS pct_closed_no_eval
FROM claims c
JOIN flags f ON f.claim_id = c.claim_id
GROUP BY c.claim_type, submission_month
ORDER BY submission_month, c.claim_type;
```
A sudden jump in `pct_closed_no_eval` after a certain month points to a policy change (H3); concentration in one claim type points to an unscoped fast-track (H2).

**Q13 — Amount-band analysis (fast-track for small claims?)**
```sql
WITH flags AS (
    SELECT claim_id,
           BOOL_OR(activity = 'E') AS has_e,
           BOOL_OR(activity = 'C') AS has_c
    FROM claim_events
    GROUP BY claim_id
)
SELECT CASE
           WHEN c.claim_amount < 1000  THEN '1_small'
           WHEN c.claim_amount < 10000 THEN '2_medium'
           ELSE '3_large'
       END AS amount_band,
       COUNT(*) AS claims,
       COUNT(*) FILTER (WHERE f.has_c AND NOT f.has_e) AS closed_no_eval
FROM claims c
JOIN flags f ON f.claim_id = c.claim_id
GROUP BY 1
ORDER BY 1;
```

**Q14 — Adjuster/resource consistency (is evaluation properly linked to assignment?)**
```sql
-- (a) Evaluations performed by resources that are not adjusters
SELECT ce.claim_id, ce.resource, ce."timestamp"
FROM claim_events ce
LEFT JOIN adjusters adj ON adj.name = ce.resource
WHERE ce.activity = 'E'
  AND adj.adjuster_id IS NULL;
```
```sql
-- (b) Evaluator differs from the assigned adjuster
WITH first_event AS (
    SELECT claim_id, activity, resource,
           ROW_NUMBER() OVER (PARTITION BY claim_id, activity
                              ORDER BY "timestamp", event_id) AS rn
    FROM claim_events
    WHERE activity IN ('A', 'E')
)
SELECT a.claim_id, a.resource AS assigned_to, e.resource AS evaluated_by
FROM first_event a
JOIN first_event e ON e.claim_id = a.claim_id
WHERE a.activity = 'A' AND a.rn = 1
  AND e.activity = 'E' AND e.rn = 1
  AND a.resource <> e.resource;
```
```sql
-- (c) Specialization mismatch vs. claim type
SELECT ce.claim_id, c.claim_type, adj.name, adj.specialization
FROM claim_events ce
JOIN claims c    ON c.claim_id  = ce.claim_id
JOIN adjusters adj ON adj.name  = ce.resource
WHERE ce.activity IN ('A', 'E')
  AND ((c.claim_type LIKE 'home%' AND adj.specialization <> 'home')
    OR (c.claim_type LIKE 'auto%' AND adj.specialization <> 'auto'));
```

**Q15 — Data-quality scan (tests the mining-artifact hypothesis H4)**
```sql
-- Unknown or unexpected activity labels

FROM claim_events

ORDER BY 1;

-- Evaluation-like information recorded under other activities
SELECT claim_id, activity, additional_info, "timestamp"

WITH b AS (
```

## 3.4 Reading the results

| Observation | Most likely explanation |
|---|---|
| Q5 returns the majority of traces | The `noncoexistence` constraint is simply wrong (H1/H3); replace with `precedence(C  E)` plus a full ordering chain |
| Q6/Q13 show closed-without-eval clustered in small amounts or one claim type | Unscoped fast-track path (H2) or deliberate bypass (H5) |
| Q12 shows a step change after a specific month | Policy change not propagated to the model (H3) |
| Q15 finds evaluation data under other labels, in `additional_info`, or backfilled after C | The constraint was mined from an incomplete log (H4) |
| Q14(a) shows evaluations by "system" or unknown resources | Evaluation is automated/outsourced and logged inconsistently — feeding the artifact (H4) |
