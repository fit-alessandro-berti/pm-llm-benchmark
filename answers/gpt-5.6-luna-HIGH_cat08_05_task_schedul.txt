# 1. Historical Scheduling Performance and Shop-Floor Dynamics

A useful target state for Precision Parts Inc. is a **process-mining-enabled production digital twin**: a continuously updated representation of jobs, routings, machines, operators, queues, setups, breakdowns, and due-date commitments.

## 1.1 Prepare and reconstruct the event log

The MES log should first be converted into an analysis-ready event model. Each event should contain, at minimum:

- Case or job ID
- Operation or task ID, including repeat and rework occurrences
- Activity name and lifecycle stage
- Machine and operator
- Event timestamp
- Job priority and due date
- Planned and actual duration
- Setup indicator and previous job
- Breakdown, maintenance, hold, or priority-change status

The basic case perspective is the **job**, but this environment benefits from an **object-centric process mining model**. Related objects include:

- Job
- Operation
- Machine
- Operator
- Setup event
- Breakdown event
- Schedule version
- Material lot or part family

This allows analysis of relationships such as:

- Which jobs were affected by a particular breakdown?
- Which operators and machines were associated with long setups?
- Which operation sequences generated the most waiting?
- How did one job’s use of a bottleneck affect other jobs?

### Event normalization

The event log should be normalized into state intervals, for example:

| State | Start | End |
|---|---:|---:|
| Waiting in queue | Queue Entry | Setup Start or Task Start |
| Setup | Setup Start | Setup End |
| Processing | Task Start | Task End |
| Breakdown | Breakdown Start | Breakdown End |
| Blocked | Task End | Transfer or next operation start |
| Idle | End of prior activity | Start of next activity |

The analysis should explicitly address:

- Missing queue-entry or task-end events
- Duplicate events
- Out-of-order timestamps
- Clock differences between MES, machine controllers, and maintenance systems
- Jobs that are reworked or routed through the same operation more than once
- Operator changes during a task
- Planned schedule versions that changed after release

If a task has no explicit queue-entry event, its waiting time can sometimes be inferred from the prior operation completion and the next task start, but this should be marked as inferred rather than observed.

## 1.2 Process discovery and conformance analysis

Several process-mining techniques would be appropriate.

### Process discovery

Use directly-follows graphs, Petri nets, BPMN models, or heuristic process discovery to reconstruct:

- Common job-routing variants
- Actual sequences of operations
- Rework loops
- Skipped or added operations
- Frequency of each routing variant
- Transition times between work centers
- Resource-specific execution patterns

For example, the process model may show that the nominal routing is:

> Cutting  Milling  Grinding  Heat Treatment  Inspection

but actual cases may include:

> Cutting  Milling  Rework  Milling  Inspection

or:

> Cutting  Milling  External Heat Treatment  Grinding  Inspection

These variants have different capacity and due-date implications.

### Conformance checking

If standard routings or released manufacturing plans are available, conformance checking can compare planned and actual execution using:

- Token replay
- Alignment-based conformance checking
- Variant comparison
- Constraint violation analysis

Useful conformance measures include:

- Percentage of jobs following the planned route
- Frequency of skipped or added operations
- Excessive waiting between planned consecutive tasks
- Tasks performed on non-designated machines
- Operations started before predecessors were complete
- Rework and restart rates

This distinguishes scheduling problems from routing instability. If many jobs are late because actual routings contain additional rework loops, the issue is not solely dispatching.

## 1.3 Flow-time, lead-time, and makespan metrics

For job \(i\), define:

- Release time: \(R_i\)
- Completion time: \(C_i\)
- Due date: \(D_i\)

The basic job flow time is:

\[
F_i = C_i - R_i
\]

This should be decomposed into:

\[
F_i =
\text{Processing Time}
+
\text{Setup Time}
+
\text{Queue Time}
+
\text{Transfer Time}
+
\text{Blocked/Hold Time}
+
\text{Disruption Time}
\]

Metrics should be reported by:

- Job family
- Customer
- Priority
- Routing variant
- Due-date bucket
- Machine and work center
- Shift and operator
- Load level

Important statistics are:

- Mean, median, and 90th/95th percentile lead time
- Flow-time distribution by job class
- Release-to-first-operation time
- Time between successive operations
- Total value-added time versus total elapsed time
- Lead-time variability and coefficient of variation
- Jobs exceeding quoted lead-time estimates

For a production cohort, campaign, or planning horizon, makespan is:

\[
C_{\max} = \max_i(C_i) - \min_i(R_i)
\]

The makespan distribution can be compared across:

- Normal versus high-load periods
- Periods with and without major breakdowns
- Different priority mixes
- Different scheduling policies
- Similar job portfolios

## 1.4 Task waiting and queue-time analysis

For operation \(k\) of job \(i\), if \(Q_{ik}\) is queue entry and \(S_{ik}\) is setup start or task start:

\[
W_{ik} = S_{ik} - Q_{ik}
\]

Queue time should be separated into several forms:

1. **Waiting for machine availability**
2. **Waiting for an operator**
3. **Waiting for material or predecessor completion**
4. **Waiting because of planned sequencing**
5. **Waiting because of a breakdown**
6. **Waiting because the downstream machine is blocked**
7. **Waiting caused by a priority or hot-job insertion**

For each machine, calculate:

- Average and percentile queue time
- Queue length over time
- Maximum queue length
- Queue time by priority class
- Queue time by job family
- Queue time before and after breakdowns
- Queue-time contribution to total lead time

A useful visualization is a time-aligned queue heat map showing queue length and average age by machine. This frequently reveals that the largest lead-time problem is not processing time but waiting at one or two constrained work centers.

Little’s Law provides an additional consistency check:

\[
\text{Average WIP} \approx \text{Throughput} \times \text{Average Flow Time}
\]

If WIP rises while throughput does not, the process is accumulating waiting time rather than creating output.

## 1.5 Machine and operator utilization

For machine \(m\), establish its available calendar time:

\[
A_m = \text{scheduled production time} - \text{planned maintenance}
\]

Then classify observed time into:

- Productive processing
- Setup
- Planned maintenance
- Unplanned breakdown
- Waiting or idle
- Starved: machine available but no job ready
- Blocked: machine cannot release completed work
- Changeover or qualification
- Unaccounted time

Example metrics include:

\[
U^{\text{productive}}_m =
\frac{\text{productive processing minutes}}{A_m}
\]

\[
U^{\text{setup}}_m =
\frac{\text{setup minutes}}{A_m}
\]

\[
U^{\text{effective}}_m =
\frac{\text{productive processing}+\text{setup}}{A_m}
\]

The important point is that high utilization is not always desirable. A machine operating at 98–100% effective utilization with high variability may generate disproportionately long queues. A better analysis considers:

- Utilization
- Queue growth
- Queue-time percentiles
- Throughput
- Availability
- Setup burden
- Downstream starvation and blocking

Operator analysis should include:

- Productive labor time
- Setup labor time
- Waiting for machine, material, or instructions
- Overtime
- Multi-machine assignments
- Operator-specific duration and setup effects

Operator utilization must account for concurrent assignments. An operator should not be counted as fully productive on two tasks simultaneously unless the operating model explicitly permits that.

## 1.6 Sequence-dependent setup-time analysis

For each machine, sort jobs by the actual start or completion sequence. For a transition from job or family \(a\) to job or family \(b\), calculate:

\[
S_m(a,b) =
\text{Setup End}_{b,m}
-
\text{Setup Start}_{b,m}
\]

The result is a sequence-dependent setup matrix for each machine:

| Previous family | Next family | Count | Median setup | P90 setup |
|---|---|---:|---:|---:|
| Aluminum-small | Aluminum-small | 42 | 8 min | 13 min |
| Aluminum-small | Steel-large | 18 | 35 min | 52 min |
| Steel-large | Titanium | 9 | 61 min | 84 min |

This analysis should include:

- Job-to-job and family-to-family transition matrices
- Median, variance, and P90 setup duration
- Setup duration by machine
- Setup duration by operator and shift
- Setup duration by tooling, material, geometry, and part size
- Setup duration following a breakdown or emergency changeover
- First-job-of-shift or first-job-after-maintenance effects
- Frequency of “unplanned” setups
- Setup duration estimation error

A simple average setup time can be misleading. The transition from one family to another may have a highly asymmetric cost:

\[
S(a,b) \neq S(b,a)
\]

Historical setup data can be used to fit a predictive model, for example:

\[
\hat{S} =
f(\text{machine}, \text{previous family}, \text{next family},
\text{tooling}, \text{operator}, \text{shift}, \text{material})
\]

The actual sequence can then be compared with a setup-efficient sequence under the same job set. The difference represents a measure of potentially avoidable setup time.

## 1.7 Schedule adherence and tardiness

Schedule adherence requires the planned schedule, or at least schedule snapshots. If the MES stores only planned durations but not planned start and finish times, the company should begin storing:

- Schedule version
- Planned machine
- Planned start
- Planned finish
- Dispatch decision timestamp
- Reason for schedule change

For each task:

\[
\text{Start Deviation}_{ik}
=
\text{Actual Start}_{ik}
-
\text{Planned Start}_{ik}
\]

\[
\text{Finish Deviation}_{ik}
=
\text{Actual Finish}_{ik}
-
\text{Planned Finish}_{ik}
\]

For each job:

\[
T_i = \max(0, C_i-D_i)
\]

where \(T_i\) is tardiness.

Key measures include:

- On-time delivery percentage
- Mean and median tardiness
- P90 and maximum tardiness
- Weighted tardiness by customer or priority
- Number of late operations
- Final-job tardiness versus internal milestone tardiness
- Earliness, if early completion creates WIP
- Tardiness by routing, machine, customer, and priority
- Schedule adherence at task and job level
- Number of schedule changes per job
- Schedule stability between release and execution

Tardiness should also be decomposed into:

- Late release
- Excessive queue time
- Excessive setup
- Processing-time overruns
- Breakdown delay
- Hot-job interruption
- Rework
- Downstream congestion

## 1.8 Disruption impact

Breakdowns, urgent orders, and priority changes should be represented as explicit events and linked to affected jobs.

For a breakdown at time \(b_s\) ending at \(b_e\), analyze:

- Jobs active on the machine
- Jobs waiting for the machine
- Jobs whose planned start was after the breakdown
- Queue growth during and after the event
- Recovery time
- Additional tardiness
- Additional setups caused by recovery resequencing
- Downstream starvation
- Overtime or subcontracting required to recover

Useful techniques include:

- Before/after event studies
- Disruption-window cohort comparison
- Causal or matched comparison of similar jobs
- Survival analysis for time to completion
- Propagation graphs showing downstream affected operations
- Simulation-based counterfactual analysis

For hot jobs, measure not only whether they were expedited, but also:

- Which jobs they displaced
- How much setup time they caused
- The tardiness added to displaced jobs
- Whether the hot job actually met its revised due date
- Whether repeated priority changes caused queue oscillation

# 2. Diagnosing Scheduling Pathologies

The historical analysis should produce evidence-based diagnoses rather than relying on anecdotal explanations. The following pathologies are likely candidates.

## 2.1 Bottleneck resources and throughput loss

A bottleneck is not necessarily the machine with the highest nominal utilization. It is the resource that most constrains system throughput.

Evidence can include:

- Sustained utilization near available capacity
- Persistent queue growth
- High queue-age percentiles
- Large share of total job flow time
- Frequent downstream starvation or upstream blocking
- High sensitivity of makespan to that machine’s availability
- Large required load-to-capacity ratio

For machine \(m\), a rough load ratio is:

\[
\rho_m =
\frac{\text{required processing}+\text{expected setup}}
{\text{available capacity}}
\]

This should be calculated using actual routing demand and realistic setup times rather than planned processing time alone.

Bottleneck analysis can use:

- Performance overlays on discovered process models
- Queue and utilization heat maps
- Critical-path analysis
- Resource contention graphs
- Throughput impact of downtime
- Simulation-based capacity removal or expansion tests

If a 5% capacity increase at MILL-03 reduces total tardiness materially, while the same increase at CUT-01 has little effect, MILL-03 is a stronger system bottleneck candidate.

## 2.2 Poor prioritization and rank inversion

Local FCFS/EDD rules can create priority failures. Examples include:

- A high-priority job waiting behind several lower-priority jobs
- A job with little remaining slack being bypassed
- A job close to due date being delayed for a job with a later due date
- A hot job being inserted without considering its impact on already committed jobs
- Different machines applying incompatible priorities

Process mining can identify **rank inversions** by comparing the order in which eligible jobs were processed with their:

- Due-date slack
- Customer priority
- Remaining route workload
- Bottleneck requirements
- Predicted tardiness risk

The analysis should compare on-time and late job cohorts. If late high-priority jobs have significantly longer waits at specific machines, and lower-priority jobs with later due dates are routinely processed first, the problem is likely dispatching logic rather than only capacity.

## 2.3 Suboptimal setup sequencing

Evidence of poor setup sequencing includes:

- High frequency of expensive family-to-family transitions
- Large setup minutes per productive hour
- Repeated switching between material, tooling, or geometry families
- Long setups at bottleneck machines despite an available setup-compatible alternative
- High variation in setup times for supposedly similar transitions
- A large gap between observed setup time and a setup-optimized benchmark

A transition heat map can show whether the shop is repeatedly making avoidable transitions such as:

> Steel  Aluminum  Steel  Aluminum

when a sequence such as:

> Steel  Steel  Aluminum  Aluminum

would have been feasible without causing unacceptable tardiness.

However, setup reduction must not be pursued blindly. Large batches can reduce setups while increasing:

- Waiting time for urgent jobs
- WIP
- Due-date violations
- Customer response time

The relevant objective is not minimum setup time alone, but an appropriate weighted combination of setup, tardiness, and WIP.

## 2.4 Downstream starvation and upstream blocking

A work center may have low utilization because upstream scheduling does not release work at the correct time, rather than because it has excess capacity.

Process mining can detect:

- Machine idle intervals while upstream jobs are late
- Repeated absence of ready jobs
- Downstream machines becoming starved after a bottleneck delay
- Completed work waiting because the next machine is unavailable
- Jobs released in bursts rather than paced to downstream capacity

For each downstream machine, calculate the proportion of idle time caused by:

- No released jobs
- Predecessor incomplete
- Material unavailable
- Operator unavailable
- Maintenance
- Batch-release behavior

This separates genuine underutilization from flow imbalance.

## 2.5 WIP oscillation and a manufacturing bullwhip effect

In this setting, the bullwhip effect is an analogous pattern in which variability in job releases creates larger variability in queues and WIP downstream.

Analyze:

- Variability of job releases by hour or shift
- Variability of completions from upstream machines
- Queue-length variance downstream
- Correlation between release bursts and WIP spikes
- WIP accumulation after hot-job insertions
- Difference between average WIP and peak WIP
- Flow-time variance during WIP surges

A common pattern may be:

1. A bottleneck delays several jobs.
2. Upstream operations continue producing or releasing work.
3. A large batch reaches the downstream station.
4. WIP spikes and lead times become unpredictable.
5. A later period has no work because upstream capacity was consumed by recovery activity.

## 2.6 Disruption amplification

The same breakdown can have very different effects depending on queue state and schedule structure. Process mining should identify whether disruptions cause:

- Immediate loss of capacity only
- Large queue growth
- Resequencing and extra setups
- Priority inversions
- Downstream starvation
- Overtime and schedule instability
- Cascading lateness across multiple customer orders

A disruption impact matrix can classify breakdowns by machine, duration, load level, affected priority mix, and recovery approach.

# 3. Root-Cause Analysis of Scheduling Ineffectiveness

## 3.1 Limitations of local static dispatching rules

FCFS and EDD are locally simple but inadequate for a high-mix job shop because they generally do not account for:

- Remaining route length
- Downstream bottlenecks
- Sequence-dependent setup cost
- Operation criticality
- Future machine contention
- Predicted processing-time uncertainty
- Current WIP
- Breakdown risk
- Hot-job disruption cost

EDD at one work center can be counterproductive if it sends a job to a downstream bottleneck that is already overloaded. Similarly, FCFS can preserve arrival order even when a later job has substantially higher tardiness risk.

Process mining can quantify this weakness by replaying actual decisions and measuring:

- How often the selected job was not the most urgent by global slack
- How many expensive setups were caused by local decisions
- How frequently locally optimal decisions caused downstream queues
- Whether decisions differed across shifts or supervisors
- Whether the same job class performed differently under different dispatchers

## 3.2 Lack of real-time visibility

A static or locally informed system may not know:

- The true machine state
- Actual remaining processing time
- Current queue age
- Whether a predecessor is late
- Whether a downstream machine is available
- The actual setup state of the machine
- Whether a breakdown has changed the feasible routing
- Which jobs are likely to become late

Process mining exposes this problem by comparing the information available when a decision was made with the state that actually existed. It can also reveal large differences between planned and actual machine states, indicating that schedules are being executed against stale assumptions.

## 3.3 Inaccurate duration and setup estimates

The planned duration for JOB-7001’s cutting task was 60 minutes, whereas the actual duration was 66.4 minutes. One example is not enough to establish a systemic problem, but the full data set can quantify:

\[
\text{Duration Error} =
\text{Actual Duration} - \text{Planned Duration}
\]

Analyze duration error by:

- Job family
- Machine
- Operation
- Operator
- Shift
- Material
- Part complexity
- Setup state
- Lot size
- Priority or hot-job status

If planned times consistently understate P90 actual times at a bottleneck, schedules will appear feasible on paper but fail in execution.

The same analysis applies to setup estimates. A planning system using a single average setup time will systematically underestimate certain transitions and overestimate others.

## 3.4 Poor handling of sequence-dependent setup

If the system records only “setup required = true” without using the previous job’s attributes, it cannot make setup-aware sequence decisions.

Likely causes include:

- No maintained setup matrix
- No part-family classification
- No visibility of the current machine setup state
- Setup time treated as a constant
- No explicit cost for changing material, tooling, or fixture
- Urgent jobs inserted without setup impact analysis

Process mining provides the empirical transition matrix and can reveal whether setup effects are concentrated in certain machines, families, shifts, or operators.

## 3.5 Poor coordination between work centers

A job shop requires coordination across the complete route. Local decisions can cause:

- Upstream overproduction
- Downstream starvation
- Excessive WIP before a bottleneck
- Jobs being completed early at one station but waiting for days at the next
- Misalignment between heat treatment batch schedules and machining completion
- Inspection queues delaying shipment

This can be analyzed through end-to-end traces rather than only machine-level logs. For each job, identify where its elapsed time accumulates and whether upstream completion is synchronized with downstream availability.

## 3.6 Ineffective responses to breakdowns and urgent orders

A static schedule typically responds through manual expediting. This may create:

- Repeated rescheduling
- Excessive schedule churn
- Unplanned setups
- Displaced jobs becoming late
- Poor recovery after breakdowns
- Misleading due-date promises

Process mining can distinguish this from pure capacity limitation by examining what happens after similar disruptions. If one recovery policy results in substantially lower tardiness and fewer setups than another for comparable events, the recovery logic is a root cause.

## 3.7 Separating logic problems from capacity and variability problems

This distinction is critical.

### Evidence of a capacity problem

- Required load consistently exceeds practical capacity
- Queues remain high even when priority sequencing is reasonable
- Tardiness is strongly related to sustained utilization
- Adding simulated capacity materially improves outcomes
- All scheduling policies perform poorly under the same load

### Evidence of a scheduling-logic problem

- Large differences between policies at the same capacity and job mix
- Excessive setup time despite feasible setup-compatible sequences
- High-priority jobs frequently bypassed
- Downstream starvation caused by poor release timing
- Large schedule changes without corresponding external disruptions
- Strong performance variation between shifts using different dispatching practices

### Evidence of inherent process variability

- Large residual duration variation after controlling for machine, job, operator, and route
- Breakdown and rework events explain substantial delay
- Even optimal schedules experience high P90 tardiness
- Performance deteriorates nonlinearly at high utilization
- Similar decisions produce different outcomes because processing times are highly uncertain

Statistical models, matched cohorts, survival analysis, and discrete-event simulation can be used together. Process mining describes what happened; simulation and controlled comparisons estimate what might have happened under a different policy.

# 4. Advanced Data-Driven Scheduling Strategies

## Strategy 1: Dynamic, Bottleneck-Aware Dispatching

### Core logic

Replace separate local FCFS/EDD rules with a real-time dispatch score calculated whenever:

- A machine becomes available
- A task arrives
- A breakdown occurs
- A hot job is released
- A priority or due date changes

For each eligible operation \(o\), calculate a score using several normalized factors:

\[
\text{Score}_o =
w_1(\text{Due-Date Risk})
+
w_2(\text{Customer Priority})
+
w_3(\text{Remaining Route Criticality})
+
w_4(\text{Bottleneck Demand})
+
w_5(\text{Queue Age})
+
w_6(\text{Downstream Readiness})
-
w_7(\text{Setup Cost})
-
w_8(\text{Disruption Risk})
\]

Relevant features include:

- Global slack:

\[
\text{Slack}_i =
D_i - t - \widehat{\text{remaining processing and setup time}}
\]

- Remaining number of operations
- Remaining work at constrained machines
- Probability of missing the due date
- Current queue age
- Predicted downstream congestion
- Estimated transition setup from the current machine state
- Whether the downstream operation is ready or nearly ready
- Priority class and contractual penalty

A high-priority job should not automatically be selected if it creates a very large setup and will then wait behind a blocked downstream operation. Conversely, setup savings should not override a job with severe due-date risk.

### Use of process-mining insights

The weights should be informed by historical analysis:

- If due-date risk explains most tardiness, increase urgency weighting.
- If setup transitions dominate bottleneck capacity, increase setup awareness.
- If downstream starvation is common, add downstream-readiness and release-pacing terms.
- If high-priority jobs are frequently late, increase priority protection.
- If high utilization makes the system unstable, include stronger WIP controls.

Weights can be tuned using historical backtesting, simulation, or learning-to-rank methods. They should not be selected solely by intuition.

### Practical controls

To avoid constant schedule churn:

- Use rolling-horizon rescheduling
- Freeze work already started
- Freeze the next few hours unless a severe disruption occurs
- Require approval for large changes to committed jobs
- Use explicit rules for hot-job insertion
- Protect a limited amount of capacity for urgent work

A CONWIP or WIP-cap mechanism can also prevent upstream machines from releasing work into an already overloaded downstream queue.

### Pathologies addressed

- Local decision myopia
- Priority inversion
- Downstream starvation
- Excessive WIP
- Poor response to changing machine states
- Unnecessary schedule instability

### Expected KPI impact

Expected improvements include:

- Lower weighted tardiness
- Better on-time performance for critical jobs
- Reduced queue-time variance
- Lower WIP through better release pacing
- Improved bottleneck throughput
- More balanced utilization

Total utilization may decline at some non-bottleneck machines, which is acceptable if flow time and delivery performance improve.

## Strategy 2: Predictive, Robust Rolling-Horizon Scheduling

### Core logic

Use historical event data to estimate realistic task, setup, delay, and breakdown distributions. At regular intervals, solve a finite-capacity scheduling problem over a rolling horizon.

The scheduler can use:

- Predicted median processing time
- P80 or P90 processing time for risk-sensitive jobs
- Predicted setup time
- Expected machine availability
- Probability of rework
- Queue and downstream congestion
- Due-date risk
- Alternative machine capability

The scheduling engine could use:

- Constraint programming
- Mixed-integer optimization
- Stochastic programming
- Scenario-based optimization
- A heuristic search initialized by the dynamic dispatching policy

The objective can combine:

\[
\min
\left[
\alpha \sum_i w_i T_i
+
\beta \sum_i \text{WIP}_i
+
\gamma \sum \text{Setup Time}
+
\delta \sum \text{Schedule Changes}
+
\epsilon \sum \text{Overtime}
\right]
\]

### Predictive duration models

Duration models can be built using:

- Hierarchical statistical models
- Gradient-boosted regression
- Quantile regression
- Bayesian updating
- Survival or time-to-completion models

Potential predictors include:

- Part family and geometry
- Material
- Operation
- Machine
- Operator
- Shift
- Tooling and fixture
- Previous job
- Batch size
- Actual queue conditions
- Rework history
- Whether the job is urgent

Instead of predicting only one value, the model should produce a distribution or quantiles:

\[
\hat{p}_{50}, \hat{p}_{80}, \hat{p}_{95}
\]

The scheduler can use P50 for normal capacity planning and P80/P90 for jobs with severe due-date penalties.

### Predictive maintenance and availability

Breakdown logs can be used to estimate:

- Failure frequency by machine
- Mean time between failures
- Mean time to repair
- Failure hazard by operating hours
- Failure risk by shift or load condition
- Probability that a scheduled machine will be available during a future interval

If sensor data is available, remaining-useful-life or anomaly models can be incorporated. If not, a simpler machine-specific hazard model is still useful.

The scheduler can then:

- Avoid placing a critical job immediately before a likely maintenance window
- Reserve alternative capacity
- Schedule preventive maintenance during low-impact windows
- Add risk buffers at vulnerable bottlenecks
- Recalculate plans when breakdown risk changes materially

### Use of process-mining insights

The discovered process model provides:

- Actual routing probabilities
- Rework frequencies
- Operation duration distributions
- Machine eligibility
- Transition and setup behavior
- Breakdown and repair distributions
- Typical recovery patterns after disruption

The scheduler therefore uses actual execution behavior rather than idealized standard times.

### Pathologies addressed

- Unrealistic duration estimates
- Fragile schedules with no uncertainty allowance
- Unanticipated breakdowns
- Inaccurate capacity assumptions
- Excessive reliance on manual expediting
- Poor prediction of due-date risk

### Expected KPI impact

Expected benefits include:

- More reliable completion-time estimates
- Lower P90 tardiness
- Better promise-date accuracy
- Reduced recovery overtime
- Better use of alternative machines
- More stable schedules under disruption

A robust schedule may sometimes produce slightly lower nominal utilization because it protects capacity and incorporates uncertainty. The relevant comparison is total delivery performance, not nominal utilization alone.

## Strategy 3: Setup-Aware Sequencing and Intelligent Batching

### Core logic

Use the mined setup-transition matrix to sequence jobs in a way that balances:

- Setup reduction
- Due-date performance
- Job priority
- Bottleneck utilization
- WIP limits
- Maximum permitted waiting time

Jobs should be grouped into setup families based on attributes such as:

- Material
- Thickness or size
- Tooling
- Fixture
- Surface finish
- Machine program
- Heat-treatment requirements

For each bottleneck machine, sequence decisions should use estimated transition setup times rather than a binary setup flag.

Possible methods include:

- Setup-aware dispatching
- Apparent tardiness cost with setup time
- Traveling-salesperson-like sequence optimization within a job window
- Constraint programming
- Local search and swap heuristics
- Clustering followed by due-date sequencing within clusters

### Guardrails against excessive batching

Batching should be constrained by:

- Maximum wait time for any job
- Due-date slack
- Maximum batch size
- Maximum time between customer milestones
- Priority protection
- WIP caps
- Need to keep downstream machines supplied

For example, the scheduler might allow a steel-family batch to continue only while the earliest due-date job in another family has more than a defined slack threshold. Once that threshold is crossed, the urgent job overrides the setup saving.

### Setup improvement opportunities

Process mining may also identify operational improvement opportunities beyond scheduling:

- Frequent long setups by a particular machine
- Operators with significantly different setup performance
- Repeated tooling searches
- Setup tasks that could be performed externally
- Setup steps that could be standardized or parallelized
- Excessive first-job or post-maintenance setup times

These findings support SMED-like initiatives and better standard work.

### Pathologies addressed

- Excessive sequence-dependent setups
- Underestimated bottleneck capacity
- Repeated family switching
- Setup-driven queue growth
- Inconsistent setup performance

### Expected KPI impact

Expected improvements include:

- Lower setup time per job
- Higher effective bottleneck capacity
- Reduced queue growth
- Better throughput
- Lower setup-related variability

The principal risk is over-batching. Therefore, setup savings must be evaluated jointly with tardiness and WIP.

## Optional Strategy 4: Global Finite-Capacity Critical-Chain Scheduling

For particularly constrained periods, Precision Parts could use a global finite-capacity scheduler that explicitly models:

- All eligible machines
- Alternative routings
- Operator availability
- Setup transitions
- Maintenance windows
- Job precedence
- Due-date penalties
- WIP caps
- Critical bottleneck capacity

This would be used for a daily or shift-level baseline plan, while Strategies 1 and 2 manage real-time execution. The combination is usually more practical than trying to solve the entire job shop from scratch every few minutes.

# 5. Simulation, Evaluation, and Continuous Improvement

## 5.1 Discrete-event simulation

A discrete-event simulation should be built before production deployment. It should model:

- Job arrivals and releases
- Actual routing variants
- Operation precedence
- Machine calendars
- Alternative resources
- Processing-time distributions
- Setup-transition matrices
- Operator availability
- Breakdowns and repair times
- Priority changes and hot jobs
- WIP limits
- Dispatching and rescheduling policies
- Rework and inspection behavior

The simulation should be parameterized from process-mining outputs, not from simple averages. For example:

- Use a distribution of cutting durations by part family and machine
- Use conditional setup-time distributions by transition
- Model breakdown frequency by machine
- Model routing variants by job type
- Model rework probability by operation and product family

Where possible, preserve correlations. For example, highly loaded periods may have longer effective durations or more setup errors. Treating all events as independent can make the simulation unrealistically optimistic.

## 5.2 Baselines and candidate policies

At minimum, compare:

1. Current local FCFS/EDD policy
2. Dynamic bottleneck-aware dispatching
3. Predictive rolling-horizon scheduling
4. Setup-aware sequencing
5. Combinations of the above

All policies should be tested on the same historical job portfolios and disruption scenarios. Useful performance measures include:

- On-time delivery percentage
- Weighted tardiness
- Mean and P90 tardiness
- Flow time and P90 flow time
- Average and peak WIP
- Setup hours
- Bottleneck utilization
- Total throughput
- Machine starvation and blocking
- Overtime
- Schedule changes
- Hot-job response time
- Promise-date accuracy

A policy that reduces average tardiness but greatly increases P95 tardiness may not be acceptable for customer service.

## 5.3 Scenarios to test

The simulation should include at least:

### Normal operating load

The historical average job mix and typical machine availability.

### High-load periods

For example, 90%, 95%, and 100% of nominal demand. This reveals whether the policy is stable as utilization approaches capacity.

### Frequent bottleneck breakdowns

Vary:

- Breakdown frequency
- Breakdown duration
- Availability of alternate machines
- Timing relative to due dates

### Hot-job scenarios

Test:

- One urgent job per day
- Multiple urgent jobs
- Hot jobs arriving near bottleneck saturation
- Different hot-job insertion policies

### Setup-heavy product mix

Increase the proportion of jobs with expensive family transitions and compare batching policies.

### High duration variability

Use P90 or heavier-tailed processing distributions to test schedule robustness.

### Routing and rework variability

Increase the frequency of rework loops or alternative routings.

### Capacity changes

Test:

- Adding overtime
- Adding a parallel machine
- Cross-training operators
- Reducing setup time
- Removing a bottleneck machine temporarily

### Policy sensitivity

Vary the weights assigned to:

- Tardiness
- Setup
- WIP
- Priority
- Schedule stability
- Capacity protection

Simulation results should use multiple random replications and confidence intervals. Common random numbers can be used so that policies are compared under equivalent disruption and arrival conditions.

## 5.4 Validation

The model should be validated against historical periods not used for calibration. Compare:

- Queue-length distributions
- Machine utilization
- Flow-time distributions
- Setup-time distributions
- Breakdown recovery patterns
- On-time delivery
- WIP levels
- Routing variant frequencies

Validation should focus on tails as well as averages. A model that reproduces average flow time but not queue spikes or P95 tardiness is not adequate for this problem.

## 5.5 Continuous monitoring and adaptation

Once a policy is deployed, process mining should become an ongoing control system rather than a one-time study.

### Operational dashboards

Monitor by machine, job family, customer, and priority:

- On-time delivery
- Weighted tardiness
- Queue age
- Queue length
- WIP
- Productive, setup, idle, starved, and blocked time
- Processing-time prediction error
- Setup-time prediction error
- Breakdown frequency and recovery time
- Number of schedule changes
- Hot-job displacement cost
- Bottleneck load

### Online conformance monitoring

Compare actual execution with the expected policy:

- Were jobs dispatched in accordance with the approved rule?
- Were freeze-window jobs changed?
- Were WIP limits exceeded?
- Were setup-compatible jobs bypassed?
- Were machine and operator constraints respected?
- Did actual routing deviate from the assumed model?

### Drift detection

Detect changes in:

- Job mix
- Routing patterns
- Processing-time distributions
- Setup-transition behavior
- Breakdown rates
- Operator or shift performance
- Customer priority mix
- Arrival rates
- Bottleneck location

Useful methods include:

- Control charts
- Rolling-window comparisons
- Population stability measures
- Distribution-distance tests
- Change-point detection
- Model residual monitoring

For example, a sustained increase in P90 setup duration at MILL-03 should trigger recalibration of the setup model. A new product family may require a new routing variant and transition family.

### Policy triggers

Automatic or semi-automatic triggers can include:

- Bottleneck utilization above a threshold for several periods
- Queue age exceeding a due-date-risk limit
- Forecast on-time delivery falling below target
- Breakdown hazard increasing
- Prediction error exceeding a tolerance
- WIP exceeding its control limit
- Setup time rising above the modeled range

The response could be:

- Recalculate dispatching weights
- Reoptimize the rolling horizon
- Open an alternate machine
- Reserve overtime
- Move preventive maintenance
- Adjust WIP release limits
- Retrain duration or setup models
- Escalate capacity planning decisions

## 5.6 Governance and controlled deployment

A practical deployment path is:

1. **Diagnostic phase:** reconstruct historical performance and identify bottlenecks.
2. **Shadow mode:** generate recommendations without changing operator decisions.
3. **Backtesting and simulation:** compare candidate policies.
4. **Pilot at one bottleneck work center:** use visible recommendations and operator feedback.
5. **Champion-challenger operation:** compare the current policy against the new policy.
6. **Progressive rollout:** extend to other work centers.
7. **Continuous process mining:** monitor performance, drift, and exceptions.

Operators and planners should be able to override recommendations, but override reasons should be logged. Those overrides become valuable data for identifying missing constraints, quality issues, or practical rules not yet represented in the scheduling model.

The overall objective is not simply to keep every machine busy. It is to create a stable, globally coordinated flow that minimizes weighted tardiness and WIP while controlling setup effort, disruption exposure, and lead-time variability. Process mining supplies the factual operating model; predictive analytics supplies better estimates; optimization and simulation test the alternatives; and continuous monitoring keeps the scheduling strategy aligned with changing shop-floor conditions.
