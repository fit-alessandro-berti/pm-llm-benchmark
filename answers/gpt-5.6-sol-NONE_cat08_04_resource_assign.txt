## 1. Analyzing Resource Behavior and Assignment Patterns

### 1.1 Prepare and enrich the event log

The analysis should begin by converting the log into a consistent case-event model:

- **Case ID:** Ticket ID
- **Activity:** Create, assign, work start, work end, escalate, reassign, resolve, close, reopen
- **Event timestamp:** Preserve start and completion timestamps where available
- **Resource:** Agent performing work or assignment decision
- **Case attributes:** Priority, category, channel, required skill, creation time, SLA target
- **Resource attributes:** Tier, skill set, proficiency level, shift, team, location, availability
- **Assignment attributes:** Assigned agent, assignment reason, source queue, destination queue
- **Outcome attributes:** Resolution code, SLA status, reopen status, customer satisfaction

Assignment events should distinguish the **decision maker** from the **recipient**. For example, an `Assign L2` event performed by Dispatcher should also have `Assigned Agent = B12`. Without this distinction, handover and workload analyses may incorrectly treat the dispatcher as the ticket owner.

Useful derived fields include:

- Queue time between assignment and work start
- Active handling time between work start and work end
- End-to-end resolution time
- Number of assignments, reassignments, escalations, and tiers visited
- First assigned tier and final resolver
- Required-skill-to-agent-skill match
- Remaining SLA time at each assignment
- Concurrent workload at assignment time
- Business-hours-adjusted duration
- L1 first-contact or first-call resolution indicator
- Whether the ticket was reopened
- Skill level of work relative to agent proficiency

Data-quality checks should cover missing events, inconsistent timestamps, duplicate events, skill naming differences such as `DB-SQL` versus `Database-SQL`, and tickets still open at the extraction date.

---

### 1.2 Agent- and tier-level performance metrics

Metrics should be segmented by priority, category, required skill, channel, time period, and ticket complexity. Raw comparisons between agents can otherwise be misleading because specialists may receive inherently harder work.

#### Workload and utilization

For each agent and tier:

- Tickets assigned, accepted, worked, and resolved
- Active handling hours
- Number of concurrent open tickets
- Queue backlog over time
- Utilization: active work time divided by available scheduled time
- Workload variance, coefficient of variation, or Gini index across agents
- Percentage of work performed outside normal hours
- Arrival-to-capacity ratio by hour, day, and skill queue
- Aging distribution of assigned tickets

A distinction is needed between:

- **Assigned workload:** Tickets owned by an agent
- **Active workload:** Tickets currently being worked
- **Effective workload:** Work adjusted for priority and complexity

A P1 infrastructure incident should not be weighted the same as a routine P4 access request.

#### Time and quality metrics

- Median and percentile queue time, handling time, and resolution time
- Time to first response
- Time to first meaningful work
- Mean time to resolve, preferably supplemented with median, P75, P90, and P95
- SLA attainment by agent, tier, category, and skill
- Reopen and repeat-contact rate
- Escalation and reassignment rate
- Resolution quality or customer satisfaction where available
- Touch time versus elapsed time

Percentiles are important because averages can hide long-tail delays.

#### L1 effectiveness

- First-contact resolution rate
- L1 resolution rate by category and required skill
- Average diagnostic time before escalation
- Percentage of L1 escalations later resolved using standard procedures
- Escalations rejected or returned by L2
- “Bounce” rate from L2 back to L1
- L1 resolution rate adjusted for ticket mix
- Avoidable escalation rate

A high escalation rate is not automatically bad. Immediate escalation of a confirmed firewall fault may be better than 40 minutes of ineffective L1 troubleshooting.

#### Skill and ticket-type behavior

For each agent:

- Frequency of handling each category and required skill
- Success and resolution time by skill
- Reassignment rate after receiving each skill type
- Effective skill inferred from successful historical resolutions
- Difference between documented and observed capability
- Proportion of work below, at, or above proficiency level

This creates an empirical agent-skill performance matrix rather than relying only on HR skill records.

---

### 1.3 Discover actual assignment and handover behavior

#### Process discovery and conformance checking

Discover process models for:

- All incidents
- Each priority
- Each category or required skill
- SLA-compliant versus breached tickets
- First-contact resolution versus escalated tickets

The discovered model will show whether the actual sequence is:

`Create  Assign L1  Work L1  Escalate  Assign L2  Resolve`

or whether tickets commonly exhibit loops such as:

`Assign L2  Reassign  Assign L2  Escalate L3  Return L2`.

Conformance checking should compare this behavior with the intended operating model and quantify:

- Skipped triage steps
- Unauthorized tier jumps
- Excessive assignment loops
- Work beginning before formal assignment
- Tickets assigned to agents without required skills
- Escalations that do not satisfy policy
- Delayed escalation despite low remaining SLA time

#### Handover-of-work social network

Create a directed resource network where an edge from Agent A to Agent B represents a ticket handover. Edge weight can represent:

- Number of handovers
- Average delay after handover
- SLA breach rate of handed-over tickets
- Frequency of returns from B to A
- Skill mismatch at the initial assignment

This identifies:

- Agents who act as routing hubs
- Specialists receiving disproportionate inbound work
- Recurrent “ping-pong” relationships
- Tier or team silos
- Single points of failure
- Informal expert networks not reflected in the official structure

Organizational mining can also examine subcontracting, joint-case, and working-together networks.

#### Role discovery

Cluster agents by actual activity and ticket profile rather than formal title. Possible discovered roles include:

- L1 generalist
- Access-management resolver
- CRM specialist
- Database specialist
- Escalation triager
- Incident coordinator
- Senior specialist handling routine work

Differences between formal and discovered roles indicate either obsolete role definitions, hidden dependencies, or poor routing.

#### Assignment-pattern comparison

For each queue, determine whether assignments are actually:

- Round-robin
- Self-selected
- Dispatcher-selected
- Skill-based
- Based on personal relationships
- Routed to the agent who most recently handled a similar case
- Concentrated on a few “safe” specialists

Compare assignment shares with what round-robin or policy-based allocation would predict. A large divergence suggests informal assignment behavior.

---

### 1.4 Skill utilization analysis

Normalize skills into a taxonomy, for example:

- Networking
  - Routing
  - Firewall
  - VPN
- Database
  - SQL
  - Performance
- Applications
  - CRM
- ERP

Represent proficiency separately, such as novice, competent, advanced, or expert.

For every assignment, calculate:

1. Whether the agent has the required skill
2. Whether proficiency is sufficient for estimated complexity
3. Whether another available suitable agent existed
4. Whether the assignment led to resolution, reassignment, or escalation
5. Whether the assigned agent was substantially overqualified

Key skill metrics include:

- Skill-match rate at first assignment
- Skill-match rate at each tier
- Resolution probability by agent-skill pair
- Queue time by required skill
- Specialist utilization by skill
- Percentage of specialist time spent on routine work
- Tickets waiting for a skill while qualified agents are idle
- Concentration of a skill among agents
- Capacity-to-demand ratio by skill and time period

“Below skill level” should be defined carefully. A specialist handling a routine ticket is not necessarily wasteful if demand is low. It becomes a concern when specialist capacity is constrained and eligible generalists were available.

## 2. Identifying Resource-Related Bottlenecks and Issues

### 2.1 Skill-capacity bottlenecks

For each skill queue and time interval, compare:

- Ticket arrival rate
- Required effort
- Number of available qualified agents
- Effective capacity based on schedules and proficiency
- Queue length and ticket aging
- SLA time remaining

Evidence of a skill bottleneck includes:

- High queue time but normal active handling time
- Persistent backlogs for a specific skill
- High utilization of a small specialist group
- Strong dependence on one or two agents
- SLA breaches clustered around those agents’ shifts or absences
- Tickets waiting while unqualified agents are available

For example, if `Networking-Firewall` tickets have a median handling time of 40 minutes but a median pre-work queue time of 3 hours, the primary issue is capacity or routing—not technical execution.

---

### 2.2 Reassignment and escalation delay

Measure the incremental effect of each additional handover:

- Time from reassignment decision to next work start
- Total idle time accumulated between owners
- Additional handling time due to repeated diagnosis
- Increase in SLA breach probability per reassignment
- Probability of reopening after multiple handovers

Recommended analyses include:

- Matched cohorts with similar priority, category, complexity, channel, and creation time
- Regression or survival models controlling for ticket difficulty
- Comparison of tickets with zero, one, two, and three or more reassignments
- Sequence analysis to distinguish beneficial specialist escalation from avoidable bouncing

Example output:

| Reassignments | Median Resolution Time | SLA Breach Rate |
|---:|---:|---:|
| 0 | 3.2 hours | 8% |
| 1 | 5.1 hours | 17% |
| 2 | 8.7 hours | 31% |
| 3+ | 15.4 hours | 52% |

The figures should be calculated from the full log, not inferred from the snippet.

A useful impact measure is:

\[
\text{Incremental reassignment delay} =
E(T \mid n\text{ reassignments}) -
E(T \mid n-1\text{ reassignments})
\]

after controlling for complexity and priority.

---

### 2.3 Incorrect initial assignment

Define incorrect initial assignment using observable outcomes, such as:

- Agent lacked the required skill
- Ticket was transferred without substantive work
- Ticket was reassigned within a short threshold
- Destination agent changed the required-skill classification
- Ticket ultimately resolved by a different specialist group
- Initial queue historically has a very low resolution probability for that ticket type

Analyze error rates by:

- Dispatcher
- L1 agent
- Channel
- Category
- Time of day
- Ticket description quality
- Required skill
- Assignment method

The cost should include:

- Delay before correct routing
- Duplicate diagnostic effort
- Number of extra touches
- SLA breaches attributable to the delay
- Specialist interruption cost

For instance, compare P2 tickets initially matched to the correct skill with otherwise similar P2 tickets initially mismatched.

---

### 2.4 Overloaded and underutilized resources

Identify overload through:

- Sustained high utilization
- High concurrent case count
- Long queues behind an agent
- Increasing response time as workload grows
- High overtime
- Rising error or reassignment rates at peak load

Identify underutilization through:

- Low active workload during periods when matching tickets are waiting
- Low assignment share despite appropriate skills
- Disproportionately easy ticket mix
- Agents in a skill group receiving little work because routing records are incomplete

Performance assessments should be case-mix adjusted. A specialist may close fewer tickets because those tickets are more complex.

Control charts can distinguish persistent underperformance from normal variation. Agents should not be penalized for data artifacts, unusual shifts, mentoring duties, major incidents, or incomplete work-time logging.

---

### 2.5 Link assignments to SLA breaches

Create an event-level timeline for each breach and calculate:

- SLA time consumed before first assignment
- SLA time consumed in L1
- SLA time consumed in queues
- SLA time consumed after reassignments
- Active work time
- Time waiting for a required skill
- Time waiting for customer or third party, if applicable

Build an explanatory model where SLA breach is the outcome and predictors include:

- Initial skill match
- Number of reassignments
- Number of tiers visited
- Agent workload at assignment
- Queue length
- priority, category, channel, complexity
- time of day and weekday
- specialist availability
- ticket description quality
- dispatcher or assignment mechanism

Report both associations and estimated incremental effects. Examples:

- Percentage of breached tickets with an initial skill mismatch
- Adjusted odds ratio for breach after a mismatch
- Percentage of breach delay spent waiting after reassignment
- Breaches potentially avoidable if correctly routed at first assignment

Care is needed not to claim causality from correlation alone. Hard tickets may both breach and be reassigned frequently.

## 3. Root Cause Analysis for Assignment Inefficiencies

### 3.1 Potential root causes

#### Assignment rules ignore relevant constraints

Round-robin may balance ticket counts while ignoring:

- Required skill
- Skill proficiency
- ticket complexity
- active workload
- working schedule
- current queue age
- SLA urgency
- likelihood of successful resolution

This can produce nominally equal distribution but materially unequal effort and poor first-time routing.

#### Skill profiles are inaccurate or incomplete

Profiles may be:

- Outdated after training or role changes
- Too broad to distinguish CRM support from database support
- Self-reported without proficiency validation
- Missing informal expertise
- Unlinked to certifications and historical results

A mismatch between documented skills and observed successful resolutions is evidence of profile-quality problems.

#### Poor categorization and requirement detection

L1 or customers may select generic categories such as `Software-App`, while the underlying problem requires `Database-SQL`. Indicators include:

- Category changes late in the case
- Required skill changing after specialist review
- Categories with high reassignment entropy
- Frequent free-text clues that contradict selected categories
- High error rates for email or portal tickets with sparse descriptions

#### Lack of real-time workload visibility

Dispatchers may know who is qualified but not who is:

- Already handling a P1
- Near shift end
- Absent
- Carrying a large backlog
- Waiting on several simultaneous cases

Static assignment tables therefore become obsolete during peaks.

#### L1 capability or empowerment gaps

Excessive escalation may result from:

- Missing knowledge articles
- Limited system permissions
- Inadequate training
- Fear of SLA penalties
- Unclear escalation criteria
- Incentives favoring short L1 handling time over resolution
- Lack of access to specialist consultation

#### Organizational and process causes

Other possibilities include:

- Narrow skill ownership creating single points of failure
- Specialist queues accepting work without triage
- Metrics rewarding ticket closure count rather than end-to-end flow
- Shift coverage misaligned with demand
- Manual dispatcher preferences
- Poor handover documentation causing repeated diagnosis

---

### 3.2 Variant analysis

Separate cases into variants such as:

- Correct first assignment and direct resolution
- L1 resolution
- One justified escalation and resolution
- Multiple within-tier reassignments
- Tier bouncing
- Reopened after resolution
- SLA compliant versus breached

For each variant, compare:

- Ticket characteristics
- Initial required skill
- assignment method
- First assigned agent’s proficiency
- workload at assignment
- shift and time of day
- queue length
- description completeness
- dispatcher
- active and waiting time
- outcome quality

A contrast such as “smooth CRM tickets versus reassigned CRM tickets” may reveal that successful tickets had an explicit product name, were assigned to CRM-proficient agents, and arrived during core coverage hours.

---

### 3.3 Decision mining

Decision mining analyzes process choice points such as:

- Assign L1 or route directly to L2
- Resolve at L1 or escalate
- Assign to Agent B08 or B12
- Escalate to L2 or L3
- Reassign within tier or retain ownership

Candidate explanatory attributes include:

- Category, priority, channel, and text-derived features
- Required skill and estimated complexity
- agent proficiency
- workload and availability
- time remaining to SLA
- queue length
- prior incidents for the customer or asset
- diagnostic results
- knowledge article availability

Decision trees or interpretable rules can reveal actual behavior, for example:

> P2 network tickets are usually sent to B08 unless B08 is absent; when B08 has more than six open cases, dispatchers still assign to B08, and waiting time rises sharply.

Compare learned decision rules with policy. This distinguishes policy deficiencies from noncompliance.

## 4. Data-Driven Resource Assignment Strategies

The strategies should be combined in a controlled routing framework rather than implemented as isolated changes.

### Strategy 1: Proficiency-weighted skill-based routing

**Issue addressed:** Initial skill mismatches and unnecessary reassignments.

**Approach:** Maintain an agent-skill matrix with proficiency scores and route tickets only to agents meeting a minimum skill threshold. Rank eligible agents using factors such as:

- Required skill fit
- Proficiency
- Historical success for similar tickets
- Reassignment and reopen rate
- Tier appropriateness
- Current availability

A conceptual score could be:

\[
Score(a,t)=
w_1 SkillFit+
w_2 Proficiency+
w_3 SuccessProbability-
w_4 ExpectedDelay-
w_5 OverqualificationPenalty
\]

The overqualification penalty protects scarce experts when a less specialized qualified agent is available.

**Process-mining basis:** Skill mismatch rates, handover networks, discovered specialist roles, and historical resolution performance identify which skill-agent combinations work well.

**Data required:**

- Normalized ticket skill requirements
- Agent skills and proficiency
- Historical outcomes by agent and ticket type
- Availability and tier
- Complexity estimate
- reopen and reassignment data

**Expected benefits:**

- Higher correct-first-assignment rate
- Fewer handovers
- Shorter queue and resolution time
- Better specialist utilization
- Lower breach rates for skill-constrained tickets

A fallback path must exist when no qualified agent is immediately available.

---

### Strategy 2: Workload- and SLA-aware assignment

**Issue addressed:** Overloading preferred agents while eligible colleagues remain underused.

**Approach:** Among skill-qualified agents, route based on predicted completion risk rather than ticket count alone. Include:

- Active and queued effort
- Ticket priorities already assigned
- Estimated remaining effort
- shift availability
- concurrent work limits
- SLA time remaining
- expected time to start and resolve

A useful objective is to minimize expected weighted lateness:

\[
\min \sum_t PriorityWeight_t
\times
P(\text{SLA breach}_t)
\]

subject to skill, schedule, and concurrency constraints.

**Process-mining basis:** Historical queue times by workload level show when particular agents or teams become bottlenecks. Workload snapshots at assignment time can quantify the risk of adding another case.

**Data required:**

- Real-time agent availability
- Open workload and ticket status
- Predicted effort or remaining time
- SLA targets and time remaining
- Skills and proficiency
- shift calendars and planned absences

**Expected benefits:**

- More even effective workload
- Reduced queue time
- Lower P2/P3 SLA risk
- Fewer assignments to unavailable agents
- Better use of underutilized qualified resources

Urgent-ticket routing should avoid starving P3/P4 work indefinitely; aging factors and reserved capacity can protect lower priorities.

---

### Strategy 3: Predictive ticket classification and assignment

**Issue addressed:** Incorrect categories and delayed discovery of the true required skill.

**Approach:** Use historical structured data and ticket text to predict:

- Required skill
- resolver group
- likely tier
- expected complexity
- probability of L1 resolution
- expected handling time
- reassignment risk

Inputs can include description keywords, affected asset, customer, product, error codes, channel, category, and similar past incidents.

Predictions should be confidence-based:

- High confidence: automatic routing
- Medium confidence: recommended destination for dispatcher approval
- Low confidence: enhanced triage or clarification request

**Process-mining basis:** Successful case variants provide labels for final resolver, true skill, and resolution path. Reassigned cases reveal common classification errors.

**Data required:**

- Ticket descriptions and structured fields
- Final resolver group and final skill
- configuration item or asset data
- historical assignment sequence
- resolution codes
- quality-reviewed labels

**Expected benefits:**

- Better first-time routing
- Earlier identification of database, firewall, or application dependencies
- Lower dispatcher effort
- Shorter time to specialist engagement
- Fewer category changes and reassignment loops

The model should be monitored for drift and should provide explainable recommendations.

---

### Strategy 4: Evidence-based L1 resolution and escalation rules

**Issue addressed:** Excessive escalation and unnecessary L2/L3 involvement.

**Approach:** Identify ticket families that L1 can resolve safely and provide:

- Guided diagnostic workflows
- Knowledge articles
- scripts and automation
- expanded permissions where risk permits
- specialist “swarming” consultation without ownership transfer
- explicit escalation triggers and time boxes

Examples of routing rules:

- Route directly to L2 when historical L1 resolution probability is very low and delay threatens the SLA.
- Keep at L1 when the ticket matches a known procedure with high L1 success.
- Escalate after specified failed diagnostic steps, not merely after a fixed elapsed time.

**Process-mining basis:** Compare successful L1 variants with escalated variants and identify avoidable escalations resolved using standard actions.

**Data required:**

- L1 diagnostic activities
- resolution codes
- knowledge article usage
- escalation reason
- ticket type and complexity
- downstream specialist action
- permission and tool constraints

**Expected benefits:**

- Higher first-contact resolution
- Lower specialist workload
- Faster resolution of routine cases
- More consistent escalation quality
- Fewer returns from L2 to L1

The goal is not simply to maximize L1 resolution; it is to minimize end-to-end delay while maintaining quality.

---

### Strategy 5: Dynamic capacity and cross-skilling

**Issue addressed:** Recurrent skill bottlenecks, poor shift coverage, and dependence on a few experts.

**Approach:**

- Forecast demand by priority and skill
- Adjust schedules and on-call coverage
- Temporarily move cross-skilled agents to high-demand queues
- Reserve specialist capacity for P1/P2 incidents
- Cross-train agents in high-volume, moderate-complexity skills
- Create backup coverage for single-expert skills
- Use real-time thresholds to trigger queue support

**Process-mining basis:** Arrival patterns, skill queue backlogs, utilization, and social-network concentration show when and where capacity is insufficient.

**Data required:**

- Historical demand by interval and skill
- handling-time distributions
- schedules, leave, and availability
- cross-skill eligibility
- service-level targets
- forecast events such as releases or maintenance

**Expected benefits:**

- Reduced skill-specific queues
- Less dependence on individual specialists
- Improved peak-time SLA compliance
- More resilient service coverage
- Better balance across tiers

---

### Recommended routing hierarchy

A practical decision sequence is:

1. Confirm priority and estimate required skill and complexity.
2. Determine whether L1 resolution is appropriate.
3. Filter agents by minimum skill, authorization, tier, and availability.
4. Estimate start time, completion time, and SLA risk for each eligible agent.
5. Apply penalties for overloading scarce experts or assigning work below their level.
6. Assign to the agent with the lowest expected cost or risk.
7. Re-evaluate if no work begins within a defined threshold.
8. Record the recommendation, decision, and override reason for future mining.

Human overrides should remain possible, but they should be logged and analyzed.

## 5. Simulation, Implementation, and Monitoring

### 5.1 Business process simulation

Build a discrete-event simulation or digital twin using the mined process as the baseline.

#### Calibrate the model with historical data

Include:

- Ticket arrival distributions by priority, category, skill, channel, and time
- Activity and handling-time distributions
- Queue and waiting-time distributions
- branching probabilities for resolution, escalation, reassignment, and reopen
- agent calendars, skills, proficiency, and capacity
- prioritization rules
- SLA clocks, including pauses if contractually valid
- interruptions from major incidents
- customer and third-party waiting states

Use distributions rather than simple averages because incident workloads are variable and often heavy-tailed.

#### Test scenarios

Compare:

1. Current round-robin/manual baseline
2. Skill-based routing
3. Skill plus workload-aware routing
4. Predictive routing
5. Revised L1 escalation rules
6. Dynamic cross-tier capacity
7. Combined strategy
8. Stress scenarios such as a network outage, specialist absence, or demand surge

#### Simulation outputs

Measure:

- SLA attainment by priority
- Median and P90 resolution time
- Time to first meaningful work
- queue time by skill and tier
- reassignment and escalation count
- L1 resolution rate
- utilization by agent and skill
- specialist time spent on routine work
- backlog and aging
- probability of overload
- cost per resolved ticket
- reopen rate, if modeled

Run multiple replications and report confidence intervals. Perform sensitivity analysis for forecast errors, handling-time uncertainty, absences, and model thresholds.

Validate the baseline by checking whether simulated performance reproduces observed historical patterns before trusting scenario results.

---

### 5.2 Implementation plan

#### Phase 1: Data and policy foundation

- Standardize event semantics and skill taxonomy
- Separate actor from assigned recipient
- Clean and validate agent profiles
- Define skill proficiency and ticket complexity scales
- Document intended assignment and escalation rules
- Establish baseline KPIs
- Add fields for assignment recommendation, actual decision, and override reason

#### Phase 2: Controlled pilot

Pilot in one or two high-volume areas, such as CRM and network support:

- Start with decision support rather than fully automatic assignment
- Show dispatchers recommended agents and rationale
- Maintain manual override
- Randomize or phase rollout where operationally feasible
- Monitor quality, fairness, and unintended queue effects

Compare pilot performance with a matched control queue or pre-pilot baseline.

#### Phase 3: Expand and automate

- Automate only high-confidence routing
- Integrate real-time workload and availability
- Introduce L1 guided resolution and dynamic capacity rules
- Review model performance monthly
- Retrain prediction models as categories, applications, and staffing change

#### Governance

- Do not use mined performance metrics as unreviewed individual scorecards.
- Adjust for ticket mix, shift, complexity, and non-ticket responsibilities.
- Audit routing for systematic exclusion or favoritism.
- Maintain explainability and override capability.
- Define ownership for skill-data quality and model changes.

### 5.4 KPI targets and monitoring cadence

Targets should be set after baselining. Illustrative targets might include:

- Reduce reassignment rate by 25–40%
- Increase first-assignment skill match by 15–25 percentage points
- Reduce P2/P3 queue time by 20%
- Improve P2/P3 SLA attainment by 10–15 percentage points
- Increase L1 resolution for eligible ticket families without increasing reopens
- Reduce specialist routine-work share
- Reduce workload inequality across qualified agents

Monitoring cadence:

- **Real time:** Queue aging, capacity, P1/P2 risk, skill gaps
- **Daily:** Assignment quality and overload exceptions
- **Weekly:** SLA, reassignment, escalation, and pilot results
- **Monthly:** Skill profiles, model drift, fairness, staffing, and training needs
- **Quarterly:** Policy review, simulation refresh, and capacity planning

Statistical process-control charts should distinguish sustained improvement from random fluctuation. Any gains should also be checked against reopen rate, customer satisfaction, and resolution quality so that faster routing does not produce poorer outcomes.

## Overall Recommendation

TechSolve should replace tier-only round-robin assignment with a layered routing model combining:

1. Accurate skill and complexity detection  
2. Minimum skill and authorization filtering  
3. Workload- and SLA-aware agent selection  
4. Evidence-based L1 resolution and escalation  
5. Dynamic capacity management  

Process mining should serve both as the diagnostic mechanism and the ongoing control system. The central objective is not merely equal ticket allocation, but assigning each ticket to the least specialized qualified resource who can resolve it within the SLA, while preserving scarce specialist capacity and minimizing avoidable handovers.
