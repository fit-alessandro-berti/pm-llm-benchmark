## 1. Analyzing Resource Behavior and Assignment Patterns

### 1.1 Performance metrics per agent and tier

I would compute the following, segmented by agent, tier, priority, category, and required skill:

| Metric | Definition / Computation | What It Reveals |
|---|---|---|
| **Utilization (occupancy)** |  processing time ÷ available working time (per calendar) | Overloaded (>~85%) vs. underutilized agents |
| **Workload share** | Tickets/activities handled per agent vs. tier average | Round-robin may equalize *counts* but not *effort* |
| **Processing time per activity** | `Work End  Work Start`, per agent/skill (median, p90) | Relative proficiency; slow outliers |
| **Queue time per assignment** | `Work Start  Assign timestamp`, per skill/tier | Where demand exceeds capacity |
| **First-Contact Resolution (FCR)** | % of tickets closed at L1 with no escalation, per agent and per category | L1 effectiveness; escalation-prone agents |
| **Escalation rate per L1 agent** | Escalations initiated ÷ tickets handled | Agents who "reflexively" escalate |
| **Handovers per ticket** | Count of assign/reassign events per case | Assignment quality (target: trend toward 1) |
| **Skill-match rate** | % of assignments where `Required Skill  Agent Skills` | Direct measure of misassignment |
| **Time-to-right-agent** | Creation timestamp  assignment to the agent who ultimately resolves | End-to-end cost of bad routing |
| **SLA compliance rate** | Breach rate sliced by agent, tier, skill, priority, reassignment count | Links behavior to business outcomes |

### 1.2 Revealing the *actual* assignment logic via organizational mining

- **Handover-of-work social network:** Build a directed graph where nodes are agents and edge weights = number of handovers (AB). This exposes the *real* escalation pathways: dominant L1L2 flows, unexpected L2L2 lateral shuffles, and any L3L1 backward flows. Overlay this on the *documented* escalation matrix to quantify deviation from policy.
- **Subcontracting (ping-pong) analysis:** Detect reciprocal handovers (ABA). High reciprocity between an agent pair signals unclear ownership, ambiguous skill boundaries, or "ticket bouncing" — a direct driver of delay.
- **Working-together analysis:** Agents co-occurring on the same cases reveal informal collaboration clusters (often skill silos). If Network specialists never appear on the same tickets as Security specialists, cross-functional tickets (e.g., firewall change with IAM impact) will predictably bounce.
- **Role discovery:** Build a resource–activity profile vector per agent (which activities/skills they actually handle, at what volume and speed) and cluster them. The discovered roles are compared with formal tiers. Typical findings: a subset of "L1" agents who de facto perform L2 work in certain categories (candidates for upskilling/shift-left), and L2 agents whose profile is indistinguishable from L1 (misallocated capacity).
- **Conformance checking against the intended logic:** Define a reference routing model (e.g., "P2 Network  L2 Networking-Firewall pool") and use alignment-based conformance to measure how often actual assignments deviate, and *which* deviations correlate with good vs. bad outcomes. Not all deviation is bad — the log may reveal that dispatchers' manual overrides sometimes *outperform* the official rule, which is itself a policy improvement insight.

**Illustrative tie-back to the snippet:** INC-1002 (P2, phone, self-assigned by L1 Agent A02 who lacks `Networking-Firewall`) was statistically near-certain to escalate. The handover graph and decision mining would quantify how often this pattern occurs and its cost, converting an anecdote into a business case.

### 1.3 Skill utilization analysis

- **Skill–resource matrix:** For each required skill, which agents actually resolve those tickets (volume, success rate, median duration). This produces a **data-derived proficiency score** per agent-skill pair, replacing self-reported skill profiles.
- **Skill coverage / "bus factor":** Count of competent agents per skill. Skills with coverage = 1 are single points of failure; map their coverage against shift calendars to find hours of the day/week with *zero* coverage.
- **Overqualification leakage:** For each L2/L3 specialist, compute the share of their working time spent on tickets that historically resolve at L1 (same category/complexity, high L1 success rate). Multiply leaked hours by the loaded cost differential  a concrete €/£/$ figure for "specialists doing L1 work."
- **Skill scarcity vs. demand curves:** Plot arrival rate per required skill by hour/day against available skilled capacity. Chronic queue build-up at specific times localizes the bottleneck precisely (e.g., "Firewall demand peaks Monday 08:00–11:00; only one specialist starts before 10:00").

## 2. Identifying Resource-Related Bottlenecks and Issues

Each suspected issue gets a specific, quantifiable diagnostic:

**a) Skill-capacity bottlenecks.** Rank skills by average queue time (`Work L2 Start  Assign L2`). Validate that the queue is a *capacity* problem (utilization of that skill pool >85% during queue build-up) vs. an *assignment* problem (skilled agents idle while tickets wait — visible when queue time is high but pool utilization is low; that points at the dispatcher/round-robin, not headcount).

**b) Reassignment delay.** For each `Reassign` event, compute: (i) time from reassign to next work start, and (ii) re-triage overhead. Aggregate: **average delay per reassignment** × frequency. Then compare case cohorts:

| Cohort | Median cycle time | SLA breach rate |
|---|---|---|
| 0 reassignments | baseline | baseline |
| 1 reassignment | e.g., 1.8× baseline | e.g., +22 pts |
| 2+ reassignments | e.g., 3.1× baseline | e.g., +45 pts |

*(Figures illustrative — to be computed from the log.)*

**c) Incorrect initial assignments.** Two measures: (i) the **skill-match rate at first assignment** (how often the first human agent held the required skill); (ii) the **required-skill correction rate** (% of tickets where `Required Skill` changes mid-lifecycle, as in INC-1001's App-CRM  Database-SQL switch). The second points at intake/categorization quality rather than agent assignment.

**d) Overloaded vs. underutilized agents.** Scatter-plot agents on utilization (x) vs. SLA contribution (y), sized by volume. Agents simultaneously high-utilization *and* high-breach are bottlenecks; high-volume/low-utilization agents with matching skills are rebalancing targets. A workload-balance index (e.g., standard deviation of utilization within a skill pool) quantifies the unevenness management suspects.

**e) SLA breach attribution.** Segment breached P2/P3 tickets and overlay them on the performance-annotated process map to locate the breach "hotspots" (usually queue before L2/L3 work). Then test association strength: breach rate for skill-matched first assignments vs. mismatched; breach rate vs. number of handovers. Use a logistic regression (breach ~ skill mismatch + handovers + assignment-to-overloaded-agent + priority + category) to isolate each factor's contribution while controlling for ticket mix — this prevents misleading conclusions like "Agent X causes breaches" when Agent X simply receives all the hard tickets.

## 3. Root Cause Analysis for Assignment Inefficiencies

For each plausible root cause, I define the **evidence test** in the log:

| Hypothesized Root Cause | Evidence Test in Event Log |
|---|---|
| **Round-robin ignores skill/workload** | Low skill-match rate at first assignment; queue forming at busy agents while equally skilled agents idle (high queue time + low pool utilization) |
| **Stale/incomplete skill profiles** | Data-derived proficiency diverges from documented skills; tickets reassigned *away* from agents documented as skilled, or successfully resolved by agents *without* the documented skill |
| **Poor initial categorization / skill identification** | High required-skill correction rate; correction rate concentrated in specific categories or channels (e.g., web-portal free text) |
| **No real-time workload visibility for dispatchers** | Assignment timestamps immediately followed by long queue times at the chosen agent; dispatch-time workload predicts wait |
| **L1 under-empowerment (training/knowledge gaps)** | Categories with high escalation rate *despite* high historical L1 success rate — i.e., the same ticket type sometimes resolves at L1, sometimes escalates, depending on agent |
| **Misaligned incentives** | L1 escalation spikes near end-of-shift or when handle-time pressure is highest (time-stamp pattern analysis) |

**Variant analysis:** Partition cases into "happy path" variants (e.g., `Create  Assign  Work  Resolve`, single agent) vs. problematic variants (multiple reassignments/escalations). Use discriminative pattern mining to find which attribute combinations (category × channel × priority × time-of-day × initial agent) are statistically over-represented in bad variants. This turns "some tickets bounce a lot" into "Web-portal Software-App tickets created outside business hours have a 4× reassignment risk" (illustrative).

**Decision mining:** At the process decision point "resolve at L1 vs. escalate," train a decision tree on case attributes available *at that moment* (category, priority, channel, description keywords, agent, current workload). The resulting rules make the implicit policy explicit — e.g., discovering that "Network + P2  escalate in 92% of cases" regardless of complexity. Rules that are near-deterministic *and* where escalation is usually justified are candidates for direct routing (skip L1 entirely). Rules with high variance across agents indicate training/knowledge inconsistency rather than ticket difficulty.

## 4. Data-Driven Resource Assignment Strategies

### Strategy 1 — Skill-Based Routing with Data-Derived Proficiency Weighting

- **Issue addressed:** Skill mismatches and "needs different skill" reassignments; misuse of specialists.
- **Leverages:** Skill-match analysis, the skill–resource matrix, and role discovery (Section 1.3). Proficiency scores come from observed history (success rate + median duration per agent-skill), not self-declaration.
- **Mechanism:** At assignment, score eligible agents: `Score = ·(skill match) × ·(proficiency) × ·(tier appropriateness)`. Tier appropriateness penalizes routing L1-resolvable work to L2/L3 (protects specialists). Route to the lowest appropriate tier whose pool contains a match.
- **Data required:** Validated skill taxonomy, reliable required-skill field at intake (see Strategy 3), rolling proficiency scores refreshed monthly from the log.
- **Expected benefits:** Fewer reassignments (target: 40–60%), shorter time-to-right-agent, reduced specialist leakage, improved first-assignment SLA outcomes.

### Strategy 2 — Workload- and Availability-Aware Assignment

- **Issue addressed:** Uneven workload, queue delays, "assigned but untouched" tickets at busy agents.
- **Leverages:** Utilization and queue-time analysis, arrival-pattern heatmaps per skill, resource calendars.
- **Mechanism:** Replace pure round-robin with **minimum predicted start time** routing: assign to the agent (among skill-eligible) with the lowest `current backlog + estimated processing times`, i.e., the one who will actually *start* soonest — not the one next in rotation. Include a fairness floor/ceiling so load stays balanced over the week.
- **Data required:** Real-time agent WIP and availability status, per-type processing time estimates (from the log), shift calendars.
- **Expected benefits:** Lower queue times (the dominant SLA-breach driver), compressed utilization spread across agents, better peak-period performance.

### Strategy 3 — Predictive Triage and Direct-to-Specialist Routing at Intake

- **Issue addressed:** Wrong initial categorization (INC-1001), inevitable escalations consuming L1 touches (INC-1002), long time-to-right-agent.
- **Leverages:** Decision-mining rules and discriminative variant analysis showing which ticket types predictably escalate; historical mapping from intake attributes  *true* required skill and resolving tier.
- **Mechanism:** An ML classifier at ticket creation predicts (i) true required skill(s), (ii) likely resolving tier, (iii) complexity/duration. Low-confidence or "L1-resolvable" predictions go to L1 as normal; high-confidence "will need L2 Firewall" predictions route **directly to the correct L2 pool with L1 bypass**, with guardrails (e.g., P1 always dual-notified; L1 can still grab if a specialist queue is long).
- **Data required:** Ticket descriptions (NLP features), structured attributes, historical outcomes (actual resolving skill/tier/duration) as labels.
- **Expected benefits:** Eliminated L1 handling on predicted escalations (each avoided handover saves its measured reassignment delay), higher effective FCR, corrected categorization feeding Strategy 1.

### Strategy 4 — Data-Driven Shift-Left: L1 Empowerment and Escalation Criteria Refinement

- **Issue addressed:** Excessive L1 escalations; specialists consumed by L1-able work.
- **Leverages:** The gap analysis between *actual* escalation rates and *achievable* L1 resolution rates per category (categories where some L1 agents succeed but most escalate = knowledge gap, not complexity); role discovery identifying high-performing L1 agents as playbook sources.
- **Mechanism:** Mine the activity sequences and resolution notes of successful L1 resolutions per category; codify them into guided scripts/knowledge articles; make escalation conditional on completing a category-specific checklist (enforced in the tool, logged as an activity). Set FCR targets per category based on the *best observed* L1 cohort performance, not gut feel.
- **Data required:** Resolution activity detail/notes, per-category L1 success distributions.
- **Expected benefits:** FCR increase in targeted categories (e.g., closing half the gap between median and best-quartile agents), freed L2/L3 capacity for genuinely complex work.

### Strategy 5 — Dynamic Capacity Management and Cross-Skilling

- **Issue addressed:** Time-of-day skill bottlenecks, single-points-of-failure skills, chronic demand/supply mismatch.
- **Leverages:** Arrival heatmaps per skill vs. calendar-aware coverage; bus-factor analysis.
- **Mechanism:** (i) Adjust shift schedules to demand curves per skill; (ii) cross-train agents in adjacent skills identified from the working-together network (agents already near a skill boundary train fastest); (iii) create an overflow protocol — when a skill queue exceeds a threshold, pre-authorized agents from adjacent pools (e.g., upskilled L1s for L2 overflow, or L2s absorbing L1 phone overflow) are temporarily reallocated.
- **Data required:** Demand forecasts per skill (from arrival history), training records, real-time queue monitoring.
- **Expected benefits:** Reduced peak queue times, resilience to absence/attrition, smoother SLA compliance across the day.

## 5. Simulation, Implementation, and Monitoring

### 5.1 Simulation-Based Evaluation (Before Implementation)

Build a **discrete-event simulation** of the incident process with parameters extracted directly from the event log — this is what distinguishes evidence-based simulation from assumption-based modeling:

- **Parameters from the log:** inter-arrival distributions per priority/category/channel (including time-of-day seasonality); processing-time distributions per activity × skill (log-normal/Erlang fits, not averages); resource calendars; escalation and reassignment probabilities per category; queue discipline.
- **Baseline validation:** Run the as-is model and compare simulated vs. observed KPIs (median cycle time, queue times, utilization, SLA rate). Require close agreement (e.g., within ±5–10%) before trusting the model.
- **To-be scenarios:** (S1) replace round-robin with skill-scored routing; (S2) add min-predicted-start-time logic; (S3) direct routing at the classifier's expected accuracy (run at 70%/80%/90% to test robustness); (S4) increase FCR per category toward best-quartile levels; (S5) add cross-trained capacity and revised shifts.
- **Sensitivity analysis:** Stress-test demand +20%, loss of one scarce-skill specialist, and delayed proficiency ramp-up. This reveals which strategies are robust vs. fragile.
- **Outputs compared:** cycle-time distribution, SLA breach rate by priority, per-skill utilization and queue time, handovers per ticket, and cost per ticket.

### 5.2 Implementation Plan

1. **Phase 0 (weeks 1–4):** Fix data foundations — skill taxonomy cleanup, enforce START/COMPLETE logging, connect live event feed to the process mining tool.
2. **Phase 1 (quick wins, months 1–2):** Strategy 2 (workload-aware dispatch) and escalation checklists for the top-3 over-escalated categories — both low-risk, no ML dependency.
3. **Phase 2 (months 2–4):** Strategy 1 skill-based routing, piloted on one skill domain (e.g., Network) with an A/B split against round-robin; validate proficiency scores with team leads.
4. **Phase 3 (months 4–6):** Strategy 3 predictive triage behind a human-in-the-loop (classifier *recommends*, dispatcher confirms) until accuracy is proven, then automate high-confidence cases. Strategy 5 staffing changes follow the simulation's shift recommendations.
- **Guardrails:** communicate metrics as *system* diagnostics, not individual scorecards initially (to avoid gaming, e.g., cherry-picking easy tickets); monitor for side effects like L1 agents inflating resolution notes.

### 5.3 Post-Implementation Monitoring with Process Mining Dashboards

Continuous monitoring on the live event stream, with the as-is year as the baseline benchmark:

| KPI | Definition | Cadence / Alert |
|---|---|---|
| SLA compliance by priority | % within SLA, vs. target | Daily; alert on 3-day negative trend |
| First-assignment skill-match rate | % first assignments with required skill present | Weekly; alert < threshold |
| FCR rate (L1), per category | Closed at L1, no escalation | Weekly per category |
| Escalation & reassignment rates | Per ticket, per agent, per category | Weekly; flag agent outliers (statistical, not anecdotal) |
| Avg handovers per ticket | Direct proxy for routing quality | Weekly |
| Queue time per skill/tier | Assign  Work Start | Real-time; threshold alerts trigger overflow protocol (Strategy 5) |
| Utilization & balance index | Per agent and per skill pool; std-dev of utilization | Weekly; watch for both overload (>85%) and gaming (<40%) |
| Specialist leakage hours | L2/L3 time on historically L1-resolvable tickets | Monthly, with cost figure |
| Predictive routing accuracy | Predicted vs. actual resolving skill/tier (model drift) | Monthly; retrain trigger |
| Workload-balance index | Utilization spread within pools | Weekly |

**Process views to keep live:** (1) performance-annotated process map (mean waiting times on edges, refreshed daily); (2) handover social network refreshed weekly to detect re-emerging ping-pong patterns; (3) variant explorer showing top variants by volume and by SLA breach contribution; (4) bottleneck heatmap (activity × skill × hour-of-day); (5) conformance dashboard measuring adherence to the *new* routing policy — with the crucial nuance that deviations are reviewed monthly to distinguish policy violations from intelligent human overrides, which feed back as rule refinements.

**Continuous improvement loop:** monthly process-mining review (operations + team leads)  recalibrate proficiency scores and the triage classifier  adjust routing weights and thresholds  re-simulate major changes before rollout. This closes the loop: the assignment logic stops being a static set of rules and becomes a system that is continuously measured, simulated, and tuned against SLA outcomes.

**Bottom line:** The event log almost certainly already contains the evidence for TechSolve's core problems — low first-assignment skill-match rates, queue-time concentration in scarce skills, and a measurable delay tax per reassignment. The fastest path to impact is: **(1)** workload-aware dispatch and escalation checklists as quick wins, **(2)** skill-based routing with data-derived proficiency as the structural fix, and **(3)** predictive triage and dynamic capacity as the strategic layer — each validated in simulation first and governed afterward by a live process-mining monitoring loop rather than periodic anecdote-driven reviews.
