## Process overview

The process handles a customer request from initial receipt through validation, feasibility or operational checks, approval, invoicing, and customer confirmation. It has two primary routes:

- **Standard request path:** Performs routine validation and parallel credit and inventory checks.
- **Custom request path:** Assesses whether the requested customization is feasible and, if so, prepares a quotation.

Both successful routes eventually converge at the approval decision. Once the request is approved—or approval is determined not to be necessary—the process generates the final invoice, sends confirmation to the customer, and ends.

---

## Step-by-step explanation

### 1. Start Event

The process begins when a customer request is received or otherwise enters the organization’s workflow.

---

### 2. Task A: Receive Customer Request

This task records and accepts the customer’s request. It may include capturing customer details, requested products or services, quantities, delivery expectations, and any customization requirements.

The request is then classified by the first gateway.

---

### 3. XOR Gateway: Check Request Type

This is an **exclusive-choice gateway**, meaning exactly one route is selected based on the request type:

- **Standard request**
- **Custom request**

The paths are mutually exclusive at this point, although they later converge.

---

## Standard request path

### 4. Task B1: Perform Standard Validation

For a standard request, the organization performs routine checks such as:

- Confirming that the request is complete
- Verifying customer and order information
- Checking that the requested product or service is supported
- Confirming standard terms, quantities, and requirements

If validation fails, the representation does not explicitly show an exception path. In a complete BPMN model, a validation failure route would normally lead to correction, rejection, or a request for additional information.

---

### 5. AND Gateway: Run Parallel Checks

After standard validation, the process splits into parallel work. This is an **AND gateway**, which means both branches must be executed:

- **Task C1: Credit Check**
- **Task C2: Inventory Check**

The checks may be performed independently and at the same time.

#### Task C1: Credit Check

This determines whether the customer has sufficient credit standing or payment eligibility for the request. It could include reviewing credit limits, payment history, account status, or financial risk.

#### Task C2: Inventory Check

This verifies whether the requested goods or resources are available, or whether sufficient capacity exists to fulfill the request.

---

### 6. Parallel Join: All Parallel Checks Completed

The AND join waits until both the credit check and inventory check have finished. Only then can the process continue.

This join is important because the delivery date should not be calculated until all required standard checks are available.

---

### 7. Task D: Calculate Delivery Date

Using the results of validation, inventory availability, and possibly credit status, the organization calculates or confirms the expected delivery date.

This may involve considering:

- Available stock
- Production or preparation time
- Shipping time
- Customer requirements
- Any restrictions identified during validation

The standard path then proceeds toward the common approval decision.

---

## Custom request path

### 8. Task B2: Perform Custom Feasibility Analysis

For a custom request, routine validation is not sufficient. The organization evaluates whether it can deliver the requested customization.

The analysis may consider:

- Technical feasibility
- Required materials or resources
- Production complexity
- Delivery constraints
- Cost implications
- Regulatory or operational restrictions

---

### 9. XOR Gateway: Is Customization Feasible?

This is another exclusive-choice gateway with two possible outcomes.

#### If customization is not feasible

The process follows:

**Task E2: Send Rejection Notice  End Event**

The customer is informed that the requested customization cannot be provided, and the process terminates. This route does not continue to approval, invoicing, or confirmation because no fulfillable request remains.

#### If customization is feasible

The process continues to:

**Task E1: Prepare Custom Quotation**

The organization prepares a quotation reflecting the custom requirements. This may include:

- Customized pricing
- Additional fees
- Estimated delivery time
- Special terms and conditions
- Scope and assumptions
- Validity period of the quotation

The custom path then joins the common downstream flow.

---

## Convergence of the standard and custom paths

After the standard path completes Task D, or the feasible custom path completes Task E1, both routes converge conceptually at the next decision:

### 10. XOR Gateway: Is Approval Needed?

This gateway determines whether managerial or other formal approval is required.

Approval may be required because of factors such as:

- A high-value transaction
- A discount beyond normal limits
- Credit risk
- A nonstandard delivery commitment
- A custom quotation
- Exception terms or unusual commercial conditions
- Internal policy thresholds

The decision is exclusive:

- **Yes, approval is required**
- **No, approval is not required**

In a formal BPMN model, the standard and custom paths should use a merge or converging gateway before this decision so that the process has a clear common point.

---

## Approval path

### 11. Task F: Obtain Manager Approval

If approval is needed, the request or quotation is sent to the appropriate manager or authorized decision-maker.

The manager reviews the relevant information, which may include:

- Customer and request details
- Credit and inventory results
- Delivery date
- Custom feasibility findings
- Pricing and margin
- Risks and exceptions

The manager then either grants or denies approval.

---

### 12. XOR Gateway: Is Approval Granted?

This gateway again represents an exclusive decision.

#### If approval is granted

The process proceeds directly to:

**Task G: Generate Final Invoice**

The organization has authorization to finalize the commercial transaction.

#### If approval is denied

The process proceeds to:

**Task H: Re-evaluate Conditions**

Approval denial does not necessarily mean the process must terminate. Instead, the request may be changed so that it can potentially satisfy the approval criteria.

---

## Rework and loop-back behavior

### 13. Task H: Re-evaluate Conditions

This task analyzes why approval was denied and determines what should change. Possible rework includes:

- Revising the price or discount
- Changing the delivery commitment
- Modifying the custom scope
- Adjusting quantities
- Rechecking credit or payment terms
- Finding alternative inventory or fulfillment options
- Removing or mitigating a business risk

The representation shows a loop back to different tasks depending on the request type:

- **Custom request:** Loop back to **Task E1, Prepare Custom Quotation**
- **Standard request:** Loop back to **Task D, Calculate Delivery Date**

This means the reworked conditions are reflected in the relevant downstream deliverable.

For a custom request, the quotation is revised. For a standard request, the delivery commitment or related fulfillment calculation is revisited.

After rework, the process should return to the approval evaluation. In practice, the revised quotation or conditions would normally pass again through the “Is Approval Needed?” decision and, if necessary, another manager approval cycle.

The model should explicitly show this return path if multiple approval attempts are possible. Otherwise, the loop is conceptually implied but not fully represented.

---

## No-approval path

If the “Is Approval Needed?” gateway determines that no approval is required, the process bypasses Task F and proceeds directly to:

**Task G: Generate Final Invoice**

This applies when the request falls within normal policy limits and no exception or managerial authorization is necessary.

---

## 14. Task G: Generate Final Invoice

This task creates the final billing document based on the approved or otherwise authorized request.

For a standard request, the invoice may reflect standard pricing and delivery terms. For a custom request, it should reflect the approved quotation, custom scope, pricing, and any special conditions.

The invoice should only be generated after:

- The relevant request path has completed successfully
- Any required approval has been granted
- Any required rework has been resolved

---

## 15. Task I: Send Confirmation to Customer

After the final invoice is generated, the organization sends confirmation to the customer. This communication may include:

- Confirmation that the request has been accepted
- Final pricing or invoice details
- Delivery date or estimated schedule
- Custom terms, if applicable
- Next steps
- Payment or fulfillment instructions

Both standard and custom successful paths converge before this task.

---

### 16. End Event

The process ends after the customer confirmation is sent.

There is also an earlier end event for infeasible custom requests, because those requests are rejected and do not proceed to invoicing.

---

## Meaning of the gateways

| Gateway | Type | Purpose |
|---|---|---|
| Check Request Type | XOR | Selects either the standard or custom process path |
| Run Parallel Checks | AND split | Starts credit and inventory checks concurrently |
| All Parallel Checks Completed | AND join | Waits for both standard checks to finish |
| Is Customization Feasible? | XOR | Determines whether the custom request can be fulfilled |
| Is Approval Needed? | XOR | Determines whether managerial approval is required |
| Is Approval Granted? | XOR | Determines whether the manager authorizes the request or sends it to rework |

---

## Summary of the main paths

### Standard request

```text
Receive request
 Standard validation
 Credit and inventory checks in parallel
 Wait for both checks
 Calculate delivery date
 Determine whether approval is needed
 Obtain approval if necessary
 Rework and recalculate delivery conditions if approval is denied
 Generate invoice
 Send customer confirmation
 End
```

### Feasible custom request

```text
Receive request
 Custom feasibility analysis
 If feasible, prepare quotation
 Determine whether approval is needed
 Obtain approval if necessary
 Revise quotation if approval is denied
 Generate invoice
 Send customer confirmation
 End
```

### Infeasible custom request

```text
Receive request
 Custom feasibility analysis
 If infeasible, send rejection notice
 End
```

Overall, the process separates routine operational handling from more complex custom-request handling, uses parallelism to speed up standard checks, routes exceptional cases through approval, and provides a rework loop when approval is initially denied.
